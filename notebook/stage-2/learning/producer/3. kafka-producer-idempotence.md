# Kafka Producer: The Idempotent Producer

*Producer note 3 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read producer note 2 (acks) and Kafka note 3 (replication) first. `enable.idempotence` removes duplicates caused by producer retries within a session. It does not deduplicate across application-level retries or consumer reprocessing. This note explains the mechanism, its exact limits, and which layer of EventPulse absorbs each kind of duplicate. It supports Step 1 (producer settings), Step 5 (retries and 503s), Step 3 (at-least-once and `ON CONFLICT`) and Step 7 (audit checks D and G).*

**What was run.** **[observed]** means seen on this repo's cluster (a scratch topic, deleted afterwards), in this repo's source or in the installed client's source. No broker was stopped and no fault was injected, so **the deduplication itself was not triggered here**: the evidence is the metadata the broker stores and the configuration rules, not a duplicate being suppressed. **[reasoning]** marks standard Kafka behavior that was not observed here. A fault-injection lab is described in section 17 for later.

## 1. TL;DR

- Producers **retry** when they do not hear back (timeout, connection reset, leader change). A retry of a batch that **did** reach the broker, whose response was lost, writes that batch **twice**. This is the classic producer-side duplicate.
- The **idempotent producer** (`enable.idempotence=true`) prevents it. The broker gives each producer a **producer id (PID)** and an **epoch**. The producer numbers every record it sends to each partition with a **sequence number**. The leader remembers the latest sequence numbers per `(PID, partition)`, so a repeated batch is recognized and **acknowledged without being appended again**.
- It also **preserves order across retries**, as long as at most **5** batches are in flight per connection.
- **Scope is narrow and exact:** one producer **session** (one PID), one **partition** at a time. It protects against duplicates caused by **the client library's own automatic retries**.
- It does **not** protect against:
  - **Application-level retries**: an HTTP client that gets a 503 and posts the same event again causes a **new** `send()` with a **new** sequence, so the event is appended twice.
  - **Producer restarts** (a new process gets a new PID).
  - **Several producer instances** writing the same event.
  - **Consumer reprocessing** (a different layer, at-least-once, note 2 of the Kafka series).
- Requirements: **`acks=all`**, retries enabled, at most **5** in-flight requests per connection **[observed config errors]**. Cost: almost nothing.
- So in EventPulse duplicates are still possible and the **sink's `ON CONFLICT (event_id) DO NOTHING`** is what makes the system correct. Idempotence is a cheap first line that removes one class of them.

> **One-line version:** *The idempotent producer makes the library's own retries safe by numbering every record, so the broker can say "I already have that" instead of appending it twice.*

## 2. The mental model

A bank teller who writes a **running sequence number** on every deposit slip you hand in for one account.

| Bank | Kafka |
| --- | --- |
| Your customer ID, issued once per visit | **Producer id (PID)** (plus an **epoch**) |
| A new number on every slip: 1, 2, 3, ... for this account | **Sequence number**, per partition |
| The teller keeps your last few slip numbers | The leader keeps the last **5** batches' sequences per `(PID, partition)` |
| You hand in slip 7 again because you did not hear "done" | A **retry** after a lost response |
| The teller sees "7 is already booked" and says "done" without booking again | **Duplicate detected**: success returned, nothing appended |
| You skip from slip 7 to slip 9 | **Out of order sequence**: error |
| You come back tomorrow and the teller gives you a **new** customer ID | New PID after a restart: old numbers mean nothing |
| A different person hands in the same deposit under their own ID | **Not deduplicated**: a different PID |

The bank deduplicates **slips from one customer visit**. It has no idea that two different slips mean the same deposit.

## 3. The problem

An `acks=all` produce, with a lost response:

```
 producer                                   leader (and followers)
    | --- batch B (records r1..r500) ------->  appended at offsets 4000..4499, replicated to ISR
    |                                          leader sends the response ...
    | <-- X  response lost (network blip, leader crash right after replicating, timeout)
    |
    |  (no answer within the request timeout)
    | --- batch B again (retry) ------------->  WITHOUT idempotence: appended AGAIN at 4500..4999
    | <-------- success                         the log now holds r1..r500 twice
```

Which situations trigger it:

- **Timeout** on a slow response (`REQUEST_TIMED_OUT`): the data may or may not have been written (Kafka note 3, section 10: "maybe appended").
- **Connection reset** or network partition between the request and the response.
- **A leader change** while a batch was in flight and replicated.
- **`NOT_ENOUGH_REPLICAS_AFTER_APPEND`**: the record was appended before the ISR dropped.

Because the client cannot tell "not written" from "written but response lost", **retrying is the only safe-looking option**. Without idempotence, "retry" means "maybe duplicate". With it, "retry" means "safe".

A second, quieter problem: with several batches in flight, a failed batch is retried **after** a later one succeeded, so the **order within a partition changes** (Kafka note 3, section 9.2). Idempotence fixes that too (section 7).

## 4. The mechanism

### 4.1 The pieces

1. **`InitProducerId`.** When the producer connects with idempotence on, it asks the cluster for an identity: a **PID** (a 64-bit number) and an **epoch** (a small counter). The broker records them.
2. **Sequence numbers.** For each partition it writes to, the producer keeps a counter that starts at 0 and counts **records** (not batches). A batch carries `baseSequence` (the sequence of its first record) and the number of records, so `lastSequence = baseSequence + count - 1`.
3. **The leader checks every produced batch** against what it has stored for `(PID, partition)`.
4. **The sequence state is part of the partition's data.** It is stored with the log and replicated, so a **new leader** knows the same state after a failover **[reasoning]**. That is why the dedup survives leader changes.

### 4.2 The check, case by case

For a producer `P` and a partition, the leader remembers `lastSeq` (the last accepted record's sequence, plus the metadata of the last 5 batches). A batch arrives with `baseSequence = b` and count `n`:

| Situation | Leader's decision |
| --- | --- |
| `b == lastSeq + 1` | **Accept**: append, advance `lastSeq` |
| `b + n - 1 <= lastSeq` and the batch matches one of the last 5 remembered | **Duplicate**: return success with the original offset, **append nothing** |
| `b > lastSeq + 1` (a gap) | **Reject** with `OUT_OF_ORDER_SEQUENCE_NUMBER`: something earlier is missing |
| Epoch lower than the broker's known epoch for this PID | **Reject** (producer fenced): a newer instance exists |
| Unknown PID (state expired) | The broker cannot validate; handled as a new sequence or an error depending on the case |

The consequence for retries: the client resends the **same** `(PID, baseSequence, count)`, so the leader can recognize it. A batch is never "renumbered" on retry, which is what makes the check work.

### 4.3 Why "last 5 batches"

The broker keeps the metadata of the **last 5** batches per `(PID, partition)`. That is why `max.in.flight.requests.per.connection` **must be at most 5** with idempotence: with up to 5 batches outstanding, a retry of any one of them is guaranteed to still be remembered. The client refuses a higher value (section 11, observed).

## 5. What the broker does

Putting 4.2 into a timeline, the earlier lost-response example now becomes:

```
 producer                                   leader
    | --- batch B (PID 1003, seq 4000..4499) ->  accepted: seq == lastSeq+1. appended, replicated
    | <-- X  response lost
    | --- batch B again (PID 1003, seq 4000..4499) ->  seq <= lastSeq and matches remembered batch:
    |                                                   DUPLICATE. nothing appended.
    | <-------- success (offset 4000)                   the log holds r1..r500 once
```

And for **ordering** with two batches in flight:

```
 producer sends B1 (seq 0..99) and B2 (seq 100..199) at once
   B1 fails in transit (timeout); B2 arrives first
   leader: expected next seq is 0, got 100  ->  OUT_OF_ORDER_SEQUENCE_NUMBER for B2 (rejected, not appended)
   producer retries B1, then B2 (in order)  ->  accepted in order. The log is 0..199 in the right order.
```

Without idempotence, B2 would have been appended first, and B1 appended on its retry, reordering the records.

## 6. Visible on this cluster

The sequence metadata is plainly visible in the log **[observed]**. From `kafka-dump-log.sh` of a partition written by the Java perf-test client (idempotence is on by default there):

```
baseOffset: 0   lastOffset: 3   count: 4   baseSequence: 0   lastSequence: 3   producerId: 1002 producerEpoch: 0
baseOffset: 4   lastOffset: 19  count: 16  baseSequence: 0   lastSequence: 15  producerId: 1003 producerEpoch: 0
baseOffset: 20  lastOffset: 35  count: 16  baseSequence: 16  lastSequence: 31  producerId: 1003 producerEpoch: 0
baseOffset: 36  lastOffset: 51  count: 16  baseSequence: 32  lastSequence: 47  producerId: 1003 producerEpoch: 0
```

and, from a 50,000-record run: `count: 186  baseSequence: 0  lastSequence: 185` for the first batch of a producer.

What it shows:

- **Each producer session has its own PID** (1002 and 1003 are two different producers writing to the same partition; the first four records came from a console producer, the rest from a perf-test producer).
- **Sequences are per record and continuous within a PID**: 0..15, then 16..31, then 32..47. Each next `baseSequence` is exactly the previous `lastSequence + 1`.
- **Epoch 0** because each producer was new and nothing bumped it.
- The **PID is not the offset** and not related to partition numbering: offsets belong to the partition, sequences belong to the producer.

Also visible in the client source **[observed]**: the Node client's compatibility layer maps the producer option `idempotent` to librdkafka's `enable.idempotence`, and `maxInFlightRequests` to `max.in.flight`; EventPulse sets `idempotent` from `KAFKA_IDEMPOTENT` (default `true`) in `producer.service.ts`.

## 7. Ordering

With idempotence and `max.in.flight.requests.per.connection <= 5`:

- **Retries never reorder records within a partition**, because the broker rejects any batch whose sequence is not next, and the client resends in order.
- **Different partitions are unaffected**: order is per partition (Kafka note 1, section 9).

Without idempotence, the choices were: set `max.in.flight=1` (safe order, low throughput) or accept possible reordering. Idempotence gives **both** order and pipelining.

EventPulse's own batcher has a separate setting, `BATCH_MAX_IN_FLIGHT` (default **1**), which limits **`send()` calls** in flight at the application layer **[observed in `config.ts`]**. That is a different layer from the client's per-connection limit: even if the client could pipeline 5 batches, the batcher only starts the next `send()` after the previous one settles. Two batches carrying the same key could complete out of order only if the batcher's value is above 1 (producer note 5).

## 8. Scope

What the guarantee covers, precisely:

| Dimension | Covered? |
| --- | --- |
| Library-internal retries of a batch (timeout, reset, leader change) | **Yes** |
| Ordering of records within a partition across those retries | **Yes** (up to 5 in flight) |
| Exactly one copy **in a partition** from a given producer session | **Yes** |
| Across **partitions** (atomicity of one `send()` over several partitions) | **No**: each partition is independent |
| Across a **producer restart** (new PID) | **No** |
| Across **producer instances** | **No** |
| **Application-level** retries (a new `send()` of the same logical event) | **No** |
| **Consumer** reprocessing | **No** (that is delivery semantics on the read side) |
| Data in the producer's memory when the process dies | **No** (nothing was sent) |

One more limit: the broker only keeps **producer state** for a while. If a producer is idle for longer than the broker's producer-id expiration (a day by default **[reasoning]**), the state is dropped; a very late retry from that session would no longer be recognized, and the producer handles the "unknown producer" situation by getting a fresh identity. For a long-running API this does not matter; it is why "idempotent" is described as per **session**.

## 9. What it does not remove

Walk through the places duplicates can still be created in EventPulse.

**A. The HTTP client retries.** The client got a 503 (or lost the response) and posts the **same event** again. At the API this is a new request: the batcher creates a new message, the producer makes a **new batch with new sequence numbers**, and the broker has no reason to connect it to the first attempt. If the first attempt was actually written (ambiguous failure, see D), the log now has the event **twice**. The API contract tells clients to retry with the **same `event_id`** precisely so the sink can recognize it.

**B. The batcher's own abandonment.** The batcher gives up on a send after `KAFKA_SEND_TIMEOUT_MS` (5 s) and rejects its waiters, while the client library keeps retrying that batch in the background until its own delivery timeout (30 s) **[observed in `config.ts` and the batcher's header comment]**. The library's later success writes the batch (once, deduplicated against its own retries). The waiting HTTP requests have already been answered with 503, so their clients retry (A): **duplicates**, and a record counted as "written but not acknowledged" (audit check D). The design note in the batcher says exactly this ("the send may still complete later, so a client retry can create a duplicate"); producer note 5 discusses the trade-off.

**C. Restart of the API.** A new process connects and gets a new PID. Requests that were in flight to the old process were never answered (no 202), so the clients retry: if the first attempt was written, duplicate.

**D. Ambiguous outcomes.** Timeouts and `NOT_ENOUGH_REPLICAS_AFTER_APPEND` leave "maybe written" (producer note 2 and Kafka note 3 section 10). Whatever the producer does next, the **client** of the HTTP API cannot tell either.

**E. Multiple API instances.** Two instances accept the same event (a load balancer retry): two PIDs, two appends.

**F. Consumer side.** A crash between the DB commit and the offset commit re-reads records (Kafka note 2, section 10). That is not a producer duplicate at all, but it produces the same visible effect: the same `event_id` seen twice by the sink.

## 10. Layers

Every duplicate source above has to be absorbed by **some layer**. In EventPulse:

| Duplicate source | Absorbed by | How |
| --- | --- | --- |
| Library retry after a lost response, timeout, leader change | **Idempotent producer** | Sequence check at the leader |
| Reordering by retries | **Idempotent producer** (<= 5 in flight) | Out-of-order rejection and in-order resend |
| HTTP client retry (A), API restart (C), second instance (E), ambiguous failures (B, D) | **Sink** | `INSERT ... ON CONFLICT (event_id) DO NOTHING`, with `attempted - inserted` counted as duplicates |
| Consumer reprocessing (F) | **Sink** | Same |
| Duplicates within a Kafka transaction boundary | (not used) | Would need transactions (section 13) |

The design principle: **make the final write idempotent** (here, a primary key on `event_id`) and treat everything upstream as a cheap optimization that reduces how often the final layer has to work. Idempotence in the producer is nice to have; the sink's idempotence is what is **required**.

## 11. Configuration

| Rule | Evidence |
| --- | --- |
| `acks` must be `all` | **[observed]** Java client: `ConfigException: Must set acks to all in order to use the idempotent producer. Otherwise we cannot guarantee idempotence.` |
| `max.in.flight.requests.per.connection` must be at most 5 | **[observed]** `ConfigException: To use the idempotent producer, max.in.flight.requests.per.connection must be set to at most 5. Current value is 6.` |
| `retries` must not be 0 | **[observed]** `ConfigException: Must set retries to non-zero when using the idempotent producer.` |
| `delivery.timeout.ms >= linger.ms + request.timeout.ms` (a general rule, relevant when tuning retries) | **[observed]** `delivery.timeout.ms should be equal to or larger than linger.ms + request.timeout.ms` |
| EventPulse: `KAFKA_IDEMPOTENT=true` with `KAFKA_ACKS` other than `-1` fails at startup with a message telling you to set `KAFKA_IDEMPOTENT=false` | **[observed in `config.ts`]** |
| The client maps `idempotent` to `enable.idempotence` and `maxInFlightRequests` to `max.in.flight` | **[observed in the library source]** |
| Idempotence is the **default** in recent Java clients when you do not set conflicting options | **[reasoning]**; observed: `acks=1` alone ran fine, i.e. the Java client disabled it silently instead of failing |

Practical notes:

- **Set it explicitly** in EventPulse (it is: `KAFKA_IDEMPOTENT`) and record it in `/debug/stats` `config`, rather than depending on a library default that changed between versions.
- To run a K2-style experiment with `acks=1` or `acks=0`, set `KAFKA_IDEMPOTENT=false` first (producer note 2, section 9).
- `max.in.flight` is not exposed as an EventPulse env var; the library's default for an idempotent producer is within the limit.

## 12. Cost and failure modes

**Cost.** Negligible:

- An extra round trip at connect (`InitProducerId`).
- A few bytes per batch (PID, epoch, base sequence are already in the batch header, seen in the dump).
- Broker memory for the per-`(PID, partition)` state.
- It forces **`acks=all`**, which is the real latency cost (producer note 2, section 8), but that is the setting EventPulse wants anyway.

**Failure modes you can meet [reasoning]:**

- **`OUT_OF_ORDER_SEQUENCE_NUMBER` / `UNKNOWN_PRODUCER_ID`** that the client cannot resolve: the broker lost the state (expired producer id, a log truncation, an unclean election, data deleted). The producer may have to **bump its epoch** or reinitialize; if it cannot continue safely it raises a **fatal** error.
- **A fatal idempotence error leaves the producer unusable.** In librdkafka the producer must be **recreated**. EventPulse's `ProducerService` already rebuilds its client when it sees the "client is disconnected" state (`ERR__STATE`) **[observed in `producer.service.ts`]**; whether a fatal idempotence error surfaces as that state in this client was not tested, and is worth a fault-injection test.
- **Producer fenced** (`INVALID_PRODUCER_EPOCH`): only for transactional producers or when a newer instance took over the same identity. Not expected in the API.

## 13. Transactions

Idempotence is the foundation of Kafka's **transactions**. Adding a `transactional.id` gives:

- **Atomic writes to several partitions and topics** (all committed or all aborted).
- **A stable identity across restarts** (the transactional id survives; the epoch increases and old instances are fenced).
- **Committing consumer offsets inside the same transaction** (`sendOffsetsToTransaction`), which makes "read from Kafka, write to Kafka" exactly-once.

What it is for: **Kafka-to-Kafka** pipelines. What it does **not** do: make a **Postgres** write exactly-once. EventPulse's sink writes to Postgres, so the practical answer is **at-least-once plus an idempotent write** (`ON CONFLICT`) (Kafka note 2, section 10). Transactions are not used in Stage 2.

## 14. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| `KAFKA_IDEMPOTENT` | **true** (default) | Safe client retries and ordering across retries |
| Requires | `KAFKA_ACKS=-1` | Enforced at startup |
| Where duplicates are finally absorbed | **Sink** (`ON CONFLICT (event_id) DO NOTHING`) | Producer idempotence does not cover HTTP retries, restarts or instances |
| API contract | Clients retry 503s and network errors with the **same `event_id`** | So the sink can recognize them |
| Duplicate visibility | Count them (`attempted - inserted`, audit check G) | Never hide them |
| Transactions | Not used | Postgres sink; at-least-once plus idempotent write |
| `KAFKA_IDEMPOTENT=false` | Experiment-only (needed for `acks` 0 or 1) | Record it with the result |

## 18. Common confusions

1. **"Idempotent producer means exactly-once."** It means no duplicates from the library's own retries, within one session and one partition. That is a small slice of exactly-once.
2. **"It deduplicates my HTTP retries."** No. Each retry is a new `send()` with a new sequence.
3. **"It survives an API restart."** A restart is a new PID: no.
4. **"It guarantees order."** Within a partition, across retries, up to 5 in flight. Not across partitions, not across producers.
5. **"The broker deduplicates by key or by content."** Only by `(PID, partition, sequence)`.
6. **"Sequence numbers count batches."** They count records.
7. **"It works with any `acks`."** It requires `acks=all`.
8. **"It makes `max.in.flight=1` unnecessary for ordering."** Yes for up to 5; the batcher's own in-flight limit is a separate setting.
9. **"I can drop the sink's `ON CONFLICT` if the producer is idempotent."** No. The producer does not cover half of the duplicate sources.
10. **"Duplicates in the audit mean idempotence is broken."** Not necessarily. Duplicates from HTTP retries, ambiguous failures and consumer reprocessing are expected and are reported, not hidden.
11. **"A duplicate means a record was written twice by the client."** Often the **consumer** re-read it, which is a different mechanism.
12. **"Producer id equals producer name."** It is a number assigned by the broker per session, not stable across restarts.

<details>
<summary>Short answers</summary>

1. A retry of a batch that was written but whose response was lost appends it twice. Draw: send, append, response lost, retry, second append (without idempotence).
2. Producer id (PID), epoch, and a per-partition sequence number counting records.
3. Lower and matching a remembered batch: duplicate, acknowledge without appending. Equal to next: accept and append. Greater (a gap): reject as out of order.
4. The broker remembers only the last 5 batches per producer and partition; with at most 5 outstanding, any retried batch is still remembered.
5. `producerId`, `producerEpoch`, `baseSequence`, `lastSequence` (also `count`, `baseOffset`).
6. HTTP-client retries, producer restarts, several producer instances, consumer reprocessing, ambiguous failures followed by an application retry.
7. The sink, by `ON CONFLICT (event_id) DO NOTHING`.
8. A new process asks for a new PID; the broker treats it as a different producer.
9. Without acknowledgement from the whole ISR the producer could believe a record was written when a failover removes it, and retry or resequence incorrectly; the guarantee requires full acknowledgement.
10. The client's limit is unacknowledged requests per connection (at most 5 with idempotence). `BATCH_MAX_IN_FLIGHT` is how many `send()` calls the batcher keeps in flight (default 1).
11. When the broker lost the producer's sequence state (expiry, truncation, unclean election) and the client cannot resume safely. The producer must be recreated.
12. Kafka transactions make Kafka writes atomic. A Postgres write is outside them, so the practical solution is an idempotent write.
13. The batcher answers 503 and abandons the send while the library retries and eventually writes the batch (deduplicated against its own retries). The client then retries over HTTP; the second send has a new sequence, so the event is appended again.

</details>

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| PID | Producer id assigned by the broker for one producer session |
| Producer epoch | Counter that fences older instances of the same identity |
| Sequence number | Per-partition record counter for a PID |
| `baseSequence` / `lastSequence` | First and last sequence of a batch |
| Duplicate sequence | A repeated batch; acknowledged, not appended |
| Out-of-order sequence | A gap; rejected |
| Session | The lifetime of one PID (one producer instance) |
| Application-level retry | A new `send()` of the same logical event |

### Rules

```
idempotence requires:   acks = all,   retries > 0,   max.in.flight <= 5
covers:                 library retries, one session, one partition, order across retries
does NOT cover:         HTTP retries, restarts, other instances, consumer reprocessing
final defense:          INSERT ... ON CONFLICT (event_id) DO NOTHING   (and count the duplicates)
```

### Configuration errors seen

| Setting | Error |
| --- | --- |
| `acks=1` + idempotence | `Must set acks to all in order to use the idempotent producer.` |
| `max.in.flight=6` + idempotence | `max.in.flight.requests.per.connection must be set to at most 5` |
| `retries=0` + idempotence | `Must set retries to non-zero when using the idempotent producer.` |

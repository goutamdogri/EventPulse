# Kafka Producer: Retries and Timeouts

*Producer note 5 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read producer notes 2 (acks) and 3 (idempotence) first. `retries`, `delivery.timeout.ms` and `max.in.flight.requests.per.connection` decide what happens to a record when the cluster misbehaves, and they interact with ordering. This note maps every timer a record meets on its way through EventPulse, shows which ones actually fire in which failure, and points out a mismatch in the current configuration. It supports Step 1 (producer settings), Step 5 (Kafka unavailable: 503, bounded memory) and the broker-failure experiments.*

**What was run.** **[observed]** means seen in this repo's source, in the installed client's source (`@confluentinc/kafka-javascript` 1.11.0), in the Java client's behavior on this cluster (a scratch topic, deleted afterwards), or in Kafka note 3's broker-failure labs. **No broker was stopped for this note** and the **Node client was not put through a failure**, so every statement about what the Node client does **under failure** is **[reasoning]** derived from the observed configuration. The most important of those is flagged in section 9 and should be confirmed with a fault-injection run before you rely on it. Numbers are from one run on a laptop.

## 1. TL;DR

- When a send fails with a **retriable** error (timeout, connection reset, `NOT_LEADER_OR_FOLLOWER`, `NOT_ENOUGH_REPLICAS`, ...), the producer library **retries it itself** after a **backoff**, and keeps doing so until either the **retry count** or the **delivery timeout** (`delivery.timeout.ms`, `message.timeout.ms` in librdkafka) runs out. Only then does your code see an error.
- So the caller usually sees **one** of two things: success, or a **timeout** after the delivery timeout. The underlying reason (not enough replicas, no leader) is mostly hidden (Kafka note 3, section 10.1, observed).
- Retries interact with **ordering** (a retried batch can land behind a later one unless the producer is idempotent and keeps at most 5 batches in flight) and with **duplicates** (a retry of a write that already happened). The idempotent producer removes both for the library's own retries (producer note 3).
- EventPulse has **layers of timers**: the library's retries and delivery timeout, the broker-side ack wait, the batcher's **send timeout (5 s)** and **queue wait limit**, the circuit breaker, the HTTP request, and the clients' own retries. The **shortest one that applies fires first**, and the work underneath it **does not necessarily stop**.
- **Current configuration facts [observed]:** `KAFKA_DELIVERY_TIMEOUT_MS=30000`, `KAFKA_ACK_TIMEOUT_MS=30000`, `KAFKA_SEND_TIMEOUT_MS=5000`, `KAFKA_RETRIES=5` with a backoff of 100 ms growing to at most 1,000 ms. Two consequences, both **[reasoning]** and worth a test:
  1. Because the batcher gives up after **5 s** while the library may keep trying for **30 s**, an abandoned batch can still be written later (a "zombie write"), which turns a 503 into a possible duplicate (section 10).
  2. Because the client retries only **5 times** with sub-second backoffs, it may give up after **a few seconds**, well inside a broker failover (observed **9 to 17 s** in Kafka note 3), so a failover shows up as errors and 503s, not as a transparent delay (section 9).
- Retries across layers **multiply load** exactly when the system is weakest. The breaker, `Retry-After`, bounded queues and client backoff with jitter are the controls.

> **One-line version:** *Every layer retries, every layer has a clock, and the shortest clock decides what the user sees while the longer ones keep working in the background.*

## 2. The mental model

A parcel service with a stack of "give up" rules, from the sender's front desk down to the courier.

| Delivery | Kafka and EventPulse |
| --- | --- |
| The courier retries a closed door a few times with a pause between | Library **retries** with **backoff** |
| "We stop trying after 5 attempts" | `retries` (5 here) |
| "Whatever happens, we stop at 30 days" | `delivery.timeout.ms` / `message.timeout.ms` |
| The courier waits at the depot for the warehouse to confirm receipt | **Request timeout**: how long the broker may wait for replicas |
| The front desk tells the customer "no" after 5 minutes | The batcher's **send timeout** (5 s) |
| The courier **keeps trying** after the desk already said "no" | The library keeps retrying a batch the batcher abandoned |
| The customer comes back and re-sends the same parcel | **Client retry** of the HTTP request |
| A busy depot posts "closed for 5 s" | **Circuit breaker** and `Retry-After` |

The trap in the picture: the customer was told "no" while the courier is still delivering. The parcel can arrive **and** be re-sent.

## 3. The life of one message

From `enqueue()` in the API to the acknowledgement, with the timer that bounds each phase:

```
  HTTP request arrives
        |
  [A] waits in the micro-batcher queue          bounded by  KAFKA_SEND_TIMEOUT_MS (5 s)   (queue expiry)
        |  batch starts
  [B] batch handed to producer.send()
        |
  [C] sits in the client's queue / batch        bounded by  message.timeout.ms (delivery timeout, 30 s)
        |                                       (the whole life of the message inside the client)
  [D] ProduceRequest in flight to the leader    bounded by  socket / request timeouts (30 s each here)
        |     leader waits for the ISR           bounded by  request.timeout.ms ("ack timeout", 30 s)
        |  ---- failure? ---->  retriable?  yes -> wait backoff (100 ms .. 1 s), go back to [C]
        |                                    no  -> fail now
        |                       retries used up (5)?  or delivery timeout passed? -> fail
  [E] acknowledged -> the batcher resolves every waiting request -> 202
        |
        v   at any point, the batcher's SEND timeout (5 s from the start of [B]) can fire first:
            the waiters get 503 and the library's work on that batch is NOT cancelled.
```

Two things to notice:

- The **delivery timeout bounds the message's entire stay in the client** (queue, in-flight and retry waits), not one request.
- The **batcher's timeout is outside the library**. When it fires, the batch is **abandoned by us**, not by the library.

## 4. The settings

How each knob is named and where it is set. The Java name is the reference; "librdkafka" is what the Node client uses; the last column is EventPulse's setting and its value **[observed in `config.ts`, `env.ts`, `producer.service.ts`, `kafka-config/src/client.ts` and the library's source]**.

| Meaning | Java | librdkafka | EventPulse env (default) |
| --- | --- | --- | --- |
| Total time a message may spend in the client, retries included | `delivery.timeout.ms` (120 s **[reasoning]**) | `message.timeout.ms` (300 s per the ADR) | `KAFKA_DELIVERY_TIMEOUT_MS` (**30,000**) |
| How long the broker may wait for the ISR to ack one request | `request.timeout.ms` (30 s **[reasoning]**) | `request.timeout.ms`; the compat option `timeout` maps to it | `KAFKA_ACK_TIMEOUT_MS` (**30,000**) |
| Network request timeout (socket) | (part of `request.timeout.ms`) | `socket.timeout.ms`; the compat option `requestTimeout` maps to it | `KAFKA_REQUEST_TIMEOUT_MS` (**30,000**) |
| Max retries of a failed send | `retries` (2,147,483,647 **[reasoning]**) | `message.send.max.retries` / `retries` | `KAFKA_RETRIES` (**5**): the compat layer sets `retries = retry.retries ?? 5` |
| First backoff between retries | `retry.backoff.ms` (100) | `retry.backoff.ms` | `KAFKA_RETRY_INITIAL_MS` (**100**) |
| Maximum backoff | `retry.backoff.max.ms` | `retry.backoff.max.ms` | `KAFKA_RETRY_MAX_MS` (**1,000**) |
| Unacknowledged requests per connection | `max.in.flight.requests.per.connection` (5) | `max.in.flight` | not exposed (library default; idempotence caps it at 5) |
| How long `send()` blocks on a full buffer or missing metadata | `max.block.ms` (60 s) | (queue-full error returned at once) | n/a |
| Connect timeout | `socket.connection.setup.timeout.ms` | same | `KAFKA_CONNECTION_TIMEOUT_MS` (**3,000**) |
| **Batcher send timeout** (ours) | n/a | n/a | `KAFKA_SEND_TIMEOUT_MS` (**5,000**) |
| **Breaker** (ours) | n/a | n/a | `KAFKA_BREAKER_FAILURES` (**3**), `KAFKA_BREAKER_COOLDOWN_MS` (**5,000**) |

Facts worth stating plainly:

- **The Java-only default of effectively unlimited retries is not what you get here.** The compatibility layer of the Node client sets `retries` to `5` unless you pass `retry.retries`; EventPulse's `KAFKA_RETRIES` default is also `5`, so the effective value is 5 either way **[observed]**.
- **A Java constraint that applies to the Java client only [observed]:** `delivery.timeout.ms` must be at least `linger.ms + request.timeout.ms`, or the producer refuses to start (`ConfigException: delivery.timeout.ms should be equal to or larger than linger.ms + request.timeout.ms`). Whether librdkafka enforces a similar rule was not tested.
- **Retriable and delivery-timeout behavior in the Java client [observed, Kafka note 3, Lab 5 and Lab 7]:** with `delivery.timeout.ms=9000`, a write the broker kept refusing ended **after about 9 s** as `TimeoutException: Expiring 5 record(s) ... 9000 ms has passed since batch creation`. The client never showed the underlying `NOT_ENOUGH_REPLICAS`.

## 5. What is retried

Retriable errors are retried by the library; non-retriable ones fail immediately. EventPulse's own classifier lists the librdkafka codes that mean "Kafka cannot take this write right now" **[observed in `errors.ts`]**, which are the ones that become a **503**:

| Code | Name | Meaning |
| --- | --- | --- |
| -195 | `ERR__TRANSPORT` | Broker connection failure |
| -187 | `ERR__ALL_BROKERS_DOWN` | No broker reachable |
| -192 | `ERR__MSG_TIMED_OUT` | Delivery timeout expired (or retries used up) |
| -196 | `ERR__MSG_TIMED_OUT_QUEUE` | Timed out while still in the client's queue |
| -185 | `ERR__TIMED_OUT` | A request timed out |
| -193 | `ERR__RESOLVE` | Could not resolve a broker address |
| -172 | `ERR__STATE` | Producer not connected |
| -184 | `ERR__QUEUE_FULL` | The client's own queue is full |
| -152 | `ERR__PURGE_QUEUE` | Queue purged (shutdown) |
| 3, 5, 6 | `UNKNOWN_TOPIC_OR_PARTITION`, `LEADER_NOT_AVAILABLE`, `NOT_LEADER_OR_FOLLOWER` | Metadata not there yet, no leader, leader moved |
| 7, 8, 9, 13, 15 | `REQUEST_TIMED_OUT`, `BROKER_NOT_AVAILABLE`, `REPLICA_NOT_AVAILABLE`, `NETWORK_EXCEPTION`, `COORDINATOR_NOT_AVAILABLE` | Broker-side unavailability |
| 19, 20 | `NOT_ENOUGH_REPLICAS`, `NOT_ENOUGH_REPLICAS_AFTER_APPEND` | ISR below min ISR (the second: appended first) |

Everything else is **not** a "Kafka unavailable" case. Examples: `MESSAGE_TOO_LARGE`, `INVALID_TOPIC`, authorization failures, serialization errors. They are bugs or bad messages: retrying cannot help, and **they must not trip the circuit breaker** (the batcher only counts `KafkaUnavailableError` toward the breaker, **[observed in `micro-batcher.ts`]**).

Three kinds of failure, three treatments:

| Kind | Examples | Library | EventPulse |
| --- | --- | --- | --- |
| **Transient** | Leader moved, brief network error | Retries with backoff, usually succeeds | Invisible except as latency |
| **Persistent** | Broker down, ISR below min, no leader for a while | Retries until retries or the delivery timeout run out, then fails | `KafkaUnavailableError`, breaker counts it, 503 |
| **Permanent** | Message too large, bad topic | Fails at once | Not "unavailable"; not counted by the breaker |

## 6. Retries, backoff and the delivery timeout

How a retried send plays out:

```
 attempt 1 fails (retriable)  -> wait backoff 100 ms
 attempt 2 fails              -> wait about 200 ms     (exponential growth, with jitter, capped at 1,000 ms)
 attempt 3 fails              -> wait about 400 ms
 attempt 4 fails              -> wait about 800 ms
 attempt 5 fails              -> wait 1,000 ms (cap)
 retries used up (5)          -> fail with the last error
   ... OR the delivery timeout (30 s) passes first -> fail with "message timed out"
```

(The exact growth and jitter are internal to librdkafka and not configurable in the compatibility layer **[observed: the layer states that backoff growth and jitter are handled internally]**; the 100 ms start and 1,000 ms cap are the configured values.)

The arithmetic that matters:

- **If each attempt fails quickly** (connection refused, "not leader"), five retries use up about **2.5 to 3 seconds** of backoff in total plus the attempt times. **The delivery timeout is then irrelevant** (30 s is never reached): the retry count is what ends it **[reasoning, from the observed settings]**.
- **If each attempt hangs** (a broker that does not answer), one attempt can take up to the request timeout (30 s here). Then **the delivery timeout** ends it, possibly before all retries are used.
- With the **Java client's** effectively unlimited retries, only the delivery timeout ends a retry loop **[reasoning]**, which is how the observed 9 s `TimeoutException` arose in Kafka note 3.

Therefore **"how long does the library ride out a failure?"** depends on the **failure mode**: seconds for fast failures (retry count), up to the delivery timeout for slow ones. This is the single most useful fact to confirm in a fault-injection test (section 17).

Rules for choosing values:

- **Make `retries` large and let the delivery timeout be the bound**, so one number answers "how long do we try"; otherwise two limits interact in a failure-mode-dependent way. (EventPulse currently bounds by count.)
- **`delivery.timeout.ms >= linger.ms + request.timeout.ms`** (the Java rule) is a good habit: a message needs time for at least one full attempt.
- **Backoff exists to avoid hammering a struggling broker**: do not set it to zero.

## 7. Ordering

Records within a partition can be reordered by retries when several batches are in flight (Kafka note 3, section 9.2):

```
 two batches in flight, no idempotence:  B1 fails, B2 succeeds, B1 retried -> log has B2 then B1
```

| Setup | Ordering across retries |
| --- | --- |
| `max.in.flight = 1` | Preserved (at the cost of pipelining) |
| `max.in.flight > 1`, **not idempotent** | **Can reorder** |
| **Idempotent**, `max.in.flight <= 5` | **Preserved**: the broker rejects out-of-sequence batches and the client resends in order (producer note 3, section 7) |
| EventPulse's `BATCH_MAX_IN_FLIGHT` (default 1) | A separate, **application-level** limit: the batcher does not start the next `send()` until the previous one settles |

In EventPulse two things protect ordering at once: idempotence (client layer) and the batcher's single in-flight batch (application layer). If you raise `BATCH_MAX_IN_FLIGHT` above 1 and a send fails or times out, **a later batch may complete first**, so per-key order across batches is **not guaranteed** (this is stated in the batcher's header comment **[observed]**).

## 8. Duplicates

A retry of a write that already happened creates a duplicate. Three situations:

1. **Library retry, idempotent producer**: removed by the sequence check (producer note 3). **Not a problem.**
2. **Library retry, not idempotent** (`KAFKA_IDEMPOTENT=false`): duplicate possible. Experiment-only configuration.
3. **Application-level retries**: the batcher abandons a batch after 5 s and answers 503; the library may still deliver the batch; the HTTP client retries; **two records in Kafka**. The sink's `ON CONFLICT (event_id)` removes the second.

Also "**maybe written**" outcomes (timeouts, `NOT_ENOUGH_REPLICAS_AFTER_APPEND`) mean the HTTP client **cannot know** whether the event is in Kafka. The contract therefore says: retry 503s and network errors with backoff and the **same `event_id`**.

## 9. Every timer

From the outside in, with the **observed** values. The shortest bound that applies fires first.

| # | Timer or limit | Where | Value | What it bounds |
| --- | --- | --- | --- | --- |
| 1 | Client's HTTP timeout | k6 / client | (client-defined) | The caller's patience |
| 2 | Batcher **queue expiry** | micro-batcher | `KAFKA_SEND_TIMEOUT_MS`, 5 s | A message waiting for its batch to start (rejected with a 503) |
| 3 | Batcher **send timeout** | micro-batcher | 5 s | One `send()`; on expiry all its waiters get a 503 and the batch is abandoned |
| 4 | Circuit breaker | micro-batcher | 3 failures, 5 s cooldown | Turns a known outage into immediate 503s |
| 5 | Delivery timeout | library | 30 s | A message's whole stay in the client |
| 6 | Retries | library | 5, backoff 100 ms to 1 s | Number of attempts |
| 7 | Ack timeout | broker | 30 s | Broker's wait for the ISR per request |
| 8 | Socket / request timeout | library | 30 s | One network request |
| 9 | Connection setup | library | 3 s | Connecting to a broker |

The batcher's own header comment states the resulting bound for a request: **"queue wait + send timeout"** (up to about 10 s in the worst case: 5 s waiting to be batched plus 5 s of sending) **[observed]**.

What the timers mean for the three important failures (derived from the observed settings and Kafka note 3's measured failover times; **[reasoning]** for what the Node client does):

**A. A brief blip (a few hundred ms).** The library retries within its backoff and succeeds. Requests see extra latency, no errors.

**B. A leader failover (`docker kill` of a leader: detection about 9 s plus election; `docker stop` about 5 s; Kafka note 3 measured 17 s from the stop command for a leader).**
  - Library: fast failures (connection reset, not-leader) use up **5 retries in about 3 s**, then the batch fails. The batcher receives `KafkaUnavailableError`, counts a breaker failure, answers the waiters with 503. After **3** such failures the **breaker opens** for 5 s and everything queued is rejected at once; then a probe goes through, and so on until Kafka is back.
  - So a failover is **not hidden**: it appears as **a burst of 503s lasting roughly the failover time**, then normal service. The breaker keeps memory flat and latency low during it.
  - Whether the library fails fast or keeps trying depends on the failure mode (section 6): a **hung** leader (no response) holds attempts for up to the request timeout (30 s) and the **batcher's 5 s timeout fires first**.

**C. Kafka fully down.** Fast connection failures: the library fails in seconds; the batcher counts failures; the breaker opens; requests get immediate 503s with `Retry-After`. Memory stays flat because queued requests are rejected when the breaker opens.

**D. One slow follower.** Not a failure: `acks=all` waits for it. If the delay exceeds the batcher's 5 s, requests time out in the batcher (503) while the batch is still being replicated: the zombie write of section 10.

## 10. Mismatch

The configuration relationship **batcher send timeout (5 s) < library delivery timeout (30 s)** has consequences **[observed values, reasoning about behavior]**:

1. **When the batcher times out first, nobody cancels the library's batch.** The waiters get a 503. The library keeps working on the batch until it succeeds, runs out of retries, or hits 30 s. If it succeeds, **the events are in Kafka although their requests were answered with 503.** (The batcher's code comment acknowledges it: "The send may still complete later, so a client retry can create a duplicate".)
2. **Every such event is a candidate duplicate** (the client retries), and shows up in the audit as "written but not acknowledged" (check D).
3. **The delivery timeout (30 s) is effectively never the one that fires** for a batch in the batcher: the 5 s timer always comes first. It only cleans up.
4. **The shorter the batcher's timeout relative to a real failover, the more 503s** (a 9 s detection delay exceeds 5 s regardless).

Options:

| Option | Settings | Effect | Trade-off |
| --- | --- | --- | --- |
| **A. Align: the library gives up first** | `KAFKA_DELIVERY_TIMEOUT_MS` a bit below `KAFKA_SEND_TIMEOUT_MS`, and `KAFKA_ACK_TIMEOUT_MS` below the delivery timeout (for example ack timeout 3,000, delivery 4,500, send 5,000) | The library fails the message cleanly before the batcher gives up: **no zombie writes**, fewer "written but not acknowledged" events | Shorter retry window: less failover tolerance; the library must accept such a combination (untested here; the Java client requires delivery >= linger + request timeout) |
| **B. Keep it as is** | 30 s delivery, 5 s send | The library can ride out a longer failover in the background | **Zombie writes** and duplicates; the audit's check D rises; 503s anyway |
| **C. Long everything** | Send timeout 30 s too | Requests wait up to 30 s instead of failing: fewer errors, **unbounded-feeling latency and memory** (queue grows 30 s deep) | Defeats the point of fast failure (Step 5) |

**Recommendation:** option **A** as the default, because the design principle of Step 5 is **fast, honest failure with bounded memory**, and a 503 should mean "we gave up", not "we are still trying". Verify with a fault-injection run that (1) the Node client accepts the combination, and (2) duplicates and check D drop. This is a good small K-style experiment, and it is the **actionable finding of this note**: it is the one place where the current configuration is internally inconsistent.

## 11. Retry storms

Retries are fine until **every layer retries at once**:

```
 HTTP client retries 503s   x   (library retries up to 5 per batch)   x   (batcher: none)
 -> one failed write can become many attempts, arriving exactly when the cluster is weakest.
```

How the stack limits it, and what is missing:

| Control | Layer | Effect |
| --- | --- | --- |
| Bounded retries and delivery timeout | Library | A message does not retry forever |
| **No retry in the batcher** | Batcher | One outcome per batch; no amplification here (stated in its header **[observed]**) |
| **Circuit breaker** (3 failures, 5 s) | Batcher | Stops sending to a broken Kafka; rejects at once |
| **Bounded queue** by count and bytes | Batcher | Memory stays flat; overload becomes 503 immediately |
| **`Retry-After`** header on 503 | API | Tells clients when to come back (Step 5) |
| **Client backoff with jitter** | Clients | Must be done by the callers; the contract should say so |
| Fast failure | Whole path | Short timeouts keep requests from piling up |

The Stage 1 experiments already studied the same phenomenon at the database (see `notebook/stage-1/experiments/B9`, the retry storm analysis): the lesson carries over. The API cannot force clients to back off, but it can **make backing off the cheap choice** (fast 503 with `Retry-After`) and **never amplify load itself**.

## 12. Startup and shutdown

Timers outside the steady-state path **[observed in `producer.service.ts`, `config.ts`]**:

| Timer | Value | Purpose |
| --- | --- | --- |
| `KAFKA_STARTUP_WAIT_MS` | 10,000 | How long startup waits for the first connection; then the API starts anyway and keeps trying in the background |
| `KAFKA_RECONNECT_INITIAL_MS` / `KAFKA_RECONNECT_MAX_MS` | 500 / 10,000 | Backoff of the background connect loop (doubling) |
| `KAFKA_CONNECTION_TIMEOUT_MS` | 3,000 | Per-connection setup time |
| `SHUTDOWN_DRAIN_TIMEOUT_MS` | (config) | On SIGTERM, how long `drain()` may wait for Kafka before the remaining waiters get a 503 |
| `KAFKA_HEALTH_INTERVAL_MS` / `KAFKA_HEALTH_TIMEOUT_MS` | 2,000 / 2,000 | Background health checks that drive readiness and the breaker |
| `KAFKA_STATS_INTERVAL_MS` | 5,000 | librdkafka statistics for metrics |

Remember that **a failed Confluent producer cannot `connect()` again**, so each connect attempt builds a new producer (comment in `producer.service.ts`), and that the client's `ERR__STATE` ("disconnected") triggers a rebuild in the background.

## 13. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| Retries | **Library retries, bounded** (`KAFKA_RETRIES=5`, backoff 100 ms to 1 s) | A brief blip is invisible; a persistent failure surfaces quickly |
| Retries in the batcher | **None** | No amplification; one outcome per batch |
| Idempotence | **On** | Safe library retries, order preserved |
| In-flight | Client: idempotence caps at 5; batcher: **1** | Per-key order across batches |
| Delivery timeout vs. send timeout | **Align (option A), to be confirmed by a test** | Avoid zombie writes; 503 means "gave up" |
| Breaker | 3 failures, 5 s cooldown | Fast failure and flat memory during an outage |
| Client contract | Retry 503s and network errors with backoff, jitter, **the same `event_id`**; honor `Retry-After` | Avoid retry storms; let the sink dedupe |
| 503 reasons | `overloaded` (queue full) and `kafka_unavailable` | Distinguishable in metrics (Step 6) |

## 16. Failure scenarios

## 18. Common confusions

1. **"`retries=5` means five seconds."** It means five attempts; the time depends on backoff and attempt duration.
2. **"The delivery timeout always applies."** Only if the retry count lasts that long. Fast failures hit the retry count first (with 5 retries).
3. **"A 503 means the event was not written."** It can mean "maybe written".
4. **"The batcher's timeout cancels the send."** It abandons our wait; the library continues.
5. **"Retries are free."** They multiply load during failures.
6. **"More retries make the system more reliable."** Past a point they make it worse (storms) and slower to fail.
7. **"Idempotence removes the need for client-side event ids."** It does not cover HTTP retries.
8. **"The ack timeout and the delivery timeout are the same."** The first is the broker's wait per request; the second bounds the message's entire life in the client.
9. **"Setting `max.in.flight=1` is required for ordering."** Not with idempotence (up to 5).
10. **"The breaker counts every error."** Only "Kafka unavailable" ones; a bad message does not open it.
11. **"A retriable error shows up in my code."** Usually only as a final timeout.
12. **"If the library retries, my queue is protected."** The queue is protected by the batcher's bounds and the breaker, not by retries.

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Retriable error | An error the library retries by itself |
| Backoff | Pause between retries (100 ms growing to 1,000 ms here) |
| Delivery timeout | Bound on a message's whole life in the client |
| Ack timeout | Broker's wait for the ISR per request |
| Send timeout | Batcher's limit on one `send()` (ours) |
| Zombie write | A batch the batcher gave up on but the library later wrote |
| Circuit breaker | Fails fast after repeated failures, probes after a cooldown |
| Retry storm | Layered retries amplifying load during a failure |

### The timers in EventPulse (observed values)

| Timer | Value |
| --- | --- |
| Batcher queue expiry and send timeout | 5 s |
| Breaker | 3 failures, 5 s cooldown |
| Library retries / backoff | 5 / 100 ms to 1 s |
| Delivery timeout / ack timeout / socket | 30 s / 30 s / 30 s |
| Connect | 3 s |

### Rule of thumb

```
ack timeout  <=  delivery timeout  <=  batcher send timeout   (so the library gives up first: no zombie writes)
request bound = queue wait (<= send timeout) + send (<= send timeout)
```

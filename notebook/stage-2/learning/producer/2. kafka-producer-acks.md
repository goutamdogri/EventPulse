## 1. TL;DR

- **`acks` tells the leader when to answer the producer**: `0` never waits, `1` after the leader's own append, `all` (`-1`) after **every replica currently in the ISR** has the record (and the ISR is at least `min.insync.replicas`).
- Each value is a **different promise** and has a different **loss window**: the situation and the time span in which an acknowledged record can still disappear.
  - `acks=0`: the producer **does not even learn whether the broker got it**. The "window" is everything: any error, any failover, any dropped connection.
  - `acks=1`: the record exists on **one** machine at ack time. It is lost if the leader dies **before the followers copy it**. The window lasts as long as the followers lag.
  - `acks=all` with min ISR 2: the record exists on **at least two** machines at ack time. It is lost only if **both** fail before anything else happens, so a single failure loses nothing.
- Cost, measured on this cluster for a saturated producer [observed]: `acks=0` about **31.5 k** records/s, `acks=1` about **22.7 k**, `acks=all` about **17.2 k**. Safety is paid for in throughput and latency.
- **`min.insync.replicas` only has a say when `acks=all`.** `acks=1` and `acks=0` writes are accepted whatever the ISR size (Kafka note 3, and observed in its Lab 5: same cluster state, `all` timed out, `1` and `0` succeeded).
- `acks` is **per producer** in this client, not per `send()` (ADR). Changing it means restarting the API with another `KAFKA_ACKS`. The idempotent producer **requires** `acks=all`.
- For EventPulse the API's **202 must mean durably appended** (Step 1). That is only true with `acks=all`. With `acks=1` or `acks=0` a 202 can be a lie after a leader crash, and the audit's "acknowledged but not in the log" check (check C) is the tool that catches it.

> **One-line version:** *`acks` is a purchase of certainty: 0 buys nothing, 1 buys "one machine has it", all buys "everyone who counts has it".*

## 2. The mental model

Posting a registered letter with three different services (the three offices from Kafka note 3):

| Service | Kafka | You receive... |
| --- | --- | --- |
| Drop it in a postbox and walk away | `acks=0` | Nothing. You will never know if it arrived |
| The first clerk stamps it "received" | `acks=1` | A receipt from one clerk, who may not have passed it on yet |
| The clerk stamps it only after the copies in all the caught-up offices are filed | `acks=all` | A receipt that means "filed in every office that matters" |
| The post office refuses to stamp if fewer than 2 offices are open | `min.insync.replicas=2` | A refusal instead of a thin receipt |

The question to ask of any setting is not "does it usually work" but **"what happens to a record I was told succeeded, if the machine that told me dies one millisecond later?"**

## 3. What an acknowledgement is

A produce request goes to the **leader** of one partition (Kafka note 1, section 7). The leader answers with a response per partition. When it answers depends on `acks`:

```
 producer ---- ProduceRequest(batch) ----> leader
                                            |
   acks=0   leader does not respond at all. The client considers the send done once the bytes are written
            to the socket.
   acks=1   leader appends to its log (page cache), then responds.
   acks=all leader appends, then WAITS until every ISR member has fetched the batch
            (high watermark passes it), then responds.
                                            |
 producer <--- response (offset / error) ---+
```

Facts that apply to every setting:

- A **response is per partition and per batch**, so a `send()` of 500 messages over 6 partitions has up to 6 outcomes. The client reports **one** result to the caller: success only if all succeeded (producer note 1, section 5).
- **"Durable" never means fsynced** here. An acknowledged record is in the OS page cache of the brokers that confirmed it (Kafka note 1, section 7.1). Durability is replication, not `fsync`.
- The response carries the **assigned offset** (except `acks=0`, where the client has none to report).
- **The ack timeout** is separate from the delivery timeout: in this client, `timeout` is mapped to `request.timeout.ms` (`KAFKA_ACK_TIMEOUT_MS`, 30 s) **[observed in the library source and `producer.service.ts`]**. It bounds how long the broker may wait for the ISR before answering with an error (producer note 5).

## 4. acks=0

**Behavior.** The producer writes the batch to the socket and considers it sent. The leader sends no response. There is **no way to learn** about any failure after the send:

- The leader never got it (network loss, wrong or dead broker, leader just changed): **lost, silently**.
- The leader got it but rejected it (message too large, unknown topic, not leader): **lost, silently** (the client may log, but the caller's `send()` still succeeds).
- The ISR is below `min.insync.replicas`: **accepted** (min ISR is not checked).
- The leader crashed a moment later: **lost**.
- The record is still in the producer's memory when the process dies: **lost**.

**Loss window: unbounded.** Not a time span, but a category: anything that goes wrong between "handed to the client" and "persisted on a broker" goes unreported.

**Observed** [Kafka note 3, Lab 5]: with the ISR smaller than `min.insync.replicas`, a producer with `acks=all` **timed out and appended nothing**, while a producer with `acks=0` reported **success** for the same records. The `acks=0` "success" says nothing about the log.

**When it is acceptable.** Data you can afford to lose completely and where you want the lowest possible latency and CPU: sampled metrics, best-effort debug logs. **Not** for EventPulse: the whole point of Stage 2 is that an accepted event is not lost.

## 5. acks=1

**Behavior.** The leader appends the batch to its own log and answers immediately. The followers fetch it **afterwards**, asynchronously.

```
 t0   producer sends batch                     leader log: ... 98 99
 t1   leader appends                           leader log: ... 98 99 [100 101 102]
 t2   leader answers SUCCESS  ──────────────►  producer: "acknowledged"
 t3   (window) followers have NOT fetched yet  follower logs: ... 98 99
 t4   leader's machine fails
 t5   a follower is elected (it is in the ISR, it has up to 99)
      records 100..102 existed only on the dead leader: LOST. The producer was told they succeeded.
```

**Loss window.** From **t2 until the slowest follower that could be elected has fetched the batch.** In a healthy cluster that is typically milliseconds, because followers fetch continuously (replica fetch wait is 500 ms maximum when idle, but a fetch is answered as soon as data exists) **[reasoning]**. It is **not bounded by a constant**: a lagging follower stays in the ISR for up to `replica.lag.time.max.ms` (30 s here, Kafka note 3), so the window can be seconds long exactly when the cluster is under stress.

**What it protects against.** A producer-to-broker network failure (you get an error or timeout, so you can retry) and a record that the leader could not append (you get an error). It does **not** protect against the leader dying after answering.

**What min ISR does.** Nothing. A leader accepts `acks=1` writes with an ISR of one (itself), so after the ISR has shrunk, `acks=1` writes are acknowledged by a single machine for as long as that lasts (Kafka note 3, section 7).

**After a failover.** The old leader, when it returns, **truncates** the tail that the new leader does not have (Kafka note 4, section 7.3). So the lost records are not recoverable from it either.

**When it is acceptable.** Throughput matters more than a small amount of loss on broker failure and you can tolerate losing the last few milliseconds of data. Not EventPulse.

## 6. acks=all

**Behavior.** The leader waits until **every replica in the current ISR** has the batch (the high watermark passes it), and refuses to accept the write at all if the ISR has fewer than `min.insync.replicas` members (Kafka note 3, sections 7 and 8).

**Loss window.** For a record acknowledged with `acks=all` and `min.insync.replicas = m`:

- It exists on **at least m brokers** at ack time.
- It survives any **m - 1** simultaneous broker failures (data on a surviving ISR member).
- It is lost only if **m or more brokers holding it fail together** before it spreads further, or through a failure that replication cannot cover: a bug or an operator deleting data (replication copies mistakes), or **simultaneous power loss of all of the brokers that hold it** (the data is only in page cache, Kafka note 1 section 7.1).

For EventPulse (RF 3, min ISR 2): one broker failure at a time loses nothing; two simultaneous failures of the two brokers that hold a record can lose it. In practice a record is typically on all three brokers within milliseconds, so the window for **only two** having it is short.

**What can still go wrong with `acks=all`** (not data loss, but things you must handle):

- **Refusal**: ISR below min ISR gives retriable errors and, after the delivery timeout, a timeout (Kafka note 3, section 10.1). The record is not accepted.
- **Ambiguity**: a timeout or `NOT_ENOUGH_REPLICAS_AFTER_APPEND` means the record **may** have been appended. A retry may duplicate it (producer notes 3 and 5).
- **Latency**: the ack waits for the **slowest ISR follower** (section 8).

## 7. Loss windows

All for a record that the producer was told succeeded. RF 3. "Leader dies" means the broker holding the partition's leader crashes just after the ack.

| Event after the ack | `acks=0` | `acks=1` | `acks=all`, min ISR 2 |
| --- | --- | --- | --- |
| Producer never reached the broker (network, wrong leader) | **Lost, silent** | Error returned, retry | Error returned, retry |
| Leader rejected it (too large, etc.) | **Lost, silent** | Error returned | Error returned |
| Leader crashes before followers copied it | **Lost** | **Lost** | **Not lost**: ISR members have it |
| Leader crashes, ISR is only itself (followers lagging) | Lost | **Lost** | **Refused earlier** (ISR 1 < min ISR 2), not acknowledged |
| One follower fails | Unaffected | Unaffected | Unaffected (ISR shrinks to 2) |
| Two brokers (both holding the record) fail together | Lost | Lost | **Can be lost** |
| All brokers lose power at once | Lost | Lost | Lost (page cache) |
| Leader reports success, then a new leader is elected before replication (unclean election, Kafka note 4) | Lost | Lost | Can be lost only with unclean election enabled (ours is off) |
| Operator deletes the topic / bad write replicated | Lost | Lost | Lost |

Three ways to describe the same thing:

| | Who knows the outcome | Copies at ack time | Single machine failure loses acknowledged data? |
| --- | --- | --- | --- |
| `acks=0` | Nobody | 0 to 3, unknown | Yes, and you never learn it |
| `acks=1` | The leader | 1 | **Yes** |
| `acks=all`, min ISR 2 | The ISR | at least 2 | **No** |

## 8. Cost

Measured on this cluster [observed]: 100,000 records of 1 KB to a 6-partition topic, RF 3, `min.insync.replicas=2`, `linger.ms=5`, `batch.size=64 KiB`, producer saturated, idempotence disabled so that all three settings can be compared:

| `acks` | Records/s | MB/s | Avg latency | p50 | p99 |
| --- | --- | --- | --- | --- | --- |
| `all` | **17,229** | 16.4 | 1,352 ms | 1,063 ms | 3,121 ms |
| `1` | **22,701** | 21.7 | 101 ms | 98 ms | 283 ms |
| `0` | **31,476** | 30.0 | 18 ms | 4 ms | 192 ms |

Reading it:

- **Throughput**: `acks=1` is about 32 percent higher than `all`, and `acks=0` about 83 percent higher. The ordering is robust; the exact ratios depend on the hardware (each broker has 1 CPU here) and the batch settings.
- **Latency in this table is mostly queueing**: the producer is saturated, so records wait in its buffer behind a slower cluster. With `acks=all` the cluster is the slowest, so the queue is longest. At a **light fixed rate** the difference is just the extra round trips, a few milliseconds on localhost (producer note 1, section 7).
- **Why `all` is slower**: the response waits for the **slowest ISR follower**: a follower round trip plus its append, once per batch. It is also sensitive to **one slow follower** (a degraded disk), which delays acknowledgements for every partition it follows until it leaves the ISR (Kafka note 3, section 14).
- **`acks=0`** still pays for the client's batching and sending; it only skips waiting.

What you buy for that throughput difference is the entire section 7 table. For EventPulse the right framing is not "which is faster" but "what does a 202 need to mean", which is section 10.

## 9. Configuration rules

Observed on this cluster's client and in this repo's code.

| Rule | Evidence |
| --- | --- |
| **`enable.idempotence=true` requires `acks=all`.** Setting `acks=1` together with explicit idempotence is a hard config error | **[observed]** Java client: `ConfigException: Must set acks to all in order to use the idempotent producer. Otherwise we cannot guarantee idempotence.` |
| If you set `acks=1` and do **not** mention idempotence, the Java client quietly **turns idempotence off** and runs | **[observed]**: a 100-record run with only `acks=1` succeeded |
| **EventPulse refuses the combination at startup**: `KAFKA_ACKS` must be `-1`, `0` or `1`, and `KAFKA_IDEMPOTENT=true` with an acks other than `-1` throws with the message `KAFKA_IDEMPOTENT=true requires KAFKA_ACKS=-1 (set KAFKA_IDEMPOTENT=false to try acks 0/1)` | **[observed in `config.ts`]** |
| **`acks` is per producer, not per `send()`**. The PRD sketch passes `acks: -1` inside `send()`; this client throws on it | **[observed in the ADR and in the library source: `send` rejects `acks`, `timeout`, `compression` options]** |
| The ack timeout (`KAFKA_ACK_TIMEOUT_MS`, 30 s) maps to `request.timeout.ms` | **[observed in the library source and `producer.service.ts`]** |
| Readiness checks follow `acks`: the health check's minimum ISR is **2** when `acks=-1` and **1** otherwise | **[observed in `config.ts`: `KAFKA_HEALTH_MIN_ISR`]** |

How to run the K2 experiment safely: set `KAFKA_ACKS=1` **and** `KAFKA_IDEMPOTENT=false`, restart the API, and **record the effective settings** in the result. `/debug/stats` already reports `acks`, `idempotent` and the other producer settings in its `config` block (Step 6), so every result carries its own settings.

## 10. What 202 means

The API contract (Step 1) says: **202 means durably appended to `events.raw` under the configured `acks` policy.** What that sentence is worth depends on the policy:

| `KAFKA_ACKS` | The batcher resolves the request when... | A 202 means... | Is the audit's check C expected to hold under a leader crash? |
| --- | --- | --- | --- |
| `-1` (`all`) | The leader confirmed, with the whole ISR (at least 2) having it | The record is on at least 2 brokers' memory | **Yes** |
| `1` | The leader confirmed its own append | One machine has it | **No**: expect failures; that is the experiment |
| `0` | The client handed the batch to the socket | **Nothing is promised** | **No** |

Under `acks=0`, the batcher's "resolve when the send succeeds" turns into **"202 after the client wrote to a socket"**. That is the opposite of the Stage 2 contract, which is why the default is `-1` and the others are labelled **experiment knobs only** (see the decisions section).

Also keep in mind what a 202 **never** promises under any setting: that the event is **visible in Postgres** (that is eventual, via the sink) or that **only one copy exists** (duplicates can occur, Kafka note 3 section 13 and producer notes 3 and 5).

## 11. Loss no acks setting prevents

Even with `acks=all` and min ISR 2, acknowledged data can be lost by:

1. **Two simultaneous failures** of exactly the brokers that held it (plus a leader election that cannot find a copy, or unclean election turned on).
2. **Correlated failure**: all brokers on one power circuit, rack or host. Replication only helps if replicas fail independently. (In this lab, all three brokers run on one machine: a host failure loses everything. Production uses racks and `broker.rack`.)
3. **Page-cache loss**: simultaneous power loss on every broker that held it before the OS flushed.
4. **Human or software action**: deleting the topic, `kafka-delete-records`, a retention change that deletes data a consumer has not read (note on retention: a consumer behind retention loses data without any failure).
5. **Retention**: data acknowledged yesterday and not consumed within the window is deleted (Kafka note 5). That is not an `acks` matter, but it ends durability in the same practical way.
6. **A bug before the producer**: events the API accepted (202) but that were never sent (a crash with queued requests) are **never acknowledged to the client** by design (no 202), so they are not "lost acknowledged data". This is the point of answering the HTTP request only after the ack.

## 12. Detecting loss

You cannot see a loss from inside the producer: it was told "success". Detection is by **reconciliation**, comparing independent counts:

| Check | Compares | Catches |
| --- | --- | --- |
| Audit check B | k6's count of 202s vs. the API's acknowledged counter (`ep_kafka_messages_acked_total`) | Counting bugs, lost responses |
| **Audit check C** | Delta of Kafka end offsets vs. acknowledged count | **Acknowledged but not in the log** |
| Audit check E | Distinct rows in Postgres for the run vs. acknowledged minus DLQ | Acknowledged but never stored |
| Audit check D | Kafka offset delta minus acknowledged | The opposite case: written but not acknowledged (ambiguous failures, retries) |

**This is why `acks=1` and unclean election experiments are valuable**: with a broker kill during load, the audit should report a gap under `acks=1` and none under `acks=all`. Keep both runs as reference results (Step 7).

## 13. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| `KAFKA_ACKS` default | **-1 (`all`)** | A 202 must mean durably appended |
| `KAFKA_IDEMPOTENT` default | **true** | Safe client retries; forces `acks=all` |
| `acks=1` and `acks=0` | **Experiment-only knobs**, with idempotence off, recorded in the result | To measure the loss and the speed gain, not to run in the pipeline |
| `min.insync.replicas` | **2** | Without it, `acks=all` can shrink to one copy (Kafka note 3, section 8) |
| `unclean.leader.election.enable` | **false** | Otherwise `acks=all` data can still be lost on election (Kafka note 4) |
| Ack timeout | `KAFKA_ACK_TIMEOUT_MS` 30 s | Broker-side wait for the ISR |
| Contract wording | 202 = acknowledged by at least 2 in-sync brokers, not "on disk everywhere" | Be precise (Step 1) |

## 16. Failure scenarios

Setup: RF 3, EventPulse API sending to `events.raw`.

| Scenario | `acks=all`, min ISR 2 | `acks=1` | `acks=0` |
| --- | --- | --- | --- |
| Leader's broker `docker kill` mid-load | Some requests wait or time out (503), then recover. **No acknowledged loss** | Some **acknowledged records lost** (those not yet copied) | Records lost **and not even counted as failures** |
| A follower killed | Slight latency change, then fine | Fine | Fine |
| Two brokers down | Writes time out (503) | Succeed against a surviving leader (unsafe) | "Succeed" |
| ISR shrinks to 1 for a while | **Writes refused** | Writes accepted on a single copy | Accepted |
| Network blip between API and broker | Retried by the client (idempotent) | Retried; possible duplicates without idempotence | **Lost silently** |
| API crashes with requests queued | Queued requests were never acknowledged, so no 202 | Same | Same, plus any batch handed to the socket and not yet sent |

## 18. Common confusions

1. **"`acks=all` means all replicas."** All replicas **in the ISR**, and only if the ISR has at least `min.insync.replicas` members.
2. **"`acks=1` is almost as safe as `all`."** It loses acknowledged data on a single leader failure.
3. **"`acks=0` just skips the wait."** It also skips error reporting: failures are invisible.
4. **"`min.insync.replicas` protects every producer."** Only `acks=all`.
5. **"I can set `acks` per message."** Not in this client: it is per producer.
6. **"Acknowledged means on disk."** On the page cache of the confirming brokers.
7. **"`acks=all` can't lose data."** Not under correlated failure, human error, retention, or unclean election.
8. **"If `send()` succeeded, the event is in Kafka."** True for `all` (with the caveats above), not for `0`, and only briefly for `1`.
9. **"A slower `acks=all` means something is wrong."** It is the cost of waiting for the slowest ISR follower; look at follower health if it grows.
10. **"I can fix `acks=1` loss with retries."** Retries only help when you got an error. The loss window is after a success response.
11. **"Idempotence works with any `acks`."** It requires `acks=all`.
12. **"The 202 is the same promise in every experiment."** It is not; record the `acks` with every result.

<summary>Short answers</summary>

1. `0`: nothing (no response). `1`: the leader's own append. `all`: every replica in the current ISR (and an ISR of at least min ISR).
2. From the leader's acknowledgement until a follower that could be elected has fetched the record. It lasts as long as the followers lag, which is longer when the cluster is stressed (a lagging follower stays in the ISR up to 30 s).
3. The producer never learns of failures at all: loss is silent, including errors the broker would have reported.
4. At least 2. It survives any single broker failure (more precisely, m - 1 = 1 simultaneous failures).
5. min ISR is only checked for `acks=all` writes; `acks=1` is accepted by the leader regardless of the ISR size.
6. It is lost: the new leader never had it. When the old broker returns it truncates that tail, so it is not recoverable from it either.

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| `acks` | Who must confirm a write before the producer sees success |
| Loss window | The condition and time in which an acknowledged record can still be lost |
| Page cache durability | A record is in memory of the brokers, not fsynced |
| min ISR | Smallest ISR size at which `acks=all` writes are accepted |
| Ack timeout | How long the broker may wait for the ISR (maps to `request.timeout.ms`) |
| Reconciliation | Comparing independent counts to find lost or extra records |

### Summary table

| `acks` | Waits for | Copies at ack | Survives one broker failure | Needs idempotence off? |
| --- | --- | --- | --- | --- |
| `0` | nothing | unknown | No | Yes (must be off) |
| `1` | leader append | 1 | **No** | Yes (must be off) |
| `all` / `-1` | whole ISR (>= min ISR) | >= 2 | **Yes** | No (required for idempotence) |

# Kafka Producer: Batching (`linger.ms`, `batch.size`, `buffer.memory`)

*Producer note 1 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read Kafka notes 1 (partitions and segments) and 3 (replication and `acks`) first. Larger batches raise throughput and add latency: this note explains why, shows the numbers on this cluster, and shows where batching happens in EventPulse. It supports Step 1 (producer and micro-batcher), Step 6 (batch metrics) and experiments K1 and K2.*

**What was run.** Everything marked **[observed]** was measured on this repo's cluster (3 brokers, 1 CPU and 1 GiB each, RF 3, `min.insync.replicas=2`) on a scratch topic that was deleted afterwards, using the Java `kafka-producer-perf-test.sh` inside the broker container, unless noted. No broker was stopped. Numbers are from **one run each on a laptop**: use them for the shape of the curve, not as constants. Statements marked **[reasoning]** are standard Kafka or librdkafka behavior that was not observed here.

## 1. TL;DR

- A Kafka producer does **not** send one network request per record. It **accumulates records into batches** (one batch per destination partition) and sends batches, because per-request fixed costs (network round trip, syscalls, a CRC, a replication round, a compression frame) are paid once per batch instead of once per record.
- Three knobs shape it: **`batch.size`** (how big a batch may get), **`linger.ms`** (how long to wait for a batch to fill), **`buffer.memory`** (how much the producer may hold in total before it pushes back on the caller).
- **Bigger batches raise throughput and add latency.** A record may sit in a batch for up to `linger.ms` waiting for company. On this cluster, going from "one record per batch" to 256 KB batches with 50 ms linger moved a saturated producer from **about 1.6 k to about 35 k records/s** [observed].
- Batches are **per partition**, so spreading the same load over more partitions makes each batch smaller (Kafka note 1, section 7.3).
- At **low load** `linger.ms` only adds delay, because batches never fill. At **high load** batches fill before the linger expires and `linger.ms` becomes irrelevant.
- When the producer's memory is full, `send()` **blocks or fails**: that is the producer's backpressure. In EventPulse a second, explicit queue (the micro-batcher) sits in front of it.
- EventPulse batches in **three layers**: concurrent HTTP requests into the micro-batcher, the batcher's `send()` into the client's per-partition batches, and those into broker record batches that are stored, replicated and compressed as units.

> **One-line version:** *Batching trades a small, bounded wait for a large reduction in per-record cost: wait until the batch is big enough or old enough, then send once.*

## 2. The mental model

A shuttle bus to the airport. A bus costs the same to run whether it carries 1 passenger or 40.

| Shuttle bus | Producer |
| --- | --- |
| The bus | A produce request / a record batch |
| Seats | `batch.size` |
| "Leaves when full, or after 10 minutes, whichever is first" | Send when the batch is full **or** `linger.ms` expires |
| One bus per destination | One batch per partition |
| The parking lot holds only so many buses | `buffer.memory`: when full, new passengers wait outside or are turned away |
| 10 minute rule at a busy hour | The bus fills at once; the timetable does not matter |
| 10 minute rule at 3 a.m. | Every passenger waits 10 minutes for nothing |

Two sentences carry most of the topic:

1. **The wait is a cost only when the batch does not fill.** Under heavy load, batches fill instantly and add almost no delay. Under light load, `linger.ms` is pure added latency.
2. **A batch is one unit all the way down**: one CRC, one compression frame, one replication fetch, one acknowledgement.

## 3. Why batching exists

Sending one record costs (roughly) the same fixed work however small the record:

| Fixed cost per request or batch | Where |
| --- | --- |
| A network round trip to the leader | `acks=all` waits for it (and for the followers' round trip too) |
| Request/response framing, syscalls, buffer copies | Client and broker |
| The leader's append, CRC and index update | Broker (Kafka note 1, section 7) |
| One replication fetch round per batch | Followers (Kafka note 3) |
| One compression frame, whose ratio improves with size | Client (producer note 4) |
| One idempotence sequence number per batch, not per record | Broker (producer note 3) |

If a record is 350 bytes and these fixed costs are the equivalent of, say, a few kilobytes, then at one record per request you are mostly paying overhead. At 500 records per batch the same overhead is split 500 ways.

**Measured** [observed, 6 partitions, 1 KB records, `acks=all`, producer saturated]:

| Batching | Records/s | MB/s |
| --- | --- | --- |
| `batch.size=1`, `linger.ms=0` (effectively one record per batch) | **about 1,550** | 1.5 |
| `batch.size=16 KiB`, `linger.ms=0` | about 11,250 | 10.7 |
| `batch.size=16 KiB`, `linger.ms=5` | about 16,600 | 15.9 |
| `batch.size=64 KiB`, `linger.ms=20` | about 29,400 | 28.1 |
| `batch.size=256 KiB`, `linger.ms=50` | **about 35,400** | 33.8 |

That is a factor of more than 20 between no batching and good batching on the same hardware and the same replication settings. It is also why Step 1 asks you to build a micro-batcher: **batching is the single biggest throughput lever in the producer.**

## 4. The three knobs

Java client names first; the Node client (librdkafka underneath, see the ADR) has equivalents. Defaults marked **[reasoning]** come from the client documentation and may differ by version: confirm with the client you actually run.

| Knob | Meaning | Java default **[reasoning]** | librdkafka equivalent **[reasoning]** |
| --- | --- | --- | --- |
| `batch.size` | Maximum bytes of **one partition's** batch before it is sent. A **ceiling**, not a target. | 16,384 | `batch.size` (and `batch.num.messages`, a count cap) |
| `linger.ms` | How long to wait for more records after the first one lands in a batch | 0 in older versions, 5 in the newest | `linger.ms` (alias `queue.buffering.max.ms`), default 5 |
| `buffer.memory` | Total bytes of unsent records the producer may hold | 33,554,432 (32 MiB) | `queue.buffering.max.messages` and `queue.buffering.max.kbytes` |
| `max.block.ms` | How long `send()` may block when the buffer is full or metadata is missing | 60,000 | (n/a: the queue-full error is returned) |

What each one does, precisely:

- **`batch.size` is a maximum, not a minimum.** A batch is sent when it is **full**, **or when linger expires**, **or for other reasons** (section 6). A batch of 16 KiB capacity holding 3 KB is perfectly normal. A single record **larger** than `batch.size` is sent in a batch of its own.
- **`linger.ms` is the added-latency knob.** It bounds how long a record can wait **purely to be batched**. `linger.ms=0` does not mean "no batching": records that arrive while a request is already in flight still pile up in the batch and go out together (section 7).
- **`buffer.memory` is the safety valve.** It bounds the producer's memory and defines when the caller feels backpressure.

In EventPulse the env vars are `KAFKA_LINGER_MS` (default **0**, passed as librdkafka's `linger.ms`) and the batcher's own `BATCH_MAX_MESSAGES` (500), `BATCH_MAX_WAIT_MS` (5), `BATCH_MAX_BYTES` (900,000) **[observed in `config.ts`]**. The client's `batch.size` and queue limits are left at the library defaults.

## 5. Batches are per partition

The producer keeps **one open batch per destination partition**. A record is placed into the batch of the partition the partitioner chose for it (producer note 6).

```
 send({ messages: [m1..m500] })            partitioner (key -> partition)
        |
        v
  +------------+ +------------+ +------------+ ... +------------+
  | batch P0   | | batch P1   | | batch P2   |     | batch P5   |   one open batch per partition
  | (m3, m17..)| | (m1, m9..) | | (m4..)     |     | (m2..)     |
  +------------+ +------------+ +------------+     +------------+
        \              |             /                 /
         group by leader broker -> one ProduceRequest per broker, carrying all its ready batches
```

Consequences:

- **More partitions, smaller batches** at the same message rate: 500 records over 6 partitions is about 83 per batch; over 60 partitions about 8 per batch. Smaller batches compress worse and cost more requests (Kafka note 1, section 7.3).
- **A skewed key means one fat batch and several thin ones.** The hot partition's batch fills fast; the cold partitions' batches wait for `linger.ms` (producer note 6).
- **Records with no key** are placed so as to **fill one batch at a time** (a "sticky" choice per batch, **[reasoning]**) instead of one record per partition round-robin, which would make every batch tiny. EventPulse always sets a key, so this does not apply.
- **Requests carry several batches**: all ready batches for the same broker travel in one `ProduceRequest`. The response acknowledges each partition's batch separately, and a `send()` call only resolves when **all** partitions it touched are acknowledged (Kafka note 1, section 7.3).

## 6. When a batch is sent

A batch leaves the producer when **any** of these is true **[reasoning, standard behavior]**:

1. **It is full** (`batch.size`, or the count cap).
2. **`linger.ms` has elapsed** since the first record was added to it.
3. **Another batch for the same broker is ready**, so it is sent along in the same request.
4. **The producer is flushing or closing** (`flush()`, `disconnect()`): everything goes now.
5. **The buffer is under pressure** and the producer wants to free memory.

And it is **held back** when the connection to that broker already has its maximum number of unacknowledged requests (`max.in.flight.requests.per.connection`, producer note 5). Records keep accumulating into the batch meanwhile.

This explains a common surprise: **with `linger.ms=0` you still get batching under load.** If the network is busy, a batch that is "ready" cannot leave yet, so more records join it. Batching is self-adjusting: the slower the broker responds, the bigger the batches get, until the buffer fills.

## 7. Throughput versus latency

### 7.1 Saturated: batching raises throughput

From section 3. Producer sending as fast as it can (`--throughput -1`) [observed]. The "latency" in that mode is mostly **time waiting in the producer's own buffer** because the producer is faster than the cluster: do not read it as request latency.

| Setting | Records/s | Avg reported latency | p99 |
| --- | --- | --- | --- |
| `batch.size=1`, `linger=0` | 1,554 | 16,054 ms | 24,741 ms |
| `16 KiB`, `linger=0` | 11,251 | 1,762 ms | 3,474 ms |
| `16 KiB`, `linger=5` | 16,631 | 1,288 ms | 2,402 ms |
| `64 KiB`, `linger=20` | 29,412 | 129 ms | 389 ms |
| `256 KiB`, `linger=50` | 35,398 | 46 ms | 107 ms |

Even the "latency" column falls as batches grow, because a producer that drains its buffer faster has a shorter queue. That only holds when the producer is **overloaded**. Section 7.2 shows the opposite regime.

### 7.2 Fixed, light rate: waiting is a cost

Producer paced at 1,000 records/s (1 KB each, about 1 MB/s), `batch.size=64 KiB`, 6 partitions [observed]:

| `linger.ms` | p50 | avg | p95 | p99 |
| --- | --- | --- | --- | --- |
| 0 | **1 ms** | 36 ms | 208 ms | 474 ms |
| 10 | 9 ms | 33 ms | 169 ms | 275 ms |
| 50 | 33 ms | 39 ms | 101 ms | 175 ms |
| 100 | 43 ms | 47 ms | 103 ms | 181 ms |

Read the **p50**: it rises with `linger.ms` (1 to 9 to 33 to 43 ms), which is the cost of waiting for a batch that does not fill quickly. The tails (p95 and p99) are dominated by one-off effects in a 10-second run (the first connection to each broker, JIT, a background flush), so they are noisy and do not trend cleanly with linger. Do not draw conclusions from them without more runs.

Why p50 stops growing at 43 ms for `linger=100`: at about 1 MB/s with sticky batching, a 64 KiB batch fills in about 64 ms, so it is sent **full** before the 100 ms linger **[reasoning]**; a typical record waits about half of that. That is "section 6, reason 1" beating "reason 2".

### 7.3 The two regimes

| Regime | Condition | `linger.ms` effect | What to tune |
| --- | --- | --- | --- |
| **Under-loaded** | Batches never fill before `linger.ms` | **Pure latency**, no throughput gain | Lower `linger.ms` (even 0) |
| **Loaded** | Batches fill before `linger.ms` | None (batches leave full) | Increase `batch.size`, check CPU and the broker |
| **Overloaded** | Producer faster than the cluster | Queueing in the buffer | Backpressure, fix the real bottleneck |

For an API that must answer each HTTP request after the ack, **per-request latency matters**, so the linger must be small (EventPulse: batcher `BATCH_MAX_WAIT_MS=5`, client `linger.ms=0`).

## 8. Memory and backpressure

The producer holds records in memory from `send()` until the broker acknowledges. `buffer.memory` caps that. When it is exhausted:

- **Java client:** `send()` blocks up to `max.block.ms`, then throws. **[observed]** with `buffer.memory=64 KiB`, `max.block.ms=1`, `linger.ms=50`: **1,072** sends failed with `BufferExhaustedException: Failed to allocate 16384 bytes within the configured max blocking time 1 ms. Total memory: 65536 bytes. Available memory: 0 bytes.` and the run still finished with the rest.
- **librdkafka (our client) [reasoning]:** `produce()` fails immediately with a **queue full** error when `queue.buffering.max.messages` or `.kbytes` is reached. EventPulse's error classifier already lists it: `-184 ERR__QUEUE_FULL` is in the "unavailable" set in `errors.ts` **[observed in source]**, so it becomes a 503.

Why this matters:

- It is **the last line of defense** against memory growth when Kafka is slow. Without it a slow broker would grow memory until the process is killed.
- It is **a different thing from the micro-batcher's queue** (section 9): the batcher bounds **requests waiting to be batched** (`BATCH_MAX_QUEUE`, `BATCH_MAX_QUEUE_BYTES`); the client's buffer bounds **batches waiting to be acknowledged**. Memory is bounded at both places, and the batcher's bounds are the ones you control and observe.
- **Do not size `buffer.memory` as a throughput knob.** A bigger buffer only delays when the caller notices the cluster is slow.

## 9. Three layers

In EventPulse a record passes through three batching steps, in this order:

```
 HTTP requests (many concurrent, one event each)
      |
      |  Layer 1: MICRO-BATCHER (our code)         up to BATCH_MAX_MESSAGES=500 or BATCH_MAX_BYTES=900 KB,
      v                                            or the oldest waited BATCH_MAX_WAIT_MS=5 ms; 1 batch in flight
 producer.send({ messages: [up to 500] })
      |
      |  Layer 2: CLIENT (librdkafka)              groups messages into ONE BATCH PER PARTITION;
      v                                            KAFKA_LINGER_MS=0 by default so it adds no wait of its own
 record batches per partition, grouped per broker
      |
      |  Layer 3: BROKER / LOG                     each batch is appended, replicated, acknowledged as a unit;
      v                                            compression and idempotence sequence apply per batch
 events.raw-N segment files
```

Points to hold on to:

- **Layer 1 exists for the HTTP side**: it turns many independent requests into one `send()` and resolves every waiting request when its batch is acknowledged. It also gives the API a bounded queue, byte caps, a send timeout, a circuit breaker and metrics. It is the subject of producer note 7.
- **Layer 2 exists in the library regardless**. The ADR sets `linger.ms=0` by default so that **our** batcher alone decides the wait, and K2 can switch to "librdkafka linger only" by env var **[observed in the ADR]**. If both waits are enabled they **add**: a message may wait up to `BATCH_MAX_WAIT_MS` in layer 1 and then up to `linger.ms` in layer 2.
- **One `send()` is not one broker batch.** A 500-message `send()` over 6 partitions becomes up to 6 broker batches (section 5). One outcome (all resolve or all reject) is reported for the whole call, which is the batcher's "one outcome per batch" rule.
- **Layer 3's batch is also what `max.message.bytes` limits** (section 11).

A result from this stack that is worth knowing [observed, Node client with the same settings as the API: `acks=-1`, idempotent, 400-byte records, 6 partitions, 20,000 records, 500 concurrent callers]:

| Approach | Records/s | p50 | p99 |
| --- | --- | --- | --- |
| Each caller does its own `send()` of one record, `linger.ms=0` | 34,539 | 8 ms | 68 ms |
| Each caller does its own `send()` of one record, **`linger.ms=5`** | **71,876** | 6 ms | 30 ms |
| Micro-batcher (500 or 5 ms, 1 in flight), `linger.ms=0` | 35,914 | 10 ms | 70 ms |
| Micro-batcher plus `linger.ms=5` | 16,661 | 13 ms | 79 ms |

So at this load the library's own linger did as well as, and here better than, a hand-built batcher. That is not a reason to drop the batcher (section 13 and producer note 7 explain what it gives that the library does not), but it **is** a reason to measure both (K2) rather than assume. The Node numbers were produced by a small script that copies the batcher's rules, not by the repository's own class, and they are from one run: treat them as a hypothesis for K2.

## 10. Sizing

### 10.1 What fills a batch

Records that land in one partition's batch during the wait window:

```
 records per batch  ≈  (arrival rate into that partition)  ×  (wait time)

 wait time = min( time to fill batch.size,  linger.ms )   (and longer if the connection is busy)
```

Worked example (assumptions, replace with measured numbers): 2,000 events/s, 350 bytes per event, 6 partitions, key spread even.

| | Value |
| --- | --- |
| Per-partition rate | about 333 events/s = about 117 KB/s |
| Records in a batch with `linger=5 ms` | about 1.7 |
| Records with `linger=50 ms` | about 17 |
| Time to fill 16 KiB | about 140 ms |

At this load, **nothing fills**: batches are 1 to 17 records and `linger.ms` is the only thing that grows them. This is why a micro-batcher that collects events **across all partitions first** (500 at a time) makes better use of the wire than leaving it to per-partition batches. It is also why K2 (producer sweep) is worth running at several rates, not one.

### 10.2 What to expect

- **Throughput rises steeply with the first increases in batch size**, then flattens (the table in section 3: 1.5 k, 11 k, 17 k, 29 k, 35 k). Past a point the bottleneck moves to the broker's CPU or disk (here each broker has 1 CPU), or to replication.
- **Latency grows with `linger.ms` only when batches do not fill.**
- **There is no universal best value.** It depends on rate, record size, partition count and the latency you can afford. Measure, then pick.

## 11. Size limits

Several different byte limits apply to a batch. Mixing them up produces confusing rejections:

| Limit | Applies to | In EventPulse |
| --- | --- | --- |
| `batch.size` (producer) | Target maximum of one partition's batch, **uncompressed** | Library default |
| `max.request.size` / `message.max.bytes` (client) | Largest request or record batch the client will build | Library default (about 1 MB) |
| `max.message.bytes` (**topic**) | Largest **record batch** (after compression) the broker accepts | **1,048,588** [observed on `events.raw`] |
| `BATCH_MAX_BYTES` (batcher) | Total bytes the batcher puts into one `send()` | **900,000**, and config refuses values above **1,000,000** (`MAX_BATCH_BYTES_LIMIT`) [observed in `config.ts`] |
| `BODY_LIMIT` (HTTP edge) | One request body | 64 KB |

The ordering that must hold: **`BODY_LIMIT` < `BATCH_MAX_BYTES` <= the limit the client and broker will accept.** The batcher counts bytes **before** compression (`sizeBytes` is key plus value plus header bytes, **[observed in `micro-batcher.ts` and `encodeEvent`]**), which is conservative because compression only makes the batch smaller. A `send()` of 900 KB spread over 6 partitions gives batches well under the broker limit.

A single message larger than `BATCH_MAX_BYTES` is rejected by the batcher itself (`MessageTooLargeError`); it is never sent.

## 12. Observing

What to look at, and where it lives:

| Signal | Where | What it tells you |
| --- | --- | --- |
| Messages per batcher flush (`ep_batcher_batch_size_messages`) and bytes (`..._bytes`) | The API's metrics (Step 6) | Layer 1 batch sizes. Persistently 1 means the batcher is not batching (low concurrency) |
| Flush reason counts (`ep_batcher_flush_total{reason}`) | Same | `size` dominates under load, `time` when under-loaded |
| Queue wait (`ep_batcher_queue_wait_seconds`) | Same | The latency cost of layer 1 |
| Send duration (`ep_kafka_send_seconds`) | Same | Ack latency including the slowest ISR follower (Kafka note 3) |
| Client statistics: average batch size, request counts, internal queue depth | librdkafka statistics via `statistics.interval.ms`, fed into the metrics service (`stats_cb` in `producer.service.ts`) **[observed in source]** | Layer 2 behavior and in-flight requests |
| Broker: record batch counts and sizes | `kafka-dump-log.sh` on a segment (`count:` and `size:` per batch) | What actually reached the log (layer 3) |

In a dumped segment [observed, Kafka note 1 and this run]: batches of `count: 16` and `size: 16205` bytes (the load test's 16 KiB batches), and batches of `count: 177` to `186` for 341-byte JSON records with 64 KiB batches. Those counts are the ground truth for "how well did we batch".

## 13. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| Batcher flush rule | **500 messages or 900 KB or 5 ms** (`BATCH_MAX_MESSAGES`, `BATCH_MAX_BYTES`, `BATCH_MAX_WAIT_MS`) | Fill batches under load, bound added latency to 5 ms |
| Client `linger.ms` | **0** (`KAFKA_LINGER_MS`) | Let the batcher alone decide; avoid stacking waits. K2 can compare |
| Max in flight batches | **1** (`BATCH_MAX_IN_FLIGHT`) | Per-key ordering across batches (producer note 5) |
| `batch.size`, buffer sizes | Library defaults | Not the bottleneck at Stage 2 volumes; sweep in K2 |
| Queue bound | `BATCH_MAX_QUEUE=10,000`, `BATCH_MAX_QUEUE_BYTES=64 MB` | Bounded memory, fast 503 (Step 5) |
| Batch cap | `BATCH_MAX_BYTES <= 1,000,000` enforced in config | Never exceed broker's batch limit |

**An open question for K2, based on section 9's numbers:** is the batcher faster than the library's own batching for this API, and at what concurrency? The measurements above say that at **500 concurrent callers** the library with `linger.ms=5` was about twice as fast as the batcher with `linger.ms=0`, and that at **1 sequential caller** the batcher's 5 ms wait cut throughput by about 8x (133 versus 1,049 records/s, producer note 7). Both effects are real; what matters is your actual concurrency. A cheap safeguard if it is low: lower `BATCH_MAX_WAIT_MS` (1 or 2 ms).

## 14. Build checklist

**Step 1: S2-F1**

- [ ] The batcher flushes on count, on bytes and on the oldest message's age (not the newest). Unit tests cover all three, plus "wait measured from the oldest message" and "never builds a batch above `maxBytes`" (all present and passing: 25 of 25 in the batcher spec **[observed]**).
- [ ] The producer's `linger.ms` comes from `KAFKA_LINGER_MS` (default 0) and is recorded in `/debug/stats` `config` so every result states the settings it ran with (Step 6).
- [ ] `BATCH_MAX_BYTES` is validated against the broker's batch limit at startup (already enforced).
- [ ] `producer-perf-test` once with your event size and `acks=all` to get the raw ceiling (the K1 baseline).

**Step 5: S2-F5**

- [ ] The batcher bounds queued **requests** (count and bytes). Do not rely on the client's buffer for this: it protects a different thing and its error mapping is separate (`ERR__QUEUE_FULL`).

**Step 6: S2-F6**

- [ ] Metrics for batch size (messages and bytes), flush reason, queue wait, queue depth and send duration, with flush reasons as a low-cardinality label.
- [ ] A panel for "batch size versus rate": it tells you whether you are in the under-loaded or loaded regime.

**Experiments**

- [ ] K2: sweep `BATCH_MAX_WAIT_MS`, `BATCH_MAX_MESSAGES`, `KAFKA_LINGER_MS` at several arrival rates and concurrency levels, with both batching layers on and off.

## 16. Edge cases

| Case | What happens |
| --- | --- |
| Very low load, `linger.ms` large | Every record waits the full linger. Latency equals `linger.ms` plus the ack |
| One huge record bigger than `batch.size` | Sent in a batch of its own (still bounded by `max.message.bytes`) |
| Skewed key, one hot partition | One batch fills fast, the others wait; per-partition batch sizes are uneven (producer note 6) |
| A batch is slow because one follower is slow | The whole batch waits (Kafka note 3); the next batch for that partition waits behind it when in-flight is 1 |
| Broker down | Batches for its partitions cannot leave; they age in the buffer until the delivery timeout fails them (producer note 5) |
| `buffer.memory` exhausted | `send()` blocks or fails; in EventPulse the batcher's bounds act first |
| Shutdown with records in a batch | Must be flushed (batcher `drain()` and client `flush()`/`disconnect()`), else those requests are lost |
| Compression on tiny batches | Poor ratio; batching and compression reinforce each other (producer note 4) |

## 18. Common confusions

1. **"`linger.ms=0` means no batching."** Records that arrive while a request is in flight still batch together. It only means "do not wait on purpose".
2. **"`batch.size` is the size of every batch."** It is a ceiling. Many batches are smaller.
3. **"Bigger `linger.ms` always means more throughput."** Only when batches would not otherwise fill, and at the cost of p50 latency.
4. **"A `send()` of 500 messages is one batch."** It is up to one batch per partition touched, in up to one request per broker.
5. **"`buffer.memory` makes the producer faster."** It only delays backpressure.
6. **"`batch.size` is counted in messages."** Bytes (the Java client). librdkafka also has a message-count cap.
7. **"My p99 gets worse with larger `linger.ms`."** Tails are dominated by other effects; the clean trend is in p50 under light load.
8. **"The micro-batcher and the client batch the same thing."** They batch different things at different layers (requests into a `send()` vs. records into per-partition batches).
9. **"One wait is enough to reason about."** Layer 1 and layer 2 waits add up if both are on.
10. **"A bigger batch is always safer for the broker."** It must stay under `max.message.bytes` after compression; and a bigger batch also means a bigger unit to lose or retry.

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Record batch | A group of records for one partition, sent, stored, replicated and compressed as a unit |
| `batch.size` | Max bytes of one partition's batch (ceiling) |
| `linger.ms` | Max time to wait for a batch to fill |
| `buffer.memory` | Total unsent bytes the producer may hold |
| `max.block.ms` | How long `send()` blocks on a full buffer or missing metadata |
| Sticky partitioning | Filling one partition's batch before moving on (keyless records) |
| Saturation | Producer sending faster than the cluster can take |
| Micro-batcher | EventPulse's own queue that groups HTTP requests into one `send()` |

### Rules of thumb

```
records per batch  ≈ rate per partition × min(time to fill, linger)
under-loaded: linger = pure latency       loaded: linger irrelevant (batches full)
BODY_LIMIT  <  BATCH_MAX_BYTES (900 KB)  <  broker max.message.bytes (1,048,588)
```

# Kafka Producer: Key and Partitioner

*Producer note 6 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read producer note 1 (batching) and Kafka note 1 (partitions, ordering) first. The key decides the partition: same key, same partition, ordered. Skewed keys create hot partitions. This note shows the exact placement rule, proves it against this cluster, measures a hot partition with a realistic skew, and explains what to do about it. It supports Step 1 (envelope and key mode), Step 2 (consumer parallelism), Step 4 (injecting poison records into a chosen partition) and experiment K9.*

**What was run.** **[observed]** means measured on this repo's cluster (a 6-partition scratch topic, deleted afterwards), computed offline, or read from this repo's source and the installed client's source. The placement rule was **verified three ways**: the Java console producer, the Node client (the one the API uses) and an offline re-implementation of the hash gave **identical per-partition counts**. The skewed data set (50 tenants with a Zipf distribution, 6,000 events) is **synthetic**; real tenants will differ. No broker was stopped. **[reasoning]** marks standard behavior that was not observed here.

**A correction to Kafka note 1.** That note said the Node client's default partitioner (librdkafka `consistent_random`, CRC32) **might** place keys differently from the Java tools. It does not: the compatibility layer of the Node client sets `partitioner = murmur2_random` unconditionally (section 4), which matches the Java client for keyed records. Note 1 has been updated.

## 1. TL;DR

- The **producer decides the partition**, not the broker. For a record with a key, the rule is: **`partition = positive(murmur2(key bytes)) mod number_of_partitions`**. The same key always goes to the same partition (as long as the **partition count** and the **hashing client** do not change).
- Because a partition is an ordered log, **same key means same partition means ordered**. That is the only ordering Kafka gives (Kafka note 1, section 9).
- In EventPulse the key is **`tenant_id`** by default (`KAFKA_KEY_MODE=tenant`) or **`event_id`** (`event`). The first gives **per-tenant order and a hot-partition risk**; the second gives **even spread and no per-tenant order** (this is experiment K9).
- **Skewed keys create hot partitions.** With a realistic skew (one tenant sending 30 % of traffic), **the busiest of 6 partitions took 34.5 % of all events**, 2.07 times the average and **13 times the quietest one** [observed]. The busiest partition's leader, its batch, and its single consumer carry that load, and **adding consumers cannot spread it**.
- **The Node client and the Java tools place keys identically** [observed], so `produce-poison.sh --key tenant_x` lands in the same partition as the API's traffic for that tenant.
- You can **compute a key's partition offline** (section 3); this note's implementation matched the cluster's counts exactly.
- The effective parallelism of a consumer group is limited by the **hottest partition**: **`1 / (largest partition share)`** consumers' worth, **2.9 instead of 6** in the measured case.

> **One-line version:** *The key is a hash into a fixed number of lanes: it keeps each key's records in order, and it spreads load only as evenly as your keys are even.*

## 2. The mental model

A post office that sorts parcels into numbered pigeonholes by the **surname written on them**, using a fixed formula.

| Post office | Kafka |
| --- | --- |
| The formula turns a surname into a pigeonhole number | `murmur2(key) mod N` |
| Same surname always lands in the same hole | Same key, same partition |
| Within a hole, parcels stay in arrival order | Order within a partition |
| A very common surname fills one hole to the brim | A hot key makes a hot partition |
| Adding pigeonholes changes where **every** surname goes | Changing the partition count remaps keys |
| Hiring more clerks does not help if all parcels are in one hole | More consumers do not help a hot partition |
| A parcel with no surname goes into any hole | A keyless record |

## 3. The rule

### 3.1 The formula

For a non-null key, the Java client's default partitioner computes:

```
partition = toPositive( murmur2( keyBytes ) ) mod numPartitions
toPositive(h) = h & 0x7fffffff
```

`murmur2` is the 32-bit MurmurHash2 with the Java client's seed (`0x9747b28c`). Key bytes are the key's encoding (UTF-8 for strings). Nothing else matters: not the value, not the headers, not the time, not how many records came before.

### 3.2 Properties

- **Deterministic**: the same key and the same partition count always give the same partition.
- **Uniform in the long run for many distinct keys**: a good hash spreads distinct keys about evenly. That is a statement about **keys**, not **records** (section 7).
- **Few keys, lumpy spread**: with only a handful of distinct keys the spread is random-looking. Kafka note 1 showed three keys on three partitions landing on two partitions, one left empty.
- **It depends on the count**: changing `numPartitions` changes `mod`, so keys move (section 10).
- **Computable anywhere**: any language with murmur2 can predict the partition. This is how tools can write to the same partition as the producer.

### 3.3 A table you can reuse **[observed: computed offline and matched the cluster]**

With **6 partitions**, `murmur2`:

| Key | Partition |
| --- | --- |
| `tenant_1` | **5** |
| `tenant_2` | **0** |
| `tenant_3` | **1** |
| `tenant_4` | **1** |
| `tenant_5` | **3** |

With **3 partitions**: `tenant_0` goes to **2**, `tenant_1` to **2**, `tenant_2` to **0** (the same result as Kafka note 1's lab, where partition 1 stayed empty).

Fifty tenants (`tenant_1` to `tenant_50`) on 6 partitions fall as **12, 11, 10, 6, 5, 6 tenants** per partition 0 to 5. So even the **count of keys** per partition is uneven (12 versus 5), before any traffic skew is considered.

## 4. Verified

Three independent checks agree **[observed]**:

1. **Java console producer** (the reference client): 6,000 keyed records over 50 tenants into a 6-partition topic. End offsets per partition: **1379, 1355, 640, 398, 157, 2071**.
2. **Node client (`@confluentinc/kafka-javascript`, the API's client)**: the same 6,000 records, default settings: end offsets **1379, 1355, 640, 398, 157, 2071**. And the same with `partitioner: 'murmur2_random'` set explicitly: the same numbers.
3. **Offline implementation of murmur2 in Python**, applying the rule of section 3.1 to the same keys: counts **1379, 1355, 640, 398, 157, 2071**.

All three are identical in every partition, so they put every key in the same place.

Why the Node client matches **[observed in the installed client's source]**:

- The compatibility layer sets `rdKafkaConfig['partitioner'] = 'murmur2_random'` **unconditionally** for producers. In librdkafka, `murmur2_random` means **murmur2 for keyed records** (Java-compatible, as stated by the name's first half) and **random** for records without a key. librdkafka's own default would be `consistent_random` (CRC32), but the compatibility layer overrides it.
- A **custom partitioner is not supported** in this client: passing `createPartitioner` throws a `ERR__NOT_IMPLEMENTED` compatibility error **[observed in source]**. If you ever need a different placement, you must choose the partition yourself (section 11).

Consequences for EventPulse:

- The API (Node) and any tool using Java clients (the Kafka console tools, `kcat` with its murmur2 option **[reasoning]**) agree on placement. `scripts/produce-poison.sh --key tenant_x` (Step 4) lands where the API's events for `tenant_x` land. For `kcat`, check which partitioner it uses; its default may differ **[reasoning, not tested]**.
- You can predict, before running anything, which partition a given tenant will use and which consumer will own it.

## 5. Ordering

The ordering rule, in the producer's terms:

- **All records with the same key go to the same partition, in the order the producer sent them**, and they stay in that order within the partition (Kafka note 1, section 9).
- **Across keys there is no order**, even if both keys happen to share a partition (their relative order is the order of arrival at the leader, not a promise).
- **For the order of one key to survive failures**, retries must not reorder: **idempotent producer** with at most 5 in flight, plus the batcher's single in-flight batch (producer notes 3 and 5).
- **With several senders for the same key** (two API instances, or concurrent HTTP requests for one tenant), the order is the order in which records **reach the batcher and then the broker**, not the order in which clients sent them. A per-tenant order that matters to the business has to come from `occurred_at` or a client sequence, not from Kafka alone.

For EventPulse (Stage 2) the contract does **not** promise per-tenant ordering. It is listed as a known flaw to leave in place ("no ordering or late-event handling"); the key choice keeps the **option** open.

## 6. Choosing the key

The key is built in `encodeEvent` **[observed in `packages/kafka-config/src/envelope.ts`]**: `tenant_id` from the API key (never from the body) in `tenant` mode, `event_id` in `event` mode.

| Property | `tenant_id` (default) | `event_id` |
| --- | --- | --- |
| Per-tenant ordering | **Yes** (within a partition) | **No** |
| Distribution of **keys** | Few keys (tenants): lumpy | Many unique keys: even |
| Distribution of **traffic** | Follows tenant sizes: **skewed** | **Even** |
| Hot-partition risk | **High** when tenants differ in size | Negligible |
| Consumer parallelism | Limited by the hottest partition | Close to ideal |
| Batching efficiency | Hot partition fills, cold ones wait (producer note 1, section 5) | Even batches |
| Duplicates of the same `event_id` | Land in the **same** partition | Land in the **same** partition (same key) |
| Locality for per-tenant processing downstream | Good | None |
| Key size on the wire | Short (about 10 bytes) | UUID, 36 bytes (compresses well) |
| Useful for | Ordering by tenant, per-tenant backlog analysis | Pure throughput |

Important detail: **in both modes a re-sent event goes to the same partition**, because the key is derived from the event (`event_id`) or its owner (`tenant_id`). That keeps the **duplicate** and the **original** in the same partition, which helps nothing for correctness (the sink dedupes by `event_id` anyway) but means that **a retry cannot escape a poisoned partition**.

Other key candidates and why not (for now):

| Candidate | Problem |
| --- | --- |
| `tenant_id + type` | More keys, flatter spread, but orders only per `(tenant, type)`; not needed in Stage 2 |
| `tenant_id` plus a shard number | Spreads a hot tenant but breaks per-tenant order (section 9) |
| A random key | Same as `event_id`, with no benefit |
| No key | Even spread, but no ordering, and **loses the "same event, same partition"** property; sticky/random placement (section 11) |

## 7. Skew

### 7.1 The experiment [observed]

6,000 events, 50 tenants (`tenant_1` to `tenant_50`), tenant sizes following a **Zipf distribution** (weight proportional to `1 / rank^1.2`: a few big tenants and a long tail), 6-partition topic, key = tenant.

The traffic shares of the biggest tenants: `tenant_1` **29.9 %**, `tenant_2` 13.4 %, `tenant_3` 8.2 %, `tenant_4` 6.3 %, `tenant_5` 4.4 %.

Result per partition (identical with the Java and the Node producers):

| Partition | Events | Share | Tenants in it (of 50) | Notable tenants |
| --- | --- | --- | --- | --- |
| 0 | 1,379 | 23.0 % | 12 | `tenant_2` (13.4 %) |
| 1 | 1,355 | 22.6 % | 11 | `tenant_3`, `tenant_4` (together 14.5 %) |
| 2 | 640 | 10.7 % | 10 | |
| 3 | 398 | 6.6 % | 6 | `tenant_5` |
| 4 | 157 | **2.6 %** | 5 | |
| 5 | 2,071 | **34.5 %** | 6 | `tenant_1` (29.9 %) |

| Statistic | Value |
| --- | --- |
| Mean per partition | 1,000 (16.7 %) |
| Maximum / mean | **2.07** |
| Maximum / minimum | **13.2** |
| Hottest tenant's share | 29.9 % of all traffic, 86.6 % of its partition |

### 7.2 Reading it

- **One tenant produced almost a third of the traffic and landed in one partition**, which also happened to hold five other tenants, giving that partition 34.5 % of all events.
- The **least-loaded partition got 2.6 %**: 13 times less. The cluster looks "evenly partitioned" (6 partitions on 3 brokers) and is not evenly loaded.
- The spread would have been **different with a different partition count or different tenant names**: the hash decides, not the traffic. **You cannot fix skew by looking only at partition counts**; you must know the key distribution.

### 7.3 The parallelism ceiling

If each sink consumer can process `c` events/s from **one** partition, the group's throughput is capped by the partition that must process the **largest share**:

```
 sustainable total rate  =  c / (largest partition share)
 effective parallelism   =  1 / (largest partition share)

 measured:   1 / 0.345  =  2.9   (of 6 possible)
 even case:  1 / 0.167  =  6.0
```

So with this skew, a sink that can do `c` = 2,000 events/s per partition sustains about **5,800 events/s in total, not 12,000**, because partition 5 saturates first while partitions 2 to 4 idle. That is the same hot-partition effect as in Kafka note 1, section 10.3, now with numbers.

## 8. Cost of a hot partition

| Where | Effect |
| --- | --- |
| **Leader broker** | The broker leading partition 5 handles 34.5 % of the writes (and the followers replicate 34.5 % of the traffic). One of 3 brokers can be much busier (1 CPU each here) |
| **Producer batching** | The hot partition's batch fills quickly; the cold ones wait for `linger.ms`. Uneven batch sizes (producer note 1) |
| **Consumer** | The one consumer owning partition 5 is the bottleneck. Lag grows on that partition while others read 0 |
| **Time-lag and retention** | The hot partition's unread data ages while the others are caught up; with a per-partition `retention.bytes` it hits the size limit first (Kafka note 5) |
| **Rebalance and failover** | Moving the hot partition to another consumer or broker moves most of the load at once |
| **Poison and stuck partition** | A stuck hot partition blocks the most traffic |
| **Metrics** | Totals look fine; only **per-partition** lag and end offsets show it |

---

## 9. Mitigations

| Mitigation | What it does | Trade-off |
| --- | --- | --- |
| **Detect it first**: per-partition end offsets, lag and bytes (section 12) | You cannot manage what totals hide | None |
| **More partitions** | Spreads the **other** tenants more finely | **Does not split a hot key**: tenant_1 still maps to one partition. Also remaps keys (section 10) |
| **Key by `event_id`** (`KAFKA_KEY_MODE=event`) | Perfectly even spread | **No per-tenant order**; the Stage 2 contract does not need it |
| **Salted key**: `tenant_id` plus a shard number (for example `tenant_1#0` to `tenant_1#3`), applied **only to known hot tenants** or all tenants | Spreads a hot tenant over several partitions | Per-tenant order only within a shard; the consumer or the database must tolerate that; need a rule to choose the shard (round-robin, hash of `event_id`) |
| **Explicit partition** (the producer chooses it, section 11) | Full control: you can rebalance deliberately, or keep a hot tenant alone | Your code now owns the placement; custom partitioners are not supported in this client |
| **Bigger sink capacity per partition** (`c`), larger chunks, concurrency | Raises the ceiling set by the hot partition | Bounded by Postgres |
| **Splitting by tenant size into separate topics** | Isolates a hot tenant | More topics to operate; consumers per topic |
| **Rate-limit or quota the hot tenant at the API** | Protects the system | A product decision |

For Stage 2 the right move is to **measure the skew in an experiment (K9)** with both key modes, show the hot partition in the per-partition lag panel, and record the trade-off. Salting and explicit partitions are options for later stages.

## 10. Changing the partition count

From Kafka note 1, section 10.4, with numbers:

- Partition count can only **increase**. Existing records **do not move**.
- Because `mod N` changes, **keys move**. For the 50 tenants here **[observed: computed offline]**:
  - going from **6 to 12** partitions moves **25 of 50** keys (half);
  - going from **6 to 7** partitions moves **42 of 50** keys (84 %).
  Doubling is the gentlest change (each key either stays or moves to `old + 6`).
- After the change, a key's **new records** are in a different partition from its **old** ones. Per-key order **across** the change is lost, and a consumer reading both partitions sees them in unrelated order.
- Therefore: **choose the count up front with headroom** and treat it as hard to change. EventPulse reads `EVENTS_RAW_PARTITIONS` only when creating the topic (Kafka note 5, section 13). For an experiment needing another count, create a **new** topic.

## 11. No key and explicit partition

**No key (null).** The record is placed to **balance** load, not to keep order: librdkafka's `murmur2_random` chooses a **random** partition for keyless records (Java uses sticky batching instead) **[reasoning]**. Records of the same logical entity may land anywhere. EventPulse always sets a key, so this does not occur.

**Explicit partition.** A message may carry a `partition` field that **bypasses the partitioner**. This is how you would implement salting or a deliberate balancing scheme in this client, since a **custom partitioner is not supported** (section 4). Whether the compatibility layer accepts the field exactly as KafkaJS does was **not tested** here **[reasoning]**; test it before relying on it. Cautions: you must know the **current partition count** (a stale count sends to a nonexistent partition and fails), and your function must be **deterministic and stable** if you want order.

## 12. Observing

| Goal | How |
| --- | --- |
| Records per partition | `kafka-get-offsets.sh --bootstrap-server $B --topic T` (end offsets; start offsets with `--time -2`) |
| Bytes per partition and replica | `kafka-log-dirs.sh --bootstrap-server $B --describe --topic-list T` |

| Predict placement | The murmur2 rule (section 3), offline |
| **A skew number** | **max share** (and `max / mean`) of end-offset deltas per partition. `1 / max share` is the effective consumer parallelism |

Use **deltas** over a run, not totals since the topic was created, as the audit does for offsets (Step 7).

## 16. Edge cases

| Case | What happens |
| --- | --- |
| One giant tenant | One partition carries it; nothing but salting or a different key spreads it |
| Many tiny tenants | Even spread (law of large numbers) |
| Few tenants (3 on 6 partitions) | Some partitions are empty or doubled up |
| Same key from two services using different hashes | Same key in two partitions: order lost. Not the case here (Java tools and Node agree) |
| `tenant_id` with different casing or whitespace | Different bytes, different partition: normalize before keying |
| Key mode switched at runtime | Existing records stay; new ones follow the new key. Per-tenant order breaks across the switch |
| Partition added | Keys move (section 10) |
| An empty or null key | Treated as no key (random partition): validate the tenant is present |
| Very long keys | Bytes on every record; compress well but cost something |

## 18. Common confusions

1. **"The broker picks the partition."** The producer does, from the key.
2. **"Same key always goes to the same partition."** Only while the partition count and the hashing client stay the same.
3. **"Hashing spreads load evenly."** It spreads **keys** evenly (roughly); load follows key sizes.
4. **"More partitions fix a hot tenant."** A single key stays in one partition.
5. **"More consumers fix a hot partition."** One partition, one consumer.
6. **"Kafka guarantees ordering per tenant."** Per partition; per tenant only if the key is the tenant, retries cannot reorder (idempotence), and there is one sender.
7. **"The Node client uses a different hash from Java tools."** It does not here (murmur2).
8. **"Keyless records keep order."** They do not even stay together.
9. **"`event_id` as the key keeps events of a tenant together."** It does the opposite.
10. **"I can change the partition count freely."** It moves keys and breaks order across the change.
11. **"A custom partitioner is available in this client."** It is not; choose the partition explicitly.
12. **"If total lag is zero, partitions are balanced."** Totals hide skew; look per partition.

</details>

### Formulas

```
partition              = (murmur2(key) & 0x7fffffff) mod N
effective parallelism  = 1 / (largest partition share)
sustainable rate       = (per-partition consumer capacity) / (largest partition share)
keys that move when N changes: about half for 6 -> 12, most for 6 -> 7
```

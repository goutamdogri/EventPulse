# Kafka Producer: The Micro-Batcher and the Library Note

*Producer note 7 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read producer notes 1 (batching), 2 (acks) and 5 (retries and timeouts) first. The library note in the brief says: kafkajs has no `linger.ms`; it sends what you hand it, so to batch across concurrent HTTP requests you must build a micro-batcher yourself, and building it teaches the mechanism and is part of this stage. ## 1. TL;DR

- **The problem.** An HTTP API receives many concurrent requests, **one event each**. Each must be answered **only after Kafka acknowledges its event** (202). Sending one `producer.send()` per request wastes per-request overhead (producer note 1), and there is no shared place where requests can be grouped.
- **The micro-batcher** is that place: a small in-process queue that **collects messages from many requests**, flushes them as **one `send()`** when it has **N messages** or the oldest has waited **a few milliseconds**, then **resolves or rejects every waiting request with that batch's outcome**.
- In this repo it is `MicroBatcher` (`micro-batcher.ts`, no framework or Kafka imports, fully unit-tested with a fake sender and fake timers). Defaults: **500 messages, 900 KB, 5 ms, 1 batch in flight**. On top of grouping it provides: a **bounded queue** (count and bytes), a **send timeout**, a **queue-wait limit**, a **circuit breaker**, **graceful drain** on shutdown, and **observer hooks** for metrics.
- **The library note needs a caveat for this repo.** The brief is about `kafkajs`, which has no `linger.ms`. The ADR chose `@confluentinc/kafka-javascript` (librdkafka), which **does** batch internally (`linger.ms`). The batcher is still built, for the **semantics** the library does not give you (per-request resolution, bounds, timeouts, breaker, drain) and for the **learning value**, with the client's own `linger.ms` defaulted to **0** so the batcher alone decides the wait.
- **Measured** [one run each, a script that mirrors the rules]: with **500 concurrent callers**, the batcher matched individual sends at `linger.ms=0` (about **35.9 k** vs **34.5 k** msg/s) but **librdkafka's own `linger.ms=5` was about twice as fast** (**71.9 k**). With **one sequential caller**, the batcher's 5 ms wait cut throughput by about **8x** (133 vs 1,049 msg/s). The batcher's throughput is bounded by **`maxMessages / send latency x maxInFlight`**.
- So: the batcher is **the right place for the guarantees**, **not automatically the fastest way to batch**. K2 decides the tuning; `BATCH_MAX_WAIT_MS`, `BATCH_MAX_IN_FLIGHT` and `KAFKA_LINGER_MS` are the knobs.

> **One-line version:** *The micro-batcher turns many small, individually-awaited requests into a few acknowledged batches, and gives every request an honest answer, a bounded wait and a bounded memory cost.*

## 2. The library note

The brief's statement, restated: **kafkajs has no `linger.ms`; it sends what you hand it.** That was true of kafkajs: its producer sends each `send()` call as its own produce request(s) and does no time-based accumulation. To batch across concurrent callers you had to **collect messages yourself**, which is the micro-batcher.

What this repo uses instead **[observed in the ADR and the client source]**:

| | kafkajs (the brief's library) | `@confluentinc/kafka-javascript` (this repo, pinned 1.11.0) |
| --- | --- | --- |
| Engine | Pure JavaScript | librdkafka (C), in the same process |
| Batching across `send()` calls | **None** | **Yes**: `linger.ms`, per-partition batches (producer note 1) |
| API | KafkaJS | A KafkaJS-compatible API (`KafkaJS.Kafka`, `producer.send({ topic, messages })`), plus any librdkafka property next to the `kafkaJS` block |
| `acks`, compression, timeout | Per `send()` | **Per producer** (the PRD sketch's `acks: -1` inside `send()` throws here) |
| Partitioner | Customizable | Fixed `murmur2_random`; custom not supported (producer note 6) |
| Maintenance | Last release February 2023 | Maintained |

Consequences:

1. **The statement "you must build it yourself" is about the learning and the semantics here, not about a missing feature.** librdkafka would batch concurrent single-message sends if you let it (section 10 shows it doing that well).
2. **The ADR sets `KAFKA_LINGER_MS=0` by default** so that **your** batcher alone decides how long messages wait, and K2 can compare "our batcher" with "librdkafka linger" by changing env vars **[observed in the ADR]**.
3. **Even with the library's batching, you still want a batcher** for what the library does **not** provide to an HTTP API:
   - **One acknowledgement per request, resolved when the batch is acknowledged**, with an error type your filter can turn into a 503;
   - **A bounded queue with an explicit rejection** (`OverloadedError`) instead of unbounded promises;
   - **A send timeout and a queue-wait limit** that make failure fast and honest (producer note 5);
   - **A circuit breaker** that turns a known outage into immediate rejections and keeps memory flat;
   - **Byte caps** under the broker's batch limit;
   - **Graceful drain** on shutdown with a deadline;
   - **Metrics at the right layer** (messages per flush, flush reason, queue wait).
4. **It is the central teaching piece of the stage**: it is where concurrency, backpressure, timers, failure fan-out and shutdown all meet in about 300 lines.

## 3. The problem

```
 HTTP request 1  --> validate --> encode --> ?  --> wait for Kafka ack --> 202
 HTTP request 2  --> validate --> encode --> ?  --> wait for Kafka ack --> 202
 ...                                         ^
 up to thousands of these concurrently       |  what goes here?
```

Without the batcher the "?" is `await producer.send({ messages: [oneMessage] })` inside each request. That works, and with librdkafka it is not even slow, but you get:

- **No explicit limit on waiting requests** (each request is a pending promise inside the client, bounded only by the client's queue).
- **No single place for the rules** about size, time, timeouts and failure.
- **No way to answer "how many events are waiting, how big were the batches, how long did they wait"** without asking the client.
- **Nothing to turn off in an experiment** (K10 needs an unbounded mode; K2 needs the batcher's wait to be tunable).

With the batcher the "?" is `await batcher.enqueue(message)`:

```
 request --> enqueue() --> [ queue ] --> flush: one producer.send(batch) --> ack --> resolve ALL waiters --> 202s
                              ^
                  bounded; timers; breaker; byte caps; metrics
```

## 4. The contract

**[observed in `micro-batcher.ts`]**

```ts
interface BatchMessage { key: string; value: Buffer; headers: Record<string, string> }
interface BatchItem    { message: BatchMessage; sizeBytes: number }      // sizeBytes = key + value + headers
type BatchSender = (messages: BatchMessage[]) => Promise<void>;          // resolves only when Kafka acked all

class MicroBatcher {
  enqueue(item: BatchItem): Promise<void>;      // resolves when ITS batch was acknowledged; rejects otherwise
  drain(deadlineMs = 0): Promise<void>;         // stop accepting, flush everything, wait for in-flight sends
  stats(): { queueDepth; queuedBytes; inFlight; closed; breaker };
}
```

What `enqueue` returns and rejects with:

| Outcome | When | Error | HTTP (Step 5) |
| --- | --- | --- | --- |
| **Resolves** | The batch containing this message was acknowledged | (none) | **202** |
| Rejects | Queue full by count or bytes | `OverloadedError` | 503, `reason: overloaded` |
| Rejects | Breaker open (Kafka known to be down) | `KafkaUnavailableError` | 503, `reason: kafka_unavailable` |
| Rejects | The batch's `send()` failed | The send's error (wrapped as `KafkaUnavailableError` if it means "unavailable") | 503 or 500 |
| Rejects | The `send()` exceeded the send timeout | `KafkaUnavailableError` | 503 |
| Rejects | The message waited too long to be batched | `KafkaUnavailableError` | 503 |
| Rejects | A single message larger than `maxBytes` | `MessageTooLargeError` | 4xx/500 (a bug: the edge limit should prevent it) |
| Rejects | Batcher closed (shutdown) | `BatcherClosedError` | 503 |

Rule of the whole design: **every `enqueue()` promise settles exactly once, and it settles with the outcome of the one batch its message was in.**

## 5. Design decisions

From the file's header comment and options **[observed]**, with the reason for each:

| Decision | Value | Why |
| --- | --- | --- |
| **Flush on size or time or bytes, whichever first** | `maxMessages` 500, `maxWaitMs` 5, `maxBytes` 900,000 | Full batches under load; bounded added latency when quiet; never over the broker's batch limit |
| **The wait is measured from the oldest message**, not the newest | `now - queue[0].enqueuedAt >= maxWaitMs` | Otherwise a steady trickle could postpone a flush forever |
| **Bounded queue**: reject immediately when full | `maxQueue` 10,000 and `maxQueueBytes` 64 MB (`0` = unbounded, experiment K10 only) | No promise or body is kept for a request we cannot serve; memory stays flat |
| **Limit on batches in flight** | `maxInFlight` 1 | Per-key order across batches; with more than 1, two batches carrying the same key can finish out of order |
| **One `send()` equals one outcome** | All waiters resolve or all reject | Matches the client: `send()` of many messages rejects if any fails, though some may have been written |
| **The batcher never retries and never re-queues** | | The client's retries plus idempotence cover transient errors; re-queuing would invent duplicates and reorder |
| **Each message leaves the queue before it is sent** | `splice` in `takeBatch` | Exactly one batch per message: nothing sent twice by the batcher, nothing dropped |
| **Send timeout** | `sendTimeoutMs` 5,000 | A hung broker cannot hold waiters forever (producer note 5) |
| **Queue wait limit** | Same value | A request waits at most "queue wait + send timeout" |
| **Circuit breaker** | 3 failures, 5 s cooldown | Fast failure in an outage; rejects what is queued when it opens |
| **Only "Kafka unavailable" failures count toward the breaker** | | A bad message must not open it |
| **Drain with a deadline** | `drain(deadlineMs)` | Shutdown must answer queued requests, but must not hang if Kafka is down |
| **No framework imports** | Plain class, injected sender and observer | Unit-testable with fake timers |

## 6. How the code works

A guided tour of `MicroBatcher` **[observed]**. The class is built around one idea: **a single function, `pump()`, decides what to do, and it is called whenever anything changes.**

**State**

```ts
private queue: Pending[] = [];       // waiting messages, oldest first: { item, enqueuedAt, resolve, reject }
private queuedBytes = 0;
private inFlight = 0;                // sends currently running
private timer?: NodeJS.Timeout;      // one timer: "wake me when the head of the queue is due"
private closed = false;              // set by drain()
private readonly inFlightBatches = new Set<Pending[]>();   // so drain's deadline can reject them
```

**`enqueue(item)`: admission control, then queue.** In order:

1. Closed? reject `BatcherClosedError`.
2. `item.sizeBytes > maxBytes`? reject `MessageTooLargeError`.
3. Queue full by count or by bytes? reject `OverloadedError` **without creating a promise or keeping the body**.
4. Breaker open? reject `KafkaUnavailableError` (the probe after the cooldown is let through here).
5. Otherwise push `{ item, enqueuedAt, resolve, reject }`, add the bytes, call `pump()`, and return the promise.

**`pump()`: the scheduler.**

```ts
private pump(): void {
  const now = Date.now();
  this.expireQueued(now);                                   // reject messages that waited past the limit
  let reason: FlushReason | undefined;
  while (this.inFlight < this.opts.maxInFlight && (reason = this.readyReason(now))) {
    this.startSend(this.takeBatch(), reason, now);          // start as many batches as slots allow
  }
  this.armTimer(now);                                       // sleep until the next thing is due
  this.notifyIfIdle();                                      // wake drain() if everything is finished
}
```

**`readyReason()`: when may the head of the queue be sent?**

```ts
if (this.queue.length === 0) return undefined;
if (this.queue.length >= maxMessages) return 'size';
if (this.queuedBytes   >= maxBytes)    return 'bytes';
if (this.closed)                       return 'drain';       // draining: send partial batches now
if (now - this.queue[0].enqueuedAt >= maxWaitMs) return 'time';   // the OLDEST waited long enough
return undefined;
```

The returned reason is also the metric label (`size`, `bytes`, `time`, `drain`).

**`takeBatch()`: up to `maxMessages` and `maxBytes`, always at least one.** It walks the queue, adds messages until the next would exceed the byte cap, `splice`s them out and subtracts their bytes. **Removal happens here, before the send.**

**`startSend()`: run one batch, settle all its waiters once.**

- Increments `inFlight`, records the batch in `inFlightBatches`, computes per-message queue waits.
- Defines `finish(error?)` guarded by a **`done` flag**: it can be called by the send timeout **or** by a late result; **the first wins**, the second is ignored.
- In `finish`: decrement `inFlight`, call the observer's `onFlush` (messages, bytes, reason, duration, waits, error), then:
  - **Success:** `breaker.onSuccess()`, resolve every waiter.
  - **Failure:** only a `KafkaUnavailableError` calls `breaker.onFailure()` (anything else releases a half-open probe as a success: the broker did answer); reject every waiter with the same error; **if the breaker just opened, reject everything still queued at once** instead of sending it one failing batch at a time.
  - Finally call `pump()` again: a slot is free.
- Starts the **send timeout** timer (`sendTimeoutMs`), which calls `finish(new KafkaUnavailableError(...))`.
- Calls `this.send(batch messages)` **inside a try/catch**, so a sender that **throws synchronously** still rejects the batch and frees the slot, and attaches `.then(() => finish(), e => finish(e))`.

**`armTimer()`: one timer, the earliest deadline.** It clears the old timer and sets a new one for the earlier of "the head's flush time" (only if a slot is free and not closed) and "the head's expiry time". When it fires it calls `pump()`.

**`expireQueued()`: queue-wait limit.** Messages at the head that waited `>= sendTimeoutMs` without their batch starting are spliced out and rejected (`queue_timeout`).

**`drain(deadlineMs)`.** Sets `closed`, pumps (everything now flushes as `drain`), and waits until the queue is empty and nothing is in flight, racing a deadline timer. At the deadline it **rejects the queue and every in-flight batch's waiters** and returns anyway: the shutdown never hangs.

That is the entire machine: **one queue, one timer, one scheduler, one settle-once function.**

## 7. Invariants

These are what the tests prove and what any rewrite must preserve:

1. **Exactly-one-batch**: every accepted message is in exactly one `send()` call: not zero (dropped), not two (duplicated by the batcher).
2. **Settle exactly once**: every `enqueue()` promise resolves or rejects exactly once, even when a timeout and a late result race.
3. **One outcome per batch**: all waiters of a batch settle the same way.
4. **Bounded**: queued messages and bytes never exceed their limits (unless explicitly set to `0`).
5. **No batch exceeds `maxMessages` or `maxBytes`** (except a single message, which is itself capped).
6. **At most `maxInFlight` sends at once.**
7. **The wait is bounded**: a message waits at most `sendTimeoutMs` before its batch starts, and its batch is bounded by `sendTimeoutMs` more.
8. **Progress**: after any event, `pump()` runs; nothing is left waiting with no timer armed (unless it is waiting for an in-flight slot, in which case `finish()` will pump).
9. **Never retries**.
10. **After `drain()`, new messages are rejected**, and `drain()` returns by its deadline.

## 8. Failure semantics

How each failure shows up (links to producer note 5 for the timers):

| Failure | Batcher behavior | Waiters | Duplicates / notes |
| --- | --- | --- | --- |
| **`send()` rejects** (library gave up) | `finish(error)`, breaker counts it if "unavailable" | All reject | The batch **may have been partly written** (client semantics) |
| **`send()` hangs** | Send timeout fires after 5 s | All reject with `KafkaUnavailableError` | **Zombie write**: the library may still deliver later (producer note 5, section 10) |
| **A late result after the timeout** | Ignored by the `done` flag | (already rejected) | Prevents settling twice and corrupting counts |
| **The sender throws synchronously** | Caught; same as a rejection | All reject | Frees the in-flight slot (a test covers it) |
| **A message waits too long for a slot** | Expiry at the head | That message rejects | |
| **Queue full** | Immediate `OverloadedError` | The new message only | No body is kept |
| **Breaker opens** | Rejects the queue at once; new messages rejected at the door | Everyone queued and new | Probe after the cooldown |
| **A bad message (non-availability error)** | Does **not** count toward the breaker | That batch rejects | One poisonous message fails its whole batch: a known trade-off of one outcome per batch |
| **Shutdown (`drain`)** | Flush, wait, deadline | Waiters answered (202 or 503) | Never silently dropped |

The honest costs of "one outcome per batch": **(1)** a rejected batch may contain events that **were** written, so the client's retry can duplicate them; **(2)** one bad message poisons the whole batch (the validation at the edge is what keeps bad messages out). Both are recorded as known Stage 2 flaws.

## 9. Build it

If you are building it from scratch (the stage asks for that), build it in these **ten steps**, each with the test that proves it. The tests are the ones in the repo's `micro-batcher.spec.ts` (25, all passing **[observed]**); write yours as you go and compare names at the end.

| Step | Add | Test to write |
| --- | --- | --- |
| 1 | `enqueue()` returns a promise; the queue holds `{message, resolve, reject, enqueuedAt}` | A message resolves after a fake sender resolves |
| 2 | **Flush on size**: when `queue.length >= maxMessages`, `splice` that many and `send` once | `maxMessages` items go out in **one** send; timer cleared |
| 3 | **Flush on time**: a timer for the head's due time | One item goes out after `maxWaitMs` (fake timers). **Wait measured from the oldest**, not the newest |
| 4 | **Fan-out**: resolve or reject all waiters of a batch together | Failed send rejects every waiter of that batch, others unaffected |
| 5 | **Exactly one batch per message** | Fail batch 1, succeed batch 2: each message appears in exactly one `send`; total sent equals total enqueued |
| 6 | **Byte cap**: stop a batch before it would exceed `maxBytes`; reject a single oversized message | Batches never above `maxBytes`; a message larger than `maxBytes` rejects |
| 7 | **In-flight limit**: start a new batch only if `inFlight < maxInFlight`; **pump again when a send finishes** | The next batch is not sent until the current one settles; a partial batch whose wait expired while the slot was busy goes out when the slot frees |
| 8 | **Bounded queue**: reject by count and by bytes; `0` means unbounded | Queue full gives `OverloadedError`, queue unchanged; unbounded mode accepts |
| 9 | **Timeouts and breaker**: per-send timeout with a **settle-once guard**, queue-wait expiry, failure counting that ignores non-availability errors, reject-the-queue on open, half-open probe | A never-resolving send rejects all waiters after the timeout; a late result is ignored; breaker open/probe/close/re-open; a bad message does not open the breaker |
| 10 | **`drain(deadline)`** and **observer hooks** | `drain` flushes partials and resolves only after in-flight sends settle; it returns by the deadline with a hung send; after `drain`, new messages reject; the observer receives flush details |

A **minimal skeleton of steps 1 to 5 and 7**, for learning (this is **not** the repo's class; it leaves out bytes, bounds, timeouts, breaker and drain, which are steps 6 to 10):

```ts
type Msg = { key: string; value: Buffer; headers: Record<string, string> };
type Pending = { m: Msg; res: () => void; rej: (e: unknown) => void; at: number };

class MiniBatcher {
  private q: Pending[] = [];
  private inFlight = 0;
  private timer?: NodeJS.Timeout;
  constructor(
    private send: (b: Msg[]) => Promise<void>,
    private o: { maxMessages: number; maxWaitMs: number; maxInFlight: number },
  ) {}

  enqueue(m: Msg): Promise<void> {
    return new Promise((res, rej) => { this.q.push({ m, res, rej, at: Date.now() }); this.pump(); });
  }

  private ready(now: number): boolean {
    if (this.q.length === 0) return false;
    return this.q.length >= this.o.maxMessages || now - this.q[0].at >= this.o.maxWaitMs;  // oldest, not newest
  }

  private pump(): void {
    const now = Date.now();
    while (this.inFlight < this.o.maxInFlight && this.ready(now)) this.flush();
    this.arm(now);
  }

  private flush(): void {
    const batch = this.q.splice(0, this.o.maxMessages);   // removed BEFORE sending: exactly one batch per message
    this.inFlight++;
    let sending: Promise<void>;
    try { sending = this.send(batch.map((p) => p.m)); } catch (e) { sending = Promise.reject(e); }
    sending.then(
      () => { this.inFlight--; batch.forEach((p) => p.res()); this.pump(); },     // one outcome for the whole batch
      (e) => { this.inFlight--; batch.forEach((p) => p.rej(e)); this.pump(); },
    );
  }

  private arm(now: number): void {
    if (this.timer) clearTimeout(this.timer);
    if (this.q.length === 0 || this.inFlight >= this.o.maxInFlight) return;
    this.timer = setTimeout(() => this.pump(), Math.max(0, this.q[0].at + this.o.maxWaitMs - now));
  }
}
```

Traps this skeleton illustrates (each one is a real bug people ship):

1. **Forgetting to `pump()` when a send finishes**: a partial batch waits for the next arrival instead of going out.
2. **Measuring the wait from the newest message**: a steady trickle never flushes.
3. **Leaving messages in the queue while sending** (instead of `splice` first): double sends.
4. **Not clearing and re-arming the timer** after a flush: stale timers fire at odd times, or no timer exists.
5. **Settling a promise twice** (timeout and late result): add the `done` guard when you add timeouts.
6. **A sender that throws synchronously** leaks the in-flight slot.
7. **`await`ing inside `enqueue`**: it would serialize requests; `enqueue` must return the promise and let many callers wait together.
8. **Unhandled rejections**: someone must handle every returned promise (the controller `await`s it).

## 10. Measured

**Setup [observed]:** Node script using the **same client and producer settings as the API** (`acks=-1`, idempotent, `message.timeout.ms=30000`), 400-byte values, keys `tenant_0..49`, 6-partition RF 3 scratch topic, 20,000 messages (5,000 for the sequential case), brokers with 1 CPU each. "Concurrency" is the number of simultaneous callers, each sending one message and waiting for its ack, like HTTP requests. The "batcher" is a copy of the rules (500 messages or 5 ms, **one batch in flight**) in the script.

| Mode | `linger.ms` | Concurrent callers | Messages/s | p50 | p95 | p99 | Avg batch |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Each caller `send()`s alone | 0 | 500 | **34,539** | 8 ms | 52 ms | 68 ms | n/a |
| Each caller `send()`s alone | **5** | 500 | **71,876** | 6 ms | 10 ms | 30 ms | n/a |
| Batcher | 0 | 500 | **35,914** | 10 ms | 47 ms | 70 ms | 500 |
| Batcher | 5 | 500 | **16,661** | 13 ms | 76 ms | 79 ms | 500 |
| Each caller alone | 0 | 50 | 2,845 | 7 ms | 60 ms | 158 ms | n/a |
| Batcher | 0 | 50 | 3,833 | 10 ms | 33 ms | 74 ms | 50 |
| Each caller alone | 0 | 1 | **1,049** | 0 ms | 1 ms | 10 ms | n/a |
| Batcher | 0 | 1 | **133** | 6 ms | 7 ms | 60 ms | 1 |

Reading it:

1. **500 callers, `linger.ms=0`**: the batcher (35.9 k) and individual sends (34.5 k) are about equal. The batcher always built **full batches of 500**; individual sends gave librdkafka many in-flight requests to pipeline. Two different routes to the same ceiling.
2. **500 callers, individual sends, `linger.ms=5`**: **71.9 k msg/s**, twice the others, with the best percentiles. librdkafka's own batching, with several batches in flight per connection, beat a batcher with **one** batch in flight.
3. **Batcher plus `linger.ms=5`: 16.7 k, the worst**: the two waits **add** (the batcher flushes 500, then librdkafka waits up to 5 ms for more before sending that batch, and only one batch is in flight). Exactly the "do not stack waits" warning (producer note 1, section 9) and the reason the repo defaults the client's `linger.ms` to 0.
4. **The sequential caller** shows the cost of a **time-based wait with no concurrency**: every message waits the full 5 ms for company that never comes (133 msg/s vs 1,049). p50 rises from under 1 ms to 6 ms.
5. **At 50 callers** the batcher was somewhat better (3.8 k vs 2.8 k): batches of 50, fewer requests.

**The throughput formula behind rows 1 and 3** (the numbers fit it):

```
 batcher throughput  ≈  (messages per batch  ×  batches in flight)  /  send latency

 500 × 1 / ~0.014 s  ≈  36 k msg/s   (matches the 35.9 k measured with linger 0)
 500 × 1 / ~0.030 s  ≈  16.7 k       (send latency ~30 ms when linger 5 is added: matches 16.7 k)
```

So **`maxInFlight=1` caps the batcher** at `maxMessages / ack latency`. Raising `BATCH_MAX_IN_FLIGHT` raises the ceiling but gives up per-key ordering across batches (a trade-off, unless idempotence plus a per-key ordering strategy takes over; see producer note 5, section 7).

**Caveats on this table.** One run per cell; a laptop; brokers limited to 1 CPU; the Node script is not the repo's `MicroBatcher` and not the API (no HTTP, no validation, no metrics); latencies exclude the HTTP stack. **Treat the ordering of the rows as a hypothesis for K1 and K2**, to be repeated through the real API with the real class.

## 11. When it helps

| Regime | Batcher behavior | Verdict |
| --- | --- | --- |
| **High concurrency** (hundreds of simultaneous requests) | Batches fill by size; the time limit never matters; ack latency is the only bound | **Good**; throughput set by `maxMessages x maxInFlight / latency`. A pipelining client can beat `maxInFlight=1` |
| **Moderate concurrency** (tens) | Batches of tens; time limit sometimes matters | **Good**, wait adds a few ms to p50 |
| **Low concurrency or a single sequential client** | Almost every message waits the full `maxWaitMs` | **Bad for latency**: each request pays `maxWaitMs`; throughput collapses (133 vs 1,049) |
| **Bursty traffic** | Quiet periods add `maxWaitMs`; bursts fill batches | Acceptable; tune `maxWaitMs` for the quiet case |
| **Overload** | Queue bound rejects; breaker handles outages | **The batcher's strength**: bounded memory, fast 503 |

Tuning rules that follow from the measurements:

- **`BATCH_MAX_WAIT_MS` should be small**, a few milliseconds at most; **1 or 2 ms** if real concurrency is low. It is pure added latency unless batches would otherwise not fill.
- **Never stack waits**: keep `KAFKA_LINGER_MS=0` while the batcher's wait is non-zero (or test both explicitly, K2).
- **`BATCH_MAX_MESSAGES` only needs to be as big as concurrency produces**: at 50 concurrent callers, 500 is never reached.
- **`BATCH_MAX_IN_FLIGHT`**: 1 is the safe default for ordering; raising it is a K2 experiment, and the result must be read together with per-key ordering needs.
- **A rule for "do I even need the wait?"**: if the client's own `linger.ms` batches well (the 71.9 k row), the batcher's wait can be **0** and the batcher still provides its semantics (bounds, timeouts, breaker, drain): "flush when the queue is non-empty and a slot is free".

## 12. Wiring

**[observed in `batcher.service.ts`, `producer.service.ts`]**

```
 events.controller  --await enqueue(encodeEvent(...))-->  BatcherService  -->  MicroBatcher
                                                                                  |  send = ProducerService.send
                                                                                  v
                                                          producer.send({ topic, messages })   (Confluent client)
 observer hooks:  onFlush(r)  -> KafkaMetrics (messages, bytes, reason, duration, waits)
                  onReject(r) -> rejected counters by reason (overloaded, breaker_open, too_large, closed, queue_timeout)
```

- **The 202 is sent only after `enqueue()` resolves** (a unit test with a fake batcher that resolves later asserts the response is not sent early; `events.controller.spec.ts`).
- **One batcher per process**, wrapped by a Nest service that owns the breaker and the counters.
- **Shutdown order**: `beforeApplicationShutdown` calls `batcher.drain(SHUTDOWN_DRAIN_TIMEOUT_MS)` **before** the producer disconnects, so queued requests get an answer, but never waits longer than the deadline when Kafka is down.
- **`ProducerService.send`** is the injected sender. It sends to `events.raw` (or `KAFKA_TOPIC`), classifies errors (`classifySendError`) so the batcher sees `KafkaUnavailableError` for the "unavailable" cases, and rebuilds the producer if the client reports it is disconnected.
- **Metrics** the observer feeds (Step 6): `ep_batcher_batch_size_messages`, `..._bytes`, `ep_batcher_flush_total{reason}`, `ep_batcher_queue_wait_seconds`, `ep_batcher_rejected_total{reason}`, queue depth and bytes, in-flight batches, breaker state.

## 16. Edge cases

| Case | What happens |
| --- | --- |
| Exactly `maxMessages` messages arrive together | One batch, `reason: size`, timer cleared |
| One message, nothing else | Flushed after `maxWaitMs` (`reason: time`) |
| A message waiting while the slot is busy and its wait expired | Goes out the moment the slot frees (`pump` after `finish`) |
| A message larger than `maxBytes` | Rejected immediately; never sent |
| A batch that would exceed `maxBytes` | Split: `takeBatch` stops before the next message |
| The sender resolves after the timeout fired | Ignored (`done` flag) |
| The sender throws synchronously | Treated as a rejection; slot freed |
| Breaker opens with messages queued | They are rejected at once |
| `drain()` with a hung send and a deadline | Returns at the deadline; waiters rejected |
| `enqueue()` after `drain()` | `BatcherClosedError` |
| Clock jumps | `Date.now()` based waits can misbehave; the tests use fake timers. A monotonic clock would be safer **[reasoning]** |
| A huge burst | Bounded by queue limits; the rest get immediate 503 |

## 18. Common confusions

1. **"The batcher exists because the client cannot batch."** True for kafkajs, not for this client; it exists for the semantics and the learning.
2. **"Batching in the batcher and in the client are the same thing."** Different layers, different units (requests vs. per-partition records), and the waits stack.
3. **"A bigger `maxWaitMs` is always faster."** Only when batches would not otherwise fill; otherwise it is latency.
4. **"One in-flight batch is fine for throughput."** It caps throughput at `maxMessages / latency`.
5. **"A rejected batch was not written."** It may have been partly written.
6. **"The batcher retries failed batches."** It never does.
7. **"The send timeout cancels the send."** It stops our wait; the library continues.
8. **"The bounded queue protects Kafka."** It protects the API's memory and gives fast failure.
9. **"One bad message only fails itself."** It fails its whole batch (one outcome per batch); edge validation prevents it.
10. **"A micro-batcher is complicated."** It is one queue, one timer, one scheduler (`pump`) and a settle-once function, about 300 lines with all the hardening.
11. **"The measurements show the batcher is slow."** They show the **ceiling and the knobs**, from a mirror script; they are a hypothesis for K2.
12. **"`drain` waits forever."** It has a deadline.

<summary>Short answers</summary>

1. Many concurrent requests each need their own acknowledgement; the batcher groups their messages into one `send()` and resolves each request with its batch's outcome.
2. kafkajs has no `linger.ms`, so you must collect messages yourself. This repo uses the Confluent client (librdkafka), which batches internally; the batcher is built for semantics and learning, with the client's linger defaulted to 0.
3. Per-request resolution with typed errors; a bounded queue with explicit rejection; a send timeout, queue expiry and circuit breaker; byte caps; graceful drain; metrics at that layer.
4. When the queue reaches `maxMessages` or `maxBytes`, or when the oldest message has waited `maxWaitMs` (or on drain). Measuring from the oldest prevents a steady trickle from postponing the flush forever.
5. So the message is in exactly one batch: nothing is sent twice by the batcher and nothing is dropped.
6. Resolve (202); `OverloadedError` (503 overloaded); breaker `KafkaUnavailableError` (503); send error or timeout (503/500); queue timeout (503); `MessageTooLargeError`; `BatcherClosedError` (503).
7. All waiters of a batch resolve or reject together, as the client reports one result per `send()`. Costs: a rejected batch may have been partly written (a retry can duplicate), and one bad message fails its whole batch.
8. A timeout and a late result both calling `finish`: it ensures the batch is settled and counted exactly once.
9. A slot has freed, so a partial batch whose wait expired (or a full batch) can start; without it messages would wait for the next arrival.
10. `(messages per batch x batches in flight) / send latency`: 500 x 1 / 0.014 s, about 36,000 messages/s.
11. The batcher's 5 ms wait and librdkafka's 5 ms linger stack, and with one batch in flight each batch is serial: send latency of about 30 ms, so about 16.7 k/s.
12. Every message waits the full `maxWaitMs` for company that never arrives: 133 vs 1,049 msg/s.
13. They are rejected at once with `KafkaUnavailableError`, instead of being sent one failing batch at a time; memory stays flat and callers fail fast.
14. It stops accepting, flushes everything, and races a deadline timer; at the deadline it rejects the queue and the in-flight waiters and returns.
15. Flush on size; flush on time; wait measured from the oldest; error fan-out; no loss and no double send; byte cap; in-flight limit; bounded queue; timeout with a late result ignored; `drain`.

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Micro-batcher | An in-process queue grouping many requests' messages into one `send()` |
| Flush reason | `size`, `bytes`, `time` or `drain` |
| In flight | A batch handed to the client and not yet settled |
| Fan-out | Settling every waiter of a batch with the batch's outcome |
| Pump | The scheduler function called whenever state changes |
| Settle once | Each promise resolves or rejects exactly once |
| Zombie write | A batch abandoned by the batcher that the library later writes |
| Breaker | Fails fast after repeated "unavailable" errors |

### Settings (observed defaults)

| Env var | Default |
| --- | --- |
| `BATCH_MAX_MESSAGES` | 500 |
| `BATCH_MAX_WAIT_MS` | 5 |
| `BATCH_MAX_BYTES` | 900,000 (max 1,000,000) |
| `BATCH_MAX_QUEUE` / `BATCH_MAX_QUEUE_BYTES` | 10,000 / 64 MB (`0` = unbounded) |
| `BATCH_MAX_IN_FLIGHT` | 1 |
| `KAFKA_SEND_TIMEOUT_MS` | 5,000 |
| `KAFKA_BREAKER_FAILURES` / `KAFKA_BREAKER_COOLDOWN_MS` | 3 / 5,000 |
| `KAFKA_LINGER_MS` (client) | 0 |

### Rules

```
throughput ceiling  ≈  maxMessages × maxInFlight / send latency
waits add:           batcher max wait + client linger
bound on a request:  queue wait (<= send timeout) + send (<= send timeout)
never:               retry in the batcher, wait from the newest, leave messages in the queue while sending
```

# Kafka Producer: Compression

*Producer note 4 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`). Read producer note 1 (batching) first: compression is applied **per batch**, so batching decides how well it works. gzip, snappy, lz4 and zstd trade CPU for network and disk. This note shows what each does to EventPulse-shaped JSON on this cluster, where the CPU is spent, how it interacts with size limits, and what to decide. It supports Step 1 (producer settings), Step 6 (metrics) and experiments K1 and K2.*

**What was run.** **[observed]** means measured on this repo's cluster (3 brokers, 1 CPU and 1 GiB each, RF 3) with five scratch topics (one partition each, deleted afterwards) and the Java `kafka-producer-perf-test.sh`, or read from this repo's source or the installed client's source. The test data was **synthetic JSON shaped like the EventPulse envelope** (3,000 distinct lines, about 341 bytes each, random UUIDs, 50 tenants, 8 event types). **Real data will compress differently**, so treat the ratios as an illustration and repeat the measurement on captured real events. No broker was stopped. **[reasoning]** marks standard behavior that was not observed here.

**Important caveat for the speed numbers.** The Java load generator ran **inside `ep-kafka1`**, a container limited to **1 CPU** that also runs a broker. Compression CPU in the generator therefore competed with the broker for the same core. The **size** results are exact and repeatable; the **throughput** results are distorted by that and from one run each. Do not use them to rank codecs by speed in general.

## 1. TL;DR

- Compression shrinks the bytes a producer sends, the broker stores and replicates, and consumers fetch. It costs **CPU** at the producer and the consumer, and **a little latency**. On JSON events it is **highly effective**: on this cluster **zstd stored 83 bytes per record versus 351 uncompressed (about 4.2x smaller)** and gzip 90 [observed].
- Compression is applied **per record batch**, by the **producer**. The broker stores the batch **exactly as it arrived** (default `compression.type=producer`) and consumers decompress. So **bigger batches compress better** and the codec is a **producer** setting (`KAFKA_COMPRESSION`).
- The codecs sit on a CPU-versus-ratio curve: **gzip** and **zstd** give the best ratios, **snappy** and **lz4** are fast with moderate ratios (about 2.3 to 2.4x here). **zstd** is usually the best compromise **[reasoning]**; the order of speed in this test was distorted by the shared CPU (see the caveat above).
- Savings compound: less network, less **replication traffic** (x2 followers), less **disk** (retention), a **more effective page cache**. For example, at 2,000 events/s the 24-hour disk footprint per broker drops from about **61 GB to about 14 GB** with zstd on this data.
- Limits to keep in mind: the broker's `max.message.bytes` applies to the **compressed** batch while `batch.size` and the batcher's `BATCH_MAX_BYTES` count **uncompressed** bytes (so compression only ever adds headroom). Random-looking data (IDs, already-compressed payloads) compresses poorly.
- EventPulse default is **`none`**; the sweep is a K2 experiment. This note gives you the numbers and the checklist to run it.

> **One-line version:** *Compression turns repetitive JSON into a quarter of the bytes at a CPU price, and because it works on whole batches, batching and compression help each other.*

## 2. The mental model

Vacuum-packing luggage before a flight.

| Packing | Kafka |
| --- | --- |
| One bag of clothes squashed flat | One **record batch** compressed as a unit |
| A bigger bag compresses better (more air to remove) | Bigger batches compress better (more repetition to exploit) |
| A pump that is fast but removes less air | snappy, lz4 |
| A pump that is slow but squeezes hard | gzip, and zstd at higher levels |
| Hand-written serial numbers cannot be squeezed | Random IDs and already-compressed data |
| You pack at home, the airline just carries and stores the bag as is | Producer compresses; broker stores as is |
| The receiver unpacks | Consumer decompresses |

The producer pays at packing time, the consumer at unpacking time. Everything in between (network, replication, disks, caches) moves the smaller bag.

## 3. Where compression happens

```
 producer                                broker (leader)                 follower            consumer
 --------                                ---------------                 --------            --------
 batch of records  ---compress--->  [compressed batch]  ----------> [compressed batch] --> decompress
   (batching, note 1)                 validated (CRC), appended          copied as is          to read records
                                      stored AS IS (no recompression
                                      when compression.type=producer)
```

- **The producer** compresses the **whole batch** (all records of one partition's batch) into one frame. It also computes the batch CRC.
- **The broker** by default **does not decompress or recompress**: topic config `compression.type=producer` means "keep what the producer used". **[observed]** `compression.type=producer` is the setting on `__consumer_offsets` on this cluster; `events.raw` does not override it, so it inherits the default **[reasoning]**.
- **If the topic forces a different codec** (`compression.type=zstd` on the topic, say), the broker must **decompress and recompress** every batch whose codec differs. That moves CPU to the broker, and on a 1-CPU broker it is expensive: avoid it.
- **Followers** fetch the compressed batch as it is stored, so replication traffic shrinks by the same ratio.
- **Consumers** receive the compressed batch and decompress it. The decompression happens inside the client library.
- **Each batch carries its own codec** in its header. A partition can hold batches with different codecs. **[observed]** in `kafka-dump-log.sh` output: `compresscodec: none`, `compresscodec: gzip` and `compresscodec: zstd` each appear per batch, with `count: 186`, `177` and `177` records in the first batches of those runs.

## 4. The codecs

| Codec | Character **[reasoning, general knowledge]** | Notes |
| --- | --- | --- |
| `none` | Nothing to compress | Baseline |
| `gzip` | Good ratio, **highest CPU**, the oldest option | Universally supported. Slow to compress |
| `snappy` | **Fast**, moderate ratio | Designed for speed. Common default in event pipelines |
| `lz4` | **Very fast**, ratio similar to snappy | Very low CPU, especially to decompress |
| `zstd` | **Best ratio per CPU** across a wide range, with **tunable levels** | Newer; needs clients and brokers that support it (Kafka 2.1 or later). Often the best default today |

Broker-side levels exist for recompression (in this cluster's broker config **[observed]**: `compression.gzip.level=-1`, `compression.lz4.level=9`, `compression.zstd.level=3`). Producer-side levels are client settings (Java `compression.gzip.level`, `compression.lz4.level`, `compression.zstd.level`; librdkafka `compression.level`) **[reasoning]**. EventPulse does not set a level, so the library default applies.

## 5. Measured

Five topics, one partition each, RF 3, `min.insync.replicas=2`, `acks=all`, `linger.ms=20`, `batch.size=64 KiB`, 50,000 records drawn at random from the 3,000 distinct JSON lines [observed]. On-disk size of the partition on one broker, divided by 50,000.

| Codec | Bytes on disk | Bytes per record | Size vs none | Ratio | Records/s (generator) |
| --- | --- | --- | --- | --- | --- |
| `none` | 17,571,640 | **351** | 100 % | 1.0x | 29,797 |
| `gzip` | 4,511,637 | **90** | 25.7 % | **3.9x** | 9,649 |
| `snappy` | 7,510,848 | **150** | 42.7 % | 2.3x | 24,814 |
| `lz4` | 7,220,752 | **144** | 41.1 % | 2.4x | 15,778 |
| `zstd` | 4,192,038 | **83** | **23.9 %** | **4.2x** | 13,793 |

Observations that are solid (sizes):

- **zstd was smallest** (83 bytes per record) and **gzip a close second** (90). Both are about **4x** smaller than raw.
- **snappy and lz4 landed at about 2.3 to 2.4x**: they give up some ratio for speed.
- The uncompressed 351 bytes per record on disk is the 341-byte average line plus about 10 bytes of per-record batch overhead (key, timestamp delta, offset delta, lengths).

Observations that are weak (speed), because of the shared 1-CPU container and a single run:

- The order **none > snappy > lz4 > zstd > gzip** in records/s is plausible in the sense that gzip was the slowest, but **lz4 should normally be at least as fast as snappy** **[reasoning]**, so the gap here is a measurement artifact. The "latency" values from the generator in saturation mode are mostly queueing in the producer's buffer and are not comparable between codecs.
- Real conclusions about CPU cost need the production shape: the producer running in the Node process, on its own cores, with the brokers on theirs.

## 6. Ratio

Compression finds **repetition**. What decides how much of it exists:

**Batch size (more records per frame, better ratio).** Each batch is compressed independently. In JSON events, the field names (`"event_id"`, `"tenant_id"`, `"occurred_at"`, `"schema_version"`, `"payload"`, ...) and many values repeat from record to record. A batch of 180 records lets the compressor encode each field name once and reference it 179 times. A batch of 2 records has little to reference. **[reasoning]**: the ratio rises quickly with the first few dozen records per batch and then flattens. This note's runs used batches of about 180 records; the effect of smaller batches was not measured. (It is one more reason to care about batch size, producer note 1, section 10.)

**Content entropy (random parts cannot be squeezed).** In the test data each record carries two random UUIDs (`event_id`, `session`) of 36 characters each. A UUID is 16 bytes of real entropy; a timestamp, a user id and amounts add some more. A rough floor: **about 16 bytes per UUID, plus a few bytes for the time, user id and amounts, is 50 to 80 bytes of true information per record**. zstd's 83 bytes per record is close to that floor, which is why going from 90 to 83 is the last gain available. Real data with fewer random IDs would compress even better; data that is already compressed (images, encrypted blobs, base64 of compressed data) would not compress at all.

**Order of fields and key repetition.** Stable, repeated structure compresses best. EventPulse's envelope is stable, so the structure part compresses to almost nothing.

**Keys and headers.** They are part of the batch and compress along with the values; with `tenant_id` keys repeating, they compress very well.

Practical consequence: **measure on real events**, at the batch sizes you will actually have (a micro-batcher of 500 messages over 6 partitions is about 83 messages per partition batch, producer note 1).

## 7. CPU

Where compression work lands:

| Where | Work | In EventPulse |
| --- | --- | --- |
| **Producer** | Compress each batch before sending (the main cost) | In the **ingest-api** process. The Node client uses **librdkafka threads**, so the compression CPU is **outside the JavaScript event loop** but inside the same process and the same pinned cores (the ADR warns that Node CPU now includes librdkafka threads) |
| **Broker** | Validate the batch (CRC and checks); **no recompression** if `compression.type=producer` | Brokers have 1 CPU each: this is why a forced topic codec would be painful |
| **Follower** | Copy as is | None |
| **Consumer** | Decompress each fetched batch | In `consumer-sink` |

Practical points:

- **Compression moves CPU from the network/disk to the producer.** If the ingest-api CPU is already the bottleneck (it is pinned with `taskset` in this setup), adding gzip or zstd can **lower** the ceiling on the API instead of raising it. K1/K2 should look at **producer CPU** alongside throughput.
- **The sink pays decompression**, per batch fetched, in addition to its parse and DB work. Usually small compared with Postgres, but include it when measuring the consumer's per-partition capacity `c` (Kafka note 1, section 11.2).
- **Latency** impact is the compression time of the batch (sub-millisecond to a few milliseconds for a 64 KiB batch), added to the batch's time in the producer. It is small next to `linger.ms` and the ack time, unless the CPU is saturated.
- **Compressed batches mean fewer, larger network writes**, which can offset some of the cost when the network or the broker is the bottleneck. When the **broker** is the bottleneck (as it is for 1 CPU per broker), compression usually **helps** overall throughput, because the broker handles fewer bytes per record **[reasoning]**; this is a good K2 hypothesis to test properly.

## 8. Savings

Everything downstream of the producer handles fewer bytes.

| Resource | Effect |
| --- | --- |
| **Producer to leader network** | Bytes divided by the ratio |
| **Replication** | Each partition's bytes are copied to 2 followers (RF 3). Compression divides that traffic too (broker CPU and network) |
| **Disk space** | Retention-sized (Kafka note 5, section 8) |
| **Page cache** | More records fit in the same memory, so more reads are served from RAM and followers/consumers that are slightly behind stay in cache |
| **Consumer fetch** | Fewer bytes over the wire (but the decompression is on the consumer) |

Worked example (illustrative, from this note's measured sizes; replace with your real numbers): 2,000 events/s, 24 h retention, RF 3 on 3 brokers (every broker holds a full copy, Kafka note 5, section 8):

| Codec | Per-record bytes | Bytes per second | Per day, per broker |
| --- | --- | --- | --- |
| none | 351 | 702 KB/s | about **61 GB** |
| snappy | 150 | 300 KB/s | about 26 GB |
| zstd | 83 | 166 KB/s | **about 14 GB** |

(2,000 x 351 B x 86,400 s is about 60.7 GB; 2,000 x 83 B x 86,400 s is about 14.3 GB.) A 4x reduction in disk and replication traffic for the same retention window, which also means a 4x longer window for the same disk.

## 9. Size limits

Several limits count different things (see producer note 1, section 11). With compression:

| Limit | Counts | Effect of compression |
| --- | --- | --- |
| `batch.size` (client) | **Uncompressed** bytes of one partition's batch | None: the batch is filled first, then compressed |
| `BATCH_MAX_BYTES` (batcher, 900,000) | **Uncompressed** bytes (`sizeBytes`: key plus value plus header bytes) | None |
| `max.message.bytes` (**topic**, 1,048,588) | The **compressed batch** as written to the log | Compression gives **headroom**: a batch that is 4x compressible could be 4x larger uncompressed |
| `BODY_LIMIT` (HTTP edge) | One request body, 64 KB | None |

Rules:

- **Do not raise `BATCH_MAX_BYTES` because compression exists.** The batcher cannot know how well a batch will compress, and a batch of random data does not compress. Staying with uncompressed sizes keeps you safe whatever the codec.
- **A single record that compresses poorly** still has to fit `max.message.bytes` on its own.
- **Consumer memory** is governed by compressed fetch sizes on the wire, but decompressed data is what the consumer holds. A highly compressible batch can expand a lot in memory (this is also why the sink's `maxBytes` settings should be set with the decompressed size in mind) **[reasoning]**.

## 10. Configuration

| Fact | Evidence |
| --- | --- |
| The codec is a **producer** setting, not a topic setting, in EventPulse (the topic keeps `compression.type=producer`) | **[observed]** broker/topic configs |
| In this client, the codec is set when **creating the producer**, not per `send()`. Passing `compression` in `send()` throws | **[observed in the library source]**: `send` rejects `acks`, `timeout` and `compression` options with a compatibility error |
| The client maps the `compression` option to librdkafka's `compression.codec` | **[observed in the library source]** |
| EventPulse supports `none`, `gzip`, `snappy`, `lz4`, `zstd`, from `KAFKA_COMPRESSION` (default `none`) | **[observed in `config.ts` and `producer.service.ts`]** |
| Each batch has its own codec, so a topic can hold a mix after you change settings | **[observed]** `compresscodec:` per batch in the dump |
| Changing the codec needs an API restart (the producer is built once) | **[observed in the ADR]** |
| Whether the Node client's bundled librdkafka supports **all four** codecs was **not tested** here | **[reasoning]**: the code maps all four, but run each one through the Node client once before trusting a K2 result |

## 13. Decision guide

| Situation | Choice |
| --- | --- |
| Producer CPU is the bottleneck, network and brokers are fine | `none` or `lz4`/`snappy` |
| Brokers or network or disk are the bottleneck, producer has spare CPU | `zstd` (or `gzip`), larger batches |
| Disk or retention cost dominates | `zstd` |
| Lowest latency, tiny batches | `none` or `lz4` (small batches compress poorly anyway) |
| Data is already compressed or random | `none` |
| Mixed consumers on old clients | `gzip` or `snappy` (widest support); check before using `zstd` |
| Do not force a topic-level codec | Leave `compression.type=producer` |

For EventPulse the **likely** winner on a 1-CPU-per-broker lab is `zstd` or `snappy`, because the **brokers** are the scarce resource, but that is a hypothesis for K2, not a result.

## 16. Edge cases

| Case | What happens |
| --- | --- |
| Tiny batches (low load, `linger.ms=0`) | Poor ratio, still some CPU cost. Compression pays when batches are large |
| Incompressible payloads | Little or no saving; CPU spent for nothing |
| Topic-level `compression.type` different from the producer's | Broker recompresses each batch: CPU on the (small) broker |
| Producer codec changed during a run | Mixed codecs in the log; consumers handle it |
| Old consumer without zstd support | Fails to decode zstd batches; check client versions |
| A batch that compresses to nearly its original size | Some codecs store it uncompressed internally; no harm |
| Very large decompressed size from a small compressed batch | Consumer memory spike (sizing of consumer fetch limits) |
| CPU-starved producer | Compression adds queueing; batches get larger and throughput can fall |

## 17. Commands that were run

(Scratch topics `lab.c.none`, `lab.c.gzip`, `lab.c.snappy`, `lab.c.lz4`, `lab.c.zstd`; each 1 partition, RF 3; deleted afterwards. `K` runs a command in `ep-kafka1`; the payload file was copied into the container.)

```bash
B=kafka1:19092
K() { docker exec -i ep-kafka1 /opt/kafka/bin/"$@"; }

# data: 3,000 JSON lines shaped like the envelope, ~341 bytes each (generated with a short script, then docker cp)

  K kafka-producer-perf-test.sh --topic lab.c.$c --num-records 50000 --payload-file /tmp/payload.txt --throughput -1 \
    --command-property bootstrap.servers=$B acks=all compression.type=$c linger.ms=20 batch.size=65536
done

# bytes per record on disk (leader/replica on broker 1)
K kafka-log-dirs.sh --bootstrap-server $B --describe --topic-list lab.c.zstd     # size field of the replica
K kafka-get-offsets.sh --bootstrap-server $B --topic lab.c.zstd                  # record count

# codec per batch
docker exec ep-kafka1 sh -c 'f=$(ls /var/lib/kafka/data/lab.c.zstd-0/*.log | head -1); /opt/kafka/bin/kafka-dump-log.sh --files $f | head -3'
```

## 18. Common confusions

1. **"The broker compresses my data."** By default it stores exactly what the producer sent. It only recompresses if the topic forces a different codec.
2. **"Compression is per record."** Per **batch**.
3. **"Compression is a topic setting."** In EventPulse it is a producer setting; the topic should stay `producer`.
4. **"Higher compression is always better."** It costs CPU; on a CPU-bound producer it can lower throughput.
5. **"Compression makes reading slower."** The consumer pays decompression CPU but reads fewer bytes; usually a net win unless CPU-bound.
6. **"Bigger `BATCH_MAX_BYTES` is fine because data is compressed."** The batcher cannot know the ratio; keep limits on uncompressed bytes.
7. **"All codecs have the same support."** Client and broker versions matter, especially for zstd.
8. **"JSON compresses 10x."** Structure compresses; random IDs do not. Here about 4x.
9. **"The ratio is a property of the codec."** It is a property of the codec **and the data and the batch size**.
10. **"I changed the codec and old data is recompressed."** Old batches keep their codec; only new ones change.
11. **"Speed rankings measured in a shared 1-CPU container are universal."** They are not.
12. **"`max.message.bytes` is checked on the uncompressed size."** On the compressed batch.

## 20. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Compression codec | gzip, snappy, lz4, zstd (or none) |
| Batch compression | One compressed frame per record batch |
| `compression.type` (topic) | `producer` (keep as sent) or a forced codec (recompress) |
| Recompression | Broker decompresses and recompresses to match the topic codec |
| Ratio | Uncompressed size / compressed size |
| Entropy | The information that cannot be squeezed (random IDs) |

### Measured sizes (EventPulse-shaped JSON, bytes per record on disk)

| Codec | Bytes per record | Ratio |
| --- | --- | --- |
| none | 351 | 1.0x |
| snappy | 150 | 2.3x |
| lz4 | 144 | 2.4x |
| gzip | 90 | 3.9x |
| zstd | 83 | 4.2x |

### Rules

```
codec is chosen by the producer; broker keeps it (compression.type=producer); consumer decompresses
ratio improves with batch size; random IDs set a floor
batch.size and BATCH_MAX_BYTES count UNCOMPRESSED bytes; max.message.bytes counts the COMPRESSED batch
```

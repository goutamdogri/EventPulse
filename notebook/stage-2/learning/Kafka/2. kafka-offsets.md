## 1. TL;DR

- An **offset** is the **position of a record within one partition**: 0, 1, 2, ... assigned by the partition leader when the record is appended. It is the record's address inside that partition, not a count of anything global.
- The broker **does not delete a record when it is read**. Reading is a read-only operation on the log. A record leaves only when **retention** removes its segment.
- Because of that, the broker does not need to know who has read what. **The consumer tracks its own progress** as one number per partition, and **commits** that number to Kafka so it survives a restart. That commit is the only thing the broker stores about a consumer's progress.
- A **committed offset is the offset of the next record to read**, which is **the last processed offset + 1**.
- A consumer has two numbers: its **position** (in memory, moves with every fetch) and its **committed offset** (durable, moves only when you commit). **Everything about at-least-once, duplicates and loss is the gap between them.**
- **Commit after the work, not before.** Commit first and crash, and records are lost. Do the work first and crash before committing, and records are redone (duplicates), which the sink's `ON CONFLICT (event_id) DO NOTHING` absorbs.
- A new group with no committed offset starts according to `auto.offset.reset` (`earliest` or `latest`). Offsets can be moved on purpose (reset, seek) to replay data, as long as retention still has it.

> **One-line version:** _An offset is a bookmark per partition, kept by the reader and saved to Kafka on request; the log itself never changes because someone read it._

## 2. The mental model

A partition is a long paper tape with numbered slots (note 1). Reading a slot does not tear it off the tape.

| Tape                                                      | Kafka                                                  |
| --------------------------------------------------------- | ------------------------------------------------------ |
| The number printed on a slot                              | The record's offset                                    |
| The tape stays intact when you read it                    | Records are not deleted on read                        |
| Your finger on the tape                                   | The consumer's **position** (in memory)                |
| A bookmark you slide in and leave there                   | The **committed offset** (durable, in Kafka)           |
| Leaving, then coming back and starting at the bookmark    | Restart or rebalance: resume from the committed offset |
| Two people reading the same tape with their own bookmarks | Two consumer groups with independent committed offsets |
| Sliding the bookmark back to re-read                      | Resetting offsets / replay                             |
| Old tape rolls thrown away from the start                 | Retention moving the log start offset                  |

Compare with a **traditional queue** (RabbitMQ, SQS): the broker hands you a message and deletes it after your ack, so only one logical reader sees it and it is gone afterwards. Kafka is a **log with bookmarks**: many independent readers, replay for free, and the broker is cheap because it does not track each message.

## 3. The numbers

Every partition has several offsets that mean different things. Mixing them up is the most common source of confusion, so learn them as a set.

```
partition events.raw-3

 offset:  100 101 102 103 104 105 106 107 108 109 110 111
         +---+---+---+---+---+---+---+---+---+---+---+---+
         |   |   |   |   |   |   |   |   |   |   |   |   |   (next record goes here: 112)
         +---+---+---+---+---+---+---+---+---+---+---+---+
           ^           ^                       ^           ^
           |           |                       |           |
   log start offset    |                  consumer          log end offset (LEO) = 112
   (oldest kept = 100) |                  position = 109
                       committed offset = 104
                       (next to read after a restart)

   high watermark = 112 here (all ISR replicas have everything). During replication lag it can be lower
   than the leader's LEO. A consumer is never given records at or above the high watermark.
```

| Name                     | Where it lives                               | Meaning                                                                                  | Who moves it                                                 |
| ------------------------ | -------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Log start offset**     | broker                                       | Offset of the oldest record still stored                                                 | Retention (deleting old segments)                            |
| **Log end offset (LEO)** | each replica                                 | The offset the **next** record will get (last record + 1)                                | Appends                                                      |
| **High watermark (HW)**  | leader                                       | Offset up to which **all ISR** replicas have the data. Consumers can read below it only  | Follower replication                                         |
| **Position**             | **consumer, in memory**                      | Offset of the next record the consumer will **fetch**                                    | Every fetch / `seek()`                                       |
| **Committed offset**     | **broker** (`__consumer_offsets`), per group | Offset of the next record this **group** will start from after a restart or reassignment | Only an explicit (or automatic) **commit** or an admin reset |

Notes:

- LEO is "last offset + 1", exactly like a committed offset is "last processed + 1". Both are "next" numbers, which is why `lag = LEO - committed` has no off-by-one: if the group has processed everything, committed equals LEO and lag is 0.
- `kafka-get-offsets.sh` prints the **end offset** per partition (the LEO as the consumer sees it, effectively the high watermark). With `--time -2` it prints the log start offset.
- A consumer group has **one committed offset per partition**, never one per topic.

## 4. An offset belongs to a partition

- **Per partition.** Partition 0 and partition 1 both have an offset 5. A record is identified by `(topic, partition, offset)`. In EventPulse this triple is what the DLQ headers (`dlq.original_topic`, `dlq.original_partition`, `dlq.original_offset`) record so a poison message can always be found again in `events.raw`.
- **Assigned by the leader on append.** The producer never chooses an offset and never learns one before the ack. The producer's `send()` result (record metadata) includes the offset after acknowledgement.
- **Monotonic and never reused.** Offsets only grow. After retention deletes old data, new records keep counting up from the LEO. An offset that existed once will never name a different record.
- **Within a batch, offsets are consecutive.** A record batch has a `baseOffset` and records carry an `offsetDelta` (see note 1, `kafka-dump-log.sh` output: `baseOffset: 4 lastOffset: 19 count: 16`).
- **Not guaranteed gap-free in general.** Transaction markers and compacted topics leave gaps. For plain produce-only topics like `events.raw`, `end - start` equals the record count. The audit (Step 7) relies on that, so state the assumption in the script.
- **Not a timestamp, not an id.** It says nothing about when the event happened (`occurred_at`) or when the API got it (`received_at`). Two partitions' offsets cannot be compared with each other.

## 5. The broker does not delete on read

The second half of the idea, spelled out:

- A fetch request is a read of bytes from the segment files. Nothing is marked, moved or removed. The record stays exactly as it was.
- **The broker does not track "delivered" or "acknowledged" per message.** It only stores, for each `(group, topic, partition)`, one number that the consumer told it (section 7).
- **Deletion has nothing to do with consumption.** The only things that remove records are retention (time or size), compaction, and topic deletion. See note 1, section 8.

Why Kafka is designed this way, and what you get for free:

| Property                                                    | Consequence                                                                                                   |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Reads are non-destructive                                   | **Many independent consumer groups** read the same topic. Adding an analytics reader does not affect the sink |
| Consumer progress is just a number                          | **Replay** is "move the number back". Reprocess a day of events after fixing a bug                            |
| The broker keeps no per-message state                       | Brokers stay cheap and fast; a million messages cost the same bookkeeping as ten                              |
| A consumer that is slow or down does not block others       | Per-group, per-partition progress; lag grows, nothing is lost until retention                                 |
| Delivery guarantees live in the **consumer's commit logic** | You must design commit order carefully (sections 8 and 10). Kafka will not do it for you                      |

The flip side: **there is no automatic "retry this message later" and no per-message ack.** If one record fails and you refuse to move past it, the whole partition is stuck behind it. That is exactly the poison-message problem of Step 4. Per-message ack, delays and dead-lettering have to be built (which is why the DLQ exists).

And one more consequence that is easy to forget: **because data is kept for 24 h whether read or not, a consumer that is down longer than the retention window loses data it never read** (section 14).

## 6. Position vs committed

A running consumer has two different notions of "where I am":

|                  | **Position**                    | **Committed offset**                                    |
| ---------------- | ------------------------------- | ------------------------------------------------------- |
| Stored in        | the client's memory             | Kafka, in `__consumer_offsets`                          |
| Meaning          | next offset to **fetch**        | next offset to start from after a **restart/rebalance** |
| Moves            | with every fetch, automatically | only on commit                                          |
| Survives a crash | **No**                          | **Yes**                                                 |
| Used for         | the live read loop              | recovery                                                |

```
time -->

 consumer position:    100 -> 150 -> 200 -> 250 -> 300     (advances as batches are fetched)
 committed offset:     100 ------------> 200 ----------->  (jumps when we commit)

 crash at position 300 with committed 200:
   the new consumer starts at 200 and re-reads 200..299    (100 records are reprocessed)
```

That redo window, "position minus committed at the moment of the crash", is the **maximum duplicate count** for that partition. Committing more often shrinks the window but costs more commits (each commit is a write to `__consumer_offsets`, with its own `acks=all` latency). Committing after every chunk of `SINK_MAX_ROWS` (Step 3) bounds duplicates to roughly one chunk per partition.

The reverse failure is the dangerous one: if the **committed offset gets ahead of what was really processed**, those records are skipped forever. Never let that happen (section 10).

## 7. Committing

### 7.1 What a commit is

A commit is a **write to an internal topic**, `__consumer_offsets` (50 partitions, RF 3, `cleanup.policy=compact`). It is an ordinary Kafka topic: the record **key** is `(group, topic, partition)` and the **value** is the offset. Real record from the lab (Lab 5):

```json
{
  "key": { "group": "g1", "topic": "lab.offsets", "partition": 0 },
  "value": {
    "offset": 4,
    "leaderEpoch": -1,
    "metadata": "",
    "commitTimestamp": 1795326464402
  }
}
```

Things worth noticing:

- **Compaction keeps the latest** commit per key. The log of commits can grow, but only the newest value per `(group, topic, partition)` matters. That is the perfect use of `cleanup.policy=compact` (note 1, section 8): "last value per key forever".
- The value stores a **`leaderEpoch`** (which leader's version of the log the offset refers to). It lets a consumer detect that the log was truncated after a leader change, and avoid reading from a position that no longer exists.
- **`metadata`** is a free-form string a client may attach. We do not use it.
- Which partition of `__consumer_offsets` a group's commits go to is `hash(group_id) mod 50`. The **leader of that partition is the group's coordinator**, the broker that manages membership and offsets for the group.

### 7.2 Sync vs async, and what a failed commit means

- A commit can be **synchronous** (wait for the ack) or **asynchronous** (fire and continue). For correctness in Step 3 you want to know the outcome before moving on, so await it.
- A commit can fail: coordinator moved, group rebalancing, broker down. A failed commit means **"the broker doesn't know I got this far"**. The rows are still in Postgres. The next owner re-reads from the older committed offset and `ON CONFLICT` absorbs the duplicates. So a commit failure after a successful DB write causes duplicates, never loss (this is in the Step 3 plan).
- Committing is a **per-group write**. It is not free: it competes with other commits and is one more round trip per chunk. K-experiments that vary batch size will show this cost.

### 7.3 Committed offsets can expire

Committed offsets are not kept forever. If a group has **no active members** for `offsets.retention.minutes` (default **7 days**), the broker removes its committed offsets. A group that comes back after that is treated as new and falls back to `auto.offset.reset`. Separately, data retention (24 h for `events.raw`) will usually have deleted the records anyway. Both mean the same operational rule: **do not leave the sink stopped for longer than the retention window.**

## 8. Last processed plus one

> The committed offset is the offset of the **next** record to read, so it is **last processed offset + 1**.

Real evidence from the lab (Lab 1): topic with 2 partitions, a group consumed and then exited cleanly.

```
consumed:  Partition:1 Offset:0, Offset:1, Offset:2     (last processed = 2)
           Partition:0 Offset:0                          (last processed = 0)

describe:  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
           0          1               7               6        <- last processed 0, committed 1
           1          3               3               0        <- last processed 2, committed 3
```

Commit `last processed` (2) instead of `last processed + 1` (3) and a restart re-reads record 2: a harmless duplicate every time, which hides the bug. Commit `last processed + 2` and you skip a record: silent loss. Both are off-by-one mistakes that no crash ever reveals until you look. That is why Step 3 requires an explicit test for the committed value.

Quick table you can reason with:

| Records processed in partition | Last processed offset | Correct committed offset  | Lag if LEO = 7 |
| ------------------------------ | --------------------- | ------------------------- | -------------- |
| none                           | (none)                | none, or the start offset | 7              |
| 0 only                         | 0                     | 1                         | 6              |
| 0 to 2                         | 2                     | 3                         | 4              |
| 0 to 6 (all)                   | 6                     | 7                         | 0              |

Your client does the +1 for you in one place and not in another. See section 11.

## 9. Where a consumer starts

When a consumer is assigned a partition, it must decide the first offset to fetch:

```
assigned partition P
   |
   v
 does the group have a committed offset for P that is still valid?
   |                                    |
  yes                                   no (new group, expired, or out of range)
   |                                    |
   v                                    v
 start at committed offset        use auto.offset.reset
                                    earliest -> log start offset
                                    latest   -> log end offset (only records from now on)
                                    none     -> throw an error
```

Details:

- A **new group** has no commits, so `auto.offset.reset` decides. **`latest` silently skips all existing data**, which is why it surprises people ("my consumer sees nothing"). Lab 3 shows it: a brand-new group on a topic with 10 existing records read nothing and committed the end offsets (7 and 3).
- A committed offset that is **out of range** (below the log start offset because retention deleted that data, or above the LEO) also triggers the reset policy. With `earliest` you restart from the oldest data that still exists, and you will not be told you missed something. Watch the audit's check H.
- In EventPulse this is `CONSUMER_FROM_BEGINNING` (default `true`, meaning `earliest`) so a first run does not skip data. Your client maps it as `fromBeginning: true -> auto.offset.reset = earliest` (verified in the library source). K11 compares it with `latest`.
- `auto.offset.reset` is **only a fallback**. It does nothing once the group has a valid committed offset. Changing it later will not rewind an existing group (use a reset, section 13).

## 10. Commit strategies

### 10.1 What can be committed, and when

| Strategy                                    | How it works                                                                                                                                     | Risk                                                                                               |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| **Auto-commit** (`enable.auto.commit=true`) | A background timer (default every 5000 ms) commits the offsets of what the client has handed to your code, **whether or not your code finished** | Crash after the timer fires but before your work finished: **records lost**. Never in this service |
| **Manual, after processing**                | You commit after the DB commit                                                                                                                   | Crash between DB commit and commit: duplicates (at-least-once). **EventPulse uses this**           |
| **Manual, before processing**               | Commit first, process after                                                                                                                      | Crash after commit before work: **loss** (at-most-once)                                            |
| **Offset stored with the data**             | Store the offset in the same DB transaction as the rows; on start, read it and `seek`                                                            | No duplicates, no loss for that sink. More code, you own assignment and rebalance handling         |

### 10.2 The order decides the delivery guarantee

```
 A) process, then commit                     B) commit, then process
    ----------------------                      ----------------------
    fetch -> DB COMMIT -> commit offset         fetch -> commit offset -> DB COMMIT
              ^   crash here: rows saved,                  ^   crash here: offset moved,
              |   offset not -> redo -> dup                |   rows never saved -> LOST
    AT-LEAST-ONCE                               AT-MOST-ONCE
```

- **At-most-once**: never duplicates, may lose. Not acceptable for events.
- **At-least-once**: never loses, may duplicate. **EventPulse's choice**, made safe by an idempotent sink: `INSERT ... ON CONFLICT (event_id) DO NOTHING` turns a duplicate into a no-op. The duplicates are counted (`attempted - inserted`), not hidden.
- **"Exactly-once"**: Kafka has transactions that make "consume, process, produce to another topic, commit offsets" atomic (offsets are committed inside the producer transaction). That works Kafka-to-Kafka. For a Postgres sink it is not available, so the practical equivalent is **at-least-once plus an idempotent write** (our choice) or **offset stored in the same Postgres transaction as the rows** (the last row of the table above). Note this as a possible later improvement, not a Stage 2 task.

### 10.3 What "processed" means when there is a failure path

In Step 4 a record can end in two places: stored in Postgres, or published to `events.dlq`. Both count as **handled**, and the offset may only move past a record once its fate is durable in one of them. That is why the plan says: commit only after **both** the DB commit **and** the DLQ ack. If the DLQ publish fails, do not commit, retry the chunk.

### 10.4 Commit granularity

| Commit                                            | Duplicates after a crash              | Commit cost                                               |
| ------------------------------------------------- | ------------------------------------- | --------------------------------------------------------- |
| After every message                               | at most 1                             | very high (one write to `__consumer_offsets` per message) |
| After every chunk (`SINK_MAX_ROWS`, default 1000) | at most about one chunk per partition | low                                                       |
| After every fetched batch or on a timer           | up to a batch or interval             | lowest                                                    |

The plan commits **per chunk**: bounded duplicates at low cost.

## 11. Your client

Facts checked in the installed library (`@confluentinc/kafka-javascript` 1.11.0, KafkaJS-compatible API on librdkafka). Re-verify if you upgrade.

| Topic                                                     | What the client does                                                                                                                                                                |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`fromBeginning`**                                       | Sets `auto.offset.reset` to `earliest` (true) or `latest` (false)                                                                                                                   |
| **`autoCommit` default**                                  | **`true`** if you do not pass it. You must set `autoCommit: false` explicitly in the sink                                                                                           |
| **`enable.auto.offset.store`**                            | Forced to `false` by the promise API: offsets are **stored only when you resolve them**, never automatically on delivery                                                            |
| **`resolveOffset(offset)`**                               | Stores **`offset + 1`** locally. So you pass the **last processed offset** and the library adds the +1. Do not add it yourself, or you skip a record                                |
| **`commitOffsetsIfNecessary()`** with `autoCommit: false` | Calls `commitOffsets()` **immediately** and sends the stored offsets to Kafka. With `autoCommit: true` it does nothing, because librdkafka commits stored offsets in the background |
| **Resolving a lower offset after a higher one**           | Ignored (only the highest is kept)                                                                                                                                                  |
| **`seek()`**                                              | Marks any in-flight `eachBatch` payload stale (so your `isStale()` check stops writing/committing)                                                                                  |

How to read this for Step 3:

- The commit protocol is: **write rows, DB COMMIT, `resolveOffset(lastOffsetOfChunk)`, `commitOffsetsIfNecessary()`**. Resolving is local and cheap; the commit is the network write.
- `resolveOffset` **without** a commit is just a local note. If the process dies there, the note is lost and the chunk is redone. That is safe (duplicates), and is the `after_db_commit` crash point.
- The mistake to avoid: calling `resolveOffset` before the DB commit and then committing in some other code path (for example a timer, a shutdown hook, or `eachBatchAutoResolve: true`). Keep **exactly one place** that resolves and commits, after the DB commit. Use `eachBatchAutoResolve: false` so the library never resolves for you at the end of the callback.
- Add the planned **unit test** that the committed offset equals last processed + 1, and a **call-order test** (`write` before `resolveOffset` before commit).

## 12. Rebalances

When group membership changes (a consumer joins, leaves, crashes, or times out), partitions are reassigned.

- The **new owner of a partition starts from the committed offset**, not from the previous owner's position. Anything the old owner processed but did not commit is **processed again** (duplicates).
- Anything the old owner had resolved but not committed is simply forgotten.
- A consumer that has **lost** a partition must not keep writing for it or commit for it. That is the `isStale()` check in the Step 3 loop: stop before the next chunk, do not commit chunks that were not written.
- Long chunks risk missing heartbeats and being kicked out of the group (session timeout). The plan heartbeats between chunks. Rebalance behavior is covered in a later note and tested by K8.

The key invariant for exactly this note: **committed offsets, not in-memory positions, define what the next owner does.** If your commit logic is right, every rebalance is a safe handover (at worst a bounded replay).

## 13. Moving offsets on purpose

Since the log is not consumed destructively, offsets can be moved. This is a **superpower** (replay) and a **hazard** (skip or reprocess data).

Rules:

- A group's offsets can be reset by an admin only when the group has **no active members** (stop all the sinks first). Otherwise Kafka refuses.
- Always run with `--dry-run` first to see the plan, then `--execute`.
- A target beyond the log end is **clamped to the log end** (Lab 4: asking for offset 999 produced the end offsets 3 and 7). A target below the log start is clamped to the log start.

Common resets (all per group and topic, optionally per partition with `topic:partition`):

| Goal                                                      | Option                                                          |
| --------------------------------------------------------- | --------------------------------------------------------------- |
| Reprocess everything still retained                       | `--to-earliest`                                                 |
| Skip the backlog, start from now                          | `--to-latest`                                                   |
| Specific offset                                           | `--to-offset N` (use `topic:partition` to target one partition) |
| Go back or forward by N from the current committed offset | `--shift-by -N`                                                 |
| Everything since a time                                   | `--to-datetime 2026-11-22T10:00:00.000`                         |
| Last 30 minutes                                           | `--by-duration PT30M`                                           |

Replay is safe for the sink because of `ON CONFLICT (event_id) DO NOTHING`: reprocessing a day of events inserts only what is missing and counts the rest as duplicates. That is a nice demonstration for the Stage 2 report. It is also a way to recover from "committed too far" bugs, but only as far back as `events.raw` retention (24 h).

A consumer in code can also `seek()` to an offset or timestamp (for example to jump over a known-bad record). Do that with extreme care: skipping a record permanently is data loss unless the record was copied to the DLQ first.

## 14. Offsets and retention

Retention moves the log start offset (note 1, section 8). What that does to a consumer's offsets:

```
 log start offset moves from 0 to 5000 (old segments deleted)

   committed offset 6200 : fine, still inside the log
   committed offset 4000 : OUT OF RANGE (that data is gone)
                           -> reset policy kicks in:
                              earliest -> jumps to 5000, records 4000..4999 are never processed
                              latest   -> jumps to the end, even more skipped
                              none     -> error
```

- A consumer **lagging farther than the retention window** is losing data silently at the rate retention deletes it. Lag alarms should fire well before lag equals retention's worth of data.
- The audit snapshots **log start offsets** at the start and end of a run. If the log start moved during the run, it reports a retention finding (check H) instead of a false "missing rows".
- The reverse also happens: after an **unclean leader election** a replica may have a shorter log, so a committed offset can exceed the new log end. `unclean.leader.election.enable=false` in our cluster is what prevents this (and why that setting exists: see the listeners note).

## 15. Lag

**Lag** is how far the group is behind, **in offsets, per partition**:

```
lag(partition) = log end offset - committed offset
total lag      = sum over partitions
```

Things to know:

- **Offset lag is not time lag.** 10,000 records of lag at 20,000 events/s is half a second; the same lag at 50 events/s is minutes. That is why Step 6 also records **`ep_event_freshness_seconds`** (now minus `received_at` at DB commit). Use both.
- **Committed offset is a lower bound on progress.** Records between committed and position are done or in flight but not yet committed, so lag measured from committed offsets **over-reports** lag between commits. A sawtooth in the lag graph that follows your commit interval is normal.
- **Per-partition lag is the signal.** One partition growing while others stay at 0 means a stuck partition (poison message) or a hot key. Total lag hides this.
- **No committed offset yet** shows as `-` in `kafka-consumer-groups.sh` and lag falls back to the reset policy. The Step 6 lag calculator needs a test for "partition with no committed offset".
- **Local lag** inside the consumer is cheap: `highWatermark - lastOffset` of the batch just fetched, available without any admin call. Use it in `/debug/stats`; use the admin-client lag loop for the Prometheus gauge.
- The lag you read from the admin API is **committed offset based**, so it reflects commits, which for the sink happen after the DB commit. In practice that is the number you want: "records not yet safely stored".

## 16. EventPulse

### 16.1 Decisions

| Decision                       | Choice                                                                                                    | Why                                            |
| ------------------------------ | --------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Commit strategy                | **Manual, after DB commit** (and after DLQ ack when needed)                                               | At-least-once, no loss                         |
| Auto-commit                    | **Off** (`autoCommit: false`) from day one                                                                | Auto-commit can commit before the work is done |
| Commit granularity             | Per chunk of `SINK_MAX_ROWS` (1000)                                                                       | Bounded duplicates at low cost                 |
| Offset value                   | `last processed + 1`; `resolveOffset(last)` and let the client add 1                                      | Matches Kafka semantics and the client         |
| Idempotent sink                | `ON CONFLICT (event_id) DO NOTHING`, duplicates counted                                                   | Makes at-least-once safe and visible           |
| Start position for a new group | `CONSUMER_FROM_BEGINNING=true` (earliest)                                                                 | Do not skip existing data                      |
| Crash testing                  | `CRASH_AT=before_parse\|after_parse\|after_db_commit` + `CRASH_AFTER_BATCHES` (guarded by `DEBUG_FAULTS`) | Prove each crash window                        |
| Offset in DB with the rows     | Not in Stage 2                                                                                            | Possible later improvement (section 10.2)      |
| Replay                         | Allowed within the 24 h retention window; sink is idempotent                                              | Recovery and a good demo                       |

**Step 2: S2-F2**

### Lab 1: positions, commits and "last processed + 1"

```bash
K kafka-topics.sh --bootstrap-server $B --create --topic lab.offsets --partitions 2 --replication-factor 3 \
  --config min.insync.replicas=2

    --reader-property parse.key=true --reader-property key.separator=:

# consume exactly 4 records with a named group, then exit (the console consumer commits on exit)
K kafka-console-consumer.sh --bootstrap-server $B --topic lab.offsets --group g1 --from-beginning \
  --max-messages 4 --formatter-property print.partition=true --formatter-property print.offset=true

K kafka-consumer-groups.sh --bootstrap-server $B --describe --group g1
```

What we saw:

```
lab.offsets:0:7   lab.offsets:1:3                      <- end offsets: partition 0 has 7 records, partition 1 has 3
Partition:1 Offset:0 / Offset:1 / Offset:2 and Partition:0 Offset:0     <- the 4 records read

GROUP  TOPIC        PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
g1     lab.offsets  0          1               7               6
g1     lab.offsets  1          3               3               0
```

Check yourself: for each partition, what was the last processed offset and what is committed? (Partition 1: processed 2, committed 3. Partition 0: processed 0, committed 1. So committed is last processed + 1.) Why is `CONSUMER-ID` empty? (No active members: the consumer exited. Offsets persist without a member.)

### Lab 2: resume from the committed offset, and reads do not delete


### Lab 4: resetting offsets (replay)

The group must be inactive (no consumer running).

```bash
# plan only
K kafka-consumer-groups.sh --bootstrap-server $B --group g1 --topic lab.offsets --reset-offsets --to-earliest --dry-run
# move back 2 from the current committed offsets
K kafka-consumer-groups.sh --bootstrap-server $B --group g1 --topic lab.offsets --reset-offsets --shift-by -2 --execute
# one partition only
K kafka-consumer-groups.sh --bootstrap-server $B --group g1 --topic lab.offsets:0 --reset-offsets --to-offset 1 --execute
# beyond the end: clamped
K kafka-consumer-groups.sh --bootstrap-server $B --group g1 --topic lab.offsets --reset-offsets --to-offset 999 --execute
K kafka-consumer-groups.sh --bootstrap-server $B --describe --group g1
```

What we saw: dry-run planned `0` and `0`; `--shift-by -2` moved committed offsets from `(p0=4, p1=3)` to `(p0=2, p1=1)`; `--to-offset 999` was clamped to the end offsets `(p0=7, p1=3)`; afterwards lag was 0.

Then consume with `g1` again after a `--to-earliest --execute`: you get the records again (replay).

Also try, to feel the safety rule: start a consumer in one terminal (`--group g1`, no `--max-messages`), and run `--reset-offsets --execute` in another. Kafka refuses because the group is active. Stop the consumer (Ctrl-C) and retry.

### Lab 5: look at the commits themselves


## 19. Common confusions

1. **"Reading a message removes it."** No. Only retention removes data.
2. **"The broker remembers what each consumer has read."** It stores only the committed number per `(group, topic, partition)`, and only when the consumer commits.
3. **"Committed offset is the last record I processed."** It is the **next** record to read: last processed + 1.
4. **"An offset identifies a record in the topic."** Per partition. Use `(topic, partition, offset)`.
5. **"Position and committed offset are the same."** Position is in memory and moves on its own; committed is durable and moves on commit. The gap is your redo window.
6. **"Auto-commit is fine because it's what everyone uses."** It commits what you were _given_, not what you _finished_. Loss on crash.
7. **"Changing `auto.offset.reset` will rewind my group."** Only for groups with no valid committed offset. Use a reset for existing groups.
8. **"Resetting offsets while the consumer runs is fine."** Kafka refuses; and an in-process `seek()` skips or replays data silently.
9. **"Lag zero means everything is in Postgres."** Lag zero means everything is _committed_. It is only equal to "stored" if your commit order is correct (Step 3).
10. **"After a crash I lose whatever the consumer had fetched."** No: it is still in the log. You redo from the committed offset.
11. **"Offsets are timestamps or ids."** They are positions only, comparable within one partition.
12. **"`resolveOffset` commits."** It stores locally (offset + 1). The commit is a separate network call.
13. **"Committed offsets last forever."** They expire after `offsets.retention.minutes` (7 days) once the group has no members.

<summary>Short answers</summary>

1. The position of a record inside one partition. They are in different partitions (or different topics).
2. No. Only retention (or compaction/topic deletion) removes data.
3. One committed offset per `(group, topic, partition)`, in the compacted internal topic `__consumer_offsets`.
4. Position = next offset to fetch, in memory. Committed = next offset to resume from, in Kafka. Committed survives.
5. Committed is 42. With `resolveOffset(42)` the client stores 43, so record 42 is skipped (it was never processed). Pass the last processed offset, 41.
6. Process-then-commit: a crash between them redoes work but never skips. Commit-then-process: a crash after commit loses records. EventPulse tolerates duplicates because `ON CONFLICT (event_id) DO NOTHING` makes them no-ops, and counts them.
7. Up to 550 (offsets 800 to 1,349). `ON CONFLICT` absorbs the duplicates.
8. Nothing that exists now; only records produced after it joined. It commits the end offset.
9. Out of range, so it jumps to 5,000 (the log start). Records 4,200..4,999 are never processed (silent data loss). Audit check H flags the moved log start.
10. Active members own the offsets; changing them under a running consumer would corrupt its progress.
11. No. Reads are independent and each group has its own committed offsets.
12. A poison message stuck on that partition; a hot key; a slow or stalled consumer owning only that partition.
13. The rows are already in Postgres; the old committed offset only means the new owner re-reads them, and the sink dedupes.
14. `hash(group_id) mod 50`; the leader of that partition is the group coordinator.
15. `autoCommit: false`: it commits the stored (resolved) offsets immediately. `autoCommit: true`: nothing; librdkafka commits stored offsets in the background.

## 21. Cheat sheet

### Glossary

| Term                 | Meaning                                                                      |
| -------------------- | ---------------------------------------------------------------------------- |
| Offset               | Position of a record within one partition                                    |
| Log start offset     | Oldest stored offset (moves with retention)                                  |
| Log end offset (LEO) | Offset the next record will get                                              |
| High watermark       | Highest offset replicated to all ISR; consumers read below it                |
| Position             | Consumer's in-memory next-to-fetch offset                                    |
| Committed offset     | Durable next-to-read offset for a group and partition; last processed + 1    |
| `__consumer_offsets` | Compacted internal topic storing commits                                     |
| Group coordinator    | Broker leading the `__consumer_offsets` partition for a group                |
| `auto.offset.reset`  | Fallback start (`earliest`, `latest`, `none`) when no valid committed offset |
| Lag                  | LEO minus committed offset, per partition                                    |
| At-least-once        | Process then commit: no loss, possible duplicates                            |
| At-most-once         | Commit then process: no duplicates, possible loss                            |
| Replay               | Move offsets back and reprocess retained data                                |

### Commands

| Goal                      | Command                                                                                                                                     |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Group state, offsets, lag | `kafka-consumer-groups.sh --bootstrap-server $B --describe --group G`                                                                       |
| List groups               | `kafka-consumer-groups.sh --bootstrap-server $B --list`                                                                                     |
| End / start offsets       | `kafka-get-offsets.sh --bootstrap-server $B --topic T` / add `--time -2`                                                                    |
| Offset at a timestamp     | `kafka-get-offsets.sh --bootstrap-server $B --topic T --time <ms>`                                                                          |
| Plan a reset              | `kafka-consumer-groups.sh ... --group G --topic T --reset-offsets --to-earliest --dry-run`                                                  |
| Execute a reset           | same with `--execute` (group must be inactive)                                                                                              |
| Reset options             | `--to-earliest`, `--to-latest`, `--to-offset N`, `--shift-by N`, `--to-datetime ...`, `--by-duration PT30M`                                 |
| One partition             | `--topic T:0`                                                                                                                               |
| Read one record by offset | `kafka-console-consumer.sh --topic T --partition P --offset N --max-messages 1`                                                             |
| Delete a group            | `kafka-consumer-groups.sh --delete --group G` (must be inactive)                                                                            |
| Peek at raw commits       | `kafka-console-consumer.sh --topic __consumer_offsets --formatter org.apache.kafka.tools.consumer.OffsetsMessageFormatter --from-beginning` |

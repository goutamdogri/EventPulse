## 1. TL;DR

- A **topic** is a named stream of records (`events.raw`). It is a logical thing. It holds no data itself.
- A topic is split into **partitions**. Each partition is an **append-only log**: records are only added at the end, never edited, never reordered, and each gets a number called an **offset** (0, 1, 2, ...).
- A partition is physically a **directory on a broker's disk** (`events.raw-0/`) containing a series of **segment** files. Only the newest segment (the **active segment**) is written to. Old segments are deleted whole when they expire.
- **Order is guaranteed only within one partition.** Across partitions there is no order at all.
- **Throughput scales by adding partitions**, because partitions are the unit of parallelism: for producers (batches per partition), for brokers (each partition has its own leader), and for consumers (one consumer per partition inside a group).
- Which partition a record goes to is decided by its **key**: same key, same partition, so same-key records stay in order. Records with no key are spread around.
- Reading never removes data. A consumer is just a number (its offset) per partition. Data leaves only by retention.

> **One-line version:** _Kafka is a set of independent append-only files (partitions), grouped under a name (topic), split into chunks (segments) so old data can be dropped by deleting files._

## 2. The mental model

Imagine a sorting office with several numbered **lanes**. Each lane has a long paper **tape** that only ever grows at one end.

| Sorting office                                                              | Kafka                                               |
| --------------------------------------------------------------------------- | --------------------------------------------------- |
| The whole office handling "raw events"                                      | The topic `events.raw`                              |
| One lane with its own tape                                                  | One partition (an append-only log)                  |
| The position number printed on each tape slot                               | The offset (per partition, starts at 0)             |
| The tape is stored as many rolls, only the newest roll is being written     | Segments; the newest is the active segment          |
| Throwing away the oldest roll when it is too old                            | Retention deleting a whole segment                  |
| A clerk who marks "I have read up to slot 4,512 on lane 3" on a sticky note | A consumer group's committed offset for partition 3 |
| Lane chosen by stamping the customer name through a fixed formula           | Partitioner: `hash(key) % partitions`               |

Three consequences fall straight out of this picture, and they explain most of Kafka:

1. **Within a lane, order is exact.** The tape has one end; slot 7 is always before slot 8.
2. **Between lanes there is no order.** Nobody knows whether lane 1 slot 10 happened before lane 2 slot 3.
3. **More lanes means more clerks can work at once**, but one lane can be read by only one clerk of a team at a time (so order is kept).

## 3. Topic

A topic is:

- A **name** (`events.raw`, `events.dlq`). Producers write to a name, consumers read from a name.
- A **configuration bundle**: partition count, replication factor, retention, `min.insync.replicas`, `max.message.bytes`, `cleanup.policy`, and so on.
- A **grouping of partitions**. That is all. The topic never stores bytes. Partitions do.

Topic names are cluster-wide and case sensitive. Kafka warns about mixing `.` and `_` in topic names (they collide in metric names). EventPulse uses dots only: `events.raw`, `events.dlq`.

Our two topics (created by `kafka-init`, see `infra/compose/docker-compose.kafka.yml`):

| Topic        | Partitions                  | RF  | min ISR | Retention | Purpose                                                |
| ------------ | --------------------------- | --- | ------- | --------- | ------------------------------------------------------ |
| `events.raw` | 6 (`EVENTS_RAW_PARTITIONS`) | 3   | 2       | 24 h      | every accepted event, the source of truth for the sink |
| `events.dlq` | 3                           | 3   | 2       | 7 days    | poison messages that the sink could not store (Step 4) |

Why `auto.create.topics.enable=false`: if a producer mistypes `event.raw`, Kafka would silently create a brand-new 1-partition topic with default settings, and your events would vanish into it. With auto-create off, the send fails loudly. This is already set in the compose file.

Two internal topics you will see in the log directory and should not touch:

- `__consumer_offsets` (50 partitions): where consumer groups store their committed offsets. It is a normal Kafka topic.
- `__cluster_metadata`: the KRaft controller's own log (this replaces ZooKeeper).

## 4. Partition

### 4.1 The definition

A partition is an **ordered, immutable sequence of records** that is only appended to. Think "a log file", the same idea as the Postgres WAL you studied in Stage 1, but kept as a product feature instead of an internal detail.

```txt
events.raw-3 (one partition)

offset:    0     1     2     3     4     5     6     7     ...
        +-----+-----+-----+-----+-----+-----+-----+-----+
        | r0  | r1  | r2  | r3  | r4  | r5  | r6  | r7  |  <-- append here (log end offset = 8)
        +-----+-----+-----+-----+-----+-----+-----+-----+
          ^                       ^
     log start offset      consumer committed offset = 4
     (oldest kept)         (next record this group will read)
```

Properties that hold for every partition:

- **Append-only.** There is no update and no delete of a single record. (Compacted topics are the one exception, and we do not use them.)
- **Offsets are per partition.** Partition 0 has an offset 5 and partition 1 also has an offset 5. They are different records. A record is globally identified by the triple `(topic, partition, offset)`. This triple is exactly what the DLQ headers `dlq.original_partition` and `dlq.original_offset` carry in Step 4.
- **Offsets never get reused.** Even after old data is deleted, new records keep counting up. The oldest remaining offset is the **log start offset** (moves up when retention deletes). The next offset to be assigned is the **log end offset** (LEO).
- **Offsets are assigned by the partition leader** when it appends, not by the producer.
- **Offsets are not always contiguous** in general (transaction markers and compaction leave gaps), so never assume `offset == count`. In EventPulse's simple topics they are contiguous, which is why `end offset - start offset` is a fair record count for the audit (S2-F7), but write the audit with the gap possibility in mind.
- **A partition lives wholly on one leader broker** (plus copies on followers). It is never split across brokers. This is why a single partition's throughput is capped by one broker's disk and CPU.

### 4.2 Why split a topic at all?

One log has one writer-side bottleneck (one leader, one disk, one ordered stream) and one reader-side bottleneck (one consumer). Splitting into N logs gives N independent lines that can sit on different brokers and be read by different consumers. The price is that you give up a single global order. Kafka's bargain is: **ordering per key, parallelism across keys.**

### 4.3 What your cluster really looks like

```bash
docker exec ep-kafka1 /opt/kafka/bin/kafka-topics.sh --bootstrap-server kafka1:19092 --describe --topic events.raw
```

Real output:

```txt
Topic: events.raw  PartitionCount: 6  ReplicationFactor: 3  Configs: min.insync.replicas=2,retention.ms=86400000,unclean.leader.election.enable=false
  Partition: 0  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
  Partition: 1  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
  Partition: 2  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
  Partition: 3  Leader: 1  Replicas: 1,3,2  Isr: 1,3,2
  Partition: 4  Leader: 3  Replicas: 3,2,1  Isr: 3,2,1
  Partition: 5  Leader: 2  Replicas: 2,1,3  Isr: 2,1,3
```

How to read it:

- **Leader** is the one broker that accepts writes and serves reads for that partition. Here every broker leads exactly 2 of the 6 partitions. That even spread is the point of choosing 6 partitions on 3 brokers.
- **Replicas** is the list of brokers holding a copy. The first is the "preferred leader".
- **Isr** (in-sync replicas) are the copies that are caught up. With `acks=all` and `min.insync.replicas=2`, a write is acknowledged only when at least 2 ISR members have it.

## 5. A record

What a producer sends and a partition stores:

| Part                            | Meaning in EventPulse                                                                     |
| ------------------------------- | ----------------------------------------------------------------------------------------- |
| **Key** (bytes, optional)       | `tenant_id` by default, or `event_id` when `KAFKA_KEY_MODE=event`. Decides the partition. |
| **Value** (bytes)               | The JSON envelope `{ event_id, tenant_id, type, occurred_at, schema_version, payload }`   |
| **Headers** (list of key/value) | `received_at`, `schema_version`, `request_id`                                             |
| **Timestamp**                   | Set by producer (`CreateTime`) by default; used by the time index and by retention        |
| **Offset**                      | Added by the broker on append                                                             |

Kafka does not care what the bytes mean. Key and value are opaque. That is why **poison messages** exist: the broker happily stores `not json` and the consumer discovers the problem later (Step 4).

### 5.1 Records live inside batches

On the wire and on disk, records are grouped into **record batches**. A batch is the unit that gets a CRC, is compressed, and is replicated. From a real `kafka-dump-log.sh` of a partition (Lab 3):

```txt
baseOffset: 4 lastOffset: 19 count: 16 producerId: 1003 baseSequence: 0 lastSequence: 15
  position: 150 CreateTime: 1795326139846 size: 16205 magic: 2 compresscodec: none crc: 3792167175
```

Read it as: "a batch holding 16 records, offsets 4 to 19, starting at byte 150 of the segment file, 16,205 bytes long". Things worth noticing:

- **Compression is per batch**, so bigger batches compress better. The broker stores the batch exactly as the producer compressed it (default `compression.type=producer`), and the consumer decompresses. This is why `KAFKA_COMPRESSION` is a producer setting (K2).
- **`producerId` / `baseSequence`** are the idempotent producer's duplicate-detection data. The broker uses them to drop a duplicate retry of the same batch. This is why `KAFKA_IDEMPOTENT=true` costs almost nothing and is the default.
- **`max.message.bytes`** (topic config, `1048588` in our cluster) limits the size of a _batch_ (after compression), not just one record. This is why your micro-batcher has `BATCH_MAX_BYTES` (~900 KB): a batch bigger than the broker limit is rejected whole. It is also why the edge `BODY_LIMIT` (64 KB) sits well below it (K12).

## 6. Log on disk

### 6.1 The directory layout

Each partition replica is one directory under the broker's `log.dirs` (`/var/lib/kafka/data` in our containers), named `<topic>-<partition>`:

```txt
/var/lib/kafka/data/
  events.raw-0/
  events.raw-1/
  ...
  events.dlq-0/
  __consumer_offsets-0/ ... -49/
  __cluster_metadata-0/
```

A broker only has directories for partitions it holds a replica of. With RF 3 and 3 brokers every broker has all 6 `events.raw-N` directories (as leader for 2 and follower for 4).

### 6.2 Inside one partition directory

Real listing of `events.raw-0` on a fresh topic:

```txt
00000000000000000000.log          0 bytes   <- the records (the actual log)
00000000000000000000.index   10485760 bytes <- offset index
00000000000000000000.timeindex 10485756 bytes <- timestamp index
leader-epoch-checkpoint                     <- leader history (replication safety)
partition.metadata                          <- topic id
```

And the same partition after we produced about 6 MB and `segment.bytes` was 1 MB (Lab 3):

```txt
00000000000000000000.log        1037270 bytes   <- segment 1 (closed), offsets 0 .. 1027
00000000000000000000.index          504 bytes
00000000000000000000.timeindex      528 bytes
00000000000000001028.log         972300 bytes   <- segment 2 (ACTIVE), offsets 1028 ..
00000000000000001028.index   10485760 bytes
00000000000000001028.timeindex 10485756 bytes
```

### 6.3 What a segment is

A **segment** is one `.log` file plus its `.index` and `.timeindex`. The partition's log is the concatenation of its segments in order.

- **The file name is the base offset**: the offset of the first record in that segment, zero-padded to 20 digits. `00000000000000001028.log` starts at offset 1028. That makes "which file holds offset X?" a simple lookup: the file with the largest base offset that is `<= X`.
- **Only the active segment is written.** It is the one with the highest base offset. Older segments are read-only.
- **The preallocated 10 MB `.index` files** on the active segment are normal. Kafka reserves `segment.index.bytes` (10 MB) up front and shrinks the file when the segment closes. That is why closed segments above show 504 and 528 bytes. Do not be alarmed by a 10 MB index next to a 0 byte log.

### 6.4 When does a new segment start (a "roll")?

The active segment is closed and a new one opened when **any** of these happens:

| Trigger                                       | Config                | Default |
| --------------------------------------------- | --------------------- | ------- |
| Segment would exceed this size                | `segment.bytes`       | 1 GiB   |
| Segment is older than this                    | `segment.ms`          | 7 days  |
| Index file is full                            | `segment.index.bytes` | 10 MB   |
| Offset gap too large for the index to express | (internal)            | rare    |

Our `events.raw` uses the defaults: `segment.bytes=1073741824`, `segment.ms=604800000`. At lab scale you would never see a roll, which is why Lab 3 creates a scratch topic with `segment.bytes=1048576`.

### 6.5 Why segments exist at all

Because **deleting from the middle of a giant file is impossible**, but deleting a whole file is instant. Segments make three things cheap:

1. **Retention**: delete the oldest whole file, no rewriting (section 8).
2. **Lookup**: an offset is found by picking the file by name, then a short search inside (section 7).
3. **Bounded recovery and compaction work**: operations apply to a segment at a time.

### 6.6 The three small companion files

| File         | Maps                                      | Used for                                                      |
| ------------ | ----------------------------------------- | ------------------------------------------------------------- |
| `.log`       | the records, in order                     | everything                                                    |
| `.index`     | **offset to byte position** in the `.log` | a consumer asks for offset N                                  |
| `.timeindex` | **timestamp to offset**                   | "give me data from 10:00" (`--time`), and retention decisions |

Both indexes are **sparse**: one entry roughly every `index.interval.bytes` (4096 bytes) of data, not one per record. Real dump from Lab 3:

```txt
Dumping 00000000000000000000.index
offset: 35 position: 16355
offset: 51 position: 32560
offset: 67 position: 48765
```

(One entry per 16 KB batch here, because the load test's batches were 16 KB.) To find offset 40: binary-search the index for the biggest entry `<= 40` (that is offset 35 at byte 16355), jump to that byte in the `.log`, and read forward until offset 40. A tiny index (memory mapped) plus a short scan, instead of an entry for every record.

## 7. Write and read path

### 7.1 A write

```txt
 producer (batch for partition 3)
     |
     v  ProduceRequest to the LEADER of partition 3
 leader broker
     1. validate batch (CRC, size <= max.message.bytes, idempotence sequence check)
     2. assign offsets, append to the end of the ACTIVE segment (.log)   --> OS page cache
     3. followers fetch the new data and append to their own copies
     4. when every ISR member has it, the "high watermark" advances
     5. respond to producer (acks=all: only after step 4 and ISR >= min.insync.replicas)
```

Key facts:

- **Append only, sequential I/O.** Appending to the end of a file is the fastest thing a disk (and OS) can do. This is the main reason Kafka is fast.
- **No fsync per message by default.** Kafka writes into the OS page cache and lets the OS flush later (`flush.messages` and `flush.ms` default to "never force"). **Durability comes from replication, not from fsync.** That is a real contrast with Postgres, where `COMMIT` waits for a WAL fsync (see `notebook/stage-1/learning/Postgres/2. postgres-write-path.md`). In Kafka with `acks=all` and `min.insync.replicas=2`, "durable" means "in the memory of at least two brokers' OS". Losing all those machines at once could still lose data. This is the reason `min.insync.replicas=2` and `acks=all` matter so much.
- **Consumers cannot read past the high watermark.** Only records that all ISR replicas have are visible, so a consumer never sees data that could vanish in a leader change.

### 7.2 A read

A consumer says "give me from offset N on partition 3":

1. Leader picks the segment by base offset, uses the `.index` to find a byte position, then streams batches from there.
2. Usually the data is still in the **OS page cache** (recent data), so reading is a memory copy, not a disk read.
3. With no TLS, brokers can hand file bytes straight to the network socket (**zero copy**, `sendfile`), skipping the JVM heap.

Reading **does not change** the log. Two consumer groups read the same partition independently, each with its own committed offset. That is the property that lets you add a second consumer (analytics, replay) with zero impact on the sink.

### 7.3 Producers batch per partition

The client collects records into **one batch per partition** and sends the batches grouped by broker. A single `producer.send({ topic, messages: [500 messages] })` from your micro-batcher does **not** become one batch. It is split by partition:

```txt
500 messages, 6 partitions, key=tenant_id
   -> up to 6 record batches (one per partition touched)
   -> up to 3 ProduceRequests (one per leader broker)
   send() resolves when ALL partitions in it are acknowledged
```

Two consequences you will meet in the experiments:

- **More partitions means smaller batches at the same message rate.** 500 messages over 6 partitions is about 83 per batch. Over 60 partitions it is about 8 per batch. Smaller batches mean worse compression and more requests (K1/K2).
- **If one partition's leader is slow or down, the whole `send()` waits or fails**, because `send()` is one outcome for all of its messages. That is why the batcher's rule "one `send()` equals one outcome for every waiter" (Step 1) is honest, and also why a rejected batch may be partly written (a known Stage 2 flaw for the ledger).

## 8. Retention

Data in Kafka is **not deleted when it is read**. It is deleted when it is **old or big enough**, and always **whole segments at a time**.

| Config            | Meaning                                                              | `events.raw`    |
| ----------------- | -------------------------------------------------------------------- | --------------- |
| `cleanup.policy`  | `delete` (drop old segments) or `compact` (keep last value per key)  | `delete`        |
| `retention.ms`    | delete segments older than this                                      | 86400000 (24 h) |
| `retention.bytes` | delete oldest segments if the partition exceeds this (per partition) | -1 (no limit)   |

How deletion actually works, which explains surprising behavior:

1. A background task runs every `log.retention.check.interval.ms` (**5 minutes** by default).
2. A closed segment is eligible when its **newest** record's timestamp is older than `retention.ms`. (Not the oldest. A segment that still contains one fresh record stays.)
3. The **active segment is never deleted**, however old its data is. It must first roll.
4. The eligible segment is renamed with a `.deleted` suffix, and the file is removed `file.delete.delay.ms` (**60 s**) later.
5. The **log start offset** moves up to the base offset of the first remaining segment.

So with `retention.ms=24h`, data may live noticeably **longer** than 24 h: it must wait for the segment to close (size or `segment.ms` of 7 days) and then for the next 5-minute check. With a low-traffic topic and a 1 GiB `segment.bytes`, one segment can sit open for days. That is normal.

Why this matters to EventPulse:

- **A consumer that is down for more than the retention window loses data it never read.** Its committed offset points below the log start offset, and on restart the reset policy (`CONSUMER_FROM_BEGINNING` / `auto.offset.reset`) decides where it lands (K11). The audit's check **H** ("log start offset moved during the run") exists to catch exactly this.
- **Retention is your recovery window.** Because we keep 24 h, you can rewind the group's offsets and reprocess a day of events. After that, Postgres is the only copy.
- The DLQ has 7 days so a human has time to inspect poison messages.

(Compaction, `cleanup.policy=compact`, keeps the latest record per key forever. It is how `__consumer_offsets` works. It is not used for events because events are facts, not "latest state per key".)

## 9. Ordering

> **Order is guaranteed only within a partition.**

Precisely:

- Records written to one partition are stored, and delivered to a consumer, in the order they were appended.
- Records in different partitions have **no defined order**, even if you sent A before B. A consumer reading partitions 0 and 1 may see B before A, depending on fetch timing.
- A consumer group gives each partition to exactly one member, so per-partition order survives parallel consumption.

### 9.1 Getting the order you need: use a key

Same key, same partition (section 10), so **all records for one key are totally ordered**. In EventPulse the key is `tenant_id`, so each tenant's events are ordered; different tenants are not ordered relative to each other, and that is fine.

If you set `KAFKA_KEY_MODE=event` (key = `event_id`, unique per event), you get very even spread across partitions but **no ordering for any tenant**. Trading ordering for balance is the heart of K9.

### 9.2 Ways ordering is broken _within_ a partition (by sending side)

The log is ordered, but the order in the log is the order the **broker received** things. These can reorder what you intended:

| Cause                                                       | What happens                                                               | Fix / EventPulse setting                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Retry without idempotence and more than 1 request in flight | Batch 1 fails and is retried after batch 2 already landed                  | `KAFKA_IDEMPOTENT=true` (broker uses sequence numbers to keep order, allows up to 5 in flight) |
| Two senders for the same key                                | Two API instances each get events for the same tenant                      | Unavoidable; order is then "arrival at broker". Do not promise cross-instance order            |
| Your own batcher with `BATCH_MAX_IN_FLIGHT > 1`             | Two `send()` calls overlap; one may be retried or delayed behind the other | Default `BATCH_MAX_IN_FLIGHT=1`. Above 1, ordering across batches for a key is not guaranteed  |
| Changing the partition count                                | Same key now maps to a different partition (section 10.4)                  | Do not change count on a topic that needs per-key order, or accept the break                   |
| Client retries after a 503 (HTTP level)                     | The same event is sent again later and lands _after_ newer ones            | Retry with the same `event_id`; the sink dedupes, but arrival order is not preserved           |

> **Be honest about what Stage 2 promises.** The plan lists "no ordering or late-event handling" as a known flaw to leave in place. Per-tenant order inside a partition is a property of Kafka that we benefit from, not a guarantee the system exposes. `occurred_at` (client time) and `received_at` (API time) are the real ordering data, and handling them is a later stage.

## 10. The partitioner

### 10.1 The rule

The producer client, not the broker, chooses the partition. For a keyed record:

```txt
partition = hash(key) mod number_of_partitions
```

- The Java client uses **murmur2**. Plain `librdkafka` has its own default partitioner, **`consistent_random`** (a CRC32 hash), which would place keys differently. **But EventPulse's client does not use that default**: the Node client's compatibility layer (`@confluentinc/kafka-javascript`, see `docs/adr/0001-kafka-client-library.md`) sets `partitioner = murmur2_random` unconditionally (murmur2 for keyed records, random for keyless). **Verified [observed]:** the Java console producer, the Node client and an offline murmur2 calculation produced **identical per-partition counts** for the same 6,000 keys (see producer note 6, `../producer/6. kafka-producer-key-and-partitioner.md`). *(An earlier version of this note said the Node client might place keys differently. That was wrong for this client.)*
- **Why it still matters:** the same key lands on different partitions only if you mix in a client that uses a **different** hash (for example plain librdkafka tools with their default, or `kcat` with its default; check before using them). The Kafka console tools and the API agree, so `produce-poison.sh --key tenant_x` (Step 4) lands where the API's events for that tenant land.
- **Records with no key** are spread over partitions to balance load (Java: sticky batches; librdkafka: random per the partitioner). They carry no ordering promise. EventPulse always sets a key.

### 10.2 A real collision, from the lab

With only 3 tenant keys and 3 partitions, using the Java console producer (Lab 2):

```txt
partition 0: tenant_2
partition 1: (empty)
partition 2: tenant_0 and tenant_1 together
```

Three keys did **not** spread evenly over three partitions: two keys shared a partition and one partition got nothing. Hashing is random-ish, so **few keys on few partitions gives lumpy distribution**. This is not a bug. It is the same effect that makes a hot tenant overload one partition.

### 10.3 Hot partitions and key skew

The partition for a key is fixed, so if one key is much busier than the rest, one partition (and therefore one leader broker and one consumer) gets most of the load while others idle:

```txt
key = tenant_id, one tenant sends 80% of traffic
   partition 4: ###########################  (hot: one leader, one consumer saturated)
   partition 0: ###
   partition 1: ##
   ...
```

Adding consumers or partitions does **not** fix this: the hot key still maps to exactly one partition and is read by exactly one consumer. The only fixes are to change the key (spread a hot tenant with a sub-key such as `tenant_id + ":" + (n % k)`, losing strict per-tenant order) or accept it. Detect it by looking at **per-partition** end offsets and per-partition lag, never only totals. You can already check your own cluster:

```bash
docker exec ep-kafka1 /opt/kafka/bin/kafka-get-offsets.sh --bootstrap-server kafka1:19092 --topic events.raw
```

At the time of writing, this printed `events.raw:5:302` and zeros for partitions 0 to 4: every one of the 302 test events had landed in partition 5. That is what a single key does.

### 10.4 Changing the partition count

- You can **increase** partitions on an existing topic. You can **never decrease** them (you would have to create a new topic and migrate).
- Existing data **does not move**. Only new records use the new count.
- Because `hash(key) mod N` changes when N changes, **the same key may start going to a different partition**. For about half the keys when going 3 to 6, new records land in a different partition than the older records of the same key, and per-key order across the change is lost. Lab 5 shows it.
- Therefore: **choose the partition count up front with headroom, and treat it as hard to change.** This is why `EVENTS_RAW_PARTITIONS` is read only by `kafka-init`, and why changing it for a topic that already exists does nothing (`--if-not-exists`). For experiments that need a different count, recreate the topic.

## 11. Throughput and partitions

> **Throughput scales by partitions.** The partition is the unit of parallelism.

### 11.1 Where parallelism comes from

| Layer           | What scales with partitions                                                                                          | Limit when there are too few                       |
| --------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| **Producer**    | Independent batches per partition, sent to different leaders in parallel                                             | One partition = one ordered stream into one leader |
| **Broker**      | Each partition has its own leader, log and disk writes, spread across brokers (our 6 over 3 brokers: 2 leaders each) | Hot broker, idle brokers                           |
| **Replication** | Followers fetch each partition independently                                                                         | Single-partition replication stream                |
| **Consumer**    | In a group, **one partition is read by at most one consumer**                                                        | More consumers than partitions sit **idle**        |

The last row is the hard ceiling you will hit first: **a consumer group's parallelism is capped at the partition count.** With 6 partitions, the 7th `consumer-sink` instance gets nothing (Step 2 test: "extra instances beyond 6 get no assignment"). Inside one process, `CONSUMER_PARTITIONS_CONCURRENTLY` lets one consumer work on several of its partitions at once, but each partition is still processed in order, one batch at a time.

### 11.2 Sizing a topic (rule of thumb)

Measure, then compute:

```txt
p = throughput one producer can push into ONE partition   (measure it)
c = throughput one consumer can process from ONE partition (measure it: your Postgres batch write)
t = target throughput

partitions >= max( t / p , t / c )     then add headroom
```

For EventPulse the consumer side `c` is almost certainly the smaller number (a Postgres transaction per chunk), so **the sink, not Kafka, decides the partition count**. `kafka-producer-perf-test.sh` (Step 1 manual test) gives you the broker/producer ceiling `p`; the end-to-end test in Step 2 gives you `c`.

### 11.3 Why 6 for EventPulse

- **3 brokers x 2 leaders each**: leadership is even, and when one broker dies its 2 partitions move to the other two (typically one each), so the load stays balanced to within one partition.
- **Up to 6 parallel sink consumers**: enough to demonstrate scaling and a rebalance (K8) without idle instances being the story.
- **Not so many that batching degrades** (section 7.3) or that a single laptop's three brokers drown in open files and replication fetchers.
- Cheap to change in the lab (recreate the topic with `EVENTS_RAW_PARTITIONS`), expensive to change in production (section 10.4).

### 11.4 The cost of too many partitions

More is not free. Each partition adds:

- **Open file handles and memory** per replica (segment, index and timeindex files, mapped indexes).
- **Replication overhead**: more fetch work for followers, more state for the controller.
- **Slower failover**: when a broker dies, the controller must elect a new leader for each of its partitions.
- **Smaller producer batches** at a fixed rate (section 7.3), hurting compression and per-request efficiency.
- **Longer end-to-end latency** for each partition's batch to fill.
- **More consumer assignment churn** during rebalances.

Modern KRaft clusters handle thousands of partitions per broker, so for our 6 this is academic. Know the shape of the trade-off so you can answer "why not 600?".

### 11.5 Parallelism does not equal speed

A partition is bounded by **one leader broker**, **one consumer thread of work**, and, for us, **one Postgres transaction at a time per consumer**. Adding partitions past the point where the DB is the bottleneck just moves the queue from Kafka to Postgres connections (`PG_POOL_MAX`). The point of Stage 2 is that the queue now _absorbs_ the mismatch (lag grows instead of 503s), not that it removes it.

## 12. Replication

Each partition has `replication-factor` copies on different brokers.

```txt
partition events.raw-3, RF 3

 broker 1  [LEADER]    log: 0 1 2 3 4 5 6 7         <- producers write here, consumers read here
 broker 3  [follower]  log: 0 1 2 3 4 5 6 7         <- fetches from the leader (in ISR)
 broker 2  [follower]  log: 0 1 2 3 4 5 6           <- a little behind (still in ISR if close enough)
```

Terms you need (the next note goes deeper):

| Term                        | Meaning                                                                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Leader**                  | The one replica that takes all reads and writes for the partition                                                                   |
| **Follower**                | A replica that copies the leader's log by fetching from it                                                                          |
| **ISR**                     | In-sync replicas: the leader plus followers that are caught up                                                                      |
| **LEO** (log end offset)    | Next offset to be written on a given replica                                                                                        |
| **High watermark**          | The offset up to which **all ISR members** have the data. Consumers see only up to here                                             |
| **`acks=all`**              | Producer waits until all ISR members have the record                                                                                |
| **`min.insync.replicas=2`** | If ISR shrinks below 2, `acks=all` writes are **refused** (`NOT_ENOUGH_REPLICAS`) rather than accepted with one copy                |
| **Leader election**         | When the leader dies, a follower from the ISR becomes leader (never an out-of-sync one when `unclean.leader.election.enable=false`) |

Why it belongs in _this_ note: replication is **per partition**, not per topic or per broker. One broker failing triggers an independent leader election for each partition it led. That is why partition count affects failover time, and why in Step 5 "one broker down" gives a brief blip but "two of three down" gives `NOT_ENOUGH_REPLICAS` and 503s.

## 13. Consumer view

A consumer group tracks **one number per partition**: the **committed offset**, the offset of the _next_ record to read. They are stored in the `__consumer_offsets` topic.

```txt
partition 3:  log end offset (LEO)  = 8
              committed offset      = 4        (records 0..3 are done, next to read is 4)
              lag                   = LEO - committed = 4
```

- **Committed offset = last processed offset + 1.** This off-by-one is a classic bug, and Step 3 asks for a test of it.
- **Lag** is `log end offset - committed offset`, per partition. Total lag is the sum. Per-partition lag is the interesting one: one partition with growing lag while others are 0 means a stuck partition (poison message, Step 4) or a hot key (section 10.3).
- **Order of work for Step 3:** _DB commit first, offset commit second._ If the offset were committed first and the process died, the record would be skipped forever (loss). Committing second means a crash between the two re-reads a few records (duplicates), which `ON CONFLICT (event_id) DO NOTHING` absorbs. At-least-once is the deliberate choice.
- A **poison record** blocks only **its own partition**, because that partition cannot advance past the offset that keeps failing. Other partitions keep draining. This is the observable that the Step 4 "before" note should record.

## 14. EventPulse decisions

| Decision                            | Choice                                                                     | Reasoning                                                                                                                     |
| ----------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Partitions of `events.raw`          | **6** (`EVENTS_RAW_PARTITIONS`)                                            | Even leaders on 3 brokers (2 each), up to 6 sink consumers, little batching loss (sections 11.3, 11.4)                        |
| Replication factor                  | **3**                                                                      | Survive one broker loss with no data loss and no downtime                                                                     |
| `min.insync.replicas`               | **2**                                                                      | With `acks=all`: one broker may be down and writes still succeed; two down means refuse (503), never silently under-replicate |
| `unclean.leader.election.enable`    | **false**                                                                  | Prefer an offline partition over electing a stale replica that lost acknowledged writes                                       |
| Message key                         | **`tenant_id`** (`KAFKA_KEY_MODE=tenant`)                                  | Per-tenant order inside a partition. Cost: a hot tenant makes a hot partition (K9)                                            |
| `events.raw` retention              | **24 h** (`retention.ms=86400000`)                                         | Replay window and recovery time. Beyond it, only Postgres has the data                                                        |
| `events.dlq` partitions / retention | **3 / 7 days**                                                             | Low volume, order not needed, humans need time to inspect                                                                     |
| Segment size / age                  | Kafka defaults (1 GiB / 7 days)                                            | Nothing to gain by tuning at this scale. Only shrink them in labs                                                             |
| `auto.create.topics.enable`         | **false**                                                                  | A typo fails loudly                                                                                                           |
| Batch ceiling vs broker limit       | `BODY_LIMIT` 64 KB < `BATCH_MAX_BYTES` ~900 KB < `max.message.bytes` 1 MiB | Oversized input is rejected by the edge, a batch never exceeds the broker limit                                               |
| Cap on parallel sinks               | 6 (= partitions)                                                           | Hard Kafka rule (section 11.1)                                                                                                |

Before you move on, make sure you can explain each row to yourself in one sentence. They are the choices the Stage 2 report will have to defend.

### 15.1 Snippets that tie the concepts to code

Topic creation (already in the compose file, shown for reference). Partition count and replication are fixed here, not in application code:

```bash
kafka-topics.sh --bootstrap-server "$BOOTSTRAP" --create --if-not-exists --topic events.raw \
  --partitions 6 --replication-factor 3 \
  --config min.insync.replicas=2 --config retention.ms=86400000
```

Producing with a key (shape of what the producer sends; the key decides the partition, the client calculates it):

```ts
await producer.send({
  topic: "events.raw",
  messages: [
    {
      key: "tenant_a",
      value: Buffer.from(json),
      headers: { received_at: "..." },
    },
    {
      key: "tenant_b",
      value: Buffer.from(json2),
      headers: { received_at: "..." },
    },
  ],
});
// tenant_a and tenant_b may be in different partitions of the same send(): different batches,
// possibly different brokers. send() resolves only when every partition acknowledged.
```

Consuming, partition by partition (illustrative shape; the real code is in Step 2/3):

```ts
await consumer.run({
  eachBatchAutoResolve: false,
  eachBatch: async ({
    batch,
    resolveOffset,
    heartbeat,
    commitOffsetsIfNecessary,
  }) => {
    // batch.partition  -> which partition these records are from (one partition per call)
    // batch.messages   -> in offset order; each message.offset is that partition's offset
    // batch.highWatermark -> the partition's high watermark (cheap "local lag" = hw - lastOffset)
    for (const m of batch.messages) {
      // ... parse, collect rows ...
    }
    // write rows to Postgres, THEN resolveOffset(lastOffset), THEN commit. Never before the DB commit.
  },
});
```

## 18. Common confusions

1. **"A topic is where data is stored."** No. Partitions store data. A topic is a name plus config over a set of partitions.
2. **"Kafka guarantees message order."** Only within one partition. Globally: no.
3. **"Offsets identify a message in the topic."** Offsets are per partition. The identifier is `(topic, partition, offset)`.
4. **"Consuming deletes the message."** No. Data stays until retention. Many groups can read it independently.
5. **"More consumers always means faster."** Only up to the partition count. Extra consumers idle. A hot key stays on one partition regardless.
6. **"I can reduce partitions later."** No. Increase only, and increasing changes where keys land.
7. **"Retention.ms of 24 h means data is gone after 24 h."** Not exactly: whole segments only, the active segment never, and the check runs every 5 minutes.
8. **"`acks=all` means fsynced to disk."** No: acknowledged by all in-sync replicas (in their OS memory). Durability is by replication. Contrast Postgres `COMMIT`.
9. **"Same key always means same partition."** Only for a **fixed partition count** and the **same hashing client**. Both can change.
10. **"The batcher's one send equals one Kafka batch."** It is split into one batch per partition (and one request per broker).
11. **"A 10 MB index file next to an empty log is a bug."** No: preallocated.
12. **"Total lag is enough to monitor."** No. Per-partition lag finds poison and hot partitions.

8. Retries with more than one request in flight without idempotence; `BATCH_MAX_IN_FLIGHT>1`; changing partition count; multiple senders. Idempotent producer prevents retry reordering.
9. 6 work, 3 are idle (until a member leaves).

11. Existing data stays where it is. New records of an existing key may go to a different partition (about half the keys), breaking per-key order across the change.
12. Lag 60. Next offset to read is 100.
13. One broker can die and writes still succeed (2 in ISR), no write is accepted with fewer than 2 copies. Two down: ISR below 2, writes refused with `NOT_ENOUGH_REPLICAS` (a 503 in our API).
14. `send()` resolves only when every partition in it is acknowledged; one outcome for all waiters.
15. Fsync per message is expensive. Data is in the OS cache of at least the ISR brokers (replication provides durability). The OS flushes later.

## 20. Cheat sheet

### Glossary

| Term                    | Meaning                                                                 |
| ----------------------- | ----------------------------------------------------------------------- |
| Topic                   | Named stream; config + a set of partitions                              |
| Partition               | One ordered append-only log; unit of parallelism, order and replication |
| Offset                  | Position number of a record within one partition                        |
| Log start offset        | Oldest offset still stored (moves up with retention)                    |
| Log end offset (LEO)    | Next offset to be written                                               |
| High watermark          | Highest offset replicated to all ISR; consumers read up to here         |
| Segment                 | One `.log` file plus indexes; the unit of rolling and deletion          |
| Active segment          | The newest segment, the only one being written; never deleted           |
| Base offset             | First offset in a segment; is the file name                             |
| Record batch            | Group of records stored/compressed/checksummed together                 |
| Key                     | Optional bytes that choose the partition                                |
| Partitioner             | `hash(key) mod N` logic, in the client                                  |
| Leader / follower / ISR | Replication roles of a partition's copies                               |
| Committed offset        | Next offset a consumer group will read (last processed + 1)             |
| Lag                     | LEO minus committed offset, per partition                               |
| Retention               | Time/size based deletion of whole old segments                          |

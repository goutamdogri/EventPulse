## 1. TL;DR

- Kafka keeps records for a **period of time** (`retention.ms`) and/or up to a **size** (`retention.bytes`), then deletes them. It does **not** care whether anyone has read them. **Reading never deletes; not reading never preserves.**
- Deletion is **whole segments** (note 1). A segment is deleted when **every record in it** is older than `retention.ms` (judged by its **newest** timestamp), or when the partition's total size exceeds `retention.bytes`. The **active segment is never deleted**.
- So `retention.ms` is a **minimum** age (data lives at least that long) and in practice often **much longer**. `retention.bytes` is a **maximum** size and **can delete data younger than `retention.ms`**.
- Deleting moves the partition's **log start offset** up. Offsets are never reused.
- **A consumer that falls behind retention loses data permanently**: its next offset points at records that no longer exist. Kafka then applies the reset policy (`earliest` jumps forward to what still exists, `latest` jumps to the end, `none` errors). Nothing tells the application what it missed unless you look.
- Retention is **EventPulse's recovery window**: it is how long you can replay `events.raw`, and how long a stopped sink may stay stopped. After it, **Postgres is the only copy**.
- EventPulse's `events.raw` uses `retention.ms = 24 h`, `retention.bytes = unlimited`, and default segment sizes **[observed]**. At lab traffic levels those defaults mean **nothing is actually deleted for about a week**, which is a trap (section 7).

> **One-line version:** _Retention is a clock and a ruler for the log, not a receipt for readers: when the clock or ruler says "too old" or "too big", the oldest segment goes, whether or not it was read._

## 2. The mental model

Back to the paper tape (notes 1 and 2): a long tape of numbered slots, kept as rolls. Readers keep bookmarks.

| Tape                                                                 | Kafka                                                          |
| -------------------------------------------------------------------- | -------------------------------------------------------------- |
| A janitor who walks along every few minutes                          | The retention check (`log.retention.check.interval.ms`, 5 min) |
| "Throw away any **roll** whose newest slot is older than a day"      | `retention.ms`                                                 |
| "If the shelf holds more than N metres, throw away the oldest rolls" | `retention.bytes`                                              |
| The janitor never touches the roll currently being written           | The active segment is never deleted                            |
| The janitor does not look at the bookmarks                           | Retention ignores consumers                                    |
| A reader whose bookmark is on a roll that was thrown away            | A consumer behind retention: out-of-range offset               |
| The label "first slot still on the shelf"                            | The log start offset                                           |

Two consequences you must hold at once:

1. **Time and size are the only rules.** No reader can hold a roll on the shelf.
2. **The janitor works in whole rolls and on a schedule**, so deletion is coarse and late. That is why "24 hours" is not a precise number.

## 3. Age and size

### 3.1 What retention is not

- **Not "delete after consumption".** A record read by every group is still kept until it ages out. (This is the opposite of a classic queue; see note 2, section 5.)
- **Not "keep until consumed".** A record no one has read is deleted on schedule. Kafka has no concept of an unread record it must protect.
- **Not per record.** It is per segment (section 5).
- **Not about consumers' lag.** A consumer that is one second behind and one that is two days behind are treated identically; only the second one loses data.

### 3.2 Why Kafka is designed this way

- **Brokers stay simple and fast**: no per-record, per-consumer bookkeeping (note 2, section 5).
- **Replay for free** within the window.
- **Predictable disk use**: bounded by rate × window, not by the slowest reader. A single stuck consumer cannot fill the disks (the price: it loses data instead).

The price of the design is exactly the sentence in this note's title: **a consumer that falls behind retention loses data, and Kafka will not stop it.** The protection has to be built into your operations (sections 9 and 10).

## 4. The settings

All of these are **topic-level** configs with a **broker-level default**. Values on this cluster are **[observed]** from `kafka-configs.sh --describe --all --topic events.raw`.

| Topic config                                   | Broker default name                        | Meaning                                                                                               | `events.raw`                          |
| ---------------------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------- |
| `cleanup.policy`                               | `log.cleanup.policy`                       | `delete` (drop old segments), `compact` (keep latest per key), or both                                | `delete`                              |
| `retention.ms`                                 | `log.retention.ms` / `.minutes` / `.hours` | Delete segments whose newest record is older than this. `-1` = keep forever                           | **86,400,000 (24 h)**                 |
| `retention.bytes`                              | `log.retention.bytes`                      | Per **partition**: keep at most about this much. `-1` = no size limit                                 | **-1**                                |
| `segment.bytes`                                | `log.segment.bytes`                        | Roll the active segment at this size                                                                  | **1,073,741,824 (1 GiB)**             |
| `segment.ms`                                   | `log.roll.ms` / `.hours`                   | Roll the active segment when it is this old                                                           | **604,800,000 (7 days)**              |
| `segment.index.bytes`                          | `log.index.size.max.bytes`                 | Size of the offset index file per segment                                                             | 10,485,760                            |
| `file.delete.delay.ms`                         | `log.segment.delete.delay.ms`              | Wait this long after marking a segment deleted before removing the file                               | **60,000**                            |
| `delete.retention.ms`                          | `log.cleaner.delete.retention.ms`          | Only for **compacted** topics: how long tombstones stay                                               | 86,400,000 (unused for delete topics) |
| `message.timestamp.type`                       | `log.message.timestamp.type`               | `CreateTime` (producer's) or `LogAppendTime` (broker's)                                               | default (`CreateTime`)                |
| `local.retention.ms` / `local.retention.bytes` | `log.local.retention.*`                    | Only with **tiered storage**: how long to keep data on **local** disk; `-2` means "same as retention" | -2 (unused)                           |

Broker-wide, not per topic:

| Setting                           | Value               | Meaning                    |
| --------------------------------- | ------------------- | -------------------------- |
| `log.retention.check.interval.ms` | **300,000 (5 min)** | How often the janitor runs |

Notes on how these combine:

- **Precedence:** a topic config overrides the broker default. Among the broker settings for the same thing, the finer unit wins (`log.retention.ms` over `.minutes` over `.hours`).
- **If both `retention.ms` and `retention.bytes` are set,** a segment is deleted when **either** limit says so. That is how size can remove data younger than the time limit.
- **`retention.bytes` is per partition, not per topic.** A topic's size cap is `retention.bytes × partitions` (and ×RF across the cluster).
- **Changing retention is retroactive [reasoning].** The janitor applies the **current** config to **existing** segments at its next run. Lowering `retention.ms` can delete a lot of data at the next check. Raising it only helps for segments that have not yet been deleted: it cannot bring back what is gone.
- **Retention is dynamic.** It can be changed on a live topic with `kafka-configs.sh --alter` without a restart.

## 5. How deletion works

### 5.1 The janitor's procedure **[reasoning, standard Kafka behavior; not observed here]**

Every `log.retention.check.interval.ms` the broker, for each partition **it hosts** (leader and follower alike, each on its own):

1. Looks at the **closed** segments (everything except the active one), oldest first.
2. **By time:** a segment is eligible if its **largest record timestamp** is older than `now - retention.ms`.
3. **By size:** if the partition's total size exceeds `retention.bytes`, the oldest closed segments are eligible until the remainder fits (in whole-segment steps).
4. **Marks** each eligible segment for deletion: the files get a `.deleted` suffix, and the log start offset is advanced past them.
5. After `file.delete.delay.ms` (60 s) a background task **removes the files**.

Practical readings:

- **Granularity is a segment.** Deleting "1 hour of data" from a 1 GiB segment is impossible; the segment goes only when **all** of it is old enough.
- **The newest record decides.** One recent record in a segment keeps all its older neighbours alive.
- **The active segment is exempt.** However old its contents, it stays until it **rolls** (by `segment.bytes` or `segment.ms`) and then becomes a candidate on a **later** check.
- **Each replica deletes independently**, based on its own files and clock. Replicas hold identical segments (note 3), so they normally agree, but not to the second.
- **Followers' log start offsets and the leader's can differ briefly**, with no ill effect.

### 5.2 Lag in the timeline

For a record written at time `T` in a segment that closes at time `C` (when the segment rolls) with its newest record at time `N ≤ C`:

```
 data first becomes deletable at   N + retention.ms         (the segment's NEWEST record has aged out)
 deleted at the next janitor run   up to +5 min
 files physically removed          +60 s later
```

So a record's real lifetime is **at least** `retention.ms` and as much as **`retention.ms` + the time the segment spent open + 5 min + 1 min**. With a segment that stays open for days (section 7), "24 hours" becomes "days".

### 5.3 What "log start offset moves" means for readers

- Any fetch for an offset **below** the new log start offset fails with an out-of-range error.
- Offset numbers are **not recycled**: the next record still gets the end offset (note 2, section 4).
- The audit's start/end snapshots of log start offsets exist to catch exactly this (check H).

## 6. Timestamps

"Older than `retention.ms`" is measured with the **record timestamp**, not the file's modified time. That has consequences:

| `message.timestamp.type`   | Timestamp is                                       | Notes                                                                  |
| -------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------- |
| **`CreateTime`** (default) | Set by the **producer** when the record is created | Trusts the producer's clock                                            |
| `LogAppendTime`            | Set by the **broker** when it appends              | Immune to producer clock skew; consumers lose the original create time |

What can go wrong with `CreateTime`:

- **Producer clock far in the past** (or records carrying old timestamps, for example a replay or backfill): segments look **old at once** and can be deleted at the **next check**, even though the data was written seconds ago. This is the classic "I loaded old data and it vanished" surprise.
- **Producer clock far in the future** (or a bogus future timestamp): the segment's **largest timestamp is in the future**, so it is **not deleted until that future time plus retention**. One bad record can pin a whole segment (and its disk) for a long time.
- Brokers can **reject** records whose timestamps are too far from the broker's clock, using `message.timestamp.before.max.ms` and `message.timestamp.after.max.ms` **[reasoning]**: defaults vary by Kafka version; check yours with `--describe --all` before relying on them.

For EventPulse:

- The envelope carries **`occurred_at`** (the client's event time) and the header **`received_at`** (the API's receipt time). Neither is the Kafka record timestamp. `encodeEvent` does not set a record timestamp explicitly, so the **client library stamps the record at send time [reasoning, confirm by reading a record's `CreateTime`]**. That is the sane choice: retention then follows **when the API accepted the event**, not the event's own, possibly weird, `occurred_at`.
- **Do not set the Kafka timestamp from `occurred_at`.** A client sending an event from last month would then have its segment deleted almost immediately, or one dated in 2100 would pin storage.
- Late events (old `occurred_at`) are a **data-modelling** matter for a later stage; retention only sees the send time.

## 7. Why retention seems not to work

The commonest retention bug is **"my data is older than retention and it is still there"**. The reasons, in order of likelihood:

1. **The data is in the active segment.** The active segment is never deleted. With default `segment.bytes` = 1 GiB and `segment.ms` = 7 days, a quiet partition keeps one segment open for **up to 7 days**, and **all of its data, however old, stays**.
2. **The janitor has not run yet.** Up to 5 minutes after a segment becomes eligible, plus 60 s before the files go.
3. **A newer record keeps the segment alive** (the newest timestamp decides).
4. **A future-dated record** pinned the segment (section 6).
5. **The topic's retention is not what you think**: a topic override or a broker default (`--describe --all` tells you).

### 7.1 The EventPulse case, with arithmetic

Assumptions (illustrative; replace with measured numbers): average record about **600 bytes** on disk, including key, headers and batch overhead, no compression; `events.raw` has **6 partitions**; the load is spread evenly.

| Rate                       | Per partition  | Time to fill a 1 GiB segment | What the 24 h retention actually does                                                         |
| -------------------------- | -------------- | ---------------------------- | --------------------------------------------------------------------------------------------- |
| 50 events/s (a quiet test) | about 5 KB/s   | about **2.5 days**           | Active segment rolls by `segment.ms` (**7 days**), so **nothing is deleted for up to a week** |
| 2,000 events/s             | about 200 KB/s | about **1.5 hours**          | Segments roll every 1.5 h; data is deleted about 24 h + 1.5 h + 6 min after it was written    |
| 20,000 events/s            | about 2 MB/s   | about **9 min**              | Close to the nominal 24 h                                                                     |

(1 GiB / 5 KB/s ≈ 215,000 s ≈ 2.5 days; 1 GiB / 200 KB/s ≈ 5,400 s ≈ 1.5 h; 1 GiB / 2 MB/s ≈ 540 s ≈ 9 min.)

**Consequence for your experiments.** At laptop-test volumes, `events.raw` effectively retains up to **a week**, not 24 h. That is why a "consumer stays down longer than retention" test **will not lose data** unless you shrink `segment.ms` (or `segment.bytes`) on a scratch topic. It is also why audit check H (log start offset moved) will normally stay quiet. **Decide on purpose** (section 13) whether you want realistic retention behavior, and if so set `segment.ms` on the topic so the window is honest.

## 8. Sizing

### 8.1 Disk needed

```
disk per broker  ≈  produce_rate (bytes/s)  ×  retention (s)  ×  RF  /  number_of_brokers   (+ headroom)
```

With RF 3 on 3 brokers every broker holds a **full copy** of every partition, so each broker needs about `rate × retention`. Illustration with the assumptions above:

| Rate            | Bytes/s (600 B events) | Per day           | Disk per broker for 24 h retention |
| --------------- | ---------------------- | ----------------- | ---------------------------------- |
| 2,000 events/s  | 1.2 MB/s               | about **104 GB**  | about 104 GB + headroom            |
| 20,000 events/s | 12 MB/s                | about **1.04 TB** | about 1.04 TB + headroom           |

Add: the active segment of every partition (up to 1 GiB each), the delete delay and janitor lag (data lives a bit longer than the window), the `__consumer_offsets` and DLQ topics, and a safety margin (disk should not exceed about 70 to 80 percent). **Compression** (`KAFKA_COMPRESSION`, note 1 section 5.1) can reduce this a lot for JSON, at the cost of CPU: measure it.

### 8.2 What fills the disk

- **Retention window too long** for the volume.
- **A traffic spike or flood**: rate × window grows with the rate.
- **Future-dated timestamps** pinning segments (section 6).
- **Unbounded `retention.bytes = -1` with huge `retention.ms`**.
- **A broker that hosts more partitions** than its peers (skewed leaders do not matter for disk, replica placement does).

A broker whose log directory fills up **takes that log dir offline**: its replicas fail, ISRs shrink, and with min ISR 2 the cluster may start refusing writes (note 3). So **disk-full is an availability incident**, not only a storage one. `retention.bytes` is a cheap safety net: it caps each partition **regardless of window**, at the cost of possibly deleting data earlier than `retention.ms` promises.

### 8.3 Per-partition size cap versus skew

`retention.bytes` applies **per partition**. A **hot partition** (note 1, section 10.3) fills faster and hits the size limit first, so with a size cap the hot partition's **effective retention in time is shorter** than the others'. Another reason to watch **per-partition** lag and sizes, not only totals.

## 9. Falling behind

### 9.1 The failure

```
 log start offset: 5,000                    (retention already deleted 0..4,999)
 consumer's committed offset: 4,200         (it was still reading in the part that is now gone)

 next fetch for 4,200 -> OFFSET_OUT_OF_RANGE
   auto.offset.reset = earliest -> jump to 5,000.  Records 4,200..4,999 are NEVER processed.  Silent loss.
   auto.offset.reset = latest   -> jump to the end. Everything unread is skipped.
   auto.offset.reset = none     -> the consumer errors out. Loud, but nothing is processed until you decide.
```

The consumer **continues normally** (with `earliest`/`latest`). Unless you look at metrics or logs, **nothing breaks and nothing is reported**. The missing events were acknowledged to API clients with a 202.

### 9.2 When does it happen?

A consumer is **in danger** when **the age of the oldest record it has not yet processed approaches the age at which that record's segment is deleted**. In rough terms:

```
 danger when:   time-lag  ≳  retention.ms  (+ the up-to-a-segment-span slack)

 time-lag  ≈  lag (records)  /  consume rate (records/s)           [or: now - timestamp of the next unread record]
```

Retention guarantees data lives **at least** `retention.ms`, so a consumer whose oldest unread record is younger than 24 h is **safe** (barring `retention.bytes`). Once the oldest unread record is older than 24 h, its segment **may** be deleted at the next janitor run, and the consumer is racing the janitor.

### 9.3 How a sink falls behind in EventPulse

| Cause                                                   | Example                                                                                                                                                         |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Sink stopped**                                        | Crash loop, deploy mistake, laptop asleep, container removed                                                                                                    |
| **Postgres unavailable or slow**                        | Step 4's rule: `TRANSIENT_DB` errors **wait as long as needed** and never go to the DLQ. During a long DB outage the lag grows and **the retention clock runs** |
| **Throughput below the arrival rate for a long time**   | Consumer capacity `c` smaller than the produce rate for hours (note 1, section 11.2). Lag grows without bound                                                   |
| **A poison message blocks a partition** (before Step 4) | That one partition's lag grows while others drain; its slice of data ages toward deletion                                                                       |
| **A very slow rebalance loop**                          | Consumers repeatedly kicked out of the group                                                                                                                    |
| **Wrong reset after a bad deploy**                      | `latest` skips data on purpose or by accident                                                                                                                   |

Note the interplay with Step 4: "never DLQ a transient DB error; wait" is the right correctness rule for short outages, but **during an outage longer than retention, waiting becomes silent data loss**. The design needs a **ceiling**: alert well before the window closes, and decide in advance what the operator does (section 10).

### 9.4 Where the data goes after retention

Gone from Kafka, and **not in Postgres** if it was never consumed. There is no other copy. This is the only situation in Stage 2 where acknowledged events can be lost **without any failure**, only a slow or stopped consumer. It is why the audit checks "log start offset moved during the run" and why you should treat time-lag as a first-class SLO next to freshness.

## 10. Staying inside the window

### 10.1 Detect it early

| Signal                                                                                                                | Why it helps                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Per-partition lag** (`ep_consumer_lag{partition}`, Step 6)                                                          | Shows which partition is behind                                                                                                                             |
| **Time-lag**: age of the oldest unread record, or `ep_event_freshness_seconds` (now minus `received_at` at DB commit) | In seconds, directly comparable to `retention.ms`. **Alert at a fraction of the window**, for example 25 percent and 50 percent of 24 h, not at 100 percent |
| **Log start offset** per partition (add a gauge)                                                                      | Lets you see "committed offset is within X records of the log start". Distance to the log start offset is the most direct "how close to data loss" number   |
| **Consumer liveness**: members in the group, `ep_consumer_rebalances_total`, process uptime                           | A stopped sink is caught by "no members" long before lag looks large                                                                                        |
| **Audit check H**                                                                                                     | Retroactive proof that the log start moved during a run                                                                                                     |
| **Disk usage per broker**                                                                                             | A different failure of the same cause (section 8.2)                                                                                                         |

(A freshness figure only exists for records that were just processed. A completely stopped consumer produces **no** freshness samples, which is why you also need group membership and lag.)

### 10.2 React

When the oldest unread record is close to the window:

1. **Fix the cause** (restart the sink, restore Postgres, remove the poison record).
2. **Add capacity** (more consumer instances, up to the partition count; larger `SINK_MAX_ROWS`).
3. **Reduce arrivals**: the API returns 503 (`Retry-After`) when its own limits are hit; you can also deliberately slow producers.
4. **Extend retention on the topic now** (`retention.ms` up, dynamic, no restart). This **buys time** but only for segments **not yet deleted**, and costs disk (section 8).
5. **Last resort, never silent**: accept a gap, record it, and reset to a chosen offset with the reset tool, rather than letting the reset policy skip data at random.

### 10.3 Design the settings so the margin is real

- Choose `retention.ms` so that **the longest realistic outage you want to survive** fits inside it, with margin. For a sink that can be down overnight, 24 h is a reasonable floor, 72 h is comfortable. The disk cost is linear in the window.
- Keep `auto.offset.reset=earliest` for the sink (EventPulse's `CONSUMER_FROM_BEGINNING=true`) so a fall-behind **processes everything that remains** instead of skipping to the end. Know that it still loses what retention removed.
- Consider `auto.offset.reset=none` for **production-like** runs: a consumer that **refuses to continue** after an out-of-range offset is a loud failure instead of a silent one. (Trade-off: it also refuses to start for a brand new group, which then needs an explicit start position.) This is a design option, not a Stage 2 requirement.

## 11. Committed offsets

Two different expirations, easy to confuse:

|                  | Data retention                    | Committed-offset retention                                                                       |
| ---------------- | --------------------------------- | ------------------------------------------------------------------------------------------------ |
| What is kept     | Records in `events.raw`           | The group's committed offsets in `__consumer_offsets`                                            |
| Setting          | `retention.ms` (24 h here)        | `offsets.retention.minutes` (default **7 days**, counted from when the group has **no members**) |
| Mechanism        | Delete old segments               | The group's commits are removed (the topic is compacted)                                         |
| What expiry does | Out-of-range offsets, data loss   | The group is forgotten; on return it behaves like a **new group** and uses `auto.offset.reset`   |
| Which hits first | **Usually data retention (24 h)** | Rarely (7 days)                                                                                  |

Interactions (see note 2, sections 7.3 and 14):

- If data retention is shorter than commit retention (our case), a returning consumer with a valid commit often finds its offset **below the log start** and falls into the reset policy.
- If a group is **gone for more than 7 days**, even a topic with long retention treats it as new.
- A group that has been **empty for a long time** is still listed by `kafka-consumer-groups.sh --list` until its offsets expire. Old test groups (for example the `sink-e2e-...` groups seen on this cluster) are harmless but clutter; they are deleted by `--delete --group`.

## 12. Other ways data leaves

### 12.1 Explicit deletion (not retention)

`kafka-delete-records.sh` deletes records **before a given offset** per partition, advancing the log start offset **immediately**, regardless of retention. It is an administrative action (for example to skip a known-bad prefix, or to free disk). Same effect on consumers as retention: those behind the new log start lose data.

### 12.2 Compaction

`cleanup.policy=compact` keeps the **latest record per key** and drops older ones **by key**, not by age. It is how `__consumer_offsets` works. For EventPulse events it is wrong: events are facts, not "latest state per tenant", and compaction would erase most of a tenant's history. Never set it on `events.raw`. `cleanup.policy=compact,delete` combines both (compaction plus age-based deletion) and is not used here.

### 12.3 Keeping data longer

- **Larger `retention.ms` / `retention.bytes`**: simple, costs local disk on every replica.
- **Tiered storage** (`remote.storage.enable`, `local.retention.*`): keeps recent data on local disks and older data on cheap object storage, with `retention.ms` governing the **total**. The `local.retention.*` settings appear in this cluster's `--describe --all` output **[observed]** with value `-2` (unused). Not part of Stage 2.
- **Sink to another system** (Postgres in our case): the durable copy. That is the real answer to "how do we keep events for months": Kafka is the buffer with a replay window; the database or a lake is the archive.

### 12.4 The DLQ

`events.dlq` has **7 days** of retention so a human can inspect and fix poison messages. **Anything not handled in 7 days is deleted**. If you want a permanent record of failures, copy them to a table or storage before then.

## 13. EventPulse decisions

| Decision                                    | Choice                                                                       | Reason                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `events.raw` `retention.ms`                 | **24 h** **[observed]**                                                      | Replay window and tolerated sink downtime. It is a **minimum**, not an exact value                        |
| `events.raw` `retention.bytes`              | **-1 (unbounded)** **[observed]**                                            | Keep the time rule predictable. Revisit if disk becomes a risk; a cap would delete data earlier than 24 h |
| `events.raw` `segment.bytes` / `segment.ms` | Defaults (1 GiB / 7 days) **[observed]**                                     | See below                                                                                                 |
| `events.dlq` retention                      | **7 days**                                                                   | Time for humans to inspect                                                                                |
| Cleanup policy                              | **delete**                                                                   | Events are facts                                                                                          |
| Kafka record timestamp                      | The producer's `CreateTime` at send time (not `occurred_at`) **[reasoning]** | Retention follows acceptance time                                                                         |
| `CONSUMER_FROM_BEGINNING`                   | **true** (`earliest`)                                                        | Do not skip existing data                                                                                 |
| Time-lag alerting                           | Add (Step 6)                                                                 | The one number that tells you retention is about to bite                                                  |

**A decision you should make explicitly (Step 1):** with default segments, retention at test volumes effectively means up to **7 days** (section 7.1). Options:

| Option                                                                                                            | Effect                                                                                                                 | When                                                                |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Keep defaults                                                                                                     | Simplest; retention rarely deletes anything in tests. ## 16. Failure scenarios

| Scenario                                                                    | What happens                                                                              | Data                                                        | What you see                                                                                           |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Sink stopped for 3 h, retention 24 h                                        | Lag grows; no segment holding unread data is old enough                                   | Safe                                                        | Lag and time-lag grow; freshness spikes when it restarts                                               |

| Producer with a clock 1 year ahead                                          | Segment's newest timestamp is in the future                                               | Retained far too long; disk grows                           | Disk usage, segments not deleted                                                                       |

| Disk full on a broker                                                       | Log dir goes offline; replicas fail                                                       | Availability problem                                        | Under-replicated and, with min ISR 2, refused writes                                                   |

## 18. Common confusions

1. **"Messages are deleted after they are consumed."** No. Only age or size removes them.
2. **"Messages are kept until consumed."** No. Unread data is deleted on schedule.
3. **"`retention.ms=24h` means data is gone after exactly 24 h."** It means **at least** 24 h; real lifetime depends on segment rolling and the janitor, and can be days.
4. **"A record older than retention is deleted."** Only if its **whole segment** is, and never from the active segment.
5. **"`retention.bytes` is for the whole topic."** Per partition (and per replica).
6. **"Retention is evaluated by file age."** By the **record timestamp** of the segment's newest record.
7. **"Increasing retention restores deleted data."** No. It only stops further deletion.
8. **"A consumer that loses data will error."** Not with `earliest` or `latest`. It silently skips ahead.
9. **"Retention only matters for old consumers."** It also sets disk size, replay window and the maximum safe sink outage.
10. **"The log start offset is always 0."** It rises as segments are deleted.
11. **"Committed offsets and data expire together."** Different settings: 7 days after the group is empty vs. the topic's `retention.ms`.
12. **"Set `retention.ms=-1` and forget it."** Infinite retention means disk grows with the rate until a broker fills and the cluster degrades.
13. **"Retention is a durability setting."** It is the opposite: it is when durability **ends**. Durability is replication (note 3).

## 20. Cheat sheet

### Glossary

| Term                | Meaning                                                               |
| ------------------- | --------------------------------------------------------------------- |
| Retention           | Rule that deletes old data by age or size                             |
| `retention.ms`      | Minimum age before a segment becomes deletable (by its newest record) |
| `retention.bytes`   | Per-partition size ceiling (can delete younger data)                  |
| Janitor             | Periodic retention check (every 5 min here)                           |
| Active segment      | The segment being written; never deleted                              |
| Log start offset    | Oldest offset still stored; moves up on deletion                      |
| Time-lag            | Age of the oldest unread record (what retention is compared to)       |
| Out-of-range offset | A consumer's offset is outside `[log start, log end]`                 |
| `auto.offset.reset` | What to do then: `earliest`, `latest`, `none`                         |
| Compaction          | Keep latest record per key (not used for events)                      |
| Tiered storage      | Keep older data on remote storage (not used)                          |

### Settings on this cluster **[observed]**

| Setting                                      | Value                |
| -------------------------------------------- | -------------------- |
| `events.raw` `retention.ms`                  | 86,400,000 (24 h)    |
| `events.dlq` `retention.ms`                  | 604,800,000 (7 days) |
| `retention.bytes`                            | -1                   |
| `segment.bytes` / `segment.ms`               | 1 GiB / 7 days       |
| `log.retention.check.interval.ms`            | 300,000              |
| `file.delete.delay.ms`                       | 60,000               |
| `offsets.retention.minutes` (broker default) | 10,080 (7 days)      |

### Rules of thumb

```
data lifetime   ≥  retention.ms       (up to  + time the segment stays open + 5 min + 1 min)
disk per broker ≈  rate × retention × RF / brokers   (+ 20 to 30 percent headroom)
fall-behind     =  oldest unread record older than retention.ms  (alert at a fraction of it)
```

# Kafka Consumer: Rebalances and Timeouts

*Consumer note 2 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`, the producer series in `../producer/`). Read consumer note 1 (groups) and Kafka note 2 (offsets) first. A rebalance is triggered when members join, leave, or are considered dead; consumption pauses during eager rebalances. This note explains every trigger, the three timers that decide when a member is "dead" (`session.timeout.ms`, `heartbeat.interval.ms`, `max.poll.interval.ms`, and how this client maps them), what a rebalance costs, how the sink protects itself, and how to design experiment K8. It supports Step 2, Step 3 (commit safety), Step 6 (rebalance metrics) and experiments K5 and K8.*

**What was run.** **[observed]** means seen on this repo's cluster on **scratch topics that were deleted afterwards**, or read from this repo's source (`services/consumer-sink`) or the installed client's source (`@confluentinc/kafka-javascript` 1.11.0). Two lab runs feed this note. **Lab A** (members joining a group, per assignor) is in consumer note 1. **Lab B** ran 3 to 4 Node consumers with a **6 s session timeout and 1 s heartbeat** while a steady producer wrote 300 records/s, then added a member, killed one with `kill -9` and stopped another with SIGTERM, once per assignor. **Only the rebalance event timings and counts from Lab B are used here.** Its consumption-gap and message-count measurements are **discarded** because the test consumer had a harness problem (see consumer note 1, section 16). No broker was stopped. **[reasoning]** marks standard Kafka behavior that was not observed here, and **the behavior of long-running batches under the real sink was not tested**.

## 1. TL;DR

- A **rebalance** is the group redistributing partitions among its members. It is triggered when a member **joins**, **leaves**, or is **considered dead**, or when the subscription or the topic's partitions change.
- A member is considered dead in **two different ways**:
  1. **It stops heartbeating** for `session.timeout.ms` (the process crashed or the network is gone).
  2. **It is alive but not polling** for `max.poll.interval.ms` (it is stuck in a very long batch). In this client `rebalanceTimeout` is the setting that maps to `max.poll.interval.ms`.
- **`heartbeat.interval.ms`** is how often a live member says "still here"; it must be **well below** the session timeout.
- During an **eager** rebalance **every member gives up every partition** and the whole group waits until all members have rejoined: **consumption pauses everywhere**. A **cooperative** rebalance revokes only the partitions that move, so the rest keep running (consumer note 1, section 8).
- **A crash costs the session timeout; a graceful leave does not.** Measured with a 6 s session timeout [observed]: after `kill -9` the first rebalance event came **5.3 s** later; after SIGTERM (a clean leave) it came within **0.3 s**. With the sink's default **45 s** session timeout, a crash would leave its partitions unread for up to 45 s.
- A rebalance **moves partitions between members**, so work the old owner did but did not commit is **done again** by the new owner: **duplicates**, bounded by the commit granularity (one chunk per partition in the sink).
- The sink is built for this: a `rebalance_cb` hook, an `isStale()` check **between chunks and before committing**, heartbeats between chunks and during retry waits, a bounded chunk size, a config rule tying retry time to the rebalance timeout, and `ON CONFLICT (event_id)` to absorb replays.

> **One-line version:** *A rebalance is the price of changing who owns what; the timers decide how quickly the group notices a problem, and your batch time decides how long everyone waits for it to settle.*

## 2. The mental model

The checkout roster from consumer note 1, now with a **manager who calls a staff meeting** whenever the team changes.

| Supermarket | Kafka |
| --- | --- |
| A cashier walks in or out | A member joins or leaves |
| The manager calls a staff meeting to redraw the roster | A rebalance |
| **Everyone stops serving** until the roster is redrawn (eager) | Eager rebalance: all partitions revoked |
| Only the cashiers whose lanes change step away (cooperative) | Cooperative: only moved partitions revoked |
| A cashier must **look up from the till** to hear the meeting call; one mid-way through a very long transaction is late | Members only join a rebalance between polls: a long batch delays everyone |
| A cashier who **tells the manager they are leaving** is replaced immediately | Graceful leave |
| A cashier who **just disappears**: the manager waits N minutes before concluding they are gone | A crash: the **session timeout** |
| A cashier who is present but **stuck on one customer for hours** is eventually replaced | **`max.poll.interval.ms`** |
| A cashier who started a sale, got reassigned, and the next cashier restarts that sale from the last receipt | The new owner replays from the last **committed** offset (duplicates) |

## 3. Triggers

| Trigger | What happens | Cost |
| --- | --- | --- |
| **A member joins** (new process, restart) | JoinGroup; the group rebalances | Pause of all (eager) or of moved partitions (cooperative) |
| **A member leaves cleanly** (`disconnect()`, SIGTERM) | The member sends LeaveGroup; prompt rebalance | Short |
| **A member crashes or loses the network** | Heartbeats stop; after `session.timeout.ms` the coordinator removes it | Its partitions are **unread for the session timeout**, then a rebalance |
| **A member stops polling** (a very long `eachBatch`, a blocked process) | After `max.poll.interval.ms` the member is considered failed and removed | Same, and its work in flight is later redone |
| **The subscription changes** (a member subscribes to another topic) | Rebalance | |
| **The topic's partitions change** (partitions added, topic created for a pattern subscription) | Metadata change detected; rebalance **[reasoning]** | Also moves keys (producer note 6) |
| **The group coordinator moves** (broker failure, leadership change) | The group re-finds the coordinator and re-joins; may rebalance **[reasoning]** | Short blip |
| **Operator action** (delete group, reset offsets: needs an empty group) | n/a | |

Not triggers: a **partition leader election** on the broker side does **not** cause a consumer group rebalance. Fetches are retried against the new leader (Kafka note 4, section 8).

Joins **count** even when the joiner gets nothing: **[observed]** a 7th member that ended with no partitions still caused an eager rebalance that revoked all 6 partitions from 6 members (consumer note 1).

## 4. Eager and cooperative

### 4.1 Eager ("stop the world")

```
 member joins -> coordinator tells all members to rejoin
   every member:  REVOKE ALL its partitions   (stop fetching, finish/abandon in-flight work, commit)
   every member:  JoinGroup ... SyncGroup     (leader computes a fresh assignment)
   every member:  receives its (possibly the same) partitions and starts fetching again
 ==> during this window NO partition in the group is being consumed
```

Assignors: `range`, `roundRobin`, plain `sticky`.

### 4.2 Cooperative ("incremental")

```
 member joins -> rebalance round 1:
   leader computes the target assignment; each member keeps what it still owns,
   and only the partitions that must MOVE are revoked from their current owners
 rebalance round 2:
   the revoked partitions are given to their new owners
 ==> partitions that did not move were never paused
```

Assignor: `cooperativeSticky`.

**[observed]** (Lab A and Lab B). Partitions revoked per join:

| Event | Eager (`roundRobin`) | Cooperative (`cooperativeSticky`) |
| --- | --- | --- |
| Join of a 2nd member | 6 | 3 |
| Join of the 4th (Lab B, 3 members to 4) | 6 revoked, 6 assigned, finished within about **0.3 s** | **1** revoked, **1** assigned, finished about **1.2 s** after the join |
| Join of an idle 7th member (Lab A) | 6 | 0 |
| Clean leave of one of 4 members, owning 2 partitions (Lab B) | 6 revoked, 6 assigned within 0.3 s | **2** revoked, **2** assigned within 0.3 s |

Reading it: **cooperative rebalances touch far fewer partitions**; they can take **longer to finish for the moved partitions** (two rounds), but the unmoved partitions do not stop. In a quiet group the eager stop-the-world was brief (hundreds of milliseconds). **Its real cost is set by how long the members take to rejoin**, which depends on how long their current batch takes (section 7).

## 5. The three timers

### 5.1 `heartbeat.interval.ms`

How often a member sends a heartbeat to the coordinator. Heartbeats are how a live member proves it is alive and how it **learns that a rebalance has begun** (the response tells it to rejoin). Rule of thumb: **at most one third of `session.timeout.ms`** **[reasoning]**, so that two or three heartbeats can be lost before the session expires. The sink's config enforces the minimum sanity: the heartbeat interval must be **lower than** the session timeout **[observed in `config.ts`]**.

### 5.2 `session.timeout.ms`

If the coordinator receives **no heartbeat for this long**, it considers the member **dead**, removes it and rebalances. It is what detects **crashes and network loss**. It must be within the broker's allowed range (`group.min.session.timeout.ms` and `group.max.session.timeout.ms`; 6 s and 30 min by default **[reasoning]**). Trade-off:

| Smaller | Larger |
| --- | --- |
| Faster detection of a dead member: its partitions are back in service sooner | Slower detection: partitions of a dead member sit unread for longer |
| More **false positives** (a GC pause, a network blip, a loaded host triggers needless rebalances) | Fewer false positives |

### 5.3 `max.poll.interval.ms`

The **maximum time between two polls** of the consumer. A member that heartbeats fine but **does not poll** for longer than this (it is busy in one very long batch, or deadlocked) is considered failed: it is removed from the group and its partitions are reassigned. It detects **stuck consumers** that the session timeout cannot, because **heartbeats are sent by a background thread** and keep flowing while the application is stuck **[reasoning, standard since the heartbeat thread was introduced]**.

It is also the limit on **how long a rebalance may wait for a member** to come back from its current batch: a member must finish what it is doing and rejoin within this time or it is dropped. In this client the setting you pass is called **`rebalanceTimeout`**, and the comment in the client says so explicitly (section 6).

### 5.4 How they fit together

| Failure | Detected by | Time to detect |
| --- | --- | --- |
| Process crash (SIGKILL), machine loss, network cut | `session.timeout.ms` | about the session timeout (minus the time since the last heartbeat) |
| Process stuck inside a batch, still heartbeating | `max.poll.interval.ms` | about the max poll interval |
| Clean shutdown | LeaveGroup | immediate |

A **batch that takes longer than `max.poll.interval.ms`** is therefore a bug in the **design**, not in Kafka: the batch size and the processing time per record must be chosen **together** with this limit. This is the point of experiment K8's "processing longer than the poll or session limits".

## 6. Client mapping

How the settings are named in the Node client **[observed in the installed client's source and in `sink-consumer.ts`]**:

| Kafka setting | Client option (`kafkaJS` block) | Sink env var (default) | Notes |
| --- | --- | --- | --- |
| `session.timeout.ms` | `sessionTimeout` | `CONSUMER_SESSION_TIMEOUT_MS` (**45,000**) | The client's own default is 30,000 if you do not pass it. Not supported when `group.protocol` is not `classic` |
| `heartbeat.interval.ms` | `heartbeatInterval` | `CONSUMER_HEARTBEAT_INTERVAL_MS` (**3,000**) | Not supported when `group.protocol` is not `classic` |
| `max.poll.interval.ms` | **`rebalanceTimeout`** (the client comment: "In librdkafka, we use the max poll interval as the rebalance timeout as well") | `CONSUMER_REBALANCE_TIMEOUT_MS` (**60,000**) | Client default 300,000 if you do not pass it |
| Assignor | `partitionAssigners` | `CONSUMER_ASSIGNOR` (`roundRobin`) | Default when not passed: `roundRobin` |
| Max records per `eachBatch` call | `'js.consumer.max.batch.size'` (outside the `kafkaJS` block) | `CONSUMER_MAX_BATCH_SIZE` (**1,000**) | `-1` = unlimited |
| Concurrent partitions in one member | `partitionsConsumedConcurrently` (in `run`) | `CONSUMER_PARTITIONS_CONCURRENTLY` (**1**) | Must be <= `PG_POOL_MAX` |

Two details about how **this client** enforces the poll interval, taken from its source comments:

1. **The configured value is enforced by the client itself.** The JavaScript layer tracks the time since the last fetch (an internal "cache expiration" loop). If the application has not come back to poll for the configured interval, it **marks the batch payloads stale** and **clears its message cache**, so that a new poll can happen before the real limit.
2. **librdkafka is given twice the configured value.** The client sets librdkafka's `max.poll.interval.ms` to **2x** what you asked for, so that when it asks a worker to stop and there is one last message to process, that message still has the full configured time. The client's comment notes that this makes the **rebalance callback timeout double** the configured value.

What it means for you: **the effective limit seen by the broker can be up to about twice `CONSUMER_REBALANCE_TIMEOUT_MS`** **[reasoning from the source comments; not tested]**, but you should **design for the configured value** (the JavaScript layer will mark your batch stale at that point: `isStale()` becomes true, section 11).

Also relevant: **`payload.heartbeat()`** exists in the batch payload and the sink calls it between chunks, but **the ADR states heartbeats no longer have to be called manually** with this client **[observed in the ADR]**: they are sent by librdkafka's background thread. The `heartbeat()` call is still useful as a cheap "I am still working" point and for compatibility with the KafkaJS API.

## 7. Cost

### 7.1 Where the pause comes from

A rebalance **completes when every member has rejoined**. A member rejoins only **between polls**. In an eager rebalance:

```
 pause  ≈  detection delay (crash only)
        +  time for the SLOWEST member to finish its current batch and rejoin
        +  coordinator work (JoinGroup/SyncGroup rounds: tens to hundreds of ms)
        +  restart of fetching (reset positions, refill buffers)
```

- **Quiet or fast batches:** the middle term is small, the pause is sub-second (**[observed]** about 0.3 s for the eager rebalance in a group with nothing to process).
- **Slow batches:** the middle term dominates. If one member is processing a batch that takes 20 s, **all** members wait up to 20 s (eager). This is why batch time, batch size and the rebalance timeout must be designed together (K8).
- **Cooperative:** unmoved partitions are never paused; the moved ones wait for their old owner to finish and release them.

### 7.2 What else it costs

| Cost | Why |
| --- | --- |
| **Duplicates** | The new owner restarts from the last **committed** offset (section 9) |
| **Lost warm state** | Fetch buffers and prefetch are discarded; the next fetch restarts |
| **Lag spikes** | During the pause the log keeps growing; lag jumps (consumer note 4) |
| **Wasted work** | A batch being processed for a revoked partition is abandoned (the sink checks `isStale()`) |
| **Commit failures** | A commit from a member that no longer owns the partition is rejected (stale generation), counted as a commit error; the rows are already stored (Kafka note 2, section 12) |
| **Metric noise** | `ep_consumer_rebalances_total` increments on each assign |

## 8. Observed timings

Lab B, settings: **session timeout 6 s, heartbeat 1 s**, steady production, 3 members then a 4th. Event times come from each client's `rebalance_cb` callback. "Revoked"/"assigned" are partition counts summed over members within about 15 s of the action. **[observed]**

| Action | Assignor | Revoked | Assigned | First revoke / assign after the action | Last assign after the action |
| --- | --- | --- | --- | --- | --- |
| **4th member joins** | `roundRobin` (eager) | 6 | 6 | +0.2 s | **+0.3 s** |
| | `cooperativeSticky` | **1** | **1** | +0.2 s | **+1.2 s** |
| **`kill -9` of a member owning 2 partitions** | `roundRobin` | 4 (by the survivors) | 6 | **+5.3 s** | +5.3 s |
| | `cooperativeSticky` | **0** | **2** | **+5.2 s** | +5.2 s |
| **SIGTERM (clean stop) of a member owning 2 partitions** | `roundRobin` | 6 | 6 | about 0 s | **+0.3 s** |
| | `cooperativeSticky` | **2** | **2** | about 0 s | **+0.3 s** |

Reading the table:

1. **A crash is noticed after about the session timeout**: 5.3 s with a 6 s timeout (the last heartbeat arrived up to a second before the kill, so detection is the session timeout minus that gap). **Both assignors wait the same time**, because detection is the coordinator's job.
2. **A clean stop is noticed immediately** (within 0.3 s, including the rebalance). The difference between the two exits **is the whole point of graceful shutdown** in the sink.
3. **After a crash under eager, the survivors gave up all their partitions (4) and received all 6 back**; under cooperative **they gave up nothing** and simply received the 2 orphaned partitions: the survivors' partitions were never paused.
4. **With the sink's defaults (45 s session timeout, 3 s heartbeat)** the same crash would leave the 2 orphaned partitions unread for **up to about 45 s**; lag on those partitions grows that long. A smaller session timeout shortens it, at the price of false positives (section 5.2).
5. **A cooperative join takes longer to settle (1.2 s versus 0.3 s)** because the moved partition is revoked and then assigned in a second round, but it touched **1 partition instead of 6**.

These are small numbers from a lightly loaded group. **They show the mechanism, not the cost under real load**: under load the dominant term is the slowest member's batch time (section 7.1), which this lab did not exercise.

## 9. Duplicates

The new owner of a partition starts from the **last committed offset** (Kafka note 2, section 12). Work the old owner did after that point is **redone**.

```
 member A owns P3: committed offset 5,000
   A processes chunk 5,000..5,999, DB commit done, the offset commit not yet sent   <-- rebalance revokes P3 here
 member B gets P3: reads from 5,000 again -> rows 5,000..5,999 are processed a second time
 ON CONFLICT (event_id) DO NOTHING absorbs them; attempted - inserted = 1,000 (counted as duplicates)
```

Bounds and facts:

- **Duplicates per moved partition are at most one chunk's worth** (the sink commits after every chunk of `SINK_MAX_ROWS=1000`), plus anything fetched but not yet processed (which is not a duplicate, just unread).
- **No loss**: nothing is committed before the DB commit, so a rebalance can only repeat work, never skip it (consumer note 3).
- **With cooperative rebalancing there are fewer moved partitions, hence fewer duplicates.** (K8 asks "whether the cooperative or sticky assignor helps".)
- A **member that lost a partition must stop writing for it**: otherwise the old and new owner would both write the same rows (harmless here, but wasteful and confusing in counts). The sink's `isStale()` checks do this (section 11).

## 10. Storms

A **rebalance storm** is a loop of repeated rebalances that keeps the group from making progress.

| Cause | Mechanism | Fix |
| --- | --- | --- |
| **Session timeout too short** | Normal pauses (GC, a loaded host, a network blip) expire the session; the member is removed and rejoins; each cycle rebalances everyone | Raise the session timeout (and keep heartbeat <= one third of it) |
| **Batch longer than the poll interval** | The member is kicked out mid-batch, rejoins, gets a partition, repeats the same long batch, is kicked out again | Smaller batches, faster processing, or a larger max poll interval |
| **Rolling restarts or autoscaling** | Every start and stop is a rebalance | Cooperative assignor, graceful shutdown, staged changes |
| **A flapping member** (crash loop) | Join, crash, wait for session timeout, repeat | Fix the crash; consider static membership **[reasoning]** |
| **A poison message that crashes the process** | Crash loop: each restart rebalances (Step 4) | DLQ the poison record |
| **Coordinator instability** | The group keeps re-finding its coordinator | Fix the broker problem |

**Static membership** (`group.instance.id`) lets a restarted member keep its identity and partitions without a rebalance if it returns within the session timeout **[reasoning]**. Whether the Node client's compatibility layer exposes it was **not checked**; treat it as a possible later improvement, not a Stage 2 requirement.

Signals: `ep_consumer_rebalances_total` increasing steadily, assigned partitions changing in the logs, the group state flipping between `PreparingRebalance` and `Stable` (consumer note 1, section 11), and **lag that grows while members are all "up"**.

## 11. The sink

How `consumer-sink` is built to survive rebalances **[observed in `sink-consumer.ts`, `batch-handler.ts`, `config.ts`]**:

| Mechanism | Where | Effect |
| --- | --- | --- |
| **`rebalance_cb` hook** | `onRebalance` | Counts assigns (`countRebalance`), tracks owned partitions as a set, counts revokes, logs `assigned ...` and `revoked ...`; keeps the client's default assign/unassign behavior |
| **Stale check before each chunk** | `handleBatch` loop: `if (!ctx.isRunning() \|\| ctx.isStale()) return` | A revoked partition's remaining chunks are not processed |
| **Stale check before committing** | After the DB write and DLQ ack: if the partition was revoked meanwhile, **do not resolve or commit**; the new owner reads the chunk again and `ON CONFLICT` absorbs it | No commit from a member that no longer owns the partition |
| **Heartbeat between chunks and during retry waits** | `await ctx.heartbeat()` | A cheap liveness point (and compatibility) |
| **Bounded batch** | `CONSUMER_MAX_BATCH_SIZE` 1,000, `SINK_MAX_ROWS` 1,000 | Keeps the time between polls short |
| **Transient DB failures retry inside a window, then pause the partition and throw** | `SINK_TRANSIENT_RETRY_WINDOW_MS` (20 s), `SINK_RETRY_MAX_MS` (5 s), `SINK_PAUSE_MS` (5 s) | The member does not sit in a retry loop longer than the rebalance timeout |
| **Config rule** | `SINK_TRANSIENT_RETRY_WINDOW_MS + SINK_RETRY_MAX_MS < CONSUMER_REBALANCE_TIMEOUT_MS` (checked at startup; comment: "One eachBatch call must finish within the rebalance timeout (it is also the max poll interval)") | You cannot configure a retry window that guarantees a poll-interval violation |
| **Config rule** | `CONSUMER_HEARTBEAT_INTERVAL_MS < CONSUMER_SESSION_TIMEOUT_MS` | Sanity |
| **Graceful shutdown** | `consumer.disconnect()` waits for the current batch, then leaves the group | A clean leave: immediate rebalance, no session-timeout wait |
| **Injection knobs for K8** | `SINK_PROCESSING_DELAY_MS`, `SINK_PROCESSING_DELAY_CHUNKS`, `SINK_PROCESSING_DELAY_SKIP_CHUNKS`: add an artificial delay to chosen chunks | Reproduces "processing longer than the limits" on demand |
| **Throwing from `eachBatch`** | The client **seeks back** to the first unresolved offset and the batch is retried | Not a rebalance; it is how the sink retries a failed chunk (comment in the client source) |

Order of work per chunk in the sink, with the rebalance in mind (the full protocol is consumer note 3): check stale, parse, DB write, DLQ ack, **check stale again**, resolve and commit, heartbeat.

## 12. Tuning

A decision table. Each row is a knob and the direction of its trade-off.

| Knob | Increase it | Decrease it |
| --- | --- | --- |
| `session.timeout.ms` | Fewer false rebalances; slower crash detection | Faster crash detection; more false rebalances |
| `heartbeat.interval.ms` | Less coordinator traffic; slower to learn a rebalance began; more sensitive to lost heartbeats | The reverse (keep <= one third of the session timeout) |
| `max.poll.interval.ms` (`rebalanceTimeout`) | Tolerates slower batches; slower to evict a stuck member; eager rebalances may wait longer | Evicts stuck members sooner; kills legitimately slow batches |
| Batch size (`js.consumer.max.batch.size`, `SINK_MAX_ROWS`) | Higher throughput per DB transaction; **longer time between polls**, bigger replays | Shorter polls, smaller replays, more commits |
| Assignor | `cooperativeSticky`: fewer partitions paused, slightly slower settling | `roundRobin`/`range`: simple, full stop-the-world |
| Processing time per batch | Must stay **well inside** the max poll interval | |

A worked constraint for the sink (using the observed defaults): one `eachBatch` call (one chunk of up to 1,000 rows) plus its worst-case DB retry window (20 s) plus the largest backoff (5 s) is **at most about 25 s** of waiting on top of the actual work, against a **60 s** rebalance timeout; the config check rejects values that violate this. To leave margin for slow transactions, keep **typical chunk time far below 60 s** (one second or two is typical for a 1,000-row insert, to be measured).

A rule of thumb for first settings: heartbeat **3 s**, session **10 to 45 s** (shorter if you want fast failover and can tolerate more rebalances), max poll **60 s**, chunk size such that processing takes **a few seconds**.

## 13. K8

K8 from the PRD: *adding or removing consumers, or processing longer than the poll or session limits, triggers rebalances that pause consumption and cause duplicates*; observe rebalance count and duration, consumption gaps, duplicates, and whether the cooperative or sticky assignor helps.

A plan, using the knobs the sink already has:

| Variant | How | Expect |
| --- | --- | --- |
| **Scale out/in under load** | Start 1 sink, then a 2nd, 3rd; later stop them gracefully | One rebalance per change; eager pauses everything briefly, cooperative moves a few partitions |
| **Crash** | `kill -9` a member (K5/K8 overlap) | Its partitions idle for ~the session timeout, then a rebalance; duplicates up to one chunk per moved partition |
| **Aggressive session timeout** | Set `CONSUMER_SESSION_TIMEOUT_MS` just above the heartbeat (for example 6 s / 1 s) and add load or GC pressure | False rebalances; a storm if processing stalls heartbeats' host |
| **Processing delay beyond the poll interval** | `SINK_PROCESSING_DELAY_MS` larger than `CONSUMER_REBALANCE_TIMEOUT_MS` for some chunks (`SINK_PROCESSING_DELAY_CHUNKS`, `..._SKIP_CHUNKS` select which) | The member is evicted, its batch marked stale, a rebalance, replay by the new owner |
| **Eager versus cooperative** | Repeat each variant with `CONSUMER_ASSIGNOR=roundRobin` and `cooperativeSticky` | Fewer partitions paused with cooperative; compare consumption gaps and duplicates |
| **Rolling restart** | Restart members one at a time, graceful versus `kill -9` | Graceful: clean handovers; crash: session-timeout gaps |

What to record: **rebalance count** and **duration** (from the assign/revoke logs), **per-partition consumption gaps** (time between batches per partition), **duplicates** (`ep_consumer_duplicates_total`, `attempted - inserted`), **lag** per partition over time, and the **effective settings** (session, heartbeat, rebalance timeout, assignor, batch size, `SINK_MAX_ROWS`). Always state the number of members and partitions. The audit (Step 7) should still reconcile: rebalances must never cause loss.

## 14. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| Session timeout | **45 s** (default), configurable | Few false rebalances on a laptop; K8 tests shorter values |
| Heartbeat | **3 s** | One fifteenth of the session timeout |
| Max poll / rebalance timeout | **60 s** | Room for a chunk plus the DB retry window (25 s) |
| Assignor | `roundRobin` default; `cooperativeSticky` switchable | Start simple; K8 compares |
| Batch size | 1,000 rows per chunk | Bounded time between polls and bounded replays |
| Rebalance handling | Check stale before work and before commit; do not commit stale work | No commits from non-owners; duplicates absorbed |
| Shutdown | Graceful: finish the batch, `disconnect()` | Immediate, clean rebalance |
| Static membership | Not used | A later improvement |

## 17. Edge cases

| Case | What happens |
| --- | --- |
| A batch longer than the max poll interval | The member is evicted; the batch is marked stale; the new owner replays |
| Event-loop starvation in the Node process | Heartbeats still flow (background thread) but polls stop: the **poll interval** is what fires **[reasoning]** |
| A machine suspended (laptop sleep) | Heartbeats stop; after resume the member is already removed and rejoins; expect a rebalance |
| Network partition between a member and the coordinator | After the session timeout the member is removed; commits from it fail |
| A commit sent just as the rebalance completes | Rejected (stale generation); counted; the rows are stored, so a retry or replay is safe |
| `eachBatch` throws | Seek back and retry the batch; not a rebalance |
| All members restart together | One eager rebalance each time they rejoin; use staggered restarts or the cooperative assignor |
| Group coordinator broker fails | Brief blip; the group re-finds the coordinator |
| Two members with the same client id | Not a problem; the member id is assigned by the coordinator |
| Subscribing to a pattern and a new topic appears | Triggers a rebalance **[reasoning]** |

## 19. Common confusions

1. **"A rebalance only happens when a consumer dies."** Joins, leaves, stuck members, subscription and partition changes all trigger it.
2. **"A graceful stop and a crash cost the same."** A clean leave is immediate; a crash costs the session timeout.
3. **"The session timeout catches a stuck consumer."** It catches a silent one. A stuck-but-heartbeating one is caught by the **max poll interval**.
4. **"`max.poll.interval.ms` is called that in this client."** It is `rebalanceTimeout`.
5. **"Heartbeats must be sent from my processing loop."** In this client a background thread sends them.
6. **"Cooperative rebalancing has no pause."** Moved partitions still pause (and take two rounds); the others do not.
7. **"A shorter session timeout is always better."** It causes false rebalances.
8. **"A partition leader election rebalances the group."** It does not.
9. **"Rebalances lose data."** They cause replays, not loss, if commits follow the work.
10. **"An idle member does not matter."** It still triggers rebalances.
11. **"Rebalance time is a constant."** It depends on how long the slowest member takes to finish its batch.
12. **"Throwing from `eachBatch` rebalances."** It re-reads the batch (seek back).

## 21. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Rebalance | Redistribution of partitions among group members |
| Eager | All partitions revoked, then reassigned |
| Cooperative | Only moved partitions revoked; two rounds |
| Session timeout | No heartbeat for this long means the member is dead |
| Heartbeat interval | How often a member signals liveness |
| Max poll interval | Max time between polls (`rebalanceTimeout` in this client) |
| Stale payload | A batch whose partition was revoked or whose poll time expired |
| Generation | Counter incremented per completed rebalance |
| Rebalance storm | Repeated rebalances that block progress |
| Static membership | A member keeps its identity across a quick restart |

### Settings (sink defaults, observed)

| Setting | Default |
| --- | --- |
| `CONSUMER_SESSION_TIMEOUT_MS` | 45,000 |
| `CONSUMER_HEARTBEAT_INTERVAL_MS` | 3,000 |
| `CONSUMER_REBALANCE_TIMEOUT_MS` (max poll) | 60,000 |
| `CONSUMER_MAX_BATCH_SIZE` / `SINK_MAX_ROWS` | 1,000 / 1,000 |
| `SINK_TRANSIENT_RETRY_WINDOW_MS` / `SINK_RETRY_MAX_MS` | 20,000 / 5,000 |
| `CONSUMER_ASSIGNOR` | `roundRobin` |

### Observed (6 s session, 1 s heartbeat)

| Event | Reaction |
| --- | --- |
| `kill -9` of a member | first rebalance about 5.3 s later |
| SIGTERM of a member | within about 0.3 s |
| 4th member joins, eager | 6 revoked, done in about 0.3 s |
| 4th member joins, cooperative | 1 revoked, done in about 1.2 s |

### Rules

```
heartbeat  ≤  session / 3                   crash detection  ≈  session timeout
one eachBatch (incl. retries)  <  max poll interval
rebalance pause (eager)  ≈  slowest member's current batch  +  coordination
```

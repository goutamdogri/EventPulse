# Kafka Consumer: Backpressure

*Consumer note 5 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`, the producer series in `../producer/`). Read consumer notes 2 (rebalances and the poll interval), 3 (commits) and 4 (lag) first. Backpressure means pausing fetching when the downstream is slow instead of buffering without bound. This note explains where a consumer can buffer, how the client's own prefetch is bounded, how `pause()` and `resume()` work in this client, the patterns that give you bounded memory, and how the sink applies them when Postgres is slow or down. It supports Step 2 (bounded prefetch), Step 4 (the database down case), Step 6 (the paused gauge), and experiments K6/K7 (slow database) and K10.*

**What was run.** **No labs were run for this note.** Earlier lab attempts on backpressure were **abandoned** on request, and the first lab runs exposed a problem in the test script (consumer note 1, section 16), so **no measurements are used**. Everything here is **[observed in source]**: read from `services/consumer-sink` (`sink-consumer.ts`, `batch-handler.ts`, `config.ts`, `sink-stats.ts`), the Stage 2 plan, and the installed client's source (`@confluentinc/kafka-javascript` 1.11.0); or **[reasoning]**: standard Kafka and librdkafka behavior. The memory examples use **illustrative** rates. **Please measure memory in a real run** before relying on any bound stated here.

## 1. TL;DR

- Kafka consumers **pull**: the consumer decides how fast to fetch. That makes **backpressure natural**: if the consumer does not ask for more, nothing more arrives, and the data simply **stays in the log** (the log is the big buffer, bounded by retention).
- The danger is **inside the consumer process**: code that takes records from the client and **parks them in memory** (an array, a queue, a worker pool) faster than it can process them, so memory grows until the process dies. **Never buffer without bound.**
- Three levers, from simplest to most flexible:
  1. **Do the work inside the handler and `await` it.** The client does not hand a partition a new batch until the current `eachBatch` call returns. This is the sink's main backpressure.
  2. **Bound what the client prefetches** (batch size, fetch bytes, concurrency). In this client the message cache is sized from the **measured consumption rate** (about 1.5 seconds of work per worker), so it shrinks when you are slow.
  3. **`pause()` and `resume()`** stop and restart fetching for chosen partitions: for when the downstream is **failing or full** and you want to stop reading **without** blocking the poll loop or leaving the group.
- In EventPulse the sink awaits its batch (bounded by `CONSUMER_MAX_BATCH_SIZE` and `CONSUMER_PARTITIONS_CONCURRENTLY`), and **pauses a partition** for `SINK_PAUSE_MS` when Postgres stays unavailable past its retry window, then **throws** so that the unresolved chunk is re-read after the resume. It holds only **the current chunk** in memory.
- Backpressure in a queue-based design shows up as **lag**, not as errors to callers: **a slow database no longer slows ingestion** (the Stage 2 goal); the price is lag and, eventually, **retention** (consumer note 4 and Kafka note 5).
- Sleeping inside `eachBatch` to "wait for the DB" is **wrong**: it holds the batch, risks the **max poll interval** and wastes the member. Pause, release the batch, resume later.

> **One-line version:** *The log is allowed to grow; your process is not: take only what you can finish, and when you cannot finish, stop asking.*

## 2. The mental model

A **conveyor belt feeding a packing station**.

| Packing station | Consumer |
| --- | --- |
| The warehouse behind the belt holding thousands of parcels | The Kafka log (large, bounded by retention) |
| You take parcels off the belt only when your hands are free | `await` in `eachBatch`: the next batch is not delivered until you return |
| A small tray beside you holding the next few parcels | The client's prefetch cache (bounded) |
| A worker who dumps every parcel into a corner of the room as fast as they arrive, "to sort later" | An unbounded in-memory queue: the room fills up |
| A sign "stop the belt" you press when the next station is jammed | `pause()` |
| Releasing the sign when the jam clears | `resume()` |
| Sleeping at your station with a parcel in hand, blocking the belt and missing the shift roll-call | Sleeping inside `eachBatch`: holds the batch, risks the poll interval |
| The warehouse getting fuller while you pause | Lag growing (the intended effect) |

## 3. Where a consumer can buffer

Following one record from the broker to the database in the sink:

```
 broker log ──fetch──► librdkafka fetch queue ──► client message cache ──► eachBatch(batch) ──► chunk ──► Postgres
   (retention-      (bytes per partition,       (adaptive: ~1.5 s of          (max batch size:     (SINK_MAX_ROWS:   (pool: PG_POOL_MAX)
    bounded)         librdkafka queue limits)    consumption per worker)       one partition at     one transaction)
                                                                              a time per slot)
```

| Place | Bounded by | Grows when |
| --- | --- | --- |
| **The log** (broker) | `retention.ms` / `retention.bytes` | You are slower than the producers: this is the **intended** buffer (lag) |
| **librdkafka's fetch buffers** | Fetch sizes per partition, internal queue limits **[reasoning]** | You fetch faster than the client hands records out |
| **The client's message cache** | An adaptive size: about `max cache ms` of consumption per worker, rounded to the batch size (section 5) | The cache is refilled while workers are busy |
| **The batch handed to your code** | `js.consumer.max.batch.size` (`CONSUMER_MAX_BATCH_SIZE`, 1,000) | Each `eachBatch` call |
| **The chunk being written** | `SINK_MAX_ROWS` (1,000) | Per DB transaction |
| **Your own queues** (workers, arrays, retry buffers, DLQ buffers) | **Only what you write** | You enqueue faster than you drain: **the unbounded case** |
| **The database connection pool** | `PG_POOL_MAX` | More concurrent partitions than connections |

The first six are **bounded by design or by settings**; only **your own queues** are bounded by nothing unless **you** bound them. The plan says it directly: *"No unbounded queue anywhere: batcher, consumer prefetch, retry loops, DLQ buffer."*

## 4. Natural backpressure

The sink's strategy **[observed in the header comment of `sink-consumer.ts`]**:

> *Bounded prefetch: `maxBytesPerPartition` / `maxBytes` cap what is fetched and held in memory, and a partition is not handed a new batch until its current `eachBatch` call returns. That is the backpressure.*

How it works: the handler does the **whole job** (parse, write to Postgres, DLQ, resolve, commit) **inside** the `async` callback and **returns only when finished**. While it runs for partition `p`:

- the client does **not** call `eachBatch` again for `p`;
- other partitions can still be served, up to **`partitionsConsumedConcurrently`** at once (sink default **1**, so one batch at a time per member; it must be `<= PG_POOL_MAX`, enforced at startup);
- fetching **continues in the background up to the cache and fetch limits**, then stops being drained.

The effect: **processing speed sets consumption speed**. If Postgres slows, `eachBatch` takes longer, fewer batches are delivered per second, the cache stays small, and the data waits in the **log** instead of in your memory. Memory stays flat; lag grows (consumer note 4).

Costs and cautions:

- **The unit of blocking is a partition's batch.** Slow work holds that partition's batch; it must stay inside the **poll interval** (consumer note 2, section 6; the sink's config rule ties the retry window to it).
- **An un-awaited promise breaks the guarantee.** If the handler returns before its work is done, the client delivers the next batch immediately, memory is no longer bounded by processing speed, and with auto-resolve the offset moves early (consumer note 3, section 5.4). **Always `await` the whole unit of work.**
- **Concurrency is a deliberate bound**, not a free speedup: each concurrent partition holds a DB connection during its transaction.

## 5. Prefetch

What the client reads ahead of your code, and how much **[observed in the client source and in `config.ts`]**:

| Setting | Client option | Sink env var (default) | Effect |
| --- | --- | --- | --- |
| Max bytes fetched per partition per request | `maxBytesPerPartition` → `max.partition.fetch.bytes` | `CONSUMER_MAX_BYTES_PER_PARTITION` (**1,048,576**) | Size of one partition's fetch |
| Max bytes per fetch (client option) | `maxBytes` → `fetch.message.max.bytes` | `CONSUMER_MAX_BYTES` (**10,485,760**) | See the caution below |
| Max wait for a fetch to fill | `maxWaitTimeInMs` → `fetch.wait.max.ms` | `CONSUMER_MAX_WAIT_MS` (**500**) | Latency of an idle fetch |
| Min bytes before a fetch returns | `minBytes` → `fetch.min.bytes` | (not set) | |
| Max records per `eachBatch` call | `'js.consumer.max.batch.size'` | `CONSUMER_MAX_BATCH_SIZE` (**1,000**; `-1` = unlimited) | Bounds the batch handed to your code |
| Cache size per worker | `'js.consumer.max.cache.size.per.worker.ms'` | (not set; client default **1,500**) | See below |

**The client's message cache is sized by time, not by count.** From the client's source: after each fetch it measures how many messages per millisecond one worker consumes, then sets the cache so that it holds **about `maxCacheSizePerWorkerMs` (1,500 ms) of consumption for each concurrent worker**, **rounded up to a multiple of the batch size**. Consequences:

- **A slow consumer gets a small cache** (little to read ahead, because it would not get to it soon anyway). **A fast consumer gets a larger one.** The prefetch adapts to the processing rate: roughly **1.5 seconds of work** is buffered, no more.
- It is **bounded in time, not in bytes.** With very large records the byte size of 1.5 s of work can still be large: check the memory for your record size.
- **With an unlimited batch size (`-1`) the cache is unbounded** (the source says it takes one call to process each partition): do **not** use `-1`. The sink defaults to 1,000.

A rough **upper estimate** of the consumer's buffered data **[reasoning, to be measured]**:

```
 buffered bytes  ≲  (assigned partitions × max.partition.fetch.bytes)         // librdkafka fetch buffers
                  + (cache ≈ 1.5 s × consumption rate × record size)         // the client's cache
                  + (current batch ≈ max batch size × record size) × concurrency
```

With 6 partitions, 1 MiB per partition, and a sink doing 5,000 records/s of 600 bytes: fetch buffers up to about **6 MiB**, the cache about **4.5 MB**, the batch about **0.6 MB**: **on the order of 10 MB**. It is bounded and small, **provided** your own code adds nothing.

**A caution about two fetch settings [reasoning, to be verified].** The client sets `max.partition.fetch.bytes` from `maxBytesPerPartition` and then `fetch.message.max.bytes` from `maxBytes`. In librdkafka these two property names are **aliases of the same setting**, so the later assignment (`maxBytes`, 10 MiB by default in the sink) would **override** the earlier one, and the sink's `CONSUMER_MAX_BYTES_PER_PARTITION` (1 MiB) may not be what is actually applied. Confirm the **effective** value by logging the client's resolved configuration, and record it with K-experiment results; if the 10 MiB wins, the worst-case fetch buffer per partition is ten times what the doc comment suggests.

## 6. pause and resume

**[observed in the client source]**

| Call | Behavior |
| --- | --- |
| `consumer.pause([{ topic, partitions: [p] }])` | Stops **fetching** the listed partitions. If `partitions` is omitted, **all assigned partitions of the topic** are paused. The consumer must be **connected** (it throws otherwise). **Marks any in-flight batch payload of those partitions stale**, so `isStale()` becomes true in a running `eachBatch`. Returns a **function that resumes** them |
| `consumer.resume([{ topic, partitions: [p] }])` | Restarts fetching. Also requires a connected consumer |
| `consumer.paused()` | Lists the paused partitions |
| The client's own guidance (a comment) | The **pattern of `pause()` followed by throwing an error is encouraged** |

What pause does and does not do:

- **It does not leave the group and does not stop heartbeats.** The member stays alive and keeps its partitions; only fetching for the paused partitions stops. (The paused partition's lag grows.)
- **It does not discard committed progress.** The offsets are untouched.
- **It marks the current batch stale**, which the sink's checks turn into "stop now, do not commit" (consumer notes 2 and 3).
- **Throwing from `eachBatch` after pausing** makes the client **seek back** to the first unresolved offset; after `resume()`, that chunk is read again. **Nothing is lost** and **nothing that was not committed is skipped**.
- **A rebalance may take the partition away** while paused; the new owner is not paused and will meet the same downstream problem itself **[reasoning]** (and will pause in turn).

Why pause is better than sleeping in the handler:

| Sleeping inside `eachBatch` | Pausing the partition and returning (or throwing) |
| --- | --- |
| The batch is held; its partition is blocked | The batch is released |
| Counts against the **max poll interval**; a long sleep gets the member evicted | The poll loop keeps running; the member stays healthy |
| Prefetch keeps filling behind you | Fetching for that partition stops |
| Other partitions of this member may be blocked too (with concurrency 1) | Other partitions continue |

## 7. Patterns

| Pattern | How | When | Bound on memory |
| --- | --- | --- | --- |
| **A. Await in the handler** (EventPulse) | Do all the work in `eachBatch` and return when done | Work is fast enough per batch; per-partition order matters | Current batch plus the client's cache |
| **B. Concurrency limit** | `partitionsConsumedConcurrently = N`, N <= pool size | More parallelism across **partitions** | N batches |
| **C. Bounded local queue with watermarks** | Hand records to a worker pool through a queue; **pause** when the queue reaches a high watermark and **resume** at a low watermark | The work is done by separate workers (CPU pool, external calls) that cannot run inside the handler | The queue's cap |
| **D. Pause on downstream failure** (EventPulse, DB down) | On a persistent downstream error, `pause()` the partition for a while, throw, resume on a timer | A dependency is down; retrying in place would hold the batch | The current chunk |
| **E. Circuit breaker around the dependency** | Fail fast while it is down | Avoid wasting attempts | n/a |
| **F. Rate limit** | Limit work per second | Protect a downstream with a fixed budget | n/a |
| **G. Shed load** | Drop work | **Not for events**: dropping acknowledged events is loss | n/a |

A **sketch of pattern C** (illustrative, **not** the repo's code), with watermarks so the queue cannot grow without bound:

```ts
const HIGH = 2000, LOW = 200;            // records
const queue: Msg[] = [];
let paused = false;

await consumer.run({
  eachBatchAutoResolve: false,
  eachBatch: async ({ batch, resolveOffset, commitOffsetsIfNecessary }) => {
    for (const m of batch.messages) queue.push(m);                 // hand off
    if (queue.length >= HIGH && !paused) {
      consumer.pause(assignedPartitions());                        // stop fetching
      paused = true;
    }
    // CAUTION: resolving here means "done" before the workers finish. Only do this if the queue is durable
    // or you accept loss on a crash. Otherwise resolve from the workers, after each unit of work completes.
  },
});

// workers drain the queue; when it falls below LOW:
if (paused && queue.length <= LOW) { consumer.resume(assignedPartitions()); paused = false; }
```

The sketch shows the shape and its **sharpest edge**: handing records to workers and resolving the offset immediately is **commit-before-work** (consumer note 3). In EventPulse the sink does **not** use this pattern for exactly that reason: the work happens inside the handler (pattern A), so "resolved" always means "done".

## 8. Anti-pattern

> *Buffer without bound.*

```ts
consumer.run({ eachBatch: async ({ batch }) => {
  for (const m of batch.messages) workQueue.push(m);   // unbounded array / worker pool queue
  // returns immediately: the client delivers the next batch right away
}});
```

What happens when the workers are slower than the arrivals:

```
 memory ≈ (arrival rate − drain rate) × time × bytes per record
 e.g. (20,000 − 5,000) rec/s × 60 s × 1,000 B  =  900 MB in one minute
```

- The process grows until the OS or the container kills it (OOM): **everything in the array is lost**, and with auto-resolve the **offsets were already moved**: **data loss**.
- Garbage-collection pressure first slows the process, which widens the gap: a **positive feedback loop**.
- The **log was a perfectly good buffer** (bounded by retention, durable, replicated). Moving the backlog into process memory trades a safe buffer for a fragile one.

The rule: **if you buffer, bound it; if you cannot bound it, do not buffer: pause.**

## 9. End to end

How backpressure flows through the whole Stage 2 pipeline, from the database back to the HTTP callers:

```
 Postgres slow/down
      ▲  (pool wait, statement timeout, connection errors)
 sink eachBatch takes longer / fails   ──► sink PAUSES the partition (DB down) or simply drains slower
      ▲
 consumer fetches less                 ──► the backlog stays in KAFKA: LAG grows
      ▲
 Kafka absorbs it (log, bounded by retention)
      ▲
 producer side is NOT slowed:  API → micro-batcher → Kafka keeps acknowledging  ──► ingest latency stays flat
```

Compare with Stage 1: a slow database made the API slow and then return 503s, because the API wrote to Postgres directly. In Stage 2 **backpressure stops at Kafka**: the PRD's K6/K7 claim is that *ingestion keeps its latency and rate; consumer lag grows*.

Where backpressure **does** reach the API **[observed in the batcher]**: only when **Kafka itself** cannot accept writes (outage, ISR below min, overload of the batcher's own queue): the batcher's **bounded queue** and **circuit breaker** turn that into **503 with `Retry-After`**, and memory stays flat (producer notes 5 and 7).

So the system has **two separate backpressure domains**:

| Domain | Mechanism | Visible as |
| --- | --- | --- |
| **API → Kafka** (producer side) | Bounded batcher queue, send timeout, breaker | 503 with `Retry-After` |
| **Kafka → Postgres** (consumer side) | Await in the handler, bounded prefetch, pause/resume | **Consumer lag** and freshness |

The system's **limit** on the consumer side is not memory but **retention**: if the backlog's age reaches the retention window, unread data is deleted (Kafka note 5). That is why lag alerts must compare against retention (consumer note 4, section 10).

## 10. The sink

How `consumer-sink` applies backpressure when Postgres is slow or down **[observed in `sink-consumer.ts`, `batch-handler.ts`, `config.ts`, `sink-stats.ts`]**.

**Slow database (not failing).** Each chunk simply takes longer; the handler awaits it; fewer batches per second are delivered; memory stays flat; lag grows. The `SINK_PROCESSING_DELAY_MS` family of knobs reproduces this on demand (K6/K7/K8).

**Database unavailable (failing).** For a chunk whose write hits a **blocking** error (connection refused/reset, pool timeout, statement timeout, and similar), the handler:

1. **Retries inside a window** with exponential backoff and jitter (`SINK_RETRY_BASE_MS` 100 ms up to `SINK_RETRY_MAX_MS` 5 s), heartbeating while it waits, for up to **`SINK_TRANSIENT_RETRY_WINDOW_MS` (20 s)**.
2. When the window is exhausted, **pauses the partition** (`pausePartition(SINK_PAUSE_MS)`, default **5 s**) and **throws** `DbUnavailableError` ("partition paused for N ms, chunk will be retried").
3. **Nothing was resolved**, so the client seeks back to the chunk's first offset.
4. After the pause a timer **resumes** the partition (`consumer.resume`), and the chunk is **read again**; if the database is still down, the cycle repeats.

Details of `pausePartition`:

```ts
private pausePartition(topic, partition, ms) {
  const key = `${topic}:${partition}`;
  if (this.stats.paused.has(key)) return;                    // already paused
  this.consumer.pause([{ topic, partitions: [partition] }]);
  this.stats.paused.add(key);                                // feeds the paused gauge
  const t = setTimeout(() => {
    this.resumeTimers.delete(t); this.stats.paused.delete(key);
    if (!this.running) return;                               // shutting down: do not resume
    try { this.consumer.resume([{ topic, partitions: [partition] }]); }
    catch (e) { this.log.error(`resume ${key} failed: ${e.message}`); }
  }, ms);
  this.resumeTimers.add(t);
}
```

- **Per partition.** Only the partitions that hit the failure pause; each partition handles its own.
- **Timers are tracked and cleared on shutdown** (`resumeTimers`), so a resume never fires after disconnect.
- **The comment** in the code states the reason: *"stop fetching this partition for ms, then resume. Its unresolved chunk is read again after the resume, so nothing is lost, and the consumer doesn't spin on a hot retry loop meanwhile."*
- **Memory** stays at **one chunk**: the plan says "it holds only the current chunk" during a DB outage.
- **Not a poison message.** The classification keeps a **down database** apart from a **bad record**: a down DB never produces a dead letter (Step 4); it produces a pause.
- **The rule that links this to the poll interval** (config check): `SINK_TRANSIENT_RETRY_WINDOW_MS + SINK_RETRY_MAX_MS < CONSUMER_REBALANCE_TIMEOUT_MS`. The in-place retry window plus one backoff must fit within the max poll interval, which is exactly why the handler **pauses and releases the batch** instead of retrying forever in place.

**What it looks like from outside**: committed offsets stop advancing, lag on the affected partitions grows linearly (`λ` with `μ = 0`), `ep_consumer_paused` is 1 during the pauses, freshness stops updating, the DLQ stays empty, and memory stays flat. When Postgres returns, the chunk is written, offsets resume, and lag drains at `μ − λ` (consumer note 4, section 5).

## 11. Interactions

**With rebalances (consumer note 2).**

- A **paused** member keeps heartbeating and polling, so it **stays in the group**. A **sleeping** handler would not poll and could be **evicted** at the max poll interval.
- If a partition is **revoked** while paused, the new owner reads from the committed offset (replaying the uncommitted chunk). The `pausePartition` resume timer for a partition the member no longer owns could fail; the code catches and logs the error.
- `pause()` **marks the in-flight batch stale**; the sink's stale checks therefore stop the batch before any commit.

**With commits (consumer note 3).**

- A paused partition's **unresolved chunk is never committed**; after the resume it is re-read. **No loss**, and no duplicates unless the DB write had already committed before the failure.
- A handler that **hands off to a queue and resolves** breaks "resolved means done"; avoid it.

**With lag (consumer note 4).**

- Backpressure is **how lag is created on purpose**. Lag growth during an outage is the **expected, healthy-looking symptom**; the thing to watch is its **age** against retention.

**With the producer side (producer notes 5 and 7).**

- The batcher's queue and breaker are **separate** backpressure for the API; they do not know about the consumer. A slow sink does not slow the API.

## 12. Observing

| Signal | Where | What it tells you |
| --- | --- | --- |
| **`ep_consumer_paused`** gauge (and the `paused` set in `/debug/stats`) | The sink | 1 while a partition is paused for DB backpressure (Step 6) |
| **Lag per partition**, `ep_consumer_lag` | Metrics | The size of the backlog Kafka is holding (the visible backpressure) |
| **Process memory** (RSS, heap) | `/debug/stats`, `process_*` metrics | Should be **flat** while lag grows; growth means an unbounded buffer |
| **Batch processing seconds**, DB write seconds | Histograms | Slow work: the cause |
| **DB pool**: total, idle, waiting | Pool gauges | Waiting connections mean concurrency above the pool |
| **Local lag** per partition | `/debug/stats` | Quick view inside a member |
| **Freshness** p50/p99 | `/debug/stats` | Visibility delay of what was stored |
| **Errors by class, retries by class** | `ep_consumer_errors_total`, `ep_consumer_retries_total` | DB trouble classes |
| **Rebalance count** | Metrics | Poll-interval violations from blocking handlers |

A **healthy backpressure signature**: lag rising or high, memory flat, `paused` toggling during outages, DLQ unchanged, freshness stale. An **unhealthy** one: memory rising with lag, or lag rising with **no** rebalances and **no** pauses and **very long** batch times (a blocked handler).

## 13. Tuning

| Knob | Effect | Direction |
| --- | --- | --- |
| `CONSUMER_MAX_BATCH_SIZE` / `SINK_MAX_ROWS` | Records per handler call / per transaction | Smaller = lower memory, shorter polls, more commits; larger = higher throughput per transaction |
| `CONSUMER_PARTITIONS_CONCURRENTLY` | Concurrent partitions in one member | More parallelism, more memory, more DB connections (<= `PG_POOL_MAX`) |
| `CONSUMER_MAX_BYTES_PER_PARTITION`, `CONSUMER_MAX_BYTES` | Fetch buffer per partition | Lower = lower memory; see the alias caution (section 5) |
| `CONSUMER_MAX_WAIT_MS` | Fetch wait when idle | Lower = lower latency |
| `js.consumer.max.cache.size.per.worker.ms` | Prefetch in time | Lower = less readahead |
| `SINK_TRANSIENT_RETRY_WINDOW_MS` | In-place retry time before pausing | Larger = fewer pauses; must stay under the poll interval |
| `SINK_PAUSE_MS` | How long a partition stays paused | Larger = fewer retries against a down DB, slower recovery |
| `SINK_RETRY_BASE_MS` / `SINK_RETRY_MAX_MS` | Backoff | Avoid a hot retry loop |
| `PG_POOL_MAX` | Database connections | Limits concurrent transactions |

## 14. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| Where the work happens | **Inside `eachBatch`**, awaited | "Resolved" means "done"; processing speed sets fetch speed |
| Batch bound | 1,000 records (`CONSUMER_MAX_BATCH_SIZE`), never `-1` | Bounded batch and cache |
| Concurrency | 1 partition at a time per member, <= `PG_POOL_MAX` | Bounded connections and memory |
| Backpressure on DB failure | Retry window, then **pause the partition and throw** | Do not hold the batch; no hot loop; no loss |
| Pause length | `SINK_PAUSE_MS` 5,000 | A balance between probing and idling |
| Own queues | **None** (no worker pool, no local buffer) | "No unbounded queue anywhere" |
| Visibility | `ep_consumer_paused`, lag, memory | The signature in section 12 |
| What bounds the backlog | Retention (24 h), watched through lag age | Consumer note 4 and Kafka note 5 |
| Producer-side backpressure | Separate: batcher queue, breaker, 503 | Producer notes 5 and 7 |

## 17. Edge cases

| Case | What happens |
| --- | --- |
| Handler returns before its work completes | The next batch arrives at once; memory unbounded by processing speed; auto-resolve loses work on a crash |
| `-1` batch size | The cache is unbounded; avoid |
| Very large records | 1.5 s of work can be large in bytes: size the memory by record size |
| Pause while a batch is in flight | The batch is marked stale; the sink stops and does not commit |
| Pause a partition then a rebalance takes it | The new owner is not paused; it will meet the same problem and pause itself |
| Resume after disconnect | The sink skips resume when not running; the client throws if not connected |
| Pausing every partition | The member idles but stays in the group (heartbeats and polls continue) |
| Resume timer fires after the partition was revoked | The code catches and logs the error |
| DB recovers during a pause | The partition waits out the pause (up to 5 s) before reading again |
| Long outage beyond retention | The backlog's oldest data expires: loss (Kafka note 5) |
| Cache sized for fast consumption, then a sudden slowdown | The cache shrinks at the next fetch; briefly larger than needed |
| Fetch buffer aliasing | The effective per-partition fetch may be 10 MiB, not 1 MiB (verify) |

## 19. Common confusions

1. **"Backpressure means slowing the producers."** In this design it means the **consumer** stops asking; the log absorbs the difference and producers are unaffected.
2. **"A bigger buffer fixes a slow consumer."** It only hides it until memory runs out. Lag in the log is the right buffer.
3. **"Sleeping in the handler is a fine retry."** It holds the batch and risks eviction. Pause and release.
4. **"`pause()` leaves the group."** It does not; the member keeps heartbeating and polling.
5. **"Pausing loses messages."** The unresolved chunk is re-read after the resume.
6. **"The client's cache is unbounded."** It is sized from the consumption rate (about 1.5 s of work per worker), unless the batch size is `-1`.
7. **"A slow database makes ingestion slow."** Not in Stage 2: it makes lag grow.
8. **"Lag growing means something is broken."** During backpressure it is the intended symptom; the danger is its age against retention.
9. **"More concurrency always helps."** It is capped by the DB pool and adds memory.
10. **"Handing records to a worker pool is harmless."** Without a bound it is the classic out-of-memory bug, and with early resolution it loses data.
11. **"`CONSUMER_MAX_BYTES_PER_PARTITION` is certainly applied."** Possibly overridden by `CONSUMER_MAX_BYTES` (alias); verify the effective value.
12. **"A paused partition is stuck forever."** It resumes on a timer (`SINK_PAUSE_MS`).

5. The cache becomes unbounded and each batch returns everything available for a partition. Avoid it.

7. Nothing was resolved, so the client seeks back to the first unresolved offset and re-reads the chunk after the resume; the offset moved only after the DB commit, so no loss, and duplicates only if the write had already committed.
8. It holds the batch, counts against the max poll interval (risking eviction), lets prefetch fill behind it and blocks other work.
9. ## 21. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Backpressure | Slowing intake so that the slowest stage is not overrun |
| Prefetch / cache | Records read ahead of your code |
| Watermarks | High and low queue sizes that trigger pause and resume |
| `pause()` / `resume()` | Stop / restart fetching chosen partitions |
| Stale batch | A batch whose partition was revoked, paused or whose poll time expired |
| Pause then throw | Pause the partition, throw so the unresolved chunk is re-read after the resume |
| Shock absorber | The log: it holds the backlog while consumers are slow |
| Retention | The limit of the backlog's age |

### The sink's backpressure

| Condition | Response |
| --- | --- |
| Slow DB | Handler takes longer; fewer batches; lag grows; memory flat |
| DB down | Retry window (20 s), then pause the partition (5 s) and throw; resume and re-read |
| Poison record | Dead-letter it (not a backpressure case) |
| Shutdown | Clear resume timers; finish the chunk; leave the group |

### Rules

```
await the whole unit of work in the handler        never buffer without a bound
resolved == done                                    pause instead of sleeping
memory ≈ fetch buffers + cache (~1.5 s of work) + current batch × concurrency     (measure it)
```

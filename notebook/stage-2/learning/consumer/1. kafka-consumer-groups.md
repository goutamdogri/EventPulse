# Kafka Consumer: Consumer Groups

_Consumer note 1 of the Stage 2 learning notes (the Kafka series is in `../Kafka/`, the producer series in `../producer/`). Read Kafka notes 1 (partitions) and 2 (offsets) first. Partitions are divided among the consumers of a group; more consumers than partitions leaves the extras idle. This note explains how a group works, how partitions are assigned, what each assignor does (with the real assignments from this cluster), where the parallelism ceiling comes from, and how it maps to your `consumer-sink`. It supports Step 2 (the `sink-postgres` group), Step 6 (assigned-partition metrics) and experiment K3._

**What was run.** **[observed]** means seen on this repo's cluster (3 brokers, RF 3) on **scratch topics that were deleted afterwards**, or read from this repo's source (`services/consumer-sink`, `packages/kafka-config`) and the installed client's source (`@confluentinc/kafka-javascript` 1.11.0). The lab for this note (Lab A, section 16) started 4 and then 7 Node consumers in one group on a 6-partition topic, once per assignor, with no data flowing, and recorded the assignments with `kafka-consumer-groups.sh` and the clients' own rebalance callbacks. No broker was stopped. **[reasoning]** marks standard Kafka behavior that was not observed here. A separate set of lab runs on consumption, commits, lag and pausing was **abandoned** (section 16 says why), so those subjects are written from the repo's code and from standard behavior only, in the notes that cover them.

## 1. TL;DR

- A **consumer group** is a set of consumers that share one `group.id` and **split the partitions of the topics they subscribe to**. Each partition is read by **exactly one member** of the group at a time. That is how Kafka lets you scale reading **and** keep per-partition order.
- **The partition is the unit of parallelism.** With 6 partitions, at most **6 members do work**; a 7th member is **idle** (it holds no partitions). This was seen directly: in a 7-member group on 6 partitions, one member showed `#PARTITIONS 0` [observed, section 6].
- **Different groups are independent.** Two groups reading the same topic each get **every record**, each with its own committed offsets (Kafka note 2). A group is how you add a second reader (analytics, a replay, the DLQ tool) without disturbing the first.
- **Assignment is computed by a strategy (an assignor).** Three were run on this cluster:
  - `range`: contiguous blocks (`0,1 | 2,3 | 4 | 5`);
  - `roundRobin`: spread one by one (`0,4 | 1,5 | 2 | 3`);
  - `cooperativeSticky`: keeps partitions where they are and moves only what must move.
- **Membership changes trigger rebalances.** With the **eager** assignors (`range`, `roundRobin`), **every join revoked all 6 partitions from every member**, including a join by a member that ended up owning nothing. With **`cooperativeSticky`** the revokes were only the partitions that moved (3, 2, 1, 1, 1, then 0) [observed, section 8].
- A group's **effective parallelism is `min(members, partitions)`**, further limited by **skew**: the busiest partition's consumer sets the ceiling (`1 / largest share`, producer note 6).
- In EventPulse the group is **`sink-postgres`** on `events.raw` (6 partitions). The code defaults to `roundRobin`, a 45 s session timeout and one partition processed at a time per member; the assignor is switchable (`CONSUMER_ASSIGNOR`).

> **One-line version:** _A consumer group turns a topic's partitions into a work queue shared by its members: each partition has one owner, and the owner changes only through a rebalance._

## 2. The mental model

A checkout area in a supermarket with six numbered lanes (partitions) and a team of cashiers (consumers).

| Supermarket                                                                                | Kafka                                                |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Six lanes of customers, each lane a queue in order                                         | Six partitions, each an ordered log                  |
| A team of cashiers sharing the work                                                        | A consumer group (`group.id`)                        |
| A rule: **one cashier per lane at a time**, so a lane's order is never mixed up            | One consumer per partition within a group            |
| More cashiers than lanes: the extras stand idle                                            | More members than partitions: idle members           |
| The shift manager decides who takes which lane                                             | The assignor (computed by the group's leader member) |
| A new cashier arrives; the manager redraws the roster                                      | A rebalance                                          |
| Redrawing from scratch (everyone stops, everyone re-picks)                                 | **Eager** rebalance                                  |
| Moving only the lanes that must change, everyone else keeps scanning                       | **Cooperative** rebalance                            |
| A second shop team watching the same lanes for a different purpose, with their own tallies | A second consumer group with its own offsets         |

## 3. What a consumer group is

**Definition.** A group is identified by a string, **`group.id`**. Every consumer started with the same `group.id` and subscribed to the same topic belongs to it. EventPulse's is **`sink-postgres`** (`GROUP_SINK_POSTGRES` in `packages/kafka-config`, overridable by `CONSUMER_GROUP_ID`) **[observed]**.

What the group gives you:

| Property                              | Meaning                                                                                                                                 |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Exclusive ownership per partition** | At any moment each partition has at most one owner in the group, so records of a partition are processed **in order and by one worker** |
| **Load sharing**                      | The partitions are divided among the members                                                                                            |
| **Failover**                          | If a member dies, its partitions are given to the others                                                                                |
| **Progress tracking**                 | The group has **one committed offset per partition** (Kafka note 2), shared by whoever owns the partition                               |
| **Independence**                      | Other groups see the same data, with their own offsets and their own membership                                                         |

What a group is **not**: it is not a copy of the data (the data stays in the log), not a queue that removes records (reading never deletes, Kafka note 2), and not tied to one machine: members can be any processes that share the `group.id`.

**Members.** A member is one consumer client instance (one `consumer.connect()`), not one thread or one machine. In the sink, each process is one member. (A process can read several of its partitions concurrently, section 10, but it is still **one member**.)

**Subscription.** A member subscribes to one or more topics (the sink: `events.raw`). The group's assignment covers the **union** of the subscribed topics' partitions. All members of a group should subscribe to the **same** topics: members with different subscriptions in one group make assignment awkward and surprising **[reasoning]**.

## 4. The group protocol

The classic group protocol (the one in use in this repo's observed runs: the `describe` output shows empty `CURRENT-EPOCH` and `TARGET-EPOCH` columns, section 12) works through a **group coordinator** and a **group leader**.

```
 consumer starts                                 group coordinator (a broker)
      |  --- FindCoordinator(group) ------------>  the broker that leads the partition of __consumer_offsets
      |                                            chosen by hash(group.id) mod 50 (Kafka note 2, section 7)
      |  --- JoinGroup(protocols, topics) ------>  waits for the members to (re)join, then picks a LEADER
      |  <-- JoinGroup response ----------------   (leader gets the member list and their subscriptions)
      |
      |  leader: computes the assignment with the chosen assignor (CLIENT-SIDE)
      |
      |  --- SyncGroup(assignment if leader) --->  coordinator distributes the assignments
      |  <-- SyncGroup response (my partitions)--
      |
      |  start fetching my partitions from the committed offsets (or the reset policy)
      |  --- Heartbeat every heartbeat.interval.ms ... (keeps membership alive)
```

Key points:

- **The coordinator** is a broker, not a client. It holds the group's membership and committed offsets. If its broker moves (leadership change), the group re-finds it.
- **The group leader** is **one of the consumers** (the first to join, normally). It runs the assignor **in the client**: Kafka brokers do not decide who reads what in the classic protocol. This is why the **assignor is a client setting** (`partition.assignment.strategy`), and why a group's members must agree on at least one strategy.
- **Generation.** Every completed rebalance increments a **generation id**. Requests from a member with an old generation are rejected, which is how a member that was removed learns it no longer owns its partitions (and why commits from it fail, Kafka note 2).
- **Heartbeats** prove liveness; missing them for `session.timeout.ms` removes the member. A separate limit, `max.poll.interval.ms`, removes a member that is alive but not consuming (consumer note 2).
- **The first join of a new group** waits a short time (broker `group.initial.rebalance.delay.ms`, 3 s by default **[reasoning]**) so that members starting together form one group at once instead of rebalancing repeatedly. **[observed]**: the first member received its first assignment about **3.2 s** after starting; the members that joined an existing group saw their first rebalance event within **0.7 to 1.3 s**.

## 5. Assignment

An **assignor** takes the members and the partitions and returns "member X gets these partitions". Properties that distinguish them:

| Property                     | Question                                                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Balance**                  | Do all members get nearly the same number of partitions?                                                   |
| **Stability ("stickiness")** | After a membership change, how many partitions change owner?                                               |
| **Locality across topics**   | Do partitions with the same number in different topics go to the same member (co-partitioning, for joins)? |
| **Protocol**                 | **Eager** (revoke everything, then assign) or **cooperative** (revoke only what moves, in two phases)      |

The assignment is a function of the **membership at that moment**; it has no memory unless the assignor is a sticky one. That is why with `roundRobin` or `range` **a partition may change owner on every rebalance even when it did not need to** (section 6 shows it).

Why stability matters for the sink: a member that keeps its partitions keeps reading from where it was, with warm connections and fetch buffers; a member that loses a partition mid-batch must stop and may leave **uncommitted work to be redone by the new owner** (duplicates, Kafka note 2, section 12). Fewer moves means fewer duplicates and shorter pauses.

## 6. The assignors

**Lab A [observed].** Topic with 6 partitions; members started one by one every 14 s (`c1` to `c4`), then `c5`, `c6`, `c7`; the assignment was read with `kafka-consumer-groups.sh --describe --group G --members --verbose`. No data was produced: assignment does not depend on data.

### 6.1 `roundRobin` (the client's default and `consumer-sink`'s default)

| Members        | Assignment                                                                 |
| -------------- | -------------------------------------------------------------------------- |
| 4 (`c1`..`c4`) | `c1`: 0, 4 · `c2`: 1, 5 · `c3`: 2 · `c4`: 3                                |
| 7 (`c1`..`c7`) | `c1`: 0 · `c2`: 1 · `c3`: 2 · `c4`: 3 · `c5`: 4 · `c6`: 5 · `c7`: **none** |

Behavior: deals partitions out one at a time across the members. Even balance (counts differ by at most 1).

### 6.2 `range`

| Members | Assignment                                                              |
| ------- | ----------------------------------------------------------------------- |
| 4       | `c1`: 0, 1 · `c2`: 2, 3 · `c3`: 4 · `c4`: 5                             |
| 7       | `c1`: 0 · `c2`: 1 · `c3`: 2 · `c4`: 3 · `c5`: 4 · `c6`: 5 · (`c7` none) |

Behavior: per topic, sorts the members, then gives each a **contiguous block** of partitions (`ceil(6/4) = 2` for the first two members, `1` for the rest). Contiguous blocks are what makes `range` keep same-numbered partitions of **several topics** with the same member (useful for joining topics); for a single topic it gives the same balance as round robin.

### 6.3 `cooperativeSticky`

| Members | Assignment                                                              |
| ------- | ----------------------------------------------------------------------- |
| 4       | `c1`: 4, 5 · `c2`: 1, 2 · `c3`: 3 · `c4`: 0                             |
| 7       | `c1`: 5 · `c2`: 2 · `c3`: 3 · `c4`: 0 · `c5`: 1 · `c6`: 4 · (`c7` none) |

Behavior: **sticky** (keeps each partition with its current owner when the balance allows) and **cooperative** (rebalances in two phases and revokes only moved partitions). Note the 4-member assignment is **not** the tidy `0,1 | 2,3 | ...` of the other two: it is whatever came out of moving the **fewest** partitions as members joined one by one. Same balance (two members with two partitions, two with one), different assignment. Ownership depends on **history**, not only on the member list.

### 6.4 What the three tables show together

- **All three are balanced.** The assignor choice does not change how evenly partitions are split.
- **The 4-member assignments are three different assignments** of the same partitions: ownership is not a property of the topic, only of the strategy and the history.
- **The eager assignors reshuffled between 4 and 7 members** (for example, under `roundRobin`, `c1` held `0, 4` with 4 members and `0` with 7; `c5` took `4`). A partition changing owner is exactly what a rebalance costs (section 8).
- **`c7` ends up with nothing under all three** (section 7).
- The describe output also has `CURRENT-EPOCH` and `TARGET-EPOCH` columns that stay `-`: those belong to the new group protocol (section 12) and are unused with the classic one.

### 6.5 Choosing

| Assignor            | Strengths                                       | Weaknesses                                                                                                                | Use                                                            |
| ------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `range`             | Contiguous blocks; co-partitions several topics | Eager; with many topics of few partitions it favors the first members                                                     | Joining several co-partitioned topics                          |
| `roundRobin`        | Even; simple                                    | Eager; moves partitions needlessly                                                                                        | The default; fine for a small, stable group                    |
| `sticky`            | Few moves                                       | Eager (all stop during the rebalance)                                                                                     | Rarely: prefer the cooperative one                             |
| `cooperativeSticky` | Few moves **and** no stop-the-world             | Two-phase rebalances take slightly longer to settle for the moved partitions (section 8); needs all members to support it | **Groups that rebalance under load**, which is the K8 question |

In the repo the choice is `CONSUMER_ASSIGNOR=roundRobin|range|cooperativeSticky` (`consumer-sink` `config.ts`), the default being `roundRobin` **[observed]**. K8 is meant to compare them.

## 7. More consumers than partitions

> More consumers than partitions leaves the extras idle.

**[observed]** In the 7-member groups, one member (`c7`) showed `#PARTITIONS 0` and no assignment, under all three assignors. It was a full member: it had joined the group, held a session, and sent heartbeats, but there was nothing for it to read.

Why: a partition has exactly one owner in the group. With 6 partitions the maximum useful number of members is 6.

Consequences:

- **Extra consumers add no throughput.** K3 is the experiment that shows it: partitions 1, 3, 6, 12 against 1 to 12 consumers.
- **They are not useless**: an idle member is a **hot standby**. If an active member dies, the idle one takes its partitions without any new process starting (after the session timeout and a rebalance). Some deployments run N+1 members for this reason.
- **They are not free**: every idle member still **triggers rebalances** when it joins or leaves, and under an **eager** assignor **a join of an idle member still revokes every partition from every active member**. **[observed]**: when `c7` joined the `roundRobin` group, all 6 partitions were revoked from 6 members and re-assigned, although `c7` itself received nothing (the cooperative assignor revoked 0 partitions for the same join).
- **Scaling the group beyond the partition count requires more partitions**, which is a hard-to-change decision (Kafka note 1, section 10.4, and producer note 6, section 10).

## 8. What a join costs

From the same lab: at each join, the total number of partitions **revoked** across all members, and how soon after the new member started the first rebalance event happened **[observed]**.

| Join                | `roundRobin` revoked | `range` revoked | `cooperativeSticky` revoked | First rebalance event after start |
| ------------------- | -------------------- | --------------- | --------------------------- | --------------------------------- |
| `c1` (first member) | 0                    | 0               | 0                           | about 3.2 s                       |
| `c2`                | **6** (by 1 member)  | **6**           | **3**                       | about 1.2 s                       |
| `c3`                | **6** (by 2)         | **6**           | **2**                       | about 1.2 s                       |
| `c4`                | **6** (by 3)         | **6**           | **1**                       | about 1.2 s                       |
| `c5`                | **6** (by 4)         | **6**           | **1**                       | 0.7 to 1.3 s                      |
| `c6`                | **6** (by 5)         | **6**           | **1**                       | 0.7 to 1.3 s                      |
| `c7` (gets nothing) | **6** (by 6)         | **6**           | **0**                       | 0.7 to 1.3 s                      |

How to read it:

- **Eager = stop-the-world.** Under `roundRobin` and `range` every join took **all 6 partitions** from **every existing member** and gave them out again. For the length of the rebalance nobody owns anything.
- **Cooperative = minimal movement.** Under `cooperativeSticky` the number of partitions revoked equals the number that **had to move** (3, then 2, 1, 1, 1, 0). The partitions that stay never stop.
- **Cooperative rebalances take a second round.** The cooperative events spanned about **2 s** from the first event to the last, while the eager ones completed within about **0.3 s** in a quiet group. That is the price: the moved partitions are first revoked, then assigned in a **second** rebalance. It buys that **unmoved partitions never pause**.
- **What the real pause is depends on how busy the members are** (consumer note 2, section 7): in this lab nobody was processing, so the stop-the-world was short. With long-running batches an eager rebalance waits for the slowest member to finish its current batch before it can complete, and **all** partitions wait with it.

(An attempt to measure per-partition consumption gaps under live traffic was **discarded**: the load-generating consumer in that run had a harness problem that corrupted the consumption counts. The revoke/assign **event counts and timings** in the table do not depend on consumption and are reliable.)

## 9. Several groups

Two groups on the same topic **each read every record**:

```
 events.raw  ──►  group sink-postgres  (6 members max): writes to Postgres,  offsets: P0=1200 P1=1190 ...
             ──►  group audit-tool      (any size):      counts/inspects,      offsets: P0=400  P1=380  ...
```

- Each group has its **own committed offsets**, its **own membership** and its **own rebalances**. A slow or crashed analytics group does not slow the sink or move its offsets.
- Costs: each extra group adds **fetch load** on the brokers (each reads the data) and a **retention risk** per group: each group can fall behind retention independently (Kafka note 5).
- **Never share a `group.id` between different applications** by accident: they would **split** the partitions between them, and each would see only part of the data. In EventPulse the group id is a named constant, and tests use a separate group per run (the e2e tests create `sink-e2e-<uuid>` groups, which are left behind on the cluster as `Empty` groups until deleted).
- **A group per instance** is the opposite mistake: every instance would then read **everything** (N-fold duplication), with no sharing.
- A group with **no members** still exists (state `Empty`) and keeps its committed offsets until they expire (7 days by default, Kafka note 5, section 11).

## 10. Parallelism

The throughput limits of a group, from the hardest to the softest:

| Limit                                              | Value                                            | Notes                                                                                                         |
| -------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| **Partition count**                                | `partitions`                                     | At most that many members do work (section 7)                                                                 |
| **Skew**                                           | `1 / (largest partition share)` consumers' worth | Producer note 6, section 7.3: with the measured Zipf skew, 2.9 of 6                                           |
| **Members' processing capacity `c`** per partition | `c` events/s per partition                       | Set by the sink's work: parse + Postgres transaction per chunk                                                |
| **Concurrency inside a member**                    | `partitionsConsumedConcurrently` (sink: 1)       | A member can work several of its partitions at once; each partition is still one batch at a time and in order |
| **The database**                                   | Postgres connections and commit rate             | The shared downstream: more members can just move the queue to the pool (`PG_POOL_MAX`)                       |

Formulas:

```
 useful members          = min(members, partitions)
 group throughput        ≈ min( useful members , 1/(largest partition share) ) × c      (before the database limit)
 in-member parallelism   = partitionsConsumedConcurrently   (kept <= PG_POOL_MAX, enforced in the sink's config)
```

The sink's config enforces `CONSUMER_PARTITIONS_CONCURRENTLY <= PG_POOL_MAX` **[observed in `config.ts`]** because running more partitions concurrently than there are database connections just queues them on the pool.

Order is preserved **per partition** whatever you do: a member processes one batch of a partition at a time and does not fetch the next until the current one finishes (the backpressure mechanism, consumer note 5).

## 11. Group state

A group is always in one **state** **[reasoning, standard]**:

| State                 | Meaning                                                                               |
| --------------------- | ------------------------------------------------------------------------------------- |
| `Empty`               | No members (offsets kept). **Observed** for the left-over test groups on this cluster |
| `PreparingRebalance`  | A rebalance started; waiting for members to rejoin                                    |
| `CompletingRebalance` | Members joined; waiting for the leader's assignment                                   |
| `Stable`              | Assignment active; members consuming                                                  |
| `Dead`                | Group removed                                                                         |

What to look at, and the commands (all read-only):

```bash
B=kafka1:19092
K() { docker exec -i ep-kafka1 /opt/kafka/bin/"$@"; }

K kafka-consumer-groups.sh --bootstrap-server $B --list
K kafka-consumer-groups.sh --bootstrap-server $B --describe --group sink-postgres             # per partition: offsets, lag, owner
K kafka-consumer-groups.sh --bootstrap-server $B --describe --group sink-postgres --members --verbose   # per member: partitions
K kafka-consumer-groups.sh --bootstrap-server $B --describe --group sink-postgres --state     # coordinator, strategy, state, members
```

**[observed]** The `--state` output on this cluster shows, for the leftover groups, `COORDINATOR (ID)` (for example `kafka2:19092 (2)`), `ASSIGNMENT-STRATEGY`, `STATE` (`Empty`) and `#MEMBERS` (`0`): so you can see **which broker is the group's coordinator** and which strategy is active.

What to monitor: the **member count** against the expected number of sinks, the **state** (a group stuck in `PreparingRebalance` is a problem), the **rebalance count** (`ep_consumer_rebalances_total`, Step 6) and the **assigned partitions** per member (`ep_consumer_assigned_partitions`, which the sink also lists in `/debug/stats`).

## 12. The new group protocol

Kafka 4 includes a **new consumer group protocol** (often called KIP-848): the **broker coordinator computes the assignment**, rebalances are incremental and have no group-wide stop, and members do not need a "group leader". The client chooses it with `group.protocol=consumer` instead of `classic`.

What this repo shows **[observed]**:

- `kafka-consumer-groups.sh --describe --members --verbose` prints columns **`CURRENT-EPOCH`, `CURRENT-ASSIGNMENT`, `TARGET-EPOCH`, `TARGET-ASSIGNMENT`**: these belong to the new protocol and stayed `-` in all runs, because the consumers used the **classic** protocol (the client's default).
- In the installed client's source, `sessionTimeout` and `heartbeatInterval` throw "not supported when `group.protocol` is not `classic`": with the new protocol those settings are controlled **by the broker**, not the client.

Practical meaning: Stage 2 uses the **classic** protocol (the client's settings `CONSUMER_SESSION_TIMEOUT_MS` and `CONSUMER_HEARTBEAT_INTERVAL_MS` apply, and the assignor is chosen client-side). The new protocol is a possible Stage 8 comparison. This note's tables describe the classic protocol; its behavior was not tested.

## 13. EventPulse

The `consumer-sink` service **[observed in `sink-consumer.ts`, `config.ts`]**:

| Aspect                 | What it does                                                                                                                                                   |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Group id               | `sink-postgres` (`CONSUMER_GROUP_ID` to override; tests use unique ids)                                                                                        |
| Topic                  | `events.raw` (`CONSUMER_TOPIC`)                                                                                                                                |
| Assignor               | `CONSUMER_ASSIGNOR` = `roundRobin` (default), `range` or `cooperativeSticky`                                                                                   |
| Start position         | `CONSUMER_FROM_BEGINNING=true` (earliest)                                                                                                                      |
| Auto-commit            | **Off**                                                                                                                                                        |
| Concurrency per member | `CONSUMER_PARTITIONS_CONCURRENTLY=1` (must be <= `PG_POOL_MAX`)                                                                                                |
| Per-partition batches  | `eachBatch`, up to `CONSUMER_MAX_BATCH_SIZE=1000` messages per call, one partition per call                                                                    |
| Rebalance hook         | `rebalance_cb`: logs `assigned ...` / `revoked ...`, tracks the set of owned partitions, counts rebalances, and keeps the default assign/unassign behavior     |
| Several instances      | `METRICS_PORT` differs per instance (default 8001) so several members can run on one host                                                                      |
| Shutdown               | `disconnect()` waits for the current batch, then the member **leaves the group**, which triggers a prompt rebalance instead of waiting for the session timeout |

The rebalance hook is the place where the "assigned partitions" metric comes from. It uses the client's rebalance codes (`ERR__ASSIGN_PARTITIONS` and `ERR__REVOKE_PARTITIONS`). With the cooperative assignor the callback receives **only the changed partitions**, so the sink keeps a running set (`assigned.add` / `assigned.delete`) rather than replacing it, which is the right approach for both protocols **[observed in the code]**.

Design consequences:

- **Six partitions means at most six useful sink instances.** Anything above that is a standby.
- **The assignor decides what a scale-up or scale-down costs** (section 8). The default (`roundRobin`) pays a full stop-the-world each time; K8 is the experiment that quantifies it and tests `cooperativeSticky`.
- **A new member always triggers a rebalance**, even if idle. Start and stop sinks on purpose, not casually, while measuring.
- **Ownership moves, so state must not live in a member.** The sink has none beyond what is in Postgres and Kafka, which is why a rebalance is safe (at worst a bounded replay, deduplicated by `ON CONFLICT (event_id)`).

## 16. Commands

**Lab A (run on this cluster).** A small Node consumer script (using the repo's pinned client and a `rebalance_cb` that logs assign/revoke events with timestamps) was started as 4 and then 7 members of one group, once per assignor, on a fresh 6-partition topic created with `--partitions 6 --replication-factor 3 --config min.insync.replicas=2`. Between starts it waited 14 s. The group was inspected with:

```bash
K kafka-consumer-groups.sh --bootstrap-server $B --describe --group G --members --verbose
```

Then the members were stopped with SIGTERM and the group and topic deleted. The revoke/assign events were analysed from the scripts' logs (partitions revoked and assigned per join, first event after start).

**What was not kept.** Further labs for this series were started (consumption under load, commit modes with crashes, lag growth, backpressure) and then **stopped on request**. The first attempts also exposed a problem in the **test script** (a consumer that began on an empty partition kept re-reading offset 0; the cause was not determined, and it was **not** shown to be a client bug), so **no numbers from those runs are used anywhere** in these notes. Everything about commits, lag and backpressure in the other consumer notes is derived from this repo's code, the installed client's source, and standard Kafka behavior, and is labelled accordingly.

## 17. Edge cases

| Case                                            | What happens                                                                      |
| ----------------------------------------------- | --------------------------------------------------------------------------------- |
| Members > partitions                            | The extras own nothing (observed); each join/leave still rebalances               |
| One partition, many members                     | One works, the rest idle                                                          |
| Member dies without leaving                     | Its partitions wait for the **session timeout**, then rebalance (consumer note 2) |
| Member leaves cleanly (SIGTERM, `disconnect()`) | Prompt rebalance, no wait for the timeout                                         |
| Two apps with the same `group.id`               | They split the partitions; each sees part of the data                             |
| Different subscriptions in one group            | Surprising assignments; avoid                                                     |
| Partitions added to the topic                   | The group rebalances to include them, and keys move (producer note 6)             |
| Group has no members                            | State `Empty`; offsets kept until they expire                                     |
| Assignors disagree between members              | Members must share at least one strategy; if not, joins fail **[reasoning]**      |
| A member that is slow to rejoin                 | Eager rebalances wait for it; all partitions wait with it                         |
| Rolling restart of all sinks                    | A series of rebalances; with eager each restart stops everyone briefly            |

## 18. Common confusions

1. **"A consumer group is a set of machines."** It is a set of consumer clients that share a `group.id`.
2. **"More consumers means more throughput."** Only up to the partition count.
3. **"Each consumer in a group sees all messages."** Each sees only its partitions' messages; each **group** sees all.
4. **"The broker assigns partitions."** In the classic protocol the **group leader (a client)** runs the assignor.
5. **"An idle consumer costs nothing."** It triggers rebalances; under eager assignors it still stops everyone.
6. **"Rebalances move only what is needed."** Only with a sticky/cooperative assignor.
7. **"Order is global within a group."** It is per partition.
8. **"Two groups share the work."** They each get everything.
9. **"A partition's owner is fixed."** It changes at every rebalance.
10. **"`roundRobin` and `range` give different balance."** In this single-topic case they balanced the same; they differ in which partitions go together.
11. **"My group is healthy because lag is zero."** Also check members, state and rebalance count.
12. **"The assignor is a broker setting."** It is a client setting (classic protocol).

## 20. Cheat sheet

### Glossary

| Term                  | Meaning                                                      |
| --------------------- | ------------------------------------------------------------ |
| Consumer group        | Members sharing a `group.id`, splitting a topic's partitions |
| Member                | One consumer client instance                                 |
| Group coordinator     | The broker managing a group's membership and offsets         |
| Group leader          | The member that runs the assignor (classic protocol)         |
| Generation            | Counter incremented at each completed rebalance              |
| Assignor              | The strategy dividing partitions among members               |
| Eager rebalance       | Everyone revokes everything, then re-assigns                 |
| Cooperative rebalance | Only moved partitions are revoked; two phases                |
| Idle member           | A member with no partitions                                  |
| Standby               | An idle member kept for failover                             |

### Observed assignments (6 partitions, 4 members)

| Assignor            | Assignment                              |
| ------------------- | --------------------------------------- |
| `roundRobin`        | `0,4 · 1,5 · 2 · 3`                     |
| `range`             | `0,1 · 2,3 · 4 · 5`                     |
| `cooperativeSticky` | `4,5 · 1,2 · 3 · 0` (history-dependent) |

### Observed cost of joins (partitions revoked)

| Join       | Eager (`roundRobin`, `range`) | `cooperativeSticky` |
| ---------- | ----------------------------- | ------------------- |
| 2nd member | 6                             | 3                   |
| 3rd        | 6                             | 2                   |
| 4th        | 6                             | 1                   |
| 5th        | 6                             | 1                   |
| 6th        | 6                             | 1                   |
| 7th (idle) | 6                             | 0                   |

### Rules

```
useful members = min(members, partitions)       group throughput ≈ min(useful members, 1/largest share) × c
one owner per partition per group               each group sees every record
```

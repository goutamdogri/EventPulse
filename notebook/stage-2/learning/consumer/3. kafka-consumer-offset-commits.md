## 1. TL;DR

- A **commit** tells Kafka "this group has finished everything before offset N on this partition". It is the **only** progress record that survives a restart or a rebalance (Kafka note 2).
- **Where you put the commit, relative to the work, decides the delivery guarantee:**
  - **Work, then commit → at-least-once.** A crash in between **repeats** work (duplicates), never skips it.
  - **Commit, then work → at-most-once.** A crash in between **skips** work (loss), never repeats it.
- EventPulse chooses **at-least-once, with an idempotent write**: **commit only after the database transaction commits** (and after any DLQ record is acknowledged), and let `INSERT ... ON CONFLICT (event_id) DO NOTHING` absorb the replays. Duplicates are **counted** (`attempted - inserted`), never hidden.
- **Auto-commit is convenient and dangerous.** The danger depends on **what the library commits**. In the Java model it commits what was **handed to your code** on a timer, so a crash can skip records. In this client, with offsets stored only when **resolved**, it commits what you **resolved**, which makes it safer, but it still has a **duplicate window** equal to the commit interval, and it **moves the commit decision out of your code**, so you cannot tie it to the DB commit. The sink **turns it off**.
- **The client's commit API** (`resolveOffset` then `commitOffsetsIfNecessary`): `resolveOffset(n)` stores **`n + 1`** locally; with `autoCommit: false`, `commitOffsetsIfNecessary()` **commits immediately**; if `eachBatch` throws, the client **seeks back** to the first unresolved offset (retry).
- The sink has **exactly one place** that resolves and commits offsets, per chunk, after the DB commit; it **retries the commit** up to 3 times with backoff because the rows are already stored; it **skips the commit** if the partition was revoked meanwhile.
- **A crash can cost at most one chunk of duplicates per partition** (up to `SINK_MAX_ROWS` = 1,000), and **no loss**. K5 kills the consumer at every step to show it.

> **One-line version:** *Commit means "done", so only say it after you are; the cost of being early is lost events, the cost of being late is a few repeats you can afford.*

## 2. The mental model

A reading list with a **bookmark** that you move yourself.

| Reading list | Kafka |
| --- | --- |
| You read a chapter, **then** move the bookmark | Commit after processing: at-least-once |
| You move the bookmark first, then start reading; the phone rings and you never finish | Commit before processing: at-most-once; the chapter is skipped |
| Your **assistant moves the bookmark every 5 seconds** to wherever you are | Auto-commit on a timer |
| You re-read the last chapter after a power cut because the bookmark was behind | A replay; harmless if re-reading is harmless (idempotent) |
| You write the notes in a notebook (the DB) and **only then** move the bookmark | Commit after the DB commit |
| The bookmark is in **another room** (Kafka); you walk there to move it | A commit is a network write that can fail |
| If you lose the room key while moving it, the notes are saved but the bookmark is not | Commit failure after a successful DB write: a replay |

## 3. What a commit is

(Details in Kafka note 2, sections 6 to 8; only what matters here.)

- A commit writes the **next offset to read** (last processed + 1) for `(group, topic, partition)` into the compacted `__consumer_offsets` topic, through the group coordinator.
- The consumer has two numbers: its **position** (in memory, advances with every fetch) and its **committed offset** (durable, advances only on commit). **The gap between them is the replay window after a crash or rebalance.**
- A commit is a **network request** with its own latency and its own failure modes (coordinator moved, group rebalancing, stale generation, broker down).
- Only the **current owner** of a partition can commit for it; a member that lost the partition in a rebalance has its commits **rejected** (stale generation).
- Commits cost: one write per commit. Committing often shrinks the replay window and adds load.

## 4. The order decides the guarantee

```
 A) WORK, THEN COMMIT                          B) COMMIT, THEN WORK
    ------------------                            -----------------
    fetch   ->  process  ->  commit               fetch  ->  commit  ->  process
                     ^                                              ^
         crash here: work done,                          crash here: offset moved,
         offset not moved                                work NOT done
         -> restart re-reads, REDOES it                  -> restart starts AFTER it: SKIPPED
         = duplicates (at-least-once)                    = loss (at-most-once)
```

| | Commit after (A) | Commit before (B) |
| --- | --- | --- |
| Crash between the two steps | **Work repeated** | **Work skipped** |
| Guarantee | **At-least-once** | **At-most-once** |
| Needs an idempotent sink? | **Yes** (or accept duplicates) | No duplicates to absorb, but data is lost |
| Acceptable for acknowledged events? | **Yes**, with `ON CONFLICT` | **No** |

Third possibility, **"exactly once"**, has two honest forms (section 12): store the offset **in the same database transaction** as the rows, or use Kafka transactions for Kafka-to-Kafka flows. For a Postgres sink fed by Kafka, the practical form is **at-least-once plus an idempotent write**, which gives an **exactly-once effect** on the table even though delivery is at-least-once.

**The unit that matters is "done".** For the sink, a record is **done** only when it is in one of two durable places: **stored in Postgres**, or **published to `events.dlq` and acknowledged**. The offset may move past it only after that.

## 5. Auto-commit

### 5.1 What it is

A background mechanism that commits offsets **periodically** (an interval; 5 s is the usual default **[reasoning]**) without your code calling commit. In this client it is **on by default** if you do not say otherwise: the client sets `enable.auto.commit` to `true` when `autoCommit` is not passed **[observed in the client source]**. That default is why the sink sets **`autoCommit: false` explicitly** **[observed in `sink-consumer.ts`]**.

### 5.2 Why it is convenient

- No commit code to write; progress survives restarts "automatically".
- Low commit overhead (one commit per interval, not per batch).
- Fine for consumers whose work is **idempotent and cheap to repeat**, or whose loss is harmless (metrics sampling).

### 5.3 Why it is dangerous

**Hazard 1: what gets committed is not "what you finished".** In the classic Java model, auto-commit commits the offsets of the records **returned by the last poll**, on a timer, regardless of whether your code has processed them. A crash after the timer fires but before the processing finishes **skips records**. That is commit-before-work with a delay.

**Hazard 2: you cannot tie it to your transaction.** The commit happens on the library's schedule. You cannot say "commit only after this DB transaction commits".

**Hazard 3: a replay window you did not choose.** Between two timer ticks, work is done but uncommitted; a crash repeats it. The window is the interval, not something designed around your chunk size.

**Hazard 4: it hides rebalance behavior.** Commits on a timer during or after a rebalance may be rejected or may commit positions for partitions you no longer own.

### 5.4 What is different in this client

**[observed in the client source]** Two facts change the picture:

1. **Offsets are stored only when resolved.** The client forces `enable.auto.offset.store` to `false` ("changing it is unsupported while using the promisified API"). The background auto-commit therefore commits **only offsets your code (or the library's auto-resolve) has resolved**, not "whatever poll returned".
2. **With `eachBatchAutoResolve: true` (the default), the library resolves the last offset of a batch after your `eachBatch` callback returns without throwing.**

So with auto-commit **and** auto-resolve, the committed offset follows "callback returned" rather than "poll returned". That makes it **closer to commit-after-work**, with a duplicate window equal to the commit interval. But the danger is not gone:

| Risk in this client | Explanation |
| --- | --- |
| **"Returned" is not "done"** | If your callback starts asynchronous work and returns without `await`ing it, the library resolves the offset while the work is still running. A crash then **loses** that work. This is easy to do by accident (a forgotten `await`, an un-awaited promise, a fire-and-forget queue). **[reasoning from the source: resolution happens after `await config.eachBatch(payload)` returns]** |
| **Interval-sized replays** | A crash repeats up to the commit interval's worth of resolved-but-uncommitted work |
| **No coupling to the DB** | Resolution is not tied to the transaction unless you make it so |
| **A commit that happens after a rebalance** | Possibly rejected; stored work is replayed |

**Verdict for EventPulse:** turn auto-commit **off** and resolve and commit **explicitly, once, after the DB commit** (section 8). The cost is a little code; the benefit is a commit rule you can state and test.

## 6. The client API

How the commit calls in this client behave **[observed in the installed client's source, and in `batch-handler.ts`]**:

| Call | Behavior |
| --- | --- |
| `resolveOffset(offset)` | Marks the message at `offset` as processed: **stores `offset + 1` locally** (so you pass the **last processed** offset, and the library adds the +1). If you resolve a lower offset after a higher one, it is **ignored** (only the highest counts). Resolving does **not** contact Kafka |
| `commitOffsetsIfNecessary()` | With **`autoCommit: false`**: calls `commitOffsets()` **immediately**, sending the stored offsets to Kafka. With **`autoCommit: true`**: does nothing (librdkafka commits in the background) |
| `eachBatchAutoResolve` | `true` (default): after your callback returns normally, the last offset of the batch is resolved. **`false`**: you resolve explicitly; the sink sets it to `false` |
| **A throw from `eachBatch`** | The client logs the error and **seeks back**: to the offset **after** the last resolved one, or to the batch's first message if nothing was resolved. The unresolved part is read again (this is how the sink retries a failed chunk) |
| **Leaving without resolving everything** | Same: if the last resolved offset is not the batch's last offset, the client seeks back to re-read the rest. (Records after the resolved one are **not skipped**; they are re-delivered.) |
| `seek()` | Marks any in-flight batch payload **stale** (`isStale()` becomes true) |
| `isStale()` | True once the partition was revoked or the poll time expired; the sink stops and does not commit |

Consequences you rely on:

- **"Resolved" means "I am done up to here", and the library never moves past what you did not resolve.** That is the safety net behind commit-after-work: not resolving a failed chunk makes the client re-deliver it.
- **Pass the last *processed* offset to `resolveOffset`.** Passing `last + 1` would skip a record. The sink passes `part[part.length - 1].offset` (the chunk's last offset) and the unit and e2e tests check the committed value (section 8).
- **A resolved-but-not-committed offset is only a local note.** If the process dies before `commitOffsetsIfNecessary()` completes, it is lost and the chunk is redone: a duplicate, not a loss.

## 7. Granularity

How often to commit trades **replay size** against **commit cost**:

| Commit | Max replay after a crash | Commit cost |
| --- | --- | --- |
| After every message | 1 record | Very high: a network write per record |
| After every **chunk** (`SINK_MAX_ROWS`, 1,000) | About **one chunk per partition** | Low: one write per DB transaction |
| After every fetched batch (up to 1,000, `CONSUMER_MAX_BATCH_SIZE`) | One batch | Lowest |
| On a timer (auto-commit) | The interval's worth | Lowest, but decoupled from the work |

The sink commits **per chunk**, which also matches the unit of work (one DB transaction), so "chunk committed" and "chunk stored" are the same event.

Latency of the commit is observable: `ep_consumer_commit_seconds` (Step 6). A rising commit latency means coordinator or broker trouble, and it adds to every chunk's time (and therefore to the time between polls, consumer note 2).

## 8. The sink protocol

**[observed in `batch-handler.ts`]** The comment at the top of the file states the protocol; the code implements it per **chunk** of up to `SINK_MAX_ROWS` messages:

```
 for each chunk of the batch:
   1. stop if the consumer is shutting down or the partition was revoked (isRunning / isStale)
   2. parse every record              (crash points: before_parse, after_parse)
        unparseable record -> dead letter (PERMANENT_PARSE), no retry
   3. write the good rows:  BEGIN; INSERT ... ON CONFLICT DO NOTHING; COMMIT
        DB unavailable -> backoff + retry inside a window, then pause the partition and throw
                          (nothing resolved: the chunk is re-read after the pause)
        row-level DB error -> isolate by bisection; good rows stored; each bad row retried N times, then a dead letter
                          (crash point: after_db_commit)
   4. publish dead letters to events.dlq and WAIT for the acknowledgement (failure -> throw, nothing resolved)
   5. stop if the partition was revoked meanwhile           <-- stale check #2
   6. resolveOffset(last offset of the chunk)               <-- the only resolve in the service
   7. commit to Kafka (retried up to 3 times; the rows are stored, so a retry is always safe)
   8. heartbeat
```

Reading it as rules:

1. **Nothing is resolved before the DB commit and the DLQ ack.** Steps 3 and 4 complete first.
2. **Two stale checks**: before starting the chunk (step 1) and **after the work, just before resolving** (step 5). If the partition was revoked while the rows were being written, the rows **stay stored** (they are committed in Postgres), but the **offset is not resolved or committed**: the new owner re-reads the chunk and `ON CONFLICT` absorbs it (a counted duplicate, `stoppedEarly`).
3. **A failed chunk is never resolved.** Throwing from `eachBatch` makes the client seek back to the first unresolved offset, so the chunk is retried.
4. **The commit itself is retried** (section 9), because by then the rows are safe.
5. **This is the ONLY place that resolves or commits offsets in the service** (stated in the file header). A single code path is what makes the rule auditable: every `resolveOffset` and every commit call in the service can be reviewed in one place.
6. **Commit value = last processed offset + 1**, because `resolveOffset(last)` stores `last + 1` (section 6). The e2e test "committed offset = last processed offset + 1 (the next offset to read), exactly at the log end" checks it against Kafka.

The tests that pin this protocol down **[observed in the test files; their pass status was not checked here]**:

| Unit test (`batch-handler.spec.ts`) | What it proves |
| --- | --- |
| per chunk: write, DB commit, `resolve(last offset)`, Kafka commit, heartbeat | The **call order** |
| writer rejects (DB down): that chunk is never resolved or committed | No commit without the DB commit |
| 3 chunks, writer fails on chunk 2: only chunk 1 is resolved and committed | Progress is exact |
| partition revoked after chunk 1: chunk 2 not written or committed | Stale check before work |
| partition revoked during the DB write: rows stored, offset **not** resolved or committed | Stale check before commit |
| shutdown after chunk 1: finishes chunk 1, then stops | Graceful stop |
| Kafka commit fails on every attempt: `OffsetCommitError` after 1 + 3 attempts, counted, rows stay stored | Commit failure is not loss |
| commit fails twice then succeeds: retried with backoff | Commit retry |
| commit retry stops at once if the partition was revoked meanwhile | No commits from a non-owner |
| DLQ publish rejects: offset not resolved, not committed | DLQ ack before commit |
| counts duplicates absorbed by `ON CONFLICT` | Duplicates are visible |

| End-to-end test (`commit-protocol.e2e-spec.ts`, real process) | What it proves |
| --- | --- |
| crash after the DB commit, before the offset commit: **no loss, duplicates bounded by one chunk** | The main at-least-once claim |
| committed offset = last processed offset + 1, exactly at the log end | Off-by-one |
| database unreachable: **no offset advances** while it is down; after it returns every row is stored | No commit without the DB |
| SIGTERM under load: the current chunk finishes and commits, nothing lost, **nothing replayed** | Clean shutdown |

## 9. Commit failures

**Causes [reasoning]:** the group is rebalancing, the member's generation is stale (it was removed), the coordinator broker moved or is down, a request timed out, or the member is being shut down.

**What a failed commit means for the data: nothing bad.** The rows are already in Postgres. A failed commit only means Kafka's record of progress is **behind** the truth, so a restart or the new owner re-reads and replays. **Duplicates, not loss.**

**What a failed commit does to the sink's health** (from the source comment): without a retry, a commit that fails on a partition's **last** chunk leaves the offset **stored locally but uncommitted** until another chunk of that partition commits; **if none arrives, lag never reaches 0** and a restart reprocesses the chunk. That is why `commitWithRetry` exists.

`commitWithRetry` **[observed]**:

```ts
for (let attempt = 0; ; attempt++) {
  try { await ctx.commitOffsetsIfNecessary(); return; }
  catch (e) {
    deps.stats.countCommitError();
    if (attempt >= COMMIT_RETRIES || !ctx.isRunning() || ctx.isStale()) throw new OffsetCommitError(e);
    await sleep(backoffMs(attempt + 1, deps.retry.baseMs, deps.retry.maxMs, deps.rand));
  }
}
```

- `COMMIT_RETRIES = 3`: **1 + 3 attempts** with backoff (100 ms growing, up to 5 s by default).
- It **stops immediately** if the partition was revoked or the consumer is shutting down: committing then is pointless or forbidden.
- On final failure it throws `OffsetCommitError` ("offset commit failed after the DB commit (rows are stored; they may be reprocessed)"). The thrown error makes the client seek back, so the chunk is re-read; `ON CONFLICT` absorbs it.
- Every failure is **counted** (`ep_consumer_commit_errors_total`); a rising count is a signal to look at the coordinator and the rebalances.

## 10. Crash points and outcomes

The sink has debug-only **crash points** that SIGKILL the process at a chosen moment on the Nth batch **[observed in `fault-injector.ts`]**: `CRASH_AT=before_parse|after_parse|after_db_commit`, `CRASH_AFTER_BATCHES=N`, and the guard **`DEBUG_FAULTS=true`** (it refuses to start otherwise). The crash is a real SIGKILL: no cleanup, no commit. They are how Step 3 proves the guarantee and how **K5** is run.

Expected outcome per crash point (the plan's table, which the e2e test checks for the third row):

| Crash point | Rows in DB | Offset committed | After restart |
| --- | --- | --- | --- |
| **before parse** | no | no | The chunk is reprocessed: **no loss, no duplicate rows** |
| **after parse** | no | no | Same |
| **after DB commit, before the offset commit** | **yes** | no | The chunk is reprocessed; `ON CONFLICT` absorbs it; **duplicates counted** (at most one chunk, up to 1,000 per partition) |
| **after the offset commit** | yes | yes | Nothing reprocessed |

The pattern: **only the window between "DB committed" and "offset committed" produces duplicates**, and that window is exactly where commit-after-work puts them. **There is no window that produces loss**, because the offset never moves before the DB commit.

`SINK_DEDUP=false` (debug-only, needs `DEBUG_FAULTS=true`) writes to a copy of the table **without** `ON CONFLICT`, so K5 can show what the replay would have done without the idempotent write: duplicated rows **[observed in `config.ts`]**.

## 11. DLQ and the commit

Step 4 adds a second durable outcome. A record can be **stored** or **dead-lettered**, and the offset may pass it only when its fate is durable:

- **Parse failures and persistent row errors** become **dead letters**; the sink publishes them to `events.dlq` with `acks=all` and **waits for the acknowledgement** before resolving the offset (step 4 of the protocol).
- **If the DLQ publish fails, nothing is resolved**: the chunk is retried, possibly producing a duplicate DLQ record (accepted, noted for Stage 3). The test "DLQ publish rejects: offset not resolved, not committed; the rows were written but the chunk is not complete" pins it.
- **A database outage is not a poison message**: transient DB errors are retried and never dead-lettered; the partition is **paused** and the chunk is re-read after the pause.
- The invariant maintained by the stats: **`consumed = inserted + duplicates + dlq`** per completed chunk (`consumed: part.length, attempted, inserted, dlq`), which Step 6 asserts and Step 7 reconciles.

## 12. Beyond at-least-once

| Approach | How | Fit |
| --- | --- | --- |
| **At-least-once plus idempotent write** (EventPulse) | Commit after work; unique key (`event_id`) | Simple, robust; duplicates absorbed and counted |
| **Offset stored in the database transaction** | A table `consumer_offsets(group, topic, partition, next_offset)` updated **in the same transaction** as the rows; on start (and on each assignment) read it and `seek`; do not rely on Kafka commits (or commit only for monitoring) | No replay window; the commit and the data are atomic. Costs: you manage assignment and rebalance hooks yourself (seek on assign), one more table and write per transaction. Not in Stage 2 |
| **Kafka transactions** (exactly-once for Kafka-to-Kafka) | Produce results and commit offsets in one Kafka transaction | Not applicable to a Postgres sink |

A useful way to think about "exactly once": **delivery** is at-least-once; the **effect on the table** is exactly once because the write is idempotent. Say it that way in the Stage 2 report.

## 14. EventPulse decisions

| Decision | Value | Reason |
| --- | --- | --- |
| Auto-commit | **Off** (`autoCommit: false`) | The commit must follow the DB commit |
| Auto-resolve | **Off** (`eachBatchAutoResolve: false`) | No offset resolved without our say |
| Commit rule | After the DB commit **and** DLQ ack, per chunk | At-least-once with bounded replays |
| One code path | `handleBatch` only | Auditable |
| Offset value | `resolveOffset(last processed)`; the client stores `+1` | Matches Kafka semantics |
| Commit failure | Retry 3 times with backoff; then throw (replay) | Rows are stored; never loss |
| Stale partition | Do not resolve, do not commit | Not the owner any more |
| Idempotent write | `ON CONFLICT (event_id) DO NOTHING`, duplicates counted | Absorbs replays |
| Crash testing | `CRASH_AT` points guarded by `DEBUG_FAULTS` | K5 and the Step 3 proof |
| Offset in the DB | Not in Stage 2 | A later improvement |

## 17. Edge cases

| Case | What happens |
| --- | --- |
| Crash between DB commit and Kafka commit | Chunk replayed; duplicates absorbed |
| Commit rejected after a rebalance | Rows stored; the new owner replays; counted |
| Commit fails on a partition's last chunk | Retried; otherwise lag would never reach 0 |
| A callback returns before its work finishes (un-awaited promise) with auto-resolve | The offset is resolved early: **loss risk**; the sink avoids it with explicit resolution |
| `resolveOffset` called with `last + 1` | Skips a record: **loss**. Pass the last processed offset |
| Resolve a lower offset after a higher | Ignored |
| An empty batch | No-op; nothing to resolve |
| Multiple chunks in one batch, the second fails | Only the first is resolved and committed; the client seeks back to the second |
| DLQ publish fails | Not committed; retried; a duplicate DLQ record is possible |
| Process receives SIGTERM mid-chunk | The chunk finishes, commits, then the member leaves |
| Offset commit from a revoked partition | Rejected; the sink stops retrying immediately |
| Reset policy after an out-of-range commit | Kafka note 2, section 9 |

## 19. Common confusions

1. **"Committing means the message was processed."** Only if **you** commit after processing.
2. **"Auto-commit is at-least-once."** Depends on what the library commits. In the Java model it can skip records; in this client it follows resolved offsets, with an interval-sized replay window and the un-awaited-work hazard.
3. **"`resolveOffset` commits."** It stores locally (offset + 1). The commit is the next call.
4. **"I pass the next offset to `resolveOffset`."** Pass the last processed offset.
5. **"A failed commit loses data."** It causes a replay.
6. **"If eachBatch throws, the batch is skipped."** The client seeks back and re-delivers the unresolved part.
7. **"I need transactions for exactly-once."** For Kafka to Postgres, an idempotent write gives the exactly-once effect.
8. **"Committing more often is always better."** It reduces replays and adds load; per chunk is the balance.
9. **"A stale member can still commit."** Its commits are rejected.
10. **"Duplicates mean the commit logic is broken."** Duplicates after crashes and rebalances are expected and counted.
11. **"Commit after the DB commit is guaranteed by the library."** It is guaranteed by **your code** and its tests.
12. **"`enable.auto.offset.store` can be changed."** The promise API forces it off.

<details>
<summary>Short answers</summary>

1. After-work: at-least-once; a crash between work and commit repeats work. Before-work: at-most-once; a crash between commit and work skips work.
2. Stored in Postgres, or published to `events.dlq` and acknowledged.
3. It commits what was handed out by the last poll on a timer, regardless of completion, so a crash can skip records. In this client offsets are stored only when resolved, so it commits resolved offsets (closer to commit-after-work), with an interval-sized replay window.
4. If the callback returns before its asynchronous work finishes (a forgotten `await`), the library auto-resolves the offset early and a crash loses that work.
5. `resolveOffset(n)` stores `n + 1` locally (no network). `commitOffsetsIfNecessary()` commits the stored offsets immediately.
6. It logs the error and seeks back to the first unresolved offset so the unresolved part is re-delivered. If the callback returns without resolving everything, the client also seeks back to re-read the rest.
7. Check stale or shutdown; parse; write rows (DB commit); dead-letter and wait for the DLQ ack; check stale again; `resolveOffset(last)`; commit with retry; heartbeat.
8. The first avoids wasted work for a revoked partition; the second prevents committing for a partition that was revoked while the rows were being written (the new owner replays).
9. Because the rows are already stored, and an uncommitted last chunk would leave lag stuck above 0 and be reprocessed on restart. One attempt plus three retries with backoff.
10. Before parse and after parse: no rows, no commit, replay with no duplicates. After the DB commit and before the offset commit: rows stored, no commit, replay absorbed (duplicates up to one chunk). After the offset commit: nothing reprocessed.
11. The offset is committed after every chunk of at most `SINK_MAX_ROWS` rows, so only the chunk in flight can be uncommitted.
12. Delivery can repeat records; the idempotent write (`ON CONFLICT`) makes repeats have no effect on the table.
13. The offset moves atomically with the rows (no replay window). You must read the stored offset and seek on every assignment, handle rebalances yourself, and write one more row per transaction.
14. That every consumed message was accounted for as inserted, absorbed as a duplicate, or dead-lettered.

## 21. Cheat sheet

### Glossary

| Term | Meaning |
| --- | --- |
| Commit | Telling Kafka the next offset to read for a group and partition |
| Resolve | Marking an offset processed locally (`offset + 1` stored) |
| Auto-commit | Periodic background commit of stored offsets |
| Auto-resolve | The library resolves the batch's last offset after the callback returns |
| At-least-once | Process, then commit: duplicates possible, no loss |
| At-most-once | Commit, then process: loss possible, no duplicates |
| Stale | The partition was revoked (or the poll time expired) |
| Chunk | The unit of one DB transaction and one commit (`SINK_MAX_ROWS`) |
| Replay window | Work done but not yet committed |

### The sink's rule

```
parse -> DB COMMIT -> DLQ ack -> (stale?) -> resolveOffset(last processed) -> commit (retry 3x) -> heartbeat
committed value = last processed + 1        only place that resolves or commits        never before the DB commit
```

### Crash outcomes

| Crash point | Duplicates | Loss |
| --- | --- | --- |
| before parse | none | none |
| after parse | none | none |
| after DB commit, before offset commit | up to one chunk | none |
| after offset commit | none | none |

### Settings (observed defaults)

| Setting | Default |
| --- | --- |
| `autoCommit` / `eachBatchAutoResolve` | false / false |
| `SINK_MAX_ROWS` | 1,000 |
| `COMMIT_RETRIES` | 3 |
| `SINK_RETRY_BASE_MS` / `SINK_RETRY_MAX_MS` | 100 / 5,000 |

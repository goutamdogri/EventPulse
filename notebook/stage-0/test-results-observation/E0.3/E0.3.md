# E0.3 Event-loop blocking

## Hypothesis

While `/cpu?n=38` runs, `/health` latency spikes to roughly the duration of
one `/cpu` call, because one JS thread serves both.
Prediction: stall ≈ 355 ms, blocked fraction ≈ 35.5% at 1 rps, so p50 ≈ baseline,
p90 ≈ 255 ms, p99 ≈ 345 ms, max ≈ 355 ms.

## Setup

Date: 28/10/2026
commit:

Server on port 8000.
Prometheus scrape interval for the app: 1s. k6 pushes to Prometheus every 1s.

## Method

1. Calibration (idle server, 5 runs):
   `curl -w '%{time_total}\n' 'localhost:8000/cpu?n=38'`
   0.342s, 0.350s, 0.360s, 0.362s, 0.363s -> 0.3554s on average.
   At 1 rps: 0.355 s of each second blocked = 35.5%.
2. k6, two scenarios, constant-arrival-rate (open model):
   - `/health`: 200 rps, 0s–120s
   - `/cpu?n=38`: 1 rps and 2 rps, 30s–90s
     Phases: 0–30s baseline, 30–90s with /cpu, 90–120s recovery.
3. Command: `SCRIPT=E0.3.js ./runner.sh`
4. Validity: dropped_iterations = 0, generator CPU << 70%.

## Explanation

- /cpu latency ≈ its own run time because requests never overlap at 1 rps.
- Event-loop lag max matches because the loop is literally blocked for that long.
- Three independent views agree, which confirms the cause.

## Cost

One 355 ms synchronous call at 1 rps raised /health p99 from 0.352ms to 345ms
(a 980× increase) while average CPU stayed low. A single-threaded server's
latency depends on the longest synchronous task, not only on average load.

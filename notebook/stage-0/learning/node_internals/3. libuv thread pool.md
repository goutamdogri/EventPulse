# libuv thread pool

The libuv thread pool is a pool of background threads used by Node.js to perform certain operations without blocking the main JavaScript event-loop thread.

The key distinction is that it can offload specific supported operations, but it does not automatically execute your JavaScript code on background threads.

## 1. How Node.js uses the thread pool

Node.js runs JavaScript on its main thread. Some operations can be delegated to libuv's worker pool.

```txt
                  Node.js process
                         |
            +------------+------------+
            |                         |
      Main JS thread             libuv thread pool
            |                         |
       Event loop              +-------+-------+
            |                  |       |       |
       JS callbacks           Thread  Thread  Thread ...
            |                  |       |       |
       HTTP requests        fs / crypto / DNS lookup
```

For example, when an asynchronous filesystem operation is submitted, Node.js can delegate the work to a pool thread. The main thread remains available to execute other callbacks.

When the operation finishes, its completion is reported back to the event loop.

## 2. Which operations use the pool?

| Operation                                      | Uses libuv thread pool?                             |
| ---------------------------------------------- | --------------------------------------------------- |
| Many asynchronous filesystem operations (`fs`) | Yes                                                 |
| `dns.lookup()`                                 | Yes                                                 |
| `crypto.pbkdf2()`                              | Yes                                                 |
| `crypto.scrypt()`                              | Yes                                                 |
| Ordinary HTTP socket I/O                       | Generally no; handled through OS event notification |
| Your own synchronous JavaScript loop           | No                                                  |
| A CPU-heavy JavaScript function                | No, unless you explicitly offload it                |

A subtle distinction: Node.js DNS APIs don't all behave the same way. `dns.lookup()` uses the operating system's name-resolution facilities through the thread pool, while APIs such as `dns.resolve()` generally use asynchronous network queries instead.

## 3. Why is the default size 4?

By default, libuv creates a worker pool with 4 threads. You can configure its size with the `UV_THREADPOOL_SIZE` environment variable.

Suppose four requests each trigger an expensive password-hashing operation:

```js
const { pbkdf2 } = require('node:crypto');
const { promisify } = require('node:util');

const hashPassword = promisify(pbkdf2);

app.post('/hash', async (req, res) => {
  const hash = await hashPassword(
    req.body.password,
    'some-salt',
    200000,
    64,
    'sha512'
  );

  res.json({ hash: hash.toString('hex') });
});
```

If all four pool threads are occupied by these operations, another filesystem or pool-backed operation may need to wait for an available thread.

This can cause latency even when the main event loop is not blocked.

The example is for illustration; production password hashing needs proper salt generation, secure parameters, and careful handling of credentials.

## 4. Why it is not a general JavaScript CPU pool

Consider this code:

```js
app.get('/calculate', (req, res) => {
  let result = 0;

  for (let i = 0; i < 1_000_000_000; i++) {
    result += i;
  }

  res.json({ result });
});
```

The loop runs on the main JavaScript thread. It does not automatically use one of libuv's four worker threads.

Even if you set:

```bash
UV_THREADPOOL_SIZE=16 node app.js
```

the loop still blocks the event loop.

To execute CPU-heavy JavaScript on another thread, use Node.js Worker Threads or move the work to a separate worker process/service.

## 5. When should you change `UV_THREADPOOL_SIZE`?

You might increase it when profiling shows that supported thread-pool operations are queued behind other pool work.

For example:

```bash
UV_THREADPOOL_SIZE=8 node app.js
```

Set the variable before Node.js starts. Increasing it is not automatically beneficial: additional threads consume resources and can increase CPU contention. The right size depends on the workload, CPU capacity, and the types of operations sharing the pool.

For EventPulse, this matters if ingestion triggers filesystem work, cryptographic operations, or `dns.lookup()` calls. However, if analytics calculations are blocking the JavaScript event loop, changing this variable will not fix the underlying problem.

Remember the three separate execution paths:

- Event loop: JavaScript callbacks and asynchronous socket readiness.
- libuv thread pool: specific supported background operations.
- Worker Threads: JavaScript computation you explicitly offload to other threads.

# The Node.js event loop: every phase and every case

Part 1 explains, in detail, what the event loop does in each phase and in what order. Part 2 walks through the situations you will meet in practice: a request that suddenly takes much longer than normal, a burst of requests, a timer that fires late, a handler that crashes, a client that disconnects, and many more. For each case it shows what the loop does, what you see in metrics, and what to do.

Most claims were checked with small experiments on a real Node process. They are marked **Observed** and the scripts are in the appendix. The sandbox had Node v22 on **one CPU core**, so absolute times are not representative of your machine. The behaviours and the orderings are.

# Part 1: How the loop works

## 1. The big picture

Node runs all your JavaScript on **one thread**. The event loop is the code on that thread that decides what to run next. Three ideas explain everything:

1. **A callback runs to completion.** Nothing interrupts a running callback. Everything else waits.
2. **Waiting is done by the operating system, not by your thread.** While a request waits on a database, a timer or a socket, no JavaScript is running. The kernel watches (through `epoll`) and tells libuv when something is ready.
3. **The loop repeats the same fixed sequence of phases**, running the callbacks that are ready in each phase.

### One iteration (this is libuv's loop, which Node uses)

```txt
        update the loop's cached "now"
                    |
                    v
   +----------------------------------+
   | 1. TIMERS            due setTimeout / setInterval callbacks
   | 2. PENDING CALLBACKS callbacks libuv deferred from the last iteration
   | 3. IDLE, PREPARE     internal housekeeping
   | 4. POLL              ask the kernel which fds are ready; run their callbacks
   | 5. CHECK             setImmediate callbacks
   | 6. CLOSE CALLBACKS   callbacks for handles that were closed
   +----------------------------------+
                    |
        anything still alive?  yes -> next iteration
                               no  -> the process exits
```

After **every single callback** in any phase, Node runs the `process.nextTick` queue and then the microtask queue (promise continuations) until both are empty (section 3).

## 2. The phases, one by one

### 2.0 Start of an iteration: the cached clock

libuv reads the clock once at the start of the iteration and **caches it** as the loop's "now". Timers compare against this cached time. If a callback blocks for 200 ms, the cached time is old until the next iteration starts. This is one reason timers fire late after a long block.

### 2.1 Timers phase

| | |
| --- | --- |
| What feeds it | `setTimeout`, `setInterval` |
| What runs | Every timer whose scheduled time has arrived, in order of expiry |
| Guarantee | "**At least** this many ms", never "exactly" |

How it works:

- Node keeps timers in lists grouped by duration and uses **one underlying libuv timer** set to the earliest expiry.
- A timer fires when the loop's "now" is at or past `start + delay`. If the loop is busy, the timer simply waits. **Observed:** a `setTimeout(…, 10)` fired after **125 ms** when a 120 ms synchronous task ran first (experiment E4).
- Minimum delay is 1 ms (`setTimeout(fn, 0)` becomes 1 ms). Delays above about 24.8 days (2³¹−1 ms) are reduced to 1 ms with a warning.
- A timer scheduled **during** the timers phase runs in a later iteration, not in the same pass.
- Since Node 11, the microtask and nextTick queues are drained **between** timer callbacks. **Observed:** two timers that each queue a promise ran as `t1, p1, t2, p2`, not `t1, t2, p1, p2` (E2).

### 2.2 Pending callbacks phase

| | |
| --- | --- |
| What feeds it | Callbacks libuv chose to defer to the next iteration |
| Typical examples | Some completion and error callbacks from system operations (for example certain TCP errors, and some write-completion callbacks) |
| Your code | You rarely target this phase directly |

It exists so libuv can avoid calling a callback from inside the very function that started the operation.

### 2.3 Idle and prepare

Internal handles that libuv runs just before polling. Node uses an idle handle, for example, to stop the loop from sleeping when `setImmediate` callbacks are pending. You cannot attach your own code here from JavaScript.

### 2.4 Poll phase (where your network I/O happens)

This is the most important phase for a server. It has two jobs:

1. **Decide how long to block**, then ask the kernel (`epoll_wait`) which file descriptors are ready.
2. **Run the callbacks** for the ready descriptors.

**How long does it block?** (libuv's rule)

| Situation | Timeout |
| --- | --- |
| `setImmediate` callbacks are waiting, or pending/closing callbacks exist | 0 (do not wait) |
| Timers exist and nothing is waiting | Until the **nearest timer** is due |
| No timers, nothing waiting | **Forever** (until the kernel reports something) |

**What runs for a ready descriptor?**

| Descriptor | Callback |
| --- | --- |
| The listening socket (a connection is waiting in the accept queue) | `accept4()`, then the `'connection'` event |
| A connection socket (request bytes arrived) | `read()` from the kernel buffer, HTTP parser, your handler |
| A connection socket that became writable | Continue writing queued response data |
| Thread pool completion signal | Run the callback for the finished fs, crypto, zlib or DNS job |
| Signals, child process events | Their callbacks |

**Limits and fairness.** libuv takes a batch of ready events at a time (up to about 1024 per `epoll_wait`) and processes them one after another, repeating a bounded number of times, and reads each ready socket a bounded number of times per wake-up. These are libuv implementation details and may vary by version. The point: one busy socket cannot hog the loop forever, but a **batch** of ready sockets is handled in sequence, so the last one in the batch waits for all the earlier ones.

**Level-triggered readiness.** libuv uses level-triggered epoll. A socket with unread bytes keeps being reported on later iterations until it is read.

### 2.5 Check phase

| | |
| --- | --- |
| What feeds it | `setImmediate` |
| What runs | All immediates queued before the phase started |

- An immediate queued **from inside** a check callback runs in the **next** iteration. So a recursive `setImmediate` cannot starve I/O. **Observed:** with a 10 ms timer waiting and a recursive `setImmediate` chain running, the timer fired after **11 ms**, after only 1,734 recursive calls (E3).
- Right after the poll phase, so inside an I/O callback `setImmediate` is **always** before `setTimeout(…, 0)`. **Observed:** inside an `fs.readFile` callback the order was `immediate (in I/O cb)`, then `timeout (in I/O cb)` (E1).

### 2.6 Close callbacks phase

Callbacks for handles that were closed, for example when a socket is destroyed. This is where the cleanup side of `'close'` events is processed.

## 3. What runs between callbacks: nextTick and microtasks

After each callback (from any phase) returns, and before the loop continues, Node drains:

1. the **`process.nextTick` queue**, completely,
2. then the **microtask queue** (promise `then` callbacks, `await` continuations, `queueMicrotask`), completely,
3. and repeats until both are empty.

| Property | `process.nextTick` | Promise / `await` / `queueMicrotask` |
| --- | --- | --- |
| Runs | Before microtasks | After the nextTick queue |
| Can be queued from inside itself | Yes, and it keeps running | Yes, and it keeps running |
| Can starve I/O | **Yes** | **Yes** |

**Observed order (E1, E2b):**

- In a CommonJS main module: `nextTick`, `promise`, `queueMicrotask`, then `timeout`, `immediate`.
- In an **ES module** top level the first two swap: `promise` came before `nextTick`. (Module evaluation already runs inside promise machinery, so the microtask queue drains first.)
- `setTimeout(0)` versus `setImmediate` from the **main module**: officially unpredictable. I saw `timeout` first six times out of six on this machine, but do not depend on it.

## 4. Work that happens outside the loop thread

Your JavaScript is single-threaded, but Node uses other threads and the kernel for slow things.

| Mechanism | Used for | Where the result comes back |
| --- | --- | --- |
| **Kernel async I/O (epoll)** | Network sockets (all of HTTP/TCP) | Poll phase |
| **libuv thread pool** (4 threads by default, `UV_THREADPOOL_SIZE`, up to 1024) | `fs` calls, `dns.lookup`, `crypto` (pbkdf2, scrypt, randomBytes), `zlib` | A thread finishes, signals the loop, the callback runs in the poll phase |
| **Worker threads** | CPU-heavy JavaScript you move off the main thread | Message from the worker, delivered as an event on the main loop |
| **V8 helper threads** | Part of garbage collection, JIT compilation | Invisible, but a stop-the-world GC pause still blocks the main thread |

Network I/O does **not** use the thread pool. That is why 10,000 open sockets cost nothing in threads.

## 5. When the loop sleeps and when it exits

- **Sleeping.** When nothing is ready, the main thread blocks inside `epoll_wait`, using no CPU, until a timer is due or the kernel reports an event. (I confirmed an idle Node main thread sits in the kernel's `ep_poll`.)
- **Staying alive.** The loop keeps running while there is at least one **active, referenced** handle or request: a listening server, an open socket, a pending timer, a running thread pool job.
- **Exiting.** When nothing is left, Node exits by itself. `timer.unref()` marks a timer as not worth staying alive for.
- A server that is listening keeps the process alive indefinitely.

## 6. Which API runs in which phase (cheat sheet)

| You write | It runs | Notes |
| --- | --- | --- |
| `setTimeout`, `setInterval` | Timers phase | At least the delay, often later |
| Socket read/accept callbacks, `'request'` handler | Poll phase | Called directly by the parser |
| `fs.readFile` callback, `crypto.pbkdf2` callback | Poll phase | After a thread pool job finished |
| `setImmediate` | Check phase | Always after the current poll phase |
| `process.nextTick` | After the current callback, before microtasks | Can starve everything |
| Promise `.then`, `await` continuation | After nextTick, still between callbacks | Can starve everything |
| `socket.destroy()` cleanup, `'close'` | Close callbacks phase (and shortly after) | |
| Synchronous code (`JSON.parse`, loops, `readFileSync`) | Inside whatever callback calls it | Blocks the loop |

# Part 2: Cases

Each case has the same shape: **scenario**, **what the loop does**, **what you observe**, **what to do**.

## 7. Case 1: one request suddenly takes much longer (CPU-bound)

This is your example. A single request, for some reason, needs far more CPU time than usual: a huge JSON body, a slow regular expression, a big loop, a synchronous file read, or a data set larger than normal.

### What the loop does

A handler is just a callback. While it runs, **nothing else can run**: no other request is read, no timer fires, no connection is accepted.

```txt
time ----------------------------------------------------------------------------------->
loop:   [req A handler: 300 ms of CPU ..............................][req B][req C][req D]
kernel:        B arrives (t = 50 ms) -> waits in B's receive buffer  ^picked up at t = 300 ms
               C arrives (t = 150 ms) -> waits                        ^
               a new client connects -> waits in the accept queue     ^
```

### Observed (E5)

A server with a `/slow-sync` route that spends 300 ms of CPU. A second request to a fast route, sent while the slow one runs:

| Request | Normal time | Time while the slow request ran |
| --- | --- | --- |
| The slow request itself | 300 ms | 303 ms |
| `/fast` sent at t = 50 ms | about 2 ms | **254 ms** (waited for the remaining 250 ms) |
| `/fast` sent at t = 150 ms | about 2 ms | **156 ms** (waited for the remaining 150 ms) |

The fast requests did nothing wrong, and their handlers took microseconds. They finished at almost the same moment the slow one did, because that is when the loop became free.

### What every other request experiences

- A request that arrives during the block waits **the remaining block time**: between 0 and the full block duration, 150 ms on average for a 300 ms block.
- The request bytes wait **in the kernel's receive buffer** of their connection (Recv-Q), not in Node.
- **New connections** wait in the **accept queue**, not accepted until the block ends (see case 15).
- **Timers** fire late (case 7).
- **Health checks** fail if they time out, and a load balancer may remove the instance, shifting traffic to the others.

### The aftershock: a backlog (illustrative arithmetic)

While the loop is blocked, new requests keep arriving. Suppose the server handles 20,000 requests per second normally, and the maximum it could handle is about 27,700 per second (1 ÷ 36 µs, the estimate from your tests). A 300 ms block then builds a backlog:

```txt
backlog        = arrival rate x block time          = 20,000 x 0.3 s  = 6,000 requests
drain speed    = capacity - arrival rate            = 27,700 - 20,000 = 7,700 requests/s
time to drain  = backlog / drain speed              = 6,000 / 7,700   = about 0.8 s
```

So a 0.3 s freeze keeps latency elevated for about **1.1 s** in total. The closer your arrival rate is to capacity, the longer recovery takes (at 27,000 rps the drain speed is 700 per second, so the same backlog takes about 8.6 seconds). Near capacity, a single block can effectively **tip the server into overload** (this is the "metastable" behaviour from your Stage 1 notes). These numbers are arithmetic from assumed rates, not measurements.

### Client-side effects

- Clients with timeouts shorter than the block give up and **retry**, adding more load right when the server is behind.
- In k6's open model, VUs pile up (VUs needed = rate × latency). A 300 ms stall at 20,000 rps needs about 6,000 VUs, which is why you saw "Insufficient VUs".
- Dropped iterations appear, and p99 and p99.9 jump while p50 may barely move if the blocks are rare.

### What you see in metrics

| Panel | Signal |
| --- | --- |
| Event loop lag (max and p99) | Spike of about the block duration |
| Client p99 vs server p99 | Client rises, **server handler time is flat**. (Only the slow request's own handler time is long.) |
| Process CPU | A burst at about one full core |
| Latency percentiles | p99 and p99.9 jump, often p50 does not |
| Dropped iterations / VUs | Rise during and after the block |

### What to do

- Find the slow request: log handler duration and the request id, and sample CPU profiles (`clinic flame`, `0x`, `--cpu-prof`).
- Remove or bound the heavy work: limit body sizes, paginate, cap loop sizes, replace synchronous APIs.
- If the work is legitimate: slice it (case 3), move it to a worker (case 4), or move it to another service.
- Set request body limits and timeouts so one input cannot cost unbounded CPU.

## 8. Case 2: a request is slow because it waits (database, network)

### Scenario

A handler does `await db.query(...)` and the database is slow. The CPU is idle, and the request just takes a long time.

### What the loop does

At the `await`, the handler returns to the loop and its continuation is parked. The loop goes on with other requests. When the database answers, the socket becomes readable in a later poll phase, and the continuation runs as a microtask.

### Observed (E5)

A `/slow-async` route that awaits a 300 ms timer:

| Request | Time |
| --- | --- |
| The slow request | 304 ms |
| `/fast` sent at 50 ms | **2.2 ms** (unaffected) |
| `/fast` sent at 150 ms | **2.3 ms** (unaffected) |

### Second-order effects (these are real even though the loop is free)

- **More requests in flight.** In-flight requests = rate × latency (Little's Law). If latency goes from 5 ms to 500 ms at 2,000 rps, in-flight requests go from 10 to 1,000. Each holds memory, a socket, and possibly a database connection.
- **Resource exhaustion downstream.** A connection pool of 10 saturates, and new requests queue in the pool (not in the event loop), adding the wait.
- **Memory growth** from many pending requests and their closures.
- **Cascading slowness.** If clients retry on timeout, load on the slow dependency grows.

### What you see

Active handles and requests rise, CPU stays low, event loop lag is flat, and **server p99 rises along with client p99** (the handler really is taking longer, because it spans the wait).

### What to do

Timeouts on every external call, bounded pools and queues, load shedding (return 503 when too many requests are in flight), circuit breakers, and cancellation when the client gives up (case 10).

## 9. Case 3: splitting CPU work into slices

### Idea

If you cannot avoid CPU work, break it into small pieces and **yield to the loop between pieces** (`setImmediate`), so the loop can service I/O in between.

```js
let left = 300;                                    // 300 ms of work in total
const step = () => { doWork(3); left -= 3; left > 0 ? setImmediate(step) : res.end('ok'); };
step();
```

### Observed (E5)

Same 300 ms of CPU, in 3 ms slices:

| Request | Time |
| --- | --- |
| The slow request | 305 ms (barely slower) |
| `/fast` sent at 50 ms | **7.4 ms** |
| `/fast` sent at 150 ms | **6.6 ms** |

Other requests now wait at most about one slice, not the whole job.

### Trade-offs

- Every yield costs a loop iteration, so the total job is slightly slower.
- Slice size: smaller means more responsive but more overhead; 1-10 ms is a common starting point.
- Use `setImmediate` for yielding, **not** `process.nextTick` or a promise (those do not let I/O in, case 6).
- It still uses the same CPU thread, so under heavy load the throughput for everyone drops.

## 10. Case 4: moving CPU work to a worker thread

### Idea

A worker thread has its own event loop and runs on another CPU core. The main loop stays free.

### Observed (E5)

| Request | Time |
| --- | --- |
| The slow request (300 ms of work in a worker) | 345 ms (extra cost: starting the worker) |
| `/fast` sent at 50 ms | **2.2 ms** |
| `/fast` sent at 150 ms | **3.3 ms** |

### Trade-offs

- Starting a worker per request is expensive. Use a **pool** of long-lived workers.
- Data is **copied** between threads (structured clone), unless you transfer an ArrayBuffer or use a SharedArrayBuffer. Large payloads make that copy a cost.
- Number of workers should not exceed the CPU cores available.
- An **unbounded worker queue** can grow without limit (this is the "worker threads" experiment from Stage 0).

## 11. Case 5: the thread pool is saturated

### Scenario

Many requests call something that uses the libuv thread pool (`crypto.pbkdf2`, `crypto.scrypt`, `zlib`, `fs.*`, `dns.lookup`). There are only **4 pool threads** by default.

### What happens

Jobs beyond the first 4 wait in a queue. **All** pool users share that queue, including small, unrelated tasks such as a 1 KB file read.

### Observed (E7)

Six `pbkdf2` jobs plus a tiny `fs.readFile` started at 20 ms (the sandbox has one CPU, so read the order and not the absolute times):

| Pool size | Order of completion |
| --- | --- |
| 4 (default) | Jobs 1-4 finish together (~370 ms); the tiny read finishes with them at 374 ms, as soon as a thread frees up; **jobs 5 and 6 finish last** (546 ms) |
| 1 | Jobs finish strictly one after another (96, 184, 281, 387, 506, 639 ms); **the tiny file read waited for all six** (639 ms) |

### What you see

- The event loop itself is **free** (event loop lag is flat), but requests that need the pool are slow.
- CPU may be high on several cores, because pool threads run in parallel.
- A cheap `fs.readFile` can become slow just because someone else is running expensive crypto.

### What to do

Raise `UV_THREADPOOL_SIZE` (up to 1024, and ideally not above the CPU cores for CPU-bound jobs), avoid synchronous-style bursts of crypto, use async-friendly algorithms, and move heavy work to dedicated workers so it cannot starve unrelated file and DNS operations.

## 12. Case 6: nextTick and microtask starvation

### Scenario

Code that keeps queueing `process.nextTick` callbacks or promise continuations, so the loop never leaves the "between callbacks" drain step and never reaches the poll phase.

### Observed (E3, E6)

A 10 ms timer waiting, with 1,500,000 recursive calls:

| Recursion method | When the 10 ms timer fired |
| --- | --- |
| `process.nextTick` | after **191 ms**, after all 1,500,000 calls finished |
| `setImmediate` | after **11 ms**, after only 1,734 calls |

A loop of 3,000,000 `await Promise.resolve()` also finished first, and the 10 ms timer fired after **234 ms**. An `await` on an **already resolved** promise does not let I/O in: it is only a microtask.

### Why it matters on a server

While the loop is stuck in microtasks, **no socket is read and no connection accepted**. It looks exactly like case 1 (a blocked loop) but the CPU profile shows promise or nextTick machinery.

### What to do

For long iterative work, yield with `setImmediate` (or `await` something that really waits, like a timer), and put a bound on recursion depth.

## 13. Case 7: timers (late, ordered, repeating)

| Situation | What happens | Observed / note |
| --- | --- | --- |
| Loop busy when a timer is due | The timer fires **late**, after the busy callback ends | A 10 ms timer fired at **125 ms** after a 120 ms block (E4) |
| Many timers due at the same moment | They run in order of expiry, one after the other, with microtasks drained between them (Node 11+) | `t1, p1, t2, p2` (E2) |
| `setTimeout(fn, 0)` vs `setImmediate(fn)` in the main module | Not guaranteed | Timeout first 6/6 here, but depends on process speed |
| The same two calls inside an I/O callback | `setImmediate` is **always** first | Observed (E1) |
| `setInterval(fn, 100)` with a callback that takes 30 ms | Runs about every 100 ms measured from its schedule; if the loop is blocked, intervals can **bunch up late** but do not pile up | Drift can accumulate with a long-blocked loop |
| A timer should not keep the process alive | Call `timer.unref()` | The loop can exit even though the timer is pending |
| A very long delay (over about 24.8 days) | Treated as 1 ms with a warning | |
| Keep-alive and request timeouts | These are internal timers, so a blocked loop delays them too | |

**Use of timers as a probe.** The "event loop lag" metric is exactly this: schedule a timer, measure how late it fired. That is what a late timer means, and why it measures how busy the thread is.

## 14. Case 8: many sockets become ready at once (a burst)

### Scenario

A thousand clients send requests in the same millisecond, for example after a load balancer opens many connections.

### What the loop does

The next `epoll_wait` returns a batch of ready sockets. The loop processes them in sequence: read, parse, handler, drain microtasks, next.

- **The last socket in the batch waits for all the earlier ones.** With 36 µs per request, a batch of 1,000 takes about 36 ms, so the last request waits roughly 36 ms.
- If there are more ready sockets than one batch can hold, the rest are picked up by further `epoll_wait` calls. Timers and other phases get their turn **between** batches.
- Timers due during a long batch fire late (up to the batch duration).

### What you see

Short, sharp p99 and p99.9 spikes during bursts, with p50 unchanged, and brief event loop lag rises. Throughput on average is fine, but the shape of arrivals matters: bursty traffic at the same average rate gives worse tail latency than evenly spaced traffic. (This is one reason your open-model, constant-arrival-rate test is gentler than real traffic.)

### What to do

Smooth arrivals if you can (client jitter, rate limiting), keep per-request cost low, and run more processes or instances to divide bursts.

## 15. Case 9: a handler throws or rejects

### Scenario

One request hits a bug.

### Observed (E8)

| Handler code | Result in Node 22 |
| --- | --- |
| Plain function that **throws synchronously** | The error becomes an uncaught exception. **The whole process exits (code 1).** The client gets no response. |
| `async` function that **throws** | The promise rejects, unhandled, and the **process exits (code 1)**. |
| A **timer callback** throws later | The client got its 200 response, then **the process exited (code 1)** when the timer fired. |
| `async` function with `try/catch` | Client got a 500 response, and the **server stayed alive** |
| `async` function that throws, with a `process.on('unhandledRejection')` hook installed | The process survived but the **request hung forever** (the client saw no response until its own timeout) |

### What it means for the loop

An uncaught exception inside any callback propagates out of the loop. There is no per-request isolation. One bad request can kill **every** in-flight request and every open connection of that process (they all see a connection reset).

### What to do

- Wrap handler bodies in `try/catch` (or use a framework that does) and always send a response, including on failure.
- Never rely on `uncaughtException` or `unhandledRejection` hooks to "recover": the process state may be inconsistent. Log, then exit and let a supervisor restart it (Kubernetes, systemd, pm2).
- Run several instances so a crash costs a fraction of capacity.

## 16. Case 10: the client disconnects mid-request

### Scenario

A client times out and closes its connection while your handler is waiting on the database.

### Observed (E9)

A handler awaiting 1 second; the client aborts at about 200 ms:

```txt
 212 ms  client: gives up and aborts
 214 ms  server: req 'close' event fired (client went away); res.destroyed=true
1016 ms  server: handler resumed after its await; socket destroyed=true (it still does all remaining work)
```

Node notices the disconnect at once (the `'close'` event), but **your handler keeps running** until it finishes. It will do the remaining queries and compute a response that nobody reads, and a write to the destroyed socket fails or is dropped.

### Why it matters

Under overload, clients time out and retry, but the server keeps doing the abandoned work too. That is wasted capacity at the worst time.

### What to do

Listen for `req.on('close')` or `res.on('close')`, check `req.destroyed` before expensive steps, and pass an `AbortSignal` to downstream calls (`fetch`, database clients that support cancellation).

## 17. Case 11: a slow reader (backpressure)

### Scenario

The server sends a large response, and the client reads slowly or not at all.

### What happens

Data flows: Node writes into the kernel's send buffer, then the network, then the client's receive buffer. If the client does not read, the buffers fill and TCP stops accepting more. `res.write()` then **returns `false`**, meaning "stop writing; wait for `'drain'`".

### Observed (E10)

A server writing 64 KiB chunks to a client that never reads: each `res.write` returned `false` straight away (Node itself holds only about one chunk, 64 KiB), the kernel buffers absorbed about 60 chunks (roughly 3.8 MB on this loopback), and then no more `'drain'` arrived and the server stopped writing. The event loop stayed free throughout.

### What to do

Respect the return value of `write()` and wait for `'drain'`, or better use `stream.pipeline(source, res)` which handles it for you. A server that ignores backpressure buffers the whole response in memory per slow client, so a few slow clients can exhaust memory (not the loop).

## 18. Case 12: slow or stalled senders (slow uploads, slowloris)

### Scenario

A client opens a connection and sends the request very slowly, or sends headers byte by byte, or opens thousands of connections and sends nothing.

### What the loop does

Nothing blocks. Each such connection is just an idle socket registered with epoll, costing a little memory and a file descriptor. The loop only spends time when bytes actually arrive.

### What you see

Rising active handles, file descriptor usage and `ESTABLISHED` counts, with normal CPU and event loop lag. Eventually `EMFILE` (out of descriptors) or memory growth.

### What to do

Rely on Node's built-in limits and set them deliberately: `server.headersTimeout`, `server.requestTimeout` (current Node versions default to about 60 s and 300 s; check your version's docs), `server.keepAliveTimeout` (5 s default), `server.maxConnections`, a body size limit, and a reverse proxy (Nginx, Envoy) in front that buffers slow clients so Node does not have to.

## 19. Case 13: garbage collection pauses

### Scenario

The V8 garbage collector needs to run. Most young-generation collections take a fraction of a millisecond. Major collections on a large heap can take longer.

### What the loop does

Parts of GC run on helper threads, but some phases **pause the main thread** ("stop-the-world"). For that time, no callback runs, exactly like case 1.

### What you see

- Short, regular loop lag spikes and p99.9 bumps that line up with the **GC time** panel.
- A sawtooth heap line (healthy). Pauses get longer if the heap keeps growing (leaks).
- Your measurements showed GC at about 0.1-0.2% of time: not a factor.

### What to do

Reduce allocation per request, avoid huge object graphs and large caches in the heap, check `--trace-gc`, and set the heap size deliberately (`--max-old-space-size`) to match the container memory limit.

## 20. Case 14: hidden synchronous blockers

Anything synchronous that takes time acts as case 1. These look innocent:

| Blocker | Observed |
| --- | --- |
| `JSON.parse` / `JSON.stringify` of a large body | 17 MB parse blocked the loop for **277 ms** |
| A regular expression with catastrophic backtracking (ReDoS) | `/^(a+)+$/` on a 28-character string blocked for **5.6 seconds**, roughly doubling for each extra character |
| `fs.readFileSync`, `execSync`, `crypto.pbkdf2Sync`, `zlib.*Sync` | Blocks for the whole operation |
| `console.log` on every request | Costs a system call every time; on Linux, writes to files and terminals are synchronous per Node's docs, so a slow terminal can stall the loop |
| Large `for` loops, sorting big arrays, building big strings | CPU time on the main thread |
| `await` loops over many resolved promises | Starvation (case 6) |

**Detect:** event loop lag spikes without a matching dependency slowdown; CPU profile shows one function with a wide frame. **Fix:** limit input sizes, use safe regexes or a linear-time engine, use the async APIs, and measure.

## 21. Case 15: the accept queue while the loop is blocked

### Scenario

The loop is blocked (case 1, 6, 13 or 14) while new clients try to connect.

### What happens

The kernel keeps completing handshakes and queues the connections in the **accept queue** until it holds about `backlog + 1`. Beyond that, new connection attempts are **silently dropped**, the clients retransmit their SYN after growing delays, and `ListenOverflows` and `ListenDrops` increase.

### Observed (E11, from the previous document)

Backlog 4, Node blocked for 6 seconds, 8 clients:

```txt
accept-queue length = 5      (backlog + 1)
5 connections counted ESTABLISHED on both ends
3 clients stuck in SYN_SENT   (their attempts were dropped)
```

When the loop freed up, Node accepted all 8 within about 55 ms (the stuck ones after retransmitting).

### Effect

Connections that already exist (keep-alive) are unaffected by the accept queue, but their requests wait in the receive buffers. New connections see `connect` take 1 s, 3 s, 7 s and so on, which is the connection-time spikes you saw in k6 (`http_req_connecting` maximum of 7 s, 11 s, 19 s).

## 22. Case 16: keep-alive timeout race

### Scenario

Node closes an idle connection after `keepAliveTimeout` (5 s by default). A client that reuses that connection at **the same moment** sends a request into a connection the server is closing.

### What you see

An occasional `ECONNRESET` or "socket hang up" on the client, with no error on the server.

### What to do

Make the client's idle timeout shorter than the server's, retry **idempotent** requests once on a reset, and set `keepAliveTimeout` above your load balancer's idle timeout (a common rule when Node is behind an AWS load balancer).

## 23. Case 17: shutdown, signals and exit

### SIGTERM handling

A signal handler (`process.on('SIGTERM', ...)`) runs through the loop like any other callback, in the poll phase. If the loop is blocked, the handler waits too.

### Graceful shutdown sequence

1. `server.close()` stops accepting new connections. It does **not** close connections that are already open.
2. Idle keep-alive connections would keep the process alive until they time out: call `server.closeIdleConnections()` (Node 18.2 and newer).
3. Let in-flight requests finish (with a deadline), then `server.closeAllConnections()` if needed.
4. Exit.

### Exit rules

The loop exits on its own when no referenced handle remains. Pending timers keep it alive unless `unref`'d. `process.exit()` ends the process immediately and skips remaining callbacks.

## 24. Case 18: several processes (cluster)

Each Node process has its **own** event loop and its own accept handling. A block in one process affects only the connections that process owns.

- With `cluster`, the primary process accepts connections and hands them to workers in turn (round-robin, the default on Linux). A worker that is blocked still receives its share, and those requests wait.
- With separate processes behind Nginx or Kubernetes, the balancer can route around an instance that fails health checks (but a blocked instance may be slow to be noticed).
- This is why "one process per core" is the standard scaling unit, and why your load tests with pinned CPUs behave like one instance.

## 27. Rules of thumb

1. **A callback should be short.** Aim for microseconds to a few milliseconds. Long work belongs in slices, workers or other services.
2. **Never block waiting.** Use async APIs for I/O; avoid every `*Sync` call in a request path.
3. **Know your three queues:** the kernel (accept queue and receive buffers), the microtask and nextTick queues, and the thread pool queue. Waiting can hide in any of them.
4. **Measure the loop, not just the handler.** Handler time can be flat while the loop is saturated. Event loop lag and event loop utilisation (ELU) tell the truth.
5. **Bound everything:** body size, timeouts, queue lengths, worker pools, in-flight requests.
6. **Expect one bad request.** Catch errors, always answer, run more than one instance, and restart on crash.
7. **Cancel abandoned work.** Respect `'close'` and pass abort signals downstream.
8. **Test under bursts and under blocks,** not only at a steady rate (inject a 300 ms block and watch the recovery time).

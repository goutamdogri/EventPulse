# Why CPU work blocks everything?

In Node.js, JavaScript typically executes your application's callbacks on a single main thread called the event-loop thread. If that thread spends 200 ms doing synchronous CPU-intensive work, it cannot process other JavaScript callbacks during that time.

This is why CPU-heavy JavaScript can hurt the latency of every request handled by the same event loop.

## 1. How the event loop handles requests

Suppose EventPulse receives three requests almost simultaneously:

- Request A: process an event.
- Request B: validate another event.
- Request C: return an API response.

Normally, the event loop runs their callbacks as they become ready.

Now suppose Request A performs a synchronous calculation that takes 200 ms.

```js
app.post("/events", (req, res) => {
  const result = expensiveCalculation(); // Takes 200 ms
  res.json({ result });
});
```

While `expensiveCalculation()` runs, the main JavaScript thread cannot execute the callbacks for Requests B and C.

```txt
Time ──────────────────────────────────────────────>

Main JS thread:
| Request A: CPU work (200 ms) | B | C | ...

Request A: ████████████████████
Request B:                         waits...
Request C:                         waits...
```

Even if Requests B and C require only 2 ms of work each, they must wait until the synchronous calculation finishes.

Important: This doesn't mean every request in the entire system stops. It means callbacks scheduled on that same JavaScript thread cannot make progress. Other Node.js processes, worker threads, and independent services can continue running.

## 2. Why asynchronous I/O is different

Consider two operations.

A. Synchronous CPU work

```js
const result = expensiveCalculation();
```

The JavaScript thread is occupied until the calculation finishes.

B. Asynchronous I/O

```js
const result = await database.query("SELECT * FROM events");
```

Assuming `database.query()` uses a genuinely asynchronous database driver, Node.js can wait for the database response without blocking the JavaScript thread. Other callbacks can execute while the query is pending.

There is an important distinction:

- Waiting for I/O: usually doesn't block the event loop.
- Executing CPU-intensive JavaScript: blocks the event loop until the computation yields or finishes.

Using `async` and `await` does not automatically make CPU-intensive code non-blocking.

## 3. How one slow callback affects latency

Suppose EventPulse receives 1,000 requests per second.

That means, on average, a new request arrives every:

$$ \frac{1}{1000}\text{ s} = 1\text{ ms} $$

Now a single callback blocks the event loop for 200 ms.

During that interval, approximately:

$$ 1000 \times 0.2 = 200 $$

requests may arrive.

Those requests can accumulate in the networking stack or application-side queues, depending on the system. Once the event loop becomes available, it must work through the pending callbacks.

The result can be a sharp increase in p99 latency, even when most requests require very little CPU time individually.

## 4. How to handle CPU-heavy work in EventPulse

| Approach                     | Best use                                                   |
| ---------------------------- | ---------------------------------------------------------- |
| Keep work on the main thread | Short, inexpensive calculations                            |
| Optimize the algorithm       | Reduce unnecessary CPU work                                |
| Worker threads               | CPU-intensive JavaScript computations                      |
| Separate worker service      | Heavy processing that can run asynchronously through Kafka |
| Multiple Node.js processes   | Use multiple CPU cores for independent workloads           |

For example, EventPulse's ingestion API should generally validate an event, enqueue it reliably, and return quickly. Expensive analytics, aggregations, and rule evaluation can often be performed by separate workers instead of blocking the ingestion event loop.

Node.js also uses its libuv thread pool for certain operations, such as many filesystem operations and some cryptographic functions. However, arbitrary JavaScript CPU calculations do not automatically run in that pool.

## 5. How to detect event-loop blocking

You can measure event-loop delay with Node.js's built-in `perf_hooks` module:

```js
const { monitorEventLoopDelay } = require("node:perf_hooks");

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  console.log({
    p99DelayMs: histogram.percentile(99) / 1e6,
    maxDelayMs: histogram.max / 1e6,
  });

  histogram.reset();
}, 5000);
```

If event-loop delay spikes while CPU utilization is high, investigate synchronous CPU work, expensive JSON processing, large loops, or inefficient algorithms.

Key takeaway: Node.js can handle many concurrent I/O operations efficiently, but each event-loop thread can execute only one JavaScript callback at a time. For EventPulse, keep the ingestion path lightweight and move substantial CPU-intensive processing to worker threads or separate services.

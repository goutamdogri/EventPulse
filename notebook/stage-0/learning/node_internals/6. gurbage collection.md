# Garbage Collection (GC)

In Node.js, Garbage Collection (GC) is the automatic process of reclaiming memory occupied by JavaScript objects that your application can no longer reach.

For EventPulse, GC matters because your ingestion API may create thousands of objects per second while parsing JSON, validating events, and preparing messages for Kafka. If memory management takes too long, request latency can spike—even when your application code isn't doing much useful work during that time.

## 1. How garbage collection works

Consider this code:

```js
function processEvent() {
  let event = {
    id: 123,
    payload: { message: 'hello' }
  };

  event = null;
}

processEvent();
```

After `event = null`, the object is no longer reachable through that variable. If nothing else references it, the garbage collector can reclaim its memory.

You don't manually free memory as you would in languages such as C. The JavaScript engine, V8, manages it automatically.

However, unreachable does not mean immediately deleted. V8 decides when to collect garbage based on factors such as allocation activity and memory pressure.

## 2. Young generation vs. old generation

V8 divides much of its managed heap into generations because many JavaScript objects have short lifetimes.

### Young generation

Contains newly allocated objects.

Examples in EventPulse:

- Temporary objects created while parsing an incoming event.
- Short-lived validation results.
- Temporary arrays used to transform payloads.

Most of these objects become unreachable quickly. V8 uses frequent, relatively inexpensive collections to reclaim this memory. This is commonly called minor GC.

### Old generation

Contains objects that survive long enough to be promoted out of the young generation.

Examples:

- Long-lived application configuration.
- Caches that retain objects.
- Maps containing persistent in-memory state.
- Objects accidentally retained by references.

Collecting the old generation generally requires more work than collecting short-lived objects. Major collections can therefore have a more noticeable effect on latency.

| Property         | Young generation                 | Old generation                         |
| ---------------- | -------------------------------- | -------------------------------------- |
| Typical contents | New, short-lived objects         | Long-lived objects                     |
| Collection       | More frequent                    | Generally less frequent                |
| Collection cost  | Usually lower                    | Can be higher                          |
| Potential issue  | Frequent allocation and minor GC | Large heap, retained objects, major GC |

These are simplified categories; V8's actual heap structure and collection strategies are more sophisticated.

## 3. Why can large allocations cause GC pauses?

Suppose EventPulse receives a large batch of events and parses it:

```js
const events = JSON.parse(largeJsonPayload);

const enriched = events.map((event) => ({
  ...event,
  receivedAt: Date.now(),
  status: 'pending'
}));
```

This code may create many objects and arrays. Several things can happen:

1. Allocation pressure: V8 must allocate memory rapidly as objects are created.
2. More frequent GC: The young generation fills quickly, triggering collections more often.
3. Promotion: Objects that remain reachable may be promoted to the old generation.
4. Major collection: If the old generation grows substantially, V8 may need more expensive collection work.
5. Large-object handling: Large allocations may be handled differently from ordinary small objects, depending on their size and type.

Some GC work can run concurrently or incrementally, so not every collection stops JavaScript completely. However, certain GC phases require the JavaScript execution thread to pause. These are called stop-the-world pauses.

For example, a 100 ms pause can delay callbacks scheduled on that event loop, potentially increasing API latency and causing requests to accumulate.

Important distinction: Large allocations do not automatically cause a long pause. Repeated allocation, retained objects, heap pressure, and the type of GC work all influence the impact.

## 4. How to inspect GC activity with `--trace-gc`

Run your Node.js application with:

```bash
node --trace-gc dist/main.js
```

If you're running a development server:

```bash
node --trace-gc src/main.js
```

The exact entry point depends on your project.

V8 will print GC diagnostic messages to the terminal. A simplified example looks like this:

```txt
[12345:0x...]  150 ms: Scavenge 10.2 (15.0) -> 7.1 (15.0) MB, 2.0 ms
[12345:0x...] 1200 ms: Mark-Compact 80.0 (100.0) -> 45.0 (100.0) MB, 25.0 ms
```

These values are illustrative, not actual output from your application.

How to read them:

- Scavenge: Typically a young-generation collection.
- Mark-Compact: A major collection involving marking live objects and compacting memory.
- Before → after: Heap usage before and after collection.
- `2.0 ms` or `25.0 ms`: Reported duration for that GC operation in the log format shown.

The heap values in parentheses represent heap capacity information, not necessarily memory used by your entire process.

Look for repeated collections, increasing heap usage, and long GC durations. Correlate them with request latency to determine whether GC is contributing to performance problems.

## 5. How to reduce GC pressure in EventPulse

- Avoid unnecessarily creating intermediate arrays and objects when processing large batches.
- Put limits on incoming payload size and batch size.
- Avoid retaining event objects indefinitely in caches or in-memory queues.
- Use streaming or bounded batches for large datasets rather than loading everything into memory.
- Profile before optimizing; object reuse and pooling can sometimes make performance worse.
- Monitor heap usage, GC activity, event-loop delay, and p99 request latency together.

The main takeaway: Young-generation GC commonly cleans up short-lived objects, while old-generation collection can be more expensive. In EventPulse, the goal is not to eliminate garbage collection—it's to keep allocation rates and retained memory under control so that GC doesn't create unacceptable latency spikes.

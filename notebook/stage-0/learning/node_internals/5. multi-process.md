# Cluster / multi-process scaling

Cluster / multi-process scaling means running multiple independent Node.js processes on the same machine so that your application can use multiple CPU cores in parallel.

The key idea: one Node.js process typically has one main JavaScript event-loop thread, so multiple processes let you handle CPU work and requests across multiple cores.

## 1. Why do we need multiple processes?

Suppose your server has 4 CPU cores and you run a single Node.js process.

```txt
Server: 4 CPU cores

Core 1          Core 2          Core 3          Core 4
  |               |               |               |
Node.js          Idle            Idle            Idle
process
```

The operating system can schedule other work on the remaining cores, but your application's main JavaScript thread cannot execute JavaScript callbacks in parallel across all four cores.

Now run four Node.js processes:

```txt
Server: 4 CPU cores

Core 1          Core 2          Core 3          Core 4
  |               |               |               |
Node.js 1       Node.js 2       Node.js 3       Node.js 4
```

Each process has its own JavaScript runtime, event loop, and memory space. Their main threads can execute JavaScript simultaneously on different cores.

This is process-level parallelism.

## 2. How does traffic reach the processes?

You need a way to distribute incoming connections or requests across the processes.

For example, using a reverse proxy:

```txt
                  Clients
                     |
                     v
                  Nginx
                     |
            +--------+--------+
            |        |        |
            v        v        v
          Node 1   Node 2   Node 3
            |        |        |
            +--------+--------+
                     |
              Shared services
              PostgreSQL / Kafka
```

Nginx distributes requests among the Node.js instances. Each process can handle its own requests independently.

Alternatively, Node.js's built-in `cluster` module can create multiple worker processes that share a server port, with the operating system and Node.js distributing connections according to the configuration and platform behavior.

## 3. How to run multiple processes

A simple option is PM2.

Install it:

```bash
npm install -g pm2
```

Start your application using all available CPU cores:

```bash
pm2 start dist/main.js -i max
```

Useful commands:

```bash
pm2 status
pm2 monit
pm2 logs
```

Here, `-i max` asks PM2 to launch instances based on the available CPU cores. For a production deployment, you should measure performance and choose the number of instances accordingly.

## 4. What does “one process per core” really mean?

It is a starting heuristic, not a strict rule.

The optimal number depends on your workload:

- CPU-heavy application: process count near the number of available cores is a reasonable starting point.
- I/O-heavy application: fewer or more processes may work well because processes spend substantial time waiting for I/O.
- Memory-intensive application: too many processes can exhaust RAM because each has its own runtime and application memory.
- Containerized application: respect the CPU limits allocated to the container, not just the host's total CPU count.

For example, four processes that each consume 500 MB of memory require roughly 2 GB just for those process memory footprints, before accounting for the operating system, other services, and additional overhead.

## 5. What are the limitations?

Multiple processes don't automatically solve every scaling problem.

Memory is not automatically shared. Each process has its own JavaScript heap. In-memory sessions, rate-limit counters, and caches may become inconsistent across processes unless coordinated through shared infrastructure such as Redis or a database.

Database load multiplies. If each process creates its own connection pool, four processes may create four times as many potential database connections.

A shared bottleneck remains shared. If PostgreSQL or Kafka is already saturated, adding more API processes may increase pressure without improving throughput.

Failures require management. Processes need supervision, graceful shutdown, health checks, and restart policies.

## 6. How this evolves in EventPulse

A practical progression is:

1. Single process: develop and establish a performance baseline.
2. Multiple processes on one machine: use multiple CPU cores and compare throughput and latency.
3. Multiple machines or containers: distribute processes horizontally behind a load balancer.
4. Independent services and consumers: scale ingestion, rule evaluation, and analytics separately according to their bottlenecks.

The distinction is important: cluster/multi-process scaling uses more cores on one machine; horizontal scaling adds more machines or container instances. Both can be combined to grow EventPulse without depending on one increasingly powerful server.

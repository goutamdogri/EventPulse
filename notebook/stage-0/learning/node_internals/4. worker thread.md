# Worker threads

Worker Threads allow Node.js to execute JavaScript on separate threads, enabling CPU-intensive tasks to run in parallel with the main event loop.

Unlike the libuv thread pool, which handles specific supported operations, Worker Threads let you explicitly move your own JavaScript computations off the main thread.

## 1. Why do we need Worker Threads?

Suppose EventPulse receives HTTP requests while also performing CPU-intensive event processing.

Without Worker Threads:

```txt
Main JavaScript thread
    |
    ├── Handle HTTP request A
    ├── Process event (200 ms CPU work)  ← BLOCKED
    ├── Handle HTTP request B (must wait)
    └── Handle HTTP request C (must wait)
```

The CPU-heavy task prevents the main thread from handling other callbacks.

With Worker Threads:

```txt
Main thread                 Worker thread
    |                            |
    ├── Receive request          |
    ├── Send task ──────────────>|
    ├── Handle request B         ├── CPU calculation
    ├── Handle request C         ├── CPU calculation
    |<────────── Result ─────────┤
    └── Respond to request A
```

The main thread can continue handling other requests while the worker performs its calculation.

## 2. Example in Node.js

Create two files.

`worker.js` — performs the CPU-intensive calculation.

```js
const { parentPort, workerData } = require('node:worker_threads');

function calculate(limit) {
  let sum = 0;

  for (let i = 0; i < limit; i++) {
    sum += i;
  }

  return sum;
}

const result = calculate(workerData.limit);

parentPort.postMessage(result);
```

`main.js` — starts the worker and receives its result.

```js
const { Worker } = require('node:worker_threads');

const worker = new Worker('./worker.js', {
  workerData: { limit: 1_000_000_000 },
});

worker.on('message', (result) => {
  console.log('Result:', result);
});

worker.on('error', console.error);

worker.on('exit', (code) => {
  if (code !== 0) {
    console.error('Worker stopped with exit code:', code);
  }
});

console.log('Main thread can continue working');
```

Run it:

```bash
node main.js
```

The main thread prints its message without waiting for the calculation to finish.

The worker executes the JavaScript calculation on its own thread. On a multicore CPU, it can run simultaneously with the main thread.

## 3. What does “message passing cost” mean?

Workers don't make communication free.

When the main thread sends work to a worker and receives the result, there can be overhead from:

- Serialization: converting data into a transferable message representation.
- Data copying: large objects or buffers may need to be copied.
- Scheduling: assigning work and managing worker execution.
- Synchronization: coordinating task submission, completion, and errors.

For example, sending a small number to a worker is inexpensive. Sending a huge JavaScript object containing millions of events may take significant time and memory.

Node.js supports structured cloning, transferable objects such as `ArrayBuffer`, and shared memory through `SharedArrayBuffer` to address different communication needs.

Therefore, offloading a tiny calculation to a worker may be slower than simply calculating it on the main thread.

## 4. When should you use Worker Threads?

| Workload                                            | Recommended approach                    |
| --------------------------------------------------- | --------------------------------------- |
| Ordinary HTTP handling                              | Main event loop                         |
| Asynchronous database queries                       | Main event loop with async I/O          |
| Large CPU-intensive calculations                    | Worker Threads                          |
| CPU-heavy JSON transformation                       | Consider Worker Threads after profiling |
| Many small, inexpensive calculations                | Usually keep on the main thread         |
| Independent, long-running event-processing pipeline | Consider a separate worker service      |

## 5. How this applies to EventPulse

Imagine an event-processing worker must evaluate complex rules against incoming events.

A possible architecture is:

```txt
HTTP ingestion API
        |
        v
      Kafka
        |
        v
Event-processing service
        |
        v
Worker Thread Pool
   ├── Worker 1: rule evaluation
   ├── Worker 2: rule evaluation
   └── Worker 3: rule evaluation
        |
        v
Results / downstream actions
```

This is illustrative architecture, not a requirement to use threads immediately.

At low traffic, a simple Node.js consumer may be sufficient. As CPU demand grows, you can introduce a bounded worker pool. If the workload grows beyond one machine, scale the processing service horizontally across multiple instances.

Avoid creating a new Worker Thread for every event. Worker creation has overhead. A bounded pool that reuses workers is generally more appropriate for sustained workloads.

Key takeaway: Worker Threads provide real parallel execution for CPU-intensive JavaScript, helping keep the main event loop responsive. Their benefit depends on whether the computation is expensive enough to outweigh the cost of sending tasks and receiving results.

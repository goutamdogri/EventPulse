# Listen backlog and accept queue in Linux

When a TCP server listens on a port, two queues matter:

1. SYN backlog — tracks connections that have started the TCP handshake but have not completed it.
2. Accept queue — holds fully established connections that are waiting for the application to accept them using `accept()`.

## 1. How the queues work

```txt
Client
   |
   | SYN
   v
+-------------------+
| SYN backlog       |  Incomplete handshake
+-------------------+
   |
   | SYN-ACK, ACK completes handshake
   v
+-------------------+
| Accept queue      |  Established connections
+-------------------+
   |
   | Application calls accept()
   v
+-------------------+
| Application       |  Handles connection
+-------------------+
```

The accept queue is important because completing the TCP handshake does not mean your application has already accepted the connection.

For example, a Node.js server may be busy processing other work. New connections can complete their handshakes and wait in the accept queue until the server accepts them.

## 2. What does `net.core.somaxconn` control?

`net.core.somaxconn` sets the system-wide upper limit on the listen backlog that an application can request.

Check it:

```bash
sysctl net.core.somaxconn
```

Example output:

```bash
net.core.somaxconn = 4096
```

An application calls `listen(fd, backlog)` to request a backlog. On Linux, the effective accept-queue limit is constrained by `net.core.somaxconn`.

Conceptually:

$$\text{Effective backlog} = \min(\text{application backlog},\ \texttt{somaxconn})$$

For example, if the application requests `8192` but `somaxconn` is `4096`, the system caps the effective limit at `4096`.

The precise behavior depends on the Linux kernel and application. The backlog is not a limit on the total number of active connections.

## 3. Interpret `ss -ltn`

Run:

```bash
ss -ltn
```

Example:

```bash
State   Recv-Q  Send-Q  Local Address:Port
LISTEN  120     512     0.0.0.0:3000
```

For a listening socket:

- `Recv-Q = 120`: approximately 120 completed connections are currently waiting to be accepted.
- `Send-Q = 512`: the configured maximum accept-queue backlog reported by `ss`.

The key distinction: `Recv-Q` is the current queue occupancy, while `Send-Q` is the queue's reported limit.

If `Recv-Q` approaches `Send-Q`, the application may not be accepting connections quickly enough.

Inspect a specific port:

```bash
watch -n 1 "ss -ltn '( sport = :3000 )'"
```

This refreshes the queue measurements every second.

## 4. What happens when the accept queue fills?

Suppose the accept queue limit is 512 and the application stops accepting connections temporarily.

1. The queue fills with established connections.
2. Additional incoming connections may experience delayed or failed connection establishment, depending on kernel settings and conditions.
3. Clients may observe connection delays, retries, or timeouts.
4. Once the application drains the queue, new connections can progress again.

A larger backlog can absorb short bursts, but it cannot solve a sustained throughput problem.

If your application accepts 1,000 connections per second while 2,000 arrive per second, the queue grows by roughly 1,000 connections per second until traffic decreases, processing capacity increases, or the queue fills.

## 5. What about `net.ipv4.tcp_max_syn_backlog`?

This setting is related, but controls a different queue.

```bash
sysctl net.ipv4.tcp_max_syn_backlog
```

| Setting                        | Main purpose                                                              |
| ------------------------------ | ------------------------------------------------------------------------- |
| `net.core.somaxconn`           | Caps the application's requested listen backlog for completed connections |
| `net.ipv4.tcp_max_syn_backlog` | Controls the SYN backlog for incomplete handshakes                        |

Do not confuse the two. Increasing `somaxconn` does not automatically increase the SYN backlog.

## 6. How to troubleshoot EventPulse

For a NestJS ingestion server, use this sequence:

```bash
# 1. Inspect the listening socket
ss -ltn

# 2. Inspect kernel backlog limits
sysctl net.core.somaxconn
sysctl net.ipv4.tcp_max_syn_backlog

# 3. Inspect TCP listen overflow and drop counters
nstat -az | grep -E 'ListenOverflows|ListenDrops|Syncookies'
```

If the accept queue is frequently full:

- Check whether the Node.js event loop is blocked.
- Check CPU saturation and request-processing latency.
- Check whether the application is accepting connections promptly.
- Scale out behind a load balancer if the server is capacity-constrained.
- Increase backlog limits only when a larger burst buffer is useful.

Production principle: backlog tuning buys time during bursts; **_it does not increase the application's sustainable connection-acceptance rate._**

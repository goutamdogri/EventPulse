# Measuring syscall cost with `strace -c`

The command

```bash
sudo strace -c -f -p <pid>
```

summarizes the system calls made by a running process while `strace` is attached. It helps identify which syscalls are frequent and which account for significant observed time.

For EventPulse, this can help investigate whether a Node.js server spends substantial time in socket I/O, waiting for events, or performing other kernel operations.

## 1. What each option means

- `-c` — collect syscall statistics and display a summary when tracing ends.
- `-f` — follow child processes and trace threads as supported by `strace`.
- `-p <pid>` — attach to an existing process.

Example:

```bash
pgrep -af node
sudo strace -c -f -p 12345
```

Let it run during representative traffic, then press `Ctrl+C` to stop tracing and display the summary.

## 2. Understanding the output

Example output (illustrative):

```txt
% time     seconds  usecs/call  calls  errors  syscall
------  ---------  ----------  -----  ------  --------
 35.00    0.070000          70   1000       0  epoll_wait
 25.00    0.050000          50   1000       0  read
 20.00    0.040000          40   1000       0  write
 12.00    0.024000          24   1000       0  recvfrom
  8.00    0.016000          16   1000       0  futex
------  ---------  ----------  -----  ------  --------
100.00    0.200000                5000       0  total
```

| Column       | Meaning                                                            |
| ------------ | ------------------------------------------------------------------ |
| `% time`     | Percentage of the measured syscall time attributed to that syscall |
| `seconds`    | Total observed time spent in that syscall                          |
| `usecs/call` | Average observed duration per call                                 |
| `calls`      | Number of calls observed                                           |
| `errors`     | Number of calls returning errors, as counted by `strace`           |
| `syscall`    | System call name                                                   |

## 3. How to interpret it

- Many `epoll_wait` calls: The event loop is frequently checking or waiting for I/O readiness. This is normal for event-driven servers; the call count alone does not indicate a problem.
- High `epoll_wait` time: The thread may be spending a lot of time waiting for I/O. That can be perfectly healthy if the server is idle.
- Many `read`, `write`, or socket-related calls: The workload may involve substantial I/O activity. Examine call frequency and average duration.
- High `futex` activity: May indicate thread synchronization or contention, but requires further investigation.
- Many errors: Inspect the specific syscalls and their returned error codes before deciding whether they are expected or problematic.

## 4. Important limitation

`strace -c` does not tell you where all application execution time goes. It summarizes observed system-call activity, not the full CPU profile.

For example, if your NestJS handler spends 80% of its time executing JavaScript business logic, that work may not appear as a costly syscall. Use a CPU profiler for JavaScript execution and `strace` for kernel interaction.

Also, tracing adds overhead and can distort latency, especially for a high-throughput server. Use short measurement windows and avoid drawing production performance conclusions from a traced run alone.

For EventPulse: compare syscall statistics under idle, normal, and load-test traffic. Correlate the results with requests per second, p95/p99 latency, CPU utilization, and event-loop lag. That gives you a much clearer picture than syscall percentages alone.

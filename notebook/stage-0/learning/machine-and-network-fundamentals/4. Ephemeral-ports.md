# Ephemeral ports and `TIME_WAIT`: How a client runs out of ports

When a client makes a TCP connection, its operating system assigns a local IP address and port. For outbound connections, the local port is often an ephemeral port: a temporary port selected by the OS.

If a client creates too many TCP connections to the same destination in a short time, it can exhaust its available source-port combinations.

## 1. How ephemeral ports work

Suppose your EventPulse client sends HTTP requests to an ingestion server:

```txt
Client                                      EventPulse Server
10.0.0.5                                    10.0.0.10:3000

10.0.0.5:41001  --------------------------> 10.0.0.10:3000
10.0.0.5:41002  --------------------------> 10.0.0.10:3000
10.0.0.5:41003  --------------------------> 10.0.0.10:3000
```

Here:

- `10.0.0.5` is the client's local IP.
- `41001`, `41002`, and `41003` are ephemeral source ports.
- `10.0.0.10:3000` is the server's destination address and port.

A TCP connection is identified by its four-tuple:

$$ (\text{source IP},\text{source port}, \text{destination IP},\text{destination port}) $$

The same source port can be used for connections to different destinations because the full four-tuple differs. But for connections from the same local IP to the same destination IP and port, the number of available source-port combinations is limited.

## 2. Inspect the ephemeral port range

Run:

```bash
sysctl net.ipv4.ip_local_port_range
```

Example output:

```bash
net.ipv4.ip_local_port_range = 32768 60999
```

This means the default ephemeral-port allocation range on this machine is configured from port `32768` through `60999`, inclusive.

The number of ports in that range is:

$$ 60999 - 32768 + 1 = 28232 $$

So there are 28,232 candidate ephemeral ports in this example.

That does not mean the machine can only have 28,232 TCP connections in total. Connections to different destinations can reuse source ports, subject to the full connection tuple, local address selection, and other kernel constraints.

## 3. Why `TIME_WAIT` contributes to port exhaustion

Consider a client that repeatedly opens a TCP connection, sends one HTTP request, and closes the connection.

```bash
Open connection
      |
Send HTTP request
      |
Receive response
      |
Close connection
      |
      v
   TIME_WAIT
      |
      | Wait for TCP timer to expire
      v
Connection state removed
```

The active closer commonly enters `TIME_WAIT`. Linux retains this state to protect against delayed packets from the old connection and to allow retransmission of the final ACK when necessary.

During this period, the same connection tuple generally cannot be immediately reused for a new connection to that same destination.

Suppose a client creates many short-lived connections to one server:

- Ephemeral ports are allocated rapidly.
- Closed connections accumulate in `TIME_WAIT`.
- Available source-port combinations become scarce.
- Eventually, new outbound connections may fail with errors such as `EADDRNOTAVAIL` or connection-establishment failures.

The exact behavior depends on the connection pattern, local IP addresses, kernel settings, and port reuse rules.

## 4. A numerical example

Assume:

- Available ephemeral ports: 28,232.
- Destination: one server IP and port.
- New connections: 2,000 per second.
- Connections enter `TIME_WAIT` for approximately 60 seconds.

A rough estimate of how many connections remain in `TIME_WAIT` is:

$$ N \approx \lambda T $$

where:

- $\lambda$ = connection-close rate per second.
- $ T $ = average time spent in `TIME_WAIT`.

Therefore:

$$ N \approx 2000 \times 60 = 120000 $$

The client could accumulate approximately 120,000 `TIME_WAIT` connections to that destination tuple, far more than the 28,232 ports in our example.

This is a simplified estimate, not a guarantee that exhaustion occurs at an exact number. The actual limit depends on tuple reuse and other kernel behavior.

## 5. Diagnose it on Linux

Check the configured port range:

```bash
sysctl net.ipv4.ip_local_port_range
```

Count sockets in `TIME_WAIT`:

```bash
ss -tan state time-wait | wc -l
```

Inspect active connections to a destination:

```bash
ss -tan dst 10.0.0.10
```

Replace the address with your server's IP.

Check socket states by count:

```bash
ss -tanH | awk '{print $1}' | sort | uniq -c | sort -nr
```

A large `TIME_WAIT` count is not automatically a problem. The important questions are whether connections are failing and whether port allocation is the limiting factor.

## 6. How to prevent ephemeral-port exhaustion

For EventPulse or any high-throughput client, the preferred solutions are:

1. Reuse HTTP connections. Use HTTP keep-alive and a properly configured connection pool instead of opening a fresh TCP connection for every request.
2. Use HTTP/2 where appropriate. Multiple requests can share one TCP connection, reducing connection churn.
3. Scale the client across source IP addresses when justified. Additional local IPs can provide more source-port combinations, although this adds operational complexity.
4. Expand the ephemeral port range if needed. This increases the available pool, provided the new range is compatible with local port allocations and firewall/NAT configuration.
5. Investigate NAT and load balancers. A shared NAT gateway can exhaust its own source-port mappings even when individual clients have ports available.

You can inspect the current range before considering changes. For example, a carefully selected larger range might be configured with:

```bash
sudo sysctl -w net.ipv4.ip_local_port_range="10000 65535"
```

This is a runtime change, not a persistent configuration. Before applying it, check for conflicts with services using fixed local ports and account for your environment's networking and security rules.

Avoid blindly shortening `TIME_WAIT` or enabling aggressive TCP reuse settings. They are not substitutes for connection pooling and can have correctness or compatibility implications.

Key takeaway: Ephemeral ports are a finite resource for outbound TCP connections. Under high connection churn, `TIME_WAIT` can keep connection tuples unavailable long enough to exhaust that resource. For EventPulse, reusing connections is usually the first optimization to make.

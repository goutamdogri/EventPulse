# TCP sysctls that matter for connection churn

`sysctl` reads and changes Linux kernel settings. These four decide how many connections you can open and close quickly. Used in E0.6.

```bash
sysctl net.ipv4.ip_local_port_range net.ipv4.tcp_tw_reuse net.ipv4.tcp_max_tw_buckets net.core.somaxconn
```

| Setting | My value | What it means |
| --- | --- | --- |
| `net.ipv4.ip_local_port_range` | `32768 60999` | Source ports the client side can use for outgoing connections (ephemeral ports) |
| `net.ipv4.tcp_tw_reuse` | `2` | Allows reusing a TIME_WAIT socket for a new outgoing connection. `0` = off, `1` = on, `2` = loopback traffic only |
| `net.ipv4.tcp_max_tw_buckets` | `65536` | Maximum number of TIME_WAIT sockets the kernel keeps in total |
| `net.core.somaxconn` | `4096` | Upper limit of the accept queue (listen backlog) of any listening socket |

## 1. ip_local_port_range

- Every connection is identified by 4 values: source IP, source port, destination IP, destination port.
- A client talking to one server (`localhost:8000`) can only vary the source port.
- `60999 - 32768 + 1 = 28232` usable ports. That is the maximum number of connections (open + TIME_WAIT) from one client to one server.
- When ports run out, the client fails with `cannot assign requested address` (`EADDRNOTAVAIL`).

### Does it matter when I am testing a server?

- The limit is per client IP talking to one server `ip:port`. Many real clients have different IPs, so each has its own 28232 ports. The server accepting connections does not use up its ephemeral ports, because it only listens on port 8000.
- So for the server under test, this is **not** a capacity limit. In E0.6 it matters in two other places:
  1. **The load generator.** k6 is one machine, so one client IP. It can hit the 28232 limit before the server has any problem. This is a test artifact, which is why `k6_http_req_failed_rate` and `dropped_iterations` are validity checks.
  2. **Your own services acting as clients, in later stages.** Examples: Nginx or Envoy to the ingest API, the API to Redis, Postgres, Kafka and ClickHouse. These are few clients with a single destination, which is the exact case where ports run out. Connection pooling and keep-alive prevent it. This is the real lesson of E0.6.
- What the server does feel from connection churn is CPU in the kernel (accept, close) and memory for its own TIME_WAIT sockets (see `tcp_max_tw_buckets`).
- One real-world exception: many users behind one NAT gateway look like a single client IP to your server.

### Why this range, and who picks the client's port?

- The **client's own OS** picks its source port, not the server. The server only sees which port the client used.
- This sysctl is a setting on the **client machine** (here: the machine running k6). It does not change what other clients, such as phones or other servers, do. Windows, macOS and BSD use their own default (IANA suggests `49152-65535`).
- The range is only the **default pool** the OS draws from when the program does not choose a port (calling `connect()` directly, or `bind()` to port 0).
- A client **can** use a port outside the range by calling `bind()` to a specific source port before `connect()`. Ports below 1024 need root. Few programs do this (some old protocols, and some tools like `curl --local-port`). Normal HTTP clients, k6 included, let the OS pick.
- Why `32768-60999` exactly: it is the Linux default, kept below `32768` to leave room for well-known and registered ports. The upper end was historically left free for NAT or masquerade port mapping. You can change it, as the break-it variant in the E0.6 README does.
- To get more ports for one test machine, widen the range (up to `1024 65535`), or use more than one client IP. Each source IP has its own set of ports.

## 2. TIME_WAIT (not a sysctl, but needed for the next two)

- The side that closes the connection first keeps the socket in TIME_WAIT for a fixed **60 seconds**. This is hard-coded in the kernel. `tcp_fin_timeout` does not change it.
- Steady-state TIME_WAIT count is about `new connections per second x 60`, but never more than the number of distinct 4-tuples (about 28232 for one client IP and one server `ip:port`).
- Port limit math: `28232 / 60 = about 470 new connections/s` sustained before the port range is full (if no reuse happens).

### What if the server closes first and the client reuses the port right away?

- The client has no TIME_WAIT, so its OS sees the port as free. `connect()` works at once with the same source port. No ephemeral port exhaustion on the client.
- The server still has a TIME_WAIT socket for the same 4 values. The new SYN from the client arrives at that old entry.
- Linux allows this **if the new connection is clearly newer**: the SYN's sequence number (or TCP timestamp) must be higher than the last one of the old connection. Linux clients choose increasing initial sequence numbers, so this normally holds. The server then removes the old TIME_WAIT and accepts the new connection. This is allowed by RFC 1122.
- If the SYN does not look newer, the server does not accept it. The client retransmits the SYN after about 1 second, so you see a connect time of about 1 s. This is rare, but it would show as spikes in `k6_http_req_connecting_seconds`.
- This is why TIME_WAIT is held by the side that closes first: that side holds the state needed to ignore old delayed packets of the previous connection, so the other side does not have to.

## 3. tcp_tw_reuse

- Lets the kernel reuse a TIME_WAIT socket's port for a **new outgoing** connection when it is safe (it uses TCP timestamps to be sure old packets cannot be confused with new ones).
- It only helps the **client** side. TIME_WAIT sockets on the server side are not affected.
- With `2`, it works only for loopback. If k6 and the server talk over `localhost`, reuse is active, so port exhaustion may appear later than the 470/s calculation predicts. This is a finding to note in E0.6, not an error.

## 4. tcp_max_tw_buckets

- A global cap on TIME_WAIT sockets. When it is exceeded, the kernel destroys the extra ones immediately and logs `TCP: time wait bucket table overflow` in `dmesg`.
- With one client IP (k6 on one machine) and one server `ip:port`, you most likely **cannot reach this cap**. See the next section.
- Only the side that closes **first** holds the TIME_WAIT socket, so there is one TIME_WAIT per connection, not two. The cap counts them on the whole host, whichever side holds them.
- With keep-alive off, k6 sends `Connection: close`. After sending the response, Node ends the connection, so the **server usually closes first** and holds the TIME_WAIT. But it is a race: if k6 closes first, the TIME_WAIT is on the k6 side and uses up its ephemeral ports instead. Check which side with the `ss ... sport = :8000` and `dport = :8000` commands below.
- With keep-alive on, connections stay open, so there is almost no TIME_WAIT during the run.

### Can one k6 client IP reach `tcp_max_tw_buckets`?

- Usually no. A TIME_WAIT socket is unique per 4-tuple (client IP, client port, server IP, server port). With one client IP and one server `ip:port`, only the client port can vary, so there can be at most about **28232** TIME_WAIT sockets (the size of `ip_local_port_range`). That is below 65536.
- Even with the widest range (`1024 65535`, 64511 ports) it stays below 65536.
- If the client reuses a port, the new connection replaces the old TIME_WAIT (server side, see above) or fails with `cannot assign requested address` (client side, unless `tcp_tw_reuse` allows it). It never adds a second TIME_WAIT for the same 4-tuple.
- So the TIME_WAIT graph flattens at **about 28232 at most**, when `new connections per second x 60` is larger than that. That is why the E0.6 dashboard shows TIME_WAIT as a % of the port range.
- To reach the cap you need more distinct 4-tuples: several client IPs, several server addresses or ports, or many different real clients.

## 5. somaxconn

- When a client connects, the kernel completes the handshake and puts the connection in the accept queue until the app calls `accept()`.
- The real queue size is `min(backlog passed to listen(), somaxconn)`. Node's default backlog is 511, so 511 is the effective size here.
- If the queue is full, new connections are dropped. This shows up as `ListenOverflows` and `ListenDrops` in `nstat` or `node_netstat_TcpExt_*`.
- See also: `3. listen-backlog.md`.

## How to check them during E0.6

```bash
ss -s                                                    # total TIME_WAIT count
ss -tan state time-wait '( sport = :8000 )' | wc -l      # server-side TIME_WAIT
ss -tan state time-wait '( dport = :8000 )' | wc -l      # client-side TIME_WAIT
nstat -az TcpExtListenOverflows TcpExtListenDrops        # accept queue overflow
sudo dmesg | grep -i "time wait bucket"                  # tcp_max_tw_buckets overflow
```

# CPU monitoring on Linux: `htop`, `pidstat`, and `vmstat`

For EventPulse, these three tools help answer different questions:

- `htop`: Which processes and threads are consuming CPU?
- `pidstat`: How much CPU is one process consuming over time?
- `vmstat`: Is the whole system under CPU pressure, and are context switches increasing?

## 1. `htop` — interactive CPU view

Run:

```bash
htop
```

Key fields:

| Field  | Meaning                                                         |
| ------ | --------------------------------------------------------------- |
| `CPU%` | CPU usage by a process; a multithreaded process can exceed 100% |
| `MEM%` | Percentage of physical memory used                              |
| `VIRT` | Virtual memory size                                             |
| `RES`  | Resident memory currently in RAM                                |
| `S`    | Process state, such as running (`R`) or sleeping (`S`)          |
| `PID`  | Process ID                                                      |

What to look for:

- One CPU core consistently saturated: a possible CPU bottleneck.
- Many busy cores: high overall CPU demand.
- One Node.js thread consuming a core: possible event-loop or CPU-heavy JavaScript work.
- High CPU across unrelated processes: possible host-level contention.

Press `H` to toggle user threads in supported `htop` versions, and `F6` to change sorting.

Remember that 100% CPU usually represents one logical CPU fully utilized. A process using 200% is consuming approximately two logical CPUs' worth of processing time.

## 2. `pidstat -u -p <pid> 1` — CPU usage over time

Run:

```bash
pidstat -u -p <pid> 1
```

Replace `<pid>` with your process ID. The final `1` means report statistics every second.

Example:

```txt
#      Time     UID    PID   %usr  %system  %CPU  CPU  Command
12:00:01      1000  12345   72.0      8.0  80.0    2  node
12:00:02      1000  12345   85.0     10.0  95.0    2  node
12:00:03      1000  12345   88.0      9.0  97.0    2  node
```

The numbers above are illustrative.

| Field     | Meaning                                                      |
| --------- | ------------------------------------------------------------ |
| `%usr`    | CPU time executing user-space code                           |
| `%system` | CPU time executing kernel code on behalf of the process      |
| `%CPU`    | Combined CPU usage reported for the process                  |
| `CPU`     | Processor on which the task was running at the time reported |
| `Command` | Process name                                                 |

Interpretation:

- High `%usr`: investigate JavaScript execution, serialization, validation, and business logic.
- High `%system`: investigate syscall frequency, networking, memory operations, and other kernel work.
- Sustained high `%CPU`: the process may be CPU-bound or sharing a constrained CPU allocation.

For Node.js, a high `%usr` value does not by itself identify which JavaScript function is responsible. Use a CPU profile for that.

## 3. `vmstat 1` — system-wide CPU pressure

Run:

```bash
vmstat 1
```

Example:

```txt
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  0      0  ...    ...   ...      0    0     1     2  800 2500 75 10 15  0  0
```

The first report can contain averages since boot. Focus on subsequent interval reports when investigating current load.

### The two important fields: `r` and `cs`

`r` — runnable tasks

The number of processes or threads running or waiting to run on a CPU.

- `r` consistently greater than the number of available logical CPUs: possible CPU scheduling pressure.
- `r` near zero: little CPU demand at that moment.

A high `r` is a clue, not proof of a bottleneck. Interpret it alongside CPU utilization and workload.

`cs` — context switches per second

The number of context switches per second across the system. A context switch occurs when the CPU switches execution from one task to another.

- High `cs` can be normal on a busy server.
- Unexpectedly high `cs` may indicate excessive thread activity, synchronization, or frequent scheduling.
- High `cs` alone does not prove that context switching is wasting significant CPU time.

Other useful `vmstat` fields:

| Field | Meaning                                                 |
| ----- | ------------------------------------------------------- |
| `us`  | CPU time in user space                                  |
| `sy`  | CPU time in kernel space                                |
| `id`  | Idle CPU time                                           |
| `wa`  | CPU time waiting for I/O completion                     |
| `st`  | CPU time taken by the hypervisor from a virtual machine |
| `in`  | Interrupts per second                                   |

## 4. Combine all three during an EventPulse load test

Run these in separate terminals:

```bash
htop
```

```bash
pidstat -u -p <pid> 1
```

```bash
vmstat 1
```

Then generate a representative event-ingestion workload and compare the results.

| Observation                           | Likely investigation                                                  |
| ------------------------------------- | --------------------------------------------------------------------- |
| High Node.js CPU, high `us`           | Profile application code and event processing                         |
| High `sy`, high context switches      | Investigate kernel overhead, networking, and thread activity          |
| High `r`, low idle CPU                | CPU scheduling pressure; consider optimization or scaling             |
| Low Node.js CPU, high request latency | Check database, Kafka, network, locks, and downstream waits           |
| High `wa`                             | Investigate storage or other I/O waits; correlate with device metrics |
| High `st`                             | Investigate host or virtual-machine CPU contention                    |

The key principle: CPU utilization tells you how busy the CPUs are; the run queue helps reveal whether tasks are waiting for CPU time; context switches help characterize scheduling activity. Use all three alongside request throughput and p95/p99 latency before deciding what to optimize.

# `epoll` in Linux

epoll - I/O event notification facility

SYNOPSIS

```c
 #include <sys/epoll.h>
```

`epoll` is a Linux kernel API that lets a program monitor many file descriptors (FDs) to find out which ones are ready for I/O.

For EventPulse, this matters because a Node.js server may handle thousands of concurrent TCP connections. It needs to know which sockets can be read from or written to without continuously checking every socket.

## 1. The problem `epoll` solves

Imagine a server has 10,000 open TCP connections, but only 50 currently have data available.

### Without an efficient readiness mechanism

A naive event loop could repeatedly check every socket:

```txt
Check socket 1    → no data
Check socket 2    → no data
Check socket 3    → data available
...
Check socket 10000
```

Repeatedly scanning all connections can waste CPU when most connections are idle.

### With `epoll`

```txt
10,000 registered sockets
          |
          v
     Linux kernel
          |
          | Reports ready sockets
          v
     Event loop
          |
          v
Process the 50 ready sockets
```

The application asks the kernel to report which registered descriptors are ready. It can then process those sockets rather than repeatedly scanning all 10,000 itself.

This is particularly useful for I/O-heavy servers with many concurrent connections.

## 2. The three main `epoll` operations

Linux exposes three primary system calls.

| Operation         | Purpose                                                    |
| ----------------- | ---------------------------------------------------------- |
| `epoll_create1()` | Creates an epoll instance                                  |
| `epoll_ctl()`     | Adds, modifies, or removes an FD from the monitored set    |
| `epoll_wait()`    | Waits for ready events and returns them to the application |

The lifecycle looks like this:

```txt
epoll_create1()
      |
      v
epoll_ctl(ADD, socket_fd)
      |
      v
epoll_wait()
      |
      v
Socket becomes ready
      |
      v
Process read/write
      |
      v
epoll_wait() again
```

For example, a server can register a TCP socket for readability. When data arrives, `epoll_wait()` can return an event indicating that the socket is ready to read.

Important: readiness does not mean the entire request has arrived. The application may still need to read repeatedly until it reaches `EAGAIN` (especially with edge-triggered operation).

## 3. Level-triggered vs. edge-triggered

`epoll` supports two important notification modes.

| Mode                 | Behavior                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------- |
| Level-triggered (LT) | Reports a socket as ready while the relevant condition remains true                               |
| Edge-triggered (ET)  | Reports a change in readiness; the application generally needs to drain the socket until `EAGAIN` |

Example: a socket has 8 KB waiting to be read, but the application reads only 2 KB.

- Level-triggered: the socket remains readable, so it can be reported again.
- Edge-triggered: the application may not receive another event just because unread data remains. It should continue reading until the nonblocking operation returns `EAGAIN`.

For most implementations, level-triggered behavior is easier to reason about. Edge-triggered behavior can be efficient but requires careful handling to avoid leaving data unread and stalling progress.

## 4. How `epoll` relates to Node.js

Node.js uses an event-driven architecture. On Linux, its underlying I/O layer, libuv, uses mechanisms including `epoll` to monitor sockets and other supported descriptors.

Conceptually:

```txt
Your NestJS application
          |
          v
Node.js event loop
          |
          v
       libuv
          |
          v
      epoll_wait()
          |
          v
Linux kernel reports ready sockets
          |
          v
Node.js schedules I/O callbacks
          |
          v
Your application handles data
```

You normally do not call `epoll` directly in NestJS. Node.js and libuv manage this machinery underneath the JavaScript APIs.

## 5. Why `epoll` helps—and what it doesn't solve

`epoll` helps a server efficiently wait for readiness across many descriptors. It does not mean that every connection is processed simultaneously or that the server can handle unlimited traffic.

Your actual capacity still depends on:

- CPU time and event-loop blocking.
- Memory consumed by each connection and its buffers.
- File-descriptor limits.
- Network bandwidth and kernel networking costs.
- Application processing time and downstream services.
- Backpressure when requests arrive faster than they can be handled.

For EventPulse, a server might maintain 100,000 mostly idle connections efficiently, yet struggle if every connection sends events at a high rate. Efficient socket monitoring and high event-processing throughput are different problems.

Remember: `epoll` tells the application which file descriptors are ready for I/O. It does not perform your business logic, guarantee that all data has arrived, or eliminate the cost of processing requests.

## `epoll`: How one thread can serve thousands of connections

The key idea is I/O multiplexing: a thread doesn't need to block while waiting for each individual socket. Instead, it waits for readiness notifications from the Linux kernel and processes whichever connections are ready.

For EventPulse, this lets a Node.js process maintain many concurrent TCP connections without dedicating one thread to each connection.

## 1. Read the Linux man pages

Start with:

```bash
man 7 epoll
man 2 epoll_create1
man 2 epoll_ctl
man 2 epoll_wait
```

In `man 7 epoll`, focus on:

- The overview of the `epoll` API.
- The interest list versus the ready list.
- Level-triggered versus edge-triggered behavior.
- The performance discussion comparing `epoll` with `select()` and `poll()`.

The central distinction is that the application registers descriptors it wants to monitor, and the kernel reports descriptors that are ready. The application doesn't have to scan every registered socket on every wait.

## 2. Trace `epoll` on a running server

First, find your server's PID. For a Node.js server, you can use:

```bash
pgrep -af node
```

Then attach `strace` to the correct PID:

```bash
sudo strace -f -e trace=epoll_wait,accept4,read,write -p <pid>
```

Replace `<pid>` with the numeric process ID. The `-f` option follows threads and child processes as supported by `strace`; attaching may require elevated privileges.

To include timestamps and syscall durations, which are useful when investigating delays:

```bash
sudo strace -f -ttT -e trace=epoll_wait,accept4,read,write -p <pid>
```

`strace` observes system calls, so it adds overhead. Use it briefly for diagnosis rather than as a production performance benchmark.

## 3. How to interpret the output

### Case A: The server is waiting for I/O

```bash
epoll_wait(13, [], 1024, -1) = 0
```

The exact output depends on the call's timeout and formatting. With a timeout of `-1`, `epoll_wait()` normally blocks until an event occurs, a signal interrupts it, or an error happens; it would not ordinarily return `0` for that indefinite wait. The important pattern to recognize is a wait that spends time blocked rather than consuming CPU.

The `13` is the epoll file descriptor, and `1024` is the maximum number of events requested in that call. The kernel returns ready events when available.&#x20;

### Case B: A new connection arrives

```txt
accept4(4, ..., ..., SOCK_CLOEXEC|SOCK_NONBLOCK) = 21
```

The listening socket (FD `4`) accepted a connection and returned a new socket FD (`21`). The new socket is used to communicate with that client.

### Case C: The server reads request data

```txt
read(21, "GET /events HTTP/1.1\r\n...", 65536) = 420
```

The server read 420 bytes from the connection. This is one read operation, not necessarily an entire HTTP request—TCP is a byte stream, so requests may arrive in multiple reads.

### Case D: The server sends a response

```txt
write(21, "HTTP/1.1 200 OK\r\n...", 180) = 180
```

The server successfully passed 180 bytes to the kernel for writing. This does not guarantee that the remote client has already received those bytes.

## 4. What proves one thread can handle many connections?

Look for this general pattern:

1. The event loop calls `epoll_wait()`.
2. It wakes when sockets become ready.
3. It performs reads or writes on the relevant FDs.
4. It returns to waiting for more events.
5. The same thread services different socket FDs over time.

That is the core mechanism behind high concurrency: one thread can manage many connections because it spends little time waiting on any one connection individually.

However, this doesn't prove your entire application runs on one thread. Node.js also uses other threads for certain operations, and application code can block the event loop. A synchronous CPU-heavy task can delay every connection handled by that event loop.

One final debugging note: your filter only traces `epoll_wait`, `accept4`, `read`, and `write`. Node.js may also use calls such as `recvfrom`, `sendto`, `recvmsg`, or `sendmsg`, depending on the operation and runtime. If you don't see expected network activity, broaden the syscall filter before concluding that the server isn't doing I/O.

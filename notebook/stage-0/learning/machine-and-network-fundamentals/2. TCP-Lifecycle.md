# TCP lifecycle and `ss -tan` states

TCP is a connection-oriented protocol. A TCP connection moves through states as the client and server establish a connection, exchange data, and close it.

On Linux, `ss -tan` displays TCP sockets, including their connection states.

```bash
ss -tan
```

Options:

- `-t` — show TCP sockets.
- `-a` — show listening and non-listening sockets.
- `-n` — show numeric IP addresses and port numbers instead of resolving names.

## 1. TCP lifecycle

```txt
Client                                  Server
  |                                       |
  | ------------ SYN -------------------> |
  | <--------- SYN-ACK ------------------ |
  | ------------ ACK -------------------> |
  |                                       |
  | <========== Data exchange ==========> |
  |                                       |
  | ------------ FIN -------------------> |
  | <------------ ACK ------------------- |
  | <------------ FIN ------------------- |
  | ------------ ACK -------------------> |
  |                                       |
  |              TIME_WAIT                |
```

- SYN: The client requests a connection.
- SYN-ACK: The server acknowledges the request and sends its own SYN.
- ACK: The client acknowledges the server's SYN. The connection is established.
- Data: Both sides can send and receive data independently.
- FIN: One side indicates it has finished sending data.
- TIME_WAIT: The side that performs the active close waits to ensure delayed packets do not interfere with a later connection and can retransmit the final ACK if needed.

The diagram shows the common case where the client closes first. TCP closure can happen in other orders, including simultaneous close.

## 2. Understanding `ss -tan` output

Example output:

```txt
State       Recv-Q  Send-Q  Local Address:Port  Peer Address:Port
LISTEN      0       511     0.0.0.0:3000        0.0.0.0:*
ESTAB       0       0       127.0.0.1:3000      127.0.0.1:51234
TIME-WAIT   0       0       127.0.0.1:3000      127.0.0.1:51235
SYN-SENT    0       1       127.0.0.1:51236     127.0.0.1:3000
```

| Column               | Meaning                                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `State`              | Current TCP state                                                                                                          |
| `Recv-Q`             | Data received but not yet consumed by the application; for a listening socket, connections waiting to be accepted          |
| `Send-Q`             | Data queued for transmission but not yet acknowledged; for a listening socket, the completed-connection accept queue limit |
| `Local Address:Port` | This socket's local IP and port                                                                                            |
| `Peer Address:Port`  | The remote endpoint                                                                                                        |

The queue fields are kernel-specific measurements, and their exact interpretation depends on the socket state. They are not simply counts of TCP packets.

## 3. All TCP states you can see in `ss -tan`

Linux TCP has 11 named states commonly represented in `ss` output. They describe more than the handshake: they also track the two directions of connection shutdown.

### Connection establishment

| State      | Meaning                                 | Typical cause                            |
| ---------- | --------------------------------------- | ---------------------------------------- |
| `LISTEN`   | Waiting for incoming connections        | A server is listening on port `3000`     |
| `SYN-SENT` | SYN sent; waiting for SYN-ACK           | A client is attempting to connect        |
| `SYN-RECV` | SYN received; waiting for the final ACK | Server has received a connection request |
| `ESTAB`    | Connection established                  | Handshake completed; data can flow       |

Example:

```txt
SYN-SENT  0  1  10.0.0.2:45000  10.0.0.3:3000
```

The local machine has initiated a connection and is waiting for a response. If this persists, the peer may be unreachable, packets may be dropped, or the connection attempt may otherwise be failing.

### Connection termination

| State        | Meaning                                                                                    | Typical cause                                                     |
| ------------ | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `FIN-WAIT-1` | Local side sent FIN and is waiting for acknowledgment or the peer's FIN                    | Local application closes its write side or socket                 |
| `FIN-WAIT-2` | Local FIN was acknowledged; waiting for peer's FIN                                         | Peer has not finished sending data                                |
| `CLOSE-WAIT` | Peer sent FIN; local application has not finished closing                                  | Remote side closed first; local application still needs to close  |
| `CLOSING`    | Both sides sent FIN before acknowledging the other's FIN                                   | Simultaneous close                                                |
| `LAST-ACK`   | Local side sent FIN after receiving the peer's FIN; waiting for its FIN to be acknowledged | Final stage for the passive closer                                |
| `TIME-WAIT`  | Connection has closed logically; waiting for the TIME_WAIT timer to expire                 | Usually the side that actively closed                             |
| `CLOSE`      | No connection exists in the TCP state machine                                              | Socket is closed or not connected; often too transient to observe |

A key distinction:

- `FIN-WAIT-2`: I sent FIN; the peer acknowledged it. I'm waiting for the peer to finish.
- `CLOSE-WAIT`: The peer sent FIN. I acknowledged it, but my local application has not completed its close.
- `TIME-WAIT`: The TCP stack is waiting before discarding the connection's remaining state.

`CLOSE-WAIT` is especially important when debugging servers. A large, growing number of `CLOSE-WAIT` sockets can indicate that the application is not closing sockets after remote clients disconnect. The state itself is normal; sockets remaining there indefinitely are the concern.

## 4. See the states on your Linux machine

```bash
# Show all TCP sockets, including listeners
ss -tan

# Show only established connections
ss -tan state established

# Show connections waiting for the final handshake ACK
ss -tan state syn-recv

# Show sockets where the peer has closed its side
ss -tan state close-wait

# Show sockets waiting in TIME_WAIT
ss -tan state time-wait

# Count sockets in each displayed state
ss -tanH | awk '{print $1}' | sort | uniq -c | sort -nr
```

To inspect a particular server port:

```bash
ss -tan '( sport = :3000 or dport = :3000 )'
```

To see listening TCP ports:

```bash
ss -ltn
```

## 5. Why these states matter for EventPulse

When EventPulse starts handling large numbers of HTTP connections, WebSockets, or persistent TCP connections, state counts can reveal different bottlenecks.

| Observation       | What to investigate                                                                              |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| Many `SYN-RECV`   | Incomplete handshakes, connection bursts, packet loss, or SYN backlog pressure                   |
| Many `ESTAB`      | Active connections, expected workload, per-connection memory, and file-descriptor usage          |
| Many `CLOSE-WAIT` | Application socket cleanup and close handling                                                    |
| Many `TIME-WAIT`  | High connection churn; investigate connection reuse before changing kernel settings              |
| Many `FIN-WAIT-2` | Peers that are slow to close their sending side or connections waiting for peer FIN              |
| Large `Recv-Q`    | Data or pending connections are not being consumed quickly enough                                |
| Large `Send-Q`    | Data is waiting to be transmitted or acknowledged; investigate network congestion and slow peers |

Important: TCP states and file descriptors are related but not identical. A socket may consume a file descriptor while it exists, but `TIME-WAIT` connections are maintained by the kernel and do not necessarily correspond to an open application file descriptor.

For a high-throughput event ingestion service, don't optimize based on one state count alone. Correlate it with connection rate, request latency, network errors, CPU, memory, and application-level socket cleanup.

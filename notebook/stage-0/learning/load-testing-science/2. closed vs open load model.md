# Closed vs. Open Load Models

When I load-test EventPulse, I need to decide how the load generator sends requests. The two main approaches are the closed load model and the open load model.

## 1. Closed load model

In a closed model, I define a fixed number of virtual users. Each virtual user sends a request, waits for the response, and then sends its next request.

For example, I configure 100 virtual users:

```txt
User 1:  Send request → Wait for response → Send next request
User 2:  Send request → Wait for response → Send next request
...
User 100: Send request → Wait for response → Send next request
```

Suppose the server responds in 10 ms. Users can send requests frequently.

But if the server becomes slow and takes 2 seconds to respond, every virtual user waits longer before sending another request. The total request rate automatically decreases.

The problem: when my server slows down, my load generator also reduces the load. This can hide the server's capacity problem.

## 2. Open load model

In an open model, I schedule requests at a predetermined arrival rate, regardless of how quickly previous requests finish.

For example, I configure a load generator to send 1,000 requests per second:

```txt
Time       Requests scheduled
0.0 s      1,000 requests/sec
1.0 s      1,000 requests/sec
2.0 s      1,000 requests/sec
3.0 s      1,000 requests/sec
```

Even if the server takes 2 seconds to respond, I continue scheduling new requests at the configured rate, subject to the load generator's ability to sustain it.

If the server cannot keep up, the number of in-flight requests grows, latency increases, and the test exposes the overload.

## 3. The key difference

| Behavior                   | Closed model                                                         | Open model                                                       |
| -------------------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------- |
| What I control             | Number of concurrent virtual users                                   | Request arrival rate                                             |
| When the server slows down | Request rate usually falls                                           | Scheduled arrival rate remains constant                          |
| In-flight requests         | Bounded by the user count, assuming one outstanding request per user | Can grow as latency increases                                    |
| Best use                   | Testing fixed-concurrency workloads                                  | Testing systems against a target traffic rate                    |
| Main risk                  | Hiding overload due to coordinated omission                          | Overwhelming the generator or accumulating excessive queued work |

## 4. A practical EventPulse example

Suppose I want to determine whether EventPulse can handle 10,000 events per second.

With a closed model, I use 1,000 virtual users. If EventPulse becomes slower, those users wait longer, so the actual request rate might fall to 2,000 requests per second. I might incorrectly conclude that the system is healthy at the observed rate.

With an open model, I schedule 10,000 requests per second. If EventPulse can only process 7,000 per second, the backlog or number of in-flight requests will grow, and latency will rise. I can identify the point at which the system stops keeping up.

One important caveat: an open model must have sufficient load-generator capacity and appropriate limits on queued and in-flight work. Otherwise, the generator itself can become the bottleneck.

## 5. What is coordinated omission?

Coordinated omission occurs when my load test fails to record the delays that would have occurred if requests had continued arriving during a period of slowness.

For example, if I send a request, wait 2 seconds for its response, and only then send the next request, I omit the requests that would have arrived during those 2 seconds under a steady arrival rate.

As a result, the latency statistics can look better than what real traffic would experience.

An open model helps avoid this problem by maintaining the intended arrival schedule and measuring latency from the scheduled arrival time when appropriate, rather than hiding delays behind response-dependent scheduling.

## 6. Which model should I use?

For EventPulse, I would use both models for different purposes:

- Open model: to test whether the ingestion pipeline sustains target arrival rates, such as 1,000, 10,000, or 100,000 events per second.
- Closed model: to test behavior under a fixed number of concurrent clients, such as persistent connections or a fixed user population.

I would measure actual achieved throughput, p50/p99/p999 latency, errors, in-flight requests, and queue growth.

My rule of thumb: if I want to know how EventPulse behaves when real traffic keeps arriving even as the system slows down, I use an open load model. If I want to understand behavior for a fixed population of users waiting on responses, I use a closed load model.

# USE method

The USE Method is a systematic way to identify performance bottlenecks in a system. For every hardware resource or software resource, check three things:

- U — Utilization: How busy is the resource?
- S — Saturation: How much work is waiting because the resource cannot keep up?
- E — Errors: Is the resource experiencing errors?

For EventPulse, this helps you diagnose why latency increases as incoming RPS rises.

## 1. Utilization

Question: How much of the resource's capacity is being used?

Examples:

| Resource                 | What to measure                                 |
| ------------------------ | ----------------------------------------------- |
| CPU                      | CPU utilization percentage                      |
| Memory                   | Used memory, available memory                   |
| Disk                     | Busy time, I/O utilization                      |
| Network                  | Bandwidth usage                                 |
| Database connection pool | Connections currently in use                    |
| Kafka producer           | Throughput relative to its sustainable capacity |

For example, if CPU utilization is consistently 95–100%, your application may be CPU-bound.

However, high utilization alone does not necessarily mean a problem. A system can operate efficiently at high utilization if latency and queues remain acceptable.

## 2. Saturation

Question: Is work waiting because the resource cannot serve it immediately?

Saturation often reveals a bottleneck before it becomes a complete failure.

| Resource       | What to measure                               |
| -------------- | --------------------------------------------- |
| CPU            | Runnable tasks waiting for CPU time           |
| Disk           | I/O queue depth and I/O wait                  |
| Network        | Transmit queue drops or congestion            |
| Database pool  | Requests waiting for a connection             |
| Kafka          | Consumer lag or producer buffering            |
| EventPulse API | In-flight requests, pending work, queue depth |

For example, suppose EventPulse receives 3,000 events/s, but its consumer processes only 2,000 events/s.

The backlog grows by approximately:

$$ 3000 - 2000 = 1000 \text{ events/s} $$

After 60 seconds, assuming the rates remain constant and no events are removed from the backlog:

$$ 1000 \times 60 = 60{,}000 \text{ events} $$

Even if CPU utilization is moderate, growing queue depth tells you the system cannot keep up.

## 3. Errors

Question: Is the resource failing to perform its work correctly?

Examples:

| Resource       | What to measure                                    |
| -------------- | -------------------------------------------------- |
| CPU            | Hardware or machine-check errors, where applicable |
| Memory         | Out-of-memory kills, allocation failures           |
| Disk           | I/O errors, filesystem errors                      |
| Network        | Packet drops, connection failures                  |
| Database       | Connection errors, query failures                  |
| Kafka          | Produce errors, broker errors, request timeouts    |
| EventPulse API | HTTP 5xx responses, timeouts, rejected events      |

Errors can appear even when utilization is low. For example, a database might be unreachable despite the API server using only 20% CPU.

## 4. Apply USE to EventPulse

Imagine your p99 latency suddenly increases from 40 ms to 500 ms.

Use this process to investigate:

| Resource       | Utilization              | Saturation                          | Errors                      |
| -------------- | ------------------------ | ----------------------------------- | --------------------------- |
| API CPU        | CPU percentage           | Runnable task backlog               | Process crashes             |
| Memory         | Memory usage             | Memory pressure or reclaim activity | OOM kills                   |
| Kafka producer | Publish throughput       | Producer buffer buildup             | Publish failures            |
| Kafka consumer | Processing activity      | Consumer lag                        | Processing failures         |
| PostgreSQL     | CPU and connection usage | Pool wait time, lock waits          | Query and connection errors |
| Network        | Bandwidth                | Queuing and packet drops            | Connection failures         |

This narrows the search for the bottleneck instead of randomly optimizing code.

## 5. Useful Linux commands

On your Ubuntu development machine:

CPU utilization and saturation

```bash
mpstat -P ALL 1
vmstat 1
```

- `mpstat` shows CPU usage by core.
- In `vmstat`, `r` indicates runnable tasks, while `b` indicates tasks blocked waiting, commonly for I/O.

Memory

```bash
free -h
vmstat 1
```

Look for available memory and signs of swapping or memory pressure.

Disk

```bash
iostat -xz 1
```

Inspect device utilization, I/O latency, and queue-related metrics.

Network connections

```bash
ss -s
ss -tan
```

These show socket counts and TCP connection states. They do not, by themselves, measure network bandwidth or packet drops.

Application errors and resource usage

```bash
pidstat -u -r -d -p <PID> 1
```

Replace `<PID>` with your Node.js process ID.

## The key principle

When diagnosing a performance problem, don't stop at asking, "Is CPU usage high?"

Ask three questions for each relevant resource:

1. Is it busy? — Utilization
2. Is work accumulating behind it? — Saturation
3. Is it failing? — Errors

Together, these three views provide a practical starting point for finding bottlenecks in a distributed system like EventPulse.

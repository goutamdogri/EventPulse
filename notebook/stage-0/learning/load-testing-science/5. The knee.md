# The knee

The knee is the point on a load-versus-latency graph where your system starts approaching its capacity limit. Beyond this point, a small increase in traffic can cause a disproportionately large increase in latency.

## 1. Understand the graph

Imagine testing the EventPulse ingestion API while gradually increasing traffic.

Illustrative example — not actual EventPulse benchmark results.

```txt
Latency
  ^
  |                              /
  |                            /
  |                         __/
  |                      __/
  |_____________________/
  |
  +--------------------------------> Incoming RPS
                      ^
                    The knee
```

Before the knee, the system handles additional traffic comfortably. After the knee, resources become saturated, queues grow, and latency rises sharply.

## 2. Example: Finding EventPulse's capacity

Suppose a load test produces these results:

| Incoming RPS | p99 latency | Interpretation         |
| ------------ | ----------- | ---------------------- |
| 500          | 20 ms       | Comfortable            |
| 1,000        | 22 ms       | Comfortable            |
| 1,500        | 25 ms       | Healthy                |
| 2,000        | 35 ms       | Approaching the knee   |
| 2,200        | 100 ms      | Latency rising sharply |
| 2,400        | 450 ms      | Severe congestion      |
| 2,600        | 1,200 ms    | Potential overload     |

Here, the knee is roughly around 2,000–2,200 RPS.

Notice that increasing traffic from 2,000 to 2,400 RPS is only a 20% increase, but p99 latency rises from 35 ms to 450 ms—almost 13 times higher.

That is the warning sign.

## 3. Why does latency suddenly increase?

Consider an EventPulse ingestion API that publishes incoming events to Kafka.

At low traffic:

1. Requests arrive.
2. The API validates them.
3. Events are published to Kafka.
4. The API responds quickly.

As traffic increases, the Kafka producer, CPU, network, or another dependency approaches its limit.

Once the system cannot process work as quickly as it arrives:

- Requests wait longer in queues.
- In-flight requests accumulate.
- Memory consumption can increase.
- Timeouts and errors become more frequent.
- Retries can add even more load.

This creates a feedback loop: higher latency → more concurrent requests → more resource pressure → even higher latency.

The bottleneck might be the API's CPU, Kafka, database, network, or connection pool. The graph shows the symptom; monitoring helps identify the cause.

## 4. Why the knee matters more than peak RPS

There are two different capacity numbers:

- Peak RPS: the highest throughput the system manages to produce under the test conditions.
- Sustainable capacity: the throughput it can maintain while meeting your latency and error-rate requirements.

A system might briefly achieve 2,600 RPS, but if its p99 latency exceeds one second, that may be unacceptable for production.

For example, if your requirement is p99 latency below 100 ms, the useful operating capacity is the highest throughput that satisfies that requirement—not the highest RPS the system can reach.

In production, you would generally leave headroom below the knee to accommodate traffic spikes, uneven workloads, and failures.

## 5. How to find the knee in a load test

1. Increase the target RPS gradually.
2. Measure achieved RPS, p50/p95/p99 latency, and error rate at every step.
3. Track CPU, event-loop lag, queue depth, Kafka publishing latency, and memory.
4. Identify where latency starts increasing disproportionately or errors begin rising.
5. Test around that region with smaller increments to estimate the knee.

For EventPulse: Don't optimize only for maximum requests per second. Find the highest sustained throughput that meets your latency and reliability targets, then provision capacity with enough headroom to remain below the knee during normal traffic spikes.

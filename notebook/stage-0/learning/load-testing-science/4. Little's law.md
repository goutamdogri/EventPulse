# Little's law

Little’s Law describes the relationship between the number of requests in a system, the rate at which requests arrive, and the time each request spends in the system.

$$ \boxed{L = \lambda \times W} $$

Where:

- $ L $ = average number of requests in the system (in-flight requests).
- $ \lambda $ = average arrival rate (requests per second).
- $ W $ = average time spent in the system (seconds).

## 1. Example: 2,000 RPS with 50 ms latency

Suppose EventPulse receives 2,000 requests per second, and each request takes an average of 50 milliseconds to complete.

First, convert milliseconds to seconds:

$$ 50\text{ ms} = 0.05\text{ seconds} $$

Apply Little’s Law:

$$ L = 2000 \times 0.05 = \boxed{100} $$

So, on average, 100 requests are in flight at any given time.

Imagine requests arriving continuously:

- In the first 50 ms, approximately 100 requests arrive.
- Those requests take about 50 ms to complete.
- Meanwhile, new requests keep arriving as earlier requests finish.

The server doesn't need to handle all 2,000 requests simultaneously. It needs enough capacity to manage roughly 100 concurrent requests under these conditions.

## 2. How latency affects concurrency

At a constant arrival rate of 2,000 RPS:

| Average latency | Average in-flight requests |
| --------------- | -------------------------- |
| 10 ms           | 20                         |
| 50 ms           | 100                        |
| 100 ms          | 200                        |
| 500 ms          | 1,000                      |
| 1 second        | 2,000                      |

The relationship is linear: if latency doubles while throughput stays constant, average concurrency doubles.

## 3. Why this matters for EventPulse

Suppose your ingestion API receives 2,000 events per second and publishes each event to Kafka.

If the average time from receiving a request until sending the HTTP response is 50 ms, Little’s Law predicts approximately 100 concurrent HTTP requests.

Now imagine Kafka slows down and average request latency rises to 500 ms, perhaps because the API waits for Kafka acknowledgments.

At the same 2,000 RPS, concurrency rises to approximately 1,000 requests.

That can increase:

- Memory consumed by in-flight requests.
- Open sockets and file descriptor usage.
- Pending promises and buffered data.
- Pressure on the event loop and downstream services.

If the system cannot keep up, queues may grow and latency can increase further.

## 4. Use it to sanity-check load-test results

Suppose you run a load test and observe:

- Achieved throughput: 2,000 RPS
- Average latency: 50 ms
- Measured in-flight requests: approximately 100

These measurements are consistent with Little’s Law.

But if you observe 2,000 RPS and 500 ms average latency, you would expect around 1,000 in-flight requests—not 100. Investigate whether the measurements use the same time window and system boundaries, or whether concurrency is being measured incorrectly.

Important: Use average latency, not p99 latency, in the formula. Little’s Law relates long-run averages, assuming a stable system and consistent measurement boundaries. Also, 100 concurrent requests does not mean 100 CPU cores or 100 actively executing tasks; many requests may be waiting for network or database I/O.

The key takeaway: Little’s Law helps you estimate how much concurrent work your system must hold to sustain a given throughput at a given latency. It is a useful consistency check, not a guarantee that your system has enough capacity.

# Coordinated omission: Why a load test can lie about latency

When I load-test EventPulse, I want to measure how long requests would take under the traffic rate I intend to send. Coordinated omission happens when my load generator waits for a slow response before sending the next request, thereby omitting delays that real incoming traffic would experience.

## 1. How the problem happens

Suppose I configure a closed-loop load test to send one request at a time.

Normally:

```txt
Time (ms)    Action
0            Send request A
10           A responds
10           Send request B
20           B responds
20           Send request C
30           C responds
```

Everything looks healthy: each request takes 10 ms.

Now suppose the server stalls for 2 seconds.

```txt
Time         Action
0 ms         Send request A
10 ms        A responds
10 ms        Send request B
2010 ms      B responds after 2 seconds
2010 ms      Send request C
2020 ms      C responds
```

While request B is waiting, my closed-loop generator sends no new requests. But real clients may continue sending requests during those 2 seconds.

Those missing requests are the core of the problem.

## 2. Why the latency percentiles look misleading

Imagine real traffic should arrive every 10 ms. During a 2-second stall, approximately 200 additional requests would be scheduled to arrive.

In a real open-loop workload, those requests might wait in queues, encounter overload, or time out. Their latency could be substantial.

But my closed-loop generator sends none of them. It measures request A, the slow request B, and request C after the stall.

The test has omitted many requests that should have experienced the stall.

This can make the observed p99 or p999 look much better than the latency users would actually experience.

The important distinction: the slow response itself is still measured. What is missing is the latency impact on requests that should have arrived while the generator was blocked.

## 3. How `wrk2` corrects for this

[`wrk2`](https://github.com/giltene/wrk2?utm_source=chatgpt.com) is a constant-throughput HTTP benchmarking tool designed to address coordinated omission.

It schedules requests at a target rate and measures latency against the intended request schedule, rather than treating the delayed actual send time as the only relevant starting point.

For example, suppose requests are scheduled at:

```txt
0 ms, 10 ms, 20 ms, 30 ms, 40 ms, ...
```

But the server stalls, and a request scheduled for 100 ms is not actually sent until 2,000 ms.

A schedule-aware latency measurement accounts for the delay relative to the intended arrival time, rather than measuring only from the delayed send time. This exposes some of the latency that a response-dependent load generator would hide.

`wrk2` uses coordinated-omission correction in its latency measurements, but I still need to configure the target throughput correctly and ensure the load generator can sustain it.

## 4. What I should do when testing EventPulse

I would run a constant-throughput test with a tool such as `wrk2` and track:

- Target versus achieved requests per second.
- p50, p90, p99, and p999 latency.
- Error and timeout rates.
- In-flight requests and queue depth.
- CPU usage, event-loop lag, and Kafka publishing latency.

For example, if I target 10,000 requests per second but EventPulse can only sustain 7,000, I should not interpret a low latency percentile as proof that the system handles 10,000 requests per second. I must check achieved throughput, errors, and whether work is accumulating.

One caveat: coordinated-omission correction estimates the impact of missed scheduled arrivals; it does not recreate every real client's behavior or replace a properly designed open-loop test.

My takeaway: I should measure latency relative to the traffic schedule I intended to generate. Otherwise, when EventPulse stalls, my benchmark can accidentally stop asking it to do work—and hide the very problem I wanted to discover.

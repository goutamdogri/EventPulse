# E0.4 Part 3: Message overhead of the worker thread

Steps: `loadtests/k6/stage-0/E0.4/README.md` (Part 3).

## Hypothesis
With negligible compute (`n=10`), the worker route is slower than the in-thread route because every request pays for a thread hop:
`postMessage` out (structured clone), a wake-up of the worker, `postMessage` back, and a main-thread callback.
So the ceiling order is `/health` >= `/cpu?n=10` > `/cpu-worker?n=10`.

Hop cost per request = 1 / ceiling_worker - 1 / ceiling_cpu (microseconds).
Prediction (before running): `/cpu?n=10` is within a few percent of `/health`. `/cpu-worker?n=10` is clearly lower
(my guess before measuring: <fill, for example 30-60 % of the in-thread ceiling>). The hop cost is tens of microseconds per request.

## Explanation
At the ceiling the main thread is saturated, so ceiling = 1 / (main-thread CPU per request).
The worker route adds two message hops and a context switch between the main thread and the worker thread. Those run on SMT siblings
of one physical core, so they also compete for the same core. Break the difference down: <fill using pidstat thread rows>.

about hop / T (here <fill> %), which was ~1-2 % at fib(38) in Part 1 and would dominate for sub-millisecond jobs.

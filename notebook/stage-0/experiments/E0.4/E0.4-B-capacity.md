# E0.4 Part 2: Capacity of /cpu-worker vs worker count (Experiment B)

Steps: `loadtests/k6/stage-0/E0.4/README.md` (Part 2).

## Hypothesis
`/cpu-worker` throughput is bounded by the worker pool: capacity C = W / job_time. Below C, latency stays near one job time.
Above C, achieved throughput flattens at C and the excess piles up as queue, so latency climbs without bound.
`/health` stays flat the whole time (isolation, already shown in Part 1).

Predictions (written BEFORE running; job_time = <fill from capacity-calc.sh>, about 0.35 s):

| W | C theoretical (W / job_time) | Prediction |
|---|---|---|
| 1 | ~2.86 rps | Knee at 100 % of C. Real C equals theoretical, one worker on its own logical CPU |
| 2 | ~5.7 rps | Real C below theoretical: CPUs 0 and 6 are SMT siblings (one physical core) shared with the main thread |
| 4 | ~11.5 rps | No gain over W=2: four workers share the same two logical CPUs. Job time inflates, latency worse, C about equal to W=2 |

Formula: wait(t) = ((lambda - C) / C) * t, latency = wait + job_time, backlog = (lambda - C) * t jobs.

## Cost
Isolation costs a hard throughput ceiling of W / job_time that you now own, plus a queue you must watch and bound.
Adding workers helps only until the logical CPUs are used up (measured at W = <fill>); beyond that latency gets worse.
Overload does not hurt `/health` but it destroys `/cpu-worker` latency (<fill> s at 150 %).

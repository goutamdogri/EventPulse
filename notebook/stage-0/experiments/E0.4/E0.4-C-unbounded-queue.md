# E0.4 Part 4: Unbounded worker queue under overload (Experiment C)

Steps: `loadtests/k6/stage-0/E0.4/README.md` (Part 4).

## Hypothesis
With an unbounded queue, offering 1.5 x C does not make the server fail. It makes it slow without limit.
The queue grows linearly, latency grows linearly, memory grows with the queued payloads, and after the load stops the backlog
still has to be worked off. If clients give up (timeouts), the server keeps spending its capacity on abandoned jobs.
A bounded queue turns the same overload into fast 503s, bounded memory and bounded latency.

## Explanation
The event loop is never the victim: the queue lives in the worker pool, so `/health` stays flat. The cost moves to the people waiting
in that queue. Each queued job holds its request, its promise and its payload, which is why memory grows linearly with backlog.
In C2 the server cannot know that a client left, so a long queue turns into goodput collapse: the worker is 100 % busy and almost
nothing it produces is used. Bounding the queue limits both memory and waiting time, and sheds the excess explicitly (backpressure).
The right bound is a latency budget: MAX_QUEUE ~ (acceptable wait) / job_time.
Link back: this is the same "backpressure over buffering" principle the Blueprint names, and what the Stage 2 batcher bound (K10) repeats with Kafka.

## Cost
Isolation by worker threads moves overload from the event loop into a queue you have to bound. An unbounded queue costs memory and
latency without limit, plus work wasted on abandoned requests. A bounded queue costs rejected requests (<fill> % at 1.5 x C), which is a
decision about who gets served, not a free win.

## Follow-ups
- Per-request deadlines: drop a queued job whose client has already gone (check `req.destroyed`) to remove the wasted work in C2.
- Per-tenant queue caps for fairness (Stage 5).
- Try LIFO or priority queueing under overload and compare tail latency of served requests.

# Natural vs Synthetic Keys

_Idempotency note 4 of 4 in the Stage 3 learning notes. Read idempotency notes 1-3 first. This note is about the **identity** that deduplication relies on: a **natural key** (an `event_id` supplied by the producer, or a business key) versus a **synthetic key** (derived by you, most often a hash of the content, or assigned by the server). It explains when each is correct, how hashing and canonicalization work, what collisions really mean, the UUID variants, and the failure modes of each choice. It supports S3-F1 and S3-F2 and the Stage 3 design decision on what the sink's unique key is._

**No labs here.** Hash and id properties below are standard (SHA-256, RFC 8785 JSON canonicalization, RFC 9562 UUIDs). Probabilities are computed from the standard birthday bound.

## 1. TL;DR

- Dedup works only if the identity of a message is **stable across retries**. Two ways to get one:
  - **Natural key:** an id that **exists before and independent of** your pipeline and is **carried** by the message: the `event_id` the producer mints, an order number, a business key.
  - **Synthetic key:** an id **you compute**, either **assigned** (a server-generated UUID) or **derived** from content (a hash).
- **Prefer the natural key** supplied by the producer: it is cheap, stable, explicit, and expresses the producer's own notion of "the same event".
- A **server-assigned** id **cannot** deduplicate the client's own retries (each retry gets a new one). It is a good **resource id**, a bad **dedup key**.
- A **content hash** deduplicates **without client cooperation**, but it defines "same event" as "**same bytes after canonicalization**", which is wrong when two genuinely distinct events have identical content, and fragile when harmless differences change the bytes. It needs exact **canonicalization** and a clear choice of **which fields** go into the hash.
- **Collision** has two meanings that must not be confused: a **cryptographic hash collision** (two different inputs with the same hash: negligible for SHA-256) and a **semantic collision** (two different events that are _meant_ to be distinct but have the same content, so the hash merges them: common and dangerous).
- The robust pattern is **hybrid**: natural `event_id` as the **primary key**; a **content hash stored alongside** to detect "same id, different payload" (a client bug) and as a **fallback** when the id is missing.
- UUIDv4 for random ids, **UUIDv7** for time-ordered ids with better index locality, **UUIDv5** for deterministic ids derived from a namespace and name.

> **One-line version:** _Let the producer name the event; use a hash to check that the name always means the same content, not to invent the name._

## 2. The mental model

|                                                     | Natural key                                              | Content hash                                             |
| --------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| Metaphor                                            | A **person's name**                                      | A **fingerprint**                                        |
| What it says                                        | "This is Dogri" (an identity chosen by the owner)        | "This is **what you look like right now**"               |
| Two people, same name?                              | Possible; resolved by scoping (tenant) and a unique rule | Never: different fingerprints, unless identical twins    |
| Identical twins (two events with identical content) | Two names: two events, correct                           | **One fingerprint: merged into one**, which may be wrong |
| Person changes haircut (harmless difference)        | Same name, same person                                   | **Different fingerprint**: treated as a different person |
| Works without the person telling you their name?    | No                                                       | Yes                                                      |

The twins and the haircut are the two failure modes of hashing; the "no cooperation" row is its one strength.

## 3. Terminology

| Term                | Meaning                                                                              | Example                                                |
| ------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| **Natural key**     | An identifier with business meaning that exists in the domain independent of storage | `order_number`, `(tenant, event_id)` minted by the SDK |
| **Surrogate key**   | An identifier invented by the database or system with no business meaning            | `bigserial`, a server UUID                             |
| **Synthetic key**   | Informally: any key **you manufacture** rather than receive: surrogate or derived    | server UUID, `sha256(payload)`                         |
| **Derived key**     | A synthetic key **computed deterministically** from other data                       | content hash, UUIDv5 of a name                         |
| **Idempotency key** | The key used to recognize repeats (can be natural or derived)                        | `Idempotency-Key` header                               |
| **Primary key**     | The column that uniquely identifies a row in a table                                 | `event_id`                                             |

Mapping to the Stage 3 plan wording: "**natural** (`event_id` supplied by the producer)" versus "**synthetic** (a hash of content)".

Be careful with one distinction: a key can be **natural to the producer** yet **synthetic to the server** (a UUID the SDK generates means nothing in the domain, but it is **carried** by the message and stable across retries; for dedup purposes it behaves as a natural key). What matters is **who mints it and whether it survives retries**, not whether it has business meaning.

## 4. Natural keys supplied by the producer

### 4.1 Forms

| Form                         | Example                                                                  | Notes                                                          |
| ---------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------- |
| Client-minted random id      | UUIDv4/v7 generated by the SDK per event                                 | The commonest for event ingestion                              |
| Business identifier          | `order-98123`, `invoice-2026-0007`                                       | Reproducible after client restart                              |
| Business identifier + action | `order-98123:payment`                                                    | Distinguishes different effects of one entity                  |
| Source position              | `(source_system, log_position)` e.g. a DB log offset or file name + line | Deterministic from the source; good for CDC and file ingestion |
| Composite                    | `(device_id, sequence_number)`                                           | Natural for sensors with a counter                             |

### 4.2 Advantages

1. **Stable across retries by construction**: the producer sets it once, before the first attempt.
2. **Expresses the producer's intent**: "these two messages are the same event" or "different events", even if the content is identical or differs trivially.
3. **Cheap**: no hashing, no canonicalization, no CPU on the hot path.
4. **Supports legitimate identical events**: two clicks with identical fields but different ids are two events.
5. **Debuggable**: a human can look an id up in logs across systems.
6. **Enables mismatch detection**: same id with different content is visible (note 2).
7. **Works with replays**: the replay tool just preserves it.

### 4.3 Disadvantages and risks

| Risk                                                | Detail                                                        | Mitigation                                                                     |
| --------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Missing id**                                      | A client omits it                                             | Reject (400), or fall back (section 15)                                        |
| **Duplicate id for different events**               | Client bug (a counter reset after a crash, a copied template) | Payload hash check; 422; metrics                                               |
| **Id regeneration on retry**                        | Client mints a new id inside its retry loop                   | Documentation, SDK that persists the id with the pending event, contract tests |
| **Low entropy / predictability**                    | Sequential ints from many clients collide across clients      | Tenant scope; require UUIDs                                                    |
| **Untrusted clients**                               | A malicious client picks another tenant's id                  | Scope by authenticated tenant; never trust ids as authorization                |
| **Clock-embedded ids (v1/v7) leaking time or skew** | Client clock wrong                                            | Do not rely on the embedded time for correctness                               |
| **Id reuse across environments or after restore**   | Test and prod data mixed                                      | Namespaces; environment validation                                             |
| **Cooperation required**                            | Third-party senders may not supply ids                        | Provide a fallback path                                                        |

### 4.4 Rules for a good natural key

1. Minted **before the first attempt**, persisted with the pending work.
2. Unique within its **scope** for the **dedup lifetime** (forever for storage).
3. **Immutable**: never recomputed from changing data.
4. Opaque to the pipeline; no parsing for logic.
5. Validated at the edge: format, length, non-empty.
6. Never reused after the event is delivered or abandoned.

## 5. Synthetic key type 1: server-assigned id

The server mints an id when it receives the request (a `uuid_generate_v4()` default or a sequence).

| Aspect                                                                      | Verdict                                               |
| --------------------------------------------------------------------------- | ----------------------------------------------------- |
| Uniqueness                                                                  | Excellent                                             |
| Stable across **client** retries                                            | **No**: each retry is a new request and gets a new id |
| Use as **resource id** after creation (returned in the response)            | Good                                                  |
| Use as **dedup key**                                                        | **Useless** for client retries                        |
| Use for **internal** dedup between your own services, after the first stamp | Fine **if** it is stamped once and carried downstream |

The legitimate pattern: the **first** trusted service in your pipeline stamps an id **once** and every later hop carries it. That id dedups everything **downstream of the stamp**, but **not** duplicates **created before** the stamp (the client's own retries, which hit the stamping service twice and get two ids). That is why the client-supplied `event_id` must come first when client retries matter.

`bigserial` ids are the same: a retried insert gets the next number. A sequence value is **never** an idempotency key.

## 6. Synthetic key type 2: content hash

### 6.1 Definition

```
key = H( canonical( identifying fields of the message ) )
```

where `H` is a cryptographic hash (typically SHA-256, optionally truncated).

### 6.2 When it is attractive

| Situation                                                                       | Why a hash helps                                                |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Third-party senders that provide no id                                          | You still need dedup                                            |
| Webhooks from external providers                                                | The provider may send the same payload several times; no key    |
| File or batch ingestion where rows have no ids                                  | Hash the row to find repeats                                    |
| Detecting **identical resubmission** of a whole request                         | Request fingerprint for the "same key, different payload" check |
| Content-addressed storage (blobs, artifacts)                                    | Identity **is** the content by design                           |
| Cross-source dedup when two systems report the same fact differently-identified | Hash of normalized business fields                              |

### 6.3 What a hash identity actually means

> Two messages are "the same event" **if and only if** their canonicalized, selected fields are byte-identical.

Everything dangerous about hash keys follows from that one sentence.

### 6.4 Failure mode A: semantic collision (the twins)

Two distinct real-world events can have identical content:

```
{"type":"button_click","user":"u1","page":"/pricing","ts":"2026-11-22T10:00:00Z"}   <- click 1
{"type":"button_click","user":"u1","page":"/pricing","ts":"2026-11-22T10:00:00Z"}   <- click 2 in the same second
```

A content hash **merges them into one event**: a **silent loss** of a real event. Timestamps help only down to the resolution of the clock. Adding a **client sequence number** or id into the hash fixes it, but then you are back to a natural key.

For **counting** products (EventPulse analytics), silently merging distinct events **undercounts**.

### 6.5 Failure mode B: false distinction (the haircut)

Harmless differences change the hash, so a true duplicate is not recognized:

| Difference                                                      | Cause                 |
| --------------------------------------------------------------- | --------------------- |
| JSON key order or whitespace                                    | Different serializers |
| `1` vs `1.0` vs `1e0`                                           | Number formatting     |
| Unicode normalization (`é` as one code point or two)            | Different clients     |
| Time zone formats (`Z` vs `+00:00`), precision (`.1` vs `.100`) | Clients               |
| An added per-attempt field (retry counter, `sent_at`, trace id) | SDK                   |
| Default values present or omitted                               | Versions              |
| Field added by a newer schema                                   | Schema evolution      |

Result: the duplicate **slips through** (a false negative). Fixed only by **canonicalization** and by **excluding** transport noise from the hashed set (section 7).

### 6.6 Failure mode C: instability across versions

If you change the hashed field set, the canonical form, or the hash function, **old keys no longer match new ones for the same event**. Replays of old data then re-insert. A hash key needs a **version tag** (`v1:`) and a migration plan.

### 6.7 Failure mode D: privacy and leakage

A hash of low-entropy content (an email, a small id space) can be **reversed by guessing** (dictionary attack). Do not treat a hash as anonymization. Use a keyed hash (HMAC) if the key might be exposed.

### 6.8 When content hashing is **correct**

- The content **is** the identity (content-addressed blobs, immutable documents).
- Duplicates are **semantically** the same, and distinct events with identical content are impossible or irrelevant (for example, a "last known state" snapshot of an entity with a version).
- You hash a **business key** (`order_id + line_no + amount`), not the whole payload, and that business key is unique by domain rules.

## 7. Canonicalization: making equal things hash equal

Canonicalization turns "equal in meaning" into "equal in bytes".

### 7.1 For JSON

Use a documented canonical form such as **RFC 8785 (JSON Canonicalization Scheme, JCS)**:

| Rule                                                                                   | Effect                  |
| -------------------------------------------------------------------------------------- | ----------------------- |
| Object members sorted by key (UTF-16 code units)                                       | Order independence      |
| No insignificant whitespace                                                            | Whitespace independence |
| Strings in a defined escaped form                                                      | Escape independence     |
| Numbers serialized by the ECMAScript number rules (shortest round-trip representation) | `1.0` and `1` agree     |
| UTF-8 encoding                                                                         | Byte stability          |

Gotchas:

- **Big integers** beyond 2^53 lose precision as JSON numbers in JavaScript. Carry them as **strings** in the schema.
- **Floats**: `0.1 + 0.2` artifacts differ across languages; avoid floats in identity fields.
- **Unicode normalization** (NFC vs NFD) is **not** done by JCS; normalize identifying strings explicitly if needed.
- **Arrays** are ordered; if order is not meaningful, sort them yourself before hashing.
- **Null vs absent**: decide and apply consistently.

### 7.2 For Avro / Protobuf

Hash the **decoded canonical fields** or the **fully resolved writer-schema encoding**, not "whatever bytes arrived". Avro binary encoding is deterministic for a given schema and data, but **different schema versions** encode the same logical record differently (a defaulted field added). Protobuf serialization is **not canonical** by spec (field order, unknown fields, map ordering). Hash a **projection** of the identifying fields instead of the entire serialized message.

### 7.3 Choosing the hashed field set

| Include                                                                                                     | Exclude                                                                                       |
| ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Fields that define **what the event is** (tenant, type, subject, business ids, business timestamp, amounts) | Transport and bookkeeping: `received_at`, retry counters, trace ids, SDK version, request ids |
| A producer sequence or id if present (this makes a twin distinct)                                           | Server-added fields                                                                           |
|                                                                                                             | Fields that legitimately differ between retries                                               |

Write the rule down as the **identity definition** of the event type, version it, and test it.

### 7.4 Domain separation

Prefix the hashed input with a **type/version tag** so different entity types cannot collide: `H("event.v1" || 0x00 || canonical(...))`. Also avoid **ambiguous concatenation**: hashing `a || b` where `("ab","c")` and `("a","bc")` give the same bytes. Hash a structured encoding (length-prefixed or JSON array), not naive string concatenation.

## 8. Collisions: the two meanings

### 8.1 Cryptographic collision (hash function level)

Two **different** inputs yield the **same** hash value.

For an ideal `b`-bit hash and `n` items, the probability of **any** collision is roughly (birthday bound):

```
p  ~=  n^2 / 2^(b+1)
```

| Hash width | n = 1 billion (10^9)                             | n = 10^12                    |
| ---------- | ------------------------------------------------ | ---------------------------- |
| 64-bit     | n^2 = 10^18, 2^65 ~= 3.7x10^19, so p ~= **2.7%** | essentially certain (p ~= 1) |
| 128-bit    | 10^18 / 2^129 ~= 1.5x10^-21                      | 10^24 / 2^129 ~= 1.5x10^-15  |
| 256-bit    | ~4x10^-60                                        | ~4x10^-54                    |

Takeaways:

- **SHA-256 (256-bit)** collisions are not a practical concern. Even a **128-bit** truncation is safe at planetary scale.
- **64-bit** keys (for example a truncated hash, or a `bigint` hash) become **risky around a billion keys**: a 2.7% chance of at least one collision, and one collision means **a distinct event silently dropped**.
- Non-cryptographic hashes (`xxHash`, `MurmurHash`, `CRC32`) are **not designed to resist** adversarial collisions; an attacker can craft colliding inputs. Use them for sharding or bloom filters, **not** as a dedup identity for untrusted input. CRC32 and 32-bit hashes collide at only ~77,000 items (birthday on 2^32).

### 8.2 Semantic collision (domain level)

Two **different events** that you intended to keep distinct **map to the same key** because the key does not capture what makes them different. This happens **even with a perfect hash**, because the input to the hash is identical. It is a **design** error, not a math error, and it is the dominant risk of content hashing (section 6.4).

### 8.3 Collision handling policy

For any key scheme decide:

| Question                                     | Typical answer                                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| On a key conflict, compare the full content? | Yes, at least a stored hash or a full compare on the conflict path                                   |
| Same key, same content                       | Duplicate: absorb, count                                                                             |
| Same key, different content                  | **Alert**: either a client bug (natural key) or a genuine collision (hash key); never silently merge |

A stored `payload_hash` next to a natural `event_id` gives this check cheaply (note 2, section 9).

## 9. Choosing hash functions

| Function                               | Output        | Use                                                                                        |
| -------------------------------------- | ------------- | ------------------------------------------------------------------------------------------ |
| **SHA-256**                            | 256-bit       | Default for identity and request fingerprints; fast enough (hundreds of MB/s) and standard |
| **SHA-512/256**, **SHA-3**, **BLAKE3** | 256-bit       | Equivalent security; BLAKE3 is faster                                                      |
| **SHA-1**, **MD5**                     | 160 / 128-bit | **Broken for collision resistance**; avoid for new designs involving untrusted input       |
| **HMAC-SHA256**                        | 256-bit       | Keyed hash; use when the hash must not be guessable or forgeable by outsiders              |
| **xxHash64/128, Murmur3, CityHash**    | 64/128        | Speed; non-adversarial settings (internal partitioning, bloom filters)                     |
| **CRC32**                              | 32-bit        | Error detection only; never an identity                                                    |

Truncation: keeping the first 128 bits of SHA-256 is fine for identity; document it. Store as `bytea` (16 or 32 bytes) rather than hex text (doubles the size).

Cost on the hot path: hashing a 1 KB payload with SHA-256 is on the order of a few microseconds; canonicalization (parsing and re-serializing JSON) usually costs **more than the hash**. Measure both.

## 10. Deterministic ids: UUIDv5, UUIDv7 and friends

| Version           | Construction                           | Deterministic? | Notes                                                                                                                                           |
| ----------------- | -------------------------------------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **v4**            | 122 random bits                        | No             | Common client id; no ordering; random index insertion                                                                                           |
| **v1**            | Timestamp + node (MAC)                 | Partly         | Leaks MAC/time; mostly avoided                                                                                                                  |
| **v3**            | MD5 of namespace + name                | **Yes**        | Legacy; prefer v5                                                                                                                               |
| **v5**            | SHA-1 of namespace + name              | **Yes**        | **A natural key turned into a UUID**: the same (namespace, name) always yields the same UUID. Useful to give a business key a uuid-typed column |
| **v7** (RFC 9562) | 48-bit Unix ms timestamp + random bits | No             | **Time-ordered**: new ids sort roughly by creation; better B-tree locality. Leaks creation time                                                 |
| **v8**            | Custom                                 | Depends        | Vendor-defined                                                                                                                                  |
| **ULID / KSUID**  | Timestamp + random                     | No             | Similar to v7 in intent                                                                                                                         |

Using **v5** for dedup: `event_id = uuidv5(NAMESPACE_EVENTPULSE, tenant + ":" + source_system + ":" + source_position)`. A re-ingest of the same source record gets the **same** event id without any client state. This is a **deterministic natural key** and is often the best answer for CDC, file loads and webhooks: it is derived (no client cooperation needed) **and** based on a **stable business position**, not on whole-content bytes. Note v5 uses SHA-1 internally; it is fine as an **identifier derivation** (not a security boundary), but if the inputs are attacker-controlled, collisions engineered against SHA-1 could matter; for that case derive your own SHA-256-based id.

## 11. Business-event identity: what makes two events "the same"

Ask this question per event type, explicitly, and write the answer in the schema docs.

| Event type                           | "Same event" means                                             | Identity                                                |
| ------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------- |
| User action event (click, page view) | The same **occurrence**, even if another click looks identical | Producer `event_id` (SDK-minted per occurrence)         |
| Order placed                         | The same **order**                                             | `order_id` (business key), or `order_id + ":placed"`    |
| Payment attempt                      | The same **attempt**                                           | Client idempotency key; a retried charge is one attempt |
| Sensor reading                       | `(sensor_id, timestamp)` or `(sensor_id, sequence)`            | Composite natural key                                   |
| Entity state snapshot                | `(entity_id, version)`                                         | Natural with version                                    |
| Webhook from a provider              | Provider's delivery id or event id (many providers send one)   | Prefer their id; hash only if absent                    |
| Row from a file                      | `(file_id, line_number)`                                       | Position-derived                                        |
| CDC change                           | `(source, LSN/offset)`                                         | Position-derived                                        |

The pattern: **the identity is a property of the domain's definition of "occurrence"**, not of the bytes. Bytes are a weak proxy for it.

## 12. Composite keys and scope

Dedup identity is usually composite:

```
identity = (tenant_id, [event_type or source,] event_id)
```

Considerations:

- **Order columns in the index for the access pattern.** The unique constraint's leading column should be the one you filter by most; `(tenant_id, event_id)` supports per-tenant range access.
- **Never put server-side fields** (`received_at`) in the identity.
- **Include the operation** when one id could legitimately be used for two different actions.
- **Nullable parts** break uniqueness (nulls are distinct): make all parts `NOT NULL`, or use a sentinel.
- **Encoding of composite string keys** for Redis: use an unambiguous delimiter and validate components, or hash the structured tuple.
- **Consistent scope everywhere:** the API's Redis key, the sink's unique constraint, and any replay tool must use the **same** tuple.

## 13. Comparison table

| Dimension                                           | Natural key (producer `event_id`) | Server-assigned id   | Content hash                                      |
| --------------------------------------------------- | --------------------------------- | -------------------- | ------------------------------------------------- |
| **Who mints**                                       | Producer/client                   | Server               | Server (derived)                                  |
| **Stable across client retries**                    | **Yes**                           | **No**               | Yes (if canonical)                                |
| **Needs client cooperation**                        | Yes                               | No                   | No                                                |
| **Distinguishes identical-looking distinct events** | **Yes**                           | Yes                  | **No** (merges them)                              |
| **Merges true duplicates with trivial differences** | Yes (same id)                     | No                   | **Only with canonicalization**                    |
| **Detects "same id, different payload"**            | Yes, with a stored payload hash   | n/a                  | n/a (a different payload is a different key)      |
| **CPU cost**                                        | None                              | None                 | Canonicalize + hash                               |
| **Collision risk (math)**                           | Negligible (UUID)                 | Negligible           | Negligible for SHA-256; real for short hashes     |
| **Collision risk (semantic)**                       | Low (client bug only)             | None                 | **High** for events with repeatable content       |
| **Debuggability**                                   | High (carry it everywhere)        | High                 | Low (opaque digest)                               |
| **Version/schema fragility**                        | Low                               | None                 | **High** (field set, canonical form, algorithm)   |
| **Works for replays**                               | Yes (preserve it)                 | Only if preserved    | Yes (recomputed)                                  |
| **Typical role**                                    | Primary dedup identity            | Resource id / row id | Fallback; payload fingerprint; content addressing |

## 14. Failure modes of each choice

| Choice          | Failure                                   | Consequence                                                     |
| --------------- | ----------------------------------------- | --------------------------------------------------------------- |
| Natural key     | Client omits id                           | Cannot dedup (unless fallback)                                  |
| Natural key     | Client regenerates id per retry           | Duplicates pass; detectable only by content similarity          |
| Natural key     | Client reuses one id for different events | Second event dropped (`DO NOTHING`) unless mismatch is detected |
| Natural key     | Hostile client claims another tenant's id | Prevented by scope; otherwise cross-tenant interference         |
| Server-assigned | Used as dedup key                         | No client-retry dedup at all                                    |
| Content hash    | Twins merged                              | **Silent undercount/loss**                                      |
| Content hash    | Non-canonical input                       | Duplicates pass                                                 |
| Content hash    | Field set or algorithm changed            | Historical keys no longer match; replays duplicate              |
| Content hash    | Short or weak hash                        | Collisions drop events (or crafted collisions)                  |
| Content hash    | Includes a per-attempt field              | No duplicate ever matches                                       |
| Any             | Different scope in API vs sink            | Gaps or false conflicts                                         |
| Any             | Nullable component                        | Unique constraint ineffective                                   |

## 15. Hybrid designs

### 15.1 The recommended hybrid

```
PRIMARY KEY (tenant_id, event_id)          -- natural, producer-supplied
payload_hash bytea NOT NULL                -- SHA-256 of canonical identifying fields, stored beside it
```

Behavior:

| Situation                              | Action                                      |
| -------------------------------------- | ------------------------------------------- |
| Id present, new                        | Insert                                      |
| Id present, repeat, same hash          | Duplicate; absorb; count                    |
| Id present, repeat, **different hash** | Mismatch; 422 at the API, alert at the sink |
| Id absent                              | Fallback (15.2)                             |

### 15.2 Fallback when the id is missing

Options, in order of preference:

1. **Reject** with 400 for first-party clients (enforce the contract).
2. **Derive a deterministic id** from a stable business position (UUIDv5 over `(tenant, source, position)`), for sources like files, CDC, webhooks.
3. **Content-hash the identifying fields** and mark the event as `id_source = 'derived_hash'` so analysts know that merging semantics apply, and so you can measure how many events rely on it.

Never silently substitute a **random** server id as the dedup identity; that disables dedup without anyone noticing.

### 15.3 Two-level dedup

- **Level 1 (exact id):** unique constraint on the natural id.
- **Level 2 (near-duplicate detection):** an analytical job that looks for **different ids with identical content in a short window** to find clients that regenerate ids on retry. Report, do not auto-merge. This surfaces the "id regeneration" bug without risking silent loss.

---

## 16. Decision procedure

```
Do you control the producer / can you require an id?
 ├─ yes -> natural key: producer-minted event_id (UUIDv4/v7), scoped by tenant. DONE.
 │         add payload_hash for mismatch detection.
 └─ no  -> Does the source offer a stable position or its own id (webhook id, CDC offset, file+line)?
            ├─ yes -> derive a deterministic id from it (uuidv5 / hash of the tuple).
            └─ no  -> Are distinct events with identical content impossible or harmless to merge?
                       ├─ yes -> content hash of canonical identifying fields (versioned, SHA-256)
                       └─ no  -> you cannot dedup safely; require an id or accept duplicates and
                                  make the effect idempotent another way (set-valued, derived aggregates)
```

## 17. Worked example: EventPulse event identity

### 17.1 The event

```json
{
  "event_id": "0194f5c2-7b1e-7c3a-9e44-2d1f0a8b6c11",
  "tenant_id": "acme",
  "type": "checkout.completed",
  "occurred_at": "2026-11-22T10:15:30.123Z",
  "schema_version": 3,
  "payload": { "order_id": "98123", "amount_cents": 4599 }
}
```

### 17.2 Identity decisions

| Question                            | Decision                                                                         | Reason                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Dedup key                           | `(tenant_id, event_id)`                                                          | Natural, producer-supplied                                          |
| `event_id` format                   | UUIDv7 recommended from SDKs                                                     | Time-ordered inserts, better index locality; correctness unaffected |
| Who mints                           | The SDK, once per event, persisted with the pending event                        | Survives crashes and retries                                        |
| Payload fingerprint                 | `sha256(JCS({tenant_id, type, occurred_at, payload}))`, stored as `payload_hash` | Mismatch detection; excludes `received_at` and transport fields     |
| Missing `event_id`                  | 400 for first-party SDKs                                                         | Enforce contract                                                    |
| Third-party webhook source (future) | `event_id = uuidv5(NS, tenant:source:provider_event_id)`                         | Deterministic natural key from the provider's id                    |
| `received_at`                       | Stamped once at ingest; not in the key or hash                                   | Avoid per-attempt drift                                             |
| Replay tool                         | Preserves `event_id` and `payload_hash`                                          | Sink absorbs                                                        |

### 17.3 Two scenarios

**Client retry after a timeout:** same `event_id`, same hash. API: replay 202. Sink: conflict no-op if it leaked past Redis. One stored row.

**Client bug reuses an id for a different event:** same `event_id`, different hash. API: 422, metric `idempotency_key_reuse_total`. Without the hash check, `DO NOTHING` would silently drop the second event: a loss no component notices.

**Counter-example for content hashing:** two identical `page.view` events at the same millisecond from one user. With `event_id` they are two rows; with a content-only key they would be one: the analytics undercounts.

## 18. Index and storage consequences

| Choice                                       | Effect                                                                                                                            |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| UUIDv4 primary key                           | 16 bytes; random insertion order: page splits, poor cache locality, bigger WAL (full-page writes after checkpoints) at high rates |
| UUIDv7 primary key                           | 16 bytes; mostly append-ordered; far better locality; leaks creation time                                                         |
| `text` uuid                                  | 36 bytes plus overhead; avoid; use the `uuid` type                                                                                |
| SHA-256 key as `bytea(32)`                   | 32 bytes; random order like v4                                                                                                    |
| Truncated hash 16 bytes                      | Same size as uuid, random order                                                                                                   |
| `bigserial` surrogate + unique natural index | Two indexes (PK and unique), but a compact FK target; useful when other tables reference the row                                  |
| Composite `(tenant_id, event_id)`            | Wider index entry; per-tenant locality if `tenant_id` leads                                                                       |
| `payload_hash` column                        | +32 bytes per row (or 16 truncated); small relative to payload; optional index not needed                                         |

Index locality is a **throughput** factor at scale, **not** a correctness one. Choose the id type for ordering and size; choose the dedup rule for correctness.

| Test                                                                                                  | Purpose                                                                                  |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Same event, retried N times with the same id                                                          | One row; duplicates counted                                                              |
| Two events with identical content but different ids                                                   | Two rows (proves ids, not content, define identity)                                      |
| Same id, different payload                                                                            | API 422; sink keeps the first; mismatch metric                                           |

| Cross-tenant same id                                                                                  | Both stored independently                                                                |

## 21. Common confusions

1. **"Hashing the payload is the most robust key."** It is the most **cooperation-free**, not the most robust: it merges identical distinct events and breaks on harmless differences.
2. **"SHA-256 collisions are the risk."** The practical risk is **semantic** collision (identical content, different events) and non-canonical input.
3. **"A UUID from the server is a good idempotency key."** It is unique but changes on every retry.
4. **"Natural key means it has business meaning."** For dedup, what matters is that the **origin mints it once and it survives retries**.
5. **"A sequence/serial is unique so it dedups."** Each retried insert gets a new value.
6. **"Truncate the hash to 8 bytes to save space."** At around a billion keys a collision is likely enough to silently drop an event.
7. **"MD5/SHA-1 are fine, it is only dedup."** With untrusted input, crafted collisions can suppress or overwrite events.
8. **"Canonical JSON is just sorting keys."** Numbers, Unicode and arrays matter too.
9. **"UUIDv7 reveals nothing."** It embeds a timestamp; do not use it as a secret or as a trusted clock.
10. **"If ids are unique the mismatch check is unnecessary."** Clients have bugs; the check converts silent loss into a visible error.

## 23. Cheat sheet

### Glossary

| Term                    | Meaning                                                     |
| ----------------------- | ----------------------------------------------------------- |
| Natural key             | Origin-minted, domain-level identity carried by the message |
| Surrogate key           | System-invented id with no meaning (serial, server UUID)    |
| Synthetic / derived key | Computed by you; derived means deterministic from inputs    |
| Content hash            | Digest of canonicalized identifying fields                  |
| Canonicalization        | Rewriting data into one agreed byte form                    |
| JCS (RFC 8785)          | Canonical JSON scheme                                       |
| Cryptographic collision | Two inputs, same digest                                     |
| Semantic collision      | Two distinct events, identical identifying content          |
| Birthday bound          | `p ~= n^2 / 2^(b+1)`                                        |
| UUIDv5                  | Deterministic UUID from namespace + name                    |
| UUIDv7                  | Time-ordered random UUID                                    |
| `payload_hash`          | Stored fingerprint used to detect same-id-different-content |

### Rules

1. **Natural key first**: producer mints once, persists it, reuses on retries.
2. **Server-assigned ids are resource ids, never dedup keys.**
3. **Hash to verify, not to invent**: store `payload_hash` next to the id.
4. If hashing identity: **canonicalize, choose fields deliberately, SHA-256, version-tag it.**
5. **Mismatch is an alert**, never a silent merge.
6. Short hashes (<= 64 bits) are unsafe at scale.
7. **Same scope** in API, sink and replay.
8. Pick id type for **index locality**, dedup rule for **correctness**.

### Which key, quickly

```
producer can send an id ........... natural event_id (+ payload_hash)
source has its own id/position .... derive uuidv5 from it
no id, content truly identifies ... content hash (SHA-256, canonical, versioned, flagged)
none of the above ................. make the effect idempotent another way, or require an id
```

# Dedup Stores: Redis vs a Postgres Unique Constraint

_Idempotency note 3 of 4 in the Stage 3 learning notes. Read idempotency notes 1-2 first. A **dedup store** is the durable or semi-durable memory that remembers "this identity was already seen". This note compares the two stores the Stage 3 plan names, Redis (`SET key value NX EX ttl`) and a Postgres unique constraint, in depth: how each works internally, what each guarantees, and above all **the exact failure window of each**. It ends with how to combine them and how to size them. It supports S3-F1, S3-F2, S3-F3 and the Stage 3 question "how much throughput will dedup cost?"._

**No labs here.** All numbers are rules of thumb or defaults to confirm on the versions you run; none were measured in this session. Behavior descriptions are standard documented Redis and PostgreSQL behavior.

## 1. TL;DR

- A dedup store answers "have I seen this identity?" **atomically** and **durably enough**. Two properties matter: **atomic claim** (no race between check and write) and **retention** (how long and how reliably it remembers).
- **Redis** (`SET key value NX EX ttl`): in-memory, **very fast** (sub-millisecond), one atomic command claims a key and sets its expiry. But its memory is **bounded in time** (the TTL), **bounded in space** (RAM, eviction), and **loseable** (restart without persistence, async-replication failover, `FLUSHALL`, eviction). It gives a **window**, not a guarantee.
- **Postgres unique constraint**: on-disk, **durable**, **transactional**, with **no expiry** and **no eviction**. Slower per operation (milliseconds, WAL, index maintenance), and it grows forever unless you prune. It gives a **guarantee** for as long as the row exists, and a row can live as long as the data.
- The **failure windows**:
  - Redis forgets when: the TTL elapses; the process restarts without persistence or loses the last second (AOF `everysec`); a failover promotes a replica that missed the write; memory pressure evicts the key; someone flushes it.
  - Postgres forgets only when **you delete** the row or drop the constraint. Its failure mode is the other way: **the constraint can be the bottleneck** and **a rolled-back transaction releases the claim** (correctly).
- **Use both**: Redis as a **front filter** (cheap early rejection, fast 202 replay) and the Postgres constraint as the **final guarantee**. EventPulse does exactly this in the Stage 3 design.
- The rule that falls out: **the faster, forgetful layer may only reduce cost; the slower, durable layer must provide correctness.**

> **One-line version:** _Redis remembers fast but not forever; Postgres remembers forever but not as fast; correctness must rest on the one that does not forget._

## 2. The mental model

| Store                          | Analogy                                                                                                                                                                                                                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Redis**                      | A **whiteboard** at the front desk where the receptionist ticks each visitor name. Instant to read and write. It is **wiped** at the end of the day (TTL), when the cleaner comes (restart), when the board is full and old ticks are erased to make room (eviction), or when someone spills coffee (failover loss). |
| **Postgres unique constraint** | A **bound ledger** in the archive. Writing a line takes longer, and a second line with the same name is **refused by the book itself**. Nothing is ever erased unless a clerk explicitly tears out a page.                                                                                                           |

A good office keeps both: the receptionist's whiteboard stops most repeat visitors at the door, the ledger is the legal record.

## 3. What a dedup store must provide

| Property                       | Meaning                                               | Why it matters                                                  |
| ------------------------------ | ----------------------------------------------------- | --------------------------------------------------------------- |
| **Atomic claim**               | "Check and record" is one indivisible step            | No race between two simultaneous duplicates                     |
| **Durability**                 | The record survives crashes and restarts              | The very crash that causes a duplicate must not erase the proof |
| **Retention**                  | Remembers as long as a duplicate may arrive           | Else the window reopens                                         |
| **Capacity**                   | Holds `rate x retention` entries                      | Else it evicts or fails                                         |
| **Latency**                    | Cost on the hot path                                  | Dedup runs per request                                          |
| **Consistency under failover** | A promoted replica has the record                     | Else a failover forgets                                         |
| **Transactional coupling**     | Can the record commit atomically **with the effect**? | Decides whether crash windows exist                             |
| **Cleanup**                    | Old entries are removed without harm                  | Else storage grows unbounded                                    |

The last-but-one property is the deepest difference between the two stores: **the Postgres constraint is part of the same transaction as the effect**; the Redis key is a **separate system** from the effect, so there is always a gap between "recorded in Redis" and "effect done".

## 4. Redis `SET NX EX`: how it works

### 4.1 The command

```
SET idem:{tenant}:{key} "<value>" NX EX 86400
```

| Part            | Meaning                                                                                        |
| --------------- | ---------------------------------------------------------------------------------------------- |
| `SET key value` | Store a string                                                                                 |
| `NX`            | Only if the key does **N**ot e**X**ist                                                         |
| `EX 86400`      | Expire after 86,400 seconds (`PX` for milliseconds)                                            |
| Return          | `OK` if set (you own the claim); `nil` if the key already existed (someone else claimed first) |

Two facts that make it a correct claim primitive:

1. **Atomic.** Redis executes commands on a single thread, so `SET ... NX EX` (check, set value, set expiry) happens as one indivisible command. Setting the value and the expiry in **separate** commands (`SETNX` then `EXPIRE`) is **not** atomic: a crash between them leaves a key that never expires. Always use the single combined form.
2. **Fast.** An in-memory hash table operation; typical round trip is dominated by network (hundreds of microseconds on a LAN).

### 4.2 Typical use in the API

```
claim := SET idem:{tenant}:{key} {IN_PROGRESS,...} NX EX 86400
if claim == OK:            process; then SET key {DONE,...} XX KEEPTTL
else:                      GET key and decide (replay / 409 / 422)
```

`XX` (only if exists) and `KEEPTTL` keep the update from resurrecting an expired key or changing its expiry. Updates that must be conditional on the previous value (compare-and-set) need a **Lua script** or `WATCH/MULTI`, because plain commands are not conditional on value.

### 4.3 What Redis gives you

- A fast, atomic, **time-bounded** claim.
- Automatic cleanup (expiry), no pruning job.
- Rich enough values (hash, JSON string) for state, hash and response.

### 4.4 What Redis does **not** give you

- Durability equal to a database.
- Transactional coupling with Postgres or Kafka.
- Unbounded memory.

## 5. Redis: every way an entry can disappear or be wrong

This is the **failure window** inventory. Each row is a way for "the key is not there" to be **false** (the event _was_ seen), which causes a duplicate to be treated as new.

| #   | Cause                                                    | When it happens                                                                                                         | Size of the window                                                                                                           |
| --- | -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| R1  | **TTL expiry**                                           | The key is older than `EX`                                                                                              | Everything older than the TTL (by design). A client retrying after the TTL is a "new" request                                |
| R2  | **Restart without persistence**                          | Redis process or node restarts with no RDB/AOF                                                                          | **All keys**                                                                                                                 |
| R3  | **Restart with RDB only**                                | Snapshots every N minutes (for example `save 3600 1 300 100 60 10000`); crash loses writes since the last snapshot      | Up to the snapshot interval, possibly minutes to an hour                                                                     |
| R4  | **AOF with `appendfsync everysec`** (the common default) | Crash or power loss                                                                                                     | Up to about **1 second** of writes (and the OS buffer if fsync lags)                                                         |
| R5  | **AOF with `appendfsync always`**                        | Crash                                                                                                                   | Near zero, at a large write-latency cost                                                                                     |
| R6  | **Asynchronous replication failover**                    | Primary acks a write, dies before the replica receives it; a replica is promoted (Sentinel or Cluster)                  | The replication lag at failure time, often milliseconds to seconds; larger under load or network trouble                     |
| R7  | **Eviction under memory pressure**                       | `maxmemory` reached with policy such as `allkeys-lru` or `allkeys-lfu` (and `volatile-*` policies evict keys with TTLs) | Any key, **unpredictably**. With `noeviction`, writes **fail** instead (a different problem: the claim errors)               |
| R8  | **Operator action**                                      | `FLUSHALL`, `FLUSHDB`, key deletion by pattern, restore of an old backup                                                | Everything                                                                                                                   |
| R9  | **Cluster resharding / slot migration edge cases**       | Moving slots between nodes                                                                                              | Small, but keys can be briefly unavailable (errors)                                                                          |
| R10 | **Clock or TTL surprise**                                | TTL set wrongly (milliseconds vs seconds), or `EXPIRE` not applied because of a non-atomic `SETNX` then `EXPIRE`        | A key that lives too short, or never expires (memory leak)                                                                   |
| R11 | **Network partition / client timeout**                   | The client's `SET` timed out; Redis may or may not have applied it                                                      | Ambiguity again (Two Generals, delivery-semantics note 2): a retry of the `SET` can see `nil` for **your own** earlier claim |

### 5.1 R11 deserves a note

If the `SET NX` **response is lost**, the key exists in Redis but the client does not know it won. On retry it gets `nil`, reads the value, and finds `IN_PROGRESS` with **its own** token. Store a **unique owner token** (a random id per attempt) in the value so the claimant can recognize "this is mine" and proceed rather than waiting for the lease. Without the token it would see an IN_PROGRESS stranger and return 409 until the lease expires.

### 5.2 The Redis consistency statement

> Redis is an **availability- and latency-optimized cache-grade store**. Its replication is **asynchronous** and its default durability is **best-effort**. `WAIT` can block until N replicas acknowledge a write, reducing but not eliminating the loss window (the primary can still fail before the `WAIT` returns, and replicas may not have fsynced). Treat any dedup guarantee on Redis alone as **probabilistic**.

### 5.3 What the loss means for the pipeline

Each R-row reopens the duplicate window **at the API layer only**. Duplicate requests then flow to Kafka and the sink. If the sink has its unique constraint, **no incorrectness results**, only extra work and a visible rise in absorbed duplicates. If the sink has no constraint, the duplicates are stored.

## 6. Redis: operational detail

| Topic                        | Guidance                                                                                                                                                                                                                                                                    |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Persistence choice**       | For dedup, **AOF `everysec`** is the usual compromise; RDB alone loses too much; `always` hurts latency. Since Redis is not the guarantee, do not over-pay for durability                                                                                                   |
| **Eviction policy**          | Prefer **`noeviction`** or `volatile-ttl` and size memory generously, so the failure is **loud** (write errors, alerts) rather than **silent** (evicting dedup keys). `allkeys-lru` silently turns the dedup store into a cache                                             |
| **Fail-open or fail-closed** | If Redis is down, should ingest **accept** (fail-open: risk duplicates, absorbed by the sink) or **reject** (fail-closed: protects Redis-level semantics, hurts availability)? With a sink constraint, **fail-open is usually right** for events; for payments, fail-closed |
| **Timeouts**                 | A short command timeout (tens of ms). A slow Redis must not stall the API; degrade to fail-open                                                                                                                                                                             |
| **Separate instance**        | Keep dedup keys on an instance (or DB) separate from caches so a cache eviction storm cannot evict dedup keys                                                                                                                                                               |
| **Memory per key**           | Overhead of roughly 50-100 bytes per key plus key and value size; measure with `MEMORY USAGE` on realistic entries                                                                                                                                                          |
| **Key design**               | Short key names, short values; avoid storing full responses; use hashes sparingly (small hashes use compact encodings)                                                                                                                                                      |
| **Hot keys**                 | A single key hammered by many duplicates is fine (single-threaded atomic ops), but a hot **shard** in cluster mode may bottleneck                                                                                                                                           |
| **Cluster hash tags**        | `idem:{tenant}:...` with braces forces keys of one tenant to one slot, useful for multi-key scripts, but risks a hot slot for a huge tenant                                                                                                                                 |
| **Expiry mechanics**         | Redis expires keys lazily on access plus an active sampling cycle; expired keys can linger briefly in memory. Memory is not freed at the exact TTL                                                                                                                          |
| **Monitoring**               | `expired_keys`, `evicted_keys`, `used_memory`, `keyspace_hits/misses`, replication lag, latency                                                                                                                                                                             |

## 7. Postgres unique constraint: how it works

### 7.1 The mechanism

```sql
CREATE TABLE events (
  event_id   uuid        PRIMARY KEY,       -- creates a unique B-tree index
  tenant_id  text        NOT NULL,
  ...
);

INSERT INTO events (...) VALUES (...)
ON CONFLICT (event_id) DO NOTHING
RETURNING event_id;
```

A `PRIMARY KEY` or `UNIQUE` constraint is enforced by a **unique B-tree index**. On insert Postgres:

1. Inserts the heap tuple and probes the unique index for the key.
2. If an **existing committed** entry has the same key: with `ON CONFLICT DO NOTHING` the insert is skipped; without it, a unique-violation error is raised.
3. If an **uncommitted** entry from another in-flight transaction has the same key, the inserter **waits** for that transaction to finish. If it **commits**, this insert conflicts; if it **rolls back**, this insert proceeds.

Point 3 is the correctness core: the index acts as the **serialization point** for concurrent duplicates, under the default `READ COMMITTED` isolation, with no explicit locking by you.

### 7.2 What Postgres gives you

- **Durability**: the entry is in WAL and fsynced at commit (default `synchronous_commit=on`), replicated if you use synchronous replication.
- **Atomic with the effect**: the dedup entry **is** the effect row (or is in the same transaction as it). There is **no gap** between "recorded" and "applied".
- **No expiry, no eviction**: the claim lasts as long as the row.
- **Rollback safety**: if the transaction aborts, the claim vanishes with it, which is correct (nothing was applied).
- **Multi-row atomic claims**: a batch of rows in one statement is claimed in one transaction (the EventPulse sink batches this way).

### 7.3 What Postgres does **not** give you

- Sub-millisecond speed at very high request rates for a **per-request** claim (it is fast, but each claim involves WAL and index work).
- Automatic cleanup (you prune).
- Protection against a **dropped constraint** or a **bulk load that bypasses it**.

## 8. Postgres: failure windows and costs

The Postgres store has **no "forgets" window** while the row exists, but it has other failure modes and costs.

| #   | Situation                                                           | Effect                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| P1  | **Transaction rolled back**                                         | The claim is released; a retry succeeds. Correct, but note it happens **after** you may have told another system something                                                                                   |
| P2  | **Crash before COMMIT**                                             | Nothing durable; the retry proceeds. Correct                                                                                                                                                                 |
| P3  | **Crash after COMMIT, before you tell the caller**                  | The row exists; the retry hits the conflict and no-ops. Correct (Two Generals resolved by the constraint)                                                                                                    |
| P4  | **Async replica failover** (with asynchronous physical replication) | A promoted standby can lack the most recent commits (the replication lag), so those entries are **forgotten**, same shape as R6 but typically a narrower window, and eliminated with synchronous replication |
| P5  | **Restore from backup / PITR**                                      | Entries after the restore point vanish; replays can then re-insert                                                                                                                                           |
| P6  | **Constraint dropped or table swapped**                             | The experiment-style failure (a table without a primary key): duplicates accumulate silently                                                                                                                 |
| P7  | **Pruned too early**                                                | If you delete dedup rows (an inbox table) that are younger than the replay horizon, repeats re-apply                                                                                                         |
| P8  | **Wrong constraint columns**                                        | `UNIQUE (event_id)` vs a lookup by `(tenant_id, event_id)`; or a nullable column in a unique index (nulls are distinct by default, so `NULL` keys never conflict)                                            |
| P9  | **Partitioned table without partition-key in the unique key**       | Postgres will not allow the constraint, or uniqueness is only per-partition                                                                                                                                  |
| P10 | **Deadlocks and lock waits**                                        | Two transactions inserting overlapping key sets in different orders can deadlock; sort keys within a batch to avoid it                                                                                       |
| P11 | **Index bloat and size growth**                                     | Large unique indexes (random UUIDs) cause page splits, cache misses and slower inserts; the table never shrinks without maintenance                                                                          |
| P12 | **Write amplification and contention**                              | Every claim writes WAL and the index; at extreme rates the primary's write throughput caps dedup throughput                                                                                                  |
| P13 | **Dead tuples from conflict path**                                  | A conflicting `DO NOTHING` insert can still consume a speculative heap tuple that becomes dead and needs vacuum; a high duplicate rate raises vacuum work                                                    |

### 8.1 Notes on P8 (nullable unique keys)

In PostgreSQL a unique index treats `NULL` values as **distinct** (unless `NULLS NOT DISTINCT`, PostgreSQL 15+). A composite key with a nullable column silently allows duplicates. Make dedup columns `NOT NULL`.

### 8.2 The cost model

| Cost                | Source                                         | Magnitude (rule of thumb)                                                              |
| ------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------- |
| Index lookup/insert | B-tree descent                                 | Microseconds when cached                                                               |
| WAL write and fsync | Commit                                         | Dominates latency per transaction; amortized by **batching many rows per transaction** |
| Index size          | `rows x (key size + overhead)`                 | A uuid key is 16 bytes plus tuple overhead; tens of bytes per entry                    |
| Vacuum              | Dead tuples on the conflict path and deletions | Grows with duplicate rate and pruning                                                  |
| Lock waits          | Concurrent same-key inserts                    | Only on true duplicates racing                                                         |

**Batching is the main lever**: a per-row transaction pays one commit each; one transaction for hundreds of rows pays one commit total. This is why the EventPulse sink does one multi-row `INSERT ... ON CONFLICT DO NOTHING` per chunk and measures the cost of dedup relative to the no-dedup variant.

## 9. Postgres: operational detail

| Topic                   | Guidance                                                                                                                                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Primary key type**    | `uuid` (16 bytes) is compact; text uuid doubles it. Time-ordered ids (UUIDv7) improve index locality over random v4                                                                                                                                                |
| **Pruning**             | For a separate dedup/inbox table, delete in **batches** by age (`DELETE ... WHERE created_at < now() - interval ...` with a `LIMIT` via ctid or id range) to avoid long locks and bloat; or use **time partitions** and drop whole partitions (instant, no vacuum) |
| **Partition + unique**  | If you partition by time, include the partition key in the unique key, or keep the dedup constraint in a **non-partitioned** key table                                                                                                                             |
| **Unbounded growth**    | The events table is the data; the key _is_ a column, growing with it. Retention of old data removes the dedup memory of old ids, which is fine if replays do not reach that far                                                                                    |
| **Replication**         | For zero-loss failover use synchronous replication for the dedup-critical database, accepting commit latency                                                                                                                                                       |
| **Isolation**           | `READ COMMITTED` suffices for `ON CONFLICT`; do not raise isolation just for dedup                                                                                                                                                                                 |
| **Vacuum / autovacuum** | Tune for high insert + conflict rates; monitor dead tuples and index bloat                                                                                                                                                                                         |
| **Batch ordering**      | Sort rows by key inside a batch to reduce deadlock risk between concurrent batches                                                                                                                                                                                 |
| **Statistics**          | `attempted - inserted` from `RETURNING` gives the duplicate count without extra queries                                                                                                                                                                            |
| **Monitoring**          | Insert rate, conflict rate, index size, bloat, WAL volume, lock waits                                                                                                                                                                                              |

## 10. Side-by-side comparison

| Dimension                               | Redis `SET NX EX`                                                | Postgres unique constraint                                               |
| --------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **Primary role**                        | Front filter / claim lease                                       | Final guarantee                                                          |
| **Storage**                             | RAM                                                              | Disk (WAL + heap + index)                                                |
| **Latency per claim**                   | ~0.1-1 ms (network-bound)                                        | ~1-10 ms single; amortized to microseconds per row in batches            |
| **Throughput**                          | Hundreds of thousands ops/s per node                             | Tens of thousands of rows/s per primary with batching, bounded by WAL/IO |
| **Atomic claim**                        | Yes (`SET NX`)                                                   | Yes (unique index)                                                       |
| **Atomic with the effect**              | **No** (separate system)                                         | **Yes** (same transaction)                                               |
| **Durability**                          | Best-effort (AOF everysec / RDB)                                 | Full (WAL fsync), configurable                                           |
| **Replication loss on failover**        | Likely (async)                                                   | Possible with async standby; none with synchronous                       |
| **Expiry**                              | Built-in TTL                                                     | None (you prune)                                                         |
| **Retention window**                    | Bounded by TTL and RAM                                           | Unbounded                                                                |
| **Eviction risk**                       | Yes (`maxmemory`)                                                | No                                                                       |
| **Capacity cost**                       | RAM (expensive per GB)                                           | Disk (cheap per GB)                                                      |
| **Stores rich state (response, lease)** | Easy (value, hash)                                               | Possible (columns, jsonb)                                                |
| **Race handling**                       | `NX`                                                             | Index serialization                                                      |
| **Crash behavior**                      | May forget                                                       | Remembers committed                                                      |
| **Typical failure mode**                | **Forgets** (false negative: duplicate treated as new)           | **Slows down** or bloats; rare forgetting                                |
| **Detects "different payload"**         | Via stored hash in the value                                     | Via stored hash column                                                   |
| **Best at**                             | Cheap early rejection, short windows, replay of recent responses | Permanent correctness, large windows                                     |
| **Wrong to use as**                     | The only guarantee                                               | A per-request hot-path rate limiter or lock manager at extreme rates     |

## 11. The failure window table, in one place

The requested "know the failure window of each", compactly.

| Store                                    | Window in which a seen identity may be treated as new | Mitigation                                                            |
| ---------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------------------- |
| **Redis, TTL**                           | Any duplicate arriving **after** the TTL              | Choose TTL above the retry horizon; sink constraint behind it         |
| **Redis, restart w/o persistence**       | The entire keyspace                                   | Enable AOF; accept as a window; sink behind it                        |
| **Redis, RDB only**                      | Up to the snapshot interval                           | Use AOF                                                               |
| **Redis, AOF everysec**                  | About 1 s of writes                                   | `always` (slow) or accept                                             |
| **Redis, async failover**                | Replication lag (ms to s)                             | `WAIT`, or accept                                                     |
| **Redis, eviction**                      | Any key, any time under memory pressure               | `noeviction`, size memory, separate instance, alert on `evicted_keys` |
| **Redis, flush / restore**               | Everything / since the backup                         | Access control; accept                                                |
| **Redis, lost `SET` response**           | One request                                           | Owner token in the value                                              |
| **Postgres, committed row**              | **None** while the row exists                         | n/a                                                                   |
| **Postgres, async standby failover**     | Replication lag                                       | Synchronous replication for the critical DB                           |
| **Postgres, restore/PITR**               | Since the restore point                               | Backups discipline; replay tooling idempotent                         |
| **Postgres, pruned row**                 | Anything older than the prune horizon                 | Prune horizon >= max replay age                                       |
| **Postgres, constraint absent or wrong** | Everything affected                                   | Migration checks, tests, negative control                             |

Summary in one sentence: **Redis has a window measured in seconds-to-hours and by design; Postgres has a window of zero while the row exists, and only the windows that you create (pruning, restore, constraint mistakes).**

## 12. Combining them: layered dedup

### 12.1 The standard arrangement

```
 request ──► [ Redis SET NX EX ] ──► produce to Kafka ──► [ sink: INSERT ... ON CONFLICT DO NOTHING ]
                 front filter                                        final guarantee
           cheap, fast, bounded                                  durable, atomic with the effect
```

Roles:

| Layer               | Purpose                                                                                                                                               | If it fails                                      |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Redis               | Reject most duplicate requests early; replay recent responses; protect Kafka and Postgres from retry storms; detect payload mismatch with a clear 422 | Duplicates leak downstream (costlier, not wrong) |
| Postgres constraint | Make storage correct regardless                                                                                                                       | **Incorrectness** (duplicates stored)            |

### 12.2 Why not only Postgres at the API?

You could claim in Postgres at the API (insert into an idempotency table, then produce). It is durable, but: every request pays a DB round trip and WAL write on the hot path; retry storms hit the primary database; and you still have a gap between the DB claim and the Kafka produce (two systems). Redis absorbs the repeat traffic more cheaply; the DB constraint at the sink is already required anyway.

### 12.3 Why not only Redis?

Because of section 5: it is a window. Correctness cannot depend on a store that can forget the very key whose duplicate is arriving.

### 12.4 Behavior under Redis outage

| Policy      | Behavior                               | Result with the sink constraint                   |
| ----------- | -------------------------------------- | ------------------------------------------------- |
| Fail-open   | Skip the Redis check, process normally | More duplicates reach the sink; absorbed; counted |
| Fail-closed | 503 until Redis returns                | No leaks, but availability loss                   |

State the policy in the guarantees document. For event ingest, fail-open with an alert is the natural choice because the guarantee does not depend on Redis.

### 12.5 Write-through ordering at the API

The order of "claim in Redis" and "produce to Kafka" decides the failure shape:

| Order               | Crash between                  | Outcome                                                                    |
| ------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| Claim, then produce | Claim exists, nothing produced | Retries see IN_PROGRESS until the lease lapses; **no loss** after takeover |
| Produce, then claim | Message in Kafka, no claim     | Retry produces again: duplicate in Kafka; sink absorbs                     |

Claim-then-produce with a lease is the safer order, because the failure leaves a recoverable claim instead of an untracked duplicate.

## 13. Other dedup stores

| Store                                           | Pros                                                                                              | Cons                                                       | Fit                                                       |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | --------------------------------------------------------- |
| **Postgres inbox table**                        | Same transaction as the effect; SQL; durable                                                      | Growth and pruning; DB load                                | Non-idempotent effects, small to medium volume            |
| **DynamoDB / Cassandra conditional put**        | Horizontally scalable; TTL; conditional writes (`attribute_not_exists`, lightweight transactions) | Operational and cost model; eventual consistency choices   | Very high rate, multi-region                              |
| **In-process LRU/Set**                          | Zero latency                                                                                      | Lost at restart; per-instance only                         | Micro-optimization in front of another store, never alone |
| **Kafka log compaction**                        | The topic itself holds the latest per key                                                         | Not a point-lookup claim                                   | Changelog state, not request-time dedup                   |
| **RocksDB / embedded KV (stream processors)**   | Local, fast, with a changelog for recovery                                                        | Tied to the stream framework                               | Stage 4 stream dedup                                      |
| **Object-store marker files**                   | Cheap, durable                                                                                    | Slow, eventual semantics on some stores                    | Batch jobs                                                |
| **Distributed lock (Redlock, ZooKeeper, etcd)** | Mutual exclusion                                                                                  | Not a record of "done"; locks expire; subtle safety issues | Avoid for dedup; use a claim with state                   |

## 14. Bloom filters and probabilistic dedup

A **Bloom filter** answers "possibly seen" or "definitely not seen" using a compact bit array.

| Property        | Value                                                    |
| --------------- | -------------------------------------------------------- |
| False negatives | **None** (if it says "not seen", it is new)              |
| False positives | Yes, tunable (for example 1% with ~9.6 bits per element) |
| Deletion        | Not supported by the basic form                          |
| Memory          | Tiny compared with storing keys                          |

Use: as a **pre-filter** to skip an expensive lookup for the common "definitely new" case; when it says "possibly seen", confirm in the real store (Postgres). Never use a Bloom filter **alone** to drop events: a false positive would **silently discard a genuinely new event** (a loss). Dedup by dropping must be exact; probabilistic structures only accelerate the "new" path. Variants: counting Bloom filters (deletable), cuckoo filters; Redis offers these via the Bloom module (RedisBloom).

## 15. Capacity and cost estimation

### 15.1 Redis memory

```
live keys = request rate x TTL
memory   ~= live keys x (key bytes + value bytes + ~64-100 overhead)
```

Example: 3,000 events/s, TTL 24 h, 120-byte entry average:

```
live keys = 3,000 x 86,400 = 259,200,000
memory    ~= 259.2M x ~(120 + 80) bytes  ~= 52 GB
```

That is a large Redis. Options: shorten the TTL, store a **hash only** (for example 16 bytes) instead of the response, dedup only keys that carry side effects, or accept Postgres as the only layer for high-volume, low-risk streams. Do this arithmetic **before** promising a 24 h window.

### 15.2 Postgres index size

```
entries = total events retained
index   ~= entries x (key bytes + ~20-30 index overhead)
```

For 1 billion uuid keys: 16 + ~28 bytes ~= 44 GB of primary-key index on top of table data. The index must fit mostly in memory to keep inserts fast; otherwise insert latency rises (random uuid keys touch random pages). Time-ordered ids reduce the working set to recent pages.

### 15.3 Throughput cost of dedup (the Stage 3 question)

Components of the cost of `ON CONFLICT DO NOTHING` versus a plain insert:

| Component                      | Effect                                          |
| ------------------------------ | ----------------------------------------------- |
| Unique index probe on each row | Small CPU and cache cost                        |
| Index maintenance on insert    | Already paid if the table has a primary key     |
| Conflict path                  | Wasted heap work and later vacuum on duplicates |
| Lock waits                     | Only under true concurrent duplicates           |

The honest answer is **measure it**: compare the same workload against a table with and without the constraint (the repo's no-dedup experiment variant exists for this), at several duplicate ratios, and report throughput, latency and vacuum activity.

## 16. Choosing a store

```
Is a duplicate costly enough to need a durable guarantee (money, storage correctness)?
 ├─ yes -> Postgres constraint (or equivalent durable conditional write) is mandatory
 │         Add Redis in front if request volume or retry storms are significant
 └─ no  -> Redis alone may be enough (best-effort dedup, e.g. notification coalescing)

Do you need fast replay of recent responses and clear 409/422 semantics?  -> Redis state record
Is the effect non-idempotent (balance, email)?                            -> Postgres inbox in the effect's transaction
Retry horizon longer than affordable RAM?                                 -> Postgres (or a TTL'd durable store)
Extreme rate, multi-region?                                               -> a conditional-write store (DynamoDB-style)
```

## 17. Observability of the dedup layer

| Metric                                               | Reveals                                                                    |
| ---------------------------------------------------- | -------------------------------------------------------------------------- |
| Redis claim `OK` vs `nil` rate                       | Duplicate request ratio at the API                                         |
| Redis errors / timeouts / fail-open count            | Degradation (duplicates may leak)                                          |
| Redis `evicted_keys`, memory, expired keys           | Silent windows (R1, R7)                                                    |
| Mismatch (422) count                                 | Client bugs                                                                |
| Sink `attempted`, `inserted`, `attempted - inserted` | Duplicates that **escaped** the API layer; a measure of how leaky Redis is |
| Sink conflict ratio trend                            | Spikes: crashes, rebalances, replays, or a Redis incident                  |
| Postgres index size, bloat, dead tuples, lock waits  | Cost and risk (P7-P13)                                                     |
| Dedup-latency histograms (Redis call, DB insert)     | Cost on the hot path                                                       |

A useful derived signal: **if the sink's absorbed-duplicate rate rises while the API's Redis hit rate falls**, Redis is forgetting (eviction, restart, failover).

## 18. Testing the failure windows

Describing designs only; none run here.

| Test                                                       | Expected                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| Repeat within TTL                                          | API replays; one event                                                     |
| Repeat after TTL (short test TTL)                          | Treated as new at the API; the sink keeps one row                          |
| Flush Redis between request and retry                      | Duplicate reaches Kafka; the sink keeps one row                            |
| Kill and restart Redis (with and without AOF)              | Window observed; sink still correct                                        |
| Fail-open: stop Redis; send duplicates                     | Requests accepted; sink absorbs; alert fires                               |
| Eviction: set a tiny `maxmemory` with `allkeys-lru`        | Keys evicted; windows reopen (and with `noeviction`, writes error loudly)  |
| Lost `SET` response (proxy drops it)                       | Owner token lets the retry recognize its own claim                         |
| Concurrent duplicates at the sink (many writers, same ids) | One row per id; no deadlock with sorted batches                            |
| Drop the primary key on a copy (negative control)          | Duplicates appear, proving the constraint is what protects storage         |
| Prune horizon test                                         | A replay older than the horizon re-applies, matching the documented window |

## 19. EventPulse decisions

| Decision              | Choice                                                               | Reason                                                      |
| --------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- |
| Final guarantee       | Postgres `PRIMARY KEY` + `ON CONFLICT DO NOTHING` on the sink        | Durable, atomic with the effect, unbounded                  |
| Front filter          | Redis `SET idem:{tenant}:{key} ... NX EX 86400` at the API (Stage 3) | Cheap early rejection, replay of recent 202s, clear 409/422 |
| Redis eviction policy | `noeviction` (or volatile with alerts), separate from cache data     | Make windows loud, not silent                               |
| Redis failure policy  | Fail-open with a metric and alert                                    | Correctness does not depend on Redis                        |
| Redis persistence     | AOF `everysec`                                                       | Reasonable; it is a window anyway                           |
| Order at the API      | Claim first (with lease), then produce                               | Recoverable failure shape                                   |
| Duplicate visibility  | Sink counts `attempted - inserted`; API counts replays and 422s      | S3-F3                                                       |
| Capacity              | Compute `rate x TTL x entry size` before fixing the TTL              | Section 15                                                  |
| Sink performance      | Batch rows per transaction; sort keys in a batch                     | Amortize commit; avoid deadlocks                            |
| Negative control      | Keep the no-PK table variant for tests and the cost experiment       | Prove the constraint matters                                |

## 20. Common confusions

1. **"Redis NX is a lock, so it is exactly-once."** It is an atomic claim with a forgetful memory; it is not coupled to the effect.
2. **"Redis is durable because I enabled AOF."** AOF `everysec` still loses up to about a second, and failover with async replication loses more.
3. **"TTL expiry is a Redis failure."** It is the designed window; the failure is forgetting to have a durable layer behind it.
4. **"Postgres dedup is too slow for the hot path."** Per-row it is cheap when batched; per-request transactions are the slow part.
5. **"A unique violation means the system is broken."** It means the constraint caught a duplicate; with `ON CONFLICT` it is not even an error.
6. **"Nullable columns are fine in a unique key."** Nulls are distinct, so duplicates slip through.
7. **"`allkeys-lru` is a sensible default for a dedup Redis."** It silently evicts your keys; use `noeviction`.
8. **"A Bloom filter can drop duplicates."** It has false positives; a drop would lose a real event.
9. **"A distributed lock gives idempotency."** A lock gives mutual exclusion for a time; it does not record that the work was done.
10. **"Two stores means double the correctness."** One store provides correctness; the other provides efficiency.

## 22. Cheat sheet

### Glossary

| Term                     | Meaning                                                    |
| ------------------------ | ---------------------------------------------------------- |
| Dedup store              | Durable or semi-durable memory of seen identities          |
| `SET NX EX`              | Atomic set-if-absent with expiry (Redis)                   |
| Claim                    | Reserving an identity atomically                           |
| Window                   | Interval in which a seen identity may be treated as new    |
| Eviction                 | Redis removing keys under memory pressure                  |
| AOF / RDB                | Redis persistence: append-only log / periodic snapshot     |
| `WAIT`                   | Redis command to block until replicas ack a write          |
| Unique index             | B-tree enforcing uniqueness; the Postgres claim primitive  |
| `ON CONFLICT DO NOTHING` | Skip rows whose key already exists                         |
| Fail-open / closed       | Accept / reject when the dedup store is unavailable        |
| Inbox                    | Table of applied ids written with the effect               |
| Bloom filter             | Probabilistic set with false positives, no false negatives |

### Rules

1. **Atomic claim**, always; never check then act.
2. **Redis = window; Postgres = guarantee.**
3. `SET key v NX EX ttl` in **one** command.
4. Make Redis failures **loud**: `noeviction`, alerts, separate instance.
5. **Fail-open** only because a durable constraint sits behind.
6. Size `rate x TTL x entry` before choosing a TTL.
7. Batch and sort keys for Postgres dedup throughput.
8. Never drop events on a probabilistic filter alone.
9. Prove with a negative control that the constraint matters.

### The comparison in one picture

```
            speed     durability   window            atomic with effect   role
Redis NX     ████       ██          TTL/restart/…      no                  front filter
Postgres UQ  ██         ████        none (unbounded)   YES                 guarantee
```

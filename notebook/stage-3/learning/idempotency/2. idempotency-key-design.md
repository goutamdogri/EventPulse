# Idempotency Key Design

_Idempotency note 2 of 4 in the Stage 3 learning notes. Read idempotency note 1 (fundamentals) and delivery-semantics note 4 first. This note designs the **key** itself and the **contract** around it: who generates it, its scope (tenant plus key), its lifetime (TTL), what is stored with it, the full state machine of a key record, and what must happen when the same key arrives with a different payload. It supports S3-F1 directly and feeds the delivery guarantees document (S3-F9)._

## 1. TL;DR

- An **idempotency key** is a unique identifier that the **client** attaches to one **logical operation** so the server can recognize repeats of it.
- **Who:** the **client (the origin)**, once, **before the first attempt**, reused on every retry. A key minted by the server per request is useless for deduplicating the client's own retries.
- **Scope:** the uniqueness domain is **`(tenant, key)`**, not `key` alone. Different tenants may reuse the same string without colliding, and one tenant can never probe or hijack another tenant's keys.
- **Lifetime:** the key is remembered for a **TTL** that must exceed the longest realistic retry horizon of clients (commonly 24 hours at the API layer). After expiry the key is treated as new at the API; the **durable sink constraint** still protects storage.
- **Payload binding:** store a **fingerprint (hash) of the request** with the key. The **same key with a different payload is a client bug** and must be **reported (HTTP 422)**, never silently accepted as a duplicate or processed as new.
- **Record, not just a flag:** the stored record carries **state** (IN_PROGRESS or DONE), the **request hash**, the **stored response**, and timestamps, so repeats can be answered faithfully and crashes recovered.
- **Concurrency:** claiming a key must be **one atomic operation** (Redis `SET NX EX`, or a Postgres `INSERT ... ON CONFLICT`). In-flight duplicates get a defined answer (409 with `Retry-After`, or a short wait).

> **One-line version:** _The client mints the key once per logical operation; the server scopes it by tenant, binds it to the payload, remembers it for longer than any retry, and answers repeats with the original result._

## 2. The mental model

An **airline luggage tag**.

| Luggage                                                                                            | Idempotency key                                       |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| The tag is printed **at check-in**, before the bag travels                                         | Key minted by the client **before the first attempt** |
| The same tag stays on the bag through every transfer                                               | The same key on **every retry**                       |
| The airline's tag number is only meaningful **within that airline**                                | Scope: **(tenant, key)**                              |
| Two different bags can never legitimately carry the same tag; if they do, an agent raises an alarm | Same key, **different payload** = a reported conflict |
| Tags are archived for a while, then reused by the system                                           | **TTL**                                               |
| The desk can tell "this bag is still on the belt" from "this bag has arrived"                      | **IN_PROGRESS** vs **DONE**                           |

If the **airport** printed a fresh tag every time the bag was scanned, tracking would be impossible. That is the server-generated-key anti-pattern.

## 3. What a key is for

A key lets a server answer one question about an incoming request: **"Is this a repeat of something I already accepted, started, or rejected?"**

The three answers need different handling:

| Answer                                 | Meaning                            | Action                   |
| -------------------------------------- | ---------------------------------- | ------------------------ |
| **Never seen**                         | New operation                      | Claim and process        |
| **Seen, finished**                     | Duplicate of a completed operation | Replay the stored result |
| **Seen, in progress**                  | Duplicate of a running operation   | 409/wait                 |
| **Seen, but with a different payload** | Client bug (key reuse)             | 422                      |

Keys are **not** authentication, **not** ordering tokens, **not** database primary keys of resources (though in EventPulse the `event_id` plays both the key and the stored row id; section 17 explains the trade-off).

## 4. Who generates the key

### 4.1 The rule

**The client generates the key**, because only the client knows what a "retry" is. The client decides "this POST is the same logical request as that POST".

### 4.2 Why not the server

| Server mints key per request        | Consequence                                                                                              |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Request 1 gets key A, response lost | Client retries; the server sees request 2 and mints key B. The server cannot link A and B. **No dedup.** |

A server-assigned id **is** useful as the resource's identity afterward (the order number returned in the response). It simply cannot serve as the **dedup** key.

### 4.3 Exceptions and variants

- **Derived by the client from stable business data**, for example `order-{orderId}-payment`. Natural, reproducible after a client restart, and no need to persist a random value (note 4 covers natural keys).
- **Minted by the first trusted service** in your own system when the original client cannot (for example a legacy sender): that service becomes the "origin", and it must **persist the key before the first attempt** downstream.
- **Generated by an SDK**: the SDK mints at the call site and reuses it across its internal retries. It must also let callers **supply their own** (needed when the retry happens after a process restart).

### 4.4 Persist before sending

A client that mints the key **in memory** and then crashes loses it; the restarted client mints a new key and the request is no longer recognizable. For operations whose duplicates cost money, the client **writes the key to durable storage before the first attempt** (for example inside the same DB transaction that records the intent), then sends it.

## 5. Key format and entropy

| Choice         | Recommendation                                                                                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Type           | Opaque string, case-sensitive                                                                                                                                           |
| Typical format | UUIDv4, UUIDv7 or ULID; or a deterministic business string                                                                                                              |
| Length         | Bound it (for example <= 255 characters; reject longer) to cap storage and abuse                                                                                        |
| Character set  | Restrict to printable ASCII or a documented set                                                                                                                         |
| Randomness     | Enough that accidental collision between two **different** operations is negligible (122 random bits in UUIDv4)                                                         |
| Predictability | Unpredictable keys prevent guessing **if** scope is weak; with proper tenant scoping predictability is less dangerous, but still avoid sequential integers from clients |

### 5.1 UUIDv4 vs time-ordered ids

- UUIDv4: random, no ordering. In a B-tree index (the Postgres primary key) random inserts touch random pages, causing more page splits and cache churn at high write rates.
- UUIDv7 (RFC 9562): leading **timestamp** bits, so inserts are roughly append-ordered. Better index locality. It does **reveal creation time** in the id and relies on a client clock, so do not use the time part as truth.

For a key you also store in a unique index (EventPulse `event_id`), the locality difference is a real throughput factor on large tables; measure before deciding. Correctness is identical.

### 5.2 Version the format, validate at the edge

Reject malformed keys with 400 at the API. Never let an unbounded string reach the database or Redis.

## 6. Scope: tenant plus key

### 6.1 Why `key` alone is wrong

| Risk                     | Scenario                                                                                                                      |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| **Accidental collision** | Tenant A and Tenant B both use `order-1` (a natural key). B's request is treated as a duplicate of A's.                       |
| **Information leak**     | B sends `order-1`, gets "409 conflict" or a replayed response, and learns that A used that key (or sees A's stored response). |
| **Denial / poisoning**   | B pre-claims A's expected keys so A's real request is rejected.                                                               |

### 6.2 The scoped identity

```
identity = (tenant_id, idempotency_key)        // optionally also (endpoint/operation)
Redis key   : idem:{tenant_id}:{operation}:{key}
Postgres    : PRIMARY KEY (tenant_id, key)   or  UNIQUE (tenant_id, operation, key)
```

Rules:

1. The `tenant_id` comes from the **authenticated identity**, never from a client-supplied body field that could be forged.
2. Include the **operation or endpoint** in the scope when one tenant might reuse a key across different endpoints (`POST /events` vs `POST /exports`). Otherwise a key used for one call blocks a different call.
3. Keep delimiters unambiguous when building composite string keys (`:`). A tenant id containing `:` could otherwise make `a:b` + `c` equal `a` + `b:c`. Validate characters or encode components.

### 6.3 Scope in EventPulse

The current sink constraint is `PRIMARY KEY (event_id)`. If ingest becomes multi-tenant with client-supplied ids, the constraint should become `(tenant_id, event_id)`, **and every lookup and the `ON CONFLICT` target must use the same columns**. The Stage 3 design diagram already specifies `ON CONFLICT (tenant_id, event_id)`. A mismatch (constraint on one column, API check on two) leaves gaps in either direction.

## 7. What is stored with a key

A key is not a bare "seen" flag. A good record:

| Field                                             | Purpose                                                     |
| ------------------------------------------------- | ----------------------------------------------------------- |
| `tenant_id`, `operation`, `key`                   | The scoped identity                                         |
| `request_hash`                                    | Fingerprint of method + path + canonical body (section 9)   |
| `state`                                           | `IN_PROGRESS` or `DONE` (and optionally `FAILED_RETRYABLE`) |
| `response_status`, `response_body` (or a pointer) | The stored original response to replay                      |
| `created_at`                                      | Start of the TTL window and for audit                       |
| `locked_until` / lease expiry                     | When an IN_PROGRESS claim may be taken over (section 13)    |
| `resource_id`                                     | What was created (the event id, order id)                   |
| `attempts` / `last_seen_at`                       | Observability: how many repeats                             |

For a Redis implementation these live in one value (a small JSON or hash) under the scoped key, with the TTL set by `EX`.

### 7.1 Size discipline

Store a **bounded** response (or a reference to the resource and recompute the response), not megabytes per key. At millions of keys a few KB each becomes tens of GB in RAM.

## 8. The key state machine

```
                  claim (atomic)                  complete(result)
   (absent) ───────────────────► IN_PROGRESS ──────────────────────► DONE(result, hash)
        ▲                          │   ▲                                   │
        │  TTL expiry              │   │ lease expired: another request    │ TTL expiry
        │                          │   └──── takes over (re-claims) ◄──────┘ (not allowed from DONE)
        └──────────────────────────┴─────────────────────────────────────── (absent)
                                   │
                                   └─ fail permanently ─► DONE(error result)  (replayed like success)
```

Transitions:

| From        | Event                  | To                                | Notes                                           |
| ----------- | ---------------------- | --------------------------------- | ----------------------------------------------- |
| absent      | first request          | IN_PROGRESS                       | Atomic claim; stores `request_hash` and a lease |
| IN_PROGRESS | same hash arrives      | (unchanged)                       | Reply 409 + `Retry-After` or wait               |
| IN_PROGRESS | different hash arrives | (unchanged)                       | 422 mismatch                                    |
| IN_PROGRESS | work done              | DONE                              | Store response; keep TTL                        |
| IN_PROGRESS | lease expires          | IN_PROGRESS (new owner) or absent | Recovery; requires idempotent effect            |
| DONE        | same hash              | (unchanged)                       | Replay stored response                          |
| DONE        | different hash         | (unchanged)                       | 422 mismatch                                    |
| any         | TTL                    | absent                            | Treated as new                                  |

**Should a permanent failure be stored?** Many payment APIs store and **replay the first result even when it was an error** (a validation failure repeats the same failure). That keeps the contract simple: same key, same answer. Transient server errors (5xx from your own bug) are different: do **not** pin them under the key, release the claim so a retry can try again. Decide, and document.

## 9. Same key, different payload

### 9.1 Why it is a bug and must be reported

The key means "this is the same logical request". If the body differs, either:

- the client **reused a key by mistake** (a bug: two different events share an id), or
- the client **intentionally changed** the request but forgot to change the key.

Two silent behaviors are both wrong:

| Silent behavior                             | Damage                                                                        |
| ------------------------------------------- | ----------------------------------------------------------------------------- |
| Treat as duplicate (ignore the new payload) | The new data is **lost without any signal**; the client believes it was saved |
| Treat as new (process the new payload)      | Defeats idempotency; the key no longer guarantees anything                    |

Correct behavior: **reject with a clear error** (422 Unprocessable, with a body naming the key and the mismatch), **count** it in a metric, and **log** the tenant and key. This turns a silent corruption into a visible client bug (the Stage 3 plan states exactly this).

### 9.2 How to detect

1. On the first request store `request_hash = SHA-256(canonical(method, path, relevant headers, body))`.
2. On a repeat, compute the hash again and compare. Equal: duplicate. Different: mismatch.

Notes:

- **Canonicalization is mandatory**, otherwise harmless differences (JSON key order, whitespace, number formatting like `1.0` vs `1`) produce false mismatches. See note 4 (canonical JSON, RFC 8785 style).
- **Which fields count?** Include fields that change the **outcome**. Exclude transport noise (timestamps added by the client SDK per attempt, request ids, tracing headers). A per-attempt field inside the body makes every retry look "different". Define the hashed set explicitly.
- Store only the **hash**, not the body, to save space and avoid keeping sensitive data.

### 9.3 Mismatch at the sink

The sink's `ON CONFLICT DO NOTHING` cannot tell same-content from different-content duplicates; both are no-ops. Two options:

- Keep a `payload_hash` column and compare in a separate periodic check, or
- Use `ON CONFLICT DO NOTHING RETURNING` and for conflicts select the existing hash to compare (cost: an extra lookup, only on the conflict path).

Reporting the mismatch at the **API** is the primary mechanism; at the sink it is an audit, since by then the client is gone.

## 10. Lifetime: choosing the TTL

### 10.1 The principle

> **TTL >= the longest time a duplicate of that request can still arrive.**

A key expiring while a retry is still possible reopens the duplicate window at that layer.

### 10.2 Inputs to the decision

| Factor                                                          | Effect                                                  |
| --------------------------------------------------------------- | ------------------------------------------------------- |
| Client retry policy (max attempts, backoff, total time)         | Lower bound                                             |
| Client-side queues or offline mode (mobile apps, batch senders) | Can extend retries to hours or days                     |
| Human retries (a user presses "pay" again tomorrow)             | Business rule                                           |
| Storage cost (RAM in Redis)                                     | Pushes TTL down                                         |
| Downstream replays (DLQ replay days later)                      | Not covered by API keys; covered by the sink constraint |
| Regulatory or audit requirements                                | May require longer records elsewhere                    |

### 10.3 Common choices

| Layer                         | Typical TTL                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------- |
| Payment-style APIs            | 24 hours (a widely used convention)                                              |
| Event ingest API (EventPulse) | 24 hours (`EX 86400`) per the Stage 3 design                                     |
| Sink unique constraint        | Unbounded (data lifetime)                                                        |
| Inbox table                   | Retention aligned with maximum replay horizon (days to weeks), pruned in batches |

### 10.4 Sliding vs fixed TTL

| Policy                            | Behavior                            | Risk                                                                               |
| --------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------- |
| **Fixed** (from first claim)      | Key dies exactly TTL after creation | A retry just after expiry is treated as new                                        |
| **Sliding** (refresh on each hit) | Key lives while retries continue    | A continually retrying client keeps it alive; memory is bounded by client behavior |

Fixed is simpler to reason about and to size. Sliding suits long retry sequences. Either way, the DONE state's TTL may differ from the IN_PROGRESS lease.

### 10.5 Behavior after expiry

State the rule in the contract: "A key older than the window is treated as new at the API; **storage is still protected by the sink's unique constraint.**" That sentence is the Stage 3 table row and it is only true if the sink constraint exists. A system that has **only** a TTL'd key store has a **bounded** idempotency guarantee.

### 10.6 Capacity estimate

`keys alive = request rate x TTL`. At 5,000 requests/s and 24 h: `5,000 x 86,400 = 432 million` keys. At roughly 100-200 bytes of Redis overhead plus value each that is tens of GB. A TTL that looks harmless can be the largest memory consumer in the system. Size it before choosing it, and consider storing only the hash plus a few bytes rather than the full response.

## 11. The response contract

Define, per situation, exactly what the client sees. The Stage 3 plan's table, expanded:

| Situation                               | Status             | Body / headers                                                  | Client action                     |
| --------------------------------------- | ------------------ | --------------------------------------------------------------- | --------------------------------- |
| New key                                 | 202 Accepted       | Event accepted; resource id                                     | Done                              |
| Same key, same payload, **DONE**        | 202 (the original) | Same body as the original; optional `Idempotent-Replayed: true` | Treat as success                  |
| Same key, same payload, **IN_PROGRESS** | 409 Conflict       | `Retry-After: n`                                                | Retry after n seconds             |
| Same key, **different payload**         | 422                | Error code `idempotency_key_reuse`, message, key                | Fix the bug; do not retry blindly |
| Key missing where required              | 400                | Error code                                                      | Add a key                         |
| Key malformed or too long               | 400                | Error code                                                      | Fix                               |
| Key older than the window               | Treated as new     | Normal flow                                                     | n/a                               |
| Server error before the claim completed | 5xx                | Standard                                                        | Retry **with the same key**       |

Design points:

- **Replay original, not a recomputation.** If the original answer was 202 with a body, replay it. Recomputing could produce different data (a later timestamp).
- **Mark replays** with a response header so clients and dashboards can distinguish them (useful for S3-F3 visibility).
- **Never return 5xx for a duplicate** of a successful request; that would train the client to retry forever.
- **Retries must reuse the same key** after a 5xx; document it, because clients that mint a new key on 5xx recreate the duplicate problem.

## 12. Concurrency: two requests, one key

### 12.1 The atomic claim

Both approaches below make "check if exists" and "reserve" a single step.

**Redis:**

```
SET idem:{tenant}:{op}:{key}  "{state:IN_PROGRESS, hash:H, started:T}"  NX  EX 86400
  -> OK        : you own the claim, proceed
  -> (nil)     : someone else has it; GET the value and decide
```

**Postgres:**

```sql
INSERT INTO idempotency_keys (tenant_id, op, key, request_hash, state, locked_until)
VALUES ($1, $2, $3, $4, 'IN_PROGRESS', now() + interval '30 seconds')
ON CONFLICT (tenant_id, op, key) DO NOTHING
RETURNING 1;
-- row returned: you own the claim; zero rows: read the existing row and decide
```

### 12.2 After losing the claim

Read the existing record and branch (section 8). Care: between the failed claim and the read, the winner may have **completed** (so you see DONE, good) or **crashed** (IN_PROGRESS with an expired lease, so recover). Keep this logic in one tested function.

### 12.3 Completing

Finishing means: write the **effect** and move the key to DONE with the stored response. If these live in different systems (Kafka produce and a Redis update), crash between them leaves the key IN_PROGRESS after the effect happened. That is why the effect itself (the sink insert) must be idempotent: a takeover repeats it harmlessly.

## 13. Crash and recovery of a claim

The owner of an IN_PROGRESS claim can die at any point. Recovery is by **lease**:

1. The claim includes a short **lease** (`locked_until`, or a Redis TTL on the IN_PROGRESS value, say 30 s).
2. If the owner finishes, it sets DONE with the normal longer TTL.
3. If the owner dies, the lease lapses. A later retry finds an expired lease and **takes over**: re-claim atomically (compare-and-set on the old value or `locked_until < now()`), then process again.
4. Because the owner may have progressed (even finished the effect but not the DONE update), the **effect must be idempotent** so the takeover is safe.

Lease length trades off:

| Too short                                                                                                          | Too long                                      |
| ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| A slow but healthy owner loses its claim; two workers run concurrently (a **zombie** scenario; fence with a token) | Clients get 409 for a long time after a crash |

A **fencing token** (the claim's version number, compared when completing) prevents a late, stale owner from overwriting the new owner's DONE record.

## 14. Which operations need a key

| Operation                                           | Needs a client key?                     | Reason                                     |
| --------------------------------------------------- | --------------------------------------- | ------------------------------------------ |
| `POST` that creates a resource                      | **Yes**                                 | Not idempotent by method                   |
| `PUT` with full body                                | No                                      | Idempotent by definition                   |
| `DELETE`                                            | No                                      | Idempotent                                 |
| `PATCH` that sets values                            | Usually no                              | Absolute values                            |
| `PATCH` that increments                             | **Yes**                                 | Delta                                      |
| Payment, transfer, order placement                  | **Yes, mandatory**                      | Money                                      |
| Sending a message / notification                    | **Yes**                                 | Irreversible                               |
| Pure reads                                          | No                                      | Safe                                       |
| Bulk ingest of events carrying their own `event_id` | The **`event_id` is the key** per event | Batch has no single key; dedup is per item |

For batch endpoints decide whether the key covers the **whole batch** (all-or-nothing, replay the batch result) or **each item** (per-item results). Per-item `event_id` is the EventPulse choice because the sink dedups per row.

## 15. Keys across hops: propagation

The key's job continues after the API:

| Hop                        | What happens to the key                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| API to Kafka               | Place `event_id` (and the tenant) in the message **value** and optionally a header; **never** change it |
| Kafka to sink              | Sink uses it as the unique key                                                                          |
| Retry topics / DLQ         | **Preserve it** in the payload or headers; add attempt metadata separately                              |
| Replay tool                | **Reuses** the original; never generates a new one                                                      |
| Outbox relay               | The outbox row id (or business id) travels with the published message                                   |
| Downstream APIs (webhooks) | Send a derived key (`{event_id}:{target}`) so each target dedups independently                          |

A **derived key** per downstream effect (`orderId:charge`, `orderId:email`) avoids one key colliding across two different effects.

Do not use the Kafka **message key** (the routing key, for example `tenant_id`) as the idempotency key; it is shared by many events by design.

## 16. Security and abuse

| Concern                                                 | Mitigation                                                                                          |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Key guessing / cross-tenant probing                     | Scope by authenticated tenant; do not reveal other tenants' state                                   |
| Storage exhaustion by flooding unique keys              | Rate limit per tenant; bound key length; cap per-tenant live keys; TTL                              |
| Replay of old responses to the wrong caller             | Scope includes tenant and operation; bind to the authenticated principal if responses are sensitive |
| Sensitive data cached in the stored response            | Store the minimum (id and status), or encrypt; short TTL                                            |
| Hash oracle (attacker learns whether a payload matched) | Return only a generic mismatch, not the stored hash or body                                         |
| Key used as a lock for denial of service                | Lease expiry; per-tenant limits                                                                     |

## 17. Worked design for EventPulse ingest

Request:

```
POST /v1/events
Authorization: <tenant credentials>
Idempotency-Key: <optional; if absent, event_id from the body is the key>
{ "event_id": "...", "type": "...", "occurred_at": "...", ... }
```

Flow:

```
1. authenticate -> tenant_id
2. key := Idempotency-Key header, else body.event_id   (reject if neither)
3. validate key format/length; validate body against the schema
4. request_hash := sha256(canonical(body minus transport noise))
5. SET idem:{tenant}:{key} {IN_PROGRESS, hash, lease} NX EX 86400
     OK    -> continue
     nil   -> GET it:
                DONE + same hash       -> return original 202 (+ Idempotent-Replayed)
                IN_PROGRESS + same hash-> 409, Retry-After
                any state + other hash -> 422 idempotency_key_reuse (metric, log)
6. stamp received_at once; serialize; produce to Kafka (acks=all, idempotent producer)
7. on produce success: set DONE with the 202 body (keep EX 86400)
   on produce failure: delete the claim (or let the lease lapse) and return 503; client retries with the same key
8. return 202
Sink (later): INSERT ... ON CONFLICT (tenant_id, event_id) DO NOTHING; count duplicates
```

Crash analysis:

| Crash                        | State                           | Retry result                                              | Final effect                              |
| ---------------------------- | ------------------------------- | --------------------------------------------------------- | ----------------------------------------- |
| Before step 5                | Nothing                         | New                                                       | One event                                 |
| After 5, before produce      | IN_PROGRESS, lease running      | 409 until lease expires, then takeover                    | One event                                 |
| After produce, before step 7 | Event in Kafka, key IN_PROGRESS | After lease: takeover re-produces; **duplicate in Kafka** | Sink constraint absorbs; one stored event |
| After step 7                 | DONE                            | Replay original 202                                       | One event                                 |
| Redis lost entirely          | No keys                         | Retries treated as new                                    | Duplicates in Kafka; sink absorbs         |

The third and fifth rows are exactly why the API key layer is an **optimization with a window**, and the sink constraint is the **guarantee**.

### 17.1 One key or two (`Idempotency-Key` vs `event_id`)

If clients supply both, they should agree or the API must define precedence. Simplest: **`event_id` is the idempotency key for `POST /events`**; no separate header; batch endpoints dedupe per item. A separate header makes sense for non-event endpoints (config changes) that have no natural id.

## 18. Testing the contract

| Test                                | Assertion                                                                                        |
| ----------------------------------- | ------------------------------------------------------------------------------------------------ |
| Repeat same key and payload         | One event; second call returns the original 202                                                  |
| Same key, different payload         | 422 and a metric increment; stored event unchanged                                               |
| Same key, different tenant          | Both processed independently                                                                     |
| Parallel 50 identical requests      | One claim winner; no more than one event stored; losers get 202 replay or 409                    |
| Key expiry                          | After the TTL (use a shortened test TTL) a repeat is processed as new; sink still stores one row |
| Redis flushed mid-test              | Duplicates may reach Kafka; the sink still yields one row                                        |
| Claim owner crash                   | Lease expires; retry succeeds with one effect                                                    |
| Malformed or oversized key          | 400, nothing stored                                                                              |
| JSON key order or whitespace change | Same hash, treated as a duplicate (canonicalization works)                                       |
| Per-attempt noise field in body     | Excluded from the hash (or the test documents that it is not)                                    |

## 19. EventPulse decisions

| Decision            | Choice                                              | Reason                                 |
| ------------------- | --------------------------------------------------- | -------------------------------------- |
| Key origin          | Client (`event_id` or `Idempotency-Key`)            | Only the client knows retries          |
| Scope               | `(tenant_id, key)`; tenant from authentication      | Isolation and no collisions            |
| TTL                 | 24 h at the API (`EX 86400`); unbounded at the sink | Cover retry horizon; durability behind |
| Record              | State, request hash, stored response, lease         | Faithful replay and crash recovery     |
| Mismatch            | 422 with a metric and log                           | Report client bugs                     |
| In-flight duplicate | 409 + `Retry-After` (documented)                    | Simple and honest                      |
| Claim primitive     | Redis `SET NX EX`; Postgres constraint behind it    | Note 3                                 |
| Replays             | Preserve `event_id`                                 | Sink can absorb                        |
| Batch               | Per-item `event_id`                                 | Sink dedups per row                    |
| Failure of produce  | Release the claim; client retries with the same key | Do not pin 5xx                         |

## 20. Common confusions

1. **"The server can generate the key."** It cannot link a retry to the original request.
2. **"Tenant scoping is optional if keys are UUIDs."** Collisions are unlikely, but probing, poisoning and natural keys still need scope.
3. **"A longer TTL is always better."** It costs memory (rate x TTL) and does not remove the need for a durable constraint.
4. **"Same key means same request, so ignore the body."** That silently drops changed data.
5. **"A 409 for an in-progress duplicate is an error."** It is a defined state, to be retried with the same key.
6. **"Store 5xx responses under the key."** Pinning a transient failure makes the key permanently fail; release the claim.
7. **"The key store is the guarantee."** It has a window and can be lost; the guarantee is the sink constraint.
8. **"Use the Kafka message key as idempotency key."** It is a routing key shared by many events.
9. **"Hash the whole request including headers."** Per-attempt headers make every retry a mismatch.

## 22. Cheat sheet

### Glossary

| Term               | Meaning                                                  |
| ------------------ | -------------------------------------------------------- |
| Idempotency key    | Client-minted id for one logical operation               |
| Scope              | The uniqueness domain: tenant (and operation) plus key   |
| Request hash       | Fingerprint of the canonical request, bound to the key   |
| Claim              | Atomic reservation of the key                            |
| IN_PROGRESS / DONE | The two stored states                                    |
| Lease              | Expiry on an IN_PROGRESS claim enabling takeover         |
| Fencing token      | Version number that stops a stale owner from completing  |
| Replay             | Returning the stored original response                   |
| TTL window         | How long the API remembers the key                       |
| Derived key        | Key built from a base key plus a suffix for a sub-effect |

### Rules

1. **Client mints, before the first attempt, constant across retries.**
2. **Scope by authenticated tenant** (and operation).
3. **Bind to a canonical payload hash**; mismatch is **422**, counted and logged.
4. **TTL >= retry horizon**, sized by rate x TTL.
5. **Claim atomically**; record state and a lease.
6. **Replay the original** result; do not pin 5xx.
7. **The sink constraint is the guarantee**; the key store is a window.
8. **Preserve the key** through every hop and replay.

### Contract at a glance

```
new            -> 202
repeat, DONE   -> 202 original (+ replayed header)
repeat, running-> 409 + Retry-After
other payload  -> 422 idempotency_key_reuse
expired        -> treated as new (sink still dedups)
```

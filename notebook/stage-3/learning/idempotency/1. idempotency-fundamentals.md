## 1. TL;DR

- An operation is **idempotent** if performing it **N times (N >= 1)** leaves the system in the **same state** as performing it **once**.
- It matters because delivery is **at-least-once**: retries, crashes, rebalances and replays make every receiver see repeats (delivery-semantics note 2). Idempotency is what turns "repeats happen" into "repeats are harmless".
- Idempotency is about the **effect on state**, **not** about the return value or the work done. A second call may return a different status (for example "already exists") or even do extra work (a lookup) and still be idempotent.
- Operations fall in three classes: **naturally idempotent** (set, upsert, delete by id), **made idempotent** with an id and a record of seen ids (increment, charge, send), and **impossible to make idempotent** without help from the other side (an irreversible external action with no key support).
- The conversion recipe has three parts: **an identity** (key) that survives retries, **a durable record** of "this identity was applied", and **atomicity** between the record and the effect.
- Concurrency is the hard part: two copies of the same request can arrive **at the same time**. The check and the claim must be **one atomic step** (a unique constraint, `SET NX`), never "read, then write".
- Test idempotency as a **property**: `apply(x); apply(x)` equals `apply(x)`, for any interleavings and any crash point, and prove the test can fail with a negative control.

> **One-line version:** _Idempotent means a repeat is a no-op on state; you get there with an identity, a durable record of it, and one atomic claim step._

## 2. The mental model

An **elevator call button**.

| Elevator                                                       | System                                                        |
| -------------------------------------------------------------- | ------------------------------------------------------------- |
| Pressing the button once calls the elevator                    | One request has its effect                                    |
| Pressing it ten more times while waiting changes nothing       | Repeats are no-ops                                            |
| The light turns on and stays on                                | The **state** ("elevator requested") is a fact, not a counter |
| A "floor 5" button pressed twice does not take you to floor 10 | Setting a value is idempotent; adding to a value is not       |

Compare with a **doorbell that rings each press**: ten presses, ten rings. That is a **counter**; every repeat changes the world.

The design question for every operation is: **am I writing a fact ("the elevator is requested") or applying a delta ("ring once more")?** Facts are idempotent. Deltas are not, until you attach an id that says which delta this is.

## 3. Definitions

### 3.1 Mathematical

A function `f` is idempotent if `f(f(x)) = f(x)` for all `x`. Examples: `abs`, `round`, `max(x, c)`, "set to uppercase". Non-examples: `x + 1`, `x * 2`, `append(list, item)`.

### 3.2 Operational (the one that matters in systems)

Let `S` be system state and `op` an operation parameterized by a request `r`. Then `op(r)` is idempotent when:

```
state after   op(r)               =  S1
state after   op(r); op(r)        =  S1      (same state, not necessarily the same response)
state after   op(r); op(r); ...   =  S1
```

Three refinements that real systems need:

1. **Interleaved idempotence.** Other operations may run between the repeats. The right statement is: repeated `op(r)` adds nothing beyond the first application **relative to whatever else happened** (a delete-then-recreate in between legitimately changes things).
2. **Concurrent idempotence.** Two copies of `op(r)` running **at the same time** still leave one effect.
3. **Crash idempotence.** If `op(r)` crashes at **any** internal step and is then re-run, the final state equals a single successful run.

Real "idempotent" claims in a delivery system must hold for all three. Many implementations only satisfy the first.

### 3.3 What idempotent does **not** mean

| Not required                              | Why                                         |
| ----------------------------------------- | ------------------------------------------- |
| Same response                             | A retry can return "409 already exists"     |
| Same side-channel effects (logs, metrics) | A repeat may log "duplicate"                |
| Same latency or cost                      | A repeat still does a lookup                |
| That the operation is safe or read-only   | `DELETE` is idempotent but destructive      |
| Commutativity with other operations       | Different operation types may need ordering |

## 4. Classifying operations

### 4.1 The big table

| Operation                                         | Idempotent?                                | Why                                     |
| ------------------------------------------------- | ------------------------------------------ | --------------------------------------- |
| `SET x = 5`                                       | Yes                                        | Fact                                    |
| `UPDATE users SET status = 'active' WHERE id = 7` | Yes                                        | Fact                                    |
| `UPSERT` by primary key with the same values      | Yes                                        | Fact                                    |
| `INSERT ... ON CONFLICT DO NOTHING`               | Yes                                        | Second is a no-op                       |
| `DELETE FROM t WHERE id = 7`                      | Yes                                        | After the first, nothing to delete      |
| `PUT /orders/42` with a full body                 | Yes (by HTTP definition)                   | Replace state                           |
| `INSERT` into a table with a unique key           | **Only the first succeeds**; second errors | Idempotent in effect, noisy in response |
| `INSERT` without any unique key                   | **No**                                     | Creates N rows                          |
| `x = x + 1`, `balance += 10`                      | **No**                                     | Delta                                   |
| `list.append(item)`                               | **No**                                     | Delta                                   |
| `POST /payments`                                  | **No** by default                          | Creates a resource per call             |
| Send an email / SMS / push                        | **No**                                     | Irreversible side effect                |
| Generate a new UUID inside the handler            | **No**                                     | Each run differs                        |
| Write `now()` into a column on every run          | **No** (value drifts)                      | Depends on clock                        |
| `UPDATE ... SET count = count + 1`                | **No**                                     | Delta                                   |

### 4.2 Fact vs delta vs event

| Style                                      | Stored as             | Repeat effect             |
| ------------------------------------------ | --------------------- | ------------------------- |
| **Fact / state** ("status is active")      | A value               | None                      |
| **Delta** ("add 10")                       | An operation to apply | Applied again             |
| **Event** ("deposit e-123 of 10 happened") | A row keyed by id     | Insert conflicts, ignored |

The **event** style is the robust one: store immutable facts keyed by id, and **derive** totals by aggregating. EventPulse is built this way: events are rows keyed by `event_id`; counts and dashboards are computed from them, so a repeated event cannot inflate a number.

### 4.3 The "derived value" trick

Instead of mutating a counter on every message (a delta), store the message (an event) and compute the counter (a query or a periodically rebuilt aggregate). Repeats collide on the event key. The price is a read-time or batch aggregation cost, which is why systems also keep materialized counters, updated **inside the same transaction as the dedup insert** (section 6.3).

## 5. Idempotent is about effect, not response

A common bug: "idempotent API" implemented as "return the same JSON every time". Consider a create call:

| Call              | Naive non-idempotent          | Idempotent in effect (response differs) | Idempotent in effect and response              |
| ----------------- | ----------------------------- | --------------------------------------- | ---------------------------------------------- |
| First             | 201, order created            | 201, order created                      | 201, order created                             |
| Second (same key) | 201, **second** order created | 200/409, no new order                   | **201 with the same order body**, no new order |

The third column (replay the **stored original response**) is friendliest for clients because a retrying client cannot tell it was a retry. It is what well-known payment APIs do: they store the first response and return it for repeats, even when the first response was an error. It costs storage for the response.

Be explicit in the API contract which style you offer. EventPulse's idempotency table in the Stage 3 plan chooses: same key and payload, original complete: **return the original result (202), no new event**.

## 6. Making a non-idempotent operation idempotent

### 6.1 The recipe

```
1. IDENTITY    every logical operation gets a unique id, minted at the origin, before the first attempt
2. RECORD      the receiver durably records "id X was applied"
3. ATOMICITY   recording and applying happen in ONE atomic step
4. REPEAT      on a repeat, the receiver finds the record and skips the effect
```

Each part has a failure mode if missing:

| Missing                      | Symptom                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Identity changes per retry   | Dedup never matches                                                                                           |
| Record not durable           | Restart forgets; duplicate applied                                                                            |
| Record and effect not atomic | Crash between them leaves "recorded but not applied" (**loss**) or "applied but not recorded" (**duplicate**) |
| No check on repeat           | No dedup at all                                                                                               |

### 6.2 Pattern A: unique key (the effect is the record)

When the effect is "a row exists", the row **is** the record:

```sql
INSERT INTO events (event_id, ...) VALUES (...) ON CONFLICT (event_id) DO NOTHING;
```

Atomic by construction: the unique index decides the winner.

### 6.3 Pattern B: inbox, effect and record in one transaction

When the effect is a delta on other data:

```sql
BEGIN;
INSERT INTO processed (op_id) VALUES ($1);            -- PRIMARY KEY; conflict => already applied
UPDATE counters SET n = n + 1 WHERE key = $2;         -- effect
COMMIT;
```

Either both rows are written or neither. A repeat hits the conflict and skips the update. Handle the conflict explicitly: `ON CONFLICT DO NOTHING RETURNING op_id` and apply the update only if a row came back.

### 6.4 Pattern C: conditional write (compare-and-set)

```sql
UPDATE orders SET status = 'paid', version = version + 1
 WHERE id = 42 AND status = 'pending';
```

A repeat finds `status <> 'pending'`, matches zero rows, and does nothing. Works for **state machines**, where transitions are only valid from specific states. Also used with a `version` column (optimistic concurrency).

### 6.5 Pattern D: deterministic target

Name the output by the input: object key `reports/{tenant}/{date}.csv`. A re-run overwrites with identical bytes. Requires **deterministic** output (no `now()` or random content in it).

### 6.6 Pattern E: delegate to the remote side's idempotency

For an external API (payment, email provider), pass an **idempotency key** header; the provider guarantees one effect per key. You still need to **persist the key before the first attempt**, so a crash and restart reuses it instead of minting a new one.

### 6.7 Pattern F: replace delta by absolute

Instead of "add 10 to the balance", send "balance was 90, is now 100 (version 7)". Absolute values with versions are idempotent; deltas are not. Not always possible (concurrent writers), but where it is, it is the simplest.

### 6.8 Choosing

```
Effect = "a row should exist"?                  -> A unique key
Effect = change to other rows, with an op id?   -> B inbox in one transaction
Effect = state transition?                      -> C conditional write
Effect = produce a file/object?                 -> D deterministic name
Effect = call an external service?              -> E provider key + persist the key first
Can the message carry an absolute value?        -> F
```

## 7. Idempotency in HTTP

### 7.1 Method semantics (RFC 9110)

| Method             | Safe (no state change) | Idempotent                           |
| ------------------ | ---------------------- | ------------------------------------ |
| GET, HEAD, OPTIONS | Yes                    | Yes                                  |
| PUT                | No                     | **Yes** (replace the resource)       |
| DELETE             | No                     | **Yes**                              |
| POST               | No                     | **No** (by definition)               |
| PATCH              | No                     | **No** (depends on the patch format) |

Why it matters: **HTTP clients, proxies and load balancers may retry idempotent methods automatically** after a connection failure, but should not retry POST without knowing. Making `POST /events` safe to retry requires an application-level key.

### 7.2 The Idempotency-Key header

A widely used convention (popularized by payment APIs, with an IETF draft standardizing the header) is:

```
POST /v1/events
Idempotency-Key: 8f1c2d3e-...
Content-Type: application/json
```

The server treats the `(scope, key)` pair as the identity of the logical request. The expected status handling (in the IETF draft and common practice):

| Situation                                 | Typical response                                   |
| ----------------------------------------- | -------------------------------------------------- |
| Key missing where required                | 400                                                |
| First time seen                           | Process normally                                   |
| Same key, same request, original finished | Return the original response (or an equivalent)    |
| Same key, original still running          | 409 Conflict (with `Retry-After`), or wait briefly |
| Same key, **different request**           | 422 (some APIs use 400/409)                        |

This matches the EventPulse Stage 3 table (202, 409 with `Retry-After`, 202 original, 422, new after the window).

### 7.3 What "same request" means

Compare **method + path + canonical body** (and any parameters that change the outcome), usually by storing a **hash** next to the key. Whitespace or JSON key order differences must not matter, which needs a canonical form (note 4).

## 8. Idempotency in databases

### 8.1 SQL features that give you idempotency

| Feature                                                      | Use                                       |
| ------------------------------------------------------------ | ----------------------------------------- |
| `PRIMARY KEY` / `UNIQUE`                                     | The atomic duplicate detector             |
| `INSERT ... ON CONFLICT DO NOTHING`                          | Insert once                               |
| `INSERT ... ON CONFLICT DO UPDATE ... WHERE <version guard>` | Upsert without regressing to stale data   |
| Conditional `UPDATE ... WHERE <expected state>`              | State machine transitions                 |
| `MERGE` (SQL standard, PostgreSQL 15+)                       | Combined match/insert/update              |
| `INSERT ... RETURNING`                                       | Learn whether a row was actually inserted |

### 8.2 `RETURNING` as the "was it new?" signal

With `ON CONFLICT DO NOTHING`, rows that conflicted are **not** returned. So `inserted = rows returned` and `duplicates = attempted - inserted`. That is exactly how the EventPulse sink counts duplicates without a second query.

### 8.3 Pitfalls

- **`DO NOTHING` hides different content.** If the repeat carries _different_ data for the same key, it is silently ignored. Detect with a stored hash or a comparison.
- **Constraint scope mismatch.** A unique constraint on `event_id` but a lookup by `(tenant_id, event_id)` (or the reverse) leaves gaps.
- **No constraint in a partitioned table covering the partition key.** In PostgreSQL a unique constraint on a partitioned table must include the partition key columns; uniqueness across partitions on `event_id` alone cannot be enforced by the table itself.
- **Sequences and `SERIAL` ids are not idempotency keys.** A retry gets a new sequence value.
- **`NOW()`/`DEFAULT now()` inside the transaction** changes per execution; stamp times at the origin.

## 9. Idempotency and concurrency

### 9.1 The race

Two copies of the same request, `R1` and `R2`, arrive together:

```
R1: SELECT ... WHERE key = K   -> not found
R2: SELECT ... WHERE key = K   -> not found
R1: INSERT key K, apply effect
R2: INSERT key K, apply effect      <- duplicate effect (or a unique-violation error)
```

"Check, then act" is a **race**, whatever the language or store. The fix is to merge the check and the claim into **one atomic operation**:

| Store          | Atomic claim                                                                                                                             |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Postgres       | `INSERT ... ON CONFLICT DO NOTHING` (second waits for the first transaction to finish, then no-ops or proceeds if the first rolled back) |
| Redis          | `SET key value NX EX ttl` (returns OK to exactly one caller)                                                                             |
| DynamoDB-style | Conditional put `attribute_not_exists`                                                                                                   |
| Any            | A single-row compare-and-set                                                                                                             |

### 9.2 What the loser should do

When the claim fails, the request is either **a finished duplicate** (return the stored result) or **an in-flight duplicate** (the winner is still working). This is why a key record has a **state**:

```
 (none) --claim--> IN_PROGRESS --complete--> DONE(result)
                        \--crash/timeout--> (expired claim -> retryable)
```

Policy for IN_PROGRESS: reply 409 with `Retry-After`, or wait a short time and re-check. Decide and document (the Stage 3 plan asks for exactly this decision).

### 9.3 The stuck IN_PROGRESS problem

If the winner **crashes** after claiming, the key stays IN_PROGRESS forever and every retry gets 409. Fixes: give the claim a **lease/TTL** (Redis expiry; a `locked_until` column) so a later request can **take over**; and make the effect itself idempotent so the takeover cannot duplicate.

### 9.4 Isolation levels in one paragraph

Under PostgreSQL's default `READ COMMITTED`, `INSERT ... ON CONFLICT` is already safe for concurrent duplicates because the unique index serializes inserters of the same key. You do **not** need `SERIALIZABLE` for that pattern. You need stronger isolation only for **read-then-write** logic that is not reducible to a unique claim.

## 10. Partial failure and atomicity

An operation with several steps can crash **between** them. For crash-idempotence each step must be repeat-safe, or the steps must be atomic.

```
step 1: charge card
step 2: write order row
step 3: send receipt
```

Crash after step 1: a naive retry re-runs step 1 (double charge). Remedies:

1. **Make each step idempotent with a derived key:** `charge_key = order_id + ":charge"`, `email_key = order_id + ":receipt"`.
2. **Record progress** (a state machine row: `CHARGED`, `RECORDED`, `NOTIFIED`) in one durable place and resume from the last recorded state.
3. **Prefer one transaction** for everything in your own database; use an **outbox** for what must leave it (a later Stage 3 note).

A **saga** is this idea at larger scale: a sequence of steps each with a compensating action; idempotency of every step and compensation is mandatory.

## 11. Idempotency vs related ideas

| Concept               | Relation                                                                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **Safe** (HTTP)       | Safe means no state change; stronger than idempotent for reads                                                                          |
| **Deduplication**     | The mechanism that implements idempotency by remembering ids                                                                            |
| **Exactly-once**      | Idempotent processing plus at-least-once delivery (delivery-semantics note 1)                                                           |
| **Commutative**       | Order-insensitive; different from idempotent. Set union is both; `+` is commutative not idempotent; `max` is both                       |
| **Convergent / CRDT** | Operations designed to be commutative, associative **and** idempotent so replicas converge regardless of delivery order and duplication |
| **Transactional**     | Atomic all-or-nothing; idempotent is repeat-safe. Often combined                                                                        |
| **Immutable event**   | Store-once records; their natural keying gives idempotency                                                                              |

The CRDT triad (commutative, associative, idempotent) is the gold standard for messy delivery: the result is the same however many times and in whatever order updates arrive. For counters that means **per-origin** sub-counters merged by `max`, not a shared `+1`.

## 13. Testing idempotency

### 13.1 The properties

| Property                              | Statement                                                                     |
| ------------------------------------- | ----------------------------------------------------------------------------- |
| **Repeat**                            | `apply(x); apply(x)` equals `apply(x)`                                        |
| **Replay**                            | Applying any sequence with arbitrary repeats equals applying the distinct set |
| **Order-insensitive** (when intended) | Any permutation of the same set gives the same state                          |
| **Crash-repeat**                      | Crash at each step, re-run, final state equals a single clean run             |
| **Concurrent**                        | N parallel copies yield one effect                                            |

### 13.2 Property-based testing (`fast-check`)

Generate random lists of events with random repeats, apply them through the real sink code against a test database, and assert `rows == set(distinct event_ids)`. Shrinking then gives you a minimal failing sequence if a bug exists.

### 13.3 Fault-injection points

Crash at each named step (for example `after-db-commit`) with the Stage 3 fault injector, restart, and check the invariant. This turns "crash-idempotence" into a repeatable test.

### 13.4 Negative controls

Run the same tests against a variant **without** the unique key. They must fail. A property test that cannot fail proves nothing.

### 13.5 Concurrency test

Fire 50 identical requests in parallel against the API and assert one event stored, one 202 "created", the rest idempotent replies. Run it many times; races are probabilistic.

## 14. Anti-patterns

1. **Check-then-act** (`SELECT` then `INSERT`) without a constraint.
2. **New id per retry** (a UUID generated inside the retry loop).
3. **In-memory dedup only** (lost at the crash that causes the duplicate).
4. **Dedup record written before the effect** (crash leaves "done" but nothing happened = loss) or **after** in a separate step (crash leaves "not recorded" = duplicate). Use one atomic step.
5. **`DO NOTHING` everywhere without detecting payload mismatch.**
6. **Using timestamps as identity.**
7. **Counters mutated per message** where an event store plus aggregation would do.
8. **Retrying non-idempotent external calls without a provider key.**
9. **Treating HTTP POST like PUT** without a key.
10. **TTL shorter than the real retry horizon** (client retries for 24 h, key lives 1 h).

| Non-DB side effects later | Provider keys or outbox/inbox                                                  | Section 6                      |

## 16. Common confusions

1. **"Idempotent means returns the same response."** It means same effect on state.
2. **"PUT and DELETE are idempotent so no work needed."** True of the _method contract_, but your implementation (for example one that appends an audit row each call) can still break it.
3. **"A unique violation error means idempotency failed."** It means the constraint did its job; handle the error as "already applied".
4. **"Read-then-insert is fine because the window is tiny."** Under load or retries the window is hit regularly.
5. **"Idempotent means safe to retry forever."** Retrying still costs; use backoff and budgets.
6. **"Exactly-once makes idempotency unnecessary."** Exactly-once effect **is** idempotency (or atomicity) applied at the right place.
7. **"Idempotency is only for APIs."** It applies to consumers, jobs, migrations, deployment scripts and schedulers.
8. **"An idempotent operation is commutative."** Not related; `SET x=1` then `SET x=2` differs from the reverse order.

## 18. Cheat sheet

### Glossary

| Term                 | Meaning                                                       |
| -------------------- | ------------------------------------------------------------- |
| Idempotent           | Repeating has the same state effect as once                   |
| Safe                 | Causes no state change                                        |
| Fact / delta / event | Set a value / add to a value / immutable keyed record         |
| Idempotency key      | Origin-minted id identifying one logical operation            |
| Claim                | Atomic act of reserving a key (insert, `SET NX`)              |
| Inbox                | Table of applied operation ids, written with the effect       |
| Lease                | A claim with an expiry so crashed owners can be replaced      |
| Compare-and-set      | Write only if the current state is as expected                |
| CRDT                 | Data type whose merge is commutative, associative, idempotent |

### Rules

1. Prefer **facts and events** over **deltas**.
2. Identity at the origin, before the first attempt, constant across retries.
3. **Claim atomically**; never check then act.
4. Record and effect in **one** atomic step.
5. Key records have **state** and a **lease**.
6. Detect **same key, different payload**.
7. Test as a property with crash points, concurrency and a negative control.

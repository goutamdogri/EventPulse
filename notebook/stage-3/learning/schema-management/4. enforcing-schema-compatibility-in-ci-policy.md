## 1. TL;DR

- A compatibility mode that nobody runs is **documentation, not protection**. The policy must be enforced by **machines at the point of change**: the pull request, then the deploy, then the registry, then the producer at runtime. The Stage 3 PRD lists "registering schemas manually with no CI check, so compatibility depends on memory" as an anti-pattern to avoid.
- **Schemas live in git** (`schemas/events/*.avsc`) as the reviewed source of truth for **content**. The registry holds the **ids** and the **authoritative compatibility rules**.
- Run **two checks**: an **offline** checker (fast, no infrastructure, can check transitively against every file) for quick feedback, and a **registry-backed** check (`POST /compatibility/...`) that uses the registry's own implementation and configuration. The registry result is authoritative.
- Add **policy lints** the compatibility checker cannot express: defaults on every non-core field, enums need defaults, `null` first in unions, no `NONE` mode, version files immutable, meaning-changes called out.
- **Prove the check with real bytes**: evolution tests encode with schema A and decode with schema B in both directions, and the guard itself is tested with a table-driven suite of known good and bad changes (the matrix from note 3).
- Deployment order is **register first, then deploy**: CI registers the schema (idempotently); applications only **look up** (`auto.register.schemas=false`). Production producers cannot invent schemas.
- Keep the **registry config as code** and detect **drift** on a schedule. Alert on registrations that did not come from the pipeline.
- Breaking changes follow an **explicit, reviewed procedure** (new topic and subject, dual publishing, migration), and any override of the gate is a logged **break-glass** event, never a casual `PUT /config NONE`.

> **One-line version:** _Write the schema in git, check it by machine in CI against the real registry rules, register it only from the pipeline, and make every way around that path loud._

## 2. The mental model: the airport security line

Airport security does not depend on passengers promising to leave knives at home. It places a **mandatory checkpoint** on the only path to the gate, uses **machines** (scanners) instead of memory, **logs** what it finds, and has a **supervised procedure** for exceptions.

| Airport                                            | Schema pipeline                                                              |
| -------------------------------------------------- | ---------------------------------------------------------------------------- |
| Single path to the gate                            | Single path to production schemas: the CI/CD pipeline                        |
| Scanner decides, not the passenger's word          | Compatibility checker decides, not the author's "should be fine"             |
| Secondary screening for odd cases                  | Policy lints and reviewers for semantic changes                              |
| Prohibited-item rules posted and consistent        | Written policy: modes, defaults, no renames                                  |
| A door that only staff can open                    | Producers cannot self-register; the registry rejects writes from anyone else |
| Incident log and supervisor sign-off for overrides | Break-glass procedure                                                        |

The key insight: **protection comes from making the safe path the only path**, not from making the unsafe path forbidden on paper.

## 3. Why convention fails

"We agreed to only add optional fields" fails for predictable reasons:

1. **Review is inconsistent.** A reviewer sees a three-line JSON diff and cannot hold the BACKWARD/FORWARD/transitive reasoning of note 3 in their head at 5 p.m. on a Friday. Machines do it the same way every time.
2. **The dangerous change looks innocent.** Removing a default, making a field optional, adding an enum symbol: each is a one-line diff that breaks old readers (note 3, matrix rows 11, 13, 18).
3. **Knowledge decays.** The person who knew why `type` can never be renamed leaves. The rule remains only if it is in the checker.
4. **Breakage is delayed and distant.** The producer deploy succeeds. The failure shows up hours later in a consumer owned by another team, or weeks later in a replay. Feedback loops that long do not teach.
5. **Repair is expensive.** Bad records already in the log cannot be recalled (note 1, section 5).
6. **Escape hatches get used.** Where `auto.register.schemas=true` and `NONE` exist in production, someone eventually uses them "just this once".

The only reliable answer is **mechanical enforcement with no bypass in the normal path**.

## 4. Defense in depth: where checks must live

One check is a single point of failure (a CI job can be skipped, misconfigured or fail open). Layer them so each catches what an earlier layer missed.

```
  Developer machine        PR CI                   Deploy pipeline          Registry               Runtime
  -----------------        -----                   ---------------          --------               -------
  pre-commit / make        required status check   register step           compat check on        producer:
  schema-check             on schemas/**           (idempotent) using       every registration     auto.register=false
  (offline, fast)          offline + registry      CI credentials           (authoritative)        consumer: unknown id
                           check + lints +                                                         = permanent failure,
                           evolution tests                                  config = code          counted and alerted
```

| Layer                                                                   | Catches                                                                        | Fails how                           |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------- |
| **Local** (`make schema-check`, optional pre-commit)                    | Obvious violations in seconds                                                  | Developer fixes before pushing      |
| **PR CI** (required status check)                                       | All compatibility and policy violations                                        | PR cannot merge                     |
| **Deploy pipeline**                                                     | Schema not registered before the app that uses it; drift                       | Deploy stops                        |
| **Registry** (compat level on the subject)                              | Anything that reached it despite the above (a manual call, a misconfigured CI) | 409, nothing registered             |
| **Runtime** (producer cannot register; consumer classifies unknown ids) | Rogue or stale producers                                                       | Produce fails loudly; DLQ and alert |

The registry layer is the **last line**, not the first. If your CI check is the only thing between a bad schema and production, you are one broken job away from an incident; if the registry check is the only thing, you discover failures at deploy time instead of review time. Use both.

## 5. Schemas as code: repository layout

The Stage 3 PRD proposes:

```
schemas/events/v1.avsc, v2.avsc       (evolution tests)
tools/schema-check/                   (CI compatibility script)
```

A layout that supports everything in this note:

```
schemas/
  subjects.json                  # subject -> file set + compatibility level + owners (the config as code)
  events/
    v1.avsc                      # immutable once merged
    v2.avsc                      # immutable once merged
    v3.avsc
    fixtures/                    # sample records valid for each version, used in evolution tests
      v1.samples.json
      v2.samples.json
      v3.samples.json
tools/schema-check/
  src/                           # offline checker, lints, registry client, drift check
  test/                          # table-driven tests of the guard (section 11)
```

`schemas/subjects.json` is small and central:

```json
{
  "events.raw-value": {
    "format": "AVRO",
    "compatibility": "FULL_TRANSITIVE",
    "versions": ["events/v1.avsc", "events/v2.avsc", "events/v3.avsc"],
    "owners": ["@eventpulse/platform"]
  }
}
```

### 5.1 Versioned files or one evolving file?

| Approach                                                                     | How it works                                                                           | Pros                                                                                                 | Cons                                                                                                                              |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **A. One file, git history is the version history** (`events-envelope.avsc`) | Edit the file; CI compares the PR's version with the registered ones (and with `main`) | No file proliferation; simple diffs                                                                  | Offline transitive checks need the registry or git history; harder to run tests of old versions; easy to edit history by accident |
| **B. One file per version, immutable** (`v1.avsc`, `v2.avsc`...)             | A change is a **new file**; old files must never change                                | Offline transitive check across all files; fixtures per version; auditable; matches the PRD's layout | More files; the "current" version is the highest number                                                                           |

**Recommendation for EventPulse: B.** It makes the transitive property directly testable offline and makes "edited an already-registered schema" a detectable error.

### 5.2 Immutability check

An already-merged `vN.avsc` must never change, even whitespace, because its text (not just meaning) determines the registered schema and id (note 2, section 6). Enforce in CI by:

- comparing the file's **hash** against a committed lock file (`schemas/schemas.lock`: file -> sha256), and failing if a locked file changed; or
- diffing against `main` and failing if any existing file under `schemas/**` is modified or deleted (only additions allowed).

Adding `vN+1.avsc` is the only legal edit.

## 6. The policy, written down

Policy is a short, numbered list that the checker implements and the PR template links to. A starting policy for EventPulse:

| #   | Rule                                                                                                                                  | Enforced by                |
| --- | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| P1  | Every Kafka value subject has an explicit compatibility level in `subjects.json`; **`NONE` is never allowed** outside a local sandbox | Lint + drift check         |
| P2  | Value subjects on replayable topics use **`FULL_TRANSITIVE`**                                                                         | Lint on `subjects.json`    |
| P3  | A merged schema file is **immutable**; changes are new files                                                                          | Immutability check         |
| P4  | New schemas must pass the **offline** transitive check against all earlier versions                                                   | Offline checker            |
| P5  | New schemas must pass the **registry compatibility** check against the real subject config                                            | Registry check             |
| P6  | Every field except the **stable core** has a **default**                                                                              | Lint                       |
| P7  | The stable core (`event_id`, `tenant_id`, `type`, `occurred_at`) is never removed, renamed or retyped                                 | Lint (explicit allowlist)  |
| P8  | Optional fields are `["null", T]` with `default: null`, null first                                                                    | Lint                       |
| P9  | Enums are discouraged; any enum **declares a default symbol**                                                                         | Lint                       |
| P10 | Record names and namespaces never change                                                                                              | Lint / compat check        |
| P11 | The **meaning** of an existing field never changes; add a new field instead                                                           | Human review (PR template) |
| P12 | Schemas are registered **only by the pipeline**; applications run with `auto.register.schemas=false`                                  | Config + registry access   |
| P13 | Breaking changes follow the breaking-change procedure and need an ADR                                                                 | Human review               |
| P14 | Any override of these rules is a logged break-glass event                                                                             | Process + audit            |

Rules P1-P10 are mechanical and automated. **P11, P13 and P14 are human** and are made visible by the PR template and CODEOWNERS; the pipeline's job is to _ensure a human looked_, not to replace them.

## 7. Two kinds of compatibility check

### 7.1 Offline checker

A program that parses the `.avsc` files and tests `canRead(reader, writer)` pairs itself, using an Avro implementation (in Node, the `avsc` library):

```ts
import { Type } from "avsc";

// reader can decode data written by writer?
function canRead(reader: Type, writer: Type): boolean {
  try {
    reader.createResolver(writer);
    return true;
  } catch {
    return false;
  }
}

type Mode = "BACKWARD" | "FORWARD" | "FULL";

// n = new schema, earlier = list of earlier versions (oldest -> newest)
function check(
  n: Type,
  earlier: Type[],
  mode: Mode,
  transitive: boolean,
): string[] {
  const targets = transitive ? earlier : earlier.slice(-1);
  const errors: string[] = [];
  targets.forEach((p, i) => {
    const label = `vs version ${transitive ? i + 1 : earlier.length}`;
    if ((mode === "BACKWARD" || mode === "FULL") && !canRead(n, p))
      errors.push(
        `NOT BACKWARD ${label}: new schema cannot read data written with it`,
      );
    if ((mode === "FORWARD" || mode === "FULL") && !canRead(p, n))
      errors.push(
        `NOT FORWARD ${label}: that schema cannot read data written with the new one`,
      );
  });
  return errors;
}
```

This is note 3, section 3, expressed as code. Properties:

| Pros                                                                    | Cons                                                                                                                                                      |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No infrastructure, runs in milliseconds, runs on a laptop and in any CI | A **different Avro implementation** from the registry (JavaScript vs Java): edge cases (aliases, enum defaults, logical types, union handling) may differ |
| Checks **every** pair, any mode, including mixed-format experiments     | Does not know the registry's _configured_ mode or _actual_ history                                                                                        |
| Good error messages are under your control                              | You maintain it                                                                                                                                           |
| Usable offline and as a library in evolution tests                      |                                                                                                                                                           |

### 7.2 Registry-backed check

Call the registry's compatibility endpoint (note 2, section 12) with the candidate schema, against the **real subject** and its **real configured level**:

```
POST /compatibility/subjects/events.raw-value/versions/latest?verbose=true
```

With a **transitive** level configured on the subject, the registry evaluates against every version (the compatibility endpoint honours the subject's level). Properties:

| Pros                                                                         | Cons                                                                                                                    |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Authoritative**: the same code that will accept or reject the registration | Needs a reachable registry (a shared staging registry, or an ephemeral one in CI)                                       |
| Uses the real configured level and real history                              | Slower; network dependency in CI                                                                                        |
| Verbose output explains the violation                                        | The check reflects the registry's _current_ state: if staging drifted from production, the result misleads (section 14) |

### 7.3 Why use both

| Situation                                           | Offline                            | Registry              |
| --------------------------------------------------- | ---------------------------------- | --------------------- |
| Quick feedback on a laptop                          | ✅                                 | ✗ (needs infra)       |
| Catches violation in real configured mode           | ✗ (unless configured to mirror it) | ✅                    |
| Detects drift between git and registry              | ✗                                  | ✅ (with drift check) |
| Reproduces failure deterministically in a unit test | ✅                                 | ✗                     |
| Implementation disagreement                         | Risk: JS vs Java semantics         | Authoritative         |

Make the **registry result the gate** and the offline result the **fast first line**. **If they disagree, the registry wins**, and the disagreement itself is a bug to record (and a good C10 finding): add that case to the guard's test suite.

### 7.4 Registry in CI

Ways to provide a registry to the CI job:

1. **Ephemeral registry per run** (docker compose: Kafka + registry): the job first **seeds it** by registering `v1...vN` from git in order under the subject's mode, then checks the candidate. Hermetic and reproducible; the registry history is _reconstructed from git_, so it only matches production if git and production are in sync (guarded by the drift check).
2. **Shared staging registry** mirroring production: the job calls the read-only compatibility endpoint. Cheap and realistic; depends on staging being in sync and reachable, and needs a read-only credential.
3. **A read-only replica of production** (restored `_schemas`): most faithful; most work.

For EventPulse learning purposes: option 1 in compose for local and CI, with the drift check keeping it honest.

## 8. Designing tools/schema-check

One command, several subcommands, one exit code. Think of it as a **linter with a registry client**.

```
 schema-check validate     # parse all files; fail on syntax errors
 schema-check immutable    # locked files unchanged; only additions
 schema-check lint         # policy lints (section 9)
 schema-check compat       # offline transitive check, per subjects.json
 schema-check registry     # registry compatibility endpoint, per subject
 schema-check evolution    # encode/decode fixtures across versions (section 10)
 schema-check drift        # git vs registry: subjects, versions, ids, configs
 schema-check register     # idempotent registration (deploy pipeline only)
 schema-check all          # validate -> immutable -> lint -> compat -> evolution -> registry
```

### 8.1 Behavior requirements

1. **Deterministic and offline-capable** for everything except `registry`, `drift`, `register`.
2. **Reads its configuration from `schemas/subjects.json`**, not from flags, so the policy is in one reviewed place.
3. **Explains failures in the language of note 3**: not "incompatible" but _"NOT FORWARD vs version 2: field `source` was added without a default, so readers of version 2 ..."_ with the matrix row to consult.
4. **Exit code non-zero on any violation**; machine-readable output (JSON) for annotations in the PR.
5. **Fails closed**: if the registry is unreachable in the `registry` step, the job **fails** (retry with backoff first); it must never skip the check silently.
6. **Never prints credentials**; takes the registry URL and token from the environment.
7. **Idempotent registration**: re-running `register` for already-registered versions is a no-op (note 2, section 7).
8. **Registers in version order** and verifies that the returned id matches an expected pattern or the existing registry state, to catch out-of-order history.

### 8.2 The registry step, sketched

```ts
async function registryCompat(
  subject: string,
  candidateText: string,
): Promise<void> {
  const res = await fetch(
    `${REGISTRY}/compatibility/subjects/${subject}/versions/latest?verbose=true`,
    {
      method: "POST",
      headers: { "Content-Type": "application/vnd.schemaregistry.v1+json" },
      body: JSON.stringify({ schema: candidateText, schemaType: "AVRO" }),
    },
  );
  if (res.status === 404) return; // subject does not exist yet: first version, nothing to compare
  if (!res.ok) throw new Error(`registry error ${res.status}`); // fail closed
  const body = await res.json();
  if (!body.is_compatible) {
    throw new Error(
      `INCOMPATIBLE with ${subject}: ${(body.messages ?? []).join("; ")}`,
    );
  }
}
```

Notes on this sketch: the **404 case** (subject not found) happens only for a brand-new subject; check it deliberately instead of treating every 404 as success. The body is the **raw schema text**, so you check exactly what you will register (section 5.2: text identity matters). `is_compatible` reflects the subject's level, transitive or not.

### 8.3 The `register` step, sketched

```ts
// pipeline only. For each file in version order:
//   POST /subjects/{subject}/versions   -> id   (409 => fail the deploy)
// then
//   PUT /config/{subject} {compatibility}  iff it differs from subjects.json   (config as code)
```

The order matters: **set the compatibility level before registering the first version** (note 2, section 13), and **register in ascending version order**.

## 9. Policy lints beyond compatibility

Compatibility checking answers "will decoding throw?". Lints enforce **design hygiene** that keeps the future evolvable.

| Lint                        | Rule                                                            | Example violation                                                           |
| --------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `default-required`          | Every non-core field has a `default`                            | `{"name":"source","type":["null","string"]}` (no default)                   |
| `core-frozen`               | Core fields exist in every version with identical name and type | `type` renamed to `event_type`                                              |
| `null-first`                | Union with `default: null` lists `"null"` first                 | `["string","null"]` with `default: null` (a schema error in strict parsers) |
| `enum-default`              | Every enum declares `default`                                   | `{"type":"enum","symbols":["A","B"]}`                                       |
| `no-enum-reorder`           | Symbols only appended                                           | `["B","A"]` after `["A","B"]`                                               |
| `immutable-name`            | Record `name` and `namespace` unchanged across versions         | Namespace refactor                                                          |
| `doc-required`              | Every field has a `doc` describing meaning and units            | Missing documentation                                                       |
| `units-in-name-or-doc`      | Numeric fields state units (`amount_cents`)                     | `amount: long` with no unit                                                 |
| `no-none-mode`              | `subjects.json` never sets `NONE`                               |                                                                             |
| `transitive-for-replayable` | Replayable topics use a `*_TRANSITIVE` level                    | `BACKWARD` on `events.raw-value`                                            |
| `no-logical-type-change`    | A field's `logicalType` is unchanged across versions            | Added `timestamp-millis` to an existing `long`                              |
| `no-default-change`         | A field's default is unchanged across versions                  | `default: null` -> `default: "unknown"`                                     |
| `no-promotion-risk`         | No `long`->`double`/`int`->`float`, no `string`<->`bytes`       |                                                                             |

The last four are exactly the "things the checker allows but you must not do" of note 3, section 15: **lints are how policy closes the gap that structure checks leave**. Anything a lint cannot decide (a meaning change that keeps the same name and type) goes to the PR template and a human.

## 10. Evolution tests: proving the check with real bytes

Compatibility checks reason about schemas. **Evolution tests** reason about _actual decoding_. They protect against (a) the offline checker and registry disagreeing, (b) your own consumer code making assumptions, and (c) library upgrade regressions. The Stage 3 PRD describes them as: "Add optional field with default, remove optional field, rename field, change type -> registry accepts or rejects as the compatibility mode dictates; old and new consumers behave as predicted."

### 10.1 The matrix test

For each version pair `(vA, vB)` in `schemas/events/`, using fixtures:

```
 for each sample record r valid for vA:
     bytes = encode(r, vA)
     decode(bytes, writer=vA, reader=vB)    -> must succeed iff BACKWARD(vB, vA) in policy
 for each sample record r valid for vB:
     bytes = encode(r, vB)
     decode(bytes, writer=vB, reader=vA)    -> must succeed iff FORWARD(vB, vA) in policy
```

Under `FULL_TRANSITIVE`, **every** pair must succeed in **both** directions. Test the **whole version cross product**, not just adjacent pairs. Also assert the decoded values: for a newly added optional field the decoded value from old data must equal the **default**; for fields in both versions the value must be preserved. This is where **silent data loss** (rename with defaults) is detected: the test sees `null` where it expected the original value.

### 10.2 The consumer-level test

Run EventPulse's real decode path (`consumer-sink` decoder with the production reader schema) against **recorded bytes from every historical version** stored under `fixtures/`. This guarantees _your code_, not just the Avro library, copes with every version still in retention. When a version leaves retention and the replay window, you may retire its fixture (never before).

### 10.3 Negative tests

For every _rejected_ change class (add field without default, rename, narrowing...), assert both that:

1. the checker (offline and registry) **rejects** it, and
2. the **runtime really fails** if forced (decode with the incompatible pair throws or loses data).

Number 2 confirms that the rule exists for a reason and that your prediction table (note 3, section 20) was right. This is the C10 experiment, productized as a regression suite.

### 10.4 Regression fixtures

Whenever an incident or a near miss teaches something, add a fixture or a guard test. The suite becomes the institutional memory.

## 11. Testing the guard itself

A guard that silently passes everything is worse than no guard, because it creates false confidence. Test the checker with a **table-driven suite** whose rows are the change matrix of note 3:

```ts
const cases: Array<{
  name: string;
  prev: Schema;
  next: Schema;
  mode: Mode;
  transitive?: boolean;
  expect: "accept" | "reject";
}> = [
  { name: "add field with default", /* ... */ mode: "FULL", expect: "accept" },
  {
    name: "add field without default",
    /* ... */ mode: "FULL",
    expect: "reject",
  },
  {
    name: "remove field with default",
    /* ... */ mode: "FULL",
    expect: "accept",
  },
  { name: "remove required field", /* ... */ mode: "FULL", expect: "reject" },
  { name: "rename, no alias", /* ... */ mode: "BACKWARD", expect: "reject" },
  { name: "widen int to long", /* ... */ mode: "BACKWARD", expect: "accept" },
  { name: "widen int to long", /* ... */ mode: "FULL", expect: "reject" },
  {
    name: "v3 removes default (v1/v2/v3)",
    /* ... */ mode: "BACKWARD",
    transitive: false,
    expect: "accept",
  },
  {
    name: "v3 removes default (v1/v2/v3)",
    /* ... */ mode: "BACKWARD",
    transitive: true,
    expect: "reject",
  },
  // ... every row of the matrix, both directions
];
```

Properties of a good guard test suite:

1. **Both accept and reject cases.** A suite of only "accept" cases cannot detect a guard that always accepts.
2. **Transitive vs non-transitive** counterexample explicitly (note 3, section 8).
3. **A canary job**: periodically run the pipeline's check with a deliberately bad schema in a sandbox and assert that it **fails**. If the canary passes, the guard is broken.
4. **A "break the build" drill** in the PR checklist for the first implementation: open a throwaway PR that renames a field and confirm that CI blocks it. Record the screenshot or log in the Stage 3 notes.

## 12. The CI pipeline

An illustrative pipeline (GitHub Actions style; adapt to the project's CI). The point is the _shape_, not the syntax.

```yaml
name: schema-check
on:
  pull_request:
    paths: ["schemas/**", "tools/schema-check/**", "packages/kafka-config/**"]

jobs:
  schema-check:
    runs-on: ubuntu-latest
    services: # ephemeral Kafka + registry, or point at a shared staging registry
      # kafka: ...
      # schema-registry: ...
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 } # need history to diff against main
      - run: pnpm install --frozen-lockfile
      - run: pnpm --filter schema-check run all
        env:
          SCHEMA_REGISTRY_URL: http://localhost:8081
```

Which job must be **required** (branch protection "required status check") and which are advisory:

| Check                                                      | Required to merge?                        |
| ---------------------------------------------------------- | ----------------------------------------- |
| validate, immutable, lint, offline compat, evolution tests | **Yes**                                   |
| registry compat check                                      | **Yes**                                   |
| Generated types in sync with `.avsc`                       | **Yes**                                   |
| Drift check                                                | Scheduled (not per-PR), alerts on failure |

Supporting controls in the repository:

- **CODEOWNERS** on `schemas/**` requiring review by the schema owners.
- **A PR template** with the checklist from note 3, section 16.4 (every new field optional? meaning unchanged? migration plan? who reads this?).
- **Path filters** so the job runs on every PR that touches schemas **or the code that depends on them** (`kafka-config`, the encoder/decoder), because a library change can break decoding with an unchanged schema.
- **Required even for "docs only" schema edits**: `doc` changes alter schema text (and therefore the registered id, note 2, section 6) so they are not free.

### 12.1 What a failing run should look like

```
 schema-check: FAIL  subject events.raw-value (FULL_TRANSITIVE)
   schemas/events/v4.avsc
   - NOT BACKWARD vs v1..v3: field "event_type" (no default) is required by the new schema, but data written with v1..v3 does not contain it.
   - NOT FORWARD  vs v3:     field "type" (no default) was removed, but readers of v3 require it.
   - registry:               409 Schema being registered is incompatible with an earlier schema
   hint: this is a rename (note 3, section 12). Use expand/contract (note 3, section 16.1).
```

A failure message that names the matrix row and the remedy turns the gate from an obstacle into teaching.

## 13. The deploy pipeline: register, then roll out

Order of operations at release time:

```
 1. merge PR  (CI green)
 2. deploy pipeline: schema-check register     <- the ONLY writer of schemas (and subject config) in production
 3. verify: GET /subjects/events.raw-value/versions/latest matches the file's hash
 4. roll out applications (look up the id; auto.register.schemas=false)
 5. post-deploy: drift check + smoke test (produce and consume one record per version)
```

Why **schema first**: producers in production only _look up_ ids. A producer deployed before its schema exists fails at the first send (note 2, section 8). The failure is safe (nothing bad is published) but is an avoidable outage, so make registration a pipeline stage that **precedes** application rollout.

How rollout order interacts with the mode (note 3, section 9):

| Mode                   | App rollout order                                       |
| ---------------------- | ------------------------------------------------------- |
| BACKWARD               | Consumers fully rolled out, then producers              |
| FORWARD                | Producers first, then consumers                         |
| FULL / FULL_TRANSITIVE | Any order; the pipeline can deploy services in parallel |

**Part of the value of FULL_TRANSITIVE is that this table collapses to one row.** Without it, the deploy pipeline needs explicit ordering and a human who knows the order.

**Registration failure at step 2 must stop the pipeline.** Never "continue on error" past it.

**Rollback:** the registry is **append-only**. You do not unregister a schema to roll back; you roll back the **application code** to the version that wrote the previous schema. Because the policy is FULL_TRANSITIVE, the old code still works against data written with the new schema, and the new schema simply lies unused. This is a big safety benefit of the strict policy: **rollback is always safe**, and does not require touching the registry.

## 14. Registry configuration as code and drift detection

The registry has state git does not know about: compatibility levels, modes, the set of registered subjects and versions, the ids. If someone changes it with a `curl`, your CI check may then be evaluating against a different rule than you assume.

### 14.1 Declare and apply

`schemas/subjects.json` (section 5) is the **declaration**. The pipeline's `register` step **applies** it: sets each subject's level to the declared value (before the first version), registers versions in order.

### 14.2 Drift detection

A scheduled job (hourly or daily) and a post-deploy step compare:

| Compare                                     | Expected                                                 | Alert if                                                      |
| ------------------------------------------- | -------------------------------------------------------- | ------------------------------------------------------------- |
| Subjects in the registry vs `subjects.json` | Exactly equal (ignoring allow-listed test subjects)      | Extra or missing subject                                      |
| Versions of each subject vs files           | Same count, same schema text (by hash) in the same order | Extra version (registered outside the pipeline), changed text |
| Compatibility level per subject vs declared | Equal                                                    | Level changed (especially to `NONE`)                          |
| Global compatibility vs declared            | Equal                                                    | Changed                                                       |
| Mode vs `READWRITE`                         | Equal                                                    | Unexpected `IMPORT` or `READONLY`                             |

Drift is a **security-and-reliability signal**: a registration that did not come from the pipeline means either a person bypassed the process or a producer ran with auto-registration on. Both deserve a human look the same day.

### 14.3 Bootstrapping an existing registry

If the registry already holds history from manual work, **import it into git** (export each version's text), establish the lock file, and only then turn on enforcement. Tightening a level does not re-validate history (note 2, section 13), so run a full offline pairwise check on the imported history and record any violations as known, documented exceptions.

## 15. Locking the production door

Automatic checks are meaningless if there is a side door. Close it at three places.

### 15.1 Producers cannot self-register

`auto.register.schemas=false` (and, where available, `use.latest.version=false` with explicit lookup) in staging and production. The application is configured with the **subject** and expects the schema to exist. In Node, use the registry client's lookup (`getLatestSchemaId`, `getRegistryId`) rather than `register` (note 2, section 18), and fail readiness if the lookup fails.

Add a **unit test or lint** that the production config sets this value, so it cannot regress silently.

### 15.2 Only the pipeline identity can write to the registry

Principle of least privilege:

| Identity               | Allowed                                                         |
| ---------------------- | --------------------------------------------------------------- |
| Application (producer) | Read: `GET /schemas/ids/*`, `GET /subjects/*/versions*`, lookup |
| Application (consumer) | Read: `GET /schemas/ids/*`                                      |
| CI (pull request)      | Read plus the read-only compatibility endpoint                  |
| Deploy pipeline        | Register, set subject config                                    |
| Humans                 | Read; writes only via break-glass                               |

How strictly you can enforce this depends on the registry product: open-source Schema Registry supports basic authentication and TLS; fine-grained role-based access control is typically a commercial feature of the platform. The compensating controls when RBAC is unavailable are **network isolation** (only the pipeline network can reach the write endpoints, perhaps via a reverse proxy that blocks `POST`/`PUT`/`DELETE` from application subnets), `mode=READONLY` outside deploy windows, and the **drift detector**. Verify what your deployment supports instead of assuming.

### 15.3 The registry rejects what slips through

The subject's `FULL_TRANSITIVE` configuration is the final automated guard. Keep `NONE` out of every shared environment, and treat any `PUT /config` outside the pipeline as an alert condition.

## 16. Observability: proving the policy holds at runtime

The PRD requires "registry errors, schema ids in use, consumer deserialization failures" in Stage 3 observability. Concretely:

| Signal                                                                                                          | Why                                                                                        | Alert                                                                 |
| --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| **Registry request rate, latency, 4xx/5xx**                                                                     | Registry health; a hidden dependency (C11)                                                 | 5xx > 0 for minutes; latency spike                                    |
| **Registrations count** (per subject)                                                                           | Should be zero outside deploy windows                                                      | Any registration without a pipeline run                               |
| **Schema ids in use per topic** (consumer-side counter by id)                                                   | Shows which versions are live; reveals stragglers still producing old ids                  | A new, unexpected id; an old id after the rollout should have ended   |
| **Deserialization failures by reason** (`bad_magic`, `unknown_id`, `resolution_failed`, `registry_unavailable`) | Separates poison data from outages (note 2, section 9)                                     | Any `unknown_id` or `resolution_failed`; `registry_unavailable` spike |
| **DLQ entries tagged `schema`**                                                                                 | Permanent failures due to schema                                                           | Rate above zero                                                       |
| **Producer serialization failures**                                                                             | A producer using an unregistered schema                                                    | Any                                                                   |
| **Drift job result**                                                                                            | Config or version drift                                                                    | Any failure                                                           |
| **Per-record framing audit** (periodic scan job)                                                                | Evidence for S3-F7: every record on `events.raw` has magic byte `0x00` and a registered id | Any unframed or unknown-id record                                     |

The framing audit is the **proof** of S3-F7: a job that consumes a sample (or all) of `events.raw`, parses the five-byte prefix, checks the id against the registry, and reports `framed / unframed / unknown`. It also detects legacy JSON records during the migration period from the current format.

Include the **schema id** in logs of consumer errors and in DLQ headers so a failure can be tied to an exact schema (the Stage 3 DLQ metadata can carry `schema_id`).

## 17. Runbook: a normal schema change

For a compatible change such as adding an optional field.

```
 1. DESIGN     State the purpose, who reads it, its default and meaning in the PR description.
 2. AUTHOR     Add schemas/events/vN+1.avsc (new file) and the fixtures; add it to subjects.json. Never edit older files.
 3. LOCAL      make schema-check  (validate, immutable, lint, offline compat, evolution tests)
 4. PR         CI runs the required checks including the registry compatibility check. CODEOWNERS review.
 5. MERGE      Deploy pipeline registers vN+1 (idempotent) and verifies the stored hash.
 6. ROLL OUT   Under FULL_TRANSITIVE: deploy producers and consumers in any order.
 7. ADOPT      Consumers start using the field (handling null for legacy data). Producers start populating it.
 8. VERIFY     Per-id metric shows the new id appearing; deserialization failures stay at zero; drift job green.
 9. RECORD     Update the schema catalogue / changelog and the Stage 3 notes.
```

Two details people forget: step 7 (adding a field to the schema does nothing until code _uses_ it; adoption is a separate, normal code change) and the **null-handling** in consumers (legacy data decodes to the default).

## 18. Runbook: a breaking change

When the change cannot be made compatibly (note 3, section 16.3). This is rare and deliberate.

```
 1. JUSTIFY    Write an ADR: why compatible evolution (expand/contract) is impossible; who is affected; rollback.
 2. NEW SUBJECT / TOPIC
               Create events.raw.v2 (or a new record name) with its own subject and compatibility level.
 3. DUAL-PUBLISH
               Producers write to both topics (idempotency keys keep the sink correct: S3-F1, S3-F2).
 4. MIGRATE CONSUMERS
               Consumers move to the new topic one by one; the sink can read both during the overlap.
 5. VERIFY     Reconciliation: counts on both topics match for the overlap window (extended Stage 2 audit).
 6. CUT OVER   Stop publishing to the old topic.
 7. DRAIN      Keep the old topic and its schemas until retention and the DLQ replay window expire.
 8. RETIRE     Delete the old topic. Do NOT hard-delete its schemas while any retained data may reference them.
```

The sink's idempotent writes (Stage 3 notes on idempotency) are what make dual publishing and overlapping consumption **safe**: the same `(tenant_id, event_id)` arriving via two topics yields one row. See [idempotency fundamentals](../idempotency/1.%20idempotency-fundamentals.md) and [idempotent producer versus idempotent consumer](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md).

A last-resort alternative is a one-off **migration job** that reads old data and republishes in the new shape to a new topic (upcasting). Either way, **never** solve a breaking change by flipping the subject to `NONE`.

## 19. Runbook: incidents and rollback

| Symptom                                               | Likely cause                                                                                                                       | First actions                                                                                                                                                                                          |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Consumers throw `unknown schema id`                   | Registry lost data (`_schemas` problem), wrong registry URL, schemas hard-deleted, producer wrote with an id from another registry | Confirm registry identity and `_schemas` health; restore from backup; stop the producer if it uses a foreign id; messages are **not** lost: keep them parked (transient handling) rather than dropping |
| Spike of `registry_unavailable`                       | Registry or its Kafka dependency down (C11)                                                                                        | Check registry health; warm consumers continue; do **not** DLQ these; restart cold pods only after recovery                                                                                            |
| Consumers throw `resolution_failed`                   | An incompatible schema reached production (a bypass) or a consumer's reader schema is stale                                        | Identify the schema id and producer; roll back the producer code; fix the consumer's reader schema; investigate how the gate was bypassed (drift report)                                               |
| CI blocks a PR                                        | The guard worked                                                                                                                   | Read the message; apply expand/contract; do not request an override unless section 20 applies                                                                                                          |
| Producer fails at first send with serialization error | Schema not registered before deploy (order), or `auto.register=false` and schema missing                                           | Run the register step; confirm pipeline ordering (section 13)                                                                                                                                          |
| Drift job fails                                       | Registration or config change outside the pipeline                                                                                 | Find who/what; import or revert; close the access path                                                                                                                                                 |

**Rollback principles:**

1. **Roll back code, not the registry.** The registry is append-only; under FULL_TRANSITIVE old code still works.
2. **Do not delete a schema that data references.**
3. **Do not edit the subject level during an incident** except via break-glass.

## 20. Break-glass: the controlled override

Occasionally the gate must be bypassed (an emergency fix, a registry import, a bad early version that must be superseded). The goal is not to forbid it but to make it **rare, visible, reviewed and reverted**.

| Requirement                            | Detail                                                                                                      |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **Two-person approval**                | A second engineer approves in the incident channel or ticket                                                |
| **Time-boxed**                         | The override states when it will be reverted; e.g. set `NONE` for one registration, set back within minutes |
| **Scripted**                           | A script does the change and the revert (never hand-run `curl`), logging who, why and what                  |
| **Audited**                            | The drift job flags the change; the incident review explains it                                             |
| **Followed by a compatibility repair** | New data written under the bypass is checked with the evolution tests and, if necessary, a migration        |
| **Counted**                            | Track overrides per quarter; a non-zero trend is a process failure to address                               |

If break-glass is used often, the policy is wrong or too hard to comply with. Fix the policy or the tooling rather than normalising the override.

## 21. Anti-patterns

1. **CI check with `continue-on-error` or that skips on registry failure.** Fail closed.
2. **Compatibility level only in the registry, nowhere in git.** Invisible, unreviewed, driftable.
3. **Editing an existing `.avsc`.** Changes the text and risks silent id changes; use new files.
4. **Auto-register in production** "for convenience".
5. **Checking only against `latest`** on a replayable topic (non-transitive).
6. **Using `NONE` to unblock a deploy.**
7. **A guard with only accept tests.** No evidence it ever rejects.
8. **Trusting compatibility = correctness.** No lints, no review of meaning.
9. **Treating the offline checker as authoritative** when it disagrees with the registry.
10. **No evolution tests with real bytes**, relying on schema-level reasoning only.
11. **Hard-deleting schemas to "clean up".**
12. **Registering manually "just this once"** and forgetting to put it in git.
13. **Not testing the consumer's actual decode path** against old-version bytes.
14. **Skipping the drift check**, so CI evaluates against a registry that no longer matches production.
15. **Putting the schema in the application repo only**, so consumer teams cannot see or review the contract. Publish the contract where all parties can review it.

## 23. Common confusions

1. **"The registry already checks compatibility, so CI is redundant."** The registry rejects only at registration, i.e. at deploy time. CI gives feedback at review time and checks policies the registry cannot express.
2. **"CI is enough; the registry check is redundant."** CI can be skipped or misconfigured; the registry is the last line.
3. **"Register from the application, it is simpler."** Then the producer deploy _is_ the schema change, with no review step.
4. **"Offline and registry checks always agree."** Different Avro implementations can differ at the edges. The registry wins; log disagreements.
5. **"A passing compatibility check means no review is needed."** The checker is blind to meaning.
6. **"I can roll back a bad schema by deleting it."** Messages carrying its id then become undecodable; roll back code instead.
7. **"Config in the registry is enough."** Without git it cannot be reviewed, diffed or restored.
8. **"Editing whitespace in an `.avsc` is harmless."** The text identifies the schema; it can create a new version or id.
9. **"FULL_TRANSITIVE makes deploy ordering irrelevant, so the pipeline has no order."** Registration must still precede the apps that look the schema up.
10. **"Breaking changes should be pushed through with `NONE`."** That removes the guarantee for everyone, including consumers you have forgotten.

## 25. Cheat sheet

```
 git (schemas/*.avsc, subjects.json)  --PR-->  CI: validate, immutable, lint, offline transitive, evolution, REGISTRY compat
        ^                                              |  required status check, CODEOWNERS
        |                                              v
   drift job  <------------ registry <---- deploy pipeline: register (ONLY writer) ---> roll out apps (lookup only)
                              |
                              +--> producer/consumer runtime: metrics by failure reason, framing audit
```

| Term               | Meaning                                                                |
| ------------------ | ---------------------------------------------------------------------- |
| **Schema-as-code** | `.avsc` files and subject config reviewed in git                       |
| **Offline check**  | Local `canRead` pairs with an Avro library                             |
| **Registry check** | `POST /compatibility/subjects/{s}/versions/latest` against real config |
| **Lint**           | Policy rule beyond compatibility (defaults, enums, frozen core)        |
| **Evolution test** | Encode with one version, decode with another, assert values            |
| **Guard test**     | Test that the checker rejects known-bad changes                        |
| **Drift**          | Registry state differing from git                                      |
| **Break-glass**    | Controlled, logged override of the gate                                |
| **Fail closed**    | If the check cannot run, the pipeline fails                            |

Rules of thumb:

1. **The safe path must be the only path.**
2. **Fail closed.**
3. **Registry is authoritative; offline is fast feedback.**
4. **Register from the pipeline, look up from the app.**
5. **Roll back code, never the registry.**
6. **Test the guard with known-bad changes.**
7. **Meaning is a human review.** Lints and checks cover structure.
8. **Detect drift.** A rule that is not monitored decays.

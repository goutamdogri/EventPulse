## 1. TL;DR

- Every compatibility mode answers one question: **"can a reader with schema R decode data written with schema W?"** The modes differ in **which schema plays R and which plays W**, and **against how many previous versions** the new schema is checked.
- Let **N** be the new schema and **P** the previous (latest registered) schema.

| Mode                            | Check                                          | In words                                  | Upgrade first |
| ------------------------------- | ---------------------------------------------- | ----------------------------------------- | ------------- |
| **BACKWARD** (registry default) | reader = **N**, writer = **P**                 | New schema can read old data              | **Consumers** |
| **FORWARD**                     | reader = **P**, writer = **N**                 | Old schema can read new data              | **Producers** |
| **FULL**                        | both of the above                              | Both directions with the previous version | **Any order** |
| **BACKWARD_TRANSITIVE**         | reader = N, writer = **every** earlier version | New can read all old data                 | Consumers     |
| **FORWARD_TRANSITIVE**          | reader = **every** earlier, writer = N         | All old readers can read new data         | Producers     |
| **FULL_TRANSITIVE**             | both, against all earlier versions             | Strongest                                 | Any order     |
| **NONE**                        | no check                                       | Anything goes                             | Unsafe        |

- **Rules of thumb that fall out of resolution (note 1, section 10):**
  - **Add a field with a default** -> compatible in **all** modes.
  - **Add a field without a default** -> breaks BACKWARD and FULL (new reader cannot fill the field for old data); fine under FORWARD.
  - **Remove a field that had a default** -> compatible in all modes.
  - **Remove a field with no default** -> fine under BACKWARD; breaks FORWARD and FULL (old reader needs it).
  - **Rename** (without alias) is **remove + add**: breaks something, or silently loses data (section 12).
  - **Change a type** -> only the `int -> long -> float -> double` and `string <-> bytes` promotions work, and each in **one direction only**.
- **Kafka-specific warning:** a topic is a **log**. The non-transitive modes compare only to the _previous_ version, but a consumer replaying from the earliest offset meets _every_ version. Where replay or long retention is real (Stage 3: replays S3-F2, DLQ replay S3-F6), use a **TRANSITIVE** mode. **EventPulse recommendation: `FULL_TRANSITIVE` on `events.raw-value`.**
- A **compatibility checker verifies structure only.** It cannot detect a change in meaning (dollars to cents) or silent data loss from a rename that passes the check. Policy covers that (section 15).

> **One-line version:** _BACKWARD = new code reads old data (consumers first). FORWARD = old code reads new data (producers first). FULL = both (any order). TRANSITIVE = against all history, not just the previous version._

## 2. The mental model: two questions about every change

Whenever a schema changes, two populations exist at the same time:

```
  old data ---------> read by NEW code     (question 1: does the new reader cope with old bytes?)
  new data ---------> read by OLD code     (question 2: does the old reader cope with new bytes?)
```

| Question                | Compatibility name | Fails when                                                        |
| ----------------------- | ------------------ | ----------------------------------------------------------------- |
| 1. New reader, old data | **BACKWARD**       | The new reader demands something old data never contained         |
| 2. Old reader, new data | **FORWARD**        | The new data lacks, or changes, something the old reader demanded |

The naming is the most common stumbling block, so fix it with this device: **name = direction in time of the _reader's_ knowledge relative to the data.**

- **Backward**: the reader looks _backward_ in time at older data.
- **Forward**: the reader (older code) looks _forward_ in time at newer data.

Another device: **"BACKWARD" describes the _new schema_'s duty ("I can read the past"); "FORWARD" describes the _old schema_'s duty ("I can survive the future").** Once you decide which of the two populations can be coordinated, the mode follows.

## 3. Direction is the whole game: who is writer, who is reader

Avro compatibility is always **a check of one writer schema against one reader schema**. Because the registry compares _schemas_, not programs, you can reproduce any mode by hand:

```
 BACKWARD(N, P)  ==  canRead(reader=N, writer=P)
 FORWARD(N, P)   ==  canRead(reader=P, writer=N)
 FULL(N, P)      ==  BACKWARD(N,P) AND FORWARD(N,P)
```

where `canRead(reader, writer)` is true when every writer field is skippable or matchable and every reader field is either present in the writer's data or has a default (and types are resolvable).

To analyse any change, run the two `canRead` checks by hand:

1. **Is there a field the _reader_ needs and the _writer_ cannot provide?** Needs = a field with no default that the writer's schema lacks. -> read fails.
2. **Is there a type the writer produces that the reader cannot accept?** -> read fails.
3. Anything the writer wrote that the reader does not know is simply **skipped**. That is never a problem.

With these three rules you can answer any matrix cell yourself. The next sections apply them.

## 4. The seven compatibility levels

(Terminology follows Confluent Schema Registry. Other registries use the same names.)

| Level                 | Compared against          | Direction(s)      |
| --------------------- | ------------------------- | ----------------- |
| `NONE`                | nothing                   | none              |
| `BACKWARD`            | **latest** version only   | new reads old     |
| `BACKWARD_TRANSITIVE` | **all** previous versions | new reads all old |
| `FORWARD`             | latest only               | old reads new     |
| `FORWARD_TRANSITIVE`  | all previous              | all old read new  |
| `FULL`                | latest only               | both              |
| `FULL_TRANSITIVE`     | all previous              | both              |

Two facts to remember:

1. **The registry default is `BACKWARD`**, which is the _non-transitive_ version. It only guards against breakage relative to the single previous version.
2. A **new subject's first version is always accepted**. The check begins at version 2.

## 5. BACKWARD in depth

**Definition:** consumers using the **new** schema can read data produced with the **previous** schema.

**Allowed changes (Avro):**

- **Delete a field** (the new reader ignores bytes it no longer wants).
- **Add a field _with a default_** (the new reader fills the default for old data).
- Widen a numeric type (`int` -> `long`), because the new reader can read the old narrower type.
- Add an enum symbol, add a union branch (the new reader can read everything the old writer could produce).

**Forbidden:**

- Add a field **without** a default.
- Remove an enum symbol or union branch (old data may contain it) unless the new enum declares a default symbol.
- Narrow a type.

**Who upgrades first:** **consumers.** Reasoning: before any producer writes new-shaped data, every consumer must be able to read both old data and new data. A consumer on the new schema reads old data (guaranteed by BACKWARD) and new data (same schema). A consumer on the **old** schema is _not_ guaranteed to read new data (that is FORWARD). So upgrade **all** consumers, then producers.

```
   step 1: consumers move to N          step 2: producers move to N
   P-data --> N-consumer  OK            N-data --> N-consumer OK
   (old producers still running)        (old consumers are gone)
```

**Why it is the Kafka default:** a new consumer group, or a restarted one reading from the beginning, encounters old data. The standard "I deploy a new consumer and it must handle the existing log" scenario is exactly BACKWARD.

**What it does not protect:** an old consumer reading new data. If you cannot guarantee every consumer is upgraded before any producer (many teams, third parties), BACKWARD alone is not enough.

## 6. FORWARD in depth

**Definition:** consumers using the **previous** schema can read data produced with the **new** schema.

**Allowed (Avro):**

- **Add a field** (even without a default): the old reader just skips the unknown bytes.
- **Delete a field that had a default**: the old reader falls back to its default.
- Narrow a type (old reader `long`, new writer `int` -> OK via promotion).
- Remove an enum symbol or union branch (the new writer will never produce it).

**Forbidden:**

- **Delete a field without a default** (the old reader needs it and nothing supplies it).
- Widen a type (writer produces `long`, the old reader expects `int`).
- Add an enum symbol or union branch (the old reader meets an unknown value), unless the old enum had a default symbol.

**Who upgrades first:** **producers.** Reasoning: upgrade producers first, and the **old consumers** still running must decode the new data, which FORWARD guarantees. Consumers upgrade afterwards at leisure.

**The Kafka catch (important):** FORWARD protects old consumers from new data. It does **not** guarantee that an _upgraded_ consumer can read the _old_ data still sitting in the log. After the consumers upgrade, the log still contains P-data and a new consumer (reader N) reading P-data is the BACKWARD question, unchecked. FORWARD is therefore appropriate when:

- consumers only ever need data from "now" (no replay, short retention), or
- consumers never upgrade to a schema that needs more than old data supplies, or
- you pair it with FULL.

This is why FORWARD alone is rare for Kafka topics that support replay.

**Typical use:** a producer team that wants to move fast (add fields freely) while many downstream consumers lag behind (analytics teams, partners).

---

## 7. FULL in depth

**Definition:** the new schema is both **backward and forward** compatible with the **previous** schema.

**Allowed (Avro), effectively:**

- **Add a field with a default.**
- **Delete a field that had a default.**
- Reorder fields, change docs, add aliases (see section 12 caveats).

**Forbidden:** everything else that is one-directional: adding or removing a field without a default, widening or narrowing numeric types (a promotion works one way only), adding or removing enum symbols (without defaults), adding or removing union branches.

**Who upgrades first:** **nobody has to.** Any interleaving of producer and consumer upgrades works, because each pair `(any old or new writer, any old or new reader)` among **adjacent versions** resolves.

**The practical rule that comes out of FULL:**

> **Only add or remove _optional_ fields** (fields with defaults). Never touch required ones. Everything else is a different kind of change (section 16).

FULL is the right default for **independent teams** where you do not control deploy order: the independence-of-deploys problem from note 1 disappears _for adjacent versions_. To cover non-adjacent versions use `FULL_TRANSITIVE`.

## 8. Transitive variants and why they matter

The non-transitive modes compare the new schema only to the **latest** registered version. That is a _local_ guarantee. Compatibility is **not transitive in general**: "v2 reads v1" and "v3 reads v2" do **not** imply "v3 reads v1".

### 8.1 A concrete counterexample

BACKWARD (non-transitive) accepts all three registrations below, yet v3 cannot read v1 data:

```
 v1:  { id: string }

 v2:  { id: string,
        name: string  default ""     }      v2 reads v1?  name missing in data -> default "" -> OK    (BACKWARD ok)

 v3:  { id: string,
        name: string  (no default)   }      v3 reads v2?  v2 data always contains name            -> OK    (BACKWARD ok)
                                            v3 reads v1?  v1 data has no name, reader has no default -> FAIL
```

The registry (checking only v3 against v2) happily registers v3. Later, a new consumer starting from the earliest offset hits a v1 message and throws. **The trap is removing a default** (or tightening something) in a later version after a loosening version.

With `BACKWARD_TRANSITIVE`, v3 is checked against v1 _and_ v2, and registration of v3 is **refused**.

### 8.2 The same in FORWARD

```
 v1: { id, nick: string }                 (nick required, no default)

 v2: { id, nick: string default "" }      FORWARD vs v1: reader v1 needs nick; v2 data always has it   -> OK

 v3: { id }                               remove nick
                                          FORWARD vs v2: reader v2 has default "" for nick            -> OK (registered)
                                          FORWARD vs v1: reader v1 needs nick, no default, v3 lacks it -> FAIL
```

Non-transitive FORWARD accepts v3, yet a consumer still running the v1 schema crashes on v3 data. `FORWARD_TRANSITIVE` rejects v3 because it checks every earlier reader. The principle is the same as for BACKWARD: **adjacent-pair safety does not guarantee safety across a gap**, so use TRANSITIVE whenever old readers may be several versions behind.

### 8.3 When transitivity matters

| Scenario                                                                                      | Need transitive?                           |
| --------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Consumers always replay from earliest on a topic with long or infinite retention              | **BACKWARD_TRANSITIVE or FULL_TRANSITIVE** |
| A consumer may be several versions behind in a long-lived deployment (mobile, partners, edge) | **FORWARD_TRANSITIVE**                     |
| Short retention, all deploys within one day, a single consuming team                          | Non-transitive is acceptable               |
| DLQ and retry topics (messages parked long, replayed later; S3-F6)                            | **Transitive**                             |
| Compacted topic, archives                                                                     | **Transitive**                             |

### 8.4 The cost

TRANSITIVE modes check against every historical version, so they are **stricter over time**: a change that was fine against v3 may be rejected because of constraints from v1. That is the point, since they reflect real data that exists. The registry cost is trivial (schemas are small). The human cost is design discipline: you cannot "clean up" an old mistake by removing a default or making a field required; the history constrains you forever (or until you move to a new subject/topic, section 16).

## 9. Upgrade order and the log: who goes first

Combine the modes with the Kafka reality (a persistent log):

```
 Mode                 Safe rollout order                          Why
 BACKWARD             all consumers, then producers               new consumers read old+new; old consumers must
                                                                   not see new data
 FORWARD              all producers, then consumers               old consumers read new; but upgraded consumers
                                                                   are NOT guaranteed to read old log data
 FULL                 any order                                   both ways hold for adjacent versions
 *_TRANSITIVE         same as the base mode,                      guarantee extends to every retained version
                      but across all versions in the log
 NONE                 you decide, by hand, with a coordination    nothing is checked
                      plan and a rollback
```

### 9.1 The decisive questions

1. **Can you control deploy order?** If you own both sides and can deploy consumers first reliably, BACKWARD works. If different teams own them, prefer FULL.
2. **Do consumers read old data?** If anything ever replays, rewinds, bootstraps from earliest, or reads a DLQ, the new consumers must read old data -> you need the BACKWARD direction (in FULL or BACKWARD).
3. **Do old consumers read new data?** Whenever old and new instances coexist (rolling deploys, slow consumers), yes -> you need the FORWARD direction.

In practice almost every real Kafka system needs **both directions**, i.e. FULL (or FULL_TRANSITIVE). BACKWARD-only is the minimal setting for "I control deploy order and my retention is short"; FORWARD-only is the minimal setting for "I do not need to read old data and I deploy producers first".

### 9.2 The rolling deploy _inside_ one service

Even a single service sees both versions during its own deploy:

```
 ingest-api rolling deploy (v1 -> v2):   instance A: v2   instance B: v1   both writing to events.raw
 consumer-sink rolling deploy:           instance X: v2   instance Y: v1   both reading different partitions
```

If you can write `B` and `Y` off as "gone in 60 seconds", you may still lose a message in those 60 seconds with a decode error. Under BACKWARD alone, the ordering "all consumers first" must hold even within a single service's deploy sequence (consumer-sink must be **fully** rolled out before ingest-api starts rolling). Under FULL, that sequencing constraint vanishes.

### 9.3 Replay and DLQ in the picture

- **Replay (S3-F2):** the consumer's reader schema must read every version in the replayed range -> BACKWARD direction over all versions in the range -> `*_TRANSITIVE`.
- **DLQ replay (S3-F6):** a message parked under v2 is replayed by a v4 consumer. Same requirement.
- **Retry tiers:** messages travel with the original value bytes; the schema id inside the bytes remains valid as long as the schema is not hard-deleted (note 2, section 15).

## 10. The change matrix

**Legend:** ✅ allowed (registry accepts), ❌ rejected. The table is for **Avro**, **non-transitive** modes, judged against the _previous_ version only. For TRANSITIVE variants the cell is ✅ only if it holds against _every_ earlier version.

| #   | Change                                                          |              BACKWARD              | FORWARD | FULL | Why (short)                                                                                                             |
| --- | --------------------------------------------------------------- | :--------------------------------: | :-----: | :--: | ----------------------------------------------------------------------------------------------------------------------- |
| 1   | **Add field WITH default**                                      |                 ✅                 |   ✅    |  ✅  | New reader fills default; old reader skips the new bytes                                                                |
| 2   | **Add field WITHOUT default**                                   |                 ❌                 |   ✅    |  ❌  | New reader has nothing for old data                                                                                     |
| 3   | **Remove field that HAD a default**                             |                 ✅                 |   ✅    |  ✅  | New reader ignores; old reader uses its default                                                                         |
| 4   | **Remove field with NO default**                                |                 ✅                 |   ❌    |  ❌  | Old reader requires it                                                                                                  |
| 5   | **Rename field (no alias)**                                     |                ❌\*                |  ❌\*   | ❌\* | Equals remove + add; see section 12                                                                                     |
| 6   | **Rename with alias in new schema**                             |                 ✅                 |  ❌\*   | ❌\* | Alias helps the _new reader_; old reader does not know the new name                                                     |
| 7   | **Widen type** (`int` -> `long`, `float` -> `double`)           |                 ✅                 |   ❌    |  ❌  | Promotion works new-reads-old only                                                                                      |
| 8   | **Narrow type** (`long` -> `int`)                               |                 ❌                 |   ✅    |  ❌  | Promotion works old-reads-new only                                                                                      |
| 9   | **Incompatible type** (`string` -> `int`, `record` -> `string`) |                 ❌                 |   ❌    |  ❌  | No resolution path                                                                                                      |
| 10  | **`string` <-> `bytes`**                                        |                 ✅                 |   ✅    |  ✅  | Interchangeable by resolution rules, but semantically risky                                                             |
| 11  | **Make optional**: `T` -> `["null",T]` default null             |                 ✅                 |   ❌    |  ❌  | Old reader cannot accept null                                                                                           |
| 12  | **Make required**: `["null",T]` -> `T`                          |                 ❌                 |   ✅    |  ❌  | Old data may contain null                                                                                               |
| 13  | **Add enum symbol**                                             |                 ✅                 |   ❌†   | ❌†  | Old reader meets unknown symbol                                                                                         |
| 14  | **Remove enum symbol**                                          |                ❌†                 |   ✅    | ❌†  | Old data may contain the symbol                                                                                         |
| 15  | **Add union branch**                                            |                 ✅                 |   ❌    |  ❌  | Old reader meets unknown branch                                                                                         |
| 16  | **Remove union branch**                                         |                 ❌                 |   ✅    |  ❌  | Old data may use that branch                                                                                            |
| 17  | **Change a default value**                                      |                 ✅                 |   ✅    |  ✅  | Not part of resolution; but **semantic risk** (section 15)                                                              |
| 18  | **Remove a default** (field stays)                              |                ✅‡                 |   ✅    | ✅‡  | Against the _previous_ version the field was always written, so nothing is missing; the break only appears transitively |
| 19  | **Add a default to an existing field**                          |                 ✅                 |   ✅    |  ✅  | Loosens the reader                                                                                                      |
| 20  | **Reorder fields**                                              |                 ✅                 |   ✅    |  ✅  | Resolution is by name, not position                                                                                     |
| 21  | **Change `doc`**                                                |                 ✅                 |   ✅    |  ✅  | Documentation only                                                                                                      |
| 22  | **Change record name or namespace**                             |                 ❌                 |   ❌    |  ❌  | Full names must match (or alias)                                                                                        |
| 23  | **Change fixed size / enum name**                               |                 ❌                 |   ❌    |  ❌  | Named type mismatch                                                                                                     |
| 24  | **Nested record change**                                        | follows the same rows, recursively |         |      | The rules apply at every level                                                                                          |

Footnotes:

- **\*** A rename can _pass_ the checker while destroying data when both the old and new field have defaults (section 12). Without defaults, it fails as shown.
- **†** With an enum-level **default symbol** declared (Avro 1.9+ feature), unknown symbols resolve to the default, which turns some ❌ into ✅. Declare one on every enum you expose. A catch-all `UNKNOWN` default symbol is the standard idiom.
- **‡** Row 18 is ✅ in the non-transitive modes because the previous version always wrote the field. It becomes ❌ under **BACKWARD_TRANSITIVE / FULL_TRANSITIVE** whenever an _earlier_ version did not contain the field (section 8.1). This is exactly the case that motivates TRANSITIVE modes.

> **Verify against your registry version.** Details around aliases, enum defaults and union evolution have shifted across Avro and registry releases. Treat the matrix as the _model_ and C10 (section 20) as the confirmation for the Avro and registry versions EventPulse actually uses.

## 11. Each change explained

Rows 1-4 are the ones you will perform most. Each explained as the pair of `canRead` checks.

### 11.1 Add a field with a default (row 1)

```
 P: { id: string }
 N: { id: string, source: ["null","string"] default null }

 BACKWARD  reader=N, writer=P : data has id only; reader wants source -> has default null -> OK
 FORWARD   reader=P, writer=N : data has id and source; reader P knows only id; skips source bytes -> OK
 FULL      both OK
```

This is **the** safe change. It is why optional-with-default is the main evolution tool.

### 11.2 Add a field without a default (row 2)

```
 N: { id: string, source: string }          (no default)

 BACKWARD  reader=N, writer=P : data has no source; reader requires it, no default -> FAIL
 FORWARD   reader=P, writer=N : P skips source -> OK
```

Only FORWARD accepts it. If you are in `FULL`, you must give it a default. Practical rule: **if the registry says "reader has field without default", add a default**; if no sensible default exists, the field is not a safe addition (section 16, "required new field").

### 11.3 Remove a field that had a default (row 3)

```
 P: { id: string, nickname: string default "" }
 N: { id: string }

 BACKWARD  reader=N, writer=P : writer wrote nickname; reader skips it -> OK
 FORWARD   reader=P, writer=N : data lacks nickname; reader P has default "" -> OK
```

### 11.4 Remove a field with no default (row 4)

```
 P: { id: string, tenant_id: string }       (tenant_id required)
 N: { id: string }

 BACKWARD  OK  (new reader doesn't want tenant_id)
 FORWARD   reader=P, writer=N : data lacks tenant_id; P requires it, no default -> FAIL
```

Under `FULL` this is rejected, correctly: old consumers still running would crash.

### 11.5 Make a field optional (row 11) and required (row 12)

```
 P: { amount: long }
 N: { amount: ["null","long"] default null }

 BACKWARD  reader=N, writer=P : P writes a long; reader union accepts long -> OK
 FORWARD   reader=P, writer=N : N may write null; reader P cannot hold null -> FAIL (the writer's null branch has no match)
```

Making a field optional looks harmless and is a classic hidden forward break. Making it required is the mirror image (breaks BACKWARD).

## 12. Renaming a field

Avro identifies a field by **name**. Renaming is therefore a **delete of the old name plus an add of the new name**, with consequences depending on defaults:

| Old field has default? | New field has default? | Checker verdict                                                                                                                                         | Reality                                                                                                                                                  |
| ---------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| No                     | No                     | ❌ in BACKWARD (new needs the new field), ❌ in FORWARD (old needs the old field)                                                                       | Correctly blocked                                                                                                                                        |
| No                     | Yes                    | ✅ BACKWARD (new reader skips the old name, defaults the new one); ❌ FORWARD (old reader requires the old name, which the new writer no longer writes) | Blocked by FORWARD and FULL; passes BACKWARD, but old data's value is still lost to the default                                                          |
| Yes                    | Yes                    | ✅ in all modes                                                                                                                                         | **Passes the check, silently loses data.** Old data's value under the old name is _ignored_ by the new reader, which fills the default for the new name. |

The third row is the dangerous one: **the compatibility check says "fine", and every reader now sees default values instead of real data.** This is the most important example of "compatible does not mean correct".

### 12.1 Using aliases

Avro allows **aliases** on a field (and on named types): the _reader's_ schema may list alternative names that a writer's field may have had.

```json
{ "name": "occurred_at", "type": "long", "aliases": ["occurredAt"] }
```

With this reader schema, data written with `occurredAt` is read as `occurred_at`. So aliases solve **question 1 (new reader, old data)**: the rename is **BACKWARD-compatible**.

But aliases do **not** solve question 2: an _old_ reader, which only knows `occurredAt`, meets new data written as `occurred_at`. The old reader has no alias for the new name. So the rename remains **not FORWARD compatible**, and not FULL compatible. Therefore:

- **Aliases make a rename safe only in a BACKWARD-only world** (consumers upgraded first, no old consumers reading new data).
- In a FULL/FULL_TRANSITIVE policy, a rename is **rejected**, and should be.

Also note, since aliases are reader-side: they help only if the _consumer_ uses a **reader schema** carrying the alias (note 1, section 10.1), and only for readers in languages/libraries whose resolution honours aliases. Verify the checker you use applies alias logic (C10).

### 12.2 Why renames are almost never worth it

A rename has no value to the consumer apart from tidiness, and it costs an expand/contract migration (section 16). The advice for a stable contract: **choose names carefully once, never rename.** If a name is genuinely wrong, add the correct field, deprecate the old one in `doc`, dual-write for a window, then retire it.

## 13. Changing a type

Avro permits a handful of **promotions** in reader-from-writer resolution:

```
 int  -> long -> float -> double          (a writer of the narrower type may be read as the wider)
 string <-> bytes                          (both directions)
```

The direction is "writer -> reader". So a reader of the wider type can read narrower data. That explains rows 7 and 8:

```
 P: { count: int }       N: { count: long }      (widen)
   BACKWARD reader=N(long), writer=P(int):  int promotes to long      -> OK
   FORWARD  reader=P(int),  writer=N(long): long does NOT promote to int -> FAIL
```

### Practical type-change rules

1. **Widening** is BACKWARD-compatible only. Good for: "I need bigger numbers". Needs consumers upgraded first. In a FULL policy: rejected; use a new field (`count_v2: long`) and migrate.
2. **`int -> float`/`double`** is _allowed_ by resolution but changes precision and semantics (an `int` ID read as `float` can lose digits above 2^24). Avoid for identifiers.
3. **`long` -> `double`** loses precision above 2^53. A timestamp or ID stored this way could silently corrupt. Avoid.
4. **`string` <-> `bytes`** passes in both directions but changes semantics (encoding assumptions). Avoid unless you really intend it.
5. **Logical types** (`timestamp-millis`, `uuid`, `decimal`) are annotations: the **underlying type** governs the check. Adding or removing a `logicalType` annotation can pass the checker while changing how the data is _interpreted_, which is a semantic break (section 15).
6. **Changing a field between unrelated types** (`string` -> `int`) is rejected everywhere, correctly.

**The safe way to "change a type" is never to change it:** add a new field with the new type and a default, dual-write, migrate readers, retire the old field (section 16).

## 14. Enums and unions

Enums and unions are the places where "adding" is **not** automatically safe.

### 14.1 Enums

```json
{
  "type": "enum",
  "name": "Source",
  "symbols": ["WEB", "MOBILE"],
  "default": "UNKNOWN_"
}
```

- **Add a symbol:** the _new_ reader can read old data (all old symbols exist). The _old_ reader meets an **unknown symbol** in new data and **fails** unless the old schema declared an enum `default`. So adding a symbol is BACKWARD-compatible and **not FORWARD/FULL** unless a default exists in the old schema.
- **Remove a symbol:** old data may still contain it, so the new reader fails (not BACKWARD), unless the new enum has a default; the old reader is fine (FORWARD ok).
- **Declare a default symbol up front**, e.g. `UNKNOWN`. It lets old readers map symbols they do not know to `UNKNOWN`, converting an exception into a handled case. This is the one enum feature that makes enums evolvable under FULL. It must be in the schema **before** you need it, because it is the _old_ reader's schema that supplies the default.
- **Never reorder symbols to "keep them sorted":** reordering changes the ordinal in the encoding in some contexts. Resolution is by symbol name, but append-only is the convention and avoids confusion in generated code.

### 14.2 Enums versus strings

An enum buys validation and compactness; it costs evolvability. For values that change often (event types in EventPulse: `type` is a free tenant-defined string), **use `string`**, not an enum. Use an enum only for closed, stable sets, and always give it a default symbol.

### 14.3 Unions

- **Add a branch**: BACKWARD ✅ (new reader accepts more), FORWARD ❌ (old reader cannot handle the new branch).
- **Remove a branch**: BACKWARD ❌ (old data may use it), FORWARD ✅.
- **Union order matters for defaults:** the default must match the **first** branch. For optional fields put `"null"` first.
- **Changing the order of a union**: allowed by resolution (matching is by type), but it changes which branch the default refers to and can confuse generated code. Avoid.

## 15. Things the checker allows but you must not do

A checker verifies that **decoding will not throw**. It cannot verify that the **decoded value means the same thing**. The following pass checks and still harm consumers. Treat them as policy violations enforced in code review.

| Change                                                                             | Why it passes                                        | Why it is harmful                                                                              |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Rename with defaults on both fields**                                            | Both fields have defaults, resolution fills defaults | Real data silently replaced by defaults (section 12)                                           |
| **Change a default value**                                                         | Defaults are not part of the compatibility rules     | Readers of old data (missing the field) now see a different value from before; behavior drifts |
| **Change units/semantics** (`amount` dollars -> cents)                             | Types identical                                      | Every consumer is silently wrong                                                               |
| **Reinterpret a field's meaning** (`status` enum values reused for something else) | Structure identical                                  | Same                                                                                           |
| **Add/remove `logicalType`**                                                       | Underlying type unchanged                            | Interpretation changes (number vs timestamp)                                                   |
| **`long` -> `double` / `int` -> `float`**                                          | Allowed promotion                                    | Precision loss for large numbers                                                               |
| **`string` <-> `bytes`**                                                           | Allowed promotion                                    | Encoding assumptions change                                                                    |
| **Make a field's content stricter or looser** (e.g., format of IDs)                | Type identical                                       | Consumers' parsing assumptions break                                                           |
| **Loosen `doc`-only contracts** ("never null" in a doc comment)                    | Docs are ignored                                     | Consumers relied on the doc                                                                    |

> **Policy statement (put it in the schema review checklist):** _Never change the meaning of an existing field. Add a new field. A schema change PR must say what each added or removed field means and who reads it._

## 16. Safe procedures for changes the mode forbids

Compatible evolution only covers **adding and removing optional fields**. Everything else needs a **multi-step migration** where each step is individually compatible. The classic pattern is **expand and contract** (also called parallel change).

### 16.1 Rename or retype a field (expand / migrate / contract)

Goal: replace `amount_cents: int` by `amount: long`.

```
 Step 1  EXPAND      Add  amount: ["null","long"] default null          (compatible, FULL ok)
 Step 2  PRODUCERS   Write BOTH amount_cents and amount (dual-write)
 Step 3  CONSUMERS   Read amount when present, else fall back to amount_cents
 Step 4  WAIT        Until all data containing only the old field has aged out of the
                     retention window AND the DLQ/replay window (this can be "never" on compacted topics)
 Step 5  PRODUCERS   Stop writing amount_cents (it must have a default, or FULL rejects removal... see below)
 Step 6  CONTRACT    Remove amount_cents from the schema (allowed iff it had a default)
```

Key requirement: the **old** field must be created with a **default** from the start (or you must add a default to it at step 1: "add a default to an existing field" is a compatible loosening, row 19). Otherwise step 6 is a forbidden "remove field with no default". This is a strong argument for **giving every field a default from day one**, even fields that "always exist", so the future always has an exit.

### 16.2 Add a "required" field

You cannot add a required (no-default) field under BACKWARD/FULL. Do this instead:

1. Add it optional with a default (`["null", T]`).
2. Make all producers always populate it.
3. Consumers treat `null` as "unknown legacy data" where needed.
4. _Do not_ tighten to required in the schema. Enforce "required" at the **API validation layer** and in consumer logic. The schema stays loose so history stays readable.

### 16.3 A truly breaking change (cannot be expressed compatibly)

Examples: changing the partitioning key meaning, merging two event types, switching the format (JSON to Avro), reinterpreting `occurred_at`. Options:

| Option                                                                | How                                                                                                 | Trade-off                                                                                                                                       |
| --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **New topic and new subject** (`events.raw.v2`)                       | Producer dual-publishes to old and new topics; consumers migrate; old topic retired after retention | Clean, expensive; ordering across topics lost; double storage during the migration                                                              |
| **New record name in the same topic** with a union/RecordNameStrategy | Consumers dispatch on type                                                                          | Needs a design that anticipated it                                                                                                              |
| **Temporarily set the subject to `NONE`**, register, set back         | Quick                                                                                               | **Dangerous**: you bypass the very protection you built. Only with a written plan, a freeze, and explicit sign-off. Treat as an emergency tool. |
| **Upcast on the consumer / migration job**                            | Rewrite old data into the new shape (Kafka Streams or a batch job into a new topic)                 | Compute and complexity, but the registry stays strict                                                                                           |

### 16.4 A checklist for any schema PR

1. Is every new field optional with a default?
2. Is every removed field one that had a default?
3. Did any type, name, namespace, enum or union change? If yes, is there a migration plan?
4. Did the _meaning_ of anything change? If yes, reject.
5. Does the PR pass the compatibility check **in the subject's real mode, transitively**? (Note 4.)
6. Is there a test that decodes real v-previous bytes with the new schema, and v-new bytes with the old schema?
7. Is the consumer ready (BACKWARD), or the producer rollout safe (FORWARD)? In FULL, both.

## 17. Choosing a mode: decision guide

```
 Does anything ever read old data with new code?   (replay, new consumer group, DLQ replay, rewind)
    yes -> you need the BACKWARD direction, and over ALL retained versions -> BACKWARD_TRANSITIVE at least
    no  -> BACKWARD (non-transitive) may suffice

 Can old code ever read new data?                   (rolling deploys, slow consumers, third parties)
    yes -> you need the FORWARD direction -> FULL (or FORWARD)
    no  -> BACKWARD is enough IF you strictly deploy all consumers before producers

 Do you control deploy order across all teams, always?
    no  -> FULL / FULL_TRANSITIVE
```

| Situation                                                                                    | Recommended                |
| -------------------------------------------------------------------------------------------- | -------------------------- |
| Topic with replay, DLQ replay, long retention; several independent consumers                 | **FULL_TRANSITIVE**        |
| Internal topic, one consumer team, short retention, strict consumers-first deploy discipline | BACKWARD                   |
| Same as above but consumers may start from earliest                                          | BACKWARD_TRANSITIVE        |
| Producer team moves fast; consumers are tolerant and only read "now"                         | FORWARD (rare)             |
| Development / sandbox only                                                                   | NONE (never in production) |

**EventPulse:** `events.raw` has independent consumers (sink now, analytics later), replay is a stated requirement (S3-F2), DLQ replay is a stated requirement (S3-F6) and deploys must not need a choreography. That is the profile of **FULL_TRANSITIVE**.

## 18. Other formats: Protobuf and JSON Schema

The mode names are the same across formats; the rules for what is "compatible" differ.

|                                | Avro                                                 | Protobuf                                                                                     | JSON Schema                                                      |
| ------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Field identity                 | Name (positional encoding, reader/writer resolution) | **Field number**                                                                             | Property name                                                    |
| Add optional field             | Needs default for BACKWARD                           | Always safe on the wire (unknown fields skipped; absent fields take type defaults)           | Depends on `additionalProperties` (open vs closed content model) |
| Rename a field                 | Break (alias helps BACKWARD only)                    | **Safe on the wire** (name is not encoded), but breaks JSON mapping and source compatibility | Break                                                            |
| Remove a field                 | Needs default for FORWARD                            | Safe if the number is **reserved** and never reused                                          | Depends                                                          |
| Reuse a removed number or name | n/a                                                  | **Never**: reused numbers silently reinterpret old data                                      | n/a                                                              |
| Type change                    | Promotions, one direction                            | Some wire-compatible groups (e.g. `int32`/`int64`/`bool` share varint)                       | Complex                                                          |
| Required fields                | Field without default                                | Proto3 has no required; presence tracking via `optional`                                     | `required` array                                                 |

The takeaway: **each format has its own definition of compatibility**, so the registry's checker is format-aware. Stage 8 compares Protobuf under load; for evolution, Protobuf's field numbers make renames safe on the wire but impose "never reuse a number" discipline instead.

## 19. EventPulse worked example: v1 to v4

A planned evolution story for `events.raw-value` under **FULL_TRANSITIVE**, using the Stage 3 deliverables `schemas/events/v1.avsc`, `v2.avsc`.

**v1 (baseline):**

```json
{
  "type": "record",
  "name": "EventEnvelope",
  "namespace": "io.eventpulse.events",
  "fields": [
    { "name": "event_id", "type": "string" },
    { "name": "tenant_id", "type": "string" },
    { "name": "type", "type": "string" },
    {
      "name": "occurred_at",
      "type": { "type": "long", "logicalType": "timestamp-millis" }
    },
    { "name": "schema_version", "type": "int", "default": 1 },
    { "name": "payload_json", "type": "string", "default": "{}" }
  ]
}
```

Design note: even in v1, fields that _could_ one day need retiring (`schema_version`, `payload_json`) carry **defaults**, so future removal or replacement is possible (section 16.1). Fields that must exist forever (`event_id`, `tenant_id`, `type`, `occurred_at`) are required and will **never** be removed or retyped; they are the **stable core** of the contract.

**v2: add `source` (optional).**

```json
{ "name": "source", "type": ["null", "string"], "default": null }
```

Check: row 1 -> ✅ in every mode; transitively also ✅ against v1. **Rollout:** any order.

**v3: add `received_at` (optional) so the timestamp the API saw travels in the data, not only in the header.**

```json
{
  "name": "received_at",
  "type": ["null", { "type": "long", "logicalType": "timestamp-millis" }],
  "default": null
}
```

Check: row 1 ✅. Rollout: any order. Note this _changes_ S3-F8's data flow (header vs value); that is a _design_ decision outside the checker: consumers should read from the value when present, else from the header, until the header is retired.

**v4 (attempted, rejected): rename `type` to `event_type`.**

```
 remove "type" (no default) -> row 4: ❌ FORWARD/FULL
 add "event_type" (no default) -> row 2: ❌ BACKWARD/FULL
```

Registry returns 409 under FULL_TRANSITIVE. Correct. The right path is expand/contract (section 16.1): add `event_type` optional, dual-write, migrate consumers. Because `type` is required with no default, it can **never** be removed under FULL; the schema keeps `type` forever. That is the cost of the stable core, and the reason to name stable-core fields carefully at v1.

**v4 (attempted, rejected): make `source` required** -> row 12 ❌ BACKWARD. Right path: keep it optional; enforce at the API.

**v4 (attempted, passes but harmful): change `source`'s default from `null` to `"unknown"`.** Row 17 ✅. Policy reject: old data without `source` now decodes to "unknown" instead of `null`; the consumer's `IS NULL` queries change meaning.

This progression is a good storyline for the C10 write-up.

## 22. Common confusions

1. **"BACKWARD means compatible with the past, so my old consumers are safe."** No. BACKWARD protects the **new reader** on **old data**. Old consumers on new data is FORWARD.
2. **"FORWARD is the safe choice because it sounds future-proof."** It leaves upgraded consumers unprotected against old data in the log.
3. **"BACKWARD default is good enough."** It is non-transitive and only compares to the latest version.
4. **"Adding a field is always compatible."** Only with a default (BACKWARD/FULL).
5. **"Adding an enum symbol is fine."** It breaks old readers (FORWARD) unless a default symbol exists.
6. **"Making a field optional is harmless."** It breaks FORWARD: old readers cannot accept null.
7. **"Renaming with an alias is fully compatible."** Only BACKWARD.
8. **"The registry check passing means the change is safe."** It means decoding will not throw. Meaning and data loss are separate.
9. **"I can fix a bad schema by deleting the version."** Messages already carry its id; a hard delete leaves them undecodable.
10. **"TRANSITIVE is too strict."** It is as strict as the data that exists.
11. **"FULL means any change is OK in any order."** It means _adjacent versions_ interoperate both ways; non-adjacent needs TRANSITIVE.
12. **"I can rely on defaults for removed fields forever."** Only if the field had a default _in the old schema_.

## 24. Cheat sheet

```
 BACKWARD   new schema reads OLD data       consumers first         allowed: add w/ default, delete any field
 FORWARD    old schema reads NEW data       producers first         allowed: add any field, delete w/ default
 FULL       both, vs previous version       any order               allowed: add/delete only fields w/ default
 *_TRANSITIVE  same, against ALL versions   (use for log + replay)
 NONE       no check                        never in prod
```

Quick verdicts:

```
 add w/ default ........ ✅✅✅    add w/o default ....... ❌✅❌
 remove w/ default ..... ✅✅✅    remove w/o default .... ✅❌❌
 widen type ............ ✅❌❌    narrow type ........... ❌✅❌
 make optional ......... ✅❌❌    make required ......... ❌✅❌
 add enum/union ........ ✅❌❌    remove enum/union ..... ❌✅❌
 rename (alias) ........ ✅❌❌    reorder / doc ......... ✅✅✅
                       (BACKWARD, FORWARD, FULL)
```

Rules of thumb:

1. **Only add or remove optional fields.** Everything else needs expand/contract or a new topic.
2. **Give every non-core field a default from day one**, so removal stays possible.
3. **Never change meaning.** The checker cannot see it.
4. **Use TRANSITIVE wherever data outlives a deploy.** On Kafka that is almost always.
5. **Declare default symbols on enums, or avoid enums.**
6. **A rename is a migration, not an edit.**
7. **If the registry says no, believe it**, and design the migration instead of the bypass.

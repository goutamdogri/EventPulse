## 1. TL;DR

- The **schema registry** is a small service that stores schemas and hands out **ids**. It is the shared catalogue that lets a 5-byte prefix in each message stand for a whole schema.
- A **subject** is a named, ordered history of schemas. For a topic's value schema the default subject name is `<topic>-value`, so for EventPulse: **`events.raw-value`**. The key subject is `<topic>-key` (EventPulse keys are plain strings; no key schema needed).
- Within a subject, schemas have **versions** `1, 2, 3...` in registration order. **Versions are per subject.** Across the whole registry, every distinct schema has a **global id**. **Messages carry the id, not the version.**
- Registering a new schema to a subject makes the registry **check compatibility** against existing versions according to the subject's configured **compatibility level**. If the check fails, registration is refused (HTTP 409) and the producer never gets an id to use.
- At runtime producers **cache** `(subject, schema) -> id`, consumers cache `id -> schema`. The registry is on the hot path only for **cache misses**: first use of a schema, first sight of an id, or after a restart.
- The registry persists everything in a **single-partition, compacted Kafka topic** (`_schemas` by default), so its durability is Kafka's durability.
- **Production rule:** producers must not be able to register schemas themselves (`auto.register.schemas=false`); registration happens only from the CI/CD path after the compatibility check passes (note 4).

> **One-line version:** _Subjects are named histories, versions are positions in a history, ids are global handles; messages carry ids; the registry's job at write time is to say no to a bad change._

## 2. The mental model: a library catalogue

A library catalogue:

| Library                                                                     | Registry                                                                      |
| --------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| A **shelf title** ("Cooking") groups editions of the same work              | A **subject** (`events.raw-value`) groups versions of the same logical schema |
| **Edition numbers** within a title (1st ed., 2nd ed.)                       | **Versions** within a subject (1, 2, 3)                                       |
| A unique **barcode** on each physical book, unique across the whole library | A global **schema id**, unique across the registry                            |
| The same book photocopied onto two shelves has one barcode                  | The same schema registered under two subjects gets **one id**                 |
| Librarian refuses to shelve a new edition that does not fit the shelf rules | Registry refuses a schema that fails the compatibility check                  |
| Readers scan the barcode, then look up the book's details                   | Consumers read the id from the message, then look up the schema               |

The detail "the same schema under two subjects shares one id" is easy to forget and explains why **id is not a version**.

## 3. What the registry is and what it stores

An HTTP service (default port 8081) with a REST API, plus durable storage. It stores:

- **Schemas**: the schema text, its format (`AVRO`, `PROTOBUF`, `JSON`), any **references** to other schemas.
- **Subjects**: names, each mapping to an ordered list of version records.
- **Ids**: a global counter; each distinct schema text gets one.
- **Configuration**: compatibility levels, global and per subject.
- **Mode**: `READWRITE` (normal), `READONLY`, `IMPORT` (used when migrating a registry; ids can be preserved).

It deliberately stores **no message data**. It never sees your events; it only sees schemas, which are small, rarely change and are cached aggressively by clients. That is why one registry instance can serve a whole company's streaming traffic.

## 4. Subjects

A **subject** is the unit of **compatibility checking and version history**. Compatibility is evaluated _within a subject_: a new schema is compared with earlier versions of the **same subject**, never with schemas of other subjects.

```
 subject: events.raw-value
 +-----------+---------------------+------------------+
 | version 1 |  id 1               |  v1.avsc         |
 | version 2 |  id 2               |  v2.avsc         |
 | version 3 |  id 5               |  v3.avsc         |    <- ids in between were used by other subjects
 +-----------+---------------------+------------------+
 compatibility checks run: v2 against v1 (and more if TRANSITIVE), v3 against v2 (...)
```

Why this matters for design: **whatever you put in one subject must be evolvable as one stream of changes.** If you put two unrelated record types in the same subject you will fight the compatibility checker constantly (section 17).

For EventPulse: one subject for the main topic, **`events.raw-value`**. The Stage 3 retry and DLQ topics (`events.retry.{tier}`, `events.dlq`) carry the **same original value bytes** plus headers (the diagnostic metadata), so they need no separate value schema as long as the **value is forwarded untouched**. If the DLQ stores a _wrapper_ record (original bytes plus error info), the wrapper is a new schema in its own subject, `events.dlq-value`, with its own compatibility policy.

## 5. Subject naming strategies

The serializer decides which subject a message belongs to using a **subject name strategy**. This is a client-side setting; the registry just receives a subject string.

| Strategy                        | Subject name                                                           | Use when                                                                         | Consequence                                                                            |
| ------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| **TopicNameStrategy** (default) | `<topic>-value`, `<topic>-key`                                         | One record type per topic (the common case)                                      | Subject history == topic history. Simple: compatibility is "the topic's contract".     |
| **RecordNameStrategy**          | Fully qualified record name, e.g. `io.eventpulse.events.EventEnvelope` | Same record type used across several topics; or several types mixed in one topic | Compatibility is per record type, independent of topic. The topic can hold many types. |
| **TopicRecordNameStrategy**     | `<topic>-<record fullname>`                                            | Several types per topic _and_ you want per-topic evolution                       | Most granular; most subjects to manage.                                                |

Why the default is a fine choice for EventPulse: there is one envelope type on `events.raw`. If later you route multiple event kinds to one topic with a union or multiple record types, revisit.

**The trade-off to remember:** with `TopicNameStrategy`, a topic is limited to **one evolving schema** (subject). Putting different record types on one topic then requires a union at the top-level or a different strategy. This is a design-time decision hard to reverse later because subject names are baked into registered history.

## 6. Versions versus ids

|                             | **Version**                                                                                      | **Id**                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| Scope                       | Within one **subject**                                                                           | Global across the **registry**                                     |
| Assigned                    | In order of registration to that subject: 1, 2, 3                                                | From one global counter when a new distinct schema is first stored |
| Embedded in messages        | **No**                                                                                           | **Yes** (4 bytes after the magic byte)                             |
| Used for                    | Humans, APIs (`/versions/latest`, `/versions/3`), compatibility ("latest" means highest version) | Decoding: schema lookup by id                                      |
| Same schema in two subjects | Each subject has its own version number                                                          | **Same id**                                                        |
| Reuse                       | Never reused after delete (version numbers are not recycled in normal flow)                      | Never reused                                                       |
| Typical bug                 | Assuming `version == id`                                                                         | Same                                                               |

A worked example of divergence:

```
 register A to subject s1  -> s1 v1, id 1
 register B to subject s2  -> s2 v1, id 2
 register A to subject s2  -> s2 v2, id 1     (same schema text as A: reuses id 1)
 register C to subject s1  -> s1 v2, id 3
```

After this: `s2` has version 2 with id 1. If you wrote `schema_version = id` anywhere, you are already wrong.

**Identity of a schema.** Two registrations count as "the same schema" when their _schema text_ matches (by default compared as exact string; with the `normalize` option the registry canonicalises first). Semantically identical schemas that differ in whitespace, key order or doc strings may therefore get **different ids** unless you normalise. A CI step that always registers from the same formatted file avoids accidental new versions.

## 7. What happens on registration

`POST /subjects/{subject}/versions` with the schema as a JSON-escaped string.

```
 Client                         Registry
   |  POST /subjects/events.raw-value/versions
   |     {"schema": "{\"type\":\"record\",...}", "schemaType": "AVRO"}
   |-------------------------------->|
   |                                 | 1. parse the schema (syntax valid? else 422)
   |                                 | 2. already registered under this subject? -> return existing id (idempotent)
   |                                 | 3. otherwise: compatibility check against the subject's
   |                                 |    existing version(s) per the effective compatibility level
   |                                 |       - fail -> 409 Conflict (incompatible)
   |                                 | 4. assign a version number and id (reusing id if schema known globally)
   |                                 | 5. write to the _schemas topic (durable)
   |  {"id": 7}                      |
   |<--------------------------------|
```

Details worth knowing:

- **Idempotent**: registering the same schema again to the same subject returns the same id and creates no new version. This is what makes CI "register on deploy" safe to retry.
- **First version has nothing to check against**, so the first registration always succeeds (if valid). That is why compatibility must also be protected by **review of the initial schema** and by config (e.g. setting the level _before_ the first schema).
- **Error codes** you will meet: `409` incompatible schema; `422` schema is not valid Avro (or invalid config value); `404` subject or version not found; `42201` invalid schema (error code in the JSON body).
- The **compatibility level used is the subject's config if set, otherwise the global default** (section 13).
- Registration is a **write** and goes to the registry **primary** instance (section 14); followers forward.

## 8. The producer path step by step

What the Avro serializer inside the producer does for each message. Think of it as three layers: runtime flow, caches, and the first-time path.

```
 produce(topic="events.raw", value=record)
   1. subject = strategy(topic, record)           -> "events.raw-value"
   2. id = cache[(subject, schema)]               -> hit: use it
        miss:
          if auto.register.schemas = true:
              POST /subjects/events.raw-value/versions   -> id   (may be rejected: 409)
          else (production):
              lookup existing:  POST /subjects/events.raw-value  (is this schema registered?)
              or use.latest.version = true: GET .../versions/latest -> id
              not found -> serialization exception; the produce fails
        store in cache
   3. bytes = 0x00 + int32(id) + avroEncode(record, schema)
   4. send bytes to Kafka (as in Stage 2: batching, acks, idempotence...)
```

The _serialization failure_ case is a feature, not a bug. If a developer deploys a producer whose schema differs from anything registered and auto-registration is off, the **producer fails at the first send**, before a single bad message enters the log. Failing at the producer, in a canary or in staging, beats failing in ten consumers a day later.

Also note: **step 3 validates the record against the schema** (the Avro encoder throws if a required field is missing or a type does not match). This is the first of the benefits of schema-on-write: bad data cannot be produced.

## 9. The consumer path step by step

```
 receive record from Kafka (bytes)
   1. check byte 0 == 0x00        (else: not Confluent-framed -> permanent failure)
   2. id = readInt32BE(bytes[1..4])
   3. writer schema = cache[id]   hit: use it
        miss: GET /schemas/ids/{id}   -> writer schema; store in cache
              (404 -> unknown id -> permanent failure; see below)
   4. resolver = cache[(writer id, reader schema)]  (built once, reused)
   5. record = decode(bytes[5..], resolver)
        resolution failure -> incompatible data -> permanent failure
   6. hand the typed record to the application
```

Failure classification for the Stage 3 error taxonomy (S3-F5):

| Failure                                                                     | Transient or permanent  | Why                                                                  |
| --------------------------------------------------------------------------- | ----------------------- | -------------------------------------------------------------------- |
| Registry unreachable on a **cache miss** (timeout, connection refused, 5xx) | **Transient**           | The data is fine; retry with backoff; the message must not be lost   |
| Missing magic byte / not Confluent-framed                                   | **Permanent**           | Retrying cannot fix the bytes                                        |
| Schema id not found (404)                                                   | **Permanent** (usually) | Registry never knew this id; maybe wrong registry or a purged schema |
| Decode failure (truncated body, resolution error)                           | **Permanent**           | Data or schema is inconsistent                                       |

**The classification point is the subtle one.** A registry outage during a cache miss looks like a decode failure unless you catch registry errors separately. If you treat "registry timed out" as a poison message and send it to the DLQ, an outage will push _healthy_ messages to the DLQ in bulk. Distinguish **network/5xx errors from the registry** (retry) from **semantic errors** (404, decode errors).

## 10. Caching and what it means for failure

Client libraries cache aggressively; this is both a performance feature and a resilience feature.

| Cache                  | Key                          | Value         | Populated when             | Evicted when                             |
| ---------------------- | ---------------------------- | ------------- | -------------------------- | ---------------------------------------- |
| Producer: schema to id | `(subject, schema)`          | id            | First produce of a schema  | Process restart (default in-memory only) |
| Consumer: id to schema | id                           | writer schema | First message with that id | Process restart                          |
| Consumer: resolver     | `(writer id, reader schema)` | decoder       | First decode of that pair  | Process restart                          |

Implications:

1. **Steady state does not touch the registry.** After warm-up, a producer with a stable schema produces thousands of messages per second with zero registry requests. Registry throughput is irrelevant to event throughput.
2. **Restart wipes the caches.** A freshly started consumer needs the registry for every distinct id it sees (usually a handful), and the first messages block until they resolve. A cold producer needs the registry once per schema.
3. **A registry outage hurts exactly the processes that start or see something new.** That is the core of C11.
4. **Caches are in-memory and per process.** 50 consumers each fetch each id once. That is still tiny.
5. **Negative results may or may not be cached**, depending on the library. A bad id repeatedly sent can hammer the registry; know your client.

## 11. Registry unavailable: the C11 failure analysis

The Stage 3 experiment C11: _stop the registry under load, then start a fresh consumer._ The hypothesis: _producers with cached ids keep working for known schemas but cannot register new ones; consumers fail on unknown ids._ Here is the analysis so you can predict the result before measuring it.

| Process state when the registry goes down                                      | What continues to work                    | What fails                                                                         |
| ------------------------------------------------------------------------------ | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| **Warm producer**, schema already cached                                       | All produce calls for known schemas       | Registering or looking up a **new** schema (e.g. a deploy of a new schema version) |
| **Cold producer** (just restarted)                                             | Nothing for Avro messages                 | First produce needs id lookup -> fails or blocks until timeout                     |
| **Warm consumer**, ids cached                                                  | Decoding every message whose id is cached | A message with a **new id** (a producer deployed a new schema)                     |
| **Cold consumer** (new instance, or after rebalance in a freshly deployed pod) | Nothing                                   | Every message, even the oldest, because it needs the first fetch                   |
| **Deploys during the outage**                                                  | Nothing                                   | Anything that needs registration; all new pods start cold                          |

Failure modes to expect:

- **Hidden hard dependency.** Everyone calls Kafka a hard dependency; few people list the registry as one. Under load the registry sits on the **start-up path of every producer and consumer pod**. A rolling restart during a registry outage is a full outage.
- **Cascading consumer retries.** Cold consumers retrying fast against a recovering registry can flood it ("thundering herd"). Backoff with jitter applies to registry calls too.
- **Lag grows, not data loss.** If consumers classify registry outages as **transient** and stop (pause or retry in place), offsets are not committed and nothing is lost; lag rises (Stage 2 consumer note 4). If they misclassify as permanent, healthy messages go to the DLQ (section 9).
- **Producer behavior decides data loss.** If the producer cannot serialize (cold + registry down), what does the _API_ do? Return 503 to the client (loses nothing, client retries; fits S3-F1 with idempotency keys) or buffer? Decide explicitly. Acknowledging an event the API cannot serialize would be silent loss.

Mitigations (policy, for the runbook):

1. **Run the registry highly available** (several instances; its storage is the Kafka topic).
2. **Warm start-up**: fetch required schemas during pod start-up, so readiness fails fast rather than after taking traffic. A readiness check that exercises the registry is better than discovering it on the first message.
3. **Bake known schemas into the application** (the schema file is in the repo): at startup load the local schema, look up its id once, and refuse to start if the registry has no matching version. That fails the _deploy_, not the traffic.
4. **Rate limit and back off** registry calls on the consumer.
5. **Alert on** registry 5xx rate, registry latency, and serialization/deserialization error counters (Stage 3 observability).

## 12. The REST API you will actually use

Everything the CI script and runbook need. Base URL `http://localhost:8081` in local compose (confirm the port in your compose file).

| Purpose                                   | Method and path                                                 | Notes                                                                                       |
| ----------------------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------- |
| List subjects                             | `GET /subjects`                                                 | Add `?deleted=true` to include soft-deleted                                                 |
| List versions of a subject                | `GET /subjects/{subject}/versions`                              | `[1,2,3]`                                                                                   |
| Get a specific version                    | `GET /subjects/{subject}/versions/{version}`                    | `version` may be `latest`; returns `subject`, `version`, `id`, `schema`                     |
| Get schema text by global id              | `GET /schemas/ids/{id}`                                         | What consumers call                                                                         |
| **Register** a schema                     | `POST /subjects/{subject}/versions`                             | Body `{"schema":"<escaped>","schemaType":"AVRO"}`; returns `{"id":N}`; 409 if incompatible  |
| Is this schema already in the subject?    | `POST /subjects/{subject}`                                      | Returns the existing version/id or 404; does **not** register                               |
| **Check compatibility** (no registration) | `POST /compatibility/subjects/{subject}/versions/{version}`     | `version` may be `latest`; add `?verbose=true` for reasons; returns `{"is_compatible": true | false}` (and messages when verbose) |
| Get compatibility config (global)         | `GET /config`                                                   | `{"compatibilityLevel":"BACKWARD"}`                                                         |
| Set compatibility (global)                | `PUT /config`                                                   | Body `{"compatibility":"FULL_TRANSITIVE"}`                                                  |
| Get/set per-subject config                | `GET /config/{subject}` / `PUT /config/{subject}`               | Subject config overrides global; `?defaultToGlobal=true` on GET returns the effective value |
| Mode                                      | `GET /mode`, `PUT /mode`                                        | `READWRITE`, `READONLY`, `IMPORT`                                                           |
| Delete a subject or version               | `DELETE /subjects/{subject}` (soft); `?permanent=true` for hard | Section 15                                                                                  |

An example compatibility check, written so you can see the escaping rule (the schema is a **string inside JSON**, so its quotes are escaped):

```bash
curl -s -X POST \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"schema":"{\"type\":\"record\",\"name\":\"EventEnvelope\",\"fields\":[{\"name\":\"event_id\",\"type\":\"string\"}]}"}' \
  "http://localhost:8081/compatibility/subjects/events.raw-value/versions/latest?verbose=true"
# -> {"is_compatible":false,"messages":["Incompatible because ... "]}
```

In scripts, generate the body with a JSON tool (`jq -Rs '{schema: .}' < v2.avsc`) rather than hand-escaping.

Two operational tips:

- The **compatibility check endpoint is read-only**, so it is safe to run on every pull request against the shared registry (or a registry restored from production's `_schemas`).
- The check compares against the version you name. `versions/latest` compares to the newest only; to emulate a transitive check explicitly you compare against every version (or just set the subject to a transitive level and the check honours it).

## 13. Configuration levels: global, subject, mode

Compatibility level resolves like this:

```
 effective level for subject S
   = subject-level config for S, if set
   else the global config (default BACKWARD)
```

Practical policy:

1. **Set the level explicitly per subject**, and keep that setting in version control (note 4). Relying on the registry default means relying on whoever last ran a `PUT /config`.
2. Set the level **before registering the first schema**; otherwise early versions may have been accepted under a laxer rule and the history is already non-compliant.
3. The `NONE` level disables checks. It is occasionally useful in dev, and must never be the production setting.
4. **Mode `READONLY`** blocks all writes, handy to freeze a production registry during an incident; `IMPORT` is for migrating schemas between registries while preserving ids.

Beware: **changing the compatibility level does not re-validate history.** If you move a subject from BACKWARD to FULL_TRANSITIVE, existing versions are not checked retroactively; only new registrations are. Run a full pairwise check offline when you tighten the policy.

## 14. How the registry stores data and stays available

The registry service is **stateless in the sense of local disk**: everything durable lives in a Kafka topic.

```
 +-------------+   writes     +-------------------+     reads (consume at startup,
 |  Registry   | -----------> |  _schemas topic   | <--- then tail for new records)
 |  primary    |              |  1 partition,     |     +-------------+
 +-------------+              |  compacted        |     |  Registry   |
        ^                     +-------------------+     |  followers  |
        | forwarded writes                              +-------------+
        +-----------------------------------------------------+
```

- **Topic `_schemas`** (name configurable, `kafkastore.topic`): **one partition** to give a total order of all registrations (ids are assigned by a single writer in that order), **compacted** so each schema/config record is retained forever and old versions of a record are collapsed. Use replication factor 3 in production; this topic _is_ your schema database.
- **One primary, N followers.** Writes (registrations, config changes) must go through the **primary**, elected via Kafka's group coordination. Followers serve reads from their local in-memory copy and **forward writes** to the primary. Reads therefore scale with instance count; writes are serialised.
- At start-up an instance **replays `_schemas` from the beginning** to rebuild its state. A registry restart does not lose anything, and it is "ready" only after catching up.
- **The registry depends on Kafka to start.** If the broker is down, the registry is down for writes; reads from already-loaded followers may keep working. This couples the failure of Kafka and the registry, so in local compose you need ordering: broker first, registry after.
- Consequence for **backups**: back up Kafka's `_schemas` topic (or periodically export all subjects/versions through the REST API into git). The schemas in the git repo (`schemas/events/*.avsc`) are your **source of truth for content**; the registry holds **ids**, which you cannot reproduce from git. Losing `_schemas` while keeping data in topics would leave messages whose ids point to nothing (the worst failure in section 9: "id not found"). Treat `_schemas` with the same care as the data topics.

## 15. Deleting schemas: soft versus permanent

| Operation                                                                 | Effect                                                                                                                                                                 | Danger                                                                     |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Soft delete** (`DELETE /subjects/{s}` or `.../versions/{v}`)            | Marks the subject/version as deleted: hidden from listings (unless `?deleted=true`), not usable for new registrations in the usual flow, but **the id still resolves** | Low, reversible in effect                                                  |
| **Permanent (hard) delete** (`?permanent=true`, only after a soft delete) | Removes the schema record, including the **id mapping**                                                                                                                | **High**: messages in topics carrying that id **can no longer be decoded** |

Rules:

1. **Never hard-delete a schema whose id might still be inside retained data.** In a log with indefinite retention or archives that means never.
2. Prefer to _leave history alone_ and deal with unwanted schemas by **tightening policy** for future versions.
3. Soft-deleting the latest version changes what `latest` means, which affects compatibility baselines. Be deliberate.
4. For tests and ephemeral environments, deleting subjects is fine, because nobody else's data depends on them.

## 16. Auto-registration: convenient in dev, dangerous in prod

`auto.register.schemas` (Java client setting; most clients have an equivalent) controls whether the serializer registers a schema it has not seen.

| Setting                           | Behavior                                                                                                                   | Right for                                                                |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `true` (the usual client default) | Any producer, on first send, registers its local schema (subject to the compatibility check). Unseen schema -> new version | Local development, exploratory tests                                     |
| `false`                           | Producer only **looks up** schemas that already exist; unknown schema is an error                                          | **Production**: schema creation is a deliberate, reviewed, CI-driven act |

Why prod should turn it off even though the registry checks compatibility anyway:

- Compatibility checks are **necessary but not sufficient**: a compatible but unreviewed change (a new field nobody expected) can enter production through a stray deploy.
- It enforces a **single path** to register: CI registers on merge, producers only consume what exists. The audit trail is the pipeline, not "whichever pod started first".
- **Race conditions**: ten replicas starting at once, all auto-registering, can interleave unpredictably. With explicit registration, the order is a pipeline step.
- It prevents **accidental schema pollution** (typos creating new subjects, test data hitting production).

Related setting: **`use.latest.version`** tells the serializer to use the latest registered version for the subject rather than deriving the schema from the object. Handy when the code's schema and the registry differ trivially, but it can mask drift between code and registry. Prefer to look up by schema content and fail loudly on mismatch.

## 17. Schema references and multiple event types per topic

Two advanced features you should recognise, even if EventPulse does not use them at first.

**References.** A schema can refer to other registered schemas (for Avro: a named type defined elsewhere), listed in the registration request as `{name, subject, version}`. The registry stores the dependency and resolves it at decode time. Use references to share a common type (such as `Money` or `TenantRef`) across subjects without copy-pasting. Warning: a reference creates a **coupling between subjects**; evolution of the shared type affects every referrer and the compatibility checker must be run against each.

**Multiple event types in one topic.** Two common approaches:

| Approach                                         | Subjects                                                       | Compatibility semantics                                                     |
| ------------------------------------------------ | -------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Union at the top level**                       | One subject; the schema is `["TypeA","TypeB"]` with references | One history; adding a new type to the union is a change to the same subject |
| **RecordNameStrategy / TopicRecordNameStrategy** | One subject per record type                                    | Each type evolves independently; topic can carry many types                 |

The ordering benefit of one topic (all events of one entity in order in one partition, Stage 2) is often the motivation. But you pay in consumer complexity (switch on type) and in schema tooling. For EventPulse, the generic envelope with a `type` field and a JSON payload (note 1, section 14) deliberately avoids this problem.

## 18. Node and TypeScript client notes

EventPulse is Node/TypeScript. The Stage 3 PRD says to confirm library support before committing. What to check, not assume:

| Concern                       | What to verify                                                                                                                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Library                       | The PRD names `@kafkajs/confluent-schema-registry` "or a maintained alternative". Check its last release, open issues, and whether it supports your registry version. Pair it with the Avro implementation it wraps (commonly `avsc`).                       |
| Kafka client compatibility    | EventPulse's Kafka client library may differ from kafkajs; the registry client itself is **independent of the Kafka client** (it only does HTTP and byte framing), so it can be used with any. Confirm that and use `encode`/`decode` on the value `Buffer`. |
| Register vs lookup in the app | In production, do **not** call `register` from application code. Use lookup of the latest/known id (for example the library's `getLatestSchemaId` / `getRegistryId`) and fail on a miss.                                                                     |
| Reader schema on decode       | Confirm how to pass a reader schema (so resolution normalises versions) versus decoding with the writer schema only.                                                                                                                                         |
| Cache behavior                | Confirm id-to-schema caching exists and how long it lives; confirm whether failed lookups are cached.                                                                                                                                                        |
| TypeScript types              | Generate or validate the interface from the `.avsc` (note 1, section 13) so the compiler and the schema cannot drift.                                                                                                                                        |
| Timestamps/logical types      | Check how `timestamp-millis` decodes: number vs `Date`. Be consistent with `occurred_at`.                                                                                                                                                                    |
| Large integers                | Avro `long` can exceed JavaScript's safe integer range; verify behavior for `long` fields (many libraries expose them as `number` and lose precision above 2^53, or use `BigInt`).                                                                           |

If library support is weak, an acceptable fallback is a **thin hand-written client**: framing is five bytes, and the REST API is simple. The risk is Avro encoding itself, which should come from a maintained library.

## 19. EventPulse decisions

| Decision                   | Choice                                                                                                                            | Reason                                       |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| Subject for the main topic | `events.raw-value` via TopicNameStrategy                                                                                          | One envelope type per topic; simple mapping  |
| Key schema                 | None; plain string keys (`tenant_id` or `event_id`)                                                                               | Keys are simple strings; no evolution needed |
| Registry storage           | `_schemas` topic, RF=3 in production; RF=1 acceptable locally                                                                     | Durability equals Kafka durability           |
| Producer registration      | `auto.register.schemas=false` in staging and production; CI registers                                                             | One audited path (note 4)                    |
| Local dev                  | Auto-register allowed to speed iteration, **but** CI is the authority                                                             | Avoid friction without losing control        |
| Consumer decode            | Supply reader schema; classify registry I/O errors as transient, unknown id and decode errors as permanent                        | Prevents DLQ flooding during outages         |
| Start-up                   | Look up and validate required schema id at boot; fail readiness if registry or schema missing                                     | Moves failure to deploy time                 |
| Deletes                    | No hard deletes in shared environments                                                                                            | Retained messages depend on ids              |
| Backup                     | Export subjects from the registry to artifacts regularly; protect `_schemas`                                                      | Ids are not reproducible from git            |
| C11                        | Test: kill registry, observe warm vs cold producers and consumers; record DLQ counts (should stay at zero for transient failures) | Documents the hidden dependency              |

## 20. Common confusions

1. **"Version equals id."** No. Different scope, different values.
2. **"The same schema registered twice makes two ids."** Same subject: one version, one id. Different subject: new version there, same id.
3. **"Compatibility is checked across the whole registry."** Only within the subject.
4. **"The registry is on the hot path of every message."** Only on cache misses.
5. **"A registry outage stops running producers."** Warm producers with cached ids carry on; cold ones and schema changes do not.
6. **"A registry outage is a poison-message problem."** It is a transient infrastructure failure; classifying it as poison floods the DLQ.
7. **"Deleting a schema cleans up."** A hard delete can make old messages undecodable.
8. **"Changing the compatibility level checks existing versions."** It does not; only new registrations are checked.
9. **"The first schema can't be wrong because the registry accepted it."** The first version is always accepted; nothing to compare with.
10. **"The registry stores my events."** It stores only schemas.
11. **"If the repo has the `.avsc`, I do not need to back up the registry."** Ids live only in the registry.
12. **"Auto-register is fine in prod because compatibility is checked."** Compatible is not the same as reviewed.

## 22. Cheat sheet

| Term                      | Meaning                                                                       |
| ------------------------- | ----------------------------------------------------------------------------- |
| **Registry**              | Service storing schemas, ids, configs; backed by Kafka topic `_schemas`       |
| **Subject**               | Named history of schemas; unit of compatibility checking (`events.raw-value`) |
| **Version**               | Position in a subject's history (1, 2, 3); per subject                        |
| **Id**                    | Global schema handle embedded in messages                                     |
| **TopicNameStrategy**     | Subject = `<topic>-key` / `<topic>-value`                                     |
| **Compatibility level**   | Per subject (or global) rule the registry enforces on registration            |
| **auto.register.schemas** | Whether a producer may create schemas itself                                  |
| **Soft / hard delete**    | Hide versus remove the id mapping (dangerous)                                 |
| **Primary / follower**    | Registry instances; writes go to the primary                                  |

Quick REST card:

```
 register      POST /subjects/{s}/versions
 check only    POST /compatibility/subjects/{s}/versions/latest?verbose=true
 fetch by id   GET  /schemas/ids/{id}
 latest        GET  /subjects/{s}/versions/latest
 set level     PUT  /config/{s}   {"compatibility":"FULL_TRANSITIVE"}
 get level     GET  /config/{s}?defaultToGlobal=true
```

Rules of thumb:

1. Messages carry ids; humans use versions.
2. Set the compatibility level per subject, in code, before the first registration.
3. Producers look up; CI registers.
4. Classify registry I/O errors as transient and bad bytes as permanent.
5. Never hard-delete schemas that retained data may reference.
6. Protect `_schemas` like data.

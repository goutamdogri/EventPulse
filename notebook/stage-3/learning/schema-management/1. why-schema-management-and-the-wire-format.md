# Why Schema Management, Serialization Formats and the Wire Format

_Schema-management note 1 of 4 in the Stage 3 learning notes. Read the Stage 2 producer and consumer notes first if the terms topic, partition, offset and consumer group are not yet solid. This note explains **why** an uncontrolled format change breaks someone, what a "schema" really is in an event pipeline, how the common formats (JSON, Avro, Protobuf, JSON Schema) differ, how Avro's **writer and reader schema** resolution works, and what the bytes on `events.raw` look like once a registry is involved. It supports S3-F7 (all events on `events.raw` use a registered Avro schema; incompatible changes are rejected in CI)._

**No labs here.** The EventPulse code quoted is existing code in the repo. The Avro examples are written to be read, not run.

## 1. TL;DR

- A Kafka topic is a **contract between teams that never talk at deploy time**. The producer and the consumers are separate programs, released on separate days, by separate people. The only thing connecting them is the **shape of the bytes** on the topic.
- That shape is a **schema** whether you write it down or not. If you do not write it down, it still exists, but only in the heads of the authors and in the code paths that happen to parse it. Changing it is then a **silent breaking change** waiting for a Tuesday afternoon deploy.
- **Schema management** means: (1) the schema is written down in a machine-readable form, (2) it is stored in one shared place with versions, (3) every message says which schema it was written with, (4) changes are checked against rules **automatically** before they can ship.
- **Avro** (the Stage 3 choice) writes **no field names** into the data. The bytes are meaningless without the **writer's schema**. That is why messages carry a small **schema id** that points into a registry, and why the registry can enforce evolution rules: it has every writer schema, so it can ask "could a reader using schema B decode data written with schema A?".
- The Confluent wire format is `0x00` + **4-byte schema id** + **Avro binary body**. Five bytes of overhead replace repeating field names in every message.
- Two sides are involved in every decode: the **writer schema** (what the producer used, found by id) and the **reader schema** (what the consumer's code expects). Avro **resolves** one against the other. Evolution rules are exactly the rules for when that resolution succeeds.

> **One-line version:** _A schema is the contract on the topic; schema management makes the contract explicit, versioned, attached to every message, and checked by machines instead of by memory._

## 2. The mental model: a contract between strangers

Think of a **shipping container standard**. Ports, ships, trucks and cranes were built by thousands of companies that never meet. They interoperate because everyone agreed on the exact dimensions of the container and, crucially, on **how the standard may change**. Nobody is allowed to quietly make containers one inch wider, because some crane somewhere will jam.

| Shipping                                                  | Event pipeline                                |
| --------------------------------------------------------- | --------------------------------------------- |
| Container dimensions                                      | The schema: field names, types, optionality   |
| Ships, trucks, cranes (independent parties)               | Producers and consumers (independent deploys) |
| Standards body with numbered revisions                    | Schema registry with numbered versions        |
| Label on every container saying which revision it follows | Schema id embedded in every message           |
| Rule: "a new revision must still fit existing cranes"     | Compatibility mode (BACKWARD, FORWARD, FULL)  |
| Inspection before a new design is allowed into service    | Compatibility check in CI                     |

The lesson of the analogy: the standard is useful **because change is controlled**. A standard that anyone can change without asking is not a standard.

## 3. Why this problem exists: independent deploys

Inside a single program, changing a type is safe: the compiler finds every use, and everything ships together. A Kafka topic breaks that guarantee in three ways.

1. **Producers and consumers deploy independently.** `ingest-api` ships on its schedule, `consumer-sink` on another, a future analytics consumer on a third. There is no moment when all of them change simultaneously.
2. **Rolling upgrades mean mixed versions at the same time.** Even one service has old and new instances running together during a rollout. Two versions of the producer write to the same topic concurrently; two versions of the consumer read the same partitions concurrently (after a rebalance, the old instance and the new instance can each own different partitions of the same topic).
3. **The log retains data.** A message written last month under an old schema is still readable today (see Stage 2 retention). A consumer deployed today must understand data from every version still inside the retention window, and sometimes forever (compacted topics, replays, archives).

So at any moment the system holds **many schema versions in flight simultaneously**, written by one set of programs and read by another. "Just update both sides" is not an option, because there is no instant where "both sides" are updated.

```
 time ---------------------------------------------------------------->

 producers   [ v1 ][ v1 ][ v1/v2 ][ v2 ][ v2 ][ v2 ][ v2/v3 ][ v3 ]
                             ^ rolling deploy                ^ rolling deploy
 topic log   v1 v1 v1 v1 v1 v1 v2 v1 v2 v2 v2 v2 v2 v3 v2 v3 v3 ...
                         (mixed: old and new records interleaved)
 consumers   [ v1 ][ v1 ][ v1 ][ v1/v2 ][ v2 ][ v2 ][ v2 ][ v2/v3 ]
                                 ^ consumer upgraded later than producer
```

Each arrow of "who reads what" is a compatibility question. Schema management answers all of them with rules instead of coordination meetings.

## 4. Every pipeline already has a schema, written or not

Look at the EventPulse envelope as defined in `packages/kafka-config/src/envelope.ts`:

```ts
export interface EventEnvelope {
  event_id: string;
  tenant_id: string;
  type: string;
  occurred_at: string;
  schema_version: number;
  payload: Record<string, unknown>;
}
```

The producer does `JSON.stringify(envelope)`. The consumer does `JSON.parse(...)` and reads `event_id`, `tenant_id` and so on. That interface **is** a schema. It is merely:

- **implicit** (it lives in a TypeScript interface and in the parsing code, not in a shared artifact),
- **unenforced at the boundary** (nothing stops the producer sending `eventId` or omitting `tenant_id`; the consumer finds out at runtime, as a poison message),
- **unversioned** (a change is a code change; the topic has no record of which shape a given message has, except the `schema_version` field that humans maintain by hand),
- **private** to each side (the producer's interface and the consumer's interface are two copies that can drift apart).

This is called **schema-on-read**: structure is imposed by whoever reads, at read time, with no central authority. It is flexible, and it is exactly how silent breakage happens. **Schema-on-write** moves the structure to the moment of writing: the producer cannot publish something that does not match the registered schema, and every reader can look up what a message means.

|                                  | Schema-on-read (JSON today)                 | Schema-on-write (Avro + registry)               |
| -------------------------------- | ------------------------------------------- | ----------------------------------------------- |
| Where structure lives            | In each consumer's parsing code             | In a shared, versioned registry                 |
| Bad data detected                | By the consumer, later, as a poison message | By the producer, immediately, before it is sent |
| Format change reviewed by        | Nobody, unless humans remember              | A compatibility check that blocks the change    |
| What a message says about itself | Nothing (maybe a manual `schema_version`)   | The id of the exact schema it was written with  |
| Cost                             | Zero up front, large later                  | Some up-front design and tooling                |

## 5. What breaks when a format changes without control

Concrete failure modes, each of which has appeared in real incidents. Treat them as the catalogue that the later notes' rules are designed to prevent.

| Change                                                                    | Who notices         | How it fails                                                                                                                               |
| ------------------------------------------------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Producer renames `occurred_at` to `occurredAt`                            | Consumer            | Consumer reads `undefined`; inserts null timestamps or throws. Silent data corruption if the column is nullable.                           |
| Producer drops an optional field the consumer relied on                   | Consumer            | Behavior silently changes (a feature treats "missing" as "false").                                                                         |
| Producer changes `amount` from integer to string                          | Consumer            | Parse error, or worse, `"5" + 1 = "51"` string concatenation in JavaScript.                                                                |
| Producer adds a required field                                            | Old consumers       | Usually ignored in JSON; in strict formats, old readers must still cope with the extra data.                                               |
| Consumer starts requiring a new field                                     | Old data in the log | Replaying old messages fails: the field was never written. Consumer crashes on message 1 of the replay.                                    |
| Enum gains a new value                                                    | Old consumers       | Old consumer hits an unknown symbol; in Avro this is a hard decode error unless a default is declared.                                     |
| Semantics change with the same shape (`price` was dollars, becomes cents) | Everyone            | **No tool catches this.** Schema checks guard structure, not meaning. Needs a new field name or a new version with explicit documentation. |

Two observations that organise the rest of the series:

1. **Failures happen in both directions.** A new consumer can fail on old data (it expects something old data never had). An old consumer can fail on new data (it meets something it never heard of). Each direction has a name: **backward** and **forward** compatibility (note 3).
2. **The blast radius is the topic.** One bad producer deploy poisons the shared log, and every consumer, including consumers added months later and consumers replaying history, inherits the problem. Fixing it by redeploying the producer does not remove the bad records already in the log. This asymmetry (cheap to break, expensive to repair) is the strongest argument for a **gate before publishing** rather than detection after.

> **Semantic changes are out of scope for compatibility checkers.** A checker sees `price: int` before and after; it cannot see that the unit changed. Policy has to cover this separately: never change the meaning of an existing field; add a new field.

## 6. The time dimension: a log keeps old data alive

In a request/response API, an old client talks to a new server **now**, and you can often sunset the old client after a deprecation period. A log is different: **data is a persistent client of every past schema.**

```
 events.raw, retention 7 days (default Stage 2 setting may differ)

 day 1        day 2        day 3        day 4        day 5
 [v1 v1 v1]   [v1 v1 v2]   [v2 v2 v2]   [v2 v2 v3]   [v3 v3 v3]
 ^ a consumer started from earliest today must read v1, v2 and v3 in one pass
```

Consequences:

- A **new consumer group** reading from the earliest offset sees every version in retention.
- A **replay** (Stage 3 S3-F2, "replaying any range of the log leaves stored data unchanged") reads old records through today's consumer code.
- A **DLQ message** parked for two weeks (S3-F5, S3-F6) is replayed under a newer consumer; it was written with an older schema.
- **Compacted topics** and **archives** (long-lived topics, S3 dumps) have effectively infinite retention. Their oldest record is as old as the topic.

This is why the _transitive_ compatibility modes (note 3) exist, and why "just compare with the previous version" is not always enough. It is also why, when you think about schema changes, you must ask: **how old is the oldest data I must still read, and how old is the oldest code that must still read new data?**

## 7. What a schema management system must give you

Four capabilities, in order of importance. The remaining notes map one-to-one onto them.

| #   | Capability                                                                                                       | Provided by                                                                          | Note      |
| --- | ---------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------- |
| 1   | **A written, machine-readable contract**                                                                         | An IDL such as Avro `.avsc` files in git                                             | this note |
| 2   | **A shared, versioned store** where every schema lives, and **a pointer in every message** to the schema it used | Schema registry: subjects, versions, ids                                             | note 2    |
| 3   | **Rules for what a change may do**, evaluated mechanically                                                       | Compatibility modes                                                                  | note 3    |
| 4   | **Enforcement in the delivery path** so that rules apply to every change, every time                             | CI check, registry config as code, producers that cannot self-register in production | note 4    |

Capability 4 is easy to skip and fatal to skip. A compatibility mode that nobody runs before merging is documentation, not protection. The Stage 3 PRD calls out the anti-pattern directly: "Registering schemas manually with no CI check, so compatibility depends on memory."

## 8. Serialization formats compared

The schema registry supports several formats. EventPulse picks Avro for the first implementation; knowing why makes the trade-offs concrete.

| Property                            | JSON (today)                          | JSON Schema                                            | Avro                                                  | Protobuf                                                                              |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Human readable on the wire          | Yes                                   | Yes                                                    | No (binary)                                           | No (binary)                                                                           |
| Schema required to decode           | No                                    | No (schema validates; decode is plain JSON)            | **Yes, the writer schema is mandatory**               | Needs the `.proto` to know field names; field **numbers** identify fields in the data |
| Field identity in data              | Field **name** (repeated per message) | Field **name**                                         | **Position** in writer schema (no names, no tags)     | Field **number** (tag)                                                                |
| Size                                | Largest                               | Largest                                                | Compact                                               | Compact                                                                               |
| Rename a field safely               | No (name is identity)                 | No                                                     | Only with **aliases** (reader-side)                   | **Yes**, number is identity (names are not on the wire)                               |
| Evolution model                     | Convention                            | Validation rules; compatibility checks are more subtle | Reader/writer **schema resolution** with defaults     | Unknown fields skipped; numbers must never be reused                                  |
| Compatibility tooling in registries | n/a                                   | Supported, newer                                       | **Most mature**                                       | Supported                                                                             |
| Natural fit for Node/TypeScript     | Native                                | Native                                                 | Library (e.g. `avsc` and registry client)             | `protobufjs`, `ts-proto`, others                                                      |
| Notes                               | Easy, fragile                         | Adds validation, still verbose                         | Needs the schema at read time; strong evolution story | Needs discipline about field numbers; popular in RPC                                  |

**Why Avro for Stage 3:** the PRD's reasoning is that registry compatibility rules and tooling are the most mature for Avro, and the **reader/writer resolution model** makes the compatibility rules easy to state precisely: they are exactly the rules under which resolution succeeds. **Protobuf** is flagged as a Stage 8 comparison (size, CPU and ergonomics under load).

**Why not just keep JSON and add JSON Schema validation?** You can, and many teams do. But you still need the registry, ids, and the compatibility checks, and you keep JSON's size and parse cost. The Stage 3 goal is to learn the evolution rules in the format where they are cleanest.

> **A trap with JSON-plus-registry:** compatibility of JSON Schema is harder to define (it depends on whether `additionalProperties` is open or closed, for example), so "compatible" can mean different things to different tools. Avro's closed, positional model avoids that ambiguity.

## 9. Avro in detail

You do not need to be an Avro expert, but you must read a schema fluently, because the rest of the series reasons about field-level changes.

### 9.1 A schema is JSON that describes types

```json
{
  "type": "record",
  "name": "EventEnvelope",
  "namespace": "io.eventpulse.events",
  "doc": "An event accepted by the ingest API.",
  "fields": [
    { "name": "event_id", "type": "string" },
    { "name": "tenant_id", "type": "string" },
    { "name": "type", "type": "string" },
    {
      "name": "occurred_at",
      "type": { "type": "long", "logicalType": "timestamp-millis" }
    },
    { "name": "schema_version", "type": "int" },
    { "name": "payload_json", "type": "string" }
  ]
}
```

### 9.2 Types you will meet

| Kind          | Examples                                                                                 | Notes                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Primitive     | `null`, `boolean`, `int` (32-bit), `long` (64-bit), `float`, `double`, `bytes`, `string` | `int` and `long` are zig-zag varint encoded: small numbers are 1 byte                                 |
| Complex       | `record`, `enum`, `array`, `map`, `fixed`, `union`                                       | `map` keys are always strings                                                                         |
| Logical types | `timestamp-millis`, `date`, `uuid`, `decimal`                                            | A logical type is an annotation over a primitive; the **underlying** type is what resolution compares |
| Union         | `["null", "string"]`                                                                     | Written as a branch index followed by the value                                                       |

### 9.3 Optional fields are unions with null

Avro has no "optional" keyword. An optional field is a **union that includes `null`**, normally with a **default**:

```json
{ "name": "source", "type": ["null", "string"], "default": null }
```

Rule to remember: **the default must match the first branch of the union.** So `null` goes first when the default is `null`. Putting `"string"` first with a `null` default is a schema error.

### 9.4 Defaults are the whole evolution story

A field's **default value** is what a reader uses when the writer's data does not contain that field. This single feature is what makes evolution possible:

- A reader may _add_ a field only if it can fill it from a default for old data.
- A reader may _drop_ a field freely (it just ignores the bytes).
- A field with no default is **required to be present in whatever data the reader sees**.

Remember: _the default is for the **reader**'s benefit, at decode time. It is not applied when writing._ A producer must still supply a value for every field (or rely on the library applying the default at construction), and the bytes always contain every writer-schema field.

### 9.5 Binary encoding: no names, no tags

Avro encodes a record as the **concatenation of its fields in schema order**. No field names. No type tags. No field numbers. No delimiters. A rough picture for `{event_id: "a1", schema_version: 3}` with two fields:

```
 [ len=2 ][ 'a' '1' ][ 3 zigzag-varint ]
   string "a1"          int 3
```

The reader knows the layout _only_ because it has the schema. This is why:

1. Avro data is **small** (no repeated names).
2. Avro data is **unreadable without the writer's schema**. With the wrong schema you get garbage or an exception, not a helpful error.
3. The **schema must travel with the data or be findable from it**. Files (Avro Object Container Files) embed the schema in the header. Streams cannot afford that per message; they embed a **schema id** (section 11).

## 10. Writer schema and reader schema: schema resolution

The heart of Avro evolution. When data is decoded, **two** schemas are in play:

- **Writer schema**: the exact schema the producer used to encode this message. Found via the id in the message.
- **Reader schema**: the schema the consumer's code wants to see. Compiled into or loaded by the consumer.

They may differ. **Schema resolution** is the algorithm that reads bytes laid out by the writer schema and presents them in the shape of the reader schema. The rules, simplified:

| Situation                                          | What the resolver does                                                                                                                                                          |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Field in both, same type                           | Read it.                                                                                                                                                                        |
| Field in **writer only**                           | **Skip it.** (It knows the writer's layout, so it knows how many bytes to skip.)                                                                                                |
| Field in **reader only**, reader has a **default** | Fill in the default.                                                                                                                                                            |
| Field in **reader only**, **no default**           | **Error: schema resolution fails.**                                                                                                                                             |
| Field in both but types differ                     | OK only for specific **promotions** (`int` to `long`/`float`/`double`, `long` to `float`/`double`, `float` to `double`, `string` and `bytes` interchangeable). Otherwise error. |
| Field has a different name in the writer           | Matched if the reader field lists the writer's name in its **aliases**. Otherwise treated as two unrelated fields (one skipped, one needs a default).                           |
| Enum symbol in writer not in reader                | Error unless the reader enum declares a **default** symbol.                                                                                                                     |
| Union branches                                     | Each writer branch must be resolvable to some reader branch.                                                                                                                    |

A worked example:

```
Writer schema (v1):                 Reader schema (v2):
  event_id : string                   event_id : string
  tenant_id : string                  tenant_id : string
  type : string                       type : string
                                      source : ["null","string"] default null   <- new

 Bytes written with v1 ---> resolution ---> reader sees:
   event_id, tenant_id, type     from the bytes
   source = null                 from the default       <- works
```

Reverse direction:

```
Writer schema (v2):                 Reader schema (v1):
  event_id, tenant_id, type           event_id, tenant_id, type
  source (new)

 Bytes written with v2 ---> resolution ---> reader sees:
   event_id, tenant_id, type     from the bytes
   source                        skipped (reader has no such field)   <- works
```

Both directions worked here because the new field had a **default**. If `source` had no default, the first direction (new reader, old data) would fail: the reader needs a value and the data has none.

### The sentence to memorise

> **Compatibility is a question about schema resolution succeeding: "Can a reader with schema R decode data written with schema W?"** BACKWARD, FORWARD and FULL differ only in _which_ schema plays R and which plays W (note 3).

### 10.1 Who does the resolving

The deserializer in the consumer. Given `(bytes, reader schema)`:

1. Read the schema id from the message, ask the registry (or the local cache) for the writer schema.
2. Build (and cache) a resolver for the pair `(writer id, reader schema)`.
3. Decode using the resolver.

The first message from a new writer id costs a registry call plus resolver construction. Every later message reuses the cached resolver.

If you do **not** supply a reader schema, many libraries decode using the writer schema alone. That is simple, and it gives you whatever shape the producer wrote, so your code must cope with every version. Supplying a reader schema lets the library **normalise** all versions into the shape your code expects. This is the recommended style for consumers that cannot tolerate shape variance.

## 11. Why the bytes alone are not enough: the schema id

Avro bytes need the writer schema. Options for getting it to the reader:

| Option                                                         | Problem                                                        |
| -------------------------------------------------------------- | -------------------------------------------------------------- |
| Embed the full schema in every message                         | Kills the size advantage; schema is often larger than the data |
| Agree on one schema forever, out of band                       | That is "no evolution"                                         |
| Ship the schema in a header                                    | Same size problem, and headers are not covered by the contract |
| Embed a **small id** and keep schemas in a **shared registry** | Cheap per message; the registry becomes a dependency (note 2)  |

The registry option wins and gives extra benefits: one authoritative store, a place to run compatibility checks, and a global catalogue of which topic uses which shape. Its cost is operational: the registry is now on the path of producers (on first use of a schema) and consumers (on first sight of an id). Note 2 treats that dependency, including the "registry unavailable" experiment (C11).

## 12. The Confluent wire format, byte by byte

The registry-aware serializers from Confluent (and compatible libraries in other languages, such as `@kafkajs/confluent-schema-registry`) write each message value as:

```
 byte 0        bytes 1..4                 bytes 5..n
+--------+----------------------------+--------------------------------+
|  0x00  |  schema id (int32, big-end) |  Avro binary body (writer layout) |
+--------+----------------------------+--------------------------------+
 magic     which writer schema           the actual event
 byte
```

- **Magic byte `0x00`**: format version of the _framing_. A deserializer that sees anything else knows this is not Confluent-framed data (for example plain JSON, whose first byte would be `{` = `0x7B`) and can fail fast with a clear message instead of decoding garbage.
- **Schema id**: 4 bytes, **big-endian**. A global id in the registry. Example: id 42 is `00 00 00 2A`.
- **Body**: the Avro binary encoding with the layout of the schema identified by the id.

An example in hex for a tiny schema with one string field, value `"hi"`, schema id 7:

```
00  00 00 00 07  04 68 69
|   |            |  |  +-- 'i'
|   |            |  +----- 'h'
|   |            +-------- length 2, zigzag-encoded = 4
|   +--------------------- schema id 7
+------------------------- magic byte
```

Practical consequences:

1. **A consumer that does `JSON.parse(value.toString())` on a framed message fails.** The migration from JSON to Avro is a **breaking change on the topic itself**, not a compatible evolution. Plan it as a new topic, or a cutover with dual-format handling (note 4, section on breaking changes).
2. **Poison messages change character.** A message that is not framed, or whose id is unknown to the registry, cannot be decoded at all. That is a **permanent** failure and belongs in the DLQ with diagnostic metadata (S3-F5), not in an infinite retry loop.
3. **The id is not the version.** Id is global across the registry; version is per subject (note 2). Do not store "schema version = id" assumptions.
4. **Keys can be framed too.** Key serializers use the same format (`<topic>-key` subject). EventPulse keys are plain strings (`tenant_id` or `event_id`, per `KEY_MODES`), and that is fine; no need to Avro-encode the key.
5. **Headers are outside the contract.** `received_at`, `request_id` and `schema_version` headers in the current code are not covered by the Avro schema or by compatibility checks. Treat them as a separate small contract; do not hide important structure there.

## 14. Modelling the EventPulse envelope in Avro

One design decision deserves its own section because it affects everything that follows: **what to do with `payload`**.

The current TypeScript type is `payload: Record<string, unknown>`: arbitrary tenant-supplied JSON. Avro has **no "any" type**. Options:

| Option                          | Shape                                                          | Pros                                                                              | Cons                                                                                                                         |
| ------------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **A. JSON string**              | `payload_json: string`                                         | Simple, flexible, tenants can send anything, and the envelope schema stays stable | The registry cannot check anything _inside_ the payload; the payload is an opaque blob to Avro; no size saving for that part |
| **B. Map of string to a union** | `map<union{null,string,long,double,boolean,...}>`              | Flat key/value only; the registry sees structure                                  | Cannot express nested objects without recursion; awkward to produce and consume                                              |
| **C. Per-event-type schemas**   | Union of record types, one per `type`, or one subject per type | Strong typing for known event types, true evolution of payload shapes             | Requires tenants to adopt known types; large design effort; schema explosion                                                 |
| **D. Bytes**                    | `payload: bytes` (JSON or anything)                            | Format-agnostic                                                                   | Same opacity as A, less debuggable                                                                                           |

**Recommended starting point for Stage 3: option A.** Keep the _envelope_ strongly typed and evolvable (id, tenant, type, timestamps, version) and treat the tenant payload as an opaque JSON string, validated separately at the API against per-type JSON schemas if you want. This isolates what you are learning (envelope evolution rules) from the unrelated problem of typing free-form tenant data.

Be explicit in your notes that this is a **boundary**: schema compatibility covers the envelope; the _contents_ of `payload_json` are governed by the API's validation and by the business `schema_version`.

### Two different "versions" to keep straight

| Name                                | Meaning                                                                               | Where it lives                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| **Registry schema version**         | The numbered version of the Avro schema of the envelope within a subject (1, 2, 3...) | The registry; implied by the schema id in each message |
| **Business `schema_version` field** | A field in the envelope, set by the producer, describing the event payload revision   | Inside the data                                        |

They are independent. The registry version changes when the **envelope's Avro schema** changes; the business field changes when the **tenant payload convention** changes. Mixing them up causes real confusion ("we bumped schema_version to 2, why didn't the registry get a new version?"). Document which one each consumer uses for which decision.

## 15. Common confusions

1. **"A schema is validation."** Validation (reject bad input) is one use. The deeper use is the **contract plus evolution rules**: what readers can rely on when writers change.
2. **"Avro data contains its field names."** It does not. Without the writer schema it is unreadable. That is why the id exists.
3. **"The schema id is the version."** No. Ids are global across the registry; versions are per subject (note 2).
4. **"If it compiles, it is compatible."** The generated TypeScript type passing a compiler check says nothing about whether old data decodes with the new schema.
5. **"Adding a field is always safe."** Safe only if the field has a default (so new readers can decode old data), and even then only for some consumers (note 3).
6. **"JSON is schema-less, so it cannot break."** It breaks more, just later and more quietly.
7. **"The compatibility checker will catch a unit change."** It cannot; semantics are invisible to structure checks.
8. **"Headers carry the schema so I need not worry."** Headers are not part of the registered contract.
9. **"Fixing the producer fixes the topic."** Records already written stay in the log until retention removes them.

## 17. Cheat sheet

| Term                  | Meaning                                                                 |
| --------------------- | ----------------------------------------------------------------------- |
| **Schema**            | Machine-readable definition of a message's structure                    |
| **Schema-on-read**    | Structure imposed by each reader at parse time (plain JSON)             |
| **Schema-on-write**   | Structure enforced when producing; readers look it up (Avro + registry) |
| **Writer schema**     | The schema the producer used to encode a message                        |
| **Reader schema**     | The schema the consumer's code expects                                  |
| **Schema resolution** | Avro's algorithm for reading writer-layout bytes into reader shape      |
| **Default**           | Reader-side fallback when the writer's data lacks the field             |
| **Alias**             | Alternative name letting a reader match a renamed writer field          |
| **Union**             | Avro type that can be one of several branches, e.g. `["null","string"]` |
| **Wire format**       | `0x00` + 4-byte big-endian schema id + Avro body                        |
| **Schema id**         | Global registry identifier embedded in each message                     |

```
 Producer                         Registry                          Consumer
    |  register / look up id  --->   |                                   |
    |  <--- id=42                    |                                   |
    |  encode: 00 0000002A <avro>    |                                   |
    |---------------- Kafka topic ----------------------------------->   |
    |                                |   <--- fetch schema for id 42 ---- |
    |                                |   ---- writer schema ----------->  |
    |                                |        resolve(writer, reader)     |
```

Rules of thumb:

1. Write the schema down; keep it in git next to the code that uses it.
2. Optional means `["null", T]` with `default: null`, null first.
3. A reader needs a default for any field the writer may not have written.
4. Never change the meaning of an existing field. Add a new one.
5. Think in time: the log holds every version still within retention.
6. The registry version, the schema id and the business `schema_version` are three different things.

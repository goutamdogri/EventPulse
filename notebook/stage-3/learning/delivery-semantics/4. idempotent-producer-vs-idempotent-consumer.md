## 1. TL;DR

- **Idempotent producer** (`enable.idempotence=true`) is a **Kafka client/broker feature**. It stops **duplicates caused by the producer library's own automatic retries** within **one producer session**, on **one partition at a time**, and it also keeps order across those retries. Cost is almost nothing. It is **on by default** in modern clients (Kafka 3.0+).
- **Idempotent consumer** is a **design property of your application**, not a Kafka setting. It means **processing the same message twice has the same effect as processing it once**. It is built with a unique key and a dedup mechanism in the **destination**.
- They protect **different hops** against **different causes**:

|                 | Idempotent producer                                  | Idempotent consumer                                             |
| --------------- | ---------------------------------------------------- | --------------------------------------------------------------- |
| Hop             | app -> broker                                        | broker -> app -> database                                       |
| Cause removed   | Library retry after a lost produce response          | Reprocessing after a crash, a rebalance, a replay               |
| Mechanism       | Producer id + sequence numbers checked by the broker | Unique key on `event_id`, inbox table, or atomic offset storage |
| Who builds it   | Kafka (you flip a config)                            | You                                                             |
| Scope of memory | One session, one partition, last 5 batches           | As long as you choose, up to forever                            |

- The producer setting **does not** stop: an **application** retrying a request (a new `send()`), a **producer restart** (new PID), **two instances** sending the same event, **consumer reprocessing**, DLQ or retry replays, or an operator replay.
- So the layered answer is: **idempotent producer** (cheap, removes one class) **+ API idempotency key** (removes client retries) **+ idempotent consumer/sink** (removes everything that reaches storage). The last layer is the **guarantee**; the others are **optimizations**.
- A system with only the idempotent producer is **still at-least-once with duplicates**. A system with an idempotent consumer is **correct even without** the idempotent producer (just noisier).

> **One-line version:** _The idempotent producer cleans up after the client library; the idempotent consumer cleans up after everything else._

## 2. The mental model

A nightclub with **two doormen**.

| Doorman                                | Where he stands                                 | What he checks                                                                                                                                                                                                                                                                                       |
| -------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Door 1 (the producer-side doorman)** | The street entrance, working a **single shift** | Gives each guest in a group a **ticket number in order** (1, 2, 3...). If someone is pushed in twice in a stampede he sees "number 7 again" and waves it off. He remembers only **the last few numbers and only this shift**. A new shift has a new doorman who knows none of the old numbers.       |
| **Door 2 (the consumer-side doorman)** | The VIP lounge, the **permanent guest list**    | Checks each person's **name** against the permanent list. If the name is already inside, he says "already in". He has a **memory forever**, and he recognizes the same person **regardless of which street door they used, or how many times they left and re-entered, or which shift let them in**. |

Door 1 catches **stampede duplicates within one shift** (the library's retries). Door 2 catches **everything else**: the same guest coming back after the shift change, the same guest sent by two different promoters (two producers), the same guest brought back by the manager on purpose (a replay).

You need Door 2 for **correctness**. Door 1 is a courtesy that keeps the crowd down.

## 3. The word "idempotent" is used for two different things

| Use                                 | Meaning                                                                                    | Scope                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| **Idempotent producer**             | The **broker** will not append the same _batch_ twice when the _client library_ resends it | The wire protocol between one producer session and one partition |
| **Idempotent consumer / operation** | The **effect** of processing a message does not change when processed again                | The application's business result                                |

The shared word hides a big difference:

- The producer feature is about **bytes in the log** (do not write the same batch twice).
- The consumer property is about **business effects** (do not apply the same event twice), even though the log legitimately contains the message twice.

Because of this, the **idempotent producer cannot be a substitute** for an idempotent consumer: the log can **legitimately** hold two copies of the same logical event (see section 5), and then the consumer has to decide what to do.

## 4. The idempotent producer, scoped precisely

(Full mechanism: Stage 2 producer note 3. This is the compact, exam-ready version.)

### 4.1 How it works in five lines

1. At startup the broker assigns the producer a **PID** (producer id) and an **epoch**.
2. The producer attaches a monotonically increasing **sequence number**, **per partition**, to every batch.
3. The partition leader stores the **last sequence numbers it accepted** for each `(PID, partition)` (the last **5** batches, matching the max in-flight limit).
4. If a batch arrives whose sequence was **already accepted**, the leader **does not append it again** and replies **success**.
5. If a batch arrives with a sequence **beyond the next expected** one, the broker rejects it (`OutOfOrderSequenceException`), which preserves order.

### 4.2 The one scenario it fixes

```
 producer:  send batch B (seq 42)  ------------------->  leader appends B at offsets 500-509, replicates
                                    <---- X response lost
            (timeout) retry batch B (seq 42, same PID) ->  leader sees seq 42 already stored
                                                            replies success, appends nothing
```

Result: the log has **one** copy. Without the feature, there would be **two** copies at offsets 500-509 and 510-519.

### 4.3 Requirements and defaults

- `acks=all`, `retries > 0`, `max.in.flight.requests.per.connection <= 5`. Conflicting settings cause a configuration error at startup (a sign the safety net is explicit).
- Defaults: **enabled by default from Kafka clients 3.0**; older clients require the setting. Librdkafka-based clients (including the one EventPulse uses) also expose it, and EventPulse sets it explicitly with `KAFKA_IDEMPOTENT` (default true) and rejects `idempotent && acks !== -1` in config validation.
- Cost: a few bytes of metadata per batch and a small in-memory table on the leader. Negligible.

### 4.4 The precise scope statement

> The idempotent producer guarantees that **retries performed by the producer client for a given PID and partition** do not create duplicate records in that partition's log, **for the lifetime of that PID**, and that records of that PID are appended in the order sent.

Every piece of that sentence is a limit:

| Phrase                                     | Limit                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------- |
| "retries performed by the producer client" | Not retries of your application code                                      |
| "for a given PID"                          | Not across producers, not across restarts                                 |
| "and partition"                            | Not duplicates across partitions (a retry that changes the key/partition) |
| "for the lifetime of that PID"             | A restart or a fatal error resets the memory                              |
| "last 5 batches"                           | Not arbitrarily old resends                                               |

## 5. What the idempotent producer does not stop

This section is the heart of the Stage 3 plan line: _"It does not stop an application retrying a request or a consumer reprocessing after a crash."_

### 5.1 Application-level retry

```
client ──POST /events {id: e1}──> ingest-api ──send()──> Kafka   (appended)
client <── 503 / timeout  (API crashed or load balancer cut it)
client ──POST /events {id: e1}──> ingest-api ──send()──> Kafka   (appended AGAIN)
```

The second `send()` is a **brand new record** with a **new sequence number** (or from a different PID if another instance handled it). From the broker's view these are two legitimate, separate writes. The feature has no way to know they are "the same event" because it identifies batches by sequence, **not by business id**.

### 5.2 `send()` reported failure, application resends

The producer reports "delivery timeout exceeded" after it gave up. The record may or may not be in the log. If the application reacts by calling `send()` again, that is a **new send** (note 2, section 9.2). Duplicate possible.

### 5.3 Producer restart

A process restart yields a **new PID** (the plain idempotent producer has no stable identity; only a `transactional.id` gives one). Records the previous incarnation had in flight and that the new one re-sends (for example from an upstream buffer or a replayed request) are unrelated to the old ones.

### 5.4 Multiple producers

Two `ingest-api` instances both handle retries of the same client request. Two PIDs, two sequence spaces, no cross-detection.

### 5.5 Consumer reprocessing

Totally outside its scope: the producer feature ends when the record is in the log. A consumer that crashes after the DB commit and before the offset commit re-reads records that exist **once** in the log and processes them twice. The log has no duplicate; the **processing** does.

### 5.6 Replays and re-publishes

A DLQ replay tool, a retry-topic republish, a manual re-injection: each produces a **new record** in the log with the same business id. Treated as new by the broker.

### 5.7 Poison record loops

A consumer that fails and re-publishes a message to a retry topic repeatedly creates **new** records each cycle. Not producer retries.

### 5.8 The summary table

| Duplicate source                                        | Removed by `enable.idempotence`? |
| ------------------------------------------------------- | -------------------------------- |
| Library retry after lost produce response, same session | **Yes**                          |
| Application retry (new `send()`)                        | No                               |
| Client HTTP retry creating a second POST                | No                               |
| Producer restart / new PID                              | No                               |
| Two producer instances                                  | No                               |
| Consumer crash between DB commit and offset commit      | No                               |
| Rebalance overlap                                       | No                               |
| DLQ / retry / manual replay                             | No                               |
| Mirror or CDC resend                                    | No                               |

## 6. The idempotent consumer: what it is

### 6.1 Definition

> A consumer is **idempotent** if applying the same message **any number of times** leaves the destination in the **same state** as applying it **once**.

Note what it does **not** require: it does not require that the message arrives once, that the consumer never crashes, or that the consumer never re-reads. It **accepts** at-least-once delivery and neutralizes the repeats.

### 6.2 Where the idempotence lives

Almost never in the consumer's _memory_ (it restarts and forgets). It lives in the **durable destination**, as one of:

1. **The destination's uniqueness rules** (primary key / unique index + conflict handling).
2. **A durable record of processed ids** committed **atomically** with the effect (inbox).
3. **A durable record of progress** committed atomically with the effect (offsets stored with data).
4. **A naturally idempotent write** (set, overwrite by key).

### 6.3 What the consumer must still do

The consumer is still responsible for the **order** of operations: **effect first, progress second** (note 1, section 9). Idempotence repairs duplicates, never a loss caused by committing the offset too early.

```
Correct:   process -> write to DB (idempotent) -> COMMIT -> commit offset
Wrong:     commit offset -> process -> crash     => LOSS, which no idempotence can repair
```

## 7. Techniques for an idempotent consumer

### 7.1 Technique A: unique key with `ON CONFLICT DO NOTHING` (EventPulse)

```sql
INSERT INTO events (event_id, tenant_id, ...)
SELECT * FROM unnest($1::uuid[], $2::text[], ...)
ON CONFLICT (event_id) DO NOTHING
RETURNING received_at;
```

- The **primary key** on `event_id` makes a second insert of the same event a **no-op**.
- `RETURNING` yields only the **newly inserted** rows, so `attempted - inserted` = **duplicates absorbed**, which the sink counts (`services/consumer-sink/src/sink/batch-writer.ts`). That is how requirement S3-F3 ("duplicates are counted, never silently swallowed") is met.
- No separate round trip, no TTL, no race: the **check and the write are one atomic operation** inside the database.
- Works because the "effect" is _the row itself_. Aggregates are **derived** from stored events, so a duplicate row never inflates them.

### 7.2 Technique B: upsert with a version guard

For effects that **update** state:

```sql
INSERT INTO device_state (device_id, value, version)
VALUES ($1, $2, $3)
ON CONFLICT (device_id) DO UPDATE
   SET value = EXCLUDED.value, version = EXCLUDED.version
 WHERE device_state.version < EXCLUDED.version;
```

A repeated or **stale** (older) message does not overwrite newer data. This also protects against **out-of-order** delivery, which duplicates often accompany (a delayed original arriving after its retry).

### 7.3 Technique C: inbox table (for non-idempotent effects)

When the effect is `balance = balance + amount`:

```sql
BEGIN;
INSERT INTO inbox (message_id) VALUES ($1);     -- PRIMARY KEY (message_id)
-- if this INSERT conflicts: ROLLBACK or skip; the message was already applied
UPDATE accounts SET balance = balance + $2 WHERE id = $3;
COMMIT;
```

The id insert and the effect are **one DB transaction**: either both happen or neither. A repeat fails the insert and the effect is skipped. This converts a non-idempotent effect into an idempotent one. The inbox grows; it needs a **retention policy** aligned with how long duplicates can arrive.

### 7.4 Technique D: store offsets in the destination

Write `(topic, partition, next_offset)` in the **same DB transaction** as the effect. On startup, `seek` each partition to the stored offset rather than the Kafka-committed one. Effect and progress become **one atomic fact** (note 1 section 9 third row). More machinery (you handle assignment and rebalance), but it gives true exactly-once effect even for non-idempotent writes.

### 7.5 Technique E: Redis `SET NX EX` (cache-speed dedup)

`SET idem:{tenant}:{id} 1 NX EX 86400`: the first caller gets OK and proceeds; later callers get nil and skip. Fast and cheap, with **two weaknesses**: the key **expires** (TTL window), and Redis can **lose** data on restart or failover. Therefore it is a **front-line filter** at the API, **not** the final guarantee. The Postgres constraint remains the truth.

### 7.6 Technique F: deterministic output keys

For file or object-store writes, name the output by a **deterministic key** (for example `events/{tenant}/{date}/{batch_id}.parquet`). A re-run overwrites the same object instead of creating a second one.

### 7.7 Choosing

| Effect is...                             | Technique                                             |
| ---------------------------------------- | ----------------------------------------------------- |
| Insert of an event row                   | A: unique key + `ON CONFLICT DO NOTHING`              |
| Overwrite of current state               | B: upsert with version guard                          |
| Increment, append-to-balance, send email | C: inbox, or D: offsets in DB                         |
| Call to an external API                  | Idempotency key header, plus C to remember the result |
| Object/file write                        | F                                                     |
| Fast early rejection                     | E (never alone)                                       |

## 8. Side by side comparison

| Dimension                     | Idempotent producer                                                                     | Idempotent consumer                                                                            |
| ----------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| **Type**                      | Kafka configuration                                                                     | Application design                                                                             |
| **Property name**             | `enable.idempotence`                                                                    | (none; you define it)                                                                          |
| **Protects**                  | Log contents (no duplicate batches)                                                     | Business effect (no duplicate results)                                                         |
| **Located in**                | Broker partition leader + client                                                        | Destination (DB, API, store)                                                                   |
| **Identity used**             | `(PID, epoch, partition, sequence)`                                                     | Business id (`event_id`, `Idempotency-Key`)                                                    |
| **Identity set by**           | The client library, automatically                                                       | The origin application, deliberately                                                           |
| **Memory**                    | Last 5 batches per PID/partition, in the broker                                         | As long as the unique constraint, inbox or key exists                                          |
| **Memory survives**           | Broker restart (stored in the log / snapshots) but **not** a producer restart (new PID) | Everything (durable)                                                                           |
| **Covers retries from**       | The client library                                                                      | Any source                                                                                     |
| **Covers app retries**        | No                                                                                      | Yes                                                                                            |
| **Covers crash reprocessing** | No                                                                                      | Yes                                                                                            |
| **Covers rebalance overlap**  | No                                                                                      | Yes                                                                                            |
| **Covers replays**            | No                                                                                      | Yes                                                                                            |
| **Fails when**                | New PID, new `send()`, different partition                                              | Key missing, key not unique, wrong scope, TTL expired (for Redis), key different on each retry |
| **Cost**                      | ~0                                                                                      | Index, extra write, memory for inbox/TTL store                                                 |
| **Required for correctness?** | No (an optimization and ordering aid)                                                   | **Yes**                                                                                        |
| **If removed**                | More duplicate rows reach the consumer, which absorbs them                              | Duplicate rows or double effects appear in storage                                             |
| **Typical default**           | On in modern clients                                                                    | You must build it                                                                              |

The bottom rows state the relationship: **the consumer-side property is the one that carries the correctness guarantee.**

| F   | Rebalance overlap                                  | no                  | no                                           | **yes**                               |

## 10. Walkthroughs: five failures, traced

For each, find the layer that absorbs it. Imagine event `e1` with `event_id = X`.

### 10.1 Lost produce response (library retry)

1. `ingest-api` sends batch containing `e1`; broker appends; response lost.
2. Client library retries the same batch (same PID, same sequence).
3. Broker recognizes the sequence, replies success without appending.

**Absorbed by:** the idempotent producer. Log has 1 copy. The sink sees 1.

### 10.2 HTTP client retry

1. Client posts `e1` (id X). API accepts and sends to Kafka; the client's connection drops before 202 arrives.
2. Client retries the POST with id X.
3. Without a key check, the API sends `e1` again: **two records in Kafka with id X** (new sequence, so the producer feature does not intervene).
4. With an API key check (Redis `SET NX`), the second request finds X already recorded and returns the first result.
5. If Redis lost the key (restart, TTL), both records reach Kafka.

**Absorbed by:** the API key (usually), and always by the sink's `PRIMARY KEY (event_id)`. Log may legitimately contain 2 copies; storage contains 1.

### 10.3 Consumer crash in the gap

1. Sink reads offsets 100-199, inserts 100 rows, `COMMIT` succeeds.
2. Process is `SIGKILL`ed before the offset commit.
3. Restart resumes at the committed offset 100 and reads the same 100 records.
4. `INSERT ... ON CONFLICT DO NOTHING` inserts 0 rows; `attempted=100, inserted=0`; duplicate counter +100.

**Absorbed by:** the idempotent consumer. Log has 1 copy of each record; the _processing_ happened twice; storage has 1.

### 10.4 Rebalance overlap

1. Consumer C1 is processing a batch from partition 3 and stalls past `max.poll.interval.ms`.
2. The group rebalances; C2 gets partition 3 and starts from the last committed offset, overlapping C1's in-flight batch.
3. Both write the overlapping rows. C1's offset commit is rejected (stale generation) or ignored.

**Absorbed by:** the unique constraint, which tolerates two concurrent inserters of the same key (one wins, one no-ops). No locking needed.

### 10.5 DLQ replay

1. A batch of messages was routed to the DLQ because of a transient schema-registry outage.
2. Registry is fixed; operator runs the replay tool, which **re-produces** the messages to `events.raw` with their **original `event_id`s**.
3. Some of them had in fact been stored earlier by a retry path.

**Absorbed by:** the sink constraint. This works **only if the replay preserves the original id** (section 11). A replay tool that generates new ids would **create genuine duplicates** that no layer can recognize.

## 11. Where the identity comes from: the key must outlive retries

The consumer-side design stands or falls on the quality of the **identity**.

### 11.1 Rules

1. **Created at the origin, once.** The client (or the first service to accept the event) mints it **before the first attempt**. Every retry reuses it.
2. **Not derived from anything that changes across retries.** Not the Kafka offset (it differs per copy), not a timestamp (differs per attempt), not a random id minted inside the consumer.
3. **Scoped.** `(tenant_id, event_id)` so tenants cannot collide or probe each other.
4. **Carried unchanged through every hop,** including retry topics, DLQ and replay tools.
5. **Unique for the lifetime of the dedup window,** which for the sink constraint is the lifetime of the data.
6. **Same key + different payload = bug.** Detect with a stored payload hash and return a conflict instead of silently picking one (S3-F1).

### 11.2 Natural vs synthetic keys

| Kind                                             | Example                              | Pros                             | Cons                                                                                                        |
| ------------------------------------------------ | ------------------------------------ | -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Natural, supplied by producer                    | `event_id` UUID from the SDK         | Stable across retries; cheap     | Depends on client discipline; a buggy client may reuse or omit it                                           |
| Synthetic, content hash                          | `sha256(tenant + canonical payload)` | Works without client cooperation | Two **genuinely different** events with identical content collapse into one; canonicalization must be exact |
| Synthetic, assigned by the server on first sight | UUID minted at the API               | Guaranteed unique                | **Useless for dedup of the client's own retries**, since each retry looks new                               |

Prefer the **natural id**. Use a content hash only as a fallback or a secondary check (the "same key, different payload" detector).

### 11.3 Anti-patterns

- Using `partition:offset` as the identity. A duplicate record in the log has a **different offset**, so it looks unique.
- Using `now()` or `received_at` as part of the key.
- Generating a **new** id inside the retry/DLQ replay tool.
- Treating Kafka's message **key** (used for partitioning, e.g. `tenant_id`) as an identity. It is a routing key, shared by many events.

## 12. Layered design

### 12.1 The picture

```
 client ─HTTP─▶ ingest-api ─────────▶ Kafka ───────▶ consumer-sink ────▶ Postgres
 (retries)      L1 API key (Redis)    L2 idempotent   L3 commit order      L4 PRIMARY KEY(event_id)
                SET NX EX             producer        (effect, then        ON CONFLICT DO NOTHING
                fast, bounded,        (PID+seq)       offset)              durable, unbounded
                can be lost           library retries prevents LOSS        the GUARANTEE
```

### 12.2 What each layer is responsible for

| Layer                   | Responsibility                                                                                  | Honest weakness                                                     |
| ----------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| L1: API idempotency key | Early, cheap, user-visible idempotency (return the original 202, conflict on different payload) | Redis TTL; Redis can lose data; not shared if Redis is per instance |
| L2: idempotent producer | Keep the **log** free of library-retry duplicates; preserve order                               | One session; not application retries                                |
| L3: commit-after-effect | Make crashes cause **duplicates, not loss**                                                     | Creates the reprocessing window, which L4 absorbs                   |
| L4: unique constraint   | **Final guarantee** for storage                                                                 | Cost of a unique index; does not cover non-DB effects               |

### 12.3 The golden rule of layering

> **Each earlier layer may fail without breaking correctness, as long as the last layer holds.** Earlier layers reduce _cost and noise_; the last layer provides _correctness_.

Corollary: if you ever **remove** L4 (the K5 experiment does so on purpose, using a copy of the table without a primary key) the system is wrong in proportion to how often L1-L3 leak. The experiment demonstrates the claim from the other side.

### 12.4 What if L4 cannot be a unique constraint?

Examples: the destination is an append-only store, a search index, or an API. Then:

- The destination must offer its own idempotency (an idempotency-key header, deterministic document id in the index), or
- You keep an **inbox** on your side to remember what you already sent, with the same **atomicity** requirements (recording and sending are two systems: so pick "send with a deterministic id" over "record then send").

## 13. How transactions fit in

Placement of Kafka transactions (note 3) relative to the two idempotence properties:

```
 idempotent producer  ⊂  transactional producer           (a transactional producer is automatically idempotent)
 idempotent consumer  is orthogonal: it lives in the destination, not in Kafka
```

| Capability                               | Idempotent producer | Transactional producer       | Idempotent consumer |
| ---------------------------------------- | ------------------- | ---------------------------- | ------------------- |
| No duplicate batches on library retry    | yes                 | yes                          | n/a                 |
| Stable identity across restarts          | no                  | **yes** (`transactional.id`) | n/a                 |
| Atomic multi-partition write             | no                  | **yes**                      | n/a                 |
| Atomic with consumer offsets             | no                  | **yes**                      | n/a                 |
| Zombie fencing                           | no                  | **yes**                      | n/a                 |
| Covers writes to Postgres                | no                  | **no**                       | **yes**             |
| Needed for Kafka-to-Postgres correctness | no                  | no                           | **yes**             |

So for a Kafka-to-database sink the stack is: idempotent producer (nice), **no transactions needed**, **idempotent consumer (required)**. For Kafka-to-Kafka stream processing the stack is: transactions + `read_committed` readers, and the final sink out of Kafka again needs an idempotent consumer.

## 14. Designing the idempotent sink well

Practical points the sink design in `services/consumer-sink` already follows or should be checked against:

1. **One atomic statement per chunk.** A multi-row `INSERT ... SELECT unnest(...) ON CONFLICT DO NOTHING` inside one transaction. No separate "does it exist?" query: that would be a **check-then-act race**.
2. **Constraint on the right columns.** `(event_id)` is globally unique in the current schema; if tenancy is added to the key, the constraint must be `(tenant_id, event_id)` and **the lookup scope must match** or one tenant can mask another's event.
3. **`DO NOTHING` vs `DO UPDATE`.** `DO NOTHING` keeps the **first** version of an event; correct when events are immutable facts. Use `DO UPDATE` with a version guard only when a later version is meant to replace an earlier one. Deliberately choose; never default.
4. **Count the absorbed duplicates.** `attempted - inserted` => metric. A sudden jump means a crash, a rebalance storm or a replay.
5. **Detect the "same id, different content" case.** `DO NOTHING` would silently hide it. A periodic check or a payload hash comparison on conflict reveals client bugs (S3-F1 asks the API layer to return 422; the sink may log).
6. **Commit the offset only after the DB commit returns.** The existing consumer uses `autoCommit: false` and commits in the batch handler after the write.
7. **Keep chunks bounded.** A large transaction holds locks and delays commit; a crash redoes the whole chunk (a bigger duplicate burst). Balance throughput vs reprocessing cost.
8. **Idempotence includes side channels.** A DLQ publish is also a write: a crash after the DLQ publish and before the offset commit **re-publishes** the DLQ entry. The DLQ and the replay tool need their own idempotence (dedup by `(original topic, partition, offset)` metadata plus the event id).

## 15. Testing each layer

Each layer gets a distinct test so a regression in one is not masked by another. Describing only; none run here.

| Layer             | Test idea                                                                                                                                           | What it proves                                                                       |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Producer config   | Unit test that config validation rejects `idempotent` with `acks != all` (already exists in `services/ingest-api/src/config.spec.ts`)               | The setting cannot be silently misconfigured                                         |
| Producer behavior | Fault-inject a dropped produce response and assert one copy in the log                                                                              | L2 works (needs a broker or proxy fault; later)                                      |
| API key           | Send the same `(tenant, key)` twice; assert one event and the original 202; send a different payload with the same key and assert 422               | L1 semantics                                                                         |
| Consumer order    | Crash at `after-db-commit`; assert rows == distinct ids and duplicates counter == reprocessed count                                                 | L3 + L4 (the existing `commit-protocol.e2e-spec.ts` covers this shape)               |
| Sink              | Property-based test (`fast-check`): for any sequence of events with arbitrary repeats and orderings, the final table equals the set of distinct ids | The core idempotence property: `apply(apply(x)) == apply(x)` and order-insensitivity |
| Replay            | Replay an arbitrary range three times; table unchanged (S3-F2)                                                                                      | Replay safety                                                                        |
| Negative control  | Run the same replay against a table **without** the primary key and show duplicates appear                                                          | Proves the test can fail, so a pass means something                                  |

The last row matters: a test that **cannot fail** is not evidence. The deliberate no-dedup table is the control.

## 16. Metrics and observability

A guarantee you cannot observe is a hope. Per layer:

| Metric                                                          | Reveals                                                         |
| --------------------------------------------------------------- | --------------------------------------------------------------- |
| `api_idempotent_hits_total` (key seen again)                    | Client retry volume; absorbed at L1                             |
| `api_idempotency_conflicts_total` (same key, different payload) | Client bugs                                                     |
| Producer retry count / `record-retry-total`                     | How often L2 may be doing work                                  |
| Producer `record-error-total`                                   | Failures the app sees (candidates for application-level resend) |
| `sink_rows_attempted_total`, `sink_rows_inserted_total`         | `attempted - inserted` is the duplicate count absorbed at L4    |
| Duplicate ratio over time                                       | Spikes mean crashes, rebalances or replays                      |

| DLQ size and replay counts                                      | Sources H and I                                                 |

A **sudden rise in absorbed duplicates** is a signal worth alerting on even though correctness held: it tells you something upstream is retrying, crashing or replaying.

## 17. EventPulse decisions

| Decision                   | Choice                                                                        | Reason                                                        |
| -------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Idempotent producer        | On, with `acks=-1`; config validation enforces the pairing                    | Cheap; removes library-retry duplicates and keeps order       |
| API idempotency            | `Idempotency-Key` / `event_id` checked with Redis `SET NX EX` (Stage 3 build) | Early rejection, original result returned, conflict detection |
| Consumer commit order      | DB commit, then offset commit, `autoCommit: false`                            | Crashes make duplicates, not loss                             |
| Final guarantee            | `ON CONFLICT (event_id) DO NOTHING` (Postgres primary key)                    | Durable, unbounded window, atomic                             |
| Duplicate visibility       | `attempted - inserted` counted                                                | S3-F3                                                         |
| Replay and DLQ tooling     | Preserve original `event_id`; dry-run; replays safe by construction           | The sink absorbs them only if the id is preserved             |
| Kafka transactions         | Not on this path (note 3)                                                     | Boundary: Postgres is outside                                 |
| Proof by contrast          | Keep the no-dedup variant as a negative control in tests/experiments          | A passing idempotence test must be able to fail               |
| How to describe the system | "At-least-once delivery, exactly-once storage effect, per `event_id`"         | Honest and testable                                           |

Why not rely on the producer feature alone: it removes exactly **one** of twelve sources (row C in section 9). Eleven others reach the consumer.

## 18. Common confusions

1. **"I enabled idempotence, so duplicates are impossible."** Only library-retry duplicates within one session are.
2. **"The broker knows my event id."** It does not look inside the payload. It knows `(PID, epoch, partition, sequence)`.
3. **"If my consumer is idempotent I can turn off the idempotent producer."** You can, and the system stays correct, but the log gets noisier and ordering across retries is not protected. Keep it on; it is free.
4. **"An idempotent consumer stops the broker from storing duplicates."** No. The log keeps both copies. The consumer only stops them from taking effect twice.
5. **"Dedup in memory is enough."** Memory vanishes at the very crash that creates the duplicate. Dedup state must be durable and atomic with the effect.
6. **"Redis `SET NX` makes the sink idempotent."** It is a fast filter with a TTL and loss window. The database constraint is the guarantee.
7. **"A unique index is slow."** It is the cheapest correct option: the lookup is part of the insert, in one statement. Measure the cost rather than assuming.
8. **"Hash the payload and use that as the id."** Two different events with the same content collapse; acceptable only when "same content = same event" is truly the business rule.
9. **"`DO NOTHING` means no information is lost."** It means the **later** copy is ignored. If the later copy had _different_ content, information is lost silently, which is why conflicts on different payload need detection.
10. **"Idempotent consumer = the handler function is pure."** Not required; only that the **net effect** of repeats is unchanged, usually via a unique key.

## 20. Cheat sheet

### Glossary

| Term                | Meaning                                                                            |
| ------------------- | ---------------------------------------------------------------------------------- |
| Idempotent producer | `enable.idempotence=true`: broker drops resent batches from the same PID/partition |
| PID / sequence      | Producer id and per-partition batch counter used for that check                    |
| Idempotent consumer | A consumer whose repeated processing has no extra effect                           |
| Idempotency key     | Origin-assigned id identifying one logical operation                               |
| Inbox               | Durable table of processed message ids, written with the effect in one transaction |
| Dedup window        | How long a duplicate can still be recognized                                       |
| Absorbed duplicate  | A repeat that arrived and was neutralized (counted)                                |
| Layered idempotence | Cheap early filters plus a durable final constraint                                |
| Negative control    | A variant that should fail, proving a test is meaningful                           |

### Rules

1. Producer idempotence handles **library retries in one session**. Nothing more.
2. Correctness lives in the **consumer-side durable constraint**.
3. The key is minted at the **origin**, **before** the first attempt, and **never changes** across retries, DLQ and replays.
4. **Effect, then progress.** Idempotence cannot repair loss.
5. Dedup state must be **durable** and **atomic with the effect**.
6. Earlier layers are optimizations; the last layer is the guarantee.
7. Count absorbed duplicates; alert on spikes.
8. Test with a negative control.

### Which layer, quickly

```
 library retry, lost response ........ idempotent producer
 client HTTP retry (fresh) ........... API idempotency key  (+ sink as backstop)
 crash / rebalance / replay .......... idempotent consumer (sink constraint)
 non-DB side effects ................. idempotency key header / inbox / outbox
```

## 1. TL;DR

- There are three named guarantees for moving a message from a sender to a receiver that can both fail:
  - **At-most-once:** the message is delivered **zero or one** times. Never a duplicate; may be **lost**.
  - **At-least-once:** the message is delivered **one or more** times. Never lost (if the system stays healthy enough to retry); may be **duplicated**.
  - **Exactly-once:** the message is delivered **exactly one** time. Lost nothing, duplicated nothing.
- The first two are **achievable as delivery guarantees** over an unreliable network. The third is **not achievable as a pure delivery guarantee** (section 6 explains why; note 2 gives the proof-like argument). What systems sell as "exactly-once" is an **exactly-once effect**: the message may be _delivered_ more than once, but the **observable result** happens once.
- The effect is made exactly-once in only two ways: **(a)** make processing **idempotent** (doing it twice equals doing it once), or **(b)** make "do the work" and "remember it is done" **one atomic step** (a transaction).
- The guarantee you get is decided by **one ordering choice**: do you record "I handled it" **before** or **after** you do the work?
  - Record first, work second: a crash in between **loses** the work. At-most-once.
  - Work first, record second: a crash in between **repeats** the work. At-least-once.
  - Both in one atomic unit: neither window exists. Exactly-once **effect**, within that unit's boundary.
- **A guarantee always has a boundary.** "Exactly once" inside Kafka stops at Kafka's edge. "Exactly once" inside one Postgres transaction stops at Postgres' edge. Wherever a second system joins, you must restate the guarantee for that hop. This is the single most important idea of Stage 3.
- Real systems, including EventPulse, run **at-least-once delivery + idempotent sink**. In EventPulse the idempotent step is `INSERT ... ON CONFLICT (event_id) DO NOTHING`.

> **One-line version:** _Delivery is at-most-once or at-least-once; "exactly-once" is at-least-once delivery plus a processing step that makes duplicates harmless._

## 2. The mental model

### 2.1 A chain of hand-offs, each of which can fail

A message does not "travel". It is **handed from one process to the next**, and every hand-off has the same shape:

```
   sender                                   receiver
     |  --- 1. send the message ---------->   |
     |                                        |  2. receiver acts (stores it, applies it)
     |  <-- 3. acknowledgment --------------  |
     |
     |  4. sender records "this one is done"
```

Four things can go wrong, and the **sender cannot tell them apart**:

| What happened                                                          | What the sender observes     |
| ---------------------------------------------------------------------- | ---------------------------- |
| Message lost on the way (step 1 failed)                                | Nothing comes back (timeout) |
| Receiver crashed before acting (step 2 never happened)                 | Nothing comes back (timeout) |
| Receiver acted, then crashed before replying (step 2 done, step 3 not) | Nothing comes back (timeout) |
| Receiver acted, replied, reply lost (step 3 failed)                    | Nothing comes back (timeout) |

Cases 1-2 mean "the work did **not** happen". Cases 3-4 mean "the work **did** happen". The sender sees the same timeout for both. **That ambiguity is the root of every delivery-semantics problem.** Everything in this note is a policy for what the sender does when it hits that timeout:

- **Give up** (do not resend): safe against duplicates, unsafe against loss. That is **at-most-once**.
- **Resend** until an acknowledgment arrives: safe against loss, unsafe against duplicates. That is **at-least-once**.
- **Resend, and make resends harmless:** that is **exactly-once effect**.

### 2.2 The postal analogy

You mail an important form and want to be sure it arrives.

| Policy              | What you do                                                                                                                                       | What can go wrong                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| At-most-once        | Mail it once and never check                                                                                                                      | It may be lost in the post. Never two copies.                                                 |
| At-least-once       | Mail it; if no confirmation card returns in a week, mail another; repeat                                                                          | The first one may have arrived and only the card got lost, so the office receives two copies. |
| Exactly-once effect | Mail copies as in at-least-once, but each form carries a **unique form number**, and the office **discards a form whose number it already filed** | Nothing visible. The office pays the cost of keeping a ledger of filed numbers.               |

The office in the third row is the **idempotent consumer**. The unique form number is the **idempotency key** (in EventPulse: `event_id`).

## 3. Why the word "delivery" is slippery

"Was the message delivered?" can mean at least five different things, and most arguments about "exactly-once" come from people meaning different ones.

| "Delivered" could mean               | Example in EventPulse                         | Failure that breaks it                                                              |
| ------------------------------------ | --------------------------------------------- | ----------------------------------------------------------------------------------- |
| Reached the receiver's network stack | The HTTP request reached `ingest-api`         | Network drop                                                                        |
| Was **accepted** by the receiver     | `ingest-api` validated it and returned 202    | Crash after accept, before durable write                                            |
| Was **durably stored**               | Kafka acknowledged with `acks=all`            | Leader loss with `acks=1`                                                           |
| Was **handed to application code**   | The consumer's `eachBatch` was called with it | Rebalance between fetch and handler                                                 |
| Had its **effect applied**           | The row is committed in Postgres              | Crash after DB commit but before offset commit makes it applied **and redelivered** |

**Rule for these notes:** when you read "at-least-once" or "exactly-once", always ask **"delivered to what, and counted at which of those five points?"**. A statement without that answer is not a guarantee yet.

A second slippery point: **messages vs effects.** One message can be _delivered_ three times and still have _one effect_ (idempotent processing). Conversely a message delivered once can have _two effects_ (a handler that does two non-atomic writes and crashes between them leaves a half effect). Delivery counts messages; correctness cares about effects.

## 4. At-most-once

### 4.1 Definition

Each message is delivered **0 or 1** times. Resending is forbidden, or progress is recorded **before** the work is done.

### 4.2 How you get it by accident

| Mechanism                                            | Why it is at-most-once                                                                                                                    |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Producer `acks=0`                                    | Fire and forget; no acknowledgment, no resend. A lost message is lost silently.                                                           |
| Producer with `retries=0` and `acks=1`               | A failed or unacknowledged send is not retried.                                                                                           |
| Consumer commits the offset **before** processing    | Crash after the commit but before the work: the restarted consumer starts after the message and never sees it. The work was lost.         |
| Consumer with auto-commit enabled and a slow handler | The auto-commit timer commits offsets of messages fetched but not yet finished; a crash loses them. (This is the common accidental form.) |
| UDP, metrics datagrams (StatsD style)                | The transport itself has no retry.                                                                                                        |
| A "try once, log the error, move on" catch block     | Exactly the failure policy of at-most-once.                                                                                               |

### 4.3 When it is the right choice

At-most-once is a **legitimate, deliberate** choice when:

- **Loss is cheap and duplicates are expensive** (or impossible to deduplicate).
- Examples: high-rate telemetry where a dropped sample is invisible, a "heartbeat" ping, a real-time position update that will be superseded in 100 ms, sending an SMS where a duplicate text is worse than a missed one.

It is the **wrong** choice for anything that must be counted, billed, stored, or audited. EventPulse's whole premise is that **events must not be silently dropped**, so at-most-once is excluded for the main path.

### 4.4 The loss, shown on a timeline

```
consumer:  fetch batch [10..19] ──> commit offset 20 ──> process 10..19 ──X crash after 14
                                         |
restart:   starts at the committed offset 20 -> messages 15..19 are never processed. LOST.
```

The commit said "I have handled these" **before** it was true. That is the whole bug.

## 5. At-least-once

### 5.1 Definition

Each message is delivered **1 or more** times. The sender **keeps retrying until it is told the message was handled**, and progress is recorded **after** the work is done.

### 5.2 How you get it

| Mechanism                                          | Why it is at-least-once                                                                                                                      |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Producer `acks=all` plus retries                   | A send is repeated until acknowledged by the in-sync replicas. A lost _response_ leads to a duplicate in the log.                            |
| Consumer commits the offset **after** processing   | A crash after the work and before the commit makes the restarted consumer reprocess the same messages.                                       |
| HTTP client that retries on timeout or 5xx         | The server may have processed the first call.                                                                                                |
| Message broker with visibility timeout (SQS style) | A message not deleted in time is delivered again to another worker.                                                                          |
| Rebalance during processing                        | Another consumer is assigned the partition and starts from the last committed offset, overlapping the work still in flight on the old owner. |

### 5.3 The duplicate, shown on a timeline

```
consumer:  fetch batch [10..19] ──> process 10..19 ──> DB commit OK ──X crash ──> (offset 20 never committed)
                                                                            |
restart:   starts at the committed offset 10 -> reads 10..19 again.
           Every one of these ten messages is processed a SECOND time. DUPLICATES.
```

The window between "DB commit OK" and "offset committed" is the **crash window**. It is tiny but never zero, and it is hit by:

- a `SIGKILL` / OOM kill / node loss,
- a **rebalance** that revokes the partition in exactly that window,
- an offset-commit request that **fails** (broker unavailable) after the DB already committed.

In EventPulse this exact window is the one `services/consumer-sink/test/commit-protocol.e2e-spec.ts` exercises: the restarted process re-reads the chunk, and `ON CONFLICT` absorbs it.

### 5.3.1 Duplicates have more sources than the consumer window

| Source                                                                  | Layer              | Absorbed by                                           |
| ----------------------------------------------------------------------- | ------------------ | ----------------------------------------------------- |
| Client library retries a produce whose response was lost                | Producer to broker | Idempotent producer (note 4)                          |
| Application code retries a request after a 503 or timeout               | Client to API      | Idempotency key at the API (Stage 3 idempotency note) |
| Client sends the same event twice on purpose (bug or user double-click) | Client             | Idempotency key + payload hash                        |
| Consumer crashes between DB commit and offset commit                    | Consumer           | Idempotent sink                                       |
| Rebalance gives the same range to two consumers briefly                 | Consumer group     | Idempotent sink                                       |
| Operator replays a topic range or a DLQ                                 | Operations         | Idempotent sink                                       |
| Retry-topic or DLQ replay produces the same event again                 | Pipeline           | Idempotent sink                                       |

**Conclusion:** duplicates enter from **many** layers, so a single mechanism at one layer cannot remove all of them. This is why Stage 3 builds layers (note 4 and the idempotency note).

### 5.4 The cost model

At-least-once costs you one thing: **every consumer of the data must tolerate seeing a message more than once.** Everything else (latency, throughput) is close to at-most-once. This is why it is the default of the industry: loss is rarely acceptable, and duplicates can be neutralized at the end of the pipe.

## 6. Exactly-once

### 6.1 What people want

"Each message affects the world exactly one time, even with crashes, retries and network faults."

### 6.2 Why it is not a pure delivery guarantee

Recall the table in 2.1: the sender cannot distinguish "did not happen" from "happened, reply lost". To be exactly-once, on a timeout it must **both** resend (to avoid loss) **and not** resend (to avoid a duplicate). That is a contradiction **unless the receiver can recognize a repeat**. So exactly-once is never achieved by the **sender and the network alone**. It requires **state at the receiver** that links repeated deliveries together. Note 2 develops this as the Two Generals problem.

### 6.3 The precise statement

> **Exactly-once processing = at-least-once delivery + a receiver whose effect is idempotent, or whose effect and progress-tracking commit atomically.**

The honest label is **effectively-once** or **exactly-once effect**. Vendors write "exactly-once semantics (EOS)"; read it as "within this documented boundary, the visible effect is once".

### 6.4 Three flavours of "exactly-once" you will meet

| Flavour                                           | What is exactly once           | How                                                                                 | Boundary                                                |
| ------------------------------------------------- | ------------------------------ | ----------------------------------------------------------------------------------- | ------------------------------------------------------- |
| **Idempotent write**                              | The row in the table           | Unique key + `ON CONFLICT DO NOTHING` (or upsert)                                   | The database                                            |
| **Atomic commit of effect + progress**            | The pair (effect, offset)      | One transaction writes both the result and the position that says "I consumed this" | One system that can hold both (one DB, or Kafka itself) |
| **Transactional read-process-write inside Kafka** | Output records + input offsets | Kafka transactions (note 3)                                                         | Kafka brokers only                                      |

Each of these is **exact within a boundary and silent outside it.**

### 6.5 Two sentences you must be able to say

1. "Kafka gives me exactly-once **inside Kafka**: consume, transform, produce, and commit offsets atomically. The moment my handler writes to Postgres, Redis or an HTTP API, Kafka's transaction does not cover that write, and I need idempotency or an inbox at that hop."
2. "I do not claim exactly-once delivery. I claim at-least-once delivery and **a stored result that is identical whether a message arrives once or five times**."

## 7. The same three guarantees at every hop of EventPulse

The end-to-end guarantee is the **weakest** guarantee of any hop, unless a later hop repairs it. Walk the pipeline.

```
  client ──HTTP──> ingest-api ──produce──> Kafka (events.raw) ──consume──> consumer-sink ──SQL──> Postgres
   hop A              hop B                      hop C                         hop D
```

| Hop                      | What can fail                               | Semantics by default                                                     | Mechanism that improves it                        | Residual                                                   |
| ------------------------ | ------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- | ---------------------------------------------------------- |
| A. client to API         | Timeout, 503, connection reset              | Client decides: retry (at-least-once) or drop (at-most-once)             | `Idempotency-Key` / `event_id` honored by the API | Key window expiry; client that never retries               |
| B. API to Kafka          | Lost produce response, leader change        | With `acks=all` + retries: at-least-once; with `acks=1/0`: loss possible | `acks=all`, `enable.idempotence=true`             | Application-level retries create a new send (new sequence) |
| C. Kafka storage         | Broker loss                                 | Durable if `acks=all` and `min.insync.replicas>=2`, RF 3                 | Replication (Stage 2 note 3)                      | Unclean election if enabled                                |
| D1. Kafka to consumer    | Crash, rebalance                            | At-least-once if commit-after-process                                    | Manual commit after the DB commit                 | Reprocessing window                                        |
| D2. Consumer to Postgres | Crash after DB commit, before offset commit | Duplicate writes attempted                                               | `ON CONFLICT (event_id) DO NOTHING`               | **None for storage**; duplicates counted, not stored       |

Reading the table top to bottom: the **delivery** is at-least-once at every hop, which is exactly what you want; the **effect on storage** is exactly-once because **hop D2 is idempotent**. The system as a whole is therefore "at-least-once delivery, exactly-once storage effect".

### 7.1 What is **not** covered

Anything that happens **after** storage is its own hop with its own guarantee. A future example in the roadmap: the consumer also publishes a "stored" notification, or calls a webhook. Those are new hops. The idempotent insert does **not** make the webhook exactly-once. The transactional outbox (later Stage 3 note) is the pattern for that hop.

## 8. Crash points: the table that makes it concrete

Use the consumer's steps as a checklist. Suppose the consumer does, in this order:

```
 P1  fetch messages [N..N+k] from Kafka
 P2  parse / validate
 P3  BEGIN; INSERT ... ON CONFLICT DO NOTHING; COMMIT     (the effect)
 P4  commit the Kafka offset N+k+1                          (the progress record)
```

Crash **between** each pair of steps, and observe the result **without** any dedup protection and **with** it:

| Crash point                    | State after restart                      | Without dedup                     | With `ON CONFLICT DO NOTHING`                              |
| ------------------------------ | ---------------------------------------- | --------------------------------- | ---------------------------------------------------------- |
| Before P1 completes            | Nothing happened                         | Fine                              | Fine                                                       |
| After P1, before P3            | No rows written; offset not committed    | Reprocessed; **correct**          | Correct                                                    |
| During P3 (before COMMIT)      | Transaction rolled back by Postgres      | Reprocessed; **correct** (atomic) | Correct                                                    |
| **After P3 COMMIT, before P4** | Rows committed; offset **not** committed | Reprocessed; **DUPLICATE ROWS**   | Duplicates **absorbed**, counted as `attempted - inserted` |
| After P4                       | All done                                 | Fine                              | Fine                                                       |

Only **one** row of this table produces duplicates: the gap between the effect and the progress record. That one gap is the entire reason idempotent processing exists in this pipeline.

Now reverse the order of P3 and P4 (commit the offset first):

| Crash point                                   | State after restart              | Result                                                                                |
| --------------------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------- |
| After the offset commit, before the DB COMMIT | Offset says "done"; rows missing | **LOST rows.** At-most-once. No dedup can repair a message that is never redelivered. |

**Lesson:** dedup only helps when the system is at-least-once. It cannot resurrect lost data. So the order is fixed: **effect first, progress second**, and then dedup handles the replay.

## 9. Ordering of "do the work" and "record that it is done"

This is the **core design decision** and it is worth stating as a formula.

| Order                    | Name                | Crash in the middle causes  | Fix                              |
| ------------------------ | ------------------- | --------------------------- | -------------------------------- |
| record, then work        | at-most-once        | **Lost work**               | Do not use for must-keep data    |
| work, then record        | at-least-once       | **Repeated work**           | Make the work idempotent         |
| work + record atomically | exactly-once effect | Nothing (within one system) | Put both in the same transaction |

Notes on the third row:

- It works when **one system** can hold both the effect and the progress. Example: a consumer that stores its own offset **in the same Postgres transaction** as the data rows (the "store offsets in the destination" pattern). Restart reads the offset from Postgres, not from Kafka, so the pair can never disagree.
- Kafka's own EOS is the same idea with Kafka as the single system: the output records **and** the consumed offsets are both Kafka writes, committed by one transaction (note 3).
- It does **not** work across two systems that do not share a transaction (Kafka offsets + Postgres rows). Two-phase commit could in theory join them, but it is rarely used in practice (it blocks on coordinator failure). That is why EventPulse uses the second row plus dedup instead.

## 10. Ways to get "exactly-once effect"

Four standard techniques. Know all four; EventPulse uses the first.

### 10.1 Idempotent operation (the effect is naturally repeat-safe)

| Operation                           | Idempotent?               |
| ----------------------------------- | ------------------------- |
| `SET balance = 100`                 | Yes                       |
| `INSERT ... ON CONFLICT DO NOTHING` | Yes                       |
| `UPSERT` by primary key             | Yes                       |
| `DELETE WHERE id = 5`               | Yes                       |
| `balance = balance + 10`            | **No**                    |
| `INSERT` without a unique key       | **No**                    |
| `counter++`                         | **No**                    |
| Send an email                       | **No** (cannot be undone) |

Where the operation is **not** naturally idempotent, convert it: attach a unique id and store "applied ids" (technique 10.2), or change the model so the event is the unit of storage and the count is **derived** from distinct events (this is exactly how EventPulse counts: aggregates are computed from stored events keyed by `event_id`, so replays do not inflate them).

### 10.2 Dedup store (remember which ids you have processed)

Keep a set of processed ids and skip repeats. The store can be:

- the destination table itself (unique constraint on `event_id`, the EventPulse approach),
- a separate **inbox** table written in the same transaction as the effect,
- a Redis key with `SET ... NX EX ttl` (fast but bounded in time and loseable).

Failure window of each is studied in the idempotency note. Preview: a Postgres unique constraint has **no** window; Redis `NX` has a window equal to its TTL and a loss window on restart.

### 10.3 Atomic commit of effect and progress

Section 9, third row. Covered for Kafka-internal flows in note 3 and for Postgres-internal flows by storing offsets with the data.

### 10.4 Deterministic reprocessing (replay yields the same result)

If the transformation is a **pure function** of the input (same input, same output, no clocks or random numbers in the result), then reprocessing overwrites with identical values and the system is idempotent by construction. This is the idea behind "replay the log to rebuild state" in Stage 4's stream processing. It breaks when the handler reads "now" or calls an external service whose answer changes.

## 11. Delivery guarantee vs processing guarantee vs storage guarantee

People mix these three. Separate them.

| Layer                | Question                                                         | EventPulse answer                      |
| -------------------- | ---------------------------------------------------------------- | -------------------------------------- |
| **Delivery**         | How many times does the handler get the message?                 | 1 or more (at-least-once)              |
| **Processing**       | How many times does the handler's logic run to completion on it? | 1 or more; may run again after a crash |
| **Storage / effect** | How many distinct stored results exist for it?                   | Exactly 1 per `event_id`               |

Statements like "the system is exactly-once" are only meaningful when attached to the third row. The first two rows are **never** exactly-once in a crash-prone system with an external side effect. The goal of the delivery guarantees document (S3-F9) is to write this table honestly, one claim per row, each with a test.

## 12. What the guarantees cost

|                        | At-most-once       | At-least-once                           | Exactly-once effect                                                                                              |
| ---------------------- | ------------------ | --------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Loss risk              | Yes                | No                                      | No                                                                                                               |
| Duplicate risk         | No                 | Yes                                     | No (visible effect)                                                                                              |
| Extra state            | None               | None (but consumers must be idempotent) | Dedup store, or transactional bookkeeping                                                                        |
| Latency overhead       | Lowest             | Low (waiting for acks)                  | Higher (unique index lookup, or a transaction round trip)                                                        |
| Throughput overhead    | Lowest             | Low                                     | Measurable: this is exactly what Stage 3 asks you to quantify (prediction: how much throughput will dedup cost?) |
| Failure complexity     | Simple             | Moderate                                | Highest (more moving parts: coordinators, TTLs, epochs)                                                          |
| Operational visibility | Loss is **silent** | Duplicates can be **counted**           | Needs metrics for "absorbed duplicates" or you cannot prove it works                                             |

Two practical points:

- **Silent loss is the worst failure mode**, because nothing alerts you. A duplicate that is absorbed can be counted (`attempted - inserted`), so at-least-once with counting is _observable_; at-most-once is not.
- **Dedup is cheap when keyed by an already-indexed column** (the primary key lookup happens anyway during insert) and expensive when it needs a **separate** round trip (a Redis call per message, or a transaction per message). EventPulse batches many rows per transaction so the per-row dedup cost is small.

## 13. Choosing a guarantee per data type

Not every stream needs the same guarantee. A decision rule:

```
Can a lost message be tolerated or reconstructed?
 ├─ yes, and duplicates are harmful  -> at-most-once is acceptable
 └─ no                                -> at-least-once, then:
        Is the effect naturally idempotent (upsert, set)?
         ├─ yes -> done
         └─ no  -> add an idempotency key + dedup store, or move to atomic effect+progress
```

| Data                                            | Choice                                                                 | Reason                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------- |
| EventPulse events (the product)                 | At-least-once + idempotent sink                                        | Loss unacceptable; duplicates removable by `event_id`            |
| Producer-side latency metrics                   | At-most-once acceptable                                                | A lost sample does not change a dashboard                        |
| Tenant config change + cache-invalidation event | At-least-once via outbox + idempotent consumer                         | Must not be lost; applying "invalidate cache" twice is harmless  |
| Sending a notification to a human               | Usually at-least-once + dedup key                                      | Duplicate emails annoy; lost alerts hurt more                    |
| Payment capture                                 | At-least-once + idempotency key at the payment API + ledger uniqueness | Both loss and duplicate are costly; idempotency key is mandatory |

## 14. How to write the guarantee in a document and test it

A guarantee is useful only when it is **specific** and **testable**. A template for each line of the delivery guarantees document:

```
Claim:        <what is promised, to whom, at which boundary>
Counted at:   <which of the five "delivered" meanings from section 3>
Holds when:   <preconditions: acks, min ISR, configs, no unclean election>
Fails when:   <explicit exclusions: replay older than the dedup window, schema violations ...>
Test:         <the automated test that proves it, and the fault it injects>
Metric:       <the metric that would show it being violated or exercised>
```

Example for EventPulse:

```
Claim:        Every event accepted with 202 is stored exactly once in Postgres, identified by event_id.
Counted at:   "effect applied" (a committed row), not "message handled".
Holds when:   producer acks=all, min.insync.replicas=2, RF=3; sink commits offsets after DB commit;
              events table has PRIMARY KEY (event_id) (or (tenant_id, event_id)).
Fails when:   the primary key is dropped (the K5 experiment does this on purpose); the broker loses data
              because of an unclean leader election; retention deletes the message before it is consumed.
Test:         SIGKILL the consumer at "after-db-commit", restart, assert rows == distinct event_ids and
              duplicates_total == attempted - inserted.
Metric:       sink duplicates counter; consumer lag; DLQ count.
```

What a bad line looks like: "The system guarantees exactly-once delivery." It names no boundary, no preconditions, no exclusions, and cannot be tested.

## 15. EventPulse decisions

| Decision                                          | Choice                                                          | Why                                                                        |
| ------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Delivery model                                    | At-least-once end to end                                        | Events must not be dropped silently                                        |
| Where "exactly-once effect" is created            | The sink: `INSERT ... ON CONFLICT (event_id) DO NOTHING`        | Durable, no TTL window, one round trip per batch                           |
| Order of effect vs progress in the consumer       | DB commit first, then Kafka offset commit (`autoCommit: false`) | Makes a crash produce a **duplicate**, never a **loss**                    |
| Are duplicates hidden?                            | No. `attempted - inserted` is counted as duplicates             | S3-F3: duplicates must be visible                                          |
| Kafka EOS (transactions) in the sink path         | Not used                                                        | The sink writes to Postgres, outside Kafka's transaction boundary (note 3) |
| Handling a non-idempotent downstream effect later | Transactional outbox + idempotent consumer                      | Dual-write problem (later note)                                            |

## 16. Common confusions

1. **"Exactly-once delivery exists in Kafka."** Kafka's feature is named exactly-once _semantics_ and covers read-process-write **inside Kafka**. The message may still be physically transmitted more than once; the _log_ ends up with one committed copy. And it says nothing about Postgres.
2. **"With the idempotent producer I am exactly-once."** It removes one duplicate source (library retries within a session). It does not touch application retries or consumer reprocessing (note 4).
3. **"At-least-once means usually once."** It means _one or more_. Under a healthy network duplicates are rare; under a crash storm they are common. Design for the worst case.
4. **"Dedup will recover lost messages."** No. Dedup removes extras. It cannot create a message that was never delivered.
5. **"Idempotent means the function returns the same value."** It means repeating has the **same effect** as once. A counter increment fails this test even if it returns a value.
6. **"A transaction makes it exactly-once."** Only for effects **inside that transaction's system**. A transaction cannot roll back an email already sent or a Kafka message already published.
7. **"Exactly-once is impossible, so it is all marketing."** Exactly-once **delivery** is impossible over a faulty network; exactly-once **effect** is achievable and is practical engineering. Be precise about which one you mean.
8. **"At-most-once is always bad."** It is correct for data where loss is cheaper than duplicates or complexity.

## 18. Cheat sheet

### Glossary

| Term                | Meaning                                                               |
| ------------------- | --------------------------------------------------------------------- |
| Delivery            | A message being handed to a receiver (always say at which point)      |
| At-most-once        | 0 or 1 deliveries; may lose; never duplicates                         |
| At-least-once       | 1 or more deliveries; never loses (if retries succeed); may duplicate |
| Exactly-once effect | Visible result happens once; deliveries may repeat                    |
| Idempotent          | Repeating has the same effect as doing it once                        |
| Idempotency key     | A unique id carried by a message so repeats can be recognized         |
| Dedup               | Discarding repeats of an already-processed id                         |
| Crash window        | The gap between the effect and the progress record                    |
| Boundary            | The set of systems one guarantee covers                               |
| Effectively-once    | Honest synonym for exactly-once effect                                |

### Rules

1. Effect first, progress second: crash then yields a **duplicate**, never a **loss**.
2. Dedup repairs duplicates, never loss.
3. State every guarantee with its **boundary**.
4. Exactly-once effect = at-least-once delivery + idempotent or atomic processing.
5. Count absorbed duplicates; a guarantee you cannot observe is a hope.
6. One mechanism covers one layer. Duplicates enter at many layers.

### One-screen summary

```
                 loss?   duplicate?   typical cause
at-most-once      yes       no        commit before work / acks=0 / no retry
at-least-once     no        yes       commit after work / retry on timeout
exactly-once     no        no*       at-least-once + idempotent or atomic effect     (*visible effect)
```

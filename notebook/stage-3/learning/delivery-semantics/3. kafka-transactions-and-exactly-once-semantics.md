## 1. TL;DR

- A **Kafka transaction** lets a producer write to **several partitions and topics** and (optionally) **commit consumer offsets** as **one atomic unit**: all of it becomes visible, or none of it does.
- Its flagship use is the **consume-transform-produce** loop: read from topic A, write results to topic B, and advance the input offset on A, **atomically**. After a crash the pair is never half-done, so the output has **no duplicates and no gaps** relative to the input.
- Mechanism in one paragraph: the producer has a stable **`transactional.id`**. A **transaction coordinator** (a broker, backed by the internal `__transaction_state` topic) assigns it a **producer id (PID)** and an **epoch**, and tracks the transaction state. Records are written **immediately** to the data partitions, but marked as part of an open transaction. On commit, the coordinator writes a **COMMIT control marker** into every involved partition. Consumers with **`isolation.level=read_committed`** only deliver records up to the **last stable offset (LSO)** and skip records of aborted transactions.
- **Zombie fencing:** a newer instance with the same `transactional.id` gets a **higher epoch**; the broker rejects writes from the older epoch. This is how a paused or partitioned old instance is prevented from corrupting data.
- **The boundary:** the atomicity covers **Kafka writes only**: produced records and offset commits inside Kafka. It does **not** cover a write to Postgres, Redis, an HTTP API or an email. If the handler touches any of those, Kafka cannot roll it back and cannot make it atomic with the Kafka part.
- Therefore, for EventPulse (Kafka to Postgres), **transactions are not the tool**. The tool is **at-least-once consumption + idempotent insert** (`ON CONFLICT`), or an **inbox** / offsets-in-Postgres design.
- Consumers of a transactional topic must set `read_committed`, otherwise they will read records from transactions that later abort.

> **One-line version:** _Kafka transactions make "write to Kafka and advance my Kafka offsets" one atomic step, and nothing else._

## 2. The mental model

Imagine a **notary** who must seal a bundle of documents at once.

| Notary world                                                                                        | Kafka                                                                                                    |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| You hand documents to the notary's clerks one at a time, in several rooms                           | `send()` records to many partitions during the transaction                                               |
| The clerks file them in a **pending** tray, visible only to staff                                   | Records are in the log but belong to an **open** transaction; `read_committed` consumers do not see them |
| You say "seal it"                                                                                   | `commitTransaction()`                                                                                    |
| The notary stamps a **SEALED** card in each room's tray                                             | **COMMIT control marker** written to each partition                                                      |
| Once stamped, outsiders can read all the documents                                                  | Records become visible to `read_committed` consumers                                                     |
| You say "tear it up" instead                                                                        | `abortTransaction()`: an **ABORT marker**; documents are skipped by readers                              |
| Your badge has a number that only increases; the guard rejects an older badge                       | **Epoch** fencing a zombie producer                                                                      |
| The notary can seal documents **in the building** only; a letter you posted outside is out of reach | **Boundary**: Postgres, Redis and email are outside                                                      |

The **outside letter** is the most important row for this series.

## 3. The problem transactions solve

### 3.1 The consume-transform-produce loop

```
   topic "in"  ──consume──> [ transform ] ──produce──> topic "out"
        ^                                                   |
        |  commit offset after each batch                    v
        +---------------------- group offsets (__consumer_offsets)
```

Three separate Kafka writes are involved:

1. produce results to `out`,
2. commit the consumed offset of `in`,
3. (maybe) more outputs to other topics.

Without a transaction these are independent. Crash between them:

| Crash point                                  | Result                                                                       |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| After produce to `out`, before offset commit | Restart re-reads `in`, re-produces the same results: **duplicates in `out`** |
| After offset commit, before produce          | Restart skips the input: **lost results in `out`**                           |
| Between two produces to two topics           | **Half** the outputs exist                                                   |

The idempotent producer does **not** fix this: the re-produce after restart is a **new** session and a new `send()`, so it is a distinct record (note 4).

### 3.2 What a transaction guarantees

Wrap steps 1-3 in one transaction. After any crash, the combined result is either:

- **all** outputs visible **and** the input offset advanced, or
- **none** of the outputs visible **and** the input offset not advanced (so the input will be reprocessed cleanly and produce the outputs once).

This is the **exactly-once effect inside Kafka** from note 1, third flavour.

## 4. What exactly is atomic

Be precise: transactions provide **atomic multi-partition writes** and **atomic offset commits**, plus **isolation** for readers who opt in.

| Property                                                       | Provided?     | Notes                                                |
| -------------------------------------------------------------- | ------------- | ---------------------------------------------------- |
| Atomicity across **partitions and topics** of produced records | Yes           | Commit or abort covers all                           |
| Atomicity of **produced records + consumer group offsets**     | Yes           | `sendOffsetsToTransaction`                           |
| Durability                                                     | Yes           | Writes use `acks=all` (required), markers replicated |
| Isolation for `read_committed` readers                         | Yes           | Uncommitted and aborted data hidden                  |
| Isolation for `read_uncommitted` readers (default)             | **No**        | They see open and aborted records                    |
| Atomicity with **non-Kafka** systems                           | **No**        | The boundary (section 14)                            |
| Global ordering across partitions                              | No            | Same as non-transactional Kafka                      |
| "At most one writer per partition"                             | Not by itself | Fencing is per `transactional.id`                    |
| Transactions spanning **several producers**                    | No            | One transaction belongs to one producer instance     |

Note what is _not_ mentioned: the broker does **not** roll back written records. The records are **physically in the log** even if the transaction aborts. "Atomic" here means "**visibility** is decided atomically", implemented by markers and by consumer-side filtering.

## 5. The building blocks

### 5.1 `transactional.id`

- A **stable, user-chosen string** identifying "this logical producer", **the same across restarts**.
- It must be **unique per logical producer instance** that must not run concurrently with its twin. For a consume-transform-produce app, it usually encodes the **input partition or task** so the same task always reuses the same id (EOS v1), or a per-instance id (EOS v2, section 10).
- Enables: idempotent semantics across **restarts** (a transactional producer is automatically idempotent), recovery of a pending transaction, and **fencing** of zombies.

### 5.2 Producer id (PID) and epoch

- On `initTransactions()` the coordinator maps `transactional.id` to a **PID** and bumps an **epoch** (a small integer).
- Every write carries `(PID, epoch, sequence)`.
- The broker rejects any request whose **epoch is lower** than the latest known for that `transactional.id`: the **`ProducerFencedException`** (zombie fencing).
- Because `transactional.id` is stable, the **PID persists across restarts** (unlike the plain idempotent producer, where a restart gives a fresh PID). That is why transactions can dedupe across restarts for records inside the transaction protocol.

### 5.3 The transaction coordinator

- A **broker** acts as coordinator for a given `transactional.id`. Which one is decided by hashing the id onto a partition of `__transaction_state`; that partition's leader is the coordinator.
- It keeps the **transaction state machine** per `transactional.id`: `Empty -> Ongoing -> PrepareCommit -> CompleteCommit` (or `PrepareAbort -> CompleteAbort`), plus `Dead` and `PrepareEpochFence`.
- It persists state to **`__transaction_state`**, an internal compacted topic (by default **50 partitions**, replication factor 3, `min.insync.replicas=2` in standard configs). Because it is replicated, a failing coordinator is replaced and recovers the state.
- It is the **only authority** that decides commit vs abort. Producers ask; the coordinator records the decision durably, then drives the markers.

### 5.4 Control markers

- Special **control records** (not delivered to applications) appended to each partition involved: **COMMIT** or **ABORT**.
- Each marker **consumes an offset**. So in a transactional topic **there are offset "holes" from the application's point of view**. Lag computed as `end offset - committed offset` can show **1 more** per transaction than the data records. (This surprises people: a consumer that has read everything can show a small steady "lag".)

### 5.5 Last stable offset (LSO)

- For each partition, the **LSO** = the offset **before the first record of the earliest still-open transaction** (or the high watermark if none open).
- `read_committed` consumers may read **only up to the LSO**.
- Consequence: **one long-open transaction blocks all `read_committed` consumers** of that partition behind it (head-of-line blocking), even for records of _other_ committed transactions that were written later. This is why transactions must be **short** and `transaction.timeout.ms` bounded.

### 5.6 Consumer offsets inside the transaction

- Committing offsets is a write to `__consumer_offsets`. `sendOffsetsToTransaction(offsets, groupMetadata)` makes the group coordinator **hold** those offsets as part of the transaction; they take effect only when the transaction commits.
- Abort means the offset does **not** advance; the input is reread after restart.

## 6. The life of a transaction, step by step

```
Producer P (transactional.id = "t1")          Txn coordinator (TC)         Partition leaders / group coord
-----------------------------------------------------------------------------------------------------------
1. initTransactions()
     ---- FindCoordinator, InitProducerId ---->  assign PID, epoch (bump)
          fence any older epoch; abort/complete an
          unfinished txn of the previous instance
2. beginTransaction()                            (client-local, no RPC)
3. consume a batch from "in" (read_committed)
4. send(out-0, r1)  ---- AddPartitionsToTxn --->  record partition out-0 in the txn (persisted)
     ---- Produce (PID, epoch, seq) ---------------------------------------->  append r1 (marked transactional)
5. send(out-3, r2)  ---- AddPartitionsToTxn --->  record out-3
     ---- Produce ------------------------------------------------------>  append r2
6. sendOffsetsToTransaction(offsets, groupMeta)
     ---- AddOffsetsToTxn ------------------->  record the group's offsets partition
     ---- TxnOffsetCommit ---------------------------------------------->  group coordinator stages offsets
7. commitTransaction()
     ---- EndTxn(COMMIT) -------------------->  write PrepareCommit to __transaction_state  (POINT OF NO RETURN)
                                                 ---- WriteTxnMarkers(COMMIT) ----> out-0, out-3, __consumer_offsets
                                                 markers appended; txn becomes visible
                                                 write CompleteCommit to __transaction_state
     <---- success ----------------------------
```

Key facts:

- **Records are appended during the transaction**, not at commit. Commit adds **markers**, not data. That keeps commit cheap (cost grows with the number of **partitions**, not the number of records).
- **The point of no return is the durable `PrepareCommit`** record in `__transaction_state`. After that the transaction **will** commit even if the coordinator or partition leaders crash; the new coordinator finishes writing the markers. Before it, the transaction may be aborted.
- `AddPartitionsToTxn` is called the **first time** a partition is written in the transaction (newer brokers and clients optimize this, KIP-890, but the concept is unchanged).
- If the producer crashes mid-transaction, the coordinator **times it out** after `transaction.timeout.ms` and **aborts** it; or the next instance with the same `transactional.id` calls `initTransactions()`, which **aborts the dangling transaction** and fences the old epoch.

### 6.1 Abort path

`abortTransaction()` or a timeout leads to `PrepareAbort`, then ABORT markers. The records stay in the log but are **skipped** by `read_committed` consumers using the **aborted-transactions index** returned with fetch responses. They are removed physically only by retention or compaction like any other record.

## 7. Control markers, offsets and the last stable offset

A worked picture of one partition `out-0`:

```
offset:   100   101   102   103   104   105   106   107   108
record:   a     b     T1:c  T1:d  e     T2:f  [C:T1] T2:g  [A:T2]
                      ^open  ^open  committed  ^open  COMMIT  ^open  ABORT
                      (T1)   (T1)   non-txn    (T2)   marker  (T2)   marker
```

- `a`, `b`, `e` are **non-transactional** (or committed) records.
- `c`, `d` belong to **T1**, committed by the marker at **106**.
- `f`, `g` belong to **T2**, aborted by the marker at **108**.

What each consumer sees:

| Consumer                                                       | Delivered     | Notes                                                                                                                           |
| -------------------------------------------------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `read_uncommitted` (default)                                   | a b c d e f g | All data records, including T2's aborted ones. Markers are never delivered.                                                     |
| `read_committed`, **while T1 open** (before offset 106 exists) | a b           | Stops at the LSO = 102 (first record of T1). Even `e` is **withheld**, although it is not transactional: ordering is preserved. |
| `read_committed`, after T1 commits, T2 still open              | a b c d e     | LSO = 105 (first record of the still-open T2)                                                                                   |
| `read_committed`, after both finish                            | a b c d e     | `f g` are skipped (aborted)                                                                                                     |

Observations that matter operationally:

1. **Records are visible in offset order**, so a long-open transaction delays **everything behind it** in that partition for `read_committed` readers.
2. Offset numbers **skip marker positions** (106 and 108). Do not assume consecutive offsets; do not compute "records processed" as `last offset - first offset + 1`.
3. **Log compaction** and retention handle markers, but aborted records occupy space until cleaned.

## 8. What the consumer sees: `read_committed` vs `read_uncommitted`

| Setting                                          | Behavior                                                                                                    | Use when                                                                                    |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `isolation.level=read_uncommitted` (**default**) | Sees all records, committed or not, including aborted transactions' records                                 | Consuming a non-transactional topic, or when you do not care about aborted data             |
| `isolation.level=read_committed`                 | Sees only records of committed transactions and non-transactional records, up to the LSO; **skips aborted** | **Any consumer of a topic written transactionally** where aborted data must not be acted on |

Important consequences:

- **Default is `read_uncommitted`.** A consumer that forgets to set `read_committed` will process aborted data: silently breaking the exactly-once result downstream. This is a classic mistake: the **producer side** is configured correctly and the guarantee still fails at the **consumer side**.
- **EOS is a pair of settings.** Producer: transactions. Consumer: `read_committed`. Both required.
- **Latency:** `read_committed` consumers wait until the transaction is **committed**, so end-to-end latency includes the transaction duration (often the `commit.interval.ms` in Kafka Streams, default 100 ms with EOS).
- Within a **consume-transform-produce** app, the **input** consumer itself should use `read_committed` too (so it does not process records of an upstream transaction that aborts).
- `read_committed` has **no effect** on a partition written without transactions; it just reads up to the high watermark.

## 9. Zombie fencing: epochs and `transactional.id`

### 9.1 The zombie problem (recall note 2, section 8.4)

An instance of the consume-transform-produce app stalls (GC pause, partition network cut). The group rebalances and the partition goes to a **new instance**, which starts processing from the last committed offset. Then the old instance **wakes up** and, believing it still owns the partition, writes its outputs and commits. Now both have produced outputs for the **same input**: **duplicates**, even though everything is "transactional".

### 9.2 How the epoch stops it

- The new instance calls `initTransactions()` with the **same `transactional.id`**. The coordinator **bumps the epoch** and records it.
- When the old instance sends its `Produce` or `EndTxn`, it carries the **old epoch**. The broker answers **`ProducerFencedException`** (or `InvalidProducerEpoch`). The old instance's transaction **cannot commit**.
- Reaction in the application: **close the producer and exit** (or re-create from scratch), never retry the transaction. A fenced producer is permanently dead.

### 9.3 Why the id must be **stable and task-bound**

Fencing works only if the zombie and its replacement **share the same `transactional.id`**. If every restart picked a random id, the coordinator would see two unrelated producers and **fence nobody**. Hence:

| Design              | `transactional.id`                               | Fencing                                                                                                                                      |
| ------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| EOS v1 (older)      | **One id per input partition** (e.g. `app-in-3`) | A partition always maps to the same id, so the new owner fences the old owner of that partition. Costs **one producer per input partition**. |
| EOS v2 (section 10) | One id per **instance**                          | Fencing done through consumer **group generation** instead; far fewer producers.                                                             |

## 10. EOS v2: fencing by consumer group

### 10.1 Why v1 was heavy

With one transactional producer **per input partition**, an app owning 1,000 partitions needed 1,000 producers, 1,000 sets of network connections and transaction-coordinator state. Painful at scale.

### 10.2 What v2 changed (KIP-447, Kafka 2.5+)

- A single transactional producer per **application instance** can write transactions covering offsets from **many input partitions**.
- `sendOffsetsToTransaction` takes the **consumer group metadata** (`group.id`, **generation id**, member id), not just the group id.
- The group coordinator **checks the generation** when the offsets are committed: if the producer's consumer is **no longer a valid member** of the current generation (it was rebalanced away), the **offset commit is rejected**, the transaction **cannot commit**, and the zombie is stopped.
- Requires brokers **2.5+** and clients **2.5+** (in Kafka Streams: `exactly_once_v2`, formerly called `exactly_once_beta`; it replaced `exactly_once` v1, which was deprecated).

### 10.3 What it means for you

- The **fence** that protects against zombies in EOS v2 is **"the consumer's group membership at commit time"**, not just the producer epoch.
- The guarantee still **only covers Kafka writes**. A zombie's write to Postgres is **not** fenced by any of this (section 14).

## 11. Failure scenarios, one by one

| Scenario                                                                          | What happens                                                                                                                 | Result                                                                              |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Producer crashes **before** `commitTransaction`                                   | Coordinator times out the txn after `transaction.timeout.ms` (or new instance's `initTransactions` aborts it); ABORT markers | Outputs invisible; input offset not advanced; reprocessed. **No duplicate output.** |
| Producer crashes **after** `PrepareCommit` persisted                              | New coordinator completes the commit and writes markers                                                                      | Transaction **committed**. Idempotent completion.                                   |
| Coordinator broker fails mid-commit                                               | Another replica of `__transaction_state` partition becomes coordinator, replays log                                          | Same as above; commit or abort completes                                            |
| A partition leader fails during the transaction                                   | Producer retries to the new leader (idempotent, same PID/epoch/sequence)                                                     | Transaction continues; if it cannot, it aborts                                      |
| Network partition cuts producer from coordinator                                  | Transaction times out                                                                                                        | Abort; reprocess                                                                    |
| Zombie producer after rebalance                                                   | Fenced (epoch or group generation)                                                                                           | Zombie's transaction fails; exits                                                   |
| Consumer (`read_committed`) crashes mid-read                                      | Resumes at its committed offset                                                                                              | Reads only committed data again                                                     |
| `transaction.timeout.ms` shorter than processing time                             | Coordinator aborts a transaction the app is still using                                                                      | App's next call throws; progress lost; risk of **abort loop**                       |
| Producer calls `send` after the transaction was aborted                           | `InvalidTxnState`/fenced error                                                                                               | Must begin a new transaction                                                        |
| Application **writes to Postgres** inside the loop, then Kafka transaction aborts | **Postgres write stays**; Kafka side rolls back                                                                              | **Inconsistency.** The boundary (section 14).                                       |

The last row is the essence of the note.

## 12. Configuration reference

### 12.1 Producer (transactional)

| Setting                                 | Required/typical                             | Meaning                                                                                                                                                                    |
| --------------------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `transactional.id`                      | Required, stable                             | Identity for fencing and recovery                                                                                                                                          |
| `enable.idempotence`                    | **Forced to `true`**                         | Transactions imply idempotence                                                                                                                                             |
| `acks`                                  | **`all`** (forced)                           | Durability of the data and markers                                                                                                                                         |
| `retries`                               | > 0 (effectively unlimited with idempotence) | Retries safe because of sequences                                                                                                                                          |
| `max.in.flight.requests.per.connection` | <= 5                                         | Order preserved with idempotence                                                                                                                                           |
| `transaction.timeout.ms`                | Default **60000** (1 min)                    | How long the coordinator waits before aborting an open transaction. Must be <= the broker's `transaction.max.timeout.ms` (default **15 min**) or `initTransactions` fails. |

### 12.2 Consumer

| Setting              | Typical              | Meaning                                                                |
| -------------------- | -------------------- | ---------------------------------------------------------------------- |
| `isolation.level`    | **`read_committed`** | Hide uncommitted and aborted data                                      |
| `enable.auto.commit` | **`false`**          | Offsets are committed **through the transaction**, not by the consumer |
| `group.id`           | Required             | Offsets belong to the group                                            |

### 12.3 Broker

| Setting                                    | Typical | Meaning                         |
| ------------------------------------------ | ------- | ------------------------------- |
| `transaction.state.log.replication.factor` | 3       | Durability of coordinator state |
| `transaction.state.log.min.isr`            | 2       | Same                            |
| `transaction.state.log.num.partitions`     | 50      | Spreads coordinators            |
| `transaction.max.timeout.ms`               | 900000  | Upper bound for client timeouts |
| `transactional.id.expiration.ms`           | 7 days  | Unused ids are forgotten        |

Raising `transaction.state.log.replication.factor` after the first transaction is awkward; the internal topic is created on first use, so a single-broker dev cluster needs **explicit overrides** (RF 1, min ISR 1) or transactions hang at `initTransactions`. (This is a standard gotcha on a one-broker local setup.)

## 13. Code shape

### 13.1 Language-neutral pseudocode of the canonical loop

```
producer.initTransactions()                       // once at startup; fences older instances
consumer.subscribe(["in"])                        // isolation.level=read_committed, enable.auto.commit=false

loop:
    records = consumer.poll()
    if records is empty: continue

    producer.beginTransaction()
    try:
        for r in records:
            out = transform(r)
            producer.send("out", key(r), out)

        producer.sendOffsetsToTransaction(
            offsets  = { partition: lastOffset + 1 for each partition in records },
            groupMetadata = consumer.groupMetadata()     // EOS v2: includes generation
        )
        producer.commitTransaction()

    catch ProducerFenced / fatal error:
        producer.close(); exit()                  // never retry a fenced producer
    catch other (abortable) error:
        producer.abortTransaction()
        consumer.seekToCommitted()                // re-read the same input
```

Rules embedded in that sketch:

1. Commit offset = **last consumed offset + 1**.
2. Offsets are **only** committed through the transaction.
3. On abort, the consumer must **seek back** to the committed position or it would skip the batch it just failed.
4. **Fenced = die.**
5. Keep the batch **small** and the transaction **short** (LSO blocking, timeout).

### 13.2 The client EventPulse uses

The repo uses `@confluentinc/kafka-javascript`, which is librdkafka-based and exposes both a KafkaJS-compatible API and a lower-level API. Transactions exist in the librdkafka layer (`init_transactions`, `begin_transaction`, `send_offsets_to_transaction`, `commit_transaction`, `abort_transaction`), and in the KafkaJS-style API as `producer.transaction()` with `send` and `sendOffsets` followed by `commit()` or `abort()`. Treat the exact method names and whether EOS v2 group metadata is passed as **client-version specific** and read the client's docs before relying on them. **The EventPulse sink does not call any of this** (section 19).

## 14. The boundary: where Kafka EOS stops

This is the section to memorize.

### 14.1 The statement

> **Kafka's exactly-once guarantee covers: reads from Kafka topics (read_committed), writes to Kafka topics, and offset commits to Kafka. Anything the handler does to another system is outside the transaction.**

### 14.2 The picture

```
        +-----------------------------  KAFKA TRANSACTION BOUNDARY  ----------------------------+
        |                                                                                         |
        |   topic "in" ──consume──>  [ handler ] ──produce──> topic "out"                         |
        |        ^                       |                                                        |
        |        └── offsets (__consumer_offsets) ──── committed atomically with "out" ────┘       |
        +-----------------------------------------------------------------------------------------+
                                         |
                                         |  these are OUTSIDE
                                         v
                      Postgres INSERT      Redis SET      HTTP call      email / SMS      file write
```

### 14.3 What goes wrong if the handler writes to Postgres

Handler sequence in a transactional consume-transform-produce loop:

```
beginTransaction
  rows -> INSERT INTO events ...           (Postgres, own transaction)
  send results to Kafka "out"
  sendOffsetsToTransaction
commitTransaction
```

Crash points and outcomes:

| Crash point                                | Postgres     | Kafka                                   | Outcome after restart                                           |
| ------------------------------------------ | ------------ | --------------------------------------- | --------------------------------------------------------------- |
| After Postgres COMMIT, before Kafka commit | Rows exist   | Transaction aborts, offset not advanced | Input reprocessed: **Postgres written twice** unless idempotent |
| After Kafka commit, before Postgres COMMIT | Rows missing | Offset advanced and outputs visible     | **Lost Postgres rows**; Kafka says done                         |
| Postgres COMMIT, Kafka commit both succeed | OK           | OK                                      | Fine (the happy path)                                           |

Because the two commits are **separate commits on separate systems**, a crash **between** them leaves them **inconsistent**. That is the Two Generals problem again (note 2) between Kafka's coordinator and Postgres. The **Kafka transaction cannot reach into Postgres**, and **Postgres has no knowledge of Kafka's epoch or markers**.

Ordering the two commits does not remove the problem; it only chooses whether the failure is a **duplicate** (Postgres first) or a **loss** (Kafka first). This is exactly note 1, section 9: **record progress after the effect** gives duplicates, which is the safe direction.

### 14.4 The same boundary, stated for every non-Kafka target

| Target                    | Why Kafka cannot cover it                                                | Cross-boundary tool                                                           |
| ------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------- |
| Postgres / any SQL DB     | Separate transaction manager, no shared commit                           | Idempotent insert; inbox; offsets in the DB; outbox for the reverse direction |
| Redis                     | No transactions across systems; writes are immediate and not rolled back | Idempotent ops, `SET NX`, TTL-aware design                                    |
| HTTP API call             | Remote side effect, cannot be undone                                     | **Idempotency key** header on the call                                        |
| Email / SMS / webhooks    | Irreversible                                                             | Dedup key at the provider or your own sent-log                                |
| File / object store       | Separate write                                                           | Write-then-rename, or deterministic key (overwrite-safe)                      |
| Another Kafka **cluster** | Transactions are per-cluster                                             | Idempotent consumer on the destination; MirrorMaker 2 gives at-least-once     |

### 14.5 Two hidden boundaries inside Kafka itself

1. **Consumers that are not `read_committed`** see uncommitted/aborted data. The guarantee is **opt-in at the reader**.
2. **Transactions do not span clusters.** A cross-datacenter flow is two separate guarantees.

### 14.6 The interview-ready answer

"Kafka EOS gives atomic consume-process-produce **within Kafka**. When the process step writes to an external database, the database commit and the Kafka commit are two independent commits; a crash between them can duplicate or lose. So I run at-least-once and make the database write idempotent with a unique key, which gives an exactly-once **effect** in Postgres. If I need Kafka-to-Kafka stream processing, then transactions (or Kafka Streams with `exactly_once_v2`) are the right tool."

## 15. Crossing the boundary safely

When a Kafka consumer must write to a database, these are the four patterns, in order of preference for typical systems.

| Pattern                                   | How                                                                                                                                                        | Guarantee                                                                          | Cost                                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **1. Idempotent write (EventPulse sink)** | Unique key, `INSERT ... ON CONFLICT DO NOTHING`, then commit offset                                                                                        | Exactly-once **effect**; at-least-once delivery                                    | A unique index; absorbed duplicates cost one wasted row attempt                      |
| **2. Inbox table**                        | In **one DB transaction**: insert the message id into `inbox` (PK) and apply the effect; skip if the insert conflicts                                      | Exactly-once effect for non-idempotent effects (counters, balances)                | Extra table and write                                                                |
| **3. Offsets in the database**            | Store `(topic, partition, offset)` **in the same DB transaction** as the effect; on startup `seek` to the stored offset instead of the Kafka-committed one | Atomic effect + progress; true exactly-once effect even for non-idempotent effects | You manage assignment/rebalance yourself; Kafka's group offsets become informational |
| **4. Two-phase commit / XA**              | Coordinate Kafka and DB with a transaction manager                                                                                                         | In theory exact                                                                    | Kafka does not support XA; heavy, blocking; practically unused                       |

For the reverse direction (**DB change must become a Kafka event**), the tool is the **transactional outbox** (Stage 3 later note), because Kafka cannot join the DB's transaction either.

Rule of thumb: **make the sink idempotent; reach for patterns 2-3 only if the effect is not idempotent by nature.**

## 16. Cost, limits and failure modes

| Aspect                     | Impact                                                                                                                                                                                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Throughput**             | Per-transaction overhead (several RPCs, markers on each partition). Throughput degrades for **tiny** transactions; larger transactions amortize. Producers often see modest overhead (single-digit to low double-digit percent) at sensible batch sizes. Measure; do not assume. |
| **Latency**                | End-to-end latency for `read_committed` readers includes the whole transaction duration plus marker propagation.                                                                                                                                                                 |
| **Head-of-line blocking**  | An open transaction pins the LSO and stalls `read_committed` consumers on that partition until it ends or times out.                                                                                                                                                             |
| **Marker overhead**        | One marker per partition per transaction. A transaction touching many partitions writes many markers.                                                                                                                                                                            |
| **Coordinator load**       | Each transaction updates `__transaction_state` several times. Many producers means more coordinator work (EOS v2 reduces producers).                                                                                                                                             |
| **Timeouts**               | Too short: spurious aborts. Too long: blocked readers when a producer dies.                                                                                                                                                                                                      |
| **Abort loops**            | A deterministic failure (a poison record) leads to an abort, a retry and an abort again; needs a DLQ strategy.                                                                                                                                                                   |
| **Operational complexity** | More failure states, more metrics (`txn` state, fenced producers). Needs `read_committed` discipline across all consumers.                                                                                                                                                       |
| **Topic scope**            | Only data in the same cluster.                                                                                                                                                                                                                                                   |
| **Storage**                | Aborted records still occupy log space until retention or compaction.                                                                                                                                                                                                            |

## 17. Kafka Streams and `exactly_once_v2`

Kafka Streams applies the pattern for you:

- Setting `processing.guarantee=exactly_once_v2` makes Streams use a transactional producer per **thread** (EOS v2), commit offsets and state-store changelogs **in the same transaction** as the output records, and run consumers with `read_committed`.
- **State stores** (RocksDB) are backed by **changelog topics**; the changelog writes are Kafka writes, so they are inside the transaction. After a crash, the store is rebuilt from the changelog consistent with the committed outputs. This is why Streams can offer exactly-once for **stateful** operations **as long as the state lives in Kafka**.
- If a Streams processor **calls an external service or database** inside `process()`, that call is **outside** the transaction. EOS does not extend to it. Same boundary.
- Default `commit.interval.ms` drops from 30,000 ms (at-least-once) to **100 ms** under EOS, so a transaction is committed frequently; this keeps latency low but means many small transactions.

Stage 4 of EventPulse (stream processing and analytics) is where this becomes relevant: aggregation in Kafka Streams or a similar engine can run with EOS **as long as the sink to the serving database is idempotent or upserts by key**.

## 18. When to use transactions and when not to

**Use Kafka transactions when:**

- The pipeline is **Kafka to Kafka** (stream processing, enrichment, routing, windowed aggregation, joins).
- Output must be **all-or-nothing across several topics or partitions**.
- You want to avoid the cost of idempotent consumers downstream **and** all downstream consumers can use `read_committed`.
- You publish **events plus a state change topic** (changelog) that must stay consistent.

**Do not use them when:**

- The sink is a **database or external API** (they cannot cover it; use idempotent writes).
- Throughput of **tiny messages** is critical and you can deduplicate cheaply by key.
- **Downstream consumers are not under your control** and may read uncommitted data.
- The extra operational complexity is not justified by the correctness requirement. An idempotent consumer is often **simpler and sufficient**.

A useful heuristic: **if the last box in the diagram is not Kafka, transactions only protect the middle of the pipeline, and the last hop still needs idempotence.** Since idempotence is then required anyway, ask whether the transaction adds anything.

## 19. EventPulse decisions

| Decision                                        | Choice                                                                                       | Reason                                                                                                                                                                                          |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Use Kafka transactions on the sink path         | **No**                                                                                       | Sink writes to Postgres, outside Kafka's boundary                                                                                                                                               |
| How the sink achieves exactly-once effect       | `INSERT ... ON CONFLICT (event_id) DO NOTHING`, then commit the offset (`autoCommit: false`) | Simple, durable, no TTL; crash gives duplicates, never loss                                                                                                                                     |
| Idempotent producer on `ingest-api`             | **On** (`KAFKA_IDEMPOTENT=true`, `acks=-1`)                                                  | Cheap, removes library-retry duplicates (note 4)                                                                                                                                                |
| Where transactions would be considered          | Stage 4: Kafka-to-Kafka stream processing and derived topics                                 | Inside Kafka; EOS v2 fits                                                                                                                                                                       |
| If a later consumer of a derived topic is added | Must set `isolation.level=read_committed`                                                    | Otherwise reads aborted data                                                                                                                                                                    |
| Document the boundary                           | Yes, in `notebook/correctness-notes.md` and the delivery guarantees document                 | Required by the Stage 3 plan                                                                                                                                                                    |
| DLQ and retry topics                            | Written by the consumer with normal produces, **not** transactionally with the offset        | Duplicates tolerated; the sink is idempotent. Note: a DLQ publish followed by a crash before the offset commit **re-publishes** the DLQ entry on restart; the DLQ replay must be idempotent too |

The last row is subtle and worth restating: **any side channel the consumer writes to (DLQ, retry topic, metrics, outbox) has its own at-least-once behavior** unless included in a real Kafka transaction with the offset commit. A transactional DLQ write would close that gap, but only for Kafka-to-Kafka writes; the Postgres write is still separate.

## 20. Common confusions

1. **"Kafka has exactly-once, so my Postgres sink is exactly-once."** No. The transaction covers Kafka writes only.
2. **"Idempotent producer equals transactions."** Idempotence is per-session, per-partition duplicate suppression. Transactions add atomicity across partitions, offset commits, restart-stable identity, and `read_committed` visibility. Transactions include idempotence; not the reverse.
3. **"Aborted records are deleted."** They remain in the log; they are **skipped by `read_committed` readers**.
4. **"`read_committed` is a producer setting."** It is a **consumer** setting. Without it the transactional guarantee is **not visible** to that consumer.
5. **"Consumer lag is always zero when caught up."** With transactions, markers occupy offsets, so a caught-up `read_committed` consumer can show a small constant lag.
6. **"A fenced producer can retry."** Never. Close it and recreate.
7. **"Transactions make processing exactly-once in my handler."** The handler's code can still run multiple times (after an abort, the batch is reprocessed). Its **Kafka outputs** appear once; its **other effects** may happen repeatedly.
8. **"One transactional.id per app is fine."** Two live instances sharing one id **fence each other repeatedly**. Each concurrent instance needs a distinct id (EOS v2) or a task-bound id (EOS v1).
9. **"Transactions work across two Kafka clusters."** They do not.
10. **"Long transactions are fine, we only care about throughput."** They block the LSO and stall `read_committed` consumers.

## 22. Cheat sheet

### Glossary

| Term                    | Meaning                                                                         |
| ----------------------- | ------------------------------------------------------------------------------- |
| Transaction             | Atomic set of Kafka writes plus offset commits                                  |
| `transactional.id`      | Stable producer identity enabling fencing and recovery                          |
| PID / epoch             | Producer id and a counter bumped on each `initTransactions`                     |
| Transaction coordinator | Broker owning the state machine for a `transactional.id`                        |
| `__transaction_state`   | Internal replicated topic holding transaction state                             |
| Control marker          | COMMIT/ABORT record appended to each partition involved                         |
| LSO                     | Last stable offset; the limit for `read_committed` readers                      |
| `read_committed`        | Consumer mode that hides uncommitted/aborted data                               |
| Zombie                  | Stale producer instance that resumes after being replaced                       |
| Fencing                 | Rejecting the stale instance via epoch or group generation                      |
| EOS v1 / v2             | Per-partition producers vs per-instance producers with group-generation fencing |
| Boundary                | The edge of what the transaction can make atomic: Kafka only                    |

### Rules

1. Atomic means **visibility** decided atomically; data is written early, markers decide.
2. Both sides of EOS: transactional producer **and** `read_committed` consumer.
3. Offsets are committed **inside** the transaction, `enable.auto.commit=false`.
4. Fenced means dead: close and recreate.
5. Keep transactions short; mind `transaction.timeout.ms`.
6. **Kafka transactions never include a database write.** Use idempotent writes or an inbox there.
7. If the last hop is not Kafka, the last hop needs its own idempotence.

### The boundary, drawn once

```
 Kafka-only pipeline:   in ─► handler ─► out      + offsets      => atomic (EOS)
 Kafka ─► Postgres:     in ─► handler ─► INSERT                 => NOT atomic with offsets
                                                                    use ON CONFLICT / inbox / offsets-in-DB
```

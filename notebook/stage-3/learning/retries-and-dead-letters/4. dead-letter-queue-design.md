# The Dead-Letter Queue: Design and Metadata

_Retries-and-dead-letters note 4 of 5 in the Stage 3 learning notes. Read [note 1](1.%20transient-vs-permanent-failures.md) (what deserves quarantine) and [note 3](3.%20retry-topics-and-delayed-processing.md) (the retry path that ends here). A dead-letter queue (DLQ) is a quarantine: failed messages are set aside so the main flow can proceed, with enough evidence to diagnose and replay them later. This note covers what a DLQ is for, what a good dead-letter record contains, how EventPulse's `events.dlq` is built today, and how to operate it so it never becomes a graveyard. It supports S3-F5 (DLQ with full diagnostic metadata) and prepares S3-F6 (replay, [note 5](5.%20dlq-replay-tooling.md))._

**No labs here.** EventPulse's DLQ was built and observed in Stage 2 (S2-F4). This note reads that implementation ([`dlq-publisher.ts`](../../../../services/consumer-sink/src/sink/dlq-publisher.ts), [`errors.ts`](../../../../services/consumer-sink/src/sink/errors.ts), [`batch-handler.ts`](../../../../services/consumer-sink/src/consumer/batch-handler.ts), the helper script [`scripts/dlq-peek.sh`](../../../../scripts/dlq-peek.sh)) and the [observation notes](../../../stage-2/s2-f4-poison-before-fix.md); nothing new was run. ## 1. TL;DR

- A DLQ is a **quarantine with an inventory**: it takes a message that cannot be processed _right now, as is_, moves it out of the main flow so the partition can advance, and keeps it with the evidence needed to fix and replay it.
- It is **not** a trash can, a log, a retry mechanism or a place to ignore. A DLQ nobody reads is silent data loss with extra steps.
- A good dead letter has: the **original bytes** (key, value, headers), **provenance** (topic, partition, offset, consumer group), **failure facts** (error class, code, message, attempts) and **time** (first failure, final failure). With those, a stranger at 3 a.m. can answer "what is it, where did it come from, why did it fail, and can I replay it?"
- **Write to the DLQ and wait for the ack before committing the source offset.** A crash in between creates a **duplicate** dead letter, never a **lost** one.
- The DLQ must be **as durable as the main topic** (replication, min ISR) and have **retention long enough** for humans to act (longer than the source's).
- Only **message-scoped** failures belong there ([note 1](1.%20transient-vs-permanent-failures.md)). A database outage or a systemic error must never feed it.
- Treat the DLQ as an **inbox with an owner, an SLO and an alert**. Its size, rate and age are production signals.

> **One-line version:** _A DLQ is where a message waits for a human, so label it for the human, keep it safe, and make sure a human is actually watching._

## 2. The mental model: the evidence locker

A police evidence locker works only because of its chain of custody.

| Evidence locker                                                 | Dead-letter queue                                             |
| --------------------------------------------------------------- | ------------------------------------------------------------- |
| The item itself, in a sealed bag                                | The **original bytes**, untouched                             |
| A tag: where found, when, by whom                               | Original topic, partition, offset, consumer group, timestamps |
| A note: why it was collected                                    | Error class, code, message, attempt count                     |
| Retained for the length of the case                             | Retention longer than the source                              |
| Cannot be thrown away without a record                          | Deleted only by a deliberate, logged action                   |
| Detectives open it, check it, return the item or close the case | Replay or discard, with an audit trail                        |

A bag with no tag is junk. A locker nobody visits is a warehouse. The design question is always: _could someone who has never seen this system decide what to do with this item?_

## 3. What a DLQ is and is not

| It is                                                               | It is not                                      |
| ------------------------------------------------------------------- | ---------------------------------------------- |
| A durable, replicated **Kafka topic** (in EventPulse: `events.dlq`) | A log file                                     |
| A place for **message-scoped, non-recoverable-in-place** failures   | A place for dependency outages (pause instead) |
| An **inventory** with metadata                                      | A blind copy of the message                    |
| **Reversible**: records can be replayed after a fix                 | A permanent discard                            |
| A **signal** (rate, age, size are metrics)                          | Something to ignore until storage fills        |
| Owned by a **team and a process**                                   | "Somebody's problem"                           |

Terminology: "dead-letter _queue_" comes from message brokers (RabbitMQ DLX, SQS DLQ, JMS). In Kafka there is no built-in DLQ: the "queue" is a normal topic that your consumer publishes to. Kafka Connect has `errors.tolerance=all` with `errors.deadletterqueue.topic.name`, which is a framework feature; a plain consumer must build it.

## 4. When a message becomes a dead letter

From the earlier notes, a message is dead-lettered when **all** of these hold:

1. The failure is **attributable to this message** (note 1, scope), established by isolation, not assumed.
2. **In-place retries are exhausted** (`SINK_MAX_RETRIES` = 3 for an isolated bad row) or the failure is deterministic (parse errors skip retries).
3. If a retry-topic path exists, **all tiers are exhausted** (note 3).
4. The failure is not systemic and the flood breaker has not tripped.

Typical dead-letter causes in EventPulse:

| Cause                                            | Class (`errors.ts`) | Example                                                                       |
| ------------------------------------------------ | ------------------- | ----------------------------------------------------------------------------- |
| Invalid JSON                                     | `PERMANENT_PARSE`   | The `produce-poison.sh --kind invalid-json` record at partition 5 offset 2893 |
| Invalid UUID, missing required field, wrong type | `PERMANENT_PARSE`   | `event_id` is not a UUID                                                      |
| Postgres rejects this row                        | `PERMANENT_DB`      | Value out of range (`22xxx`), NOT NULL / check violation (`23xxx`)            |
| Unrecognised error that persisted                | `UNKNOWN`           | A new library error                                                           |

What **never** becomes a dead letter: `TRANSIENT_DB` and `SYSTEMIC_DB` (`isBlocking`).

## 5. The dead-letter record: payload

**Keep the original bytes.** This is the first and most important rule.

| Choice                                                    | Result                                                                                                            |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Original key and value bytes, unmodified** (EventPulse) | The failure is inspectable exactly; replay reproduces what was sent; no information lost by a buggy parser        |
| Parsed/re-serialised JSON                                 | A parser bug or normalisation silently changes the evidence; you cannot tell whether the original was valid UTF-8 |
| Only an error string                                      | You cannot replay                                                                                                 |
| Only the message id                                       | You must find the original, which retention may have deleted                                                      |

If the payload is not valid UTF-8 (a binary blob where JSON was expected, which is a real poison case), only raw bytes can represent it. This is why the DLQ value is the original `Buffer`, not a string.

The **key** is preserved so that a replay lands on the same partition and keeps per-key locality, and so you can group dead letters by tenant (`tenant_id` keys: see [producer key note](../../../stage-2/learning/producer/6.%20kafka-producer-key-and-partitioner.md)).

**Size:** a dead letter is the original plus headers. If the original was near `max.message.bytes`, adding headers may exceed it. Set the DLQ topic's `max.message.bytes` a little higher than the source's, and truncate error text (EventPulse truncates to 1,024 bytes).

## 6. The dead-letter record: metadata

The checklist, with the reason each field earns its bytes. Fields in the first table are **[observed]** in `DLQ_HEADERS` ([`dlq-publisher.ts`](../../../../services/consumer-sink/src/sink/dlq-publisher.ts)); the second table is **[design]** additions.

### 6.1 Present today

| Header                   | Example                                              | Answers                                                                                       |
| ------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `dlq.original_topic`     | `events.raw`                                         | Where did it come from?                                                                       |
| `dlq.original_partition` | `5`                                                  | Which partition?                                                                              |
| `dlq.original_offset`    | `2893`                                               | Which record? (with topic and partition this is the **unique identity** of the source record) |
| `dlq.consumer_group`     | `sink-postgres`                                      | Which consumer failed?                                                                        |
| `dlq.error_class`        | `PERMANENT_PARSE`                                    | What kind of failure? Group by this                                                           |
| `dlq.error_code`         | `none` / `22P02`                                     | Machine-readable cause                                                                        |
| `dlq.error_message`      | `Unexpected token 'b'...` (truncated to 1,024 bytes) | Human-readable cause                                                                          |
| `dlq.attempts`           | `4`                                                  | How hard did we try?                                                                          |
| `dlq.failed_at`          | ISO timestamp                                        | When did it die?                                                                              |
| _all original headers_   | `traceparent`, producer metadata                     | Context preserved, un-namespaced                                                              |

### 6.2 Worth adding **[design]**

| Header                                                    | Why                                                                    |
| --------------------------------------------------------- | ---------------------------------------------------------------------- |
| `dlq.original_timestamp` (and type: create/log-append)    | The age of the data; needed to judge staleness at replay               |
| `dlq.first_failed_at`                                     | Total time in the failure loop (with retry topics)                     |
| `dlq.consumer_version` / `dlq.git_sha`                    | **Which code failed**: crucial to know whether a fix has shipped since |
| `dlq.classifier_version`                                  | The classification table version, for re-classification                |
| `dlq.stage` (`parse`, `write`, `publish`)                 | Where in the pipeline it failed                                        |
| `dlq.stack_hash` (hash of the normalised stack)           | Group thousands of dead letters by one root cause                      |
| `dlq.replay_count`, `dlq.replayed_from`                   | Loop protection and audit (note 5)                                     |
| `dlq.dedup_key` (a stable hash of topic/partition/offset) | Detect duplicate dead letters (section 9)                              |
| `dlq.schema_id` / content type                            | How to decode the bytes                                                |
| `dlq.tenant_id` (if not recoverable from the key)         | Triage by customer without decoding the payload                        |

### 6.3 What not to put there

- **Secrets and PII in error messages.** Error text may contain the row's values (Postgres error "Failing row contains (...)"). Redact before writing; see section 12.
- **Giant stack traces.** Store a hash and a short first line; keep full traces in logs keyed by the same trace id.
- **Derived data that can be recomputed.**

### 6.4 The litmus test

Given only the dead-letter record (not the source topic, not the logs), can you: identify the source record, classify the cause, decide whether a fix has shipped, and replay it correctly? If any answer is no, a header is missing.

## 7. Headers vs envelope

Two designs for carrying metadata.

|                      | **Headers on the original record** (EventPulse)                 | **Envelope** (wrap payload in a JSON/Avro DLQ message with `{original: bytes, error: {...}}`) |
| -------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Original value       | Byte-identical; replay is a straight republish                  | Nested/base64; replay must unwrap                                                             |
| Consumers of the DLQ | Can treat it as the original topic                              | Need to know the envelope schema                                                              |
| Binary-safe          | Yes                                                             | Needs encoding                                                                                |
| Metadata size        | Headers are small key/value pairs; limits per record apply      | Free-form but must be maintained                                                              |
| Schema evolution     | Add headers freely                                              | Version the envelope                                                                          |
| Queryability         | Headers are not queryable by Kafka itself; tools must read them | Can be projected into columns by a connector                                                  |
| Typical use          | Small teams, replay by republish                                | Data-platform teams, DLQ analysed in SQL                                                      |

Headers keep **replay trivial**, which is what matters in this series. If DLQ analytics grow, add a _second_ consumer that reads the DLQ topic and writes metadata rows into a table (`dlq_events`) for SQL triage, leaving the topic itself unchanged.

## 8. EventPulse today: reading the publisher

`DlqPublisher` **[observed]**:

```ts
this.producer = createKafka({
  ...kafka,
  clientId: `${kafka.clientId}-dlq`,
}).producer({
  kafkaJS: { acks: -1, idempotent: true, allowAutoTopicCreation: false },
  "linger.ms": 0,
  "message.timeout.ms": 15_000,
});
```

Design choices to notice:

| Setting                                  | Meaning                               | Why                                                                                                                                                 |
| ---------------------------------------- | ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Separate producer and client id (`-dlq`) | Independent from anything else        | Identifiable in broker logs and metrics; failure isolation                                                                                          |
| `acks: -1` (all)                         | Wait for the ISR                      | A dead letter is the only copy of a failure; it must be durable ([producer note 2](../../../stage-2/learning/producer/2.%20kafka-producer-acks.md)) |
| `idempotent: true`                       | Dedups library retries                | Removes one duplicate source ([producer note 3](../../../stage-2/learning/producer/3.%20kafka-producer-idempotence.md))                             |
| `allowAutoTopicCreation: false`          | A typo in the topic name fails loudly | Auto-created topics get default (weak) settings                                                                                                     |
| `linger.ms: 0`                           | No batching delay                     | Dead letters are rare; latency matters more than throughput                                                                                         |
| `message.timeout.ms: 15000`              | Give up after 15 s                    | Bounded; failure means "do not commit the source offset"                                                                                            |

`publish()` resolves **only when every dead letter is acknowledged**; `toDlqMessage()` is a pure function (unit-testable) that copies the key and the raw value and merges original headers with the `dlq.*` headers. `originalHeaders` normalises header values (arrays, buffers, strings) so nothing is dropped.

The DLQ topic name is `SINK_DLQ_TOPIC` (default constant `TOPIC_EVENTS_DLQ`, `events.dlq`), and `SINK_DLQ_ENABLED=false` restores the old behavior where a poison record blocks its partition (useful for the "before" experiments).

To inspect: the repo's `scripts/dlq-peek.sh` reads the topic (see [`scripts/dlq-peek.sh`](../../../../scripts/dlq-peek.sh)).

## 9. Ordering of operations and the duplicate window

The handler's protocol (header comment of `batch-handler.ts`, **[observed]**):

```
 ... isolate bad rows; write good rows to Postgres
 publish dead letters to the DLQ and WAIT for the ack   (failure -> throw; nothing resolved)
 resolveOffset(last offset of the chunk) + commit
```

Crash analysis:

| Crash point                         | State                                                        | Next start                                                                                  | Result                           |
| ----------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | -------------------------------- |
| Before DLQ publish                  | Good rows stored, no dead letter written, offset uncommitted | Chunk re-read; good rows duplicate-absorbed (`ON CONFLICT DO NOTHING`); bad rows fail again | Dead letter produced once, later |
| After DLQ ack, before offset commit | Dead letter written; offset uncommitted                      | Chunk re-read; the bad row fails and is dead-lettered **again**                             | **Duplicate dead letter**        |
| After commit                        | Consistent                                                   |                                                                                             | No problem                       |
| DLQ publish fails (Kafka down)      | Throw; nothing committed                                     | Chunk retried                                                                               | No loss                          |

The invariant: **duplicate dead letters are possible; lost dead letters are not.** The code comment says exactly this ("so a DLQ record can be duplicated; noted for Stage 3").

### 9.1 Deduplicating the DLQ **[design]**

Two layers:

1. **Identity key.** `(original_topic, original_partition, original_offset)` uniquely identifies the source record. Put a hash of it in `dlq.dedup_key` (or use it as the message key if you accept losing the original key; better to keep the original key and use a header).
2. **At read time.** The replay tool and the triage view group by that identity and treat repeats as one item (note 5). The DLQ topic itself stays append-only; compaction is not suitable because the original key is not unique.

Do not try to suppress duplicates at write time with a read-before-write: the DLQ path should be as simple as possible. Dedup downstream.

## 10. One DLQ or many

| Layout                                                     | Pros                                                                                              | Cons                                                                     |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| **One DLQ for the whole company**                          | One place to look                                                                                 | Mixed schemas and owners; noisy neighbour; no per-team retention or ACLs |
| **One DLQ per source topic** (`events.raw` → `events.dlq`) | Same schema, owner and retention as the source; replay target is obvious                          | More topics                                                              |
| **One DLQ per consumer group per topic**                   | Distinguishes which consumer failed (different consumers may fail differently on the same record) | Many topics                                                              |
| **Per error class** (`events.dlq.parse`, `events.dlq.db`)  | Different handling: parse errors need producer fixes; DB errors need schema fixes                 | Fragmentation; harder to alert                                           |

Recommended default: **one DLQ per source topic**, with `dlq.consumer_group` and `dlq.error_class` as headers. EventPulse follows this (`events.dlq`). If a second consumer group on `events.raw` appears, the `dlq.consumer_group` header keeps its dead letters separable.

Match the DLQ's **partition count** to the source if you want per-key locality at replay; if you only ever read it with a tool, one or two partitions suffice and keep ordering by time simple.

## 11. Topic configuration

| Setting                                     | Recommendation                                       | Reason                                                                                       |
| ------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `replication.factor`, `min.insync.replicas` | Same as the main topic                               | A weaker DLQ is a weak link in the loss-free chain                                           |
| `retention.ms`                              | **Longer than the source** (days to weeks)           | Humans are slower than machines; the source's 24 h would delete evidence before anyone looks |
| `max.message.bytes`                         | ≥ source + header headroom                           | Dead letter = original + headers                                                             |
| `cleanup.policy`                            | `delete`                                             | Compaction would drop dead letters sharing a key                                             |
| `compression.type`                          | `producer` or `zstd`                                 | Dead letters can be bursty and repetitive                                                    |
| Auto-creation                               | Disabled                                             | Explicit creation with the right settings                                                    |
| ACLs                                        | Restrict read to the owning team and the replay tool | Payloads may contain PII                                                                     |

Retention interacts with the **replay window**: a dead letter older than the DLQ's retention is gone; the source record is long gone too. Pick retention from "how long until a human surely looks?" (weekend plus holiday plus incident backlog), then add a margin. Export long-term needs to cold storage (object store) rather than extend Kafka retention indefinitely.

## 12. Security, privacy and retention

A DLQ **concentrates the worst data**: malformed messages (often from broken or malicious producers), full payloads, and error strings that may echo row contents.

1. **Treat it as sensitive as the source.** Same encryption, ACLs, and access logging.
2. **Redact error messages.** Postgres errors can include "Detail: Failing row contains (...)". Strip or hash values; keep the code and the constraint name.
3. **Apply data-retention law.** If the source data has a deletion obligation (GDPR erasure), the DLQ copy must be reachable by the same process; plan how to find and delete a tenant's dead letters (the tenant key helps).
4. **Beware malicious payloads.** A poison message can be crafted (huge, deeply nested JSON). Tools that open the DLQ must parse defensively (size limits, depth limits) and never `eval` or render untrusted HTML.
5. **Do not log whole payloads** to unprotected logs; log identifiers (topic/partition/offset).

## 13. Diagnosing from the DLQ

A triage workflow for an operator:

```
1. How many, how fast?            rate and count by dlq.error_class
2. Group by cause                 error_code + stack_hash (or error_message prefix)
3. Group by origin                producer / tenant / client id (from headers or the key)
4. Pick one exemplar per group    read bytes: is the payload actually invalid?
5. Decide per group:
     producer bug          -> fix producer, discard dead letters or repair + replay
     our parser/code bug   -> fix, deploy, replay (they were valid all along)
     schema/data drift     -> adapt schema, then replay
     genuinely bad data    -> discard with reason, audit
6. Record the decision      ticket, count, who, when
```

Questions each header answers:

| Question                               | Header(s)                                                  |
| -------------------------------------- | ---------------------------------------------------------- |
| Is this a flood or a trickle?          | `failed_at`, counts per minute                             |
| Same bug or many?                      | `error_class`, `error_code`, `error_message`, `stack_hash` |
| Which service/version failed?          | `consumer_group`, `consumer_version`                       |
| Was this valid before our last deploy? | `failed_at` vs deploy time                                 |
| Can I find the original?               | `original_topic/partition/offset` (if still retained)      |
| Is it stale?                           | `original_timestamp`                                       |
| Did I already replay it?               | `replay_count`, `replayed_from`                            |

The helper `scripts/dlq-peek.sh` reads the DLQ for exactly this step; a richer tool is part of [note 5](5.%20dlq-replay-tooling.md).

## 14. Ownership and process: the DLQ is a queue with a human at the end

A DLQ without a process is the "graveyard" from the exercise statement: _a DLQ you cannot safely replay is a graveyard_, and so is one nobody triages.

| Element            | Decision                                                                                                                          |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **Owner**          | A named team on call for `events.dlq`                                                                                             |
| **SLO**            | For example "oldest unresolved dead letter < 24 h, DLQ rate < 0.1% of consumed"                                                   |
| **Triage cadence** | Daily review, or alert-driven                                                                                                     |
| **Outcomes**       | Replay, repair-then-replay, discard (with reason), escalate to producer team                                                      |
| **Audit**          | Each batch action recorded: who, when, how many, why                                                                              |
| **Exit criteria**  | A dead letter is "done" only when replayed successfully or explicitly discarded                                                   |
| **Feedback**       | Every recurring cause gets a fix upstream (validation at the API, schema contract, classifier table update) so the DLQ rate falls |

A healthy DLQ trends to **zero**, not to "stable". A DLQ at constant 10,000 messages is a landfill.

## 15. Alerting

| Alert                               | Type   | Meaning                                                                                                  |
| ----------------------------------- | ------ | -------------------------------------------------------------------------------------------------------- |
| Dead letters per minute > threshold | Rate   | New failure mode or a flood                                                                              |
| Dead letters / consumed > x %       | Ratio  | Systemic problem likely misclassified                                                                    |
| DLQ **age of oldest** > SLO         | State  | Nobody is triaging                                                                                       |
| DLQ depth growing for N hours       | Trend  | Backlog accumulating                                                                                     |
| `error_class=UNKNOWN` count > 0     | Signal | The classifier table needs a new row                                                                     |
| DLQ publish failures                | Error  | The quarantine path itself is broken: **page**, because the consumer will now stall to avoid losing data |
| DLQ approaching retention           | State  | Evidence about to be deleted                                                                             |

Alert on **age and ratio**, not only count; a single poison dead letter at a small company is more urgent than a thousand known ones being worked off.

## 16. Anti-patterns

| Anti-pattern                             | Why it hurts                                                        |
| ---------------------------------------- | ------------------------------------------------------------------- |
| **Dead-letter on first failure**         | Quarantines transient failures; floods the DLQ during outages       |
| **Dead-letter without original bytes**   | No replay, no evidence                                              |
| **DLQ without metadata**                 | Unanalysable; "10,000 unknown messages"                             |
| **DLQ with short retention**             | Evidence expires before a human sees it                             |
| **Nobody owns it**                       | Landfill                                                            |
| **Replay without a fix**                 | Dead letters bounce back into the DLQ (loop)                        |
| **Auto-replay forever**                  | Poison loop with extra steps ([note 5](5.%20dlq-replay-tooling.md)) |
| **Same DLQ for unrelated topics**        | Mixed schemas; no clear replay target                               |
| **Weaker durability than the main path** | The only copy of the failure sits on the weakest storage            |
| **Swallow the DLQ publish error**        | Silent loss: the cardinal sin                                       |
| **Alert on count only**                  | Misses old, small, important items                                  |
| **Free-text-only errors**                | Cannot group by cause                                               |
| **Using the DLQ to hide a systemic bug** | Dead-lettering everything, then "fix by replay"                     |

## 17. Gaps in the current implementation and design improvements

Reading the code against this note gives a short improvement list for Stage 3 (S3-F5). These are **[design]** proposals derived from the observed code; none is implemented here.

1. **Duplicate dead letters** are possible after a crash between DLQ ack and commit (documented). Add `dlq.dedup_key` and dedup at read/replay.
2. **Missing "which code failed":** no consumer version or classifier version header, so you cannot tell whether a fix has shipped.
3. **Missing original record timestamp:** replay cannot judge staleness.
4. **No first-failure time or per-stage info** once retry topics exist.
5. **No replay audit headers** (`replay_count`, `replayed_from`) to detect loops.
6. **Error message may contain row values:** add redaction before truncation.
7. **Lag/age signal:** expose oldest-dead-letter age and DLQ rate as metrics alongside the existing sink stats.
8. **Flood breaker:** if the DLQ rate spikes, stop dead-lettering and pause (note 1, section 10).
9. **Topic settings:** confirm retention, replication and `max.message.bytes` of `events.dlq` meet section 11 (check in `infra/` topic creation).

## 18. Testing the DLQ

1. **Pure builder test:** `toDlqMessage` copies key and bytes unchanged, merges headers, never overwrites original headers, truncates long errors. (Present in `dlq-publisher.spec.ts`.)
2. **Round-trip:** publish a poison record; read it back; assert byte equality with the original and correct provenance.
3. **Binary payload:** a record with invalid UTF-8 survives untouched.
4. **Failure of the DLQ publish:** the source offset is not committed; the chunk is retried; once Kafka returns, exactly one (or, after a crash, more than one) dead letter exists and none is lost.
5. **Crash between ack and commit:** assert duplicate dead letters share the same `(topic, partition, offset)`.
6. **Classification:** transient and systemic errors produce zero dead letters (note 1, section 14).
7. **Flood protection:** systemic failure produces no flood.
8. **Retention config invariant:** DLQ retention ≥ source retention.
9. **PII redaction:** error messages with row contents are redacted.
10. **End to end:** (existing `poison.e2e-spec.ts` in the service's `test/` folder) a poison record at partition 5 goes to the DLQ and the partition drains.

## 19. EventPulse decisions

| Decision               | Choice                                                    | Why                                             |
| ---------------------- | --------------------------------------------------------- | ----------------------------------------------- |
| DLQ topic              | `events.dlq`, one per source topic                        | Same owner and schema as the source             |
| Payload                | Original key and raw bytes                                | Evidence and replay fidelity                    |
| Metadata               | `dlq.*` headers + original headers                        | Replay by plain republish                       |
| Producer               | Dedicated, idempotent, `acks=all`, no auto topic creation | Dead letter is the only copy                    |
| Order of operations    | DLQ ack, then offset commit                               | Duplicates over loss                            |
| Duplicates             | Accepted; to be deduplicated by identity (design)         | Keep the failure path simple                    |
| What qualifies         | Message-scoped failures only                              | Outages and systemic errors never reach the DLQ |
| Kill switch            | `SINK_DLQ_ENABLED=false`                                  | Allows the "before" behavior in experiments     |
| Retention (to confirm) | Longer than source                                        | Humans are slow                                 |
| Ownership              | Required before Stage 3 is "done"                         | A DLQ without a process is a graveyard          |

## 20. Common confusions

1. **"The DLQ is a log of errors."** It stores the _messages_; logs store the errors.
2. **"Dead-lettering is handling the error."** It is _deferring_ it. Handling means replay or a decision.
3. **"Wrap the payload to add metadata."** Wrapping breaks byte-fidelity and complicates replay; use headers.
4. **"One DLQ for everything is simpler."** It mixes owners, schemas and retention.
5. **"Exactly one dead letter per failure."** Duplicates are possible by design; dedup by identity.
6. **"Same retention as the source is fine."** Humans need longer.
7. **"The DLQ can absorb a database outage."** It cannot; it would copy your traffic.
8. **"DLQ publish failure is just a warning."** It is a stop condition; swallowing it loses data.
9. **"A growing DLQ is expected."** It is a signal and must trend to zero.

## 22. Glossary and cheat sheet

| Term           | Meaning                                                  |
| -------------- | -------------------------------------------------------- |
| Dead letter    | A message set aside because it cannot be processed as is |
| DLQ            | The durable place dead letters are stored                |
| Quarantine     | Isolation that preserves evidence and allows release     |
| Provenance     | Where the record came from (topic, partition, offset)    |
| Poison message | A record that fails every time                           |
| Triage         | Grouping and prioritising dead letters                   |
| Replay         | Re-injecting dead letters after a fix (note 5)           |
| Graveyard      | A DLQ nobody reads or can safely replay                  |

dead letter = original key + original bytes + original headers
            + dlq.original_topic/partition/offset + dlq.consumer_group
            + dlq.error_class/code/message + dlq.attempts + dlq.failed_at

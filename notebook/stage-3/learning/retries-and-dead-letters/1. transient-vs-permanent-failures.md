## 1. TL;DR

- A failure is **transient** if repeating the _same operation on the same input_ can succeed later without anyone changing anything. It is **permanent** if no amount of waiting will help; someone must change the input, the code or the environment.
- The two mistakes have opposite costs:
  - **Retrying a permanent failure** burns CPU, fills logs and, in an ordered log like Kafka, **blocks the partition forever** (a poison message).
  - **Giving up on a transient failure** turns a 20-second database restart into **lost or dead-lettered data** that a human must now repair.
- Two classes are not enough. You need at least four: **transient**, **permanent (this message)**, **systemic (everything would fail)**, and **unknown**. The systemic class prevents a broken deployment from emptying the whole topic into the DLQ.
- Classification is about **scope** as much as time: "does the problem belong to this message, to a dependency, or to our own code?" Only message-scoped failures may ever be dead-lettered.
- The default for the unknown must be **bounded retry, then quarantine**, never "retry forever" and never "drop".
- A timeout is the most dangerous error because its **outcome is unknown**: the work may have happened. Retrying it is only safe if the operation is idempotent (see [delivery-semantics note 4](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md)).

> **One-line version:** _Ask "will waiting fix it?" for transient, "is it only this message?" for permanent, and when you cannot tell, retry a bounded number of times and then park it with evidence._

## 2. The mental model: a locked door and a wrong address

A courier delivering a parcel meets two very different problems.

| Problem                             | What it is                                              | Right response                                                 |
| ----------------------------------- | ------------------------------------------------------- | -------------------------------------------------------------- |
| The door is locked, nobody answers  | **Transient.** The recipient may be back in ten minutes | Come back later, with a pause, a few times                     |
| The address does not exist          | **Permanent.** Coming back tomorrow changes nothing     | Stop. Return it to the depot with a note saying why            |
| The whole street is flooded         | **Systemic.** Every parcel on this street will fail     | Stop the whole round. Do not mark every parcel "bad address"   |
| The label is smudged and unreadable | **Unknown.** Might be either                            | Try a couple more times, then send it to the depot for a human |

The courier who keeps ringing the bell at a non-existent address forever never delivers any other parcel on the van. The courier who returns every parcel at the first locked door ruins everyone's day. Good retry design is the courier's judgment, written down as code.

## 3. Two ways to be wrong

Every retry decision can fail in exactly two ways.

### 3.1 Retrying a permanent failure ("the infinite loop")

```
poll batch -> record #2893 is not valid JSON -> handler throws
          -> client seeks back to #2893 -> redeliver -> throws -> ...
```

Real numbers from this repo ([S2-F4 part 1](../../../stage-2/s2-f4-poison-before-fix.md), observed): one invalid-JSON record froze one partition at offset 2893; its lag grew linearly with the arrival rate (760 after 20 s, 1,416 after 45 s) and **never recovered on its own**, the handler was re-run about 28 times per second, and `consumed` reached 787,810 for 11,874 real events. Only one of six partitions stopped, but every event keyed to it became invisible.

Costs: wasted CPU, log volume, growing lag, delayed (or after retention, **deleted-unread**) data for innocent neighbours.

### 3.2 Giving up on a transient failure ("the premature quit")

```
DB restarts for 20 s -> 3 retries in 600 ms all fail
                     -> 400 records dead-lettered although all were perfectly valid
```

Costs: valid data quarantined, a human must replay it, and during the replay window the user-visible data is incomplete. If the dead-lettering itself is wrongly treated as "handled", it can even become silent loss.

### 3.3 The trade, stated honestly

You cannot fully eliminate both errors, because the failure itself does not always say which kind it is. What you can do:

1. Classify **known** errors from an explicit table (cheap, deterministic).
2. For **unknown** errors, bound the damage in **count** and **time**, then quarantine **with evidence** (note 4).
3. Make quarantine **reversible** (replay, note 5). Reversible giving-up makes the "premature quit" mistake cheap; that is the real purpose of a replay tool.

## 4. Taxonomy: four classes, not two

Textbooks say "transient vs permanent". Production code needs a third and fourth class.

| Class                          | Meaning                                             | Example                                                               | Retry?                                                                    | Dead-letter?                                     |
| ------------------------------ | --------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------ |
| **Transient**                  | Dependency is temporarily unavailable or overloaded | Connection refused, pool timeout, deadlock, `57P03` "starting up"     | **Yes**, with backoff, for a bounded time                                 | **No** (see section 10)                          |
| **Permanent (message-scoped)** | This message cannot ever succeed as written         | Invalid JSON, string in an integer column, constraint violation       | **No** (or a very small bounded number, to rule out a fluke)              | **Yes**, immediately or after bounded attempts   |
| **Systemic**                   | The failure would hit _every_ message the same way  | Missing column, wrong credentials, schema mismatch after a bad deploy | Pause and alert a human; **retrying is pointless until someone fixes it** | **Never**: it would empty the topic into the DLQ |
| **Unknown**                    | The error is not in the table                       | A new library error code                                              | Bounded retries                                                           | Yes, after the bound, flagged `UNKNOWN`          |

EventPulse already encodes exactly this in [`errors.ts`](../../../../services/consumer-sink/src/sink/errors.ts) **[observed]**:

```ts
export type ErrorClass =
  | "PERMANENT_PARSE"
  | "PERMANENT_DB"
  | "TRANSIENT_DB"
  | "SYSTEMIC_DB"
  | "UNKNOWN";
```

The comment in that file states the central rule: _"a database that is DOWN (or broken for every row) must never send records to the DLQ. Only a record that fails ON ITS OWN goes there."_ The `SYSTEMIC_DB` class is described there as an addition to the plan's two-class table, because without it a schema mistake would drain the whole topic into the DLQ one row at a time.

### 4.1 Transient is a spectrum, not a point

"Transient" hides different durations. They deserve different retry budgets.

| Duration     | Typical cause                                                            | Retry shape                                                                               |
| ------------ | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------- |
| Milliseconds | Leader election, TCP reset, a lock wait, serialization failure (`40001`) | Immediate or near-immediate retry with tiny backoff                                       |
| Seconds      | Failover, connection pool exhaustion, brief overload                     | Exponential backoff, tens of seconds total                                                |
| Minutes      | Rolling restart, database failover, dependency deploy                    | Backoff then **pause the partition** and keep polling the heartbeat                       |
| Hours        | Regional outage                                                          | Not transient for retry purposes: park the work durably (retry topic or outbox) and alert |

A common design bug is one retry budget for all of these. A consumer that retries 3 times in 600 ms handles the first row only; a consumer that blocks a partition for hours without surfacing a signal handles the last one badly. Note 2 sets the budgets; note 3 gives the "park it" mechanism for the long end.

### 4.2 "Eventually valid" is a fifth wrinkle

Some failures look permanent at one instant and succeed later because the _world_ changed, not the message:

- A foreign-key reference to a tenant that has not been created yet (the creation event is still on another partition).
- A message using a schema version the registry does not know yet (the producer deployed before the registration finished).
- A message arriving before the entity it updates (ordering across topics is not guaranteed).

These are **permanent-looking, time-dependent** failures. The right treatment is **delayed retry** (note 3): park the message for a while, retry, and only dead-letter it after the horizon has passed. This is a major reason retry topics exist.

## 5. The questions a classifier really asks

A good classifier is a short decision procedure, not a list of strings.

```
1. Is the OUTCOME known?
      timeout / connection dropped mid-request -> unknown outcome -> only retry if idempotent
2. Does the error name the INPUT as the problem?
      parse error, validation, type/range/constraint on THIS row -> permanent (message-scoped)
3. Would the SAME error hit ANY message?
      auth, missing table/column, bad config, schema drift -> systemic
4. Does the error name the DEPENDENCY's state?
      refused, reset, overloaded, starting up, shutting down, deadlock -> transient
5. None of the above?
      unknown -> bounded retry, then quarantine
```

Order matters. Question 1 must come first: a connection reset in the middle of an INSERT is both "a transient network error" and "outcome unknown". The retry is safe in EventPulse only because the sink's insert is `ON CONFLICT (event_id) DO NOTHING` ([delivery-semantics note 1](../delivery-semantics/1.%20delivery-semantics-at-most-at-least-exactly-once.md)).

### 5.1 The retry-safety precondition

Classification says "this _can_ succeed". Retry-safety says "repeating this _will not do harm_". Both are needed.

| Operation                                          | Retry safe?                         | Why                                       |
| -------------------------------------------------- | ----------------------------------- | ----------------------------------------- |
| `INSERT ... ON CONFLICT DO NOTHING`                | Yes                                 | Same effect each time                     |
| `UPDATE balance = balance + 10`                    | **No**                              | Each retry adds again                     |
| `PUT /resource/42`                                 | Yes                                 | Replaces state                            |
| `POST /payments` without an idempotency key        | **No**                              | Each retry may charge again               |
| Publishing to Kafka with `enable.idempotence=true` | Yes (within a session)              | Broker dedups by producer id and sequence |
| Sending an email                                   | **No** unless a dedup key is stored | The recipient sees every copy             |

If the operation is not retry-safe, a "transient" classification must be paired with an idempotency key or a pre-check, otherwise the retry loop _creates_ duplicates.

## 6. Scope: who owns the failure

The single most useful lens is **scope**: what set of messages would experience the same failure?

| Scope                  | Question                                          | Evidence                                                        | Fix owner             | Reaction                           |
| ---------------------- | ------------------------------------------------- | --------------------------------------------------------------- | --------------------- | ---------------------------------- |
| **One message**        | Does this message alone fail?                     | Neighbours succeed; failing again on retry; error names a field | Producer / data owner | Isolate and dead-letter            |
| **One key or tenant**  | Do all messages for one key fail?                 | Failures cluster on a tenant                                    | Data owner            | Possibly quarantine the key; alert |
| **One partition**      | Do all messages on one partition fail?            | Often a poison message at the head                              | Us / producer         | Isolate head record                |
| **One dependency**     | Do all messages that touch X fail?                | Same dependency error, many keys                                | Platform / DBA        | Pause and back off; **no DLQ**     |
| **Our code or config** | Does every message fail with the same code error? | Starts exactly at a deploy                                      | Us                    | Stop, roll back, alert             |

The first row is the only one where dead-lettering is correct. The classic way to find out which row you are in is **bisection or isolation**: take the chunk that failed, split it, write the halves separately; messages that succeed alone prove the failure was not systemic, and the ones that keep failing alone are message-scoped. EventPulse's handler does exactly this ("isolate by bisection; good rows are written, each bad row is retried `SINK_MAX_RETRIES` times, then becomes a dead letter", header comment of [`batch-handler.ts`](../../../../services/consumer-sink/src/consumer/batch-handler.ts)).

**Rule:** do not dead-letter on the _first_ failure of a batch. Dead-letter only after you have shown that the failure is attributable to a specific record.

## 7. Classifying real errors

### 7.1 Postgres (what EventPulse's sink sees)

SQLSTATE codes are five characters; the first two are the _class_. This is the table that `classifyDbError` encodes **[observed]**:

| SQLSTATE / code                                                                                                          | Meaning                                                          | Class in EventPulse     | Reasoning                                                           |
| ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------- |
| `08xxx` connection exception                                                                                             | Cannot connect or connection lost                                | Transient               | The server may come back                                            |
| `53xxx` insufficient resources                                                                                           | Out of memory, disk, too many connections                        | Transient               | Pressure passes                                                     |
| `57P01`, `57P02`, `57P03`                                                                                                | Admin shutdown, crash shutdown, cannot connect now (starting up) | Transient               | Restart finishes                                                    |
| `57014`                                                                                                                  | Query cancelled (statement timeout)                              | Transient               | Load may drop; also can mean the query is pathological, so count it |
| `40001`                                                                                                                  | Serialization failure                                            | Transient               | The textbook "just retry" error                                     |
| `40P01`                                                                                                                  | Deadlock detected                                                | Transient               | Retry usually wins                                                  |
| `22xxx` data exception                                                                                                   | Value out of range, invalid text representation                  | **Permanent (message)** | This value will never fit                                           |
| `23xxx` integrity violation                                                                                              | NOT NULL, FK, check violation                                    | **Permanent (message)** | Unless the FK parent arrives later (section 4.2)                    |
| `42xxx` syntax error or access rule                                                                                      | Missing column or table, bad SQL                                 | **Systemic**            | Every row fails; a human must fix code or schema                    |
| `28xxx` invalid authorization                                                                                            | Wrong password, role removed                                     | **Systemic**            | Every row fails                                                     |
| `3D000` invalid catalog name                                                                                             | Wrong database                                                   | **Systemic**            | Config error                                                        |
| `0A`, `XX`                                                                                                               | Feature not supported, internal error                            | **Systemic**            | Not caused by this message                                          |
| Node `ECONNREFUSED`, `ECONNRESET`, `ETIMEDOUT`, `EPIPE`, `ENOTFOUND`, `EAI_AGAIN`, `EHOSTUNREACH`, `ENETUNREACH`         | Network failure                                                  | Transient               | Network heals                                                       |
| message matches "timeout exceeded when trying to connect", "Connection terminated", "the database system is starting up" | Client-library errors with no code                               | Transient               | Matched by text because no code exists                              |
| anything else                                                                                                            |                                                                  | Unknown                 | Bounded retry, then DLQ                                             |

Note the subtle `23xxx` caveat: the primary-key conflict never surfaces as an error in EventPulse because the insert uses `ON CONFLICT DO NOTHING`; a duplicate is a normal event, counted as a duplicate (S3-F3), not a failure.

### 7.2 Kafka client errors

Kafka protocol errors carry a **retriable** flag, and clients retry those themselves (see [producer note 5](../../../stage-2/learning/producer/5.%20kafka-producer-retries-and-timeouts.md)).

| Error                                                                                         | Retriable?                       | Note                                                                                                                          |
| --------------------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `NOT_LEADER_OR_FOLLOWER`, `LEADER_NOT_AVAILABLE`, `UNKNOWN_TOPIC_OR_PARTITION` (just created) | Yes                              | Metadata is stale; refresh and retry                                                                                          |
| `NOT_ENOUGH_REPLICAS`, `NOT_ENOUGH_REPLICAS_AFTER_APPEND`                                     | Yes                              | ISR below `min.insync.replicas`; the second one means the record _was_ appended, so a retry can duplicate without idempotence |
| `REQUEST_TIMED_OUT`, `NETWORK_EXCEPTION`                                                      | Yes                              | Outcome unknown                                                                                                               |
| `MESSAGE_TOO_LARGE`                                                                           | **No**                           | Retrying never shrinks the record                                                                                             |
| `INVALID_TOPIC_EXCEPTION`, `TOPIC_AUTHORIZATION_FAILED`                                       | **No**                           | Config / permission                                                                                                           |
| `OUT_OF_ORDER_SEQUENCE_NUMBER`, `PRODUCER_FENCED`                                             | **No** (fatal for that producer) | The producer must be recreated                                                                                                |

### 7.3 HTTP / downstream services (relevant when a consumer calls an API)

| Status                                                               | Class                          | Notes                                                                |
| -------------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------- |
| 408, 429, 500, 502, 503, 504                                         | Transient                      | Respect `Retry-After` if present (note 2)                            |
| 400, 404 (for a resource that should exist), 409, 410, 413, 415, 422 | Permanent (message)            | The request itself is wrong                                          |
| 401, 403                                                             | **Systemic** (credentials)     | Token expired is the one transient exception: refresh and retry once |
| 501                                                                  | Permanent                      | Not implemented                                                      |
| Connection reset / timeout                                           | Transient, **outcome unknown** | Retry only with an idempotency key                                   |

A frequent mistake is classifying every 5xx as transient. A 500 caused by a deterministic bug on one specific payload will not heal; it needs the same "bounded count" cap as any unknown.

### 7.4 Serialization and validation

| Error                                  | Class                                                                 |
| -------------------------------------- | --------------------------------------------------------------------- |
| Not valid JSON / invalid UTF-8         | Permanent (message)                                                   |
| Required field missing, wrong type     | Permanent (message)                                                   |
| Unknown schema id                      | Eventually valid: delayed retry, then permanent                       |
| Schema registry unreachable            | Transient                                                             |
| Our parser throws on a new valid shape | **Systemic** (code bug): the DLQ is the wrong place; fix and redeploy |

The last row is the trap: a **bug in our own deserializer** looks exactly like a permanent bad message but affects _every_ message of that shape. The mitigation is the **flood circuit breaker** in section 10.

## 8. The hard cases

### 8.1 Timeouts

A timeout says _we stopped waiting_, not _it did not happen_. Possible truths: request never arrived, request is queued, request executed and the reply was lost. The classifier calls it transient (retrying can succeed) but the **retry-safety rule** decides whether retrying is allowed. In EventPulse this is why the idempotent insert matters more than the classifier.

### 8.2 The same error code with different meanings

`57014` (statement timeout) may be transient load or may be a single row that triggers a pathological query. The mitigation is a **count**: transient failures are retried for a time window; if the _same_ record keeps hitting the same transient-looking error _after the dependency has proven healthy_ (other records succeed), treat that record as permanent. The sink's bisection supplies exactly this proof: after isolation, a row that fails alone while its siblings succeed is not suffering from "the database is down".

### 8.3 Errors that change class after N attempts

| Situation                                   | Initial class     | Becomes                                    |
| ------------------------------------------- | ----------------- | ------------------------------------------ |
| Row fails on FK, parent not yet created     | Permanent-looking | After the delayed-retry horizon, permanent |
| Unknown error repeats 3 times in isolation  | Unknown           | Permanent (dead-letter)                    |
| Transient error exceeds its time window     | Transient         | Blocking (pause the partition and alert)   |
| Transient error on one row only, db healthy | Transient         | Permanent for that row                     |

Classification is therefore not a pure function of the error; it is a function of **(error, attempt count, elapsed time, evidence about other messages)**. Keep the pure part (error to class) separate from the stateful part (budgets) so each can be unit-tested.

### 8.4 Partial success

A batch of 1,000 rows where one fails: classifying the _batch_ wastes the 999. Classification must be **per record**, which requires isolation. A batch-level classifier is acceptable only as a first step to decide "is this systemic?".

### 8.5 Failures in the failure path

The DLQ publish itself can fail. That is a **transient failure of a dependency (Kafka)**, so the right behavior is to **not advance the offset** and retry the chunk. EventPulse does this: `DlqPublishError` leaves the source offset uncommitted (note in `dlq-publisher.ts`: "if the publish fails, the source offset is not committed and the chunk is retried (so a DLQ record can be duplicated)"). Quarantine must never be a lossy step.

## 9. Poison messages

A **poison message** is a record that makes the consumer fail every time it is processed. In a log with ordered, offset-based consumption it has a special property: **you cannot skip it without an explicit decision**, because progress is a single number per partition.

```
offsets:  ... 2890 2891 2892 [2893 poison] 2894 2895 ...
committed offset = 2893  -> consumer will keep asking for 2893
```

Properties:

1. **Head-of-line blocking:** everything after the poison on that partition waits.
2. **Blast radius = the partition:** with key-hash partitioning, all tenants that hash there are affected.
3. **Silent from outside:** the producer got `202`; the data never reaches storage; nothing crashes.
4. **Bounded by retention:** if the consumer stays blocked longer than the topic's retention, later records are deleted unread (K11).
5. **Cannot be fixed by retrying.** Only skipping, repairing or dead-lettering ends it.

Four ways to end a poison block:

| Strategy                                                | What happens to the record | Trade-off                                                   |
| ------------------------------------------------------- | -------------------------- | ----------------------------------------------------------- |
| **Skip** (commit past it)                               | Lost                       | Simple, silent loss: acceptable only for expendable data    |
| **Dead-letter** (copy to a quarantine topic, then skip) | Preserved with metadata    | Needs a DLQ and an owner who looks at it (notes 4 and 5)    |
| **Stop the consumer**                                   | Blocks                     | Safe for strict ordering, harmful for availability          |
| **Fix forward** (patch the deserializer)                | Becomes valid              | Only right if the _code_ was wrong (systemic), not the data |

EventPulse chose dead-lettering with bounded in-place retry; the "what the fix must do" list in the [poison observation](../../../stage-2/s2-f4-poison-before-fix.md) is the specification this series teaches.

## 10. Systemic failure: why a bad classifier floods the DLQ

Suppose a deploy renames a column but the sink still inserts into the old name. Every insert fails with `42703` (undefined column). If the classifier treated "any 4xxxx error" as permanent:

```
1,000,000 valid events/hour  ->  1,000,000 dead letters/hour
```

The DLQ becomes a copy of the whole topic. Worse, the offsets advance, so the source topic's retention starts the clock on data you no longer have an easy path to replay. Without the flood protection, the DLQ is not a safety net but a **data shredder with a paper trail**.

Defenses (apply several):

1. **Explicit systemic class** that never dead-letters (EventPulse's `SYSTEMIC_DB`, `isBlocking`).
2. **Bisection evidence:** do not dead-letter a record unless its siblings succeeded around it. If _nothing_ in the chunk can be written, the problem is not the records.
3. **Flood circuit breaker:** if more than X% of records or more than N records per minute go to the DLQ, stop dead-lettering, pause consumption and page a human. The rate of dead letters is a first-class alert.
4. **Deploy-time smoke test** that pushes one known-good record through the real path before taking traffic.
5. **DLQ budget:** a cap on the DLQ's growth rate acts as a tripwire.

The rule from the code comments is worth memorising: **a database that is down must never send records to the DLQ.**

## 11. Classifier design rules

1. **Classify by cause, not by symptom.** `ECONNRESET` is about the network; the message is innocent.
2. **Allow-list the permanent class narrowly.** Permanent is the class that _discards work_; require positive evidence (a data exception code, a parse failure), not merely "an error we do not recognise".
3. **Default unknown to bounded retry then quarantine** (not infinite retry, not drop). Mark it `UNKNOWN` so humans can read the DLQ and extend the table.
4. **Keep the classifier pure and table-driven.** `classify(error) -> class` with no clock or state; budgets live elsewhere.
5. **Separate message-scoped and dependency-scoped failures** in the data model so metrics and alerts differ.
6. **Record the class and error code on the dead letter** so you can regroup the DLQ by cause later (note 4).
7. **Never classify on free-text alone when a code exists.** Fall back to message regexes only for library errors without codes, as `errors.ts` does for `pg` connection messages.
8. **Treat classification as versioned logic.** When you fix the table, old dead letters remain valid and can be re-classified when replayed (note 5).
9. **Fail closed on money-like effects.** If a retry could double-charge and you cannot prove idempotence, a doubtful failure goes to quarantine, not to a retry loop.
10. **Every class maps to a metric.** If a class has no counter you will not notice it misbehaving.

## 12. What each class triggers

```
                 +-----------------------+
 error --------> |  classify(error)      |
                 +----------+------------+
                            |
     +-----------+----------+----------+-----------+
     |           |                     |           |
 TRANSIENT   PERMANENT              SYSTEMIC     UNKNOWN
     |           |                     |           |
 backoff +   isolate row,          pause partition, bounded retries
 retry in    maybe 1-3 retries,    alert human,     (counted), then
 window;     then dead-letter      DO NOT DLQ       dead-letter
 window out:                                        flagged UNKNOWN
 pause + park
```

| Class                       | In-process retry    | Partition                                    | Offset                 | DLQ                  | Alert                                          |
| --------------------------- | ------------------- | -------------------------------------------- | ---------------------- | -------------------- | ---------------------------------------------- |
| Transient (short)           | Yes, bounded window | Keeps running                                | Held until success     | No                   | Only if prolonged                              |
| Transient (window exceeded) | Stop                | **Paused** (poll continues, heartbeat alive) | Held                   | No                   | Yes (dependency)                               |
| Permanent                   | 0 to N (small)      | Keeps running                                | Advances after DLQ ack | **Yes**              | Rate-based                                     |
| Systemic                    | No                  | Paused                                       | Held                   | **No**               | **Immediate**                                  |
| Unknown                     | Bounded             | Keeps running                                | Advances after DLQ ack | Yes, class `UNKNOWN` | Rate-based, plus "teach the classifier" ticket |

## 13. EventPulse walkthrough

Four records in one chunk of the sink ([`batch-handler.ts`](../../../../services/consumer-sink/src/consumer/batch-handler.ts)): A (valid), B (invalid JSON), C (valid), D (string in a numeric column).

```
parse stage:   B fails to parse  -> PERMANENT_PARSE -> dead letter immediately (no retry: parsing is deterministic)
write stage:   INSERT A, C, D    -> error 22P02 (invalid text representation)
               class = PERMANENT_DB -> isolate by bisection
                 write [A] ok, write [C] ok
                 write [D] fails alone -> retry SINK_MAX_RETRIES (3) times with backoff -> still fails
                 D becomes a dead letter (PERMANENT_DB)
publish DLQ:   B and D to events.dlq, wait for acks
commit:        resolve last offset of the chunk, commit
```

Now the same chunk while Postgres is restarting:

```
write stage:   INSERT A, C       -> ECONNREFUSED -> TRANSIENT_DB
               retry with backoff inside SINK_TRANSIENT_RETRY_WINDOW_MS (20 s)
               still down -> pause the partition (pauseMs) and throw DbUnavailableError
               nothing is resolved; the chunk is read again after the pause
               NO record goes to the DLQ
```

And with a schema mistake (`42703`): `SYSTEMIC_DB`: treated like transient (blocking, retried) but flagged as needing a human; nothing is dead-lettered. This three-way split is the whole lesson of this note in forty lines of code.

## 14. Testing the classifier

The classifier is a table, so test it like one.

1. **Table test:** for each SQLSTATE / Node code / HTTP status in section 7, assert the class. Include `undefined`, `null`, plain strings and errors without a `code`.
2. **Property: no systemic or transient code ever maps to permanent.** Enumerate the code families and assert the invariant, because that mapping is the one that loses data.
3. **Isolation test:** a chunk with one bad row among 999 good ones should produce 999 inserts and 1 dead letter.
4. **Outage test:** make the fake writer throw `ECONNREFUSED` for N seconds; assert zero dead letters and that the chunk eventually succeeds after recovery.
5. **Flood test:** make the fake writer throw `42703` on every row; assert zero dead letters (or that the breaker trips).
6. **Unknown test:** throw an error with an unrecognised code; assert bounded retries, then a dead letter with class `UNKNOWN`.
7. **Failure-path test:** make the DLQ publish throw; assert the offset is not committed.

EventPulse has unit tests for these in `errors.spec.ts`, `batch-handler.spec.ts` and `dlq-publisher.spec.ts` alongside the sources, and an end-to-end `poison.e2e-spec.ts` in the service's `test/` folder.

## 15. Observability

| Signal                                         | Why it matters                                                                                                                      |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Failures per class per minute                  | Shows which class is growing; a spike in `UNKNOWN` means the table is stale                                                         |
| Retry attempts histogram                       | Reveals records that need 1 retry vs 3                                                                                              |
| Dead letters per minute, by class and by topic | The flood detector                                                                                                                  |
| Time a partition spent paused                  | Cost of dependency outages                                                                                                          |
| Oldest unresolved offset age (per partition)   | A poison or paused partition shows as lag growth ([consumer note 4](../../../stage-2/learning/consumer/4.%20kafka-consumer-lag.md)) |
| Ratio `dead-lettered / consumed`               | Quick tripwire for systemic failure                                                                                                 |

Alerts should be **rate-based** (dead letters per minute) and **state-based** (partition paused longer than X), not per-event.

## 16. EventPulse decisions

| Decision            | Choice                                                                            | Why                                                |
| ------------------- | --------------------------------------------------------------------------------- | -------------------------------------------------- |
| Number of classes   | Five: `PERMANENT_PARSE`, `PERMANENT_DB`, `TRANSIENT_DB`, `SYSTEMIC_DB`, `UNKNOWN` | Two classes cannot protect against schema mistakes |
| Parse failures      | Dead-letter at once, no retry                                                     | Parsing is deterministic                           |
| Database down       | Never dead-letter; back off, then pause the partition                             | Down is not the record's fault                     |
| Unknown errors      | Treated like permanent-DB: bounded retries then DLQ                               | Never infinite, never silent drop                  |
| Retry-safety        | Insert is idempotent (`ON CONFLICT DO NOTHING`)                                   | Makes retrying a timed-out write safe              |
| Isolation           | Bisect a failing chunk                                                            | Attribute failure to specific rows                 |
| DLQ publish failure | Keep source offset uncommitted                                                    | Quarantine must not lose data                      |

## 17. Common confusions

1. **"An error is transient or permanent."** Also systemic and unknown. A missing column is "permanent" for the deploy but not the message.
2. **"Retry on every 5xx."** A deterministic bug behind a 500 will not heal; cap attempts and record the count.
3. **"Dead-letter whatever fails after 3 tries."** If the dependency is down all 3 tries fail for every record; you dead-letter the topic.
4. **"Timeouts are transient so retry is free."** Retrying a timed-out non-idempotent operation duplicates.
5. **"A poison message is rare, ignore it."** One bad record freezes a partition; the probability is irrelevant, the consequence is what matters.
6. **"The classifier lives in the DLQ publisher."** It lives _before_ it. The publisher only records the class.
7. **"Permanent means we lose the message."** Permanent means _retrying in place is pointless_. The message is preserved in the DLQ and can be replayed after a fix.
8. **"Unknown errors are probably transient."** They are probably _bugs_. Bound them.
9. **"Transient errors never need alerts."** They do when they last longer than the retry window.

## 19. Glossary and cheat sheet

| Term                  | Meaning                                                            |
| --------------------- | ------------------------------------------------------------------ |
| Transient failure     | Repeating can succeed without any change                           |
| Permanent failure     | Repeating cannot succeed until something changes                   |
| Systemic failure      | Would hit every message identically                                |
| Poison message        | A record that fails every time it is processed                     |
| Head-of-line blocking | One stuck record delays all behind it on that partition            |
| Isolation (bisection) | Splitting a failed batch to find the guilty records                |
| Retry-safe            | Repeating the operation causes no extra effect                     |
| Dead letter           | A message moved aside with diagnostics instead of retried in place |
| Flood                 | A burst of dead letters caused by a systemic problem               |

Rules:

1. Classify per record; attribute failure by isolation.
2. Only message-scoped failures are dead-lettered.
3. Dependency down means pause, not DLQ.
4. Unknown means bounded, then quarantine with evidence.
5. A retry must be safe, or it is a duplicate generator.
6. Quarantine must be lossless and reversible.

```
 will waiting fix it?          -> transient   -> backoff, bounded window
 is it only this message?      -> permanent   -> isolate, DLQ
 would every message fail?     -> systemic    -> pause, alert, no DLQ
 can't tell?                   -> unknown     -> bounded retry, DLQ flagged UNKNOWN
```

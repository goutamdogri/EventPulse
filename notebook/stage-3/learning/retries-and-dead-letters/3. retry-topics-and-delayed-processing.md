# Retry Topics and Delayed Processing

_Retries-and-dead-letters note 3 of 5 in the Stage 3 learning notes. Read [note 1 (transient vs permanent)](1.%20transient-vs-permanent-failures.md) and [note 2 (backoff and bounded attempts)](2.%20backoff-with-jitter-and-bounded-attempts.md) first. Note 2 ended with a problem: a consumer cannot sleep for minutes without being thrown out of its group. This note solves it by moving the waiting **out of the main partition and into Kafka itself**: a failed message is parked on a retry topic with a `not_before` header, the main partition keeps moving, and a retry consumer re-processes the message once its time has come. It supports S3-F5 and prepares the DLQ ([note 4](4.%20dead-letter-queue-design.md))._

**No labs here.** Kafka has no built-in delayed delivery, so everything below is a design built from ordinary primitives: topics, headers, `pause()`/`resume()`, offsets. Details about the Kafka client API (pause, resume, seek, headers) are general and described in [consumer note 5](../../../stage-2/learning/consumer/5.%20kafka-consumer-backpressure.md) and [offset-commit note](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md). EventPulse does **not** have a retry topic today; its current behavior (in-place retries, then pause, then DLQ) is read from [`batch-handler.ts`](../../../../services/consumer-sink/src/consumer/batch-handler.ts), and the retry-topic design here is the _teaching design_ for S3-F5, flagged as design, not as built code.

## 1. TL;DR

- In-place retry (sleep inside the handler) blocks the partition and is limited by the consumer's liveness timers. It suits **short** waits. For longer waits, **park the message**.
- **Retry topic pattern:** on a retriable failure, publish the message (with added headers) to a retry topic and **commit the source offset**. The main partition immediately moves on to the next record.
- A header such as **`not_before`** (an absolute timestamp) tells the retry consumer when the message becomes eligible. The retry consumer **pauses the partition until that time**, then processes it. Kafka does not delay messages for you; you build the delay.
- Use **tiered retry topics** (`retry-5s`, `retry-1m`, `retry-10m`) so that each topic has a single constant delay. Within a topic, messages are already ordered by eligibility time, so the head of the partition is always the next to become due, and waiting for the head never delays a later message.
- Parking **breaks ordering**: later messages for the same key may be processed before the parked one. This is acceptable only if the sink is order-tolerant (idempotent, last-write-wins by timestamp or version).
- The retry path must be **at least as reliable as the main path**: publish to the retry topic and wait for the ack _before_ committing the source offset, otherwise you lose the message in the gap.
- After the last tier fails, the message goes to the **DLQ** (note 4) with the full history.

> **One-line version:** _Don't make the partition wait. Move the message somewhere that can wait cheaply, label it with when to come back, and keep the main line flowing._

## 2. The mental model: the waiting room

A restaurant kitchen gets an order for a dish whose ingredient has just run out. The cook has two options:

| Option                                                                                                   | Meaning         | Effect                                                      |
| -------------------------------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------- |
| Stand at the station until the ingredient arrives                                                        | In-place retry  | Every order behind it waits                                 |
| Hand the ticket to the expediter, who sets it on a rail marked "retry at 7:40", and take the next ticket | **Retry topic** | The line keeps moving; the parked ticket comes back at 7:40 |
| After three trips to the rail, give up and file the ticket in the "problems" box with a note             | **DLQ**         | Humans decide                                               |

The rail is the retry topic; the time on the ticket is `not_before`; the "problems" box is the DLQ.

## 3. Why in-place retry is not enough

Note 2 section 9 established the limits. In summary:

| Limit                          | Why                                                                                                    |
| ------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Head-of-line blocking**      | One partition is a queue; retrying the head blocks all behind it, including records that would succeed |
| **Liveness timers**            | Sleeping inside the handler can exceed the rebalance / poll interval, evicting the consumer            |
| **Resource coupling**          | A held chunk keeps buffers, a DB connection, and an uncommitted offset                                 |
| **No durability of the wait**  | A restart forgets the in-memory attempt count and retry plan                                           |
| **No cross-instance fairness** | Each pod retries independently; no global view                                                         |

In-place retry remains right when the retry window is short (seconds) and the failure is dependency-wide (every record would fail, so "moving on" would only produce more failures). In fact **for a database outage, moving messages to a retry topic is the wrong move** (they would all just fail again and the retry topic fills). The right reaction to a dependency outage is **pause the partition**, which keeps the data where it is and costs nothing.

So two different tools address two different failures:

| Failure                                                                                                                            | Scope        | Right tool                                         |
| ---------------------------------------------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------- |
| Dependency down                                                                                                                    | Every record | **Pause** the partition, back off, resume (note 2) |
| One record fails for a reason that may clear with time (FK parent missing, rate-limited per key, dependency flaky for this record) | One record   | **Retry topic** with `not_before`                  |
| One record will never succeed                                                                                                      | One record   | **DLQ** (note 4)                                   |

The retry topic is for **record-scoped, time-dependent** failures ("eventually valid", note 1 section 4.2), not for outages.

## 4. The retry topic pattern

### 4.1 The flow

```
 main topic: events.raw
      |
  [main consumer] --success--> sink --> commit offset
      |
      +-- retriable record failure (e.g. FK parent missing)
            |
            v  produce to  events.raw.retry-30s  with headers (attempt+1, not_before = now+30s, original coordinates)
            wait for ack
            then commit the main offset          <- main partition has moved on
                                    |
                           [retry consumer]
                             head record's not_before in the future? -> pause partition until then
                             due? -> process again
                                     success -> commit
                                     failure -> attempts < N ? next tier topic : DLQ
```

### 4.2 Why a topic and not a table or a timer

| Option                                                                       | Pros                                                                                         | Cons                                                                                        |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| **Retry topic**                                                              | Durable, replicated, same tooling, survives restarts, scales by partitions, ordered per tier | No native delay; must build the wait                                                        |
| In-memory timer (`setTimeout`)                                               | Trivial                                                                                      | Lost on restart; unbounded memory; breaks at-least-once                                     |
| DB table + poller                                                            | Precise, queryable, supports `not_before` index                                              | New component, polling cost, a new availability dependency (and the DB may be what is down) |
| Broker-native delay (RabbitMQ TTL + DLX, SQS delay, Pulsar delayed delivery) | Built-in                                                                                     | Kafka lacks it                                                                              |

A table is a legitimate alternative when you need arbitrary delays; note 13 covers it. The retry topic is the Kafka-native answer.

### 4.3 What triggers parking

Only failures classified as **retriable at the record level** ([note 1](1.%20transient-vs-permanent-failures.md)):

- FK or reference not yet present
- Per-key rate limiting from a downstream API
- A transient error that persisted for **this record only** after isolation
- An "eventually valid" schema or version mismatch

Not: parse errors (permanent), dependency-wide outages (pause), systemic errors (stop and alert).

## 5. The not_before header

Kafka headers are key/value byte pairs attached to a record, invisible to the key or value. They are the right place for routing metadata because they leave the original payload byte-for-byte intact (replay needs the original bytes, [note 5](5.%20dlq-replay-tooling.md)). EventPulse already uses headers this way for DLQ metadata (`dlq.*`, [`dlq-publisher.ts`](../../../../services/consumer-sink/src/sink/dlq-publisher.ts), **[observed]**).

A proposed retry header set (design):

| Header                                                                        | Example                                  | Purpose                                                            |
| ----------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------ |
| `retry.not_before`                                                            | `2026-11-22T10:15:30.000Z` (or epoch ms) | Earliest time to process                                           |
| `retry.attempt`                                                               | `2`                                      | Attempts used so far (travels with the message: survives restarts) |
| `retry.max_attempts`                                                          | `4`                                      | Policy snapshot                                                    |
| `retry.original_topic`, `retry.original_partition`, `retry.original_offset`   | `events.raw`, `5`, `2893`                | Provenance                                                         |
| `retry.first_failed_at`                                                       | ISO time                                 | Total age of the problem                                           |
| `retry.last_error_class`, `retry.last_error_code`, `retry.last_error_message` | `PERMANENT_DB`/`23503`/...               | Diagnosis                                                          |
| `retry.consumer_group`                                                        | `sink-postgres`                          | Who parked it                                                      |

### 5.1 Absolute vs relative time

Store an **absolute** timestamp (`not_before`), not "wait 30 s". The retry consumer compares it to its own clock; the relative form would require knowing when the record arrived and would restart the wait on every re-read. Absolute times are idempotent under redelivery.

### 5.2 Clock skew

Producer and consumer clocks can differ by seconds. For delays of 30 s or more this is harmless. For sub-second delays, use broker-assigned timestamps (`LogAppendTime`) as the base and add the delay, or accept the skew. Never design correctness (ordering) around cross-machine clock agreement.

### 5.3 Jitter on `not_before`

`not_before = now + tierDelay + jitter` spreads a burst of parked records (a bad deploy parks 10,000 records at once) so they do not all return in the same second. Same herd logic as note 2.

## 6. The retry consumer: delay without a scheduler

Because Kafka consumers cannot ask "give me this record in 30 s", the consumer implements the delay itself.

```
loop:
    batch = poll(retry topic)
    for record in batch (in offset order):
        wait = record.not_before - now
        if wait > 0:
            pause(partition)                      # stop fetching; heartbeat continues
            seek(partition, record.offset)        # remember to re-read this very record
            schedule resume(partition) in wait    # a timer, not a sleep inside the handler
            break                                 # do not look at later records yet
        process(record)
```

Key points:

1. **Pause, do not sleep.** `pause()` keeps the consumer in the group while no data flows. A `sleep` blocks the loop and starves heartbeats and polling (the same trap as note 2).
2. **Seek back to the unprocessed record** so the next fetch starts at it, otherwise buffered later records are skipped or processed early (details in [consumer note 5](../../../stage-2/learning/consumer/5.%20kafka-consumer-backpressure.md)).
3. **Cap the pause** at a fraction of the liveness timeouts (for example resume at least every few seconds and re-check), so a long delay is a series of short pauses, not one long one.
4. **Each partition has its own clock** because pausing is per partition.

### 6.1 Why a single tier with a constant delay works

If every record in a topic has the same delay `D`, then `not_before = t_arrival + D`. Records arrive in offset order, so `not_before` is **non-decreasing within a partition**. When the head is not yet due, **nothing behind it is due either**. Pausing on the head wastes nothing. Mixed delays in one topic break this: a record due in 1 minute sitting in front of a record due in 5 seconds delays the second by 55 s.

This is the entire reason for tiered topics (section 7).

## 7. Single delay topic vs tiered topics

### 7.1 Tiered topics

```
events.raw.retry-5s     delay 5 s       (first failure)
events.raw.retry-1m     delay 1 min     (second)
events.raw.retry-10m    delay 10 min    (third)
events.raw.dlq          after the last tier
```

| Property                                     | Effect                                                   |
| -------------------------------------------- | -------------------------------------------------------- |
| One constant delay per topic                 | The head-of-partition argument of section 6.1 holds      |
| Exponential-ish growth across tiers          | Same logic as note 2: quick first retry, slow later ones |
| N retry consumers (or one subscribed to all) | A little operational surface                             |
| Total topics = tiers + DLQ per source topic  | Naming convention matters                                |

### 7.2 Single retry topic with variable `not_before`

Simpler operationally (one topic, one consumer) but suffers the head-of-line problem unless delays are uniform. Acceptable when there is only **one** retry delay and a small attempt count.

### 7.3 Comparison

|                   | Single retry topic, one delay | Single, variable delay | Tiered topics           |
| ----------------- | ----------------------------- | ---------------------- | ----------------------- |
| Topics            | 1                             | 1                      | 2 to 4                  |
| Head-of-line wait | None                          | **Yes**                | None                    |
| Backoff shape     | Constant                      | Any (but blocked)      | Exponential-like        |
| Complexity        | Lowest                        | Low, but flawed        | Moderate                |
| Recommended       | Single-shot retry             | Avoid                  | Default for 2+ attempts |

### 7.4 Naming and configuration

`<source>.retry.<delay>` (for example `events.raw.retry.30s`). Match partition count to the source topic (so key-to-partition affinity is preserved when you publish with the original key) and set retention to cover the _longest_ tier delay plus processing slack, not the default (section 12).

## 8. What the retry message must carry

1. **The original bytes of the key and value, untouched.** Do not re-serialise; replay must reproduce what the producer sent.
2. **The original key.** Retain it so the partitioner sends the record to the same partition number (if partition counts match) and preserves per-key locality.
3. **Original headers**, plus the retry headers. Keep a clear namespace (`retry.*`) so you do not overwrite producer headers such as trace ids.
4. **Provenance:** original topic, partition, offset. Needed for diagnosis and for deduplicating DLQ copies (note 4).
5. **Attempt counter** and a **first-failure timestamp** (total age).
6. **Error evidence** from the _last_ failure (class, code, truncated message). EventPulse truncates `dlq.error_message` to 1,024 bytes (`truncate` in `errors.ts`, **[observed]**) so one pathological stack trace cannot exceed record size limits.

Trace context (`traceparent` header) should continue through, so one trace spans the original attempt and the retries.

## 9. Ordering: what you give up

Kafka guarantees order **within a partition**. Parking a record on a different topic changes the order in which records for the same key are _processed_:

```
main partition (key K):   e1  e2(fails -> parked)  e3  e4
processed order:          e1       e3  e4  ...  later: e2
```

`e2` now arrives **after** `e3` and `e4`. Consequences:

| If the sink is...                                                     | Effect                                                                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Insert-only, idempotent by event id** (EventPulse's `events` table) | Harmless; row order in the table is irrelevant, reads sort by event time                                     |
| **Last-write-wins by arrival** (updates entity state)                 | **Wrong**: old state overwrites new                                                                          |
| **Version-aware** (compare version/timestamp, keep the newer)         | Correct                                                                                                      |
| **Running aggregate** (balance = balance + x)                         | Order-independent only if the operation is commutative and idempotent                                        |
| **State machine** (created → paid → shipped)                          | Needs strict order: an event arriving before its predecessor must itself be parked ("blocking retry" by key) |

### 9.1 Preserving per-key order (when you must)

If order matters, add **key-level blocking**: once a record for key K is parked, every later record for K must also be parked (not processed) until the first one clears. Implementation sketch: maintain a set of "blocked keys" (a state store or a compacted topic); the main consumer checks it before processing; records for blocked keys go straight to the retry topic. This restores per-key order at the cost of **state** and complexity. It is the Kafka equivalent of a head-of-line block, scoped to one key rather than a whole partition. Most systems avoid it by making the sink order-tolerant. EventPulse does, by design (idempotent insert keyed on `event_id`).

### 9.2 The honest rule

Parking trades **ordering and strictness** for **throughput and availability**. State that trade in the delivery guarantees document (S3-F9): _"A record that fails and is retried may be stored later than records that arrived after it."_

## 10. Offsets and the commit order

The most important correctness rule of the whole pattern:

> **Publish to the retry topic and wait for the acknowledgement _before_ committing the source offset.**

```
(wrong)  commit source offset -> crash -> retry publish never happened     => record LOST
(right)  publish retry (acks=all, ack received) -> commit source offset
         crash between the two -> source offset not committed -> record reprocessed => possible DUPLICATE
```

Same logic as the DLQ publisher: "the batch handler waits for the ack before committing the source offset; if the publish fails, the source offset is not committed and the chunk is retried (so a DLQ record can be duplicated; noted for Stage 3)" (header comment of [`dlq-publisher.ts`](../../../../services/consumer-sink/src/sink/dlq-publisher.ts), **[observed]**). A duplicate on the retry topic is acceptable because the sink is idempotent; a loss is not.

Use a producer with `acks=all` and idempotence for the retry/DLQ producer (EventPulse's DLQ producer is exactly this: `acks: -1, idempotent: true`). See [producer note 3](../../../stage-2/learning/producer/3.%20kafka-producer-idempotence.md).

Then, in the retry consumer, the commit order is the usual one ([offset commit note](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md)): **effect first, then offset**. If it fails again, publish to the next tier (ack), _then_ commit.

### 10.1 Transactions

Kafka transactions can make "produce to retry topic + commit source offset" atomic (`sendOffsetsToTransaction`). They cover Kafka-to-Kafka steps well ([delivery-semantics note 3](../delivery-semantics/3.%20kafka-transactions-and-exactly-once-semantics.md)). They do not cover the Postgres write. Because the sink is already idempotent, plain ack-then-commit is usually enough and simpler.

## 11. Failure modes of the retry path itself

| Failure                                | Result                                                            | Mitigation                                                                     |
| -------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Retry publish fails                    | Source offset uncommitted; record re-read                         | Retry the publish with backoff; this is a Kafka dependency failure (transient) |
| Retry topic missing or auth error      | Systemic                                                          | Stop and alert; never fall through to "drop"                                   |
| Retry consumer is down                 | Parked records accumulate; nothing is lost while within retention | Alert on retry-topic lag and oldest-record age                                 |
| Clock jumps forward                    | Records become due early                                          | Acceptable for a retry; never for correctness                                  |
| A retry loops between tiers forever    | `retry.attempt` not incremented or not respected                  | Attempt count in header; hard cap; final tier goes to DLQ                      |
| Retry storm after outage               | All records due at once                                           | Jitter in `not_before`; rate-limit the retry consumer                          |
| Poison record in the retry topic       | Same head-of-line problem, one level down                         | Classify there too; permanent errors skip straight to DLQ                      |
| Message too large after adding headers | Publish fails                                                     | Truncate error text; keep header budget small                                  |
| Partition-count mismatch               | Per-key locality lost                                             | Create retry topics with the same partition count                              |
| Duplicate retries                      | Same record parked twice                                          | Idempotent sink absorbs; DLQ dedup key (note 4)                                |

A critical design principle: **the failure handling code is the least tested and the most dangerous**. It runs only when things are already going wrong. Give it its own chaos tests (section 16).

## 12. Capacity and retention

A retry topic holds records for at least their delay. Size it deliberately.

| Parameter            | Rule                                                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `retention.ms`       | **At least** the largest tier delay + retry consumer outage tolerance + safety margin. If it is shorter than the delay, records can be **deleted before they are retried** (silent loss; the same trap as [K11 / retention note](../../../stage-2/learning/Kafka/5.%20kafka-retention.md)) |
| Partitions           | Same as the source topic for key affinity; each partition has an independent pause clock                                                                                                                                                                                                   |
| Replication, min ISR | Same as the main topic. A weaker retry topic is where data goes to die                                                                                                                                                                                                                     |
| Volume               | Steady-state ≈ (failure rate) × (delay). A 10 % failure rate with a 10-minute tier holds ~10 minutes of 10 % of the traffic                                                                                                                                                                |

Burst arithmetic: at 2,000 events/s and a 1 % record-level failure rate, you park 20 records/s; a 1-minute tier holds about 1,200 records. Trivial. The same system with an unnoticed 100 % failure rate (a systemic error misclassified as retriable) parks 2,000 records/s: **the retry topic becomes a copy of your traffic**. That is the flood of note 1 section 10 again, which is why the flood breaker must watch the retry rate too.

## 13. Alternatives

| Approach                                                                                  | How it works                                                                                       | When                                                                                    |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **Retry topics** (this note)                                                              | Parked on Kafka, delay via `not_before` + pause                                                    | Kafka-native, moderate delays, event pipelines                                          |
| **Pause and keep in place**                                                               | `pause()` partition, resume later                                                                  | Dependency-wide outages, short to medium                                                |
| **Database retry table + poller**                                                         | Row with `not_before`, `attempts`, `status`; worker selects due rows with `FOR UPDATE SKIP LOCKED` | Arbitrary delays, need to query/modify/cancel pending retries; but adds a DB dependency |
| **Scheduler service / workflow engine** (Temporal, Step Functions, Quartz)                | Durable timers and retry policies                                                                  | Complex multi-step workflows, long (hours to days) delays                               |
| **Broker-native delay** (RabbitMQ DLX + TTL, SQS `DelaySeconds`, Pulsar delayed delivery) | Broker holds the message                                                                           | Not available in Kafka                                                                  |
| **Client-side blocking retry**                                                            | Sleep in handler                                                                                   | Only sub-second, only race conditions                                                   |

Rules of thumb: seconds → in-place; seconds to ~minutes, record-scoped → **retry topics**; hours or business-meaningful timers → scheduler or table.

## 14. Delayed processing beyond failure

The same machinery serves non-failure needs:

- **Scheduled actions** ("send the reminder in 24 h"): `not_before = event.time + 24h`.
- **Cooling-off windows** ("process the refund after fraud checks complete").
- **Rate shaping** (smooth a burst by spreading `not_before`).
- **Waiting for a prerequisite** ("hold the order update until the order is created"), where the retry is the dependency wait of note 1 section 4.2.

A word of caution: a topic is a good _queue with a delay_, a poor _timer service_. If you need cancel, reschedule or inspection of pending items, use a table or scheduler.

## 14b. Interaction with the dead-letter queue

Retry topics shorten the list of messages that reach the DLQ, because _time-dependent_ failures resolve in the waiting room. They do not replace the DLQ. The final tier's failure handler publishes to the DLQ with the full header trail (all attempts, first-failed-at, last error) so that diagnosis does not require reconstructing the retry path. Details are in [note 4](4.%20dead-letter-queue-design.md).

## 15. EventPulse design

**Today [observed]** (see [`batch-handler.ts`](../../../../services/consumer-sink/src/consumer/batch-handler.ts)):

- Parse failure → DLQ immediately.
- Row-level DB failure (22xxx/23xxx, unknown) → isolate, retry in place up to `SINK_MAX_RETRIES` (3) with equal-jitter backoff, then DLQ.
- Dependency failure (transient or systemic) → retry in place inside a 20 s window, then **pause the partition** and re-read the chunk after the pause. No retry topic.

**Where a retry topic would help in Stage 3:**

| Case                                                                   | Today                       | With a retry topic                                                         |
| ---------------------------------------------------------------------- | --------------------------- | -------------------------------------------------------------------------- |
| Row fails with an FK violation because a tenant record has not arrived | Retries 3 × <1 s, then DLQ  | Parked for 5 s, 1 min, 10 min; likely clears; far fewer false dead letters |
| Per-row transient errors that do not clear in 1 s                      | DLQ after 0.7 s             | Parked with longer horizon                                                 |
| Long dependency outage (minutes)                                       | Pause (works, nothing lost) | Not needed; pausing is better (do not move good data)                      |

**Proposed shape for `events.raw`:** two tiers (`events.raw.retry.30s`, `events.raw.retry.5m`), partitions = 6 (same as source), `acks=all`, idempotent producer, `min.insync.replicas` same as main, retention ≥ 24 h (the longest tier is minutes; 24 h also covers a weekend-long retry-consumer outage with a margin you can tune), then `events.dlq`. The retry consumer is a second consumer group (`sink-postgres-retry`) running the same `handleBatch` core, so classification, bisection and DLQ publishing are reused. Treat this as a candidate design to evaluate against S3-F5, not as already built.

Order tolerance: the `events` table's key is `event_id` and reads order by event time, so out-of-order arrival is harmless, consistent with section 9.

## 16. Testing the retry path

1. **Park test:** a record that fails with a retriable record-level error appears on the retry topic with `attempt=1`, a `not_before` in the future, and the original key/value bytes unchanged; the source offset advances.
2. **Timing test (fake clock):** the retry consumer does not process before `not_before`; it processes after; it never sleeps (assert `pause` was called and the poll loop kept running).
3. **Escalation test:** fail every attempt; the record visits each tier in order then lands in the DLQ with `attempts = N` and all provenance headers.
4. **Crash test between publish and commit:** kill the consumer after the retry publish ack but before the source commit; on restart the record appears on the retry topic twice and the sink stores it once.
5. **Mixed-delay test:** show the head-of-line delay if two delays share one topic, to prove why tiers exist.
6. **Flood test:** misclassify a systemic error as retriable; verify the flood breaker trips.
7. **Retention test:** set retention shorter than the delay and show the loss, then enforce a config invariant against it.
8. **Ordering test:** with an order-sensitive sink, show that parked records invert order; with the idempotent insert-only sink, show no difference in final state.

## 17. Observability

| Metric                                              | Why                                               |
| --------------------------------------------------- | ------------------------------------------------- |
| Records parked per tier per minute (by error class) | Rising rate = something new is failing            |
| Retry topic lag and **age of oldest record**        | The retry consumer being down is silent otherwise |
| Success at attempt k (histogram)                    | Tells you whether retry tiers earn their cost     |
| Final-tier exhaustion rate (to DLQ)                 | The "gave up" rate                                |
| Time from first failure to success                  | Recovery latency                                  |
| Partition pause time on retry consumer              | Normal; spikes mean timing misconfiguration       |
| Ratio parked / consumed                             | Flood tripwire                                    |

Dashboards should answer: "how many records are waiting, how old is the oldest, and what is the success rate on each retry?"

## 18. EventPulse decisions

| Decision                              | Choice                                           | Why                                                 |
| ------------------------------------- | ------------------------------------------------ | --------------------------------------------------- |
| Outage handling                       | Pause the partition (not a retry topic)          | Good data should stay where it is                   |
| Record-level, time-dependent failures | Retry topics with tiered fixed delays (design)   | Constant delay per topic keeps the head always next |
| Delay mechanism                       | `retry.not_before` header + `pause()`/`resume()` | No scheduler dependency                             |
| Publish vs commit order               | Publish (acks=all) then commit                   | Duplicate over loss                                 |
| Producer for retries                  | Idempotent, `acks=all`, own client id            | Same as the DLQ publisher                           |
| Ordering                              | Tolerated: idempotent insert-only sink           | Avoids key-level blocking state                     |
| Attempt counter                       | Header, travels with the message                 | Survives restarts and consumer changes              |
| End of the line                       | DLQ with full history                            | Reversible quarantine                               |

## 19. Common confusions

1. **"Kafka can delay messages."** It cannot. The delay is a consumer-side convention.
2. **"Retry topics fix outages."** They multiply data movement in an outage. Pause instead.
3. **"One retry topic with different delays is fine."** The head of the partition blocks later, shorter delays.
4. **"Sleep until `not_before`."** Sleeping starves heartbeats. Pause the partition.
5. **"Commit first, then park."** Crash in between loses the record.
6. **"Retry topics preserve ordering."** They do the opposite.
7. **"The retry consumer is plumbing."** It is production code on the failure path and needs the strictest tests.
8. **"Default retention is fine."** A delay longer than retention deletes your retry.
9. **"Relative delay headers are simpler."** Absolute timestamps survive redelivery.

## 21. Glossary and cheat sheet

| Term               | Meaning                                                   |
| ------------------ | --------------------------------------------------------- |
| Retry topic        | A Kafka topic where failed records wait to be retried     |
| `not_before`       | Header: earliest time a record may be processed           |
| Tier               | A retry topic with one constant delay                     |
| Parking            | Moving a record aside so the partition can proceed        |
| Pause / resume     | Stop/start fetching a partition without leaving the group |
| Key-level blocking | Holding all later records of a key behind a parked one    |
| Delayed processing | Processing a record later than it was produced            |

```
failure (record-level, time-dependent)
  -> produce to retry-tier-k (acks=all) with attempt+1, not_before = now + delay_k + jitter
  -> then commit source offset
retry consumer: head not due? pause + resume timer : process
exhausted -> DLQ with full history
outage (dependency-wide) -> pause, do NOT park
```

Rules: park only record-scoped failures; constant delay per topic; absolute `not_before`; ack before commit; retention above the longest delay; never sleep; ordering is the price.

# DLQ Replay Tooling

_Retries-and-dead-letters note 5 of 5 in the Stage 3 learning notes. Read [note 4 (the dead-letter queue)](4.%20dead-letter-queue-design.md) first. A DLQ you cannot safely replay is a graveyard: the messages are preserved, but nothing can bring them back without risk. This note designs the tool that closes the loop: select dead letters, check them, re-inject them into the system with safeguards against loops, duplicates, ordering damage and overload, and leave an audit trail. It supports S3-F6 ("a replay tool re-injects DLQ messages safely, with filters and a dry-run mode")._

**No labs here.** EventPulse has `scripts/dlq-peek.sh` (inspection) but **no replay tool yet**, so everything about the tool itself is **[design]**. What it relies on is observed in code: the `dlq.*` headers ([`dlq-publisher.ts`](../../../../services/consumer-sink/src/sink/dlq-publisher.ts)), the idempotent insert in the sink, and the classification in [`errors.ts`](../../../../services/consumer-sink/src/sink/errors.ts). Peek helper: [`scripts/dlq-peek.sh`](../../../../scripts/dlq-peek.sh).

## 1. TL;DR

- Replay is the **second half of the DLQ contract**: quarantine is only responsible if release is possible, safe, and observable.
- **Never replay before the cause is fixed.** Replaying unfixed messages just re-creates the dead letters (a loop, with load).
- A safe replay tool has: **filters** (choose exactly which dead letters), **dry-run** (show what would happen, change nothing), **rate limiting**, **loop protection** (replay counter and cap), **idempotency awareness** (duplicates are expected and absorbed), **resumability** (crash-safe progress), and an **audit log**.
- Replay target decision: **the original topic** (normal path, full validation, simplest) versus **a dedicated replay topic** (isolates the load and lets you rate-limit and prioritise). Never write replayed data directly to the sink bypassing the pipeline unless you accept bypassing its safeguards.
- Replay **preserves the original bytes and key**, and adds provenance headers (`replay.*`). It never edits the payload silently; repairs are explicit, versioned transforms.
- Expect **duplicates** (the DLQ itself can hold some, note 4) and **out-of-order** arrival; they are harmless only when the sink is idempotent and order-tolerant, which is the design EventPulse relies on.
- Replay is a **production write to your data**. Treat it like a database migration: dry-run first, small canary batch, then the rest, with a kill switch.

> **One-line version:** _Fix first, filter precisely, dry-run, replay slowly with a brake and a counter, and write down what you did._

## 2. The mental model: returning evidence to circulation

An item held in an evidence locker can be released only after: the case is resolved (cause fixed), the paperwork identifies exactly which item (filters), a supervisor reviews the release list (dry-run), the items go back in a controlled order, not all through the front door at once (rate limit), the release is logged (audit), and an item that comes back a second time raises a flag (loop protection).

A replay tool is that procedure, written as software so that a tired person under pressure cannot skip a step.

## 3. Why replay is dangerous

| Risk                           | What happens                                                                                                                                               |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Replay loop**                | Cause not fixed; every replayed message fails again and returns to the DLQ; each pass multiplies headers and noise                                         |
| **Duplicate effects**          | The dead letter was partly processed (a crash after the DB write, before the offset commit); replaying duplicates the effect unless the sink is idempotent |
| **Flood**                      | 500,000 dead letters replayed in one minute overwhelm the database and cause _new_ failures                                                                |
| **Stale data**                 | Replaying week-old state changes over current state                                                                                                        |
| **Wrong target**               | Replaying to the wrong topic or environment (production dead letters into staging, or vice versa)                                                          |
| **Wrong selection**            | A filter that is too broad replays messages that should have been discarded (known-bad data, deleted tenants, GDPR-erased records)                         |
| **Lost provenance**            | Replayed messages indistinguishable from originals: no audit, no ability to attribute later failures                                                       |
| **Partial run**                | Tool crashes halfway; no record of which were replayed; the rerun replays everything again                                                                 |
| **Silent mutation**            | An ad-hoc script "fixes" payloads and nobody knows what changed                                                                                            |
| **Ordering violations**        | Replayed records overwrite newer state                                                                                                                     |
| **Poison amplification**       | One still-bad message blocks the replay consumer's partition, just as the original did                                                                     |
| **Human error under pressure** | An incident at 3 a.m. and a one-liner script with no confirmation                                                                                          |

Every feature in sections 7 to 18 exists to neutralise one of these.

## 4. What replay needs from the DLQ record

Replay can only be as good as what note 4 stored. The requirements:

| Need                                               | Provided by                                                                      |
| -------------------------------------------------- | -------------------------------------------------------------------------------- |
| Exact original payload                             | Original key and raw bytes (observed)                                            |
| Original destination                               | `dlq.original_topic` (observed)                                                  |
| Identity for dedup and audit                       | `dlq.original_topic`, `dlq.original_partition`, `dlq.original_offset` (observed) |
| Cause grouping                                     | `dlq.error_class`, `dlq.error_code`, `dlq.error_message` (observed)              |
| Which consumer failed                              | `dlq.consumer_group` (observed)                                                  |
| Time of failure                                    | `dlq.failed_at` (observed)                                                       |
| Which code failed, to select "failed before fix X" | `dlq.consumer_version` **[design]**                                              |
| Age of the data                                    | `dlq.original_timestamp` **[design]**                                            |
| Loop detection                                     | `dlq.replay_count`, `dlq.replayed_from` **[design]**                             |
| Stable dedup identity                              | `dlq.dedup_key` **[design]**                                                     |

If a dead letter lacks these (older records written before the headers existed), the tool must handle "missing field" explicitly: skip with a reason, or require an override flag, never guess.

## 5. Decide first: replay, repair, or discard

Not every dead letter should be replayed. The decision per **group** (cause), made during triage (note 4, section 13):

| Cause                                                  | Decision                                                 | Reason                                  |
| ------------------------------------------------------ | -------------------------------------------------------- | --------------------------------------- |
| Our parser or sink had a bug; message was valid        | **Replay as is** after the fix ships                     | Message was never wrong                 |
| Missing dependency now present (FK parent exists)      | **Replay as is**                                         | World changed                           |
| Schema evolved; old messages lack a new required field | **Repair, then replay** (explicit transform)             | The message needs a default or a lookup |
| Producer bug emitted garbage                           | **Fix the producer; discard** (or repair if recoverable) | Replaying garbage reproduces garbage    |
| Data for a deleted or erased tenant                    | **Discard** with audit                                   | Replay would resurrect deleted data     |
| Duplicate dead letters                                 | **Collapse** to one                                      | Dedup by identity                       |
| Expired relevance (too old to matter)                  | **Discard** or archive                                   | Staleness risk                          |
| Unknown cause                                          | **Hold**; investigate                                    | Never replay a mystery                  |

A tool should make "replay" the _least automatic_ choice, requiring an explicit cause fix reference (`--reason "fixed in v1.8.2"`), and make "discard" and "archive" equally deliberate.

## 6. Where to replay to

| Target                                                                                                | How                                                                                     | Pros                                                                                                       | Cons                                                                                                                             |
| ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| **Original topic** (`events.raw`)                                                                     | Produce with the original key to the source topic                                       | Full normal path: validation, classification, metrics, all consumers; simplest; per-key partition locality | Competes with live traffic; other consumer groups also see the replay (could be unwanted: an analytics consumer counts it twice) |
| **Dedicated replay topic** (`events.raw.replay`) with a separate consumer group running the same code | Lets you throttle independently, prioritise live traffic, and only the sink consumes it | Extra topic and group                                                                                      | Other consumers don't see the data (may be desired or not); code path must be identical                                          |
| **Directly into the sink** (write to Postgres)                                                        | Tool does INSERT ... ON CONFLICT                                                        | Fast, no Kafka                                                                                             | Bypasses validation and classification; a second implementation of the write that will drift; avoid                              |
| **Back to the retry topic** (note 3)                                                                  | Restart the retry ladder                                                                | Good for time-dependent failures                                                                           | Only if the cause is time-dependent                                                                                              |

Considerations:

- **Which consumers should see the replay?** If a replayed event is re-published to the source topic, _all_ groups consume it. Fan-out consumers that are not idempotent (analytics counters, notifications) may double-count or double-send. For EventPulse's sink (idempotent) this is fine; for others, use the dedicated replay topic and a targeted group, or add a header (`replay.target_group`) that other consumers ignore.
- **Environment safety:** the tool must show the **cluster and topic** in its output and require confirmation, and must refuse to run if the DLQ and target environments differ unless explicitly overridden.

Recommended default: replay to the **original topic via the normal producer path** for low volumes, and a **dedicated replay topic with rate limits** for large replays.

## 7. Tool anatomy

A replay tool is a small pipeline with distinct stages, each separately testable.

```
 [Source]   read DLQ (topic, partition range or offset range) with its own consumer group, no auto-commit
     |
 [Select]   apply filters (class, code, time range, tenant, version, id list, count limit)
     |
 [Dedup]    collapse by dlq.dedup_key / (topic, partition, offset)
     |
 [Check]    pre-flight: eligibility (replay_count < cap, not too old, target exists, cause-fix reference present)
     |
 [Plan]     report: counts by class, tenants, age range, oldest/newest, estimated duration at rate R
     |             ---- dry-run stops here ----
 [Confirm]  interactive confirmation or --yes with a plan hash
     |
 [Transform] optional named repair (versioned), else identity
     |
 [Emit]     produce to target (original bytes + key, headers: replay.*) at rate R, acks=all, idempotent
     |
 [Record]   audit log + progress checkpoint (after each acked batch)
     |
 [Report]   summary: replayed, skipped (with reasons), failed, remaining
```

Design principles:

1. **Pure planning, impure emitting:** the plan is computed with no side effects, so the dry-run and the real run share the same code path up to the emit step. The dry-run must never differ from the real run in selection logic.
2. **Read with a dedicated consumer group** and **commit progress only after the emit is acked** (the same effect-then-progress rule as everywhere in this repo).
3. **Everything bounded:** `--limit`, `--rate`, `--max-replays`.
4. **Fail closed:** missing headers, unknown classes, ambiguous filters → skip and report, never guess.

## 8. Filters

Filters decide _which dead letters_. They must be combinable (AND semantics), explicit, and echoed back in the plan.

| Filter                     | Example                                                | Use                                       |
| -------------------------- | ------------------------------------------------------ | ----------------------------------------- |
| Error class                | `--class PERMANENT_DB`                                 | Replay by cause category                  |
| Error code                 | `--error-code 23503`                                   | Replay one cause precisely                |
| Error message pattern      | `--message-contains "tenant not found"`                | When codes are missing                    |
| Failed-at range            | `--failed-after 2026-11-22T08:00Z --failed-before ...` | "Everything between deploy X and the fix" |
| Original timestamp range   | `--event-after ... --event-before ...`                 | Staleness control                         |
| Source topic               | `--original-topic events.raw`                          | Avoid mixing topics                       |
| Consumer group             | `--group sink-postgres`                                | Per-consumer causes                       |
| Consumer version           | `--version-before 1.8.2`                               | "Failed on code with the bug"             |
| Key / tenant               | `--key tenant-42`                                      | One customer's recovery                   |
| Partition and offset range | `--partition 5 --from 2893 --to 2893`                  | Surgical single-message replay            |
| Identity list              | `--ids-file ids.txt`                                   | Exactly the triaged set                   |
| Replay count               | `--max-replay-count 0`                                 | Only never-replayed items                 |
| Limit                      | `--limit 100`                                          | Canary                                    |
| Sample                     | `--sample 5%`                                          | Cheap confidence                          |

Rules: at least one **narrowing** filter must be given (no "replay everything" by default); `--all` is a separate, loud flag; the final plan prints the effective filter.

## 9. Dry-run

**Dry-run is the default.** A real run needs an explicit flag (`--execute`), and the safest design requires the dry-run's **plan hash** to be passed back to the execute call so the executed set equals the reviewed set.

A dry-run reports:

```
DLQ replay plan (DRY RUN - nothing was written)
  cluster:           kafka-prod-1  (confirm: matches --env prod)
  source topic:      events.dlq
  target topic:      events.raw         (original-topic mode)
  filters:           class=PERMANENT_DB code=23503 failed-after=2026-11-22T08:00Z
  matched:           1,842 records     (duplicates collapsed: 37)
  eligible:          1,805
  skipped:           0 missing-dedup, 12 over-replay-cap, 25 too-old (>7 d)
  by class/code:     PERMANENT_DB/23503: 1,805
  by tenant (top):   acme 1,204 | globex 311 | initech 290
  event age:         min 2m, median 41m, max 3h 12m
  rate:              200 msg/s  -> estimated 9 s   (change with --rate)
  headers added:     replay.run_id, replay.count=1, replay.original_dedup_key, replay.at, replay.reason
  sample (3):        key=acme  event_id=...  offset=5:2893 ...
  plan hash:         9c1f...   (pass --plan-hash 9c1f... with --execute)
```

What the dry-run must **not** do: write to the target, commit DLQ offsets of the real consumer group, mutate counters or alter dead letters. A good dry-run test is: run it twice, observe identical output and zero side effects.

Optional extra: **validate by simulation** (parse every selected record with the current parser and report how many would still fail). This catches "the fix did not cover case X" before anything is sent. Such a check is the best protection against a replay loop.

## 10. Safety rails

| Rail                           | Behavior                                                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **Dry-run default**            | Real run needs `--execute` (+ plan hash)                                                                 |
| **Required reason**            | `--reason` text and ideally a ticket or fix reference; stored in the audit                               |
| **Environment guard**          | Prints cluster and topic; refuses prod without `--env prod` and confirmation                             |
| **Narrowing filter required**  | No filter, no run; `--all` explicit                                                                      |
| **Canary stage**               | First `--limit 10` batch; check the outcome; then continue (the tool can pause after the canary and ask) |
| **Rate limit**                 | Mandatory ceiling                                                                                        |
| **Concurrency limit**          | One run per DLQ topic at a time (lock)                                                                   |
| **Stop condition**             | Abort if the target's failure/DLQ rate rises above X during the run                                      |
| **Kill switch**                | Signal or flag file stops the run cleanly; progress is saved                                             |
| **Max replay count**           | A message replayed N times is not replayed again without an override                                     |
| **Age guard**                  | `--max-age` skips data too old to be relevant                                                            |
| **Authorization**              | Only the owning team can run; separate read vs execute permission                                        |
| **Two-person rule** (optional) | For very large or sensitive replays                                                                      |

## 11. Loop prevention

A replay loop is: replay → fail again → back in the DLQ → replay again.

Defenses, layered:

1. **Do not replay before the fix.** The `--reason` / fix reference is mandatory; the pre-flight simulation (section 9) checks the fix on the actual records.
2. **Replay counter in a header** (`replay.count`) incremented on each replay. When the record fails again, the DLQ publisher **copies** the replay headers; the tool refuses records with `replay.count >= cap` (default 2 or 3).
3. **Lineage header** (`replay.original_dedup_key`, `replay.run_id`): a failed replay is traceable to its run, so you can see "run 42 produced 1,805 new dead letters", which is the loop alarm.
4. **Run-level circuit breaker:** if more than X% of replayed records come back as dead letters within a window, stop the run and alert.
5. **Separation:** replays to a dedicated replay topic yield dead letters from a replay consumer group (`dlq.consumer_group=sink-postgres-replay`), easy to filter and count separately.
6. **Never auto-replay.** A scheduled job that replays the DLQ is a perpetual-motion machine for poison; if automation is wanted, only for _time-dependent_ classes with the retry-topic ladder (note 3), not the DLQ.

Important: the **DLQ publisher** must preserve incoming `replay.*` headers when it re-dead-letters (the existing `originalHeaders` helper already copies all original headers, so they survive, **[observed]**), and must not copy `dlq.*` headers from a previous dead-lettering as if they were the original's (a replayed message carries stale `dlq.*` headers; the publisher overwrites them, but a good tool **strips** `dlq.*` before replay and moves them into `replay.previous_*` to avoid confusion).

## 12. Idempotency and duplicates on replay

Replay produces duplicates by design. The safety net is the same as everywhere in this stage ([delivery-semantics note 4](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md)):

| Source of duplicates                                                        | Absorbed by                                                |
| --------------------------------------------------------------------------- | ---------------------------------------------------------- |
| The dead letter's row was actually stored before the failure (crash window) | `INSERT ... ON CONFLICT (event_id) DO NOTHING` in the sink |
| The DLQ holds the same failure twice (note 4, section 9)                    | Tool dedups by identity; sink dedups by `event_id`         |
| The tool crashes and resumes                                                | Checkpoint resume; sink idempotence for the overlap        |
| Two operators replay the same set                                           | Lock; audit; sink idempotence                              |
| The same business event arrives from a producer retry _and_ via replay      | `event_id` uniqueness                                      |

Rule: **never replay into a sink that is not idempotent.** If a downstream effect is not idempotent (email, payment), the replay needs an additional guard: an idempotency key check, a "replayed" flag that suppresses the side effect, or a different path (a human re-sends).

EventPulse's duplicates are _counted_ (`attempted - inserted`); a replay of 1,805 messages of which 40 were already stored should show 40 duplicates absorbed in the metrics, which is a useful check that replay behaves as predicted.

## 13. Ordering and staleness

Replayed records arrive **late**. Consequences ([note 3, section 9](3.%20retry-topics-and-delayed-processing.md#9-ordering-what-you-give-up) gives the general argument):

- For an **insert-only idempotent sink**, order is irrelevant.
- For **state updates**, a replayed old update must not overwrite newer state. Require version or timestamp comparison in the sink (`WHERE excluded.version > table.version`) or avoid replaying such data.
- **Time-bounded semantics** (rolling windows, alerts): a late event may fall outside the window or trigger a stale alert. Decide per consumer whether late data is accepted; the tool's `--max-age` guards the source side.
- **Event time vs processing time:** the replayed message should keep its **original event time** in the payload; the sink must not stamp "now" over it. EventPulse's freshness metrics use event time; replayed events will show high freshness lag, which is true and should be excluded from SLO dashboards (tag them via the `replay.*` header).

Per-key ordering during a replay: if the DLQ contains e2 (failed) and the main flow has since processed e3, e4, a replay of e2 inverts order. Same trade as retry topics; same answer.

## 14. Rate limiting and backpressure

A replay is a **load test you run on purpose against production**.

| Control                 | Setting                                                                                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Messages per second     | Start at a small fraction (for example 5 to 10%) of the sink's spare capacity; EventPulse benchmarks (Stage 2 K-series) give the sustainable rate |
| Burst                   | Token bucket with a small bucket                                                                                                                  |
| Concurrency             | One producer, bounded in-flight                                                                                                                   |
| **Adaptive throttling** | Slow or stop when consumer lag on the target topic grows or DB write latency rises; the tool reads lag via the admin API                          |
| Priority                | Live traffic first: replay lower-priority (dedicated topic with a separate group, lower `max.poll.records`)                                       |
| Schedule                | Large replays off-peak                                                                                                                            |
| Memory                  | Streaming; never load the whole DLQ into memory                                                                                                   |

Pair with the [backpressure note](../../../stage-2/learning/consumer/5.%20kafka-consumer-backpressure.md) mindset: a replay producer that ignores downstream lag simply moves the queue from the DLQ to the target topic and may push live consumers into retention trouble (see [lag note](../../../stage-2/learning/consumer/4.%20kafka-consumer-lag.md)).

## 15. Resumability and progress tracking

A replay of a million records will be interrupted. The design must make that harmless.

1. **Read the DLQ with a dedicated consumer group** (`dlq-replay-<run_id>`) with auto-commit off.
2. **Emit, wait for ack, then commit the DLQ offset** (effect first, progress second). A crash re-emits at most one batch: duplicates, never gaps.
3. **Checkpoint** per batch: run id, last offset per partition, counts (replayed, skipped, failed).
4. **Run record** (state: planned, running, paused, completed, aborted) stored durably (a table or a compacted topic), so `status` and `resume` commands work.
5. **Idempotent resume:** `resume --run-id X` continues from the checkpoint; the plan hash ensures the same selection.
6. **Do not delete from the DLQ on replay.** Kafka topics are append-only; replayed records stay in the DLQ until retention removes them. The audit log and `replay.*` headers record the state. (Marking "resolved" can be done by writing a **tombstone/resolution record** to a separate `events.dlq.resolutions` topic, keyed by dedup key, which the tool's selection stage consults to skip resolved items.)

## 16. Repair transforms

Sometimes a message cannot be replayed unchanged (a required field was added; a field is mis-typed by a known producer bug).

Rules for repairs:

1. **Explicit, named, versioned** transforms (`add-default-region@1`), reviewed like code, never ad-hoc `sed` on payloads.
2. **Original preserved:** the repaired message gets a header `replay.repair=add-default-region@1` and, ideally, the original bytes are still in the DLQ (they are: replay never deletes).
3. **Pure functions** (input bytes → output bytes), with unit tests and a dry-run diff ("3 sample before/after").
4. **Re-validated** with the same parser the consumer uses; a repair that still does not parse is reported, not sent.
5. **Never repair semantics silently** (guessing a missing amount). Repair only where the correct value is derivable.
6. **Idempotency identity preserved:** the repaired message keeps the same `event_id`, so a duplicate of the original in the live flow is still absorbed.

## 17. Audit trail

Replay modifies production data; keep a record that answers "who replayed what, when, why, with which result?"

| Field                                | Example                                                  |
| ------------------------------------ | -------------------------------------------------------- |
| `run_id`                             | `rp-20261122-0007`                                       |
| operator                             | `alice` (authenticated identity)                         |
| `reason` / reference                 | "fixed FK ordering, v1.8.2, ticket EP-412"               |
| filters and plan hash                | exact selection                                          |
| source / target (cluster, topics)    |                                                          |
| counts                               | matched, eligible, replayed, skipped (by reason), failed |
| time                                 | start, end                                               |
| rate and settings                    |                                                          |
| outcome                              | completed / aborted, and why                             |
| per-record outcome (sampled or full) | for later reconciliation                                 |

Where: an append-only log (a table, or a topic `events.dlq.audit`) plus the `replay.*` headers on every replayed record, so an event in the target can be traced back to its run (`replay.run_id`).

Reconciliation after a run: compare `replayed` to (stored rows + duplicates absorbed + new dead letters). If they do not add up, investigate.

## 18. Discarding responsibly

Some dead letters are never replayed. Discarding is also a controlled operation:

- Require a **reason** and a **filter**; produce a **dry-run count**.
- **Archive before delete:** copy to cold storage (object store) with the metadata, because "known bad" sometimes turns out to be "evidence in a dispute".
- Record in the audit and write **resolution records** so the DLQ's open-items count drops.
- Respect legal obligations: erasure requests mean _delete_, with proof.
- Let retention do the final deletion; do not rewrite Kafka logs.

## 19. A replay runbook

```
BEFORE
 1. Triage: group the DLQ by cause (note 4, section 13). Pick ONE group.
 2. Confirm the root cause is FIXED and DEPLOYED (version header / deploy time).
 3. Decide: replay as is / repair / discard.
 4. Check capacity: consumer lag, DB headroom, error budget. Choose a rate.
DRY RUN
 5. Run with the narrowest filter. Read the plan: counts, tenants, ages, skipped reasons.
 6. (If available) run the validation simulation: how many would still fail?
CANARY
 7. Execute with --limit 10 at a low rate. Check: stored rows increased, no new dead letters,
    duplicates counter as expected.
RUN
 8. Execute the rest with the plan hash. Watch: target lag, DB latency, new dead letters/min.
 9. Be ready to stop (kill switch).
AFTER
10. Reconcile counts. Check the DLQ for new dead letters with replay headers (loop alarm).
11. Record outcome and resolve the items. Note the follow-up fix upstream.
```

## 20. Command-line design

A sketch of a CLI **[design]** (not implemented):

```bash
# inspect and plan (read-only, the default)
dlq-replay plan    --env prod --dlq events.dlq --class PERMANENT_DB --error-code 23503 \
                   --failed-after 2026-11-22T08:00Z --max-age 7d --target events.raw \
                   --rate 200 --reason "FK ordering fixed in v1.8.2 (EP-412)"

# canary
dlq-replay execute --plan-hash 9c1f --limit 10

# the rest
dlq-replay execute --plan-hash 9c1f --rate 200

# operate
dlq-replay status  --run-id rp-20261122-0007
dlq-replay pause   --run-id rp-20261122-0007
dlq-replay resume  --run-id rp-20261122-0007
dlq-replay abort   --run-id rp-20261122-0007

# discard (also dry-run by default)
dlq-replay discard --class PERMANENT_PARSE --producer legacy-importer --reason "producer fixed" --archive s3://...
```

Design choices: a `plan` command that is the dry-run; `execute` requires the hash; `status`, `pause`, `resume`, `abort` act on a stored run record; output is human-readable and also machine-readable (`--json`). The existing `scripts/dlq-peek.sh` is the seed of `plan` (read-only inspection).

## 21. Testing the replay tool

1. **Dry-run purity:** zero produces, zero commits, deterministic output across runs.
2. **Selection:** each filter alone and combined returns the expected set against a fixture DLQ; "no narrowing filter" is rejected.
3. **Byte fidelity:** replayed key and value are byte-identical to the original; original headers retained; `dlq.*` stripped or moved; `replay.*` added.
4. **Loop protection:** a message with `replay.count` at the cap is skipped; a failing replay increments the count and, when it fails again, is not replayed past the cap.
5. **Idempotency:** replay a set where some rows are already stored; final row count equals distinct `event_id`s; duplicates metric equals the overlap.
6. **Resume:** kill the tool mid-run; resume; assert no gaps and bounded duplicates.
7. **Rate limit:** measured rate ≤ configured, under a fake clock.
8. **Stop conditions:** simulated rising failure rate aborts the run.
9. **Environment guard:** wrong cluster or topic is refused.
10. **Repair transform:** before/after fixtures, re-validation, and that identity is preserved.
11. **Crash between emit and checkpoint:** the batch is re-emitted; sink absorbs.
12. **Integration (end to end):** poison record → DLQ → fix the cause (feature flag) → replay → stored once → no new dead letter.
13. **Authorisation:** an unprivileged identity cannot execute.

## 23. EventPulse decisions

| Decision                   | Choice                                                                         | Why                                           |
| -------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------- |
| Replay target              | Original topic (`events.raw`) for small runs; dedicated replay topic for large | Normal path validated, with a throttle option |
| Safety of effect           | Rely on idempotent insert `ON CONFLICT DO NOTHING`                             | Duplicates absorbed                           |
| Default mode               | Dry-run                                                                        | Production writes need review                 |
| Mandatory inputs           | Narrowing filter, reason, rate                                                 | Prevent "replay everything"                   |
| Loop protection            | `replay.count` cap + run-level breaker                                         | Prevent graveyard recycling                   |
| Progress                   | Dedicated consumer group, commit after emit ack                                | Same rule as the sink                         |
| Fidelity                   | Original bytes/key, `replay.*` headers added, `dlq.*` moved                    | Auditability                                  |
| Ordering                   | Tolerated (insert-only sink)                                                   | Consistent with retry topics                  |
| Repairs                    | Named, versioned, dry-run diffed                                               | No ad-hoc edits                               |
| Audit                      | Run record + audit topic                                                       | Accountability                                |
| Dependency on DLQ metadata | Add version, timestamp, dedup headers                                          | Needed for safe filters (note 4, section 17)  |

## 24. Common confusions

1. **"Replay is just producing the DLQ back to the source topic."** That is the emit step, about 10 % of the tool. The rest is selection, safety and audit.
2. **"Replay fixes the problem."** Only the _code or data fix_ does; replay recovers the affected messages.
3. **"Auto-replay on a schedule."** A poison loop.
4. **"Duplicates on replay are bugs."** They are expected and absorbed by idempotence; they should be _counted_.
5. **"Delete from the DLQ after replay."** Kafka is append-only; mark resolved elsewhere, let retention expire.
6. **"A dry run is optional for small replays."** Small replays are where people skip the check and replay the wrong tenant.
7. **"Replay to the sink directly, it is faster."** It bypasses validation and creates a second write path.
8. **"Repair in the payload and forget."** Unrecorded repairs destroy evidence.
9. **"The DLQ does not need ordering thought."** Late, out-of-order replays can overwrite newer state.

## 26. Glossary and cheat sheet

| Term              | Meaning                                                  |
| ----------------- | -------------------------------------------------------- |
| Replay            | Re-injecting dead letters into processing after a fix    |
| Dry-run / plan    | A side-effect-free preview of a replay                   |
| Plan hash         | Fingerprint binding execution to the reviewed plan       |
| Canary            | A small first batch to verify behavior                   |
| Replay loop       | Replayed messages failing again and returning to the DLQ |
| Resolution record | A marker that a dead letter was handled                  |
| Repair transform  | A named, versioned change to a payload before replay     |
| Replay count      | Number of times a record has been replayed               |
| Graveyard         | A DLQ that cannot be safely replayed                     |

```
fix cause -> triage group -> plan (dry-run, filters, reason) -> canary -> run at a rate
          -> reconcile -> audit
tool = select + dedup + check + plan + confirm + (repair) + emit(ack) + checkpoint + audit
safety = dry-run default, narrowing filter, rate, replay.count cap, run breaker, env guard, kill switch
sink = idempotent, order-tolerant: duplicates and lateness are absorbed and counted
```

## 1. TL;DR

- **Transactional outbox:** inside the **same database transaction** that changes business data, `INSERT` a row into an **outbox table** describing the message to publish. Commit once. A separate **relay** reads outbox rows and publishes them to Kafka, then records that it did.
- This converts the _dual write_ into a _single write plus reliable propagation_: either **both** the change and the outbox row exist (and the event **will** be published) or **neither** does (and no event ever exists).
- **Delivery to Kafka is at-least-once.** The relay can publish a row and crash before marking it done, so it will publish it again. Therefore **every outbox row carries a stable unique id** and **consumers must be idempotent** ([note 4](./4.%20the-inbox-pattern.md)).
- Ordering: the outbox gives you **per-aggregate ordering** if (a) rows are written in commit order for that aggregate, (b) the relay publishes them in that order, and (c) the Kafka key is the aggregate id so they land in one partition. Global ordering is not provided and not needed.
- The relay is either a **polling publisher** (a loop running `SELECT ... FOR UPDATE SKIP LOCKED`) or **CDC** (Debezium reading the WAL). Both are in [note 3](./3.%20relay-polling-vs-cdc.md).
- Operational concerns: **table growth** (delete or partition published rows), **relay lag** (alert on the age of the oldest unpublished row), **poison rows** (a row that can never be published must not block the others), **row size**.
- Use it when a missed or phantom event is unacceptable and the source of truth is a database. Do **not** use it for high-volume loss-tolerant streams where Kafka itself is the record (the raw `events` ingest path in EventPulse).

> **One-line version:** _Don't tell Kafka; tell your own database, in the same transaction as the change, and let a relay tell Kafka for you until it is certain it has._

## 2. The mental model

A bank teller handles a withdrawal. Instead of calling head office after each transaction (and risking a crash between the two), the teller **writes the withdrawal and a "notify head office" slip on the same ledger line**. A courier sweeps up slips every few minutes and delivers them. A slip is only removed after head office acknowledges it. If the courier faints after delivery but before ticking, they deliver the slip again tomorrow, and head office recognises the slip number and ignores the repeat.

| Bank                                                  | Pattern                                      |
| ----------------------------------------------------- | -------------------------------------------- |
| Ledger line + slip written together                   | Business row + outbox row in one transaction |
| Courier                                               | Relay                                        |
| Slip number                                           | Outbox event id (the dedupe key)             |
| Head office ignores a repeated slip                   | Idempotent consumer / inbox                  |
| Slips pile up in a drawer if the courier is sick      | Relay lag; the outbox grows                  |
| Teller refuses a withdrawal; no slip was ever written | Rolled-back transaction: no phantom event    |

## 3. The pattern in one picture

```
 Client request
      |
      v
 ┌──────────────────────── Service (owns the DB) ───────────────────────────┐
 │  BEGIN                                                                    │
 │    UPDATE tenant_config SET rate_limit_rps = 500 WHERE tenant_id = 'T1'   │
 │    INSERT INTO outbox (id, aggregate_id, type, payload, ...) VALUES (...) │
 │  COMMIT   <-------------- the single atomic commit                        │
 └──────────────────────────────────────┬────────────────────────────────────┘
                                         │ (rows sit in the outbox table)
                                         v
                              ┌─────────────────────┐
                              │  Relay (separate    │   1. read unpublished rows, in order
                              │  loop or Debezium)  │   2. publish to Kafka (acks=all, idempotent)
                              └──────────┬──────────┘   3. mark published (or delete)
                                         │
                                         v
                                 Kafka topic (keyed by aggregate id)
                                         │
                                         v
                              Consumers (each dedupes by event id, "inbox")
```

Three things can fail independently after the commit: the relay, Kafka, and the consumers. **None of them can create inconsistency**, only delay (relay/Kafka down) or duplicates (retries), because the durable intent is already committed.

## 4. The write path: one transaction

The only code change in the request handler is to add one `INSERT` to the transaction that already exists:

```ts
// Teaching sketch (node-postgres style)
async function changeRateLimit(
  pool: Pool,
  tenantId: string,
  rps: number,
): Promise<void> {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");

    const { rows } = await client.query(
      `UPDATE tenant_config
          SET rate_limit_rps = $2, version = version + 1, updated_at = now()
        WHERE tenant_id = $1
      RETURNING version`,
      [tenantId, rps],
    );

    await client.query(
      `INSERT INTO outbox (event_id, aggregate_type, aggregate_id, event_type, payload)
       VALUES ($1, 'tenant_config', $2, 'TenantConfigChanged', $3)`,
      [
        randomUUID(),
        tenantId,
        JSON.stringify({
          tenantId,
          rateLimitRps: rps,
          version: rows[0].version,
        }),
      ],
    );

    await client.query("COMMIT"); // both rows, or neither
  } catch (e) {
    await client.query("ROLLBACK");
    throw e;
  } finally {
    client.release();
  }
}
```

Rules for the write path:

1. **Same connection, same transaction.** The outbox `INSERT` must run on the same transaction handle as the business write. A second pool connection would commit independently and reintroduce the dual write. (A very common bug with ORMs and "repository" abstractions that grab their own connection.)
2. **No Kafka call here.** The request path never talks to Kafka. This also means the request succeeds even if Kafka is down, which is a feature: the outbox decouples write availability from broker availability.
3. **Do not swallow the outbox insert error.** If the outbox insert fails, the transaction must roll back, so the business change does not commit without its event.
4. **Build the payload from data you just wrote** (including the new `version`), not from a later read, so the event matches the committed state exactly.
5. **Keep it cheap.** One extra single-row insert in the same round trip pipeline is small; bulk changes insert one outbox row per event (use a multi-row `INSERT` or `unnest`, as the sink does for events).
6. Wrap it so it cannot be forgotten: a function `withOutbox(tx, event)` or a unit-of-work that collects events and writes them before commit, so individual handlers cannot "forget" the outbox.

## 5. Designing the outbox table

A solid, boring starting point (PostgreSQL):

```sql
CREATE TABLE outbox (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- relay cursor / ordering aid
  event_id       uuid        NOT NULL UNIQUE,                       -- stable message id (dedupe key downstream)
  aggregate_type text        NOT NULL,                              -- e.g. 'tenant_config' -> maps to a topic
  aggregate_id   text        NOT NULL,                              -- Kafka message key (ordering unit)
  event_type     text        NOT NULL,                              -- e.g. 'TenantConfigChanged'
  payload        jsonb       NOT NULL,                              -- the event body
  headers        jsonb       NOT NULL DEFAULT '{}'::jsonb,          -- trace id, schema version, tenant, ...
  created_at     timestamptz NOT NULL DEFAULT now(),
  published_at   timestamptz                                        -- NULL = not yet published
);

-- The relay's hot query only ever looks at unpublished rows; a partial index keeps it tiny
-- no matter how large the historical table is.
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;
```

Column by column:

| Column                            | Why it exists                                                                                                                                                                                                |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id` (identity)                   | Gives a monotonically assigned number for the relay to order by. **Not** a reliable commit-order cursor on its own (see [section 9](#9-ordering) and [note 3](./3.%20relay-polling-vs-cdc.md)).              |
| `event_id` (uuid, unique)         | **The message identity.** Generated **once** when the row is written, never regenerated by the relay. Sent as a Kafka header/field so consumers can dedupe. A relay republish carries the _same_ `event_id`. |
| `aggregate_type` / `aggregate_id` | Routing (which topic) and **ordering** (the Kafka key). Aggregate = the entity whose changes must stay ordered.                                                                                              |
| `event_type`                      | Lets consumers dispatch and lets the schema evolve per type.                                                                                                                                                 |
| `payload`                         | The body. `jsonb` is flexible; it can also be `bytea` for Avro/Protobuf bytes.                                                                                                                               |
| `headers`                         | Trace context (`traceparent`), schema version, tenant id, correlation id: copied to Kafka headers.                                                                                                           |
| `created_at`                      | Measure relay lag and end-to-end latency.                                                                                                                                                                    |
| `published_at`                    | The relay's progress marker (polling design). With CDC you may not need it ([note 3](./3.%20relay-polling-vs-cdc.md)).                                                                                       |

Design choices worth deciding explicitly:

- **One outbox per service, not per aggregate.** A single table with `aggregate_type` for routing is simpler to operate. Split only if volume or retention differs sharply.
- **Status flag vs delete-on-publish vs cursor.** Options: (a) `published_at` flag; (b) delete rows once published; (c) keep rows and track a high-water-mark id in a separate table. Section 11 compares them. For a first build, (a) plus time-based cleanup or (b) is easiest.
- **`text` for `aggregate_id`.** Aggregates may have uuid, integer or composite keys; the Kafka key is bytes anyway.
- **Do not store large blobs.** Keep payloads small (a few KB). Store a reference and let consumers fetch if the data is large (the "claim check" idea), or put only the fields consumers need.
- **Same database, same schema** as the business tables: that is the whole point. An outbox in a different database brings back the dual write.

## 6. What goes in the row: the event design

The outbox is a place to make a **deliberate** decision about what the event says. Two broad styles:

| Style                            | Payload                                                            | Pros                                                  | Cons                                                           |
| -------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------- | -------------------------------------------------------------- |
| **Event notification**           | `{ tenantId, version }` only: "something changed"                  | Tiny; consumers fetch current state                   | Consumers must call back; extra load; races with later changes |
| **Event-carried state transfer** | Full new state (or the changed fields)                             | Consumers need no callback; works offline; replayable | Larger; payload becomes a public contract; leaks fields        |
| **Domain event**                 | Intent in business terms: `RateLimitRaised { from: 100, to: 500 }` | Meaningful; good for audit                            | Needs more modelling                                           |

Guidance:

- Prefer **carrying enough state** that a consumer can act without a synchronous callback, but only the fields that are part of a contract (not the whole table row). The event is a **public API**: version it.
- Include a **monotonic version** (`version` on the aggregate) in the payload. Consumers can then ignore stale events (`if event.version <= lastSeenVersion: skip`), which also protects against the out-of-order cases in [section 9](#9-ordering).
- Include `occurred_at` (business time) separately from `created_at` (row time) if they differ.
- Never include secrets or fields a consumer is not authorised to see: the outbox is a broadcast.
- Avoid deriving the payload from a **second read after commit**; build it inside the transaction from what you wrote.

## 7. The relay at a conceptual level

(Detailed implementations: [note 3](./3.%20relay-polling-vs-cdc.md).)

The relay has one job: **ensure every committed outbox row is eventually published, in order per aggregate, at least once.** Its loop, at the concept level:

```
loop:
  1. fetch a batch of unpublished rows (oldest first)
  2. publish them to Kafka (key = aggregate_id, headers include event_id), wait for acks
  3. record success (set published_at, or delete, or advance a cursor)
  4. if nothing to do, sleep a short interval; if error, back off and retry
```

Critical property: **step 3 happens only after step 2 is acknowledged.** The gap between steps 2 and 3 is the _remaining_ small window, where a crash causes the **same rows to be published again** on restart. That is deliberate: it trades duplicates for loss-freedom. The rule is "when unsure, publish again."

Producer settings for the relay (from the Stage 2 producer notes): `acks=all` ([acks](../../../stage-2/learning/producer/2.%20kafka-producer-acks.md)), `enable.idempotence=true` ([idempotence](../../../stage-2/learning/producer/3.%20kafka-producer-idempotence.md)) so that _client-level retries inside one session_ do not duplicate or reorder, sensible `delivery.timeout.ms` ([retries and timeouts](../../../stage-2/learning/producer/5.%20kafka-producer-retries-and-timeouts.md)), and the aggregate id as the **key** ([key and partitioner](../../../stage-2/learning/producer/6.%20kafka-producer-key-and-partitioner.md)). Note the idempotent producer's dedupe is **per producer session** (PID/epoch); it does **not** remove duplicates caused by the relay **restarting** and re-reading the same row. Only the consumer-side dedupe does ([delivery-semantics note 4](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md)).

## 8. The guarantees: what you get and what you do not

**You get:**

1. **Atomicity of intent.** No lost events from crashes between the change and the publish; no phantom events from rolled-back changes.
2. **Durability of intent.** The pending event survives process crashes, deploys and Kafka outages, because it is a committed row.
3. **Availability decoupling.** Writes succeed while Kafka is down; the backlog drains afterwards.
4. **Per-aggregate order** (with the conditions in section 9).
5. **Auditability.** The table (or its retained history) is a record of what was announced and when.

**You do not get:**

1. **Exactly-once delivery.** Duplicates are normal (relay crash after publish; relay restart; Kafka `send` timeout then retry). Consumers must dedupe.
2. **Immediate delivery.** Latency is relay poll interval + publish time (milliseconds to seconds). Consumers see the change _after_ the DB commit, never before.
3. **Global ordering** across aggregates, or even guaranteed ordering without the key/partition discipline.
4. **Cross-service atomicity.** It makes one service's change-and-announce atomic, not a business process spanning services (that is a saga).
5. **Protection from consumer-side failures.** A consumer that crashes mid-processing is a separate problem, solved by offset-commit discipline ([Stage 2 offset commits](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md)) and idempotence.

The honest label: **at-least-once publication of exactly the committed changes.**

## 9. Ordering

Why it is subtle: events for the same aggregate must reach consumers in the order the changes **committed**. Three places can break it.

### 9.1 Write order vs identity order

`id` from `GENERATED ... AS IDENTITY` (a sequence) is assigned **at insert time**, not commit time. Two concurrent transactions A and B:

```
A: BEGIN; INSERT outbox -> id=10 ... (slow) ......... COMMIT
B: BEGIN; INSERT outbox -> id=11; COMMIT
```

B commits first. A relay that reads "all rows with id > last_seen" can see row 11, advance its cursor to 11, and then row 10 commits later and is **skipped forever**. This is the classic **gap problem** with cursor-based polling ([note 3](./3.%20relay-polling-vs-cdc.md) covers the fixes: use a published flag rather than a cursor, or a lock that serializes writers, or transaction-id-based visibility, or CDC).

For events of the **same aggregate** the problem is normally avoided naturally: two transactions modifying the **same row** (`UPDATE tenant_config ... WHERE tenant_id = 'T1'`) serialize on that row's lock, so the second one cannot reach its outbox insert until the first commits (when the update comes first inside the transaction). Rule: **do the business `UPDATE` on the aggregate row before the outbox `INSERT`**, so the row lock enforces per-aggregate commit-order = id-order. The gap problem then only affects _different_ aggregates, whose relative order does not matter.

### 9.2 Relay order

A single relay publishing in `id` order preserves it. With **multiple relay workers**, two workers can publish two events of the same aggregate concurrently, and the later one may overtake. Fixes: one relay per partition of aggregate ids (e.g. `hashtext(aggregate_id) % N`), or a single active relay (leader election/advisory lock), or per-aggregate claim. Details in note 3.

### 9.3 Kafka order

Per-partition order only. Use `aggregate_id` as the Kafka **key**; the same key always maps to the same partition (while the partition count is unchanged; see [key and partitioner](../../../stage-2/learning/producer/6.%20kafka-producer-key-and-partitioner.md)). With the idempotent producer and `max.in.flight ≤ 5`, retries inside a session do not reorder. A relay **restart** re-reads from the first unpublished row, so a partially published batch replays in the same order, with duplicates but not reordering.

### 9.4 Defence in depth

Because duplicates and republishing exist, add a **version** per aggregate in the payload, and let consumers drop events with `version <= lastApplied`. That makes the consumer robust to duplicates **and** to the occasional out-of-order delivery after a relay restart.

## 10. Failure walk-through: every crash point

Timeline for one change:

```
t1  BEGIN
t2  UPDATE business row
t3  INSERT outbox row
t4  COMMIT                         <- point of no return
t5  relay reads the row
t6  relay produces to Kafka
t7  Kafka acks
t8  relay marks row published
```

| Crash / failure at                                                   | State afterwards                                  | Outcome                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Between t1 and t4                                                    | Transaction rolls back automatically              | **Nothing** exists: no change, no event. Correct.                                                                                                                                                                                                               |
| t4 COMMIT fails (connection lost, unknown)                           | Either committed or not; the client does not know | Client may retry the request: needs the business operation to be **idempotent** (idempotency key / version check). If committed, the event will be published once; a retry that applies again would create a second event (guard with a version or request id). |
| After t4, before t5                                                  | Row committed, relay not yet seen it              | Relay picks it up whenever it runs. **No loss.**                                                                                                                                                                                                                |
| t5–t6: relay dies before sending                                     | Row still unpublished                             | Next relay run sends it. No loss.                                                                                                                                                                                                                               |
| t6: Kafka unavailable, send times out                                | Row still unpublished (we mark only after ack)    | Relay retries with backoff; backlog grows; alert on lag.                                                                                                                                                                                                        |
| t6–t7: send succeeded but ack lost (timeout)                         | Message may be in Kafka; relay believes failure   | Relay retries: **duplicate** in Kafka. Same `event_id`. Consumer dedupes.                                                                                                                                                                                       |
| t7–t8: acked, relay dies before marking                              | Message in Kafka, row still unpublished           | After restart, row published **again**: duplicate. Consumer dedupes.                                                                                                                                                                                            |
| t8 marking fails (DB blip)                                           | Same as above                                     | Same duplicate.                                                                                                                                                                                                                                                 |
| Consumer crashes                                                     | Not an outbox problem                             | Offset commit + idempotence ([Stage 2](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md))                                                                                                                                               |
| Relay publishes row but Kafka topic missing / auth error (permanent) | Row can never be published                        | **Poison row**: must not block the rest (see below)                                                                                                                                                                                                             |

### Poison rows

A row that cannot ever be published (payload exceeds `max.message.bytes`, invalid topic mapping, serialization error) will be retried forever, and in a strictly ordered relay **blocks everything behind it**. Strategies: (1) validate at write time so poison rows cannot be inserted; (2) after N attempts, move the row to a `outbox_dead` table and alert (accepting that this breaks ordering for that aggregate, a conscious decision); (3) per-aggregate blocking only (skip the aggregate with a poison head, continue the others). Track `attempts` and `last_error` columns if you adopt (2) or (3).

## 11. Keeping the table small: cleanup and bloat

An outbox is a **queue implemented as a table**, and a hot queue table is a classic Postgres bloat trap.

**Why it matters.** Postgres uses MVCC: an `UPDATE` (setting `published_at`) or a `DELETE` leaves a **dead tuple** that must be vacuumed. A queue with high insert + update/delete churn creates many dead tuples; if autovacuum cannot keep up, or a long-running transaction pins the oldest snapshot (preventing cleanup), the table and its indexes **bloat**, the `SELECT` scans dead entries, and the relay slows down: a feedback loop.

Options:

| Strategy                                | How                                                                                               | Pros                                              | Cons                                                                         |
| --------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Flag + periodic delete**              | `UPDATE ... SET published_at = now()`; a job deletes rows older than N hours                      | Keeps recent history for debugging; simple        | Two writes per row (update + later delete); bloat if volume is high          |
| **Delete on publish**                   | Relay `DELETE`s rows after acked publish (`DELETE ... RETURNING`)                                 | One write per row; table stays tiny               | No history; a crash after publish and before delete republishes (still fine) |
| **Partition by time + drop**            | Range-partition on `created_at`; drop old partitions                                              | `DROP`/`DETACH` is instant, zero bloat, no vacuum | More DDL management (pg_partman or a cron)                                   |
| **Insert-only + external cursor (CDC)** | Debezium reads the WAL; the table is only ever inserted into and may be truncated/deleted in bulk | No relay UPDATEs at all                           | Needs CDC infrastructure ([note 3](./3.%20relay-polling-vs-cdc.md))          |

Practical guidance:

- Always keep the **partial index** `WHERE published_at IS NULL` (or an equivalent small hot set) so the relay's query cost is proportional to the _backlog_, not the history.
- Make cleanup **batched** (delete in chunks of a few thousand) to avoid long transactions and WAL spikes.
- Tune autovacuum on this table (lower `autovacuum_vacuum_scale_factor`, higher cost limit) if it is hot.
- Avoid long-running transactions elsewhere in the same database: they block vacuum from removing dead rows.
- Retain published rows for a short **audit/debug window** (hours to days) if the table is small, but remember: the outbox is not an event store; Kafka's retention ([Stage 2 retention note](../../../stage-2/learning/Kafka/5.%20kafka-retention.md)) is the replay history.

## 12. Isolation, locking and the transaction itself

- **Default isolation (READ COMMITTED) is sufficient** for the write path: atomicity of the two inserts/updates is guaranteed by the transaction, not by isolation level.
- **Visibility:** other connections (including the relay) do not see the outbox row until `COMMIT`. This is exactly what removes the visibility race of publish-before-commit.
- **Lock order:** update the aggregate row first, then insert into the outbox, as in 9.1, so per-aggregate commit order equals outbox id order.
- **Transaction duration:** keep it short; the outbox row is invisible until commit, so a long transaction delays its event and (for cursor-based polling) can cause skipped-gap anomalies.
- **Contention on the outbox:** inserts are append-only, so writers do not conflict with each other, only briefly on index pages and the identity sequence. The relay's `FOR UPDATE SKIP LOCKED` locks only rows it is processing, so it does not block writers.
- **Retries of the business transaction** on serialization failure/deadlock re-run both writes, which is correct: the first attempt rolled back entirely, including its outbox row.
- **Idempotency of the request itself** is separate: a client that retries a timed-out HTTP request can create a second change **and** a second event. Protect with an idempotency key stored in the same transaction, or optimistic concurrency (`WHERE version = $expected`).

## 13. Message id, keys, headers and schema evolution

- **`event_id` is assigned once, at write time**, and is the dedupe key for the life of the message. Do **not** generate ids in the relay and do **not** use the Kafka offset (a republish gets a new offset; dedupe by offset would fail). Use a UUID (v4 or time-ordered v7 for index locality) or a deterministic id derived from `(aggregate_id, version)` which gives natural dedupe and idempotent writes of the outbox itself.
- **Kafka key = `aggregate_id`.** Keep the partition count stable; changing it remaps keys and breaks per-key order across the change (Stage 2 key note).
- **Headers:** `event_id`, `event_type`, `schema_version`, trace context, `tenant_id`. Having the id in a header lets generic consumer middleware dedupe without parsing the body.
- **Topic routing:** map `aggregate_type` to a topic in the relay (config, not a DB column that anyone can change), so a typo cannot publish to a random topic.
- **Schema evolution:** treat the payload like an API. Additive changes only (new optional fields) within a major version; use a schema registry (Avro/Protobuf/JSON Schema) if available; include `schema_version`. Remember that **old unpublished rows may be published by a newer relay**, and old consumers may read new events: both directions must tolerate it.
- **Serialization at write vs at publish:** storing the already-serialized bytes in the row (`bytea`) pins the schema version at the time of the change; serializing in the relay uses the relay's current schema. Pick one deliberately; storing JSON and serializing in the relay is the common compromise.

## 14. Operating it: metrics and alerts

Measure these from day one:

| Metric                                                                            | Meaning                                          | Alert when                                  |
| --------------------------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------- |
| **Oldest unpublished age** (`now() - min(created_at) WHERE published_at IS NULL`) | Relay lag in time: the single best health signal | > a few seconds to a minute, sustained      |
| **Unpublished count** (backlog)                                                   | Depth                                            | growing monotonically                       |
| **Publish rate / batch size / latency**                                           | Throughput and Kafka health                      | drops to 0 while backlog > 0                |
| **Publish error rate** (by reason)                                                | Kafka down vs poison                             | any sustained errors                        |
| **Republish / duplicate rate**                                                    | How often the relay re-sends                     | spikes after relay restarts (informational) |
| **Dead-letter count**                                                             | Rows given up on                                 | > 0                                         |
| **Table size / dead tuples / autovacuum lag**                                     | Bloat                                            | table growing though backlog is small       |
| **Relay liveness** (heartbeat, leader status)                                     | Someone is actually running                      | no active relay                             |

Query for the key one:

```sql
SELECT coalesce(extract(epoch FROM now() - min(created_at)), 0) AS oldest_unpublished_seconds,
       count(*)                                                   AS unpublished
  FROM outbox
 WHERE published_at IS NULL;
```

(Relates to consumer lag thinking in [Stage 2 consumer lag](../../../stage-2/learning/consumer/4.%20kafka-consumer-lag.md): the outbox backlog is a _producer-side lag_ and deserves the same attention.)

## 15. Costs, limits and when not to use it

**Costs**

- One additional write per event, in the business transaction (latency and WAL volume grow slightly).
- An extra table to maintain, vacuum or partition.
- A relay to deploy, monitor and keep highly available.
- End-to-end latency from the poll interval.
- Duplicate handling in every consumer.

**Throughput.** A polling relay with batching handles thousands of events per second on one Postgres primary; beyond that, move to CDC, partition the relay, or reconsider whether the stream needs an outbox at all.

**Do not use it when**

- Kafka is already the single system of record for the data (EventPulse's `POST /events` → Kafka → sink path). There is no DB write to keep atomic.
- Loss of an occasional event is acceptable and volume is very high.
- The "event" is a pure read/telemetry side effect with no state change.

**Use it when**

- A DB change must reliably trigger messages (config changes, state machine transitions, orders, entitlements).
- Another system's correctness depends on seeing every change.
- You cannot tolerate phantom events from rolled-back transactions.

## 16. Variants and neighbours

- **Outbox via CDC without relay code:** Debezium reads inserts from the outbox table's WAL and publishes (the **Outbox Event Router** SMT shapes them). See [note 3](./3.%20relay-polling-vs-cdc.md).
- **Log-based message without a table:** PostgreSQL `pg_logical_emit_message()` writes a message into the WAL transactionally without a table; a logical-decoding consumer reads it. No bloat, but needs logical decoding and is less discoverable.
- **Inbox on the consumer side:** the mirror pattern, [note 4](./4.%20the-inbox-pattern.md).
- **Event sourcing:** the event table _is_ the state; outbox-like publishing still applies.
- **Listen-to-yourself / change-data-capture of business tables:** events are row diffs; works, but couples consumers to your schema.
- **Saga orchestration:** uses outbox + inbox per participant to make each step reliable.
- **Kafka Streams / transactions:** solve Kafka-to-Kafka exactly-once, not DB-to-Kafka ([delivery-semantics note 3](../delivery-semantics/3.%20kafka-transactions-and-exactly-once-semantics.md)).

## 17. EventPulse: tenant config events (S3-F4)

[design sketch, **[reasoning]**; the outbox is not implemented yet. The existing migrations in `db/migrations/` (events, tenant counters) are **[observed in source]** and set the style: numbered SQL files.]

**Requirement (S3-F4):** config changes that must also publish an event use a transactional outbox; first use is tenant config change events, later used for cache invalidation.

**Sketch**

1. **Migration `0005`**: `tenant_config` (tenant_id PK, settings columns, `version`) and `outbox` (as in section 5).
2. **Write path:** `PUT /tenants/:id/config` handler runs one transaction: `UPDATE tenant_config ... RETURNING version` then `INSERT INTO outbox` with `event_type = 'TenantConfigChanged'`, `aggregate_id = tenant_id`, payload `{tenantId, version, changed fields}`.
3. **Relay:** a polling loop (note 3) in the same service or a small worker, `acks=all`, idempotent producer, key = `tenant_id`, topic `tenant-config-changed`.
4. **Consumers:** e.g. an ingest-API cache invalidator that applies `version > cachedVersion` and ignores the rest. The version check is the inbox for a "last writer wins by version" use case ([note 4](./4.%20the-inbox-pattern.md) explains when a version check replaces an id table).
5. **Observability:** `outbox_oldest_unpublished_seconds`, `outbox_backlog`, `outbox_publish_errors_total` exported next to the existing sink/ingest metrics.
6. **Not part of it:** the raw event ingest path stays Kafka-only; no outbox there.

**Why this fits:** config changes are low-volume, high-importance, and a lost one silently leaves a component enforcing a stale limit; exactly the profile where the outbox's cost is trivial and its guarantee valuable.

## 18. Build checklist

- [ ] Outbox table in the **same database** as the business data; partial index on unpublished rows.
- [ ] Outbox insert in the **same transaction/connection** as the change; business `UPDATE` first.
- [ ] `event_id` generated at write time, unique, sent in header.
- [ ] Kafka key = aggregate id; topic mapping in relay config.
- [ ] Payload carries a per-aggregate `version`; schema version in headers.
- [ ] Relay: mark published **only after** broker ack; producer `acks=all`, idempotence on.
- [ ] Poison-row policy decided and implemented.
- [ ] Cleanup strategy (delete-on-publish, batched delete, or partition drop) and autovacuum tuning.
- [ ] Metrics: oldest unpublished age, backlog, errors; alert on lag.
- [ ] Consumers idempotent (inbox or version check).
- [ ] Test the crash points in section 10 (kill relay between send and mark; kill app between statements; Kafka down).

## 19. Common confusions

**"The outbox makes it exactly-once."** It makes _intent atomic_ and publication _at-least-once_. Exactly-once effect needs consumer dedupe.

**"I can use the Kafka offset as the message id."** A republish gets a new offset; use the `event_id` assigned at write time.

**"The sequence id is the commit order."** It is the _insert_ order. Concurrent transactions can commit out of id order; do not use `id > last_seen` as the only cursor without handling gaps.

**"A separate connection for the outbox insert is fine."** It re-creates the dual write. Same transaction, same connection.

**"I can publish from the request thread after commit as an optimization."** You may _also_ try, but the outbox must remain the source of truth, and the relay must still publish whatever was not marked. Two publishers per event is more duplicates and more races; most teams skip the optimisation.

**"The outbox table is my event store."** It is a transient buffer. Keep history in Kafka (retention) or an events table.

**"Mark published first, then send."** That is the at-most-once order: crash between = lost event. Always send, then mark.

## 20. Self-test questions

1. State precisely what the single transaction contains and why that removes the lost/phantom-event cases.
2. After COMMIT, what three components can fail, and what is the consequence of each?
3. Why is the relay's guarantee at-least-once and not exactly-once? Name the exact gap.
4. Why must `event_id` be generated at write time rather than by the relay?
5. Two concurrent transactions insert outbox rows with ids 10 and 11; 11 commits first. What can a cursor-based poller do wrong? Why is the same-aggregate case usually safe if the business `UPDATE` comes first?
6. Name three cleanup strategies and the main trade-off of each.
7. Which single metric best summarises relay health?
8. What is a poison row, and why can it block a strictly ordered relay?
9. Which parts of EventPulse should **not** use an outbox, and why?
10. Why does the idempotent Kafka producer not remove the relay's duplicates?

<details>
<summary>Answers (try first)</summary>

1. The business change and the outbox row. Both commit or neither does, so there is never a change without its pending event, nor an event for a rolled-back change.
2. Relay (rows wait; backlog), Kafka (publish fails; rows wait; relay retries), consumers (their own offset/idempotence handling). None creates inconsistency; only delay or duplicates.
3. The relay marks a row only after Kafka acks; a crash between ack and mark (or a lost ack) causes a republish.
4. So a republish carries the same id and consumers can dedupe. The relay may run many times for one row.
5. It may read 11, advance its cursor past 10, and skip 10 when it commits later. For the same aggregate, the business UPDATE row lock serializes the transactions, so the second cannot insert its outbox row until the first commits.
6. Flag + periodic delete (two writes, bloat), delete on publish (no history), time partition + drop (DDL management), CDC insert-only (needs infra).
7. Age of the oldest unpublished row.
8. A row that can never be published; a strict in-order relay keeps retrying it and nothing behind it moves.
9. The raw ingest path: Kafka is the record and there is no DB write to keep atomic with it.
10. Its dedupe is per producer session; a relay restart is a new session re-reading the same row.

## 21. Glossary and cheat sheet

| Term                             | Meaning                                                                     |
| -------------------------------- | --------------------------------------------------------------------------- |
| **Outbox table**                 | A table in the service's own DB that holds messages waiting to be published |
| **Relay / publisher**            | Process that moves outbox rows to the broker                                |
| **Aggregate**                    | The entity whose changes must stay in order (the Kafka key)                 |
| **Published flag**               | `published_at` marker set after a successful publish                        |
| **Poison row**                   | A row that can never be published successfully                              |
| **Gap problem**                  | Cursor pollers skipping rows that commit out of id order                    |
| **Event-carried state transfer** | Event contains the new state so consumers need no callback                  |
| **Backlog / relay lag**          | Unpublished rows / age of the oldest one                                    |

```
Write path :  BEGIN; UPDATE aggregate; INSERT outbox; COMMIT;   (never call Kafka here)
Relay      :  read unpublished -> send (acks=all) -> ONLY THEN mark/delete
Guarantee  :  atomic intent + at-least-once publish; consumers dedupe by event_id
Order      :  business UPDATE first; key = aggregate_id; version in payload
Clean up   :  partial index; delete-on-publish or partition+drop; tune autovacuum
Watch      :  oldest unpublished age, backlog, errors, relay liveness
```

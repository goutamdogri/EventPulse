# The Inbox Pattern

_Outbox note 4 of 4 in the Stage 3 learning notes. Read [note 1 (dual writes)](./1.%20the-dual-write-problem.md), [note 2 (the transactional outbox)](./2.%20the-transactional-outbox.md) and [note 3 (relay options)](./3.%20relay-polling-vs-cdc.md) first, plus the Stage 2 consumer notes on [offset commits](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md) and [rebalances](../../../stage-2/learning/consumer/2.%20kafka-consumer-rebalances.md). The outbox side guarantees a message is published **at least once**. The **inbox pattern** is its consumer-side mirror: record the ids of processed messages **in the same database transaction as the side effect**, so a message seen twice changes the world once. This note covers the mechanism, the exact SQL, concurrency, retention of the dedupe records, the cases where a simpler idempotent write or a version check replaces an inbox table, side effects that cannot join a DB transaction, and how the outbox and inbox compose end to end._

**What was run.** **No labs were run for this note.** Everything is **[reasoning]** from Postgres and Kafka semantics, or **[observed in source]** where the repo is cited. The EventPulse sink's `ON CONFLICT (event_id) DO NOTHING` insert is existing code; the generic `inbox` table is a design sketch that does not exist in the repo yet.

## 1. TL;DR

- **Why:** the outbox relay, Kafka producer retries, consumer rebalances and offset-commit failures all produce **duplicates**. At-least-once is the best honest delivery; the effect must be made safe by the **consumer**.
- **Inbox pattern:** the consumer keeps a table of message ids it has processed. For each message, in **one database transaction**: (1) `INSERT` the message id into the inbox, (2) if that insert **did** insert a row, apply the side effect, (3) `COMMIT`. If the id was already there, **skip** the side effect. Then commit the Kafka offset.
- **The load-bearing property is atomicity:** the id marker and the business effect live in the **same database** and commit together. Either both exist (processed) or neither (will be retried). If they were separate, a crash between them would either lose the effect or repeat it.
- It makes the consumer **idempotent**; combined with at-least-once delivery that gives an **exactly-once effect**.
- A **unique constraint on the message id** is the enforcement mechanism, and it also serializes two concurrent deliveries of the same message.
- **Simpler alternatives** often suffice: a naturally idempotent write (`INSERT ... ON CONFLICT DO NOTHING`, upsert with `WHERE version < new`), where the target table's own key **is** the inbox (this is exactly what the EventPulse sink does with `event_id`).
- **Limits:** the effect must be in the **same database** as the inbox. Non-transactional effects (email, HTTP call, another DB) need idempotency keys downstream or an outbox of their own.
- **Retention:** inbox rows can be deleted once no duplicate can possibly arrive any more (older than the topic retention / maximum redelivery horizon). Unbounded growth is the main operational cost.

> **One-line version:** _Before you act on a message, write "I handled this" in the same transaction as the action, so a second copy finds the note and does nothing._

## 2. The mental model

A hotel front desk processes **faxed booking requests**. The fax machine sometimes sends the same fax twice. The clerk keeps a **guest book**: for each fax, the clerk writes the fax's reference number **on the same page, in the same pen stroke**, as the room allocation. A second copy of the fax arrives: the clerk checks the book, finds the reference number, and says "already done".

| Hotel                                                              | Inbox pattern                                                   |
| ------------------------------------------------------------------ | --------------------------------------------------------------- |
| Fax reference number                                               | Message id (`event_id`)                                         |
| Guest book                                                         | Inbox table (or the target table's unique key)                  |
| Writing the reference and the room allocation in one stroke        | One DB transaction                                              |
| Fax arrives twice                                                  | At-least-once delivery (relay republish, rebalance, retry)      |
| "Already done"                                                     | Insert affected 0 rows: skip the effect                         |
| Clerk writes the allocation on a **different** sheet than the book | Separate stores: a crash in between double-books or never books |
| Old fax numbers are thrown away after the booking window closes    | Inbox retention                                                 |

## 3. Why the consumer needs this

Where duplicates enter a consumer's input (see also [delivery-semantics note 2](../delivery-semantics/2.%20why-duplicates-are-inevitable-two-generals.md)):

1. **Outbox relay republish** ([note 2](./2.%20the-transactional-outbox.md), [note 3](./3.%20relay-polling-vs-cdc.md)): crash between Kafka ack and "mark published".
2. **Producer retry without session identity:** a restarted producer is a new session and the idempotent producer's per-session dedupe does not apply ([delivery-semantics note 4](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md)).
3. **Consumer redelivery:** the consumer processed a message, then crashed or lost its partition **before the offset commit**, so the next owner re-reads it ([offset commits](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md), [rebalances](../../../stage-2/learning/consumer/2.%20kafka-consumer-rebalances.md)).
4. **Offset reset / replay:** an operator rewinds the group to reprocess, or retention-bound replay after a bug fix.
5. **Upstream duplicates:** the original client retried an HTTP request and produced two events.

Kafka's own exactly-once machinery (transactions, `read_committed`) covers **Kafka-to-Kafka** flows ([delivery-semantics note 3](../delivery-semantics/3.%20kafka-transactions-and-exactly-once-semantics.md)). When the consumer's output is **a database write**, the offset commit and the DB commit are again a **dual write** (consumer-side): the same two-systems problem as [note 1](./1.%20the-dual-write-problem.md), mirrored. The inbox is how you make it safe without distributed transactions:

> Consumer-side dual write: "DB write, then Kafka offset commit". A crash between them replays the message. Make the DB write **idempotent**, so the replay is harmless.

## 4. The core idea: the marker and the effect commit together

Consider the naive "check then act" consumer using **separate** stores:

```
if (!seen(messageId))          // read marker store
   applyEffect(message)        // write to the DB
   markSeen(messageId)         // write marker store  (maybe Redis, maybe another table/connection)
```

Failure analysis:

- Crash **after** `applyEffect`, **before** `markSeen` → on redelivery the effect is applied **twice**.
- Reverse the order (`markSeen` first) → a crash before `applyEffect` marks the message seen but the effect **never happens** (lost).
- Two concurrent copies both pass `seen()` before either marks → both apply it (a **race**).

The inbox fixes all three by moving the marker into the **same transaction** as the effect, and making the marker write a **conflict-detecting insert**, not a read:

```
BEGIN
  INSERT INTO inbox(message_id, ...) ON CONFLICT DO NOTHING      -- the marker AND the race arbiter
  if 0 rows inserted: COMMIT; skip           -- duplicate
  else: apply effect (same transaction)
COMMIT                                       -- marker + effect: both or neither
```

- Crash mid-transaction → both roll back → redelivery sees no marker and does the full work. **No loss, no double effect.**
- Duplicate after success → marker exists → insert affects 0 rows → skipped.
- Concurrent duplicates → the unique index makes one wait for the other ([section 8](#8-concurrency-two-copies-of-the-same-message-at-once)).

This is exactly the **mirror of the outbox**: the outbox puts _"please publish"_ in the same transaction as the producer's state change; the inbox puts _"I have processed this"_ in the same transaction as the consumer's state change. Both use the **local ACID transaction** as the only atomic unit.

## 5. The inbox table

Minimal:

```sql
CREATE TABLE inbox (
  consumer      text        NOT NULL,   -- logical consumer / handler name (so several handlers can share the table)
  message_id    uuid        NOT NULL,   -- the producer-assigned event_id (outbox event_id)
  processed_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (consumer, message_id)
);
CREATE INDEX inbox_processed_at_idx ON inbox (processed_at);   -- for retention deletes
```

Design notes:

- **Primary key `(consumer, message_id)`**: the same event can legitimately be handled by _different_ consumers (a cache invalidator and a search indexer) in the same database; each has its own dedupe scope. If each consumer owns its own database/schema, `message_id` alone is enough.
- **No payload stored** in the minimal form: the inbox only records _that_ it was handled. (The "inbox as a queue" variant in [section 13](#13-inbox-variants-and-alternatives) stores the payload too.)
- **`processed_at`** supports retention cleanup and debugging.
- **Optional columns:** `topic`/`partition`/`offset` for forensic tracing; `result` (e.g. `applied` / `ignored_stale`); `trace_id`.
- **Same database as the side effect.** That is the requirement, not a suggestion.
- **Row size is tiny** (about 40–60 bytes plus index), so tens of millions of rows are manageable, but not unlimited: see retention.

## 6. The consumer algorithm, step by step

```ts
// Teaching sketch: one message, one transaction (node-postgres style)
async function handle(pool: Pool, msg: KafkaMessage): Promise<void> {
  const messageId = header(msg, "event-id"); // assigned by the outbox at write time
  const event = JSON.parse(msg.value!.toString());

  const client = await pool.connect();
  try {
    await client.query("BEGIN");

    // 1. Claim the message id. The unique key decides, atomically, whether we are first.
    const claim = await client.query(
      `INSERT INTO inbox (consumer, message_id) VALUES ($1, $2)
       ON CONFLICT (consumer, message_id) DO NOTHING`,
      ["config-cache-updater", messageId],
    );

    if (claim.rowCount === 0) {
      // 2a. Duplicate: someone already committed this message. Do nothing.
      await client.query("COMMIT"); // nothing to undo; ends the transaction
      metrics.duplicatesSkipped.inc();
      return; // caller still commits the Kafka offset
    }

    // 2b. First time: apply the effect in the SAME transaction.
    await client.query(
      `INSERT INTO tenant_config_cache (tenant_id, version, settings)
       VALUES ($1, $2, $3)
       ON CONFLICT (tenant_id) DO UPDATE
         SET version = EXCLUDED.version, settings = EXCLUDED.settings
         WHERE tenant_config_cache.version < EXCLUDED.version`, // stale-guard, see section 16
      [event.tenantId, event.version, event.settings],
    );

    // 3. Marker and effect commit together.
    await client.query("COMMIT");
  } catch (e) {
    await client.query("ROLLBACK"); // marker rolled back too: retry will redo it all
    throw e; // do NOT commit the Kafka offset
  } finally {
    client.release();
  }
}
// After handle() returns without throwing: commit/resolve the Kafka offset (consumer note 3).
```

Walkthrough of the invariants:

- **Claim first, then effect, one transaction.** `rowCount === 0` means the id already exists (committed by an earlier delivery, or by a concurrent one that has just committed).
- **A thrown error always rolls back the marker**, so a retry is a clean first attempt.
- **Offset commit comes last,** after the DB transaction commits ([offset commits note](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md) section 4: "work, then commit → at-least-once").
- **The duplicate path also returns success**, so the consumer proceeds and commits the offset. A duplicate is not an error.

## 7. Why the order inside the transaction matters

Within the transaction you could write the effect first and the marker second. Both orders are atomic at commit, so why prefer **marker first**?

1. **Conflict detection up front.** If the marker insert conflicts, you know **before doing any work** (and before taking locks on business rows) that this is a duplicate. No wasted effect, no side-effect rollback.
2. **Concurrency arbitration.** With the marker first, the unique index serializes duplicates at the earliest point ([section 8](#8-concurrency-two-copies-of-the-same-message-at-once)). With the effect first, two concurrent copies could both execute the effect (and contend on business-row locks, or both succeed on a non-unique effect) before one fails at the marker insert and rolls everything back.
3. **Non-DB effects:** if part of the work cannot be rolled back (a call to another service), you want certainty you are the first _before_ doing it, not after ([section 14](#14-side-effects-that-cannot-join-the-transaction)).
4. **Cheaper skip path.** Duplicates cost one index probe.

(Where the effect is itself a unique-key insert, the effect can _be_ the marker; see [section 13.1](#131-the-target-tables-own-key-is-the-inbox-recommended-when-it-fits).)

## 8. Concurrency: two copies of the same message at once

When can two copies be processed simultaneously? A rebalance can hand the same partition to a new consumer while the old one is still finishing its last batch ("zombie" consumer, [rebalances](../../../stage-2/learning/consumer/2.%20kafka-consumer-rebalances.md)); two different partitions or topics may carry the same logical event; a relay bug or CDC failover may emit a duplicate quickly after the first.

What Postgres does when two transactions run `INSERT ... ON CONFLICT DO NOTHING` for the **same** key:

```
Tx1: INSERT (c, M) ON CONFLICT DO NOTHING   → inserts the row (uncommitted)
Tx2: INSERT (c, M) ON CONFLICT DO NOTHING   → finds an in-doubt conflicting row;
                                               WAITS for Tx1 to finish
Tx1: ...applies effect...; COMMIT           → row (c, M) is now committed
Tx2: wakes up → sees committed conflict → inserts nothing → rowCount = 0 → skip
```

If Tx1 had **rolled back** instead, Tx2 would proceed and insert the row, then apply the effect. Exactly one transaction ever applies the effect, and the winner is decided by the unique index, with no application-level locking. Properties:

- **Safe under READ COMMITTED** (the default): this behaviour comes from the unique index, not from the isolation level.
- **Tx2 blocks for Tx1's whole transaction** (the marker row's uniqueness is checked against the in-progress insertion). Keep the transaction short.
- **Deadlocks** are possible only if different consumers take marker and business-row locks in different orders across messages. A consistent order (marker first, then business rows in a fixed order) avoids them.
- **Do not use `SELECT ... WHERE message_id = $1` to check first.** Two transactions can both see "not found" and both proceed (a classic check-then-act race). The insert is the check.

## 9. Interaction with Kafka offset commits

The inbox does not replace offset commits; it makes them **safe to be late or lost**.

```
poll message ─► BEGIN; claim id; effect; COMMIT ─► commit Kafka offset
                         (atomic in Postgres)         (separate system; may fail)
```

| Crash point                                       | Result                                                    | Why it is safe                                             |
| ------------------------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------- |
| Before DB COMMIT                                  | DB rolled back; offset not committed                      | Redelivered, processed fresh                               |
| After DB COMMIT, before offset commit             | Message redelivered                                       | Inbox finds the id → skip; offset advances                 |
| Offset commit succeeded, DB commit never happened | Impossible if you commit offsets only after the DB commit | This is the order rule (at-least-once, never at-most-once) |
| Rebalance revokes partition mid-batch             | New owner reprocesses from the last committed offset      | Duplicates absorbed by the inbox                           |

Rules:

- **Never commit the offset before the DB commit.** That would make delivery at-most-once and the inbox could not recover the loss.
- **Offsets and inbox are independent safety nets.** The inbox does not need to know about offsets; a replay from an earlier offset is simply a stream of duplicates.
- Auto-commit based on "message was delivered to the handler" is **dangerous** here; commit manually after the transaction ([offset commits note](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md) section 5).
- Alternative **"transactional offset store"**: store the consumed offset in the **same DB transaction** as the effect, and on assignment seek to the stored offset. That removes the dual write from the consumer entirely (offsets live in the DB) and gives exactly-once _processing_ for DB sinks without per-message ids. It requires custom assign/seek handling and gives up Kafka's group offset tracking and lag tooling; it is the other classic design, and worth knowing.

## 10. Failure walk-through: every crash point

For one message M with id `x`:

```
a  poll M
b  BEGIN
c  INSERT inbox(x)            (claim)
d  apply effect
e  COMMIT
f  commit Kafka offset
```

| Crash / failure at                                                    | DB state                     | Kafka state           | Next delivery of M                                                | Final effect                                                                                                                                                                                         |
| --------------------------------------------------------------------- | ---------------------------- | --------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a–d                                                                   | Rolled back automatically    | offset not committed  | Fresh attempt                                                     | Applied **once**                                                                                                                                                                                     |
| e fails (connection drops, outcome unknown)                           | Committed **or** rolled back | offset not committed  | If committed: inbox has `x` → skip. If rolled back: fresh attempt | **Once** either way                                                                                                                                                                                  |
| Between e and f                                                       | Committed                    | offset not committed  | Inbox has `x` → skip                                              | **Once**                                                                                                                                                                                             |
| f fails                                                               | Committed                    | offset not committed  | Skip                                                              | **Once**                                                                                                                                                                                             |
| Duplicate arrives after f (relay republish; replay)                   | Inbox has `x`                | offset past it or not | Skip                                                              | **Once**                                                                                                                                                                                             |
| Effect throws a **non-retryable** error (bad data)                    | Rolled back (marker too)     | stuck unless handled  | Retried forever → poison                                          | Needs DLQ policy: after N tries, write to a dead-letter and **then** mark/skip ([Stage 2 DLQ notes in offset commits §11](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md)) |
| Inbox row inserted, effect succeeded, but the **COMMIT** itself fails | Rolled back                  | not committed         | Retry                                                             | **Once**                                                                                                                                                                                             |

No row in the table produces zero or two effects. That is the exactly-once _effect_ claim; it holds **only if the effect is entirely inside the same DB transaction**.

## 11. What is the message id?

The inbox is only as good as the id. Requirements: **stable** across duplicates, **unique** per logical message, **available** to the consumer.

| Candidate                                                                              | Verdict                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Producer-assigned `event_id` (UUID) written once at the source** (outbox `event_id`) | **Best.** Survives relay republish, producer restart, replay. Put it in a Kafka **header** (and/or the body)                                                                                                                        |
| **Deterministic id**, e.g. hash or `(aggregate_id, version)`                           | Also good; derives the same id for the same logical change even if regenerated                                                                                                                                                      |
| **Kafka coordinates `(topic, partition, offset)`**                                     | **Wrong for dedupe of producer/relay duplicates:** a republished message gets a _different_ offset. Right _only_ for detecting redelivery to the _same_ consumer group of the _same_ record (the transactional-offset-store design) |
| **Message key**                                                                        | Not unique (many messages share a key)                                                                                                                                                                                              |
| **Timestamp**                                                                          | Not unique                                                                                                                                                                                                                          |
| **Hash of the body**                                                                   | Fragile: two legitimately identical updates (e.g. the same value set twice) would be wrongly merged; use only if "same content = same message" is truly the intent                                                                  |
| **Client request id from the original API call**                                       | Good for end-to-end idempotency if the API accepts an `Idempotency-Key`; propagate it as the event id                                                                                                                               |

Rule: **generate once, as early as possible (at the outbox write), and carry it unchanged through every hop.** In EventPulse the ingest API assigns/accepts an `event_id` for each event, which is what the sink's unique constraint uses.

## 12. Retention: how long do you keep inbox rows?

The inbox only needs to remember an id **as long as a duplicate of it could still arrive.** Beyond that, the row is dead weight.

Upper bound on "could still arrive" (take the maximum that applies):

- **Kafka topic retention** (and compaction behaviour): a consumer can only re-read what the topic still holds ([retention note](../../../stage-2/learning/Kafka/5.%20kafka-retention.md)).
- **Maximum consumer downtime / lag** you tolerate before a rewind or reset.
- **Relay republish horizon**: how old an unpublished outbox row can become and still be sent (hours, if the relay was down).
- **Operator replays**: if people can rewind a group by days, the window must cover it, or you must clear/disable dedupe consciously for the replay.

Strategies:

| Strategy                                     | How                                                                            | Notes                                                                                                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Time-based delete**                        | `DELETE FROM inbox WHERE processed_at < now() - interval '14 days'` in batches | Simple; choose the interval ≥ topic retention + safety margin                                                                                                    |
| **Partitioned by time, drop old partitions** | Range partition on `processed_at`; drop expired partitions                     | No bloat, instant; the unique key must include the partition key, so dedupe is only guaranteed **within** the live window: acceptable because that is the intent |
| **Natural-key dedupe (no inbox)**            | The target table's unique key never expires                                    | Strongest, and no cleanup, when it applies ([section 13.1](#131-the-target-tables-own-key-is-the-inbox-recommended-when-it-fits))                                |
| **Keep forever**                             | Never delete                                                                   | Fine for small volumes (config events); not for high volume                                                                                                      |

Consequences to understand:

- If you delete an id and a **very late** duplicate then arrives, the effect is applied **again**. Pick the window knowing that.
- Retention cleanup is a mass `DELETE`: do it in **batches** with a small `LIMIT`, off-peak, and watch autovacuum (same bloat reasoning as the [outbox](./2.%20the-transactional-outbox.md#11-keeping-the-table-small-cleanup-and-bloat)).
- Index size grows with the window: estimate `rate × window × ~80 bytes`. At 1,000 msg/s and 7 days that is ~600 M rows, i.e. tens of GB: at that scale prefer partitioned drops or natural-key dedupe.

## 13. Inbox variants and alternatives

### 13.1 The target table's own key is the inbox (recommended when it fits)

If the side effect is "insert a row whose primary/unique key **is** the message id", then the effect is its own marker:

```sql
INSERT INTO events (event_id, ...) VALUES (...)
ON CONFLICT (event_id) DO NOTHING;
```

- One statement, one transaction, no extra table, no retention problem, no extra write.
- `rowCount` / `RETURNING` tells you whether it was new or a duplicate.
- **This is what the EventPulse sink already does** ([batch-writer.ts](../../../../services/consumer-sink/src/sink/batch-writer.ts)): `ON CONFLICT (event_id) DO NOTHING`, with `attempted - inserted` counted as duplicates.

Use a separate inbox table only when the effect is **not** a keyed insert (updates, counters, multi-table changes, calls that need a "ran once" guard).

### 13.2 Idempotent upsert guarded by a version (last-writer-wins)

For "set current state" effects (config cache, a projection of the latest tenant settings):

```sql
INSERT INTO tenant_config_cache (tenant_id, version, settings) VALUES ($1, $2, $3)
ON CONFLICT (tenant_id) DO UPDATE SET version = EXCLUDED.version, settings = EXCLUDED.settings
WHERE tenant_config_cache.version < EXCLUDED.version;
```

- A duplicate (same version) updates nothing; an **older** event (out-of-order) is ignored too.
- **Idempotent and order-tolerant** without any id table. Requires a **monotonic per-aggregate version** in the payload (that is why [note 2](./2.%20the-transactional-outbox.md#6-what-goes-in-the-row-the-event-design) puts one there).
- **Not enough** for effects that **accumulate** (counters, balances, append-only logs): applying `+5` twice gives `+10`; use the inbox, or make the delta idempotent by id.

### 13.3 Counters and aggregates

`UPDATE tenant_counters SET n = n + $1` is **not idempotent**. Pair it with the inbox marker in the same transaction (or derive the counter from a deduped source table). EventPulse's per-tenant counters (`0003_tenant_counters.sql`) are exactly this category; they must be updated **only for rows actually inserted** (use `RETURNING` count, not the attempted count) so that duplicates do not inflate them.

### 13.4 Inbox as a durable queue (store-then-process)

Some designs store the **whole message** in the inbox table on receipt (and commit the Kafka offset right away), then process it asynchronously from the table (a mirror of the outbox's polling relay, using `SKIP LOCKED` as in [note 3](./3.%20relay-polling-vs-cdc.md)):

```sql
CREATE TABLE inbox_queue (message_id uuid PRIMARY KEY, payload jsonb, status text, received_at timestamptz, ...);
```

Pros: fast acks to Kafka, retries and parking inside the DB, no head-of-line blocking of the partition. Cons: you have rebuilt a job queue, ordering needs care, and the table is a second store of the same data. Use when processing is slow/variable and Kafka partition blocking hurts; otherwise the simple inbox is enough.

### 13.5 Transactional offset store

Described in [section 9](#9-interaction-with-kafka-offset-commits): persist offsets with the effect. Exactly-once processing for DB sinks with no per-message ids; costs custom rebalance/seek logic.

### 13.6 Redis / cache-based dedupe (`SETNX id`)

Fast, but the marker lives in a **different system** from the effect, so you are back to the dual write of [section 4](#4-the-core-idea-the-marker-and-the-effect-commit-together) (crash between effect and marker, or marker and effect). Acceptable only as a **best-effort filter in front of** a transactional dedupe, never as the guarantee.

### 13.7 Choosing

```
Is the effect a keyed insert (id is the key)?           → ON CONFLICT DO NOTHING on the target (13.1)
Is it "set latest state" with a monotonic version?      → versioned upsert (13.2)
Does it accumulate or touch several tables?             → inbox table + effect in one tx (this note)
Is processing slow / needs async retries?               → inbox as a queue (13.4)
Is the effect outside this DB?                          → idempotency key downstream / outbox (section 14)
```

## 14. Side effects that cannot join the transaction

The atomic marker-plus-effect trick requires the effect to be **inside the same database transaction**. Some effects are not:

- sending an email or SMS;
- calling an HTTP API (payment provider, another microservice);
- writing to a **different** database, a cache, or a search index;
- publishing another Kafka message (here the Kafka transaction + offset in the consume-transform-produce loop is the tool, [delivery-semantics note 3](../delivery-semantics/3.%20kafka-transactions-and-exactly-once-semantics.md), or an **outbox** in this consumer's DB).

Options, in order of preference:

1. **Make the external call idempotent** and pass the message id as an **idempotency key** (`Idempotency-Key: <event_id>`; most payment APIs support this). Then a duplicate call is harmless, and the inbox marker only avoids needless calls. This is the robust answer.
2. **Outbox the side effect:** inside the transaction, write an **outbox row** "send email X" (keyed by the message id); the relay or worker performs the call at-least-once and the downstream is idempotent. The consumer's transaction stays local and atomic (the outbox pattern applied to the consumer's own output).
3. **Order the steps and accept a gap:** claim marker (commit), do the call, record completion; this gives _at-most-once_ if you crash after the claim, or _at-least-once_ with a completion state machine (`received → in_progress → done`) and a recovery job for stuck `in_progress` rows. Needs a timeout-based reclaim and still duplicates the call in the ambiguity window unless the downstream is idempotent.
4. **Accept duplicates** when harmless (an idempotent cache refresh, an informational notification).

Key point: the inbox gives **exactly-once effect only for effects in its own database.** For everything else the guarantee is **at-least-once + downstream idempotency**.

## 15. Batch consumers

High-throughput consumers (like the EventPulse sink, which writes **chunks**) process many messages per transaction. The same principle applies per batch:

```sql
-- one transaction per batch
WITH incoming AS (SELECT * FROM unnest($1::uuid[], $2::jsonb[]) AS t(id, payload)),
fresh AS (
  INSERT INTO inbox (consumer, message_id)
  SELECT 'projector', id FROM incoming
  ON CONFLICT DO NOTHING
  RETURNING message_id
)
-- apply the effect only for ids that were actually new
INSERT INTO projection (...) SELECT ... FROM incoming JOIN fresh ON fresh.message_id = incoming.id;
```

Key points:

- `RETURNING` from the marker insert gives **exactly the new ids**; apply the effect only to those.
- **Within-batch duplicates** (the same id twice in one batch) are also collapsed: `ON CONFLICT DO NOTHING` inserts one and skips the other (use `DISTINCT ON`/dedupe first if the statement could hit the same key twice in an `ON CONFLICT DO UPDATE` — that variant errors).
- **Commit offsets for the whole batch only after the transaction commits**; a crash replays the batch and the inbox absorbs it.
- If the effect is itself `INSERT ... ON CONFLICT (event_id) DO NOTHING` (13.1) you do not need the inbox CTE at all: the existing sink pattern is already the batched inbox.
- **Count duplicates, do not hide them:** `attempted - inserted` is a useful health metric (a spike means rebalances, relay restarts or replays).

## 16. Ordering and the inbox

The inbox deduplicates; it **does not order**.

- Per-key order comes from Kafka (key → partition → single consumer in the group), as in the [consumer groups note](../../../stage-2/learning/consumer/1.%20kafka-consumer-groups.md).
- **Out-of-order after a duplicate/replay:** a redelivery of an older event can arrive **after** newer ones were applied. The inbox would skip it only if the id is **still remembered**; if the id was already purged it would be applied and could **overwrite newer state**.
- Defence: **version guards** on state-setting effects (`WHERE current.version < incoming.version`, [13.2](#132-idempotent-upsert-guarded-by-a-version-last-writer-wins)). Version guard + inbox together make the effect both idempotent and monotonic.
- For event-stream effects (append to history), apply in arrival order and rely on the inbox for dedupe, with stable ids.
- **Gaps:** if you require every version `n` before `n+1`, a missing one means a stalled aggregate; decide whether to wait, park, or fetch current state (this is a business policy, not an inbox feature).

## 17. Outbox + inbox: the full picture

```
 Service A (producer)                                  Kafka                    Service B (consumer)
┌─────────────────────────────┐                  ┌──────────────┐          ┌──────────────────────────────┐
│ BEGIN                       │                  │              │          │ poll message (event_id = x)  │
│  UPDATE business row        │   relay          │  topic       │          │ BEGIN                        │
│  INSERT outbox (event_id=x) │ ───────────────► │  key=agg id  │ ───────► │  INSERT inbox(x) ON CONFLICT │
│ COMMIT   (atomic intent)    │  at-least-once   │              │          │   DO NOTHING                 │
└─────────────────────────────┘  (may repeat x)  └──────────────┘          │  if new: apply effect        │
                                                                           │ COMMIT   (atomic effect)     │
                                                                           │ commit Kafka offset          │
                                                                           └──────────────────────────────┘
```

Guarantees by hop:

| Hop                          | Mechanism                                                        | Guarantee                                                                                   |
| ---------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Business change → outbox row | Local DB transaction                                             | **Atomic intent**: no lost or phantom events ([note 2](./2.%20the-transactional-outbox.md)) |
| Outbox → Kafka               | Relay: send then mark ([note 3](./3.%20relay-polling-vs-cdc.md)) | **At-least-once**, per-key order                                                            |
| Kafka → consumer             | Poll; offset commit after the DB commit                          | **At-least-once**                                                                           |
| Consumer → its DB            | Inbox marker + effect in one tx                                  | **Idempotent**                                                                              |
| End to end                   | Outbox + at-least-once + inbox                                   | **Exactly-once effect** (effectively once, within the DB)                                   |

This is the concrete form of the sentence from the delivery-semantics series: **exactly-once effect = at-least-once delivery + idempotent processing**. The outbox removes loss on the producer side; the inbox removes duplication on the consumer side; neither needs distributed transactions.

What still can go wrong, and where it is handled:

- A **poison message** → DLQ policy ([offset commits note](../../../stage-2/learning/consumer/3.%20kafka-consumer-offset-commits.md) §11).
- A **late duplicate beyond retention** → version guards, natural keys.
- **Non-DB side effects** → idempotency keys ([section 14](#14-side-effects-that-cannot-join-the-transaction)).
- **Out-of-order** → versions ([section 16](#16-ordering-and-the-inbox)).
- **Clock/time semantics** → use event time fields explicitly, not processing time.

## 18. Costs and operations

**Costs**

- One extra insert (and index maintenance) per message; roughly doubles single-row writes for tiny effects. Batching amortizes it.
- Inbox table growth, cleanup jobs, autovacuum attention.
- Transaction scope: the DB transaction now spans "claim + effect", so slow effects lengthen lock holding (marker row held until commit).
- Extra concept for every consumer team to implement correctly (a shared library/middleware helps: `withInbox(consumerName, messageId, tx => ...)`).

**What to monitor**

| Metric                                        | Why                                                                                 |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Duplicates skipped / total**                | Health signal: baseline near zero; spikes after rebalances, relay restarts, replays |
| **Inbox size and oldest row age**             | Retention working?                                                                  |
| **Processing latency inside the transaction** | Long ones lengthen lock waits                                                       |
| **Lock waits on the inbox unique index**      | Concurrent duplicate processing (rebalance storms)                                  |
| **Cleanup job duration / rows deleted**       | Bloat and window sanity                                                             |
| **DLQ count**                                 | Non-retryable failures                                                              |

**Testing** (cheap and high-value; none run here): process the same message twice and assert the effect happened once; kill the consumer between COMMIT and the offset commit; run two consumers on the same message concurrently; replay an older event after a newer one and assert state is not regressed; purge an id and confirm the stated retention behaviour.

## 19. EventPulse: where the inbox idea already lives and where it is needed

**Already present [observed in source].** The consumer sink ([batch-writer.ts](../../../../services/consumer-sink/src/sink/batch-writer.ts)) writes each chunk with `INSERT ... SELECT FROM unnest(...) ON CONFLICT (event_id) DO NOTHING` in one transaction and commits the Kafka offset only afterwards. That is the **inbox pattern in its simplest form** (13.1): the `events` table's unique `event_id` is the marker, the insert is the effect, and `attempted - inserted` is the duplicate count. No separate inbox table is needed there, and none should be added.

**Where an explicit or version-based inbox is needed [design, **[reasoning]**].**

1. **S3-F4 tenant config consumers** (e.g. a cache invalidator/updater in the ingest API): use the **versioned upsert** (13.2). Duplicates and stale events are both ignored without an id table. If the consumer also records an audit row or increments a counter per change, add a small `inbox` table keyed by `(consumer, event_id)` in the same transaction.
2. **Derived counters** (`tenant_counters`): update **only for newly inserted rows** in the same transaction as the event insert (use the inserted count, not the attempted count), so replays never inflate them.
3. **Any future consumer that emits an outbox row** from its own transaction (chains): inbox marker + business effect + outbox row, all in one transaction (the "transactional middleman").

**Retention rule of thumb for EventPulse:** keep inbox ids at least as long as the longest Kafka topic retention for the topic being consumed plus a margin; for the `events` table the permanent unique key makes this a non-issue.

## 20. Build checklist

- [ ] Message id assigned once at the source (outbox `event_id`) and carried in a header.
- [ ] Prefer the target table's unique key or a versioned upsert; add an `inbox` table only when needed.
- [ ] Inbox insert is `ON CONFLICT DO NOTHING` (never `SELECT` then `INSERT`).
- [ ] Marker and effect in **one transaction, one database**; marker first.
- [ ] Offset committed **only after** the DB commit.
- [ ] Duplicate path returns success (no error, offset advances) and is **counted**.
- [ ] Retention window ≥ max redelivery horizon; batched cleanup or partition drop.
- [ ] Version guard on state-setting effects.
- [ ] Non-DB effects use downstream idempotency keys or their own outbox.
- [ ] Poison-message/DLQ policy defined.
- [ ] Tests: double delivery, crash between COMMIT and offset commit, concurrent duplicates, stale event.

## 21. Common confusions

**"Kafka exactly-once means I don't need this."** Kafka EOS covers Kafka-to-Kafka. A DB sink is outside it; you need an idempotent effect.

**"I check `SELECT ... WHERE id = ?` first, then insert."** That is a check-then-act race. Use the unique-key insert as the check.

**"Store the processed id in Redis."** Different system than the effect: another dual write. Only a pre-filter.

**"Use the Kafka offset as the id."** A relay or producer duplicate has a new offset. Use the producer-assigned `event_id`.

**"The inbox gives ordering."** It only deduplicates; ordering comes from keys/partitions and version guards.

**"The inbox protects my HTTP call."** Only if the call is inside the same DB transaction, which it cannot be. Use an idempotency key at the callee.

**"Once I have an inbox I can commit the offset early."** No: early commit makes loss possible; the inbox only removes duplication.

**"I can keep inbox rows forever."** Fine at low volume; at high volume it is the main operational cost.

**"A duplicate is an error, so I should DLQ it."** A duplicate is normal, expected and silently skipped (and counted).

## 22. Self-test questions

1. State the single property that makes the inbox correct, and what breaks if the marker lives in a different store.
2. Why is `INSERT ... ON CONFLICT DO NOTHING` preferred over `SELECT` then `INSERT`? Describe the race it avoids.
3. Walk through every crash point between BEGIN and the Kafka offset commit and give the end result for each.
4. Why must the Kafka offset be committed after the DB commit? What if the order is reversed?
5. Two copies of the same message are processed concurrently by two consumers. What does Postgres do, and who applies the effect?
6. Why is the Kafka offset a bad message id for dedupe, and when is it a right one?
7. How long should you keep inbox rows? What happens if you purge too early?
8. Why does the EventPulse sink not need a separate inbox table?
9. A counter is incremented per event. Why is `n = n + 1` unsafe on a replay, and how do you fix it?
10. Name two side effects the inbox cannot make exactly-once and the right tool for each.
11. When is a version-guarded upsert better than an inbox table? When is it insufficient?
12. How do the outbox and inbox together produce an exactly-once effect without distributed transactions?

<details>
<summary>Answers (try first)</summary>

1. The marker and the effect commit atomically in the same database transaction. With a separate store, a crash between them double-applies or loses the effect, and concurrent copies can both pass the check.
2. Two transactions can both see "not found" with SELECT and both proceed. The unique-index insert is atomic: one wins, the other waits then sees a conflict (rowCount 0).
3. Before COMMIT: rolled back, retried fresh (once). After COMMIT before offset commit or offset commit fails: redelivered, marker found, skipped (once). COMMIT with unknown outcome: either way applied once.
4. DB-then-offset is at-least-once (replay is absorbed by the inbox). Offset-then-DB is at-most-once: a crash after the offset commit loses the message and nothing can recover it.
5. The second insert waits on the first's uncommitted unique entry; when the first commits, the second sees a conflict and skips; if the first rolls back, the second proceeds. Only one applies the effect.
6. A relay/producer duplicate gets a new offset, so it would not match. It is right only for redelivery of the same record to the same consumer group (transactional offset store).
7. At least as long as a duplicate can still arrive (topic retention, max downtime, relay republish horizon, replay window) plus margin. Too early: a late duplicate is applied again.
8. Its `events.event_id` unique key is the marker and `ON CONFLICT DO NOTHING` is the check, in the same transaction as the effect.
9. A replay increments again. Update the counter only for rows actually inserted (inserted count / inbox claim), in the same transaction.
10. Email/HTTP calls: idempotency key at the callee or a consumer-side outbox. Another database or a Kafka publish: downstream idempotency, an outbox, or a Kafka transaction for Kafka-only flows.
11. Better for "set latest state" effects with a monotonic version (also handles out-of-order, no retention). Insufficient for accumulating effects (counters, histories).
12. The outbox makes the producer's change-and-publish-intent atomic and delivery at-least-once; the inbox makes the consumer's marker-and-effect atomic so repeats are no-ops. Each hop uses only a local transaction.
</details>

## 23. Glossary and cheat sheet

| Term                           | Meaning                                                                             |
| ------------------------------ | ----------------------------------------------------------------------------------- |
| **Inbox table**                | Table of processed message ids, written in the same transaction as the effect       |
| **Idempotent consumer**        | A consumer whose repeated processing of one message has the same effect as once     |
| **Marker**                     | The inbox row (or the target table's unique key) proving a message was handled      |
| **Exactly-once effect**        | At-least-once delivery + idempotent processing                                      |
| **Version guard**              | `WHERE current.version < incoming.version` so stale/duplicate events change nothing |
| **Transactional offset store** | Keeping Kafka offsets in the DB, in the same transaction as the effect              |
| **Idempotency key**            | Caller-supplied id that lets a callee ignore repeated requests                      |
| **Retention window**           | How long dedupe ids are kept                                                        |
| **Check-then-act race**        | Two actors both pass a check before either records the result                       |

```
Consumer :  BEGIN; INSERT inbox(id) ON CONFLICT DO NOTHING;
            if rowCount=0 → skip; else apply effect; COMMIT;  THEN commit Kafka offset.
Id       :  producer-assigned event_id (outbox), carried in a header. Never the Kafka offset.
Simpler  :  keyed insert ON CONFLICT DO NOTHING (EventPulse sink) | versioned upsert (config state).
Needs it :  counters, multi-table effects, anything that accumulates.
Not enough: effects outside the DB → idempotency key / own outbox.
Retention:  ≥ max replay horizon (topic retention + margin); batched delete or partition drop.
Metric   :  duplicates skipped (attempted - inserted), inbox size, lock waits, DLQ count.
```

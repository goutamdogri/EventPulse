# The Dual-Write Problem

## 1. TL;DR

- A **dual write** is one logical action that updates **two systems that cannot share a transaction**, for example _write a row to Postgres_ and _publish a message to Kafka_, as two separate steps.
- Two separate steps means a window between them. If the process dies, the network fails, or either system rejects the call in that window, the two systems **disagree forever**, and nothing in either system knows it.
- There are exactly two bad outcomes, depending on order:
  - **DB first, then Kafka** → a crash in between gives a **committed change with no event** (a _lost event_; downstream never learns).
  - **Kafka first, then DB** → a crash in between gives an **event with no change** (a _phantom event_; downstream acts on something that never happened).
- **Retries, careful ordering, try/catch, and "compensating" code reduce the odds but cannot remove the window**, because the retry logic itself lives in the process that can die.
- A distributed transaction (XA/2PC) would close the window in theory, but **Kafka does not take part in XA**, and 2PC has its own availability costs. Kafka's own transactions only cover Kafka.
- The fix is structural: **turn two writes into one**. Write the business change **and** a record of "an event must be published" in **one local database transaction** (the **transactional outbox**), then let a separate process move that record to Kafka at-least-once. The remaining duplicates are handled by an idempotent consumer (the **inbox** side).

> **One-line version:** _You cannot atomically write to two systems that do not share a transaction, so write to one system atomically and replicate from it._

## 2. The mental model: two notebooks, one pen

You keep the shop ledger in a **book on your desk** (the database). You also have to post each sale on a **notice board in the hall** (Kafka) so the warehouse can see it. You can only hold one pen at a time, so you must do one first and walk to the other.

| Story                                                                                                     | Technical meaning                                                                                                                                                                |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Write the ledger, walk to the hall, **faint on the way**                                                  | DB committed, process crashed before publishing: sale recorded, warehouse never told                                                                                             |
| Pin the note first, walk back, **faint before writing the ledger**                                        | Event published, DB write never happened: warehouse ships goods you never sold                                                                                                   |
| The hall door is **locked** when you arrive                                                               | Kafka unavailable at publish time                                                                                                                                                |
| You get to the hall, pin the note, but the **door slams and you are not sure it stuck**                   | Publish timeout: the outcome is _unknown_, so retrying may duplicate (see [delivery-semantics note 2](../delivery-semantics/2.%20why-duplicates-are-inevitable-two-generals.md)) |
| You **write the sale and a "to-post" slip in the same ledger page** and a clerk posts every slip in order | Transactional outbox: one atomic write, then a reliable relay                                                                                                                    |
| The clerk posts a slip, **faints before ticking it off**, and posts it again next day                     | At-least-once relay: duplicates, so the warehouse must recognise a repeat slip (inbox / idempotent consumer)                                                                     |

The trick in the last two rows is the whole pattern: **you can only be atomic inside one book**, so make the "please tell the hall" request something written in the same book.

## 3. What a dual write is

A dual write is any code path that does this shape of thing:

```ts
// Sketch: a request handler that "updates state and announces it"
async function changeTenantRateLimit(tenantId: string, rps: number) {
  await db.query(
    "UPDATE tenant_config SET rate_limit_rps = $1 WHERE tenant_id = $2",
    [rps, tenantId],
  ); // write #1 (Postgres)
  await kafka.send({
    topic: "tenant-config-changed",
    messages: [{ key: tenantId, value: JSON.stringify({ tenantId, rps }) }],
  }); // write #2 (Kafka)
}
```

Two systems, two independent failure domains, two separate commits. Neither knows the other exists. Properties that define the problem:

- **Different durability boundaries.** Postgres makes a change durable when its transaction commits (WAL fsync). Kafka makes a message durable when the leader and in-sync replicas have it, per `acks` ([Stage 2 note on acks](../../../stage-2/learning/producer/2.%20kafka-producer-acks.md)). Those are two unrelated moments.
- **No shared atomic commit.** There is no operation "commit Postgres and Kafka together".
- **Independent failures.** Either call can fail, time out, or succeed with the _response_ lost.

The same shape appears with other pairs: DB + Redis cache invalidation, DB + Elasticsearch index, DB + an HTTP call to another service, DB + sending an email. Kafka + Postgres is just the most common teaching case. Every one has the same two-failure-orders analysis below.

## 4. Why it breaks: the two failure orders

### 4.1 Order A: database first, then Kafka

```
1. BEGIN; UPDATE tenant_config ...; COMMIT;     ← durable
        ── process crashes / pod killed / OOM / deploy ──
2. kafka.send(...)                              ← never runs
```

Result: **the change is real, the event never exists.** Consumers (cache invalidators, search indexers, analytics) keep believing the old value. No error is logged anywhere, because the process that would have logged it is gone. The loss is **silent and permanent**; nothing will ever republish it.

Variants that end the same way:

- Kafka is down or the broker is unreachable, `send` throws, and the handler returns an error _after_ the DB commit. The caller thinks the whole operation failed (and may retry the HTTP request, which re-runs the DB update — often harmlessly — and may or may not re-publish), but the DB already changed.
- `send` throws but your code swallows the exception (a common bug) and returns 200.
- Fire-and-forget producer (`acks=0` or not awaiting the promise): the message is lost in the client buffer when the process exits.

### 4.2 Order B: Kafka first, then database

```
1. kafka.send(...)                              ← durable, visible to consumers immediately
        ── crash, or the DB call fails (constraint violation, deadlock, timeout) ──
2. BEGIN; UPDATE tenant_config ...; COMMIT;     ← never commits
```

Result: **the event exists, the change does not.** This is usually _worse_: downstream systems act on a fact that is false. A "tenant created" event with no tenant row means a consumer may provision resources for a tenant the source of truth does not know about. And a published Kafka record **cannot be un-published** (the log is append-only; see [Stage 2 topic/partition/log note](../../../stage-2/learning/Kafka/1.%20kafka-topic-partition-log-segment.md)). You can only publish a _compensating_ event, which itself is another dual write.

Order B also commonly appears as a **race**, even without a crash: the event reaches a consumer **before** the DB transaction commits. The consumer queries the DB for the new data (or calls the service back) and **does not see it yet**. See [section 5.3](#53-publish-before-commit-the-visibility-race).

### 4.3 Summary of the two orders

|                     | Order A: DB → Kafka                                                   | Order B: Kafka → DB                           |
| ------------------- | --------------------------------------------------------------------- | --------------------------------------------- |
| Crash between steps | Change exists, **no event**                                           | Event exists, **no change**                   |
| Failure type        | Lost event (silent)                                                   | Phantom event (silent, and visible to others) |
| Consumer harm       | Stale downstream state forever                                        | Acting on a false fact; must be compensated   |
| Detectable?         | Only by reconciliation (compare DB to downstream)                     | Only by reconciliation                        |
| Usual preference    | Slightly more common default, because "the DB is the source of truth" | Rarely a good choice                          |

Neither order is correct. Order A is _less harmful_ in most systems, which is why teams pick it, but it still loses events.

## 5. It is not only crashes

Teams sometimes dismiss this as "only happens when the process is killed, which is rare". It also happens during **perfectly normal operations**.

### 5.1 Deploys and autoscaling

Rolling deploys send SIGTERM. A handler in the middle of "DB committed, Kafka send pending" can be killed when the grace period ends, or when `process.exit()` is called without draining. Autoscaling scale-downs and spot-instance reclaims do the same. At any scale with frequent deploys, the window is hit routinely.

### 5.2 Timeouts that leave the outcome unknown

Kafka `send` may **time out** (`delivery.timeout.ms`, [Stage 2 retries and timeouts note](../../../stage-2/learning/producer/5.%20kafka-producer-retries-and-timeouts.md)) although the broker **did** append the record. Your code sees an error, but the message exists. If you treat that as "event not sent" and roll back or retry the whole business action, you now have the opposite problem: a phantom or a duplicate. A timeout means **unknown**, not **failed**.

Similarly the database `COMMIT` can time out or lose its connection **after** the server committed. Your code sees an exception, believes the write failed, and (in Order B) the event was already published. This is exactly the Two Generals shape from [delivery-semantics note 2](../delivery-semantics/2.%20why-duplicates-are-inevitable-two-generals.md): you cannot distinguish "request lost" from "response lost".

### 5.3 Publish-before-commit: the visibility race

Even with **no failure**, publishing from _inside_ the DB transaction (before `COMMIT`) is wrong:

```ts
await db.tx(async (tx) => {
  await tx.query("INSERT INTO orders ...");
  await kafka.send(orderCreated); // consumers can receive this NOW
  // ... more work, then COMMIT happens a few ms later
});
```

A fast consumer receives `orderCreated`, calls `GET /orders/123`, and gets **404**, because the row is not committed yet and is invisible to other connections (read committed isolation). Worse, if the transaction then **rolls back**, the event is a permanent phantom. Sending from inside the transaction does **not** make it atomic; it just moves the window.

### 5.4 Partial application inside one process

Even within one request, a bug (an exception after the DB commit but before publishing; a branch that forgets to publish; two code paths where only one publishes) creates the same inconsistency. Dual writes are a **code-structure** hazard, not only an infrastructure one: every place that does "write state, then announce" re-introduces the window.

### 5.5 Concurrency reorders the two systems

Two concurrent updates to the same row: T1 commits to the DB first, T2 second; but T2's Kafka publish lands before T1's. The topic order disagrees with the database order, so a consumer that applies events in topic order ends with the **older** value. A dual write loses not just atomicity but **ordering consistency** with the source of truth. (The outbox restores this: the outbox row order is the commit order, up to subtleties covered in [note 3](./3.%20relay-polling-vs-cdc.md).)

## 6. Why "just retry" does not fix it

Natural instincts and why each fails:

**"Wrap the publish in a retry loop."** Fine for a transient Kafka error while the process is alive. But the retry state lives in **process memory**. If the process dies, the retry dies with it. This reduces probability; it does not close the window. (Kafka's own producer retries have the same property: they protect against broker blips, not producer death. See [Stage 2 idempotence note](../../../stage-2/learning/producer/3.%20kafka-producer-idempotence.md).)

**"If the publish fails, roll back the DB change."** The DB commit already happened (Order A). To "roll back" you would write a _compensating_ DB change — another write that can fail, and during which other readers have already seen the committed state. Alternatively publish _inside_ the DB transaction and fail the transaction on error: this is [5.3](#53-publish-before-commit-the-visibility-race), and it breaks on timeouts (the publish may have succeeded) and on COMMIT failure (the publish already happened).

**"Retry the whole HTTP request."** Re-running the handler repeats the DB change and the publish. If the DB part is not idempotent, you double-apply it; if the earlier publish actually succeeded, you publish again. You have moved the problem to the client and added duplicates.

**"Catch the exception and log it, we will fix it manually."** That is reconciliation by hand. Acceptable as a _safety net_, not as the design.

**Key principle:** to survive a crash you need the _intent to publish_ stored **durably and atomically with the state change**. A retry loop in memory is not durable.

## 7. Why a transaction around both does not work

An intuitive fix: put both calls inside one `BEGIN ... COMMIT`. Why that fails:

- A **database transaction** only controls changes **inside that database**. `kafka.send()` inside the callback is just a network call; it is not part of the transaction, and `ROLLBACK` cannot recall a sent message.
- The transaction's commit is atomic _within Postgres_. Kafka does not enlist in Postgres's commit log, and Postgres does not enlist in Kafka's.
- Even if you put the send _last_ (just before COMMIT), a failure of COMMIT after a successful send leaves a phantom event; and a crash after COMMIT but before send does not exist in this shape, but you have only traded one window for the other.

A transaction's atomicity is bounded by the system that implements it. Atomicity across two independent systems requires a **coordination protocol** (next sections), and those have real costs.

## 8. Why Kafka transactions do not help here

Kafka has transactions (see [delivery-semantics note 3](../delivery-semantics/3.%20kafka-transactions-and-exactly-once-semantics.md)). They give atomicity across **multiple Kafka partitions and topics** and across **consumed offsets + produced records** (the consume-transform-produce loop). They do **not** include:

- a Postgres (or any external database) write;
- an HTTP call;
- an email.

So "exactly-once" in Kafka means exactly-once **within the Kafka world**: read offsets and write outputs atomically. The moment a side effect leaves Kafka, you are back to at-least-once plus idempotence. The honest framing from the delivery-semantics series: _exactly-once effect = at-least-once delivery + idempotent processing_. The outbox and inbox are the two halves of that sentence when a database is involved.

One more wrinkle: Kafka transactions have **no relationship** to a DB transaction ID, so you cannot "commit the Kafka transaction iff the DB commits" without writing your own coordinator, which is 2PC.

## 9. Why two-phase commit (XA) is not the answer

Two-phase commit (2PC), exposed in Java as XA/JTA, makes multiple **resource managers** commit atomically via a coordinator: _prepare_ (all vote yes and durably promise), then _commit_. Why it is not used here:

1. **Kafka does not implement XA.** There is no XA resource for Kafka producers. This ends the discussion for the stack in this repo.
2. **Blocking.** After a participant votes "prepared", it holds locks and **must wait** for the coordinator's decision. If the coordinator dies, participants are stuck (in-doubt transactions) until recovery. Availability of the _whole_ operation becomes the product of the availabilities of the coordinator and all participants.
3. **Latency and throughput.** Two round-trips and extra fsyncs per transaction; lock hold times grow; contention rises.
4. **Operational complexity.** In-doubt transaction recovery, heuristic outcomes, and coordinator logs are hard to run in container platforms where pods die constantly.
5. **Ecosystem fit.** Most modern brokers, cloud services, and HTTP APIs do not support it.

So the industry answer is not "make two systems commit together" but "make one system commit and **propagate** from it" (the **log-based integration** idea: the database's own commit log or an application-level outbox is the source, and everything else is derived).

## 10. Other "fixes" and why they fall short

| Idea                                                                       | What it does                             | Why it is not enough                                                                                                                                                                                                                                  |
| -------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Publish after commit, in-process** (Order A + retries)                   | Narrows the window                       | Still loses the event if the process dies in the window; no durable intent                                                                                                                                                                            |
| **Publish before commit** (Order B)                                        | Reduces lost events                      | Creates phantoms and visibility races                                                                                                                                                                                                                 |
| **Listen to yourself** (write to Kafka only; consume it and update the DB) | Single write to Kafka, DB is derived     | The API cannot confirm the DB is updated (eventual consistency leaks into the response, read-your-writes breaks); you need all state changes as events (event-sourcing-like discipline); consumer is a second dual-write risk if it also emits events |
| **Event sourcing** (the event log _is_ the state)                          | One write, to the event store            | A real architecture change, not a drop-in; the "event store" is again a DB that must publish to Kafka                                                                                                                                                 |
| **Periodic reconciliation job** (scan DB, compare, republish)              | Heals losses eventually                  | Slow to detect, needs a "did I publish this?" marker (which is an outbox flag), expensive full scans; useful as a safety net                                                                                                                          |
| **Change Data Capture directly on business tables**                        | No app change; stream row changes        | Events are row diffs, not domain events; leaks table schema to consumers; no place for event-only metadata. Usually combined with an outbox table instead (see [note 3](./3.%20relay-polling-vs-cdc.md))                                              |
| **Saga / compensation**                                                    | Undoes earlier steps after later failure | Needs a durable record of progress, which brings you back to storing intent atomically                                                                                                                                                                |
| **Make the DB write idempotent and retry the handler**                     | Heals Order A when the client retries    | Relies on the caller to retry; no guarantee a caller exists or retries                                                                                                                                                                                |

The ones that work all share one trait: **the thing that survives a crash is stored in the database, atomically with the business change.**

## 11. The family of solutions

Every real solution reduces to "pick one system as the single source of atomic truth and derive the other":

1. **Transactional outbox** (the subject of this series): the DB is the source. The business change and the "message to publish" row commit together; a relay publishes from the table to Kafka.
2. **CDC / log tailing of the DB's WAL** feeding Kafka: the relay is the database's own commit log (Debezium). Often combined with an outbox table (so events are explicit, not row diffs).
3. **Event sourcing**: the event store is the source, and read models and publishers derive from it.
4. **Kafka as the source ("listen to yourself")**: the event log is the source, the DB is a derived projection.
5. **Transactional messaging inside the DB** (e.g. a DB that has queue tables) is the outbox again.

In all of them you accept **at-least-once, eventually consistent** propagation, plus **idempotent consumers** to turn it into an exactly-once _effect_. The synchronous guarantee you get is only: _"If the change committed, the event will eventually be published; if the change did not commit, no event will ever exist."_

## 12. The key insight: make it a single write

The dual write fails because there are **two commits**. The outbox pattern has **one commit**:

```
Before (dual write):                         After (outbox):

  handler                                      handler
   ├─ write business row  ── commit #1           └─ BEGIN
   └─ publish to Kafka    ── commit #2               ├─ write business row
        ▲ window between ▲                           ├─ INSERT INTO outbox (...)
                                                     └─ COMMIT              ← the ONLY commit

                                              relay (separate process, retries forever)
                                                 outbox → Kafka  (at-least-once)
```

After the single commit there are exactly two possible worlds:

- **Committed:** both the business row and the outbox row exist. The relay **will** publish eventually, even if everything crashes and restarts.
- **Rolled back:** neither exists. No phantom event.

The window has not disappeared; it has been **moved** to a place where it is harmless: between "outbox row committed" and "Kafka has the message". There a crash leaves the outbox row in place, so the relay simply does the publish later. The only price is that the relay may publish **twice** (published but crashed before marking), which is why [note 4](./4.%20the-inbox-pattern.md) exists.

## 13. Where dual writes hide in real code

Review code for these shapes; each is a latent dual write:

- `repo.save(entity); publisher.publish(event);` in the same service method.
- An ORM **post-commit hook** or `@TransactionalEventListener(AFTER_COMMIT)` that publishes: better than publishing inside the transaction, but still a dual write (a crash after commit loses the event). It reduces visibility races, nothing more.
- A DB trigger that calls an HTTP endpoint or `pg_notify` consumed by an app which publishes: `NOTIFY` is **not durable** (a listener that is down misses it), and the listener then dual-writes to Kafka.
- A message **consumer** that updates the DB **and** publishes a derived event to another topic, with Kafka transactions covering only the publish and offset commit but not the DB write.
- "Write to DB, then invalidate the cache." Same two-system problem; common mitigation is TTL, or an outbox event that triggers invalidation (this is exactly S3-F4's use case).
- "Write to DB, then call another service over HTTP" with no durable record of the pending call.

A simple code-review question catches all of them: **"If the process is killed on the line after the first write, what state are the two systems in, and who repairs it?"** If the answer is "nobody", it is a dual write.

## 14. How bad is it, really? Judging the stakes

Not every dual write needs an outbox. Decide by the **cost of divergence** and **who can repair it**:

| Situation                                                                | Divergence cost                                  | Reasonable choice                                                           |
| ------------------------------------------------------------------------ | ------------------------------------------------ | --------------------------------------------------------------------------- |
| Analytics event about a click; losing 0.01% is fine                      | Low                                              | Publish directly with retries; accept rare loss                             |
| Cache invalidation with a short TTL as a backstop                        | Low-medium                                       | Direct publish + TTL, or outbox for faster correctness                      |
| Config change events that gate behavior (rate limits, tenant enablement) | Medium-high; stale config persists until restart | Outbox                                                                      |
| Money, inventory, entitlement, audit trail                               | High; legal or financial impact                  | Outbox (or event sourcing), with reconciliation as a second line of defense |
| Events that drive other systems' source of truth                         | High                                             | Outbox                                                                      |

Cost of the outbox: an extra table, extra writes per change, a relay process to run and monitor, at-least-once duplicates to handle, and latency of a few ms to a second or so. It is cheap relative to silent data loss, but it is **not free**, so a high-volume, loss-tolerant stream (like the raw ingest events in EventPulse, where Kafka _is_ the system of record) should **not** use it. See the next section.

## 15. EventPulse: where the problem appears

[reasoning, from the repo layout and the Stage 3 plan; the outbox itself is not built yet]

- **The ingest path** (`services/ingest-api` → Kafka → `services/consumer-sink` → Postgres `events`) is **not** a dual write. The API writes **only to Kafka**; the sink writes **only to Postgres**, committing offsets after the DB commit. Kafka is the log of record for raw events, and `INSERT ... ON CONFLICT (event_id) DO NOTHING` ([batch-writer.ts](../../../../services/consumer-sink/src/sink/batch-writer.ts)) absorbs replays. This is already the **inbox idea in its simplest form** (see [note 4](./4.%20the-inbox-pattern.md)).
- **The tenant configuration path (S3-F4)** is where the dual write appears: changing a tenant's settings must (1) update the config row in Postgres and (2) publish a change event so other components (for example caches or the ingest API's rate limiting) learn about it. Doing both separately would reintroduce exactly the failure orders above, and a lost config-change event means a component enforcing a stale limit indefinitely. That is why the stage plan calls for a **transactional outbox** there first.
- Both halves are also **single-owner** problems: one service owns the config table and its outbox; consumers own their own idempotency.

Design target (sketch): `tenant_config` + `tenant_config_outbox` written in one transaction; a polling relay publishes to a `tenant-config-changed` topic keyed by `tenant_id`; consumers dedupe on the outbox event id. The details are in the next three notes.

## 16. Common confusions

**"Kafka is durable, so publishing first is safe."** Durable is not atomic with your DB. Order B still produces phantoms.

**"I use `acks=all` and an idempotent producer, so I am safe."** Those protect the **producer→broker hop** against loss and duplicates. They do nothing about the process dying before it calls the producer. See [delivery-semantics note 4](../delivery-semantics/4.%20idempotent-producer-vs-idempotent-consumer.md).

**"I will publish in an after-commit hook."** Narrows the visibility race; the crash-after-commit window is still there.

**"The outbox gives exactly-once."** It gives **atomic intent** (no lost or phantom events) and **at-least-once publication**. Exactly-once _effect_ needs the consumer to dedupe.

**"A transaction in my ORM wraps the Kafka call."** The ORM transaction only governs SQL statements.

**"Dual writes are only a microservices problem."** They appear in a monolith that writes a DB and a cache, a search index, or a queue just as well.

**"2PC exists, so use it."** Not for Kafka, and not without paying in availability and complexity.

9. No. Raw events are written only to Kafka; there is no second system to keep atomic. An outbox would add a pointless extra DB write at high volume.
10. "If the process is killed right after the first write, what state are the systems in and who repairs it?"
</details>

## 18. Glossary and cheat sheet

| Term                            | Meaning                                                                                   |
| ------------------------------- | ----------------------------------------------------------------------------------------- |
| **Dual write**                  | One action that writes to two systems with no shared transaction                          |
| **Lost event**                  | State changed, but no event was published                                                 |
| **Phantom event**               | Event published, but the state change never committed                                     |
| **Visibility race**             | A consumer reads an event before the producing transaction commits                        |
| **2PC / XA**                    | Two-phase commit protocol for atomic commits across resource managers                     |
| **Transactional outbox**        | Writing the event as a row in the same DB transaction as the change; a relay publishes it |
| **Relay**                       | The process that moves outbox rows to the broker                                          |
| **At-least-once**               | A message may be delivered more than once, never lost                                     |
| **Idempotent consumer / inbox** | A consumer that can safely see the same message twice                                     |

**Cheat sheet**

```
Two systems, two commits  ->  a crash window always exists.
DB then Kafka   -> lost events.      Kafka then DB -> phantom events.
Retries/timeouts are in process memory; they do not survive the crash.
Kafka transactions = Kafka only.     XA = not available for Kafka.
Fix: ONE commit (change + outbox row), then relay at-least-once, consumer dedupes.
Review question: "killed after the first write: what state, who repairs?"
```

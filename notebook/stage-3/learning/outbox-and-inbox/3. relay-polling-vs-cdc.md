# Outbox Relay Options: Polling Publisher vs Change Data Capture

_Outbox note 3 of 4 in the Stage 3 learning notes. Read [note 1 (dual writes)](./1.%20the-dual-write-problem.md) and [note 2 (the transactional outbox)](./2.%20the-transactional-outbox.md) first. The outbox table is only half the pattern; the **relay** that moves rows to Kafka is the other half, and there are two families: a **polling publisher** (a loop running `SELECT ... FOR UPDATE SKIP LOCKED`) and **change data capture (CDC)**, for example **Debezium** reading the Postgres WAL. This note builds the polling relay in detail (query, transaction shape, locking, scaling, ordering, failure modes), then explains CDC (logical decoding, replication slots, the outbox event router, operational risks), compares them, and gives a decision rule: start with polling, understand CDC as the production-scale alternative._

**No labs here.** Everything is **[reasoning]** from documented PostgreSQL, Kafka Connect and Debezium behaviour. Code is a teaching sketch. Configuration property names for Debezium are given from memory of its documented options and **must be checked against the version you deploy** (they change between releases).

## 1. TL;DR

- The relay's contract: publish every committed outbox row **at least once**, in order per aggregate, and never block forever on one bad row.
- **Polling publisher:** an ordinary program that loops: `SELECT ... FROM outbox WHERE published_at IS NULL ORDER BY id LIMIT N FOR UPDATE SKIP LOCKED`, sends the batch to Kafka, marks the rows published, commits. **`FOR UPDATE`** locks the rows so another relay will not take them; **`SKIP LOCKED`** makes another relay _skip_ rows already locked instead of waiting, which lets several relays share the queue without blocking each other.
- Polling is **simple, needs no extra infrastructure, easy to debug**, and good for thousands of events per second on one primary. Its costs: **poll latency**, **constant queries**, **UPDATE/DELETE churn (bloat)**, and **ordering becomes your problem** the moment you run more than one relay.
- **CDC:** a connector (Debezium) reads the database's **write-ahead log** via **logical decoding**, turns committed inserts into Kafka records, and stores its progress as a **log position (LSN)**. No polling queries, no `UPDATE` to mark rows, commit-order preserved, low latency. Costs: **more moving parts** (Kafka Connect, Debezium, a replication slot, `wal_level=logical`), and **operational risks**: an inactive replication slot **retains WAL and can fill the disk**.
- Both are **at-least-once**. Both need **idempotent consumers**. Both preserve the outbox's atomicity guarantee because both read only **committed** data.
- **Rule:** start with polling; keep the interface clean so you can swap in CDC when throughput, latency, or operational maturity demands it.

> **One-line version:** _Polling asks the table "anything new?" in a loop; CDC listens to the database's own commit log. Both end with the same table and the same at-least-once promise._

## 2. The mental model

A restaurant kitchen needs to learn about new orders.

| Approach                                                           | Picture                                                                                                                                           | Technical                                                     |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **Polling**                                                        | A runner walks to the order pad every few seconds, tears off new slips, and delivers them                                                         | The relay queries the outbox table periodically               |
| `FOR UPDATE SKIP LOCKED`                                           | With several runners, each takes a _different_ handful of slips and **skips any slip a colleague is already holding**, never standing and waiting | Row locks + skip: safe parallel consumption of a queue table  |
| Runner faints after delivery, before ticking the pad               | The slip is delivered again next round                                                                                                            | At-least-once: mark-after-send                                |
| **CDC**                                                            | The till **prints a copy of every order automatically into a tape** the kitchen reads in order                                                    | The WAL is the tape; Debezium is the reader                   |
| Tape position bookmark                                             | The reader notes where it stopped                                                                                                                 | The LSN / connector offset                                    |
| Reader goes on holiday but the tape is **never allowed to be cut** | The paper roll piles up until the shop floor is full                                                                                              | An inactive replication slot retains WAL until the disk fills |

## 3. What the relay must guarantee

Independent of how it is built:

1. **No loss:** every committed outbox row is eventually published.
2. **At-least-once:** it may publish a row more than once but never zero times; **publish before recording progress**.
3. **Per-aggregate order:** rows for the same aggregate reach Kafka in commit order (use the aggregate id as the key).
4. **Only committed data:** never publish a row whose transaction has not committed (both approaches get this free from the database's visibility rules).
5. **Progress under failure:** one bad row cannot stall unrelated aggregates indefinitely (poison-row policy, [note 2 section 10](./2.%20the-transactional-outbox.md#10-failure-walk-through-every-crash-point)).
6. **Observability:** lag, backlog and error metrics ([note 2 section 14](./2.%20the-transactional-outbox.md#14-operating-it-metrics-and-alerts)).
7. **Stable identity:** it forwards the `event_id` assigned at write time; it never invents ids.

## 4. Part A: the polling publisher

The simplest correct relay. Table as in [note 2 section 5](./2.%20the-transactional-outbox.md#5-designing-the-outbox-table):

```sql
CREATE TABLE outbox (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  event_id uuid NOT NULL UNIQUE,
  aggregate_type text NOT NULL,
  aggregate_id text NOT NULL,
  event_type text NOT NULL,
  payload jsonb NOT NULL,
  headers jsonb NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz
);
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;
```

The core query:

```sql
SELECT id, event_id, aggregate_type, aggregate_id, event_type, payload, headers
  FROM outbox
 WHERE published_at IS NULL
 ORDER BY id
 LIMIT 500
   FOR UPDATE SKIP LOCKED;
```

Reading it clause by clause:

- `WHERE published_at IS NULL` uses the **partial index**, so cost scales with the backlog.
- `ORDER BY id` takes the oldest first; this approximates commit order (and is exact for same-aggregate rows, see [section 9](#9-the-gap-problem-and-why-a-flag-beats-a-cursor)).
- `LIMIT 500` bounds batch size, transaction duration and the amount of data held in memory.
- `FOR UPDATE` takes a **row-level write lock** on each returned row until the transaction ends.
- `SKIP LOCKED` tells Postgres: if a candidate row is already locked by another transaction, **pass over it** instead of blocking.

## 5. Row locking in Postgres: FOR UPDATE and SKIP LOCKED

### 5.1 The three behaviours for contended rows

| Clause                   | Behaviour when the row is locked by someone else |
| ------------------------ | ------------------------------------------------ |
| `FOR UPDATE` (default)   | **Wait** until the other transaction ends        |
| `FOR UPDATE NOWAIT`      | **Fail immediately** with an error               |
| `FOR UPDATE SKIP LOCKED` | **Silently skip** the row and move to the next   |

For a work queue, `SKIP LOCKED` is the right choice: workers do not block each other, and each row goes to exactly one worker _at a time_. It was added in PostgreSQL 9.5.

### 5.2 What it does and does not give you

- **Gives:** mutual exclusion on rows currently being processed; non-blocking competition between workers; lock auto-release if a worker's connection dies (the transaction aborts, so the rows are free again).
- **Does not give:** ordering across workers. Worker A may hold rows 1–500 while worker B takes 501–1000 and publishes first. The result is a **non-deterministic view** of the queue ("inconsistent" by design, as the Postgres docs note for `SKIP LOCKED`): fine for a job queue, **dangerous for per-aggregate ordering** ([section 8](#8-scaling-polling-multiple-relays-and-ordering)).
- **Lock visibility:** the lock is held until the relay's transaction commits or aborts. Writers inserting new outbox rows are **not** blocked (inserts do not conflict with locks on other rows).
- **Locks also block the marking `UPDATE`/`DELETE` by anyone else**, which is intended.

### 5.3 A subtle read-committed detail

At `READ COMMITTED`, `FOR UPDATE` re-checks the `WHERE` clause on a locked row after acquiring the lock. If another transaction marked it published in the meantime, the row is **dropped from the result** rather than returned stale. With `LIMIT`, that can yield fewer rows than requested: expected, not an error. Always handle a short batch.

## 6. The polling loop, step by step

```ts
// Teaching sketch: a single-relay-process polling loop (node-postgres + a Kafka producer)
async function relayOnce(pool: Pool, producer: Producer, batchSize = 500): Promise<number> {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    const { rows } = await client.query(
      `SELECT id, event_id, aggregate_type, aggregate_id, event_type, payload, headers
         FROM outbox
        WHERE published_at IS NULL
        ORDER BY id
        LIMIT $1
          FOR UPDATE SKIP LOCKED`,
      [batchSize],
    );
    if (rows.length === 0) { await client.query('COMMIT'); return 0; }

    // 1. Publish and WAIT for broker acknowledgement (acks=all, idempotent producer).
    await producer.send({
      topic: topicFor(rows[0].aggregate_type),            // or group by type
      messages: rows.map((r) => ({
        key: r.aggregate_id,                              // per-aggregate ordering
        value: JSON.stringify(r.payload),
        headers: { 'event-id': r.event_id, 'event-type': r.event_type, ...r.headers },
      })),
    });

    // 2. Only now record progress.
    await client.query(
      `UPDATE outbox SET published_at = now() WHERE id = ANY($1::bigint[])`,
      [rows.map((r) => r.id)],
    );                                                    // or: DELETE FROM outbox WHERE id = ANY(...)

    await client.query('COMMIT');
    return rows.length;
  } catch (e) {
    await client.query('ROLLBACK');                       // rows unlocked, will be retried
    throw e;
  } finally {
    client.release();
  }
}

async function runRelay(...) {
  for (;;) {
    let n = 0;
    try { n = await relayOnce(...); } catch (e) { await sleep(backoff.next()); continue; }
    backoff.reset();
    if (n === 0) await sleep(pollIntervalMs);             // idle wait; skip the sleep when busy
  }
}
```

What each part buys you:

- **One transaction = lock + publish + mark.** If anything fails, `ROLLBACK` releases the locks and no row is marked, so it is retried.
- **Publish before mark** is the at-least-once rule. A crash after `send` and before `COMMIT` republishes the batch on restart: duplicates, **same `event_id`s**.
- **Mixed topics:** if one batch contains several aggregate types, group by topic, send each group, and still mark after **all** sends succeed (or mark per group).
- **Batching to Kafka** uses one `send` of many messages: efficient and keeps order within a partition ([Stage 2 batching](../../../stage-2/learning/producer/1.%20kafka-producer-batching.md)).
- **Delete variant:** replace the `UPDATE` with `DELETE ... WHERE id = ANY(...)` for a constantly tiny table (and no `published_at` column).
- **Idle backoff:** when empty, sleep; when a full batch came back, loop immediately (the backlog is non-empty).
- **Wake-ups instead of pure polling (optional):** `LISTEN/NOTIFY` can nudge the relay to poll immediately after a commit (`NOTIFY` from the writer or a trigger). Treat it as a **latency hint only**: notifications are not durable, so polling remains the source of truth.

## 7. Where the Kafka send sits relative to the DB transaction

The sketch above holds the DB transaction (and row locks) open **during the Kafka send**. Trade-offs:

| Design                                       | How                                                                                                                  | Pros                                                          | Cons                                                                                                                                                                                                                                     |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Send inside the transaction** (the sketch) | `BEGIN; SELECT..SKIP LOCKED; send; UPDATE; COMMIT`                                                                   | Simple; locks guarantee exclusivity; crash = automatic unlock | Holds a DB connection and locks for the duration of the Kafka round trip; a Kafka stall holds a connection and may leave a long transaction (blocks vacuum)                                                                              |
| **Claim, then send, then mark**              | Tx 1: select skip-locked and set `locked_until = now()+30s, locked_by = $worker`; commit. Send. Tx 2: mark published | No long transaction; DB connection free during the send       | More states; a **lease** must expire so that a dead worker's rows are reclaimed; the lease may expire while a slow send is in flight, causing a concurrent re-claim and a duplicate (acceptable but visible); more writes (claim + mark) |
| **Advisory-lock single relay**               | One relay holds `pg_try_advisory_lock(k)`; no row locks; reads, sends, marks                                         | Strict ordering; trivial                                      | Single point of throughput; failover = lock release when the session ends                                                                                                                                                                |

Guidance: start with the simple sketch and **set a statement/idle-in-transaction timeout** and a **Kafka request timeout shorter than that**, so a stalled broker cannot hold the connection for minutes. Move to claim-with-lease only if profiling shows the long transaction is a problem.

The lease variant's schema addition:

```sql
ALTER TABLE outbox ADD COLUMN locked_until timestamptz, ADD COLUMN locked_by text, ADD COLUMN attempts int NOT NULL DEFAULT 0;
-- claim:
WITH c AS (
  SELECT id FROM outbox
   WHERE published_at IS NULL AND (locked_until IS NULL OR locked_until < now())
   ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED)
UPDATE outbox o SET locked_until = now() + interval '30 seconds', locked_by = $1, attempts = attempts + 1
  FROM c WHERE o.id = c.id
RETURNING o.*;
```

## 8. Scaling polling: multiple relays and ordering

One relay is often enough (a single relay can publish thousands of rows per second). When you need more throughput or high availability, you face the ordering problem.

**The hazard.** `SKIP LOCKED` workers take **disjoint batches** concurrently. Suppose aggregate `T1` has events e1 (id 10) and e2 (id 11), and worker A grabbed id 10 while worker B grabbed 11. B may publish e2 **before** A publishes e1. Consumers see **e2 then e1**: reordered.

**Fixes (pick one):**

| Fix                                   | How                                                                                                          | Notes                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **One active relay**                  | Leader election via `pg_try_advisory_lock`, a Kubernetes lease, or simply _run one replica_                  | Simplest. HA by fast restart or a standby that takes the lock. Throughput capped at one process                                                             |
| **Partition by key**                  | Relay `i` of `N` only claims rows where `hashtext(aggregate_id) % N = i`                                     | Per-aggregate order kept (same aggregate always handled by the same relay); parallelism = N; needs a stable assignment and rebalancing story when N changes |
| **Per-aggregate claim**               | Claim by aggregate (lock the _oldest unpublished row per aggregate_ only; later rows of that aggregate wait) | Strict order with parallel aggregates; more complex query (`DISTINCT ON (aggregate_id)`)                                                                    |
| **Accept reordering + version check** | Multi-relay, consumers drop events with `version <= applied`                                                 | Works when consumers keep only the latest state (cache/config); not for append-only histories                                                               |

Example of the key-partitioned claim:

```sql
SELECT ... FROM outbox
 WHERE published_at IS NULL
   AND abs(hashtext(aggregate_id)) % $N = $i
 ORDER BY id LIMIT 500 FOR UPDATE SKIP LOCKED;
```

(The `hashtext` expression cannot use the partial index for the modulus filter; for large `N` and big backlogs, store a `shard smallint` column computed at insert time, and index `(shard, id) WHERE published_at IS NULL`.)

**Failure of ordering under retries even with one relay:** after a partial batch failure, the _whole transaction rolls back_, so the batch is retried in the same order. Per-key order is preserved; duplicates appear.

## 9. The gap problem and why a flag beats a cursor

A tempting design avoids `published_at` by storing the relay's **last seen id** and querying `WHERE id > :last ORDER BY id`. It is subtly wrong with concurrent writers:

```
Writer A: INSERT -> id 100 ...............................(still open).......... COMMIT
Writer B:                  INSERT -> id 101; COMMIT
Relay:                                      reads id>99 -> sees 101 only -> cursor = 101
                                                                            ... A commits ...
Relay:   reads id>101 -> never sees 100      <- row 100 is lost forever
```

Sequence values are **assigned at insert, not at commit**, and sequences are not rolled back, so ids can also have permanent holes (rolled-back transactions). The relay cannot tell a _hole that will never fill_ from a _row not yet committed_.

Ways out:

1. **Use the flag (`published_at IS NULL`)** as in this note: every unpublished committed row is visible to the next query regardless of its id; nothing can be skipped. This is why polling with a flag is robust. (It still orders by `id`, which only matters for relative order, and same-aggregate rows serialize via the row lock on the business row, [note 2 section 9.1](./2.%20the-transactional-outbox.md#91-write-order-vs-identity-order).)
2. **Cursor + transaction visibility:** compare against the oldest in-flight transaction (`pg_snapshot_xmin(pg_current_snapshot())`, storing `xid8`/`txid_current()` in the row and only reading rows whose xid is below the snapshot's xmin). Correct but intricate; used by some libraries.
3. **Serialize writers** with a lock (lowers write concurrency; rarely worth it).
4. **CDC:** reads in WAL commit order; no gaps by construction ([section 18](#18-cdc-guarantees-and-ordering)).

Practical rule: **polling = flag or delete, not a bare id cursor.**

## 10. Polling: batching, interval, latency and load

- **Latency** ≈ poll interval (average half of it) + send time. 100 ms interval → tens of ms average added latency; 1 s interval → ~0.5 s. Do not poll faster than you need.
- **Idle load:** each poll is one cheap indexed query if the partial index is small. 10 polls/second on an empty queue is negligible; 100 relays × 10/s is not. Use adaptive backoff: poll fast while busy, back off up to a cap when idle.
- **Batch size:** larger batches amortize round trips and Kafka batching but lengthen the transaction and the duplicate window after a crash (a crash replays up to one batch). Start at a few hundred; tune with metrics.
- **Kafka-side:** use the batching options ([Stage 2 batching](../../../stage-2/learning/producer/1.%20kafka-producer-batching.md)); await all acks once per batch.
- **Write amplification:** each published row costs one additional `UPDATE` (new tuple + index maintenance) or `DELETE`, plus WAL; this is the main throughput tax of polling.
- **Throughput ballpark** [reasoning, not measured]: low thousands of rows/s per relay is realistic on a modest primary; the limit is usually Postgres write amplification and the send round trips, not the `SELECT`.

## 11. Polling: failure modes

| Failure                                  | Behaviour                                            | Handling                                                                                                 |
| ---------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Relay crashes mid-batch                  | Transaction aborts, locks released, rows unpublished | Another/next run republishes: duplicates at most                                                         |
| Crash after send, before COMMIT          | Rows published but not marked                        | Republished on restart: duplicates (same `event_id`)                                                     |
| Kafka down                               | `send` throws/timeouts, ROLLBACK                     | Backoff; backlog grows; alert on oldest-age                                                              |
| Kafka slow                               | Long transaction, locks held                         | Timeouts; consider lease-based claim                                                                     |
| Poison row                               | Same row fails every time                            | attempts counter; dead-letter table; per-aggregate block                                                 |
| DB failover                              | Connection lost mid-transaction                      | Treated as crash; same recovery                                                                          |
| Two relays by mistake with a flag design | `SKIP LOCKED` keeps them off the same rows           | Correctness fine, **ordering** may suffer ([section 8](#8-scaling-polling-multiple-relays-and-ordering)) |
| Long-running unrelated transactions      | Block vacuum; index/table bloat                      | Monitor `idle in transaction`; set `idle_in_transaction_session_timeout`                                 |
| Clock skew                               | `now()` is from the DB, so it is consistent          | Use DB time for timestamps and leases                                                                    |

## 12. Polling: Postgres performance traps

1. **Bloat from UPDATE/DELETE churn** ([note 2 section 11](./2.%20the-transactional-outbox.md#11-keeping-the-table-small-cleanup-and-bloat)): tune autovacuum, delete in batches, or partition and drop.
2. **Index on `published_at IS NULL` must be partial**, otherwise it indexes the whole history.
3. **`ORDER BY id LIMIT n` with a dead-tuple-laden index head:** the scan walks over dead index entries first; vacuum and short transactions keep this fast. Symptom: the poll query gets slower over time while the live backlog is small.
4. **`SELECT ... FOR UPDATE` writes to the heap** (row lock is stored in the tuple header/xmax), producing WAL and dirtying pages even for a no-op; this is another reason to avoid very high poll frequency with large batches.
5. **Connection use:** each relay holds a connection during the send; size the pool and use `idle_in_transaction_session_timeout`.
6. **Statement for the mark step:** `UPDATE ... WHERE id = ANY($1)` with a bigint array is efficient; avoid per-row updates.
7. **Replicas:** read the queue only from the **primary** (replicas lag and cannot take row locks).

## 13. Part B: change data capture

**Change data capture** means _observing the changes committed to a database and streaming them out_, usually by reading the database's own transaction log rather than by querying tables. For Postgres this is the **write-ahead log (WAL)**.

The idea: Postgres already records every committed change in the WAL for crash recovery and replication. If you can read it **in a decoded, logical form** ("row inserted into `outbox` with these column values"), you have a perfectly ordered, committed-only stream of changes with no polling and no extra writes.

For the outbox pattern, CDC means: **the application inserts into the outbox table exactly as before; a connector reads those inserts from the WAL and produces them to Kafka.** The application and table design barely change; only the relay is replaced.

## 14. How Postgres logical decoding works

(Enough detail to reason about operations.)

- **`wal_level = logical`** must be set (requires a restart). It makes the WAL include the information needed to reconstruct row-level changes. It increases WAL volume somewhat.
- **Logical decoding** turns WAL records into a stream of row changes **per committed transaction, in commit order**. Changes of a transaction are only emitted after it commits, so aborted transactions never appear.
- **Output plugin** formats the stream: `pgoutput` (built in, the standard for Debezium on modern Postgres), `decoderbufs`, `wal2json`, etc.
- **Publication** (for `pgoutput`): `CREATE PUBLICATION dbz_pub FOR TABLE outbox;` declares which tables to emit.
- **Replication slot:** a server-side object that **remembers the consumer's position (LSN) and forces Postgres to keep all WAL the consumer has not yet confirmed.** Created with e.g. `pg_create_logical_replication_slot('dbz_slot', 'pgoutput')`. The slot is what makes the consumer **durable**: if the connector is down for an hour, Postgres retains that hour of WAL, and the connector resumes where it left off.
- **Confirmed flush LSN:** the consumer periodically tells Postgres "I have safely processed up to LSN X"; the slot advances and old WAL becomes reclaimable.
- **Snapshots:** when starting, Debezium can take an initial consistent snapshot of existing rows and then switch to streaming; for an outbox you normally **skip** this (`snapshot.mode=never`/`no_data`-style) because old rows have already been dealt with.
- **Permissions:** the connector's DB user needs `REPLICATION` and `SELECT` on the published tables; on managed Postgres this is often an extension or parameter group (check your provider).
- **What is read:** INSERT/UPDATE/DELETE events with before/after images (depending on `REPLICA IDENTITY`). For an insert-only outbox you only care about **inserts**.

## 15. Debezium architecture

```
 Postgres  ──WAL (pgoutput)──►  Debezium Postgres connector  ──►  Kafka topics
 (outbox table)                  (runs inside Kafka Connect)       (one per event router rule)
        ▲                                   │
        └──── replication slot <────────────┘   (confirms LSN after Kafka acks; stores progress)
                                            │
                                  Kafka Connect cluster
                                  (stores connector offsets in internal Kafka topics,
                                   handles restarts and task failover)
```

Key points:

- Debezium is a **source connector** for **Kafka Connect**. Connect provides the runtime: workers, config REST API, distributed mode, offset storage, restarts. (A "Debezium Server" and an embedded engine also exist, without Connect.)
- The connector reads the slot, converts each change into a Kafka record (envelope with before/after/source metadata, or the shaped outbox record, [section 16](#16-the-outbox-event-router)), writes them to Kafka, and then **acknowledges the LSN** so Postgres can recycle the WAL. Progress is tracked both as Connect source offsets and as the slot's confirmed LSN.
- It is **at-least-once**: after a crash it may re-read and re-emit changes whose Kafka write was not yet recorded as flushed. Records carry source metadata (LSN, transaction id) that consumers can use, but your **`event_id`** is still the practical dedupe key.
- Throughput is high (tens of thousands of changes/s per connector is typical for simple rows), and latency is milliseconds to low seconds, bounded by Kafka Connect batching/flush settings.

## 16. The outbox event router

A raw Debezium change record is an **envelope** describing a row change (`before`, `after`, `source`, `op`). Publishing that as your domain event leaks your outbox schema. Debezium ships a **Single Message Transform (SMT)**, the **Outbox Event Router** (`io.debezium.transforms.outbox.EventRouter`), that reshapes an outbox-table insert into a clean message:

| Outbox column (configurable names) | Becomes                                                                      |
| ---------------------------------- | ---------------------------------------------------------------------------- |
| `id` (uuid)                        | Event id header/field (dedupe key)                                           |
| `aggregateid`                      | Kafka message **key**                                                        |
| `aggregatetype`                    | Used to build the **topic name** (route by type, e.g. `outbox.event.<type>`) |
| `type`                             | Event type (header/field)                                                    |
| `payload`                          | Message **value** (JSON/Avro)                                                |
| optional columns                   | Extra headers/fields                                                         |

Typical configuration shape (names from Debezium documentation; verify for your version):

```json
{
  "name": "outbox-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
```

## 17. CDC and the outbox table: insert-only, no published flag

Because the WAL **already contains the insert**, the relay no longer needs a `published_at` column or any `UPDATE`:

- The app inserts rows. Debezium streams them from the WAL.
- The table can be **cleaned freely**: Debezium has the insert in the WAL regardless of whether the row is deleted later. A common trick is to `DELETE` the row **in the same transaction** as the insert (so the table is always empty and never bloats, yet the WAL records both the insert and the delete; the router emits on the insert and ignores the delete). Check your Debezium version's documentation on this and test it; some set-ups prefer a short retention and a periodic batched delete for debuggability.
- No polling query load, no lock contention, no write amplification from marking.
- **Alternative with no table at all:** `SELECT pg_logical_emit_message(true, 'outbox', payload::text)` writes a _transactional logical message_ into the WAL (no table, no bloat, no cleanup). A decoding consumer (with Debezium's message support or a custom reader) reads it. Less tooling and visibility; some managed platforms limit it. Worth knowing, rarely the first choice.

## 18. CDC: guarantees and ordering

- **Commit order, no gaps.** Changes are streamed in the order transactions committed, so the gap problem of [section 9](#9-the-gap-problem-and-why-a-flag-beats-a-cursor) cannot occur.
- **Per-key order in Kafka.** With the aggregate id as key, one partition keeps the order; the connector preserves WAL order in each topic as records are produced (Connect uses an idempotent/ordered producer configuration for source tasks; check `producer.override.*` if you tune it).
- **A single task per Postgres connector.** The Postgres connector is single-task for a given slot (the WAL is one sequential stream), so a _connector's_ throughput is bounded; scale by publications/slots per table or functional split, not by task count.
- **At-least-once.** Duplicates after connector restart or failover are possible. Same `event_id`, same consumer-side dedupe ([note 4](./4.%20the-inbox-pattern.md)).
- **Atomicity inherited.** It only sees committed rows, so the outbox guarantee of note 2 holds unchanged.
- **Failure semantics of the _source of progress_.** After a **database failover** to a replica, logical replication slots historically did **not** exist on the new primary (slots were not replicated); Postgres 17 added slot failover (`failover` slots / `pg_sync_replication_slots`) so slots can be synced to standbys. If the slot is lost, the connector cannot resume from where it was: you may need to re-snapshot or accept gaps. Know the failover story of your Postgres before depending on CDC.

## 19. CDC: operational risks (read these)

1. **Unbounded WAL retention (the big one).** A replication slot retains WAL from its `restart_lsn` forward **until the consumer confirms**. If the connector is stopped, failing, or lagging (or the slot is abandoned after you remove the connector), WAL **accumulates on the primary's disk** until it is full, at which point **Postgres can crash or stop accepting writes**. Defences:
   - Monitor `pg_replication_slots` (`active`, `restart_lsn`, `confirmed_flush_lsn`) and compute retained WAL (`pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)`).
   - Set **`max_slot_wal_keep_size`** (PG 13+) to cap retained WAL; the slot is invalidated instead of the disk filling (trade-off: the consumer must re-snapshot).
   - Drop slots when decommissioning (`pg_drop_replication_slot`).
   - Alert on slot inactivity and on lag in bytes.
2. **Idle-table WAL pinning.** If the captured table (the outbox) receives **no writes** while the database has heavy traffic on other tables, the connector may not advance its confirmed LSN (it only sees changes for included tables), so the slot keeps holding WAL. Debezium's **heartbeat** (`heartbeat.interval.ms` and a heartbeat action query that writes to a small table) forces regular LSN advancement.
3. **Extra infrastructure and expertise.** Kafka Connect cluster, connector configuration, SMT behaviour, upgrades, monitoring, secrets, the converter/schema registry choice.
4. **Schema changes.** Changing the outbox table (adding/renaming columns) needs coordination with the connector and event router mappings.
5. **Large transactions.** A very large transaction is only emitted at commit; memory/latency spikes in decoding (Postgres 14+ can stream in-progress transactions with `streaming=on`, but the outbox usually has small transactions).
6. **Managed-database limits.** Some hosted Postgres tiers restrict `wal_level=logical`, slots, or require specific roles/extensions; check before choosing.
7. **Testing difficulty.** Behaviour depends on real WAL and Connect; integration tests are heavier than a polling loop you can unit test.
8. **Debugging opacity.** "Why is the event not in Kafka?" means inspecting connector status, slot LSN, SMT config, topics: more layers than reading a table.
9. **Failover/slot continuity** ([section 18](#18-cdc-guarantees-and-ordering)).
10. **Security:** the connector has broad read access to WAL contents (every column of every published table); scope the publication tightly.

## 20. Polling vs CDC: side by side

| Aspect                    | Polling publisher                                         | CDC (Debezium)                                                                    |
| ------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| **Moving parts**          | Your service + Postgres + Kafka                           | + Kafka Connect, connector, replication slot, `wal_level=logical`, SMT            |
| **Latency**               | Poll interval + send (typically 50 ms to a few s)         | Typically tens of ms to ~1 s                                                      |
| **Throughput ceiling**    | Thousands/s; limited by update/delete write amplification | Tens of thousands/s; no marking writes                                            |
| **Load on DB**            | Constant polling queries, row locks, UPDATE/DELETE churn  | Log reading (cheap) but WAL retention and `wal_level=logical` overhead            |
| **Table bloat**           | Real concern                                              | Minimal (insert-only, can delete in the same tx)                                  |
| **Ordering**              | Easy with one relay; hard with many                       | Commit order by construction                                                      |
| **Gap problem**           | Needs flag (not a bare id cursor)                         | None                                                                              |
| **Duplicates**            | After relay crash between send and mark                   | After connector restart/failover                                                  |
| **Failure blast radius**  | A stuck relay just stops publishing; the DB is unharmed   | A stuck connector can **fill the primary's disk** via retained WAL                |
| **Debuggability**         | Plain SQL and application logs                            | Connector status, slot LSNs, SMT config                                           |
| **Code**                  | You own ~100 lines                                        | Mostly configuration; you own operations                                          |
| **Schema coupling**       | Entirely yours                                            | Event shape via SMT; table changes need config coordination                       |
| **Unit-testability**      | Easy (a function over a pool and a producer)              | Needs integration environment                                                     |
| **Hosted-DB constraints** | None                                                      | May need logical replication permissions                                          |
| **Cost to start**         | Hours                                                     | Days (plus ongoing operations)                                                    |
| **Best fit**              | Low–moderate volume, small team, first implementation     | High volume, strict latency, many services, platform team with Connect experience |

## 21. Decision guide

```
Do you already run Kafka Connect and Debezium (or have a platform team that does)?
├─ No ─► Is volume < a few thousand events/s and latency of ~0.1–1 s acceptable?
│        ├─ Yes ─► POLLING PUBLISHER.  (Most projects, including EventPulse's tenant config.)
│        └─ No  ─► Consider CDC, but budget for the operations work first.
└─ Yes ─► Many outbox tables / services, or need low latency / high volume?
          ├─ Yes ─► CDC with the Outbox Event Router.
          └─ No  ─► Either; prefer whichever you already operate well.
```

Heuristics:

- **Start with polling.** It is the smallest thing that is correct, and it teaches you the failure modes (duplicates, ordering, poison rows) you must handle under CDC anyway.
- **Keep the relay behind an interface** (the outbox table contract: columns, `event_id`, key, topic mapping) so switching relays does not change producers or consumers.
- **Move to CDC when** the polling relay's write amplification or latency becomes the bottleneck, when the number of outbox-owning services makes "one relay per service" a maintenance burden, or when operating Connect is already a solved problem for your team.
- **Do not choose CDC to avoid thinking about idempotence**: it does not remove duplicates.

## 22. Migrating from polling to CDC

Because both read the same table, a staged migration is possible:

1. Add the publication and slot; deploy the connector with `snapshot.mode` that skips old rows, **writing to a shadow topic** first and comparing against the polling relay's output.
2. Add a `published_at`-compatible mode: during cut-over, keep the polling relay running while CDC runs, accepting a **temporary duplicate stream** (consumers already dedupe by `event_id`).
3. Stop the polling relay; stop writing `published_at` (or leave it unused). Switch cleanup to batched delete or partition drop.
4. Watch slot lag and WAL retention before declaring done; set `max_slot_wal_keep_size`.
5. Keep the polling code for a while as a documented fallback (it can read rows the connector missed).

Rollback is simple: stop the connector, **drop the slot**, restart the polling relay (rows that were never marked are still there if you kept `published_at` semantics during the overlap).

## 25. Common confusions

**"`SKIP LOCKED` gives me ordered, exactly-once processing."** It gives non-blocking mutual exclusion on rows. Not ordering across workers; not exactly-once.

**"`FOR UPDATE SKIP LOCKED` locks the table."** Row-level only; writers keep inserting.

**"Polling with `id > last` is fine."** Not with concurrent writers (gap problem). Use a flag or delete.

**"CDC removes duplicates."** It is at-least-once; consumers dedupe.

**"CDC reads my table."** It reads the **WAL**, not the table, which is why it adds no query load and sees every committed change, including ones later deleted.

**"A replication slot is harmless when unused."** An inactive slot pins WAL and can fill the disk. Monitor and cap it.

**"Debezium is the outbox pattern."** Debezium is a _relay_. The outbox pattern is the table + transaction; the relay can be polling or CDC.

**"If I delete the outbox row, CDC loses the event."** The insert is already in the WAL; the router emits on the insert.

**"The relay can mark first and then send; it is faster."** That is at-most-once; a crash loses the event.

<summary>Answers (try first)</summary>

1. The locked row is silently passed over and the next candidate is considered. `NOWAIT` errors immediately; the default waits for the lock holder to finish.
2. Send-then-mark is at-least-once: a crash republishes. Mark-then-send is at-most-once: a crash after marking loses the event.

## 27. Glossary and cheat sheet

| Term                    | Meaning                                                             |
| ----------------------- | ------------------------------------------------------------------- |
| **Polling publisher**   | Loop that queries the outbox and publishes rows                     |
| **`FOR UPDATE`**        | Row-level lock for the rest of the transaction                      |
| **`SKIP LOCKED`**       | Skip rows locked by others instead of waiting                       |
| **Lease**               | Time-limited claim on rows, reclaimed if it expires                 |
| **CDC**                 | Streaming committed changes out of a database, usually from its log |
| **WAL**                 | Postgres write-ahead log                                            |
| **Logical decoding**    | Converting WAL into row-level change events                         |
| **Replication slot**    | Server-side bookmark that retains WAL for a consumer                |
| **LSN**                 | Log sequence number: a position in the WAL                          |
| **Publication**         | Declaration of which tables a `pgoutput` stream includes            |
| **Debezium**            | CDC platform with Kafka Connect source connectors                   |
| **Outbox Event Router** | Debezium SMT that turns outbox inserts into domain messages         |
| **Heartbeat**           | Periodic write/offset advance so idle captures do not pin WAL       |

```
POLLING:  BEGIN; SELECT .. WHERE published_at IS NULL ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED;
          send(acks=all); UPDATE/DELETE; COMMIT.     One relay (or key-sharded) for order.
          Use a flag/delete, never a bare id cursor.  Watch: oldest-unpublished age, bloat.
CDC:      wal_level=logical + publication + slot + Debezium + EventRouter SMT.
          Insert-only table; commit order; low latency.  Watch: slot WAL retention, heartbeat, failover.
BOTH:     at-least-once, consumers dedupe by event_id, atomic intent comes from the outbox transaction.
START:    polling.  KNOW:  CDC as the scale-up path.
```

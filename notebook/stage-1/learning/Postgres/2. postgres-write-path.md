## 1. TL;DR

- When you `INSERT`, Postgres does **not** write your row straight to its final place on disk. It changes a page **in memory** and writes a short description of the change to a **write-ahead log (WAL)**.
- At `COMMIT`, Postgres **flushes the WAL to disk (fsync)** and only then tells you "done". That is the durability point.
- So **commit latency is mostly fsync latency**. Your API's 202 in Stage 1 waits for it.
- The data pages themselves are written to disk **later, in the background** (bgwriter and checkpoints).
- Every index on the table adds more work and more WAL to each insert.
- If Postgres crashes, it **replays the WAL** to rebuild anything that was only in memory.

> **One-line version:** _Postgres makes a write durable by appending to a log and fsyncing it, not by updating the table on disk._

## 2. The mental model

Think of an accountant with a big ledger (the tables) and a notebook (the WAL).

| Accountant                                                           | Postgres                                      |
| -------------------------------------------------------------------- | --------------------------------------------- |
| The ledger on the shelf (slow to find and update the right page)     | Data files on disk (heap and index pages)     |
| The ledger page open on the desk                                     | A page in `shared_buffers` (memory)           |
| A running notebook where every change is jotted at the end, in order | The **WAL** (append-only, sequential)         |
| "I wrote it in the notebook and closed it. It's safe."               | `COMMIT` returns after the WAL is **fsynced** |
| Updating the shelf ledger later when there is time                   | Background writer and checkpoints             |
| After a power cut, re-read the notebook and fix the ledger           | Crash recovery (WAL replay)                   |

The key trick: **appending to a notebook is fast; finding and rewriting the right page in a huge ledger is slow.** So write the fast thing first, make _that_ durable, and do the slow thing later.

## 3. The journey of one INSERT

Your Stage 1 query:

```sql
INSERT INTO events (event_id, tenant_id, type, occurred_at, schema_version, payload)
VALUES ($1, $2, $3, $4, $5, $6)
ON CONFLICT (event_id) DO NOTHING;
```

What happens, in order:

```txt
 Client (pg.Pool connection)
      |
      | 1. send query to this connection's backend process
      v
 +---------------------------------------------------------------+
 | BACKEND PROCESS                                               |
 |                                                               |
 | 2. parse + plan                                               |
 | 3. probe PK index: does event_id already exist?  (ON CONFLICT)|
 | 4. find a heap page with free space, load it into             |
 |    shared_buffers if not already there                        |
 | 5. write the new row version (tuple) into that page IN MEMORY |
 |    -> page is now "dirty"                                     |
 | 6. insert an entry into EACH index (PK + secondary)           |
 |    -> those index pages become dirty too                      |
 | 7. for every change above, append a WAL record to the        |
 |    in-memory WAL buffers                                      |
 |                                                               |
 | 8. COMMIT:                                                    |
 |      write a commit record to WAL                             |
 |      flush WAL buffers to disk and fsync   <-- THE WAIT       |
 |                                                               |
 | 9. reply "INSERT 0 1" to the client                           |
 +---------------------------------------------------------------+
      |
      v
 Your Node handler returns 202
```

Meanwhile, **not on your request path**:

```txt
 later, in the background:
   bgwriter / checkpointer  -> write the dirty heap + index pages to the data files
```

### What "row becomes visible" means (MVCC, briefly)

The new row version is stamped with the ID of the inserting transaction. Other sessions treat it as invisible until that transaction **commits**. So the row exists in memory at step 5, but nobody else sees it until step 8 completes.

### What step 3 means for duplicates

`ON CONFLICT DO NOTHING` still has to **probe the unique index first**. A duplicate means "found, skip", but you still paid for the index lookup. It does not make duplicates free.

## 4. What WAL is and why it exists

**WAL = Write-Ahead Log.** The rule: _the log record describing a change must reach disk before the changed page is allowed to._

### Why not just write the data pages directly at commit?

| Approach                                        | Problem                                                                                                                                                                                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Write every changed data page to disk at commit | One insert touches a heap page plus several index pages scattered across files. That is **many random writes**, each slow, and a crash mid-way leaves **half-written, inconsistent** pages |
| Write one **sequential log record** at commit   | **One append** to one file. Fast, simple to make atomic, and enough to rebuild everything later                                                                                            |

### Properties of the WAL

- **Append-only and sequential.** Disks (and SSDs) are much better at sequential writes.
- **One shared WAL for the whole server**, not per table or per connection. Every backend appends to the same stream, which is why WAL write is a shared resource that can become a bottleneck.
- Stored as **16 MB segment files** in `pg_wal/`.
- Each position in the WAL is an **LSN** (Log Sequence Number), a growing byte offset. You can read it with `pg_current_wal_lsn()`, and subtract two LSNs to measure how many WAL bytes were generated. This is how you measure "WAL bytes per event" in B5/B7.
- The WAL is also what **replication** streams to replicas (Stage 6) and what point-in-time recovery uses.

## 5. Commit and fsync

At commit, the backend must make the WAL durable. Writing to a file is not enough, because the OS keeps writes in its **page cache** (RAM) and may not have sent them to the physical disk. **`fsync`** forces the OS and the disk to confirm the data is on stable storage.

```txt
 backend  --write()-->  OS page cache (RAM)   <- still lost on power cut
 backend  --fsync()-->  physical disk         <- now durable, call returns
```

**fsync is slow compared with everything else in the path.**

| Storage                     | Rough fsync latency                             |
| --------------------------- | ----------------------------------------------- |
| Fast local NVMe SSD         | well under a millisecond to about a millisecond |
| Typical SATA SSD / laptop   | around a millisecond to several milliseconds    |
| Network-attached cloud disk | several milliseconds, sometimes more            |
| Spinning disk               | around 10 ms                                    |

_(Rough orders of magnitude only. Measure yours with `pg_test_fsync` below.)_

### Why this matters for EventPulse

In Stage 1, **your API's latency includes this fsync**. A 2 ms insert is mostly: a little CPU, plus the commit wait. So:

```txt
API latency  ~=  queue wait in pool  +  parse/plan  +  index + heap work  +  COMMIT FSYNC  +  network
```

If your disk is slow, or the disk is shared with something noisy, every request gets slower, one for one. (This is the same lesson as B3: the API cannot be faster than its slowest synchronous dependency.)

### Docker note

Your Postgres runs in a container on a volume. fsync goes through to the host's storage stack, so results depend on your actual disk (and on WSL2/VM layers if you use them). Record the storage type in your notebook so results are comparable.

## 6. Group commit

Here is a very important and non-obvious effect. fsync is expensive, but **one fsync can make many transactions durable at once**.

```txt
 Without group commit (if each commit did its own fsync):
   T1: write -> fsync ------------>
   T2:                 write -> fsync ------------>
   T3:                                  write -> fsync ------------>
   (3 fsyncs, serialized)

 With group commit (what Postgres does):
   T1: write --\
   T2: write ---+--> ONE fsync covers all three --> all three return
   T3: write --/
```

When a backend asks to flush WAL up to its LSN, and another backend is already flushing, it can simply **wait for that flush** (or have its records included in the next one). Many concurrent committers share a single fsync.

### What this means in practice

- **Throughput under concurrency can be much higher than `1 / fsync latency`.** A single connection committing one row at a time is capped by fsync latency (about 1000 commits/sec at 1 ms). Ten busy connections can each ride along on shared fsyncs.
- This is one reason your pool should not be _too small_ for write loads: you need enough concurrent committers to benefit from batching of fsyncs.
- But it also means **adding connections has limited upside** (see the process-per-connection notes: past a point you just add contention).

### Worked example

| Setup                                             | Rough behavior                                                                                                                       |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1 connection, fsync = 1 ms, one row per commit    | at most about 1,000 commits/sec                                                                                                      |
| 10 connections, same fsync                        | fsyncs are shared, so total can be several times higher than 1,000/sec, limited by CPU, WAL write bandwidth, and the cost of indexes |
| 1 connection inserting 1,000 rows per transaction | one fsync per 1,000 rows. Throughput limited mostly by CPU and indexes, not fsync                                                    |

The last row is the key to Stage 2's batched consumer.

## 7. Dirty pages and checkpoints

After the commit, the changed pages are still only in `shared_buffers` (memory). They are **dirty**. Three mechanisms eventually write them to the data files:

| Mechanism                        | Job                                                                                                                                 |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Backend itself**               | If it needs a free buffer and the one it would evict is dirty, it must write it first (undesirable: this adds latency to a request) |
| **Background writer (bgwriter)** | Continuously writes some dirty pages ahead of time so backends rarely have to                                                       |
| **Checkpointer**                 | Periodically writes **all** dirty pages, then records "everything up to this WAL point is safely in the data files"                 |

### What a checkpoint is

A **checkpoint** is a point in the WAL where Postgres guarantees every earlier change is already in the data files. It bounds how much WAL must be replayed after a crash.

A checkpoint is triggered by:

- **Time**: `checkpoint_timeout` (default 5 minutes), or
- **WAL volume**: `max_wal_size` (default 1 GB) being approached.

Postgres **spreads** the checkpoint's writes over time (`checkpoint_completion_target`, default 0.9 of the interval) to avoid one giant burst.

### Why checkpoints cause latency spikes

Under sustained writes a checkpoint produces a large amount of disk I/O. That competes with WAL fsyncs and with reads, so **commit latency and p99 can spike while a checkpoint runs**. This is exactly what experiment **B11 (table growth soak)** is looking for, and why short tests hide it.

### Full-page writes (important for WAL size)

The first time a page is modified **after a checkpoint**, Postgres writes the **entire 8 KB page** into the WAL, not just the small change (`full_page_writes`, on by default). This protects against **torn pages** (a page half-written during a crash).

Effect:

- Right after a checkpoint, WAL volume per insert is **much larger** than the row itself.
- It decays as pages are already "touched" since the checkpoint.
- Frequent checkpoints mean more full-page writes, so **more WAL and more I/O**.
- Inserts that hit **many different pages** (random keys) trigger far more full-page writes than inserts that hit the **same recent page** (sequential keys). See the next section.

## 8. Crash recovery

This is why the design is safe.

```txt
 timeline (WAL, left = older)
 |----------|=========================|~~~~~~~~~~~~~~~|X crash
        checkpoint                 commits
        (redo point)         (flushed to WAL)
```

On restart after a crash:

1. Postgres finds the **last checkpoint** and its "redo point" in the WAL.
2. It **replays every WAL record after that point**, reapplying changes to the data pages.
3. When it reaches the end of valid WAL, the database is consistent and open.

What survives and what does not:

| State at crash time                                                          | Outcome                                         |
| ---------------------------------------------------------------------------- | ----------------------------------------------- |
| Transaction **committed** and WAL fsynced                                    | **Survives.** Recovered by replay               |
| Transaction **not yet committed**                                            | **Gone.** Rolled back (its changes are ignored) |
| Dirty pages never written to data files                                      | Fine, rebuilt from WAL                          |
| Commit returned to client but WAL not yet fsynced (`synchronous_commit=off`) | **Can be lost.** See next sections              |

> This is the crux of **B6** and of every "did I lose acknowledged events?" audit in the project: **a 202 backed by a fsynced commit means the row survives a crash.**

## 9. What your Stage 1 INSERT costs

Your schema:

```sql
CREATE TABLE events (
  event_id       uuid PRIMARY KEY,          -- random UUID  -> unique index
  tenant_id      text        NOT NULL,
  type           text        NOT NULL,
  occurred_at    timestamptz NOT NULL,
  received_at    timestamptz NOT NULL DEFAULT now(),
  schema_version int         NOT NULL DEFAULT 1,
  payload        jsonb       NOT NULL
);
CREATE INDEX events_tenant_time_idx ON events (tenant_id, occurred_at);
```

Each insert does:

| Work                       | Where                                | Notes                                                                                                      |
| -------------------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| Heap tuple insert          | The table's data pages               | Appends to a page with free space, usually the "current" last page, so locality is good                    |
| **PK index insert**        | B-tree on `event_id`                 | **Random UUID means a random position in the tree**                                                        |
| **Secondary index insert** | B-tree on `(tenant_id, occurred_at)` | Mostly clustered by tenant and time, better locality                                                       |
| WAL records                | WAL                                  | One for the heap change, one per index change, plus the commit record                                      |
| TOAST                      | Separate storage                     | Only if `payload` gets large (roughly above 2 KB, compressed or moved out of line). Not an issue at ~500 B |
| fsync                      | WAL                                  | Once per commit                                                                                            |

### Why the random UUID primary key is expensive

A B-tree keeps keys sorted. A **random** key lands on a **random leaf page** every time:

```txt
 time-ordered key (e.g. sequential id):      random UUID:
 inserts go to the right edge                inserts scatter everywhere
 [.....][.....][.....][NEW]  <- hot page      [NEW][NEW][.....][NEW][.....][NEW]
 stays in memory, few pages touched           touches many different pages
```

Consequences of random keys:

- Many **different pages** become dirty, which means more to write at checkpoint.
- More **full-page writes** into the WAL after each checkpoint (each newly touched page logs 8 KB).
- Pages **split** as they fill, leaving them partly empty and the index larger.
- Poorer **cache hit ratio** as the index grows beyond memory (B11).

This is what **B5 (index write amplification)** measures when it compares "random-UUID PK vs a time-ordered key".

### Write amplification

**Write amplification** = bytes physically written divided by bytes of useful data. A ~500 B event can cause: a heap write, two index writes, WAL for all of them, then later the data-page writes at checkpoint, plus full-page images. The total bytes written to disk can be many times the event size. That is why _bytes per event_ drives cost everywhere (B7).

## 10. `synchronous_commit`

This setting controls **whether `COMMIT` waits for the WAL fsync**.

| Setting                                 | `COMMIT` returns when...                    | Risk on crash                           |
| --------------------------------------- | ------------------------------------------- | --------------------------------------- |
| `on` (default)                          | WAL is flushed to local disk                | None for committed transactions         |
| `off`                                   | immediately, without waiting for the flush  | The most recent commits can be **lost** |
| `local`, `remote_write`, `remote_apply` | related to replicas (relevant from Stage 6) | depends on level                        |

### What `off` does and does not risk

- Transactions are still written to the WAL, just **flushed asynchronously** by the WAL writer shortly after (`wal_writer_delay`, default 200 ms).
- On a crash you can lose **a small window of recent commits** (up to roughly three times `wal_writer_delay`).
- **It does not corrupt the database.** You lose the latest transactions as a clean cut, not randomly.
- It can raise throughput significantly, because commits no longer wait for fsync.

> **The trade:** you answered the client "202 accepted" for events that may not survive a crash. That is **acknowledged data loss**. In B6 you measure exactly how many rows vanish vs 202 responses returned.

This is a **diagnostic experiment, not a setting to keep.** The same trade-off returns in Stage 2 as Kafka `acks=1` vs `acks=all`:

| Postgres                 | Kafka (Stage 2)     |
| ------------------------ | ------------------- |
| `synchronous_commit=on`  | `acks=all`          |
| `synchronous_commit=off` | `acks=1` / `acks=0` |

Two other durability-related settings to know about, **but never to change** in this project:

- `fsync=off` : disables flushing entirely. Can corrupt the database on crash. Not the same as `synchronous_commit=off`.
- `full_page_writes=off`: risks torn-page corruption.

## 11. Batching

Compare two ways to insert 1,000 rows:

| Style                                                           | Commits | fsyncs                                | Round trips |
| --------------------------------------------------------------- | ------- | ------------------------------------- | ----------- |
| 1,000 separate `INSERT` statements (autocommit)                 | 1,000   | up to 1,000 (reduced by group commit) | 1,000       |
| One `INSERT ... SELECT ... FROM unnest(...)` in one transaction | **1**   | **1**                                 | **1**       |

Batching amortizes the expensive parts: **the fsync, the network round trip, and the parse/plan cost**. It does not remove the per-row costs (heap and index inserts, WAL volume), but those are far cheaper than the fixed per-commit cost.

Why this matters for EventPulse:

- **Stage 1** inserts one row per HTTP request, so you pay a full commit per event. That is the naive baseline.
- **Stage 2's consumer** collects a batch from Kafka and does a single multi-row insert and commit. Much of the throughput gain at the database comes from this, not from Kafka itself.

Your Stage 2 SQL already uses the batch form:

```sql
INSERT INTO events (...)
SELECT * FROM unnest($1::uuid[], $2::text[], ...)
ON CONFLICT (event_id) DO NOTHING;
```

## 12. Where it becomes the bottleneck

The write path has several places it can run out of capacity. Learn the symptom of each, so you can diagnose rather than guess.

| Bottleneck                             | Symptoms                                                                          | How to confirm                                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| **WAL fsync latency**                  | Commit time dominates; low CPU on both API and DB; latency scales with disk speed | Wait events `WALSync` / `WALWrite`; `iostat -x` shows high `await` on the WAL disk; `pg_test_fsync` is slow |
| **Disk throughput (WAL + checkpoint)** | Disk utilization near 100%; spikes every few minutes                              | `iostat -x 1` (`%util`, `await`); checkpoint timing in stats                                                |
| **CPU in the backend**                 | DB CPU pegged; index maintenance and parsing dominate                             | `pidstat`, `pg_stat_statements` mean time, flame graph                                                      |
| **Index overhead**                     | Throughput drops as you add indexes                                               | B5: compare 0, 1, 3, 5 indexes                                                                              |
| **Lock contention**                    | High latency with **low CPU**; waiters piled up                                   | `pg_stat_activity` wait events of type `Lock`; `pg_blocking_pids` (B4)                                      |
| **Checkpoint storms**                  | Periodic p99 spikes                                                               | Checkpoint counts and write times; `max_wal_size` hit early                                                 |
| **Pool exhaustion**                    | `waitingCount` rising with idle DB                                                | Pool counters vs DB CPU                                                                                     |

### A useful diagnostic: "low CPU, high latency"

If latency is high but CPU is low everywhere, something is **waiting**: on fsync, on a lock, on a pool slot, or on disk. Check `wait_event_type` and `wait_event` in `pg_stat_activity` first. It tells you what each backend is waiting for.

## 13. Prove it yourself

Run these and write the observations in your notebook.

### Measure how slow fsync is on your machine

```bash
# run inside the Postgres container (or any host with the Postgres client tools)
pg_test_fsync
```

It prints operations per second and per-operation time for different sync methods. This number is your **commit latency floor**.

### Look at the settings

```sql
SHOW synchronous_commit;
SHOW wal_writer_delay;
SHOW checkpoint_timeout;
SHOW max_wal_size;
SHOW full_page_writes;
SHOW shared_buffers;
```

### Measure WAL generated per event

```sql
-- before the run
SELECT pg_current_wal_lsn() AS start_lsn \gset

-- ... run N inserts (e.g. a k6 run, or a loop) ...

-- after the run
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'start_lsn')) AS wal_generated;
-- divide by N to get WAL bytes per event
```

Repeat with 0, 1, and 3 secondary indexes, and with a random UUID vs a sequential key. You get B5's central number from your own data.

### See what backends are waiting on

```sql
SELECT wait_event_type, wait_event, state, count(*)
FROM pg_stat_activity
WHERE datname = 'eventpulse'
GROUP BY 1, 2, 3
ORDER BY 4 DESC;
```

Under write load, expect to see `IO`-type waits such as `WALSync`/`WALWrite` (commits waiting for fsync), or `Lock` waits if contention exists.

### WAL activity counters (Postgres 14+)

```sql
SELECT wal_records, wal_fpi, wal_bytes, wal_write, wal_sync
FROM pg_stat_wal;
```

`wal_fpi` is the count of **full-page images**, which is the full-page-write effect from section 7. Watch how it spikes after a checkpoint.

### Checkpoint behavior

```sql
-- Postgres 17+
SELECT * FROM pg_stat_checkpointer;
-- older versions
SELECT checkpoints_timed, checkpoints_req, checkpoint_write_time, checkpoint_sync_time
FROM pg_stat_bgwriter;
```

`checkpoints_req` (or the "requested" counter) going up means checkpoints were triggered by **WAL volume** (`max_wal_size`), not by the timer. That is a sign of heavy write load.

### Watch the disk

```bash
iostat -x 1       # watch %util and await on the device holding the data and WAL
```

### Fast experiment: `synchronous_commit` on vs off

```sql
-- per session, for a quick comparison
SET synchronous_commit = off;
```

Run the same load both ways and compare throughput and p99. Then do the crash test from B6 to see what you give up.

## 15. Common confusions

**"`COMMIT` means the data is in the table file on disk."**
No. It means the **WAL record is on disk**. The table and index pages may still be dirty in memory and will be written later. Recovery rebuilds them from the WAL.

**"Writing to a file means it is durable."**
Not until `fsync`. Before that, the data may only be in the OS cache and is lost on power failure.

**"`synchronous_commit=off` can corrupt my database."**
No. It risks losing the **most recent commits**, cleanly. `fsync=off` is the dangerous one.

**"The WAL is the same as the table."**
No. WAL is an append-only log of **changes**. Tables are the **current state**. You can rebuild the state from the log, but not the other way around.

**"More connections means more commits per second."**
Partly. Group commit lets concurrent committers share fsyncs, so some concurrency helps. Beyond a point, you add contention and context switching instead.

**"A faster API will fix slow inserts."**
No. If commit/fsync is the limit, your Node CPU can be idle while latency is high. Check wait events and disk first.

**"Bigger `shared_buffers` makes writes faster."**
It mainly helps **reads** and reduces how often dirty pages must be evicted. The commit still waits for the WAL fsync regardless.

**"Duplicates are free with `ON CONFLICT DO NOTHING`."**
You still pay the unique-index probe. You just skip the insert.

**"Checkpoints are a bug."**
They are normal and necessary. They become a **problem** only when they are too frequent or too bursty. Tuning is for later, since Stage 1 records the untuned baseline.

## 16. Self-test questions

Answer aloud first. Answers are below.

1. What exactly is written to disk at `COMMIT`, and what is not?
2. Why is commit latency mostly fsync latency?
3. What is group commit and why does it matter?
4. Why does Postgres write a WAL instead of updating data pages directly at commit?
5. Why does a random UUID primary key cost more than a sequential one?
6. What does `synchronous_commit=off` trade away, and what does it not risk?
7. After a crash, how does Postgres get back to a consistent state?
8. Why is inserting 1,000 rows in one transaction so much faster than 1,000 separate inserts?
9. Latency is high, CPU is low everywhere. What do you check first?

<details>
<summary>Answers</summary>

1. The **WAL records** (including the commit record) are flushed and fsynced. The heap and index **data pages** are not necessarily written yet; they are dirty in memory and written later by the background writer and checkpointer.
2. Everything else in the insert is in-memory work taking microseconds. The one step that must reach physical storage and wait for confirmation is the WAL fsync.
3. Multiple concurrent commits are covered by **one** fsync. It means throughput under concurrency is far higher than `1 / fsync latency`, and one slow fsync is amortized across many transactions.
4. The WAL is a single **sequential append**, which is fast and atomic-friendly. Updating data pages directly means many scattered random writes, slow and unsafe if a crash interrupts them. The log lets the slow writes happen later and be rebuilt after a crash.
5. A random key lands on a random index page every time. Many different pages become dirty, produce more full-page images in the WAL after a checkpoint, cause page splits, and hurt cache locality. A sequential key keeps hitting the same hot right-edge page.
6. It trades **durability of the most recent commits** for lower commit latency: a crash can lose up to a short window of already-acknowledged transactions. It does **not** corrupt the database, because the WAL is still written in order.
7. It finds the last checkpoint, replays WAL records from that point forward to rebuild the data pages, and discards uncommitted transactions.
8. One commit means **one fsync** (instead of up to 1,000), one network round trip, and one parse/plan. The per-row heap and index work still happens, but the large fixed per-commit costs are shared.
9. `wait_event_type` / `wait_event` in `pg_stat_activity`. Something is waiting: on WAL fsync (`WALSync`), on a lock, on I/O, or on a pool slot in the client. Then `iostat -x` for disk, and `pool.waitingCount` for the client side.

</details>

## 17. Glossary and cheat sheet

| Term                      | Meaning                                                                                      |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| **WAL**                   | Write-Ahead Log: append-only log of every change; made durable at commit                     |
| **LSN**                   | Log Sequence Number: a position in the WAL (a growing byte offset)                           |
| **fsync**                 | Forcing data from OS cache to physical disk and waiting for confirmation                     |
| **shared_buffers**        | Postgres's in-memory cache of data pages                                                     |
| **dirty page**            | A page changed in memory but not yet written to its data file                                |
| **bgwriter**              | Background process that writes some dirty pages ahead of time                                |
| **checkpoint**            | Point where all earlier changes are guaranteed to be in the data files; bounds recovery work |
| **redo point**            | WAL position where crash recovery starts replaying                                           |
| **full-page write (FPI)** | Whole 8 KB page logged to WAL on first change after a checkpoint, to prevent torn pages      |
| **group commit**          | Multiple commits sharing a single WAL fsync                                                  |
| **heap**                  | The table's main storage (rows, in pages)                                                    |
| **TOAST**                 | Out-of-line storage for large values                                                         |
| **write amplification**   | Physical bytes written divided by useful bytes written                                       |
| **`synchronous_commit`**  | Whether `COMMIT` waits for the WAL flush                                                     |

### Cheat sheet

```txt
INSERT  -> change page in memory + append WAL record
COMMIT  -> fsync WAL, then return           <- the durability point & the wait
later   -> bgwriter/checkpoint write data pages (not on the request path)
crash   -> replay WAL from last checkpoint  -> committed data survives

commit latency   ~= fsync latency
group commit      = many commits share one fsync
every index       = extra page changes + extra WAL per insert
random UUID PK    = scattered pages + more full-page writes + splits
batching          = 1 fsync / 1 round trip for N rows
synchronous_commit=off = faster, but recent acked commits can be lost (no corruption)
low CPU + high latency = something is WAITING: check wait_event
```

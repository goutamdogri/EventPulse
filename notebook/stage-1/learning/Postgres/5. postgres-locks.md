## 1. TL;DR

- A **lock** is a rule that makes one transaction **wait** while another is using something, so they don't corrupt each other.
- Postgres has **row locks**, **table locks**, **advisory locks** (you define them), and **internal lightweight locks** (the engine's own).
- **MVCC removes most read/write blocking**, but **two writers on the same row still queue**, and **schema changes can block everything**.
- Locks are held **until the transaction ends** (commit or rollback), not until the statement ends. That includes the commit's **fsync wait**.
- So a **hot row** serializes all its writers at roughly `1 / (transaction duration)` per second, **no matter how much CPU or hardware you add**.
- The signature of lock trouble is **high latency with low CPU**: requests are _waiting_, not working.
- Two deadly patterns: **hot rows** (B4) and **a schema change stuck behind a long query** (blocks everyone behind it).

> **One-line version:** _Locks make writers take turns, and the turn length is the whole transaction, so the shorter and less shared your transactions are, the faster the system goes._

## 2. The mental model

Think of an office with **meeting rooms** and a **shared whiteboard**.

| Office                                                                                    | Postgres                                                    |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| Anyone can **read** a printed copy of yesterday's whiteboard at any time                  | **MVCC snapshot reads**: never blocked by writers           |
| To **edit one section** of the whiteboard you must hold the marker for that section       | **Row lock** on that row                                    |
| If someone holds the marker, you **queue** until they put it down                         | Waiting on a row lock                                       |
| They don't put it down when they finish writing, but only when they **leave the meeting** | Lock held until **COMMIT / ROLLBACK**                       |
| To **repaint the whole room** everyone must leave                                         | **ACCESS EXCLUSIVE** table lock (`ALTER TABLE`, `TRUNCATE`) |
| Two people each hold a marker the other one needs, and both refuse to give up             | **Deadlock**. The manager (deadlock detector) kicks one out |
| Booking sign-up sheet you define yourself                                                 | **Advisory lock**                                           |

## 3. Why locks exist if MVCC exists

Quick recap from the MVCC notes:

| Conflict                             | Handled by                                         |
| ------------------------------------ | -------------------------------------------------- |
| Reader vs writer                     | **MVCC.** Reader sees an old version; no lock wait |
| Reader vs reader                     | No conflict                                        |
| **Writer vs writer on the same row** | **Row lock.** Second writer waits                  |
| **Schema change vs anything**        | **Table lock**                                     |
| Your own coordination needs          | **Advisory lock**                                  |

So the rule of thumb is:

> **MVCC is for reads. Locks are for writes and for structure changes.**

If your system is insert-only (like the Stage 1 `events` table), writers rarely conflict at all, because each insert creates a **brand new row**. Locks become a problem when many writers **touch the same row** (counters, status flags) or when someone **changes the table's structure**.

## 4. The kinds of locks at a glance

| Kind                            | Granularity                | Who takes it                                                  | Visible to you via                                           |
| ------------------------------- | -------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------ |
| **Row-level locks**             | One row                    | `UPDATE`, `DELETE`, `SELECT ... FOR UPDATE` etc.              | `pg_stat_activity` waits; `pg_locks` (transactionid / tuple) |
| **Table-level locks**           | Whole table                | **Every statement** (usually a weak mode), DDL (strong modes) | `pg_locks` (relation)                                        |
| **Advisory locks**              | A number you choose        | Your application                                              | `pg_locks` (advisory)                                        |
| **Lightweight locks (LWLocks)** | Internal shared structures | Postgres itself, very briefly                                 | `wait_event_type = 'LWLock'`                                 |

The first three are the ones you control and reason about. The fourth is an internal cost that shows up at high concurrency (section 13).

## 5. Row-level locks

### When a row lock is taken

- `UPDATE` and `DELETE` automatically lock the rows they change.
- `SELECT ... FOR UPDATE` (and its relatives) lock rows **explicitly** without changing them. Used for "read, decide, then write" safely.

### Modes (from strongest to weakest)

| Mode                | Typical use                                                                               | Blocks                              |
| ------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------- |
| `FOR UPDATE`        | "I'm going to change or delete this row"                                                  | Everything below                    |
| `FOR NO KEY UPDATE` | Update that doesn't touch key columns. This is what a normal `UPDATE` takes in most cases | Weaker modes except `FOR KEY SHARE` |
| `FOR SHARE`         | "Keep this row from changing while I read it"                                             | Updates and deletes                 |
| `FOR KEY SHARE`     | Taken by foreign key checks                                                               | Only changes to the key / deletes   |

You rarely need to memorize these. The important point: **plain `SELECT` takes no row lock at all.** Only writes and explicit `FOR ...` clauses do.

### Where is the lock stored?

Not in a big lock table in memory. Postgres records the lock **on the row itself** (using the `xmax` field you met in the MVCC notes). Consequence:

- **Locking millions of rows is cheap in memory** (no lock-table blowup).
- But it means **taking a row lock can write to the table page** (a dirty page, WAL), even for `SELECT ... FOR UPDATE`.

### What a waiter actually waits for

When transaction B wants a row that transaction A has locked, B really waits for **A's transaction to finish** (a `transactionid` wait). When A commits or rolls back, B wakes up and continues.

### Two useful clauses

| Clause        | Behavior                                                  | Use                                                                                         |
| ------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `NOWAIT`      | Fail immediately with an error instead of waiting         | "Try it, but don't queue"                                                                   |
| `SKIP LOCKED` | **Skip rows that are locked** and take the next free ones | **Work queues**: many workers each grab different rows. Your Stage 3 outbox relay uses this |

```sql
-- Stage 3 outbox relay pattern (preview)
SELECT id, payload FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
```

## 6. Table-level locks

**Every statement takes a table lock**, usually a weak one that you never notice. There are eight modes, from weak to strong. The ones that matter:

| Mode                     | Taken by                                                                                                          | Notes                                                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `ACCESS SHARE`           | Plain `SELECT`                                                                                                    | Weakest. Conflicts only with `ACCESS EXCLUSIVE`                     |
| `ROW SHARE`              | `SELECT ... FOR UPDATE/SHARE`                                                                                     |                                                                     |
| **`ROW EXCLUSIVE`**      | **`INSERT`, `UPDATE`, `DELETE`**                                                                                  | Does **not** conflict with itself. **Many inserts run in parallel** |
| `SHARE UPDATE EXCLUSIVE` | Plain `VACUUM`, `CREATE INDEX CONCURRENTLY`, some `ALTER TABLE`                                                   | Doesn't block reads or writes, but only one at a time               |
| `SHARE`                  | Plain `CREATE INDEX`                                                                                              | **Blocks writes** (INSERT/UPDATE/DELETE) for the build's duration   |
| `EXCLUSIVE`              | Rare                                                                                                              | Blocks everything except plain reads                                |
| **`ACCESS EXCLUSIVE`**   | **`ALTER TABLE` (most forms), `DROP TABLE`, `TRUNCATE`, `VACUUM FULL`, `REINDEX` (plain), explicit `LOCK TABLE`** | **Blocks everything, even plain `SELECT`**                          |

### The two facts to remember

1. **`INSERT` takes `ROW EXCLUSIVE`, which doesn't conflict with other `ROW EXCLUSIVE` locks.** That's why thousands of concurrent inserts into `events` don't block each other at the table level.
2. **`ACCESS EXCLUSIVE` conflicts with _everything_.** Any schema change that needs it must wait for all existing queries on the table to finish, and while it waits (or runs), **everything else queues behind it** (see section 9).

### A simplified conflict picture

```txt
                     SELECT   INSERT/UPDATE/DELETE   CREATE INDEX   ALTER TABLE / TRUNCATE
 SELECT                ok              ok                  ok              BLOCKS
 INSERT/UPD/DEL        ok              ok                BLOCKS            BLOCKS
 CREATE INDEX          ok            BLOCKS               (1 at a time)     BLOCKS
 ALTER TABLE/TRUNC   BLOCKS          BLOCKS               BLOCKS            BLOCKS
```

(Read as: can the row's operation run while the column's operation is in progress.)

### Safer alternatives for busy tables

| Dangerous                             | Safer                                                                                             |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `CREATE INDEX` (blocks writes)        | `CREATE INDEX CONCURRENTLY` (slower, doesn't block writes)                                        |
| `DELETE` huge ranges for retention    | Drop a **partition** instead (Stage 6)                                                            |
| `VACUUM FULL`                         | Plain `VACUUM` (let autovacuum do it)                                                             |
| `ALTER TABLE` that rewrites the table | Add columns without heavy defaults; do big changes in steps (Stage 6 "migrations during traffic") |

## 7. Locks are held until the transaction ends

This is the single most important property of locks:

```txt
 BEGIN;
   UPDATE counters SET n = n + 1 WHERE tenant_id = 't1';   <- row lock acquired HERE
   ... other work, network calls, more statements ...
 COMMIT;                                                    <- lock released HERE (after WAL fsync)
```

The lock is **not** released when the `UPDATE` statement finishes. It's released when the **transaction** ends. So:

| Anything inside the transaction...               | ...extends how long others wait                                |
| ------------------------------------------------ | -------------------------------------------------------------- |
| More statements after the lock was taken         | Yes                                                            |
| A network call or `await` to another service     | Yes (terrible)                                                 |
| The **commit's WAL fsync**                       | **Yes.** The lock is released only after the commit is durable |
| A client that goes quiet (`idle in transaction`) | Yes, **indefinitely**                                          |

### Practical rules

- **Keep transactions short.** Do all slow work (validation, calls, computation) _before_ `BEGIN` or after `COMMIT`.
- **Take the contended lock as late as possible** in a transaction. If a transaction must touch a hot row, do that update **last**, right before `COMMIT`.
- **Never `await` an external call while holding locks.**
- Use `idle_in_transaction_session_timeout` to kill abandoned transactions (they hold locks and block vacuum).

## 8. Hot row contention

This is **experiment B4**, and the clearest example of why "more hardware" doesn't fix a design problem.

### The setup

Every insert also increments a per-tenant counter, in the same transaction:

```sql
BEGIN;
INSERT INTO events (...) VALUES (...);
UPDATE tenant_counters SET n = n + 1 WHERE tenant_id = $1;   -- the hot row
COMMIT;
```

For one busy tenant, **every request updates the same row**.

### What happens

```txt
 req 1:  UPDATE row ----------- holds lock ---- COMMIT (fsync) -> released
 req 2:           waits ......................................... UPDATE ---- COMMIT
 req 3:           waits ................................................................ UPDATE ...
 req 4:           waits .........................................................................
          (all writers for this tenant form a single-file line)
```

### The throughput ceiling for one row

Writers for one row are **fully serialized**. The maximum rate is:

```txt
max updates/sec on one row  ~=  1 / (time the lock is held per transaction)
```

The lock is held from the `UPDATE` until the commit finishes (including fsync). Illustrative numbers:

| Lock hold time                                | Max updates per second on that one row |
| --------------------------------------------- | -------------------------------------- |
| 0.5 ms                                        | about 2,000                            |
| 1 ms                                          | about 1,000                            |
| 2 ms (e.g. UPDATE then more work, then fsync) | about 500                              |
| 10 ms (slow disk or extra statements)         | about 100                              |

_(Illustrative. Measure your own in B4.)_

**This ceiling doesn't care how many CPU cores, connections, or API nodes you have.** Ten times the hardware still has one marker.

### The symptom signature: low CPU, high latency

- Postgres CPU is **low** (backends are asleep, waiting).
- API CPU is **low**.
- **Latency is high** and grows.
- `pg_stat_activity` shows many backends in `wait_event_type = 'Lock'`.
- `pool.waitingCount` grows because every pool connection is stuck in the lock line.

### How it cascades

```txt
 hot row lock queue grows
        -> every pool connection ends up waiting on that lock
        -> pool has no free connection for OTHER tenants' requests
        -> requests wait in the pool queue, then hit connectionTimeoutMillis
        -> 503s for everyone, including tenants who don't touch the hot row
```

One hot tenant can take down all tenants through the shared pool. This is a **noisy neighbor** problem (Stage 5's isolation theme) born from a lock.

### The added MVCC cost

Each counter update also creates a **new row version** (a dead tuple for the old one), so the counter row generates constant garbage for vacuum. Locking pain **plus** bloat.

### Why 1 tenant vs 1,000 tenants matters in B4

With 1,000 tenants, updates spread over 1,000 different rows, so they **don't contend**. That's the experiment's key comparison: **same total load, contention appears only when it concentrates on one row.**

### What fixes it (the design answers)

See section 14. Short version: **don't update a shared row synchronously per event**. Aggregate downstream (Stages 2-4).

## 9. Lock queues and the migration trap

Postgres lock requests are **queued in order**. A waiting request blocks **later** requests that would conflict with it, even if those later requests would have been compatible with the lock currently held.

### The classic incident

```txt
 t=0   A long SELECT (e.g. a report) is running on `events`        holds ACCESS SHARE (fine)
 t=1   You run: ALTER TABLE events ADD COLUMN x int;               needs ACCESS EXCLUSIVE -> WAITS
                                                                    (can't get it while the SELECT runs)
 t=2   A normal INSERT or SELECT arrives                            conflicts with the QUEUED ALTER
                                                                    -> it queues BEHIND the ALTER
 t=3   Every new request queues behind the ALTER, which waits for the report
       => the whole table appears frozen, because of one slow query + one "tiny" ALTER
```

Even a harmless, instant `ALTER` can freeze the table if it queues behind something long.

### Defenses

| Defense                                 | How                                                                                                                    |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **`lock_timeout`**                      | `SET lock_timeout = '2s';` before DDL: the `ALTER` gives up fast instead of queueing and blocking everyone. Then retry |
| Run DDL when no long queries are active | Check `pg_stat_activity` first                                                                                         |
| Keep long reports off the primary       | Use a replica (Stage 6)                                                                                                |
| Keep every transaction short            | Fewer and shorter holders                                                                                              |

This is exactly what Stage 6's "run migrations on large tables during traffic" experiment tests.

## 10. Deadlocks

A **deadlock** is a cycle of waiting: A waits for B while B waits for A. Neither can ever proceed.

```txt
 Tx A: UPDATE counters SET n = n+1 WHERE tenant = 't1';   -- A holds t1
 Tx B: UPDATE counters SET n = n+1 WHERE tenant = 't2';   -- B holds t2
 Tx A: UPDATE counters SET n = n+1 WHERE tenant = 't2';   -- A waits for B
 Tx B: UPDATE counters SET n = n+1 WHERE tenant = 't1';   -- B waits for A  -> DEADLOCK
```

### What Postgres does

- It doesn't check constantly. After a transaction has waited for `deadlock_timeout` (default **1 second**), it runs the **deadlock detector**.
- If a cycle exists, Postgres **aborts one transaction** (the victim) with:

```txt
ERROR:  deadlock detected      (SQLSTATE 40P01)
```

- The other proceeds. The aborted transaction was **rolled back** (and left dead tuples).

### What you do about it

| Action                                                        | Detail                                                                                                                                                                    |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Lock in a consistent order**                                | If every transaction updates rows in the same order (say ascending tenant id), a cycle can't form                                                                         |
| **Keep transactions short**                                   | Less time holding locks, fewer chances to cross                                                                                                                           |
| **Retry on `40P01`**                                          | A deadlock error is **transient**. The right response is to retry the whole transaction (with backoff). This is a transient-error class for your Stage 3 error classifier |
| Avoid taking many row locks one by one in unpredictable order | E.g. batch updates should sort keys first                                                                                                                                 |

> **Related transient errors** worth retrying: `40001` (serialization failure) and `40P01` (deadlock). Both are normal under concurrency, not bugs.

## 11. Waiting on unique keys

Inserts don't lock _existing_ rows, but **unique indexes create a different kind of wait**:

- If transaction A inserts key `K` (not yet committed) and transaction B tries to insert the **same** `K`, B **waits** for A's outcome.
  - A **commits** -> B hits the conflict (an error, or silently skipped with `ON CONFLICT DO NOTHING`).
  - A **rolls back** -> B's insert succeeds.

This is how your duplicate-`event_id` handling stays correct under concurrent retries (S1-F4). It's also a (usually brief) lock wait to remember when a **flood of duplicate keys** hits at once: the waiters queue behind the first inserter's transaction.

## 12. Advisory locks

An **advisory lock** is a lock on **a number (or two numbers) you pick**. Postgres enforces it but gives it no meaning. Your application defines what it protects.

```sql
SELECT pg_advisory_lock(42);          -- session-level: held until unlock or session ends
SELECT pg_advisory_unlock(42);

SELECT pg_advisory_xact_lock(42);     -- transaction-level: auto-released at COMMIT/ROLLBACK
SELECT pg_try_advisory_lock(42);      -- non-blocking: returns true/false
```

### Good uses

- "Only one instance of this background job runs at a time."
- "Only one process may run this migration or rebuild."
- Serializing work on a logical key that isn't a single row.

### Cautions

| Caution                                                           | Why                                                                                                                                                    |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Session-level advisory locks vs PgBouncer transaction pooling** | The server connection can be handed to another client, so session-level locks leak or vanish. Prefer **transaction-level** advisory locks (Stage 6 S2) |
| **Pool connections**                                              | A session-level lock held by a pooled connection stays held when the connection returns to the pool                                                    |
| Don't treat as a distributed lock across systems                  | It's only as good as the single database connection; the broader "distributed lock" problem (fencing tokens, timeouts) comes later in the project      |

## 13. Lightweight locks

Separate from everything above, Postgres uses **LWLocks** to protect its **own internal shared structures** for tiny moments. You can't take them, but you can see them as wait events (`wait_event_type = 'LWLock'`; exact names vary by version).

Examples of what they protect:

| Internal area                       | Why it can become contended                                                |
| ----------------------------------- | -------------------------------------------------------------------------- |
| **WAL insert / WAL write**          | Every backend appends to the same WAL (see the write path notes)           |
| **Buffer mapping / buffer content** | Many backends accessing the same hot pages, e.g. the right-edge index page |
| **Lock manager**                    | Many backends taking table-level locks simultaneously                      |
| **Process array**                   | Every snapshot has to look at the list of running transactions             |

You mostly notice these **at high concurrency**: many active backends hammering shared structures. This is a big part of **why too many connections slows Postgres down** (see the process-per-connection notes, "Effect 2: contention on shared structures").

You don't tune LWLocks directly. You reduce them by **reducing concurrency** (a sensible pool size), **batching** (fewer, larger commits), and **avoiding hot pages** (ordered vs random keys, hot rows).

## 14. Designing to avoid contention

Contention is a **design** problem. Hardware only helps if you change what is shared.

| Pattern                       | Idea                                                                                       | Trade-off                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Insert, don't update**      | Append an event row instead of updating a counter. Compute totals with `SUM`/`COUNT` later | Reads must aggregate (or use a materialized/rollup table)                                                   |
| **Aggregate downstream**      | Let a stream processor compute counts (Stages 2-4)                                         | New infrastructure, but removes the shared row from the request path. **This is the intended answer to B4** |
| **Sharded counters**          | Keep N counter rows per tenant, update a random one, sum on read                           | Reads cost N rows; no strict ordering                                                                       |
| **Batch updates**             | Accumulate in memory or a queue, apply one `UPDATE n = n + 500` per interval               | Slight delay and loss risk if not durable                                                                   |
| **Shorter transactions**      | Do the hot update **last** in the transaction                                              | Helps, but doesn't remove the serial ceiling                                                                |
| **Per-tenant isolation**      | Dedicated rows/partitions/shards per tenant (Stage 6)                                      | Complexity                                                                                                  |
| **`SKIP LOCKED` work queues** | Workers take **different** rows instead of fighting over the same ones                     | Only suits queue-like workloads                                                                             |

> **Rule:** if many requests need to update **one** shared value synchronously, you have built a **single-file queue**. Move the aggregation out of the request path.

## 15. Prove it yourself

Use a scratch table. Open **two or three** `psql` terminals.

### Setup

```sql
CREATE TABLE lock_demo (id int PRIMARY KEY, n int);
INSERT INTO lock_demo VALUES (1, 0), (2, 0);
```

### Demo 1: a row lock makes the second writer wait

Terminal 1:

```sql
BEGIN;
UPDATE lock_demo SET n = n + 1 WHERE id = 1;     -- holds the row lock; do NOT commit yet
```

Terminal 2:

```sql
UPDATE lock_demo SET n = n + 1 WHERE id = 1;     -- hangs
UPDATE lock_demo SET n = n + 1 WHERE id = 2;     -- (try this one in a third terminal) returns instantly: different row
```

Terminal 3, see who waits for whom:

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, wait_event,
       now() - query_start AS waiting_for, left(query, 50) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Then `COMMIT;` in Terminal 1: Terminal 2 finishes. Note `wait_event_type = Lock`.

### Demo 2: a plain SELECT is not blocked

While Terminal 1 still holds the row lock (before committing), run in another terminal:

```sql
SELECT * FROM lock_demo;     -- returns immediately, shows the OLD value (MVCC)
```

### Demo 3: `ACCESS EXCLUSIVE` blocks even SELECT

Terminal 1:

```sql
BEGIN;
LOCK TABLE lock_demo IN ACCESS EXCLUSIVE MODE;   -- or: ALTER TABLE lock_demo ADD COLUMN x int;
```

Terminal 2:

```sql
SELECT * FROM lock_demo;     -- hangs
```

`ROLLBACK;` in Terminal 1 to release.

### Demo 4: the migration queue trap

Terminal 1:

```sql
BEGIN;
SELECT * FROM lock_demo;     -- takes ACCESS SHARE, held until the transaction ends
```

Terminal 2:

```sql
ALTER TABLE lock_demo ADD COLUMN y int;     -- waits for ACCESS EXCLUSIVE
```

Terminal 3:

```sql
SELECT * FROM lock_demo;     -- also hangs! It queued behind the ALTER
```

Now see the cure. In Terminal 2 cancel, then retry with a timeout:

```sql
SET lock_timeout = '2s';
ALTER TABLE lock_demo ADD COLUMN y int;     -- fails after 2s instead of freezing everyone
```

### Demo 5: a deadlock

Terminal 1:

```sql
BEGIN;
UPDATE lock_demo SET n = n + 1 WHERE id = 1;
```

Terminal 2:

```sql
BEGIN;
UPDATE lock_demo SET n = n + 1 WHERE id = 2;
UPDATE lock_demo SET n = n + 1 WHERE id = 1;     -- waits for T1
```

Terminal 1:

```sql
UPDATE lock_demo SET n = n + 1 WHERE id = 2;     -- cycle! after ~1s one gets: ERROR: deadlock detected
```

### Demo 6: `SKIP LOCKED`

Terminal 1:

```sql
BEGIN;
SELECT * FROM lock_demo WHERE id = 1 FOR UPDATE;
```

Terminal 2:

```sql
SELECT * FROM lock_demo ORDER BY id FOR UPDATE SKIP LOCKED;   -- returns only id = 2, skipping the locked row
```

### Look at the lock table

```sql
SELECT locktype, relation::regclass AS rel, mode, granted, pid
FROM pg_locks
WHERE pid <> pg_backend_pid()
ORDER BY granted, pid;
```

`granted = false` rows are the **waiters**. A row-lock wait shows up as a `transactionid` lock being waited on.

### Find the whole blocking chain (who is the root blocker?)

```sql
SELECT blocked.pid AS blocked_pid,
       blocker.pid AS blocker_pid,
       blocker.state AS blocker_state,
       now() - blocker.xact_start AS blocker_xact_age,
       left(blocker.query, 60) AS blocker_last_query
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS b(pid) ON true
JOIN pg_stat_activity blocker ON blocker.pid = b.pid;
```

If the blocker's state is `idle in transaction`, someone forgot to commit.

### Useful settings

```sql
SHOW deadlock_timeout;                          -- default 1s
SHOW lock_timeout;                              -- default 0 (wait forever)
SHOW idle_in_transaction_session_timeout;       -- default 0 (never)
SHOW log_lock_waits;                            -- set to on to log waits longer than deadlock_timeout
```

### For B4

1. Create `tenant_counters` and add the `UPDATE` in the same transaction as the insert.
2. Run with **1 tenant**, then **1,000 tenants**, same total rate.
3. Record: throughput, p99, Postgres CPU, wait events (`Lock`), `pool.waitingCount`, blocked count from the query above.
4. Expect: CPU low, latency high, throughput ceiling near `1 / lock hold time` with 1 tenant; healthy with 1,000.
5. Try the "do the hot update last in the transaction" variant and see how much the ceiling moves.

## 16. Stage 1 experiments

| Experiment                            | Lock connection                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| **B4 Lock contention with a hot row** | The main one: one-row serialization, low CPU / high latency, `Lock` waits            |
| **B2 Pool exhaustion**                | Lock queues can occupy every pool connection, starving unrelated requests            |
| **B3 Slow database propagates**       | Anything that lengthens a transaction lengthens lock hold time                       |
| **B6 Durability knob**                | Commit fsync is part of lock hold time, so cheaper commits raise the hot-row ceiling |
| **B10 Missing timeouts**              | Without `lock_timeout` / `statement_timeout`, requests wait indefinitely on locks    |
| **B8 DB restart under load**          | Open transactions and their locks vanish when Postgres restarts                      |
| **S1-F4 duplicate test**              | Concurrent same-`event_id` inserts wait on each other's outcome                      |

| Stage                                                  | Lock connection                                                                |
| ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **Stage 3: outbox relay**                              | `FOR UPDATE SKIP LOCKED`, and ordering caveats with multiple relays            |
| **Stage 3: error classifier**                          | Treat deadlock (`40P01`) and serialization failure (`40001`) as transient      |
| **Stage 4 / 5: checkpoint and alert state tables**     | Hot rows again if many writers update the same row                             |
| **Stage 5: noisy neighbor**                            | Lock waits are another route for one tenant to hurt others via the shared pool |
| **Stage 6: migrations on large tables during traffic** | The `ACCESS EXCLUSIVE` queue trap and `lock_timeout`                           |
| **Stage 6: PgBouncer transaction mode**                | Session-level advisory locks break                                             |

## 17. Common confusions

**"MVCC means there are no locks."**
It means reads don't block writes. Writers on the same row, and schema changes, still lock.

**"My CPU is low, so the database must be healthy."**
Low CPU with high latency usually means **waiting**, on locks, on I/O, or on the pool. Check `wait_event_type`.

**"The lock is released when my UPDATE finishes."**
It's released when the **transaction** ends, after the commit is durable.

**"More connections will fix a lock queue."**
No. Extra connections just join the queue (and eat your scarce connection budget). The row is the bottleneck.

**"`INSERT`s block each other."**
Not at the table level (`ROW EXCLUSIVE` doesn't conflict with itself). They only wait on each other for identical unique keys.

**"A quick `ALTER TABLE` is harmless."**
It needs `ACCESS EXCLUSIVE`; if it queues behind a long query, it freezes every other query on that table. Always use `lock_timeout`.

**"A deadlock is a bug I must eliminate completely."**
Reduce them with consistent lock ordering and short transactions, but also **handle them**: catch `40P01` and retry.

**"`SELECT FOR UPDATE` is read-only."**
It writes lock info to the row, takes a stronger table lock (`ROW SHARE`), and **blocks writers** of those rows.

**"Advisory locks are safe to use with any pooling."**
Session-level ones are not safe with transaction-pooling PgBouncer.

**"Row locks use lots of memory when I lock many rows."**
They're stored on the rows themselves, not in a shared lock table, so memory is fine, but they can cause page writes.

## 18. Self-test questions

Answer aloud first. Answers are below.

1. Why can two `UPDATE`s on the same row not run in parallel even with MVCC?
2. When exactly is a row lock released?
3. A hot row's transaction holds its lock for 2 ms. What's the maximum update rate on that row?
4. Why does low CPU with high latency suggest lock trouble?
5. What does `INSERT` lock at the table level, and why can many inserts run concurrently?
6. Why can a tiny `ALTER TABLE` freeze a busy table, and how do you prevent it?
7. What is a deadlock, how does Postgres resolve it, and what should your code do?
8. Why can one hot tenant cause 503s for other tenants?
9. When would you use `FOR UPDATE SKIP LOCKED`?
10. What's the design fix for a per-tenant counter updated on every event?

<details>
<summary>Answers</summary>

1. MVCC only separates reads from writes. Two writers modifying the same row must serialize to avoid lost updates, so the second waits for the first's row lock until it commits or aborts.
2. When the **transaction** ends (commit or rollback), after the commit's WAL is flushed, not when the statement finishes.
3. About `1 / 0.002` = **500 updates per second**, regardless of CPU, cores, or connections.
4. Backends are asleep waiting (for a lock, I/O, or the pool), not computing. The work isn't CPU-bound, so CPU stays low while latency grows.
5. `ROW EXCLUSIVE`, which doesn't conflict with another `ROW EXCLUSIVE`. Each insert creates a new row, so there's no shared row to fight over (except identical unique keys).
6. `ALTER TABLE` needs `ACCESS EXCLUSIVE`. If it queues behind a long-running query, later queries queue behind it and everything stalls. Prevent with `SET lock_timeout`, running DDL when no long queries are active, and keeping transactions short.
7. A cycle of transactions waiting on each other. After `deadlock_timeout` (1 s) the detector aborts one with error `40P01`. Your code should treat it as transient and **retry** the transaction, and you should reduce occurrences with consistent lock ordering and short transactions.
8. The hot row's lock queue occupies pool connections. When all pool connections are stuck waiting, other tenants' requests queue in the pool and hit the connection timeout, producing 503s.
9. For work queues where many workers each need to grab different unprocessed rows, such as the Stage 3 outbox relay. Locked rows are skipped instead of waited on.
10. Don't update a shared row synchronously per event. Aggregate downstream (stream processing), or append rows and sum later, or use sharded counters.

</details>

## 19. Glossary and cheat sheet

| Term                   | Meaning                                                                     |
| ---------------------- | --------------------------------------------------------------------------- |
| **lock**               | A rule that forces transactions to wait to avoid conflicting access         |
| **row lock**           | Lock on a single row (taken by `UPDATE`, `DELETE`, `SELECT FOR ...`)        |
| **table lock**         | Lock on a whole table, with modes from `ACCESS SHARE` to `ACCESS EXCLUSIVE` |
| **`ACCESS EXCLUSIVE`** | Strongest table lock; blocks even plain `SELECT`                            |
| **`ROW EXCLUSIVE`**    | Table lock taken by `INSERT/UPDATE/DELETE`; doesn't conflict with itself    |
| **hot row**            | A row that many transactions need to update                                 |
| **lock queue**         | Ordered line of lock requests; waiters can block later compatible requests  |
| **deadlock**           | Cycle of transactions each waiting on another                               |
| **`deadlock_timeout`** | How long to wait before checking for a deadlock (default 1 s)               |
| **`lock_timeout`**     | Max time a statement waits for a lock before failing                        |
| **advisory lock**      | Application-defined lock on a number                                        |
| **LWLock**             | Internal lightweight lock protecting shared memory structures               |
| **`SKIP LOCKED`**      | Skip rows locked by others (work queues)                                    |
| **`NOWAIT`**           | Fail immediately instead of waiting for a lock                              |
| **`40P01` / `40001`**  | SQLSTATE for deadlock / serialization failure (both retryable)              |

### Cheat sheet

```txt
SELECT                     -> no row lock, never blocked by writers (MVCC)
INSERT                     -> ROW EXCLUSIVE table lock: inserts don't block each other
UPDATE/DELETE same row     -> second writer WAITS for the first transaction to finish
lock lifetime              = until COMMIT/ROLLBACK (includes the commit fsync)
hot row ceiling            ~= 1 / lock hold time   (hardware does NOT help)
low CPU + high latency     = WAITING -> check wait_event_type = 'Lock'
ALTER TABLE / TRUNCATE     = ACCESS EXCLUSIVE; if it queues, EVERYTHING queues behind it
  -> always SET lock_timeout before DDL
deadlock                   = cycle; Postgres aborts one (40P01) -> retry, lock in consistent order
unique key insert          = second inserter waits for the first's outcome
FOR UPDATE SKIP LOCKED     = work-queue pattern (Stage 3 outbox)
advisory locks             = app-defined; session-level ones break under PgBouncer transaction mode
design fix                 = don't update shared rows per event: aggregate downstream
```

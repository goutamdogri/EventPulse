## 1. TL;DR

- Postgres makes commits fast by writing a **log (WAL)** and leaving changed data pages **dirty in memory**. A **checkpoint** is the periodic job that **writes all those dirty pages to the data files**.
- When it finishes, Postgres records: _"everything before this point in the WAL is safely in the data files."_ That point bounds **how much WAL must be replayed after a crash**, and tells Postgres **which old WAL it can delete or reuse**.
- Checkpoints are **normal and necessary**, not a bug. But they are a **burst of disk I/O**, so under sustained writes they cause **periodic latency spikes**.
- Checkpoints are triggered by **time** (`checkpoint_timeout`, default 5 min) or by **WAL volume** (`max_wal_size`, default 1 GB). If volume triggers them often, your write load is outrunning the settings.
- The first change to a page **after** a checkpoint writes the **whole 8 KB page into WAL** (a full-page image), so WAL volume forms a **sawtooth** that resets at every checkpoint.
- Frequent checkpoints: **faster recovery, more I/O and more WAL.** Infrequent: **less overhead, slower recovery, more WAL on disk.**

> **One-line version:** _A checkpoint is the periodic "flush everything to the data files and write down how far we got" job, and it is the main source of rhythmic latency spikes in a write-heavy Postgres._

## 2. The mental model

Recall the accountant from the write path notes: a fast **notebook** (the WAL) and a slow **ledger** (the data files).

| Accountant                                                                              | Postgres                                                     |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Jot every change in the notebook immediately (fast)                                     | WAL write at commit                                          |
| Keep the open ledger pages on the desk with pencil edits                                | Dirty pages in `shared_buffers`                              |
| **Every so often**, stop and copy all pencilled edits into the real ledger on the shelf | **Checkpoint**: write dirty pages to data files              |
| Then write in the notebook: **"everything above this line is in the ledger"**           | **Checkpoint record** in WAL (the redo point)                |
| Pages of the notebook above that line are no longer needed                              | Old WAL segments can be **recycled or removed**              |
| After a power cut, only re-read the notebook **below the last line**                    | **Crash recovery** replays WAL only from the last checkpoint |

Copying all the edits at once is a lot of work. That burst is the cost you pay for fast commits.

## 3. Why checkpoints exist

A checkpoint does **three jobs** at once:

| Job                        | What it means                                                                                                                                                                              |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. Bound recovery time** | After a crash, only WAL **after** the last checkpoint needs replaying. Without checkpoints, recovery would replay the **entire WAL history**                                               |
| **2. Allow WAL cleanup**   | WAL before the last checkpoint is no longer needed for recovery, so those 16 MB segments can be **recycled or deleted**. Without checkpoints, **WAL would grow forever** and fill the disk |
| **3. Flush dirty pages**   | Gets changed data onto the data files so memory (`shared_buffers`) can be reused and the data files are current                                                                            |

> **Mental shortcut:** _checkpoints trade a burst of I/O now for a shorter crash recovery and a bounded WAL later._

## 4. What happens during a checkpoint

Simplified sequence, run by the **checkpointer** background process:

```txt
 1. Record the REDO POINT: "current WAL position right now"
        |
 2. Write a "checkpoint starting" marker
        |
 3. Walk through shared_buffers and WRITE every page that was dirty
    at the start (heap pages, index pages, ...) to the OS
        |      <- this is spread out over time (section 6)
        |
 4. fsync the data files so the writes are truly on disk   <- the "sync phase"
        |
 5. Write the CHECKPOINT RECORD into WAL, and update pg_control
    ("recovery should start from the redo point from step 1")
        |
 6. Remove or recycle WAL segments older than the redo point
```

```txt
 WAL (time ->)
 |---old WAL---|--R--========= WAL generated while checkpoint runs =========|--C--|-----> ...
                ^                                                            ^
          redo point                                              checkpoint record
          (recovery would start here)
```

Important details:

- The redo point is taken **at the start**, not the end. WAL written _during_ the checkpoint is still replayed in a crash, because pages dirtied during the checkpoint may not have been flushed.
- Writes in step 3 go to the **OS page cache** first. **Step 4 (fsync)** forces them to disk, and that is where stalls tend to appear.
- Pages that get **dirtied again** after being flushed are simply dirty again for the _next_ checkpoint.
- Nothing stops while a checkpoint runs. Your inserts and commits **continue**, but they **share the disk** with the checkpoint's I/O.

## 5. What triggers a checkpoint

| Trigger                          | Setting / cause                                             | Default   | Labeled in stats as |
| -------------------------------- | ----------------------------------------------------------- | --------- | ------------------- |
| **Time**                         | `checkpoint_timeout`                                        | 5 minutes | "timed"             |
| **WAL volume**                   | WAL since the last checkpoint approaching `max_wal_size`    | 1 GB      | "requested" (`req`) |
| Manual                           | `CHECKPOINT;` command                                       | n/a       | requested           |
| Shutdown / some admin operations | Clean stop, starting a base backup, `CREATE DATABASE`, etc. | n/a       | requested           |

### Timed vs requested is a key diagnostic

| What you see                   | What it means                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Mostly **timed** checkpoints   | Healthy. The timer fires before WAL volume gets large                                                                                       |
| Many **requested** checkpoints | Write load fills `max_wal_size` **before** the timer, so checkpoints come **more often than you intended**, more I/O and more full-page WAL |

Postgres also logs a hint when this happens ("checkpoints are occurring too frequently") if `log_checkpoints`/related warnings are on.

> **Related setting:** `min_wal_size` (default 80 MB) is how much old WAL Postgres keeps around for reuse instead of deleting.

## 6. Spreading the work

If the checkpointer wrote all dirty pages in one instant, the disk would be saturated and every commit would stall. So Postgres **paces** the writes:

```txt
 checkpoint_completion_target = 0.9   (default in current versions)

 Aim to finish the write phase by 90% of the way to the NEXT expected checkpoint.

 time ---->  |<------- checkpoint interval (e.g. 5 min) ------->|
             start writing ...........................spread.....|90%
             ░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
             a steady trickle, not a burst
```

- A **higher** target (closer to 1.0) spreads writes **more thinly**, so smaller spikes.
- A **lower** target finishes the writing faster but in a **denser burst**.
- The pacing is based on how much time or WAL budget is left. If WAL fills up faster than expected, Postgres **speeds up** the writes to finish in time.

So even with good pacing, a checkpoint is **extra background I/O during the whole write phase**, not an instant event. You see it as a **rise in disk activity and commit latency over those seconds to minutes**.

(There is also `checkpoint_flush_after`, which asks the OS to start writing out data in small chunks so the final fsync has less to do. You won't tune it in Stage 1.)

## 7. The big trade-off

**Frequent checkpoints** vs **infrequent checkpoints**:

|                         | **Frequent** (short timeout, small `max_wal_size`)                                                       | **Infrequent** (long timeout, large `max_wal_size`)                          |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Crash recovery time** | Short (little WAL to replay)                                                                             | Longer (more WAL to replay)                                                  |
| **Disk I/O overhead**   | Higher (pages rewritten repeatedly)                                                                      | Lower (a hot page is flushed once per long interval, absorbing many changes) |
| **WAL volume**          | **Higher** (more full-page images, since each page's "first change after checkpoint" happens more often) | Lower                                                                        |
| **WAL disk space**      | Less retained                                                                                            | More retained                                                                |
| **Latency spikes**      | More frequent                                                                                            | Less frequent (but each flush may carry more dirty data)                     |

The key insight: **a page that is modified 100 times between checkpoints is written to the data file only once**. Longer intervals mean **more write absorption**. That's why production systems usually raise `max_wal_size` and `checkpoint_timeout` for write-heavy workloads, accepting a longer recovery time.

## 8. Checkpoints and WAL volume

Recall from the write path notes: the **first time a page is modified after a checkpoint**, Postgres writes the **entire 8 KB page** into the WAL (a **full-page image, FPI**, controlled by `full_page_writes`, on by default). This guards against **torn pages** (a page half-written during a crash).

Result: WAL volume per insert is **not constant**. It spikes right after each checkpoint and decays.

```txt
 WAL bytes
 generated
 per second
    ^
    |  |\            |\            |\
    |  | \           | \           | \
    |  |  \          |  \          |  \
    |  |   \___      |   \___      |   \___
    |  |       ‾‾‾‾‾‾|       ‾‾‾‾‾‾|       ‾‾‾‾‾‾
    +--+------------+------------+------------+----> time
      checkpoint   checkpoint   checkpoint   checkpoint
       (FPI burst: many pages touched for the first time since the checkpoint)
```

Why the sawtooth:

- Right after a checkpoint, **every page is "clean again"**, so almost every page touched needs a full-page image.
- As the interval goes on, the busy pages have already been imaged, so only the **small change records** are needed.

### How this connects to your schema

| Factor                        | Effect on the sawtooth                                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| **Random UUID primary key**   | Touches many different index pages, so **many more FPIs** after each checkpoint (a bigger, longer spike) |
| **Time-ordered key**          | Touches mostly the same few right-edge pages, so **far fewer FPIs**                                      |
| **More indexes**              | More distinct pages touched per insert, so more FPIs                                                     |
| **More frequent checkpoints** | The spike repeats more often                                                                             |

You can **see the sawtooth yourself** by sampling `wal_fpi` from `pg_stat_wal` every few seconds during a load test (section 15).

## 9. Why checkpoints cause latency spikes

A checkpoint competes with your workload in several ways:

| Mechanism                     | What happens                                                                                                                                                                                                                              |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Disk bandwidth contention** | The checkpointer's writes use the same disk as the WAL. In your compose file, **data and WAL share one volume** (`pgdata`), so checkpoint writes directly delay WAL fsyncs, and **commit latency is mostly WAL fsync** (write path notes) |
| **The fsync phase**           | At the end, fsyncing many data files can cause a burst of device flushes, stalling other I/O                                                                                                                                              |
| **OS writeback bursts**       | The OS may flush a large amount of cached dirty data at once, producing a stall                                                                                                                                                           |
| **Full-page-image WAL burst** | The post-checkpoint FPI spike (section 8) increases WAL write volume and fsync size exactly when I/O is already busy                                                                                                                      |
| **Backends forced to write**  | If the checkpointer and bgwriter can't keep up, a backend that needs a clean buffer must **write a dirty one itself** before proceeding, adding latency directly to a request (section 10)                                                |
| **Cache churn**               | Heavy writeback can evict useful cached data                                                                                                                                                                                              |

```txt
 latency (p99)
    ^
    |        *               *               *
    |       * *             * *             * *
    |  ____*___*___________*___*___________*___*______
    +----------------------------------------------------> time
         checkpoint      checkpoint      checkpoint
         (spikes line up with checkpoints, repeating on the checkpoint interval)
```

**The tell-tale sign:** p99 spikes that repeat on a **regular rhythm** (for example every ~5 minutes, or more often if WAL-triggered), with the disk showing a matching rise in write activity and `await`.

> This is exactly what **B11 (table growth soak)** is designed to catch, and why short load tests **hide** it.

## 10. Who writes dirty pages

Three actors write dirty pages from memory to the data files:

| Actor                              | When                                                                   | Impact on requests                                              |
| ---------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Checkpointer**                   | Each checkpoint, flushes **all** pages dirty at its start              | Background, paced                                               |
| **Background writer (bgwriter)**   | Continuously, in small batches, flushes pages likely to be reused soon | Background. Good: keeps clean buffers available                 |
| **Backend (your query's process)** | Only when it needs a free buffer and the candidate is dirty            | **On the request path. Adds latency.** The least desirable path |

Healthy picture: most writes done by the **checkpointer** and **bgwriter**, very few by **backends**.

Warning sign: a lot of **backend writes**. It means the background workers are not keeping up (often because the working set doesn't fit `shared_buffers` and/or write load is heavy). Requests are now paying write cost directly.

## 11. How often will checkpoints happen?

A size-triggered checkpoint is requested well before the WAL reaches the full `max_wal_size`. As a rough rule, Postgres requests a checkpoint after about:

```txt
WAL distance between checkpoints  ~=  max_wal_size / (2 + checkpoint_completion_target)
```

With the defaults (`1 GB / (2 + 0.9)`), that's roughly **350 MB of WAL**, about one third of `max_wal_size`.

### Illustrative worked example (NOT measured; replace with your numbers)

| Input                                                      | Value                               |
| ---------------------------------------------------------- | ----------------------------------- |
| Insert rate                                                | 5,000 events/s                      |
| WAL generated per event (heap + 2 indexes + FPIs, average) | assume ~1.5 KB                      |
| WAL rate                                                   | 5,000 x 1.5 KB = about **7.5 MB/s** |
| WAL distance that triggers a checkpoint                    | about 350 MB                        |
| Time to reach it                                           | 350 / 7.5 = about **47 seconds**    |

So at this load, checkpoints would be **triggered by WAL volume roughly every minute**, far more often than the 5-minute timer, and each is followed by an FPI burst. Your real WAL-per-event number comes from the LSN-diff measurement in the write path notes.

> **Takeaway:** the faster your write rate, the more your checkpoints become **WAL-driven and frequent**, and the more the sawtooth and spikes dominate your latency picture.

## 12. Checkpoints and crash recovery time

Recovery after a crash:

1. Find the last **checkpoint record** (via `pg_control`).
2. Start at its **redo point**.
3. **Replay all WAL from there to the end.**

```txt
 recovery time  ~=  (WAL generated since last checkpoint's redo point)  /  (replay speed)
```

| Situation                                    | Recovery                       |
| -------------------------------------------- | ------------------------------ |
| Crash just after a checkpoint                | Very little to replay: fast    |
| Crash just before the next checkpoint        | Maximum WAL to replay: slowest |
| Larger `max_wal_size` / `checkpoint_timeout` | Worst-case recovery grows      |

Replay is usually faster than the original workload (it's sequential and single-process), but it is **not instant**, and during recovery **the database is unavailable**. This is part of the availability story you'll see in **B8 (database restart under load)** and **B6 (hard kill)**: how long until the API recovers is partly "how long did Postgres spend replaying WAL".

(Your container logs will show lines such as `database system was not properly shut down; automatic recovery in progress`, `redo starts at ...`, and `redo done at ...`.)

## 13. Reading the signals

### Stats views

| Postgres version | Where to look                                                                                                                                   |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **17 and newer** | `pg_stat_checkpointer` (timed vs requested counts, write and sync times, buffers written). Backend and bgwriter write detail is in `pg_stat_io` |
| **16 and older** | `pg_stat_bgwriter` (checkpoint counters and buffer counters together)                                                                           |

Key numbers (names differ slightly by version):

| Signal                              | Meaning                                   | Worry when                            |
| ----------------------------------- | ----------------------------------------- | ------------------------------------- |
| **timed vs requested checkpoints**  | What triggered them                       | **Requested** is a large share        |
| **write time**                      | Time spent writing buffers in checkpoints | Very long compared with the interval  |
| **sync time**                       | Time spent in the final fsyncs            | Large or spiky (a stall source)       |
| **buffers written by checkpointer** | Volume of data flushed per checkpoint     | Huge per checkpoint (high dirty rate) |
| **buffers written by backends**     | Requests forced to write                  | Rising (workers not keeping up)       |
| **`wal_fpi`** (`pg_stat_wal`)       | Full-page images generated                | Large bursts after checkpoints        |

### The checkpoint log line

Turn on `log_checkpoints` (it's on by default in newer versions). Each checkpoint then logs something like:

```txt
checkpoint starting: time
checkpoint complete: wrote 18423 buffers (14.1%); 0 WAL file(s) added, 3 removed, 12 recycled;
  write=269.8 s, sync=0.4 s, total=270.5 s; sync files=41, longest=0.2 s, average=0.01 s;
  distance=412000 kB, estimate=398000 kB
```

How to read it:

| Part                                 | Meaning                                                                |
| ------------------------------------ | ---------------------------------------------------------------------- |
| `starting: time` or `starting: wal`  | **Trigger**: timer vs WAL volume (`wal` = requested)                   |
| `wrote N buffers (x%)`               | How much dirty data was flushed, and what fraction of `shared_buffers` |
| `write=`                             | Time in the paced write phase (long is normal with spreading)          |
| `sync=`                              | Time in the fsync phase (**spikes here hurt**)                         |
| `distance=`                          | WAL volume since the previous checkpoint                               |
| `WAL file(s) added/removed/recycled` | WAL file housekeeping                                                  |

This log is the easiest way to **line up a latency spike in Grafana with a specific checkpoint**.

## 14. Tuning

> **Stage 1 rule:** record the **untuned baseline** first. The tuning below is for understanding and for a clearly labeled follow-up experiment, not for the baseline.

| Setting                            | Effect of raising it                                               | Cost                                                         |
| ---------------------------------- | ------------------------------------------------------------------ | ------------------------------------------------------------ |
| **`max_wal_size`**                 | Fewer WAL-triggered checkpoints, more write absorption, fewer FPIs | More WAL on disk, longer worst-case recovery                 |
| **`checkpoint_timeout`**           | Fewer timed checkpoints                                            | Longer recovery; more WAL retained                           |
| **`checkpoint_completion_target`** | Smoother, thinner write spread                                     | Slightly longer-running checkpoints (already 0.9 by default) |
| **Put WAL on a separate disk**     | Removes WAL/data I/O contention                                    | Infrastructure change (a production practice)                |
| **`shared_buffers`**               | Fewer forced backend writes if the working set fits                | Memory; diminishing returns                                  |

Typical production move for write-heavy workloads: **raise `max_wal_size` substantially** (several GB or more) and keep checkpoints mostly timer-driven, accepting longer recovery.

What you should **not** do to "fix" checkpoint spikes: `fsync=off` or `full_page_writes=off`. Those risk **corruption**, which is a different category from losing recent commits (see the durability notes).

## 15. Prove it yourself

### See the settings

```sql
SHOW checkpoint_timeout;
SHOW max_wal_size;
SHOW min_wal_size;
SHOW checkpoint_completion_target;
SHOW log_checkpoints;
SHOW full_page_writes;
SHOW shared_buffers;
```

### Turn on checkpoint logging

```sql
ALTER SYSTEM SET log_checkpoints = on;
SELECT pg_reload_conf();
```

Then watch the container logs: `docker logs -f <postgres-container>`. (This changes only logging, not behavior, so it's fine for the baseline. Record it as a setting you changed.)

### Counters: timed vs requested

```sql
-- Postgres 17+
SELECT num_timed, num_requested, write_time, sync_time, buffers_written
FROM pg_stat_checkpointer;

-- Postgres 16 and older
SELECT checkpoints_timed, checkpoints_req,
       checkpoint_write_time, checkpoint_sync_time,
       buffers_checkpoint, buffers_clean, buffers_backend
FROM pg_stat_bgwriter;
```

Snapshot these **before and after** a load run and subtract.

### Force a checkpoint (needs superuser)

```sql
CHECKPOINT;
```

This is useful to start each experiment run from a **known state** (nothing dirty, fresh checkpoint). Also useful to test: run `CHECKPOINT;` **during** a load test and watch p99 and disk `await`.

### Information about the latest checkpoint

```sql
SELECT checkpoint_lsn, redo_lsn, checkpoint_time FROM pg_control_checkpoint();
```

`redo_lsn` is the **redo point**. `pg_current_wal_lsn()` minus `redo_lsn` is how much WAL a crash would have to replay **right now**:

```sql
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), redo_lsn)) AS wal_to_replay_now
FROM pg_control_checkpoint();
```

### See the FPI sawtooth

Sample every few seconds during a load run:

```bash
while true; do
  psql -Atc "SELECT now(), wal_records, wal_fpi, wal_bytes FROM pg_stat_wal;" >> wal-samples.csv
  sleep 5
done
```

Plot the **per-interval difference** of `wal_fpi` and `wal_bytes`. You should see a spike right after each checkpoint that decays (the sawtooth).

### See who is writing pages (Postgres 16+)

```sql
SELECT backend_type, object, context, writes, fsyncs
FROM pg_stat_io
WHERE writes > 0
ORDER BY writes DESC;
```

Compare writes by `checkpointer`, `background writer`, and `client backend`.

### Watch the disk during a checkpoint

```bash
iostat -x 1       # watch %util, w/s, and await on the device holding pgdata
```

Line the rise in write activity up with the checkpoint log lines.

### Measure crash recovery time (ties into B6 and B8)

```bash
# 1. run load for a few minutes so there is un-checkpointed WAL
# 2. hard-kill the container
docker kill <postgres-container>
# 3. restart and read the logs for "redo starts at" and "redo done at" timestamps
docker start <postgres-container> && docker logs -f <postgres-container>
```

Repeat the experiment immediately after a manual `CHECKPOINT;` and compare: recovery should be faster.

### WAL directory size

```sql
SELECT count(*) AS segments, pg_size_pretty(sum(size)) AS total
FROM pg_ls_waldir();
```

Watch it rise and fall around checkpoints as old segments are recycled.

### A minimal "checkpoint effect" experiment

1. Start a steady load at about 70% of the knee.
2. Record p99 over time and sample `wal_fpi` every 5 s and `iostat -x 1`.
3. Run `CHECKPOINT;` at a known moment.
4. Observe: disk write burst, `wal_fpi` spike afterward, a p99 bump, then settling.

## 16. Stage 1 experiments

| Experiment                       | Checkpoint connection                                                                                                                                                           |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B11 Table growth soak**        | The main one: periodic p99 spikes, checkpoint frequency (timed vs requested), buffer cache hit ratio, disk I/O. Sample `pg_stat_checkpointer` / `pg_stat_bgwriter` every minute |
| **B1 Ramp to collapse**          | Each step is 60 s, shorter than the 5-minute timer, so **whether a checkpoint lands inside a step is luck**. This adds variance to your curve                                   |
| **B5 Index write amplification** | More indexes (and random keys) mean more dirty pages and more FPIs, so heavier checkpoints and bigger sawtooth                                                                  |
| **B6 Durability knob**           | Hard-kill test also exposes recovery behavior; compare recovery time at different distances from the last checkpoint                                                            |
| **B7 Payload size**              | Bigger rows mean more dirty pages and more WAL, so checkpoints trigger sooner                                                                                                   |
| **B8 DB restart under load**     | Restart time includes WAL replay since the last checkpoint                                                                                                                      |

### A practical rule for all your Stage 1 load tests

> **Make runs long enough, or control the checkpoint state.** Either run several checkpoint intervals (at least 3 x 5 minutes) **or** issue `CHECKPOINT;` before each step so every run starts from the same state, and **record the checkpoint log lines** next to your results. Otherwise a spike can be misread as a code problem, or a checkpoint-free run can look better than reality.

Add to your B11 sampling: checkpoints timed vs requested, checkpoint write/sync time, `wal_fpi`, WAL directory size, and buffers written by backends.

## 17. Common confusions

**"A checkpoint is a backup or snapshot of my data."**
No. It's an internal flush that bounds crash recovery. It's not a restorable copy.

**"Checkpoints are what make my commits durable."**
No. Commits are durable once the **WAL** is fsynced. Checkpoints only move data pages to the data files and bound recovery.

**"If checkpoints cause spikes, I should disable them."**
You can't, and shouldn't. Without them, WAL grows forever and recovery would replay everything. Make them **less frequent and smoother**, not absent.

**"Checkpoints stop the database while they run."**
No. Work continues. They compete for disk I/O.

**"More frequent checkpoints mean safer data."**
Not for committed data (the WAL protects that). More frequent only means faster recovery, at the cost of more I/O and more WAL.

**"A checkpoint writes only what changed since the last one."**
Roughly yes, it flushes pages dirtied since they were last written. But a page changed many times is written once, which is why longer intervals absorb writes.

**"WAL volume per insert is constant."**
No. It follows a **sawtooth** because of full-page images after each checkpoint.

**"Requested checkpoints are errors."**
They're not errors. A high share just means your write rate fills `max_wal_size` before the timer fires.

**"`max_wal_size` is a hard limit."**
It's a **soft** limit that triggers checkpoints. WAL can exceed it under heavy load or if cleanup is held back (for example by a replica or archiving).

**"A short load test is enough to judge the write path."**
Not if it's shorter than a checkpoint interval. Checkpoint effects and their spikes only show up over longer runs.

1. It flushes all pages that were dirty at its start from memory to the data files, then records in WAL that everything before the redo point is on disk. Jobs: bound crash recovery time, allow old WAL to be recycled, and flush dirty pages so memory can be reused.
2. The WAL position recorded when a checkpoint starts. After a crash, recovery replays WAL from the last checkpoint's redo point forward, so it defines how much work recovery does.
3. Time (`checkpoint_timeout`, default 5 min) or WAL volume approaching `max_wal_size` (default 1 GB). Many requested checkpoints mean your write load fills the WAL budget before the timer, so checkpoints happen more often than intended, adding I/O and full-page-image WAL.
4. Writing all dirty pages is a burst of disk I/O, the fsync phase can stall, OS writeback can burst, and the post-checkpoint full-page-image WAL spike adds more writes. All of this competes with WAL fsyncs, which dominate commit latency, and backends may be forced to write pages themselves.
5. After each checkpoint the first change to each page logs a full 8 KB image in the WAL, so WAL volume spikes then decays until the next checkpoint. Random keys touch many different index pages, so far more first-touches and more full-page images.
6. Recovery replays WAL since the last checkpoint's redo point. Frequent checkpoints keep that distance short and recovery fast; infrequent checkpoints allow more WAL to accumulate, so recovery takes longer.
7. Frequent: faster recovery but more I/O, more full-page images and more latency spikes. Infrequent: better write absorption and less WAL, but longer recovery and more WAL on disk.
8. A 60-second step is shorter than the 5-minute timer, so whether a checkpoint falls inside it is essentially random, adding variance. Long-run effects like checkpoint spikes and cache decay never appear. Run several intervals or force `CHECKPOINT;` before each step, and record checkpoint log lines.
9. Checkpoint writes go to the same disk as WAL fsyncs. Since commit latency is mostly WAL fsync, the checkpoint's data-file writes directly delay commits. A separate WAL disk avoids this contention.
10. `synchronous_commit=off` risks losing the most recent acknowledged commits in a crash (a clean cut, no corruption). Checkpoints don't affect commit durability at all; skipping them would only mean unbounded WAL and very long recovery. The dangerous settings that risk corruption are `fsync=off` and `full_page_writes=off`.

## 19. Glossary and cheat sheet

| Term                               | Meaning                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| **checkpoint**                     | Flush of all dirty pages to data files plus a WAL record marking how far recovery can skip |
| **checkpointer**                   | The background process that performs checkpoints                                           |
| **redo point**                     | WAL position where crash recovery starts replaying                                         |
| **dirty page**                     | Page changed in memory but not yet written to its data file                                |
| **bgwriter**                       | Background process that writes some dirty pages ahead of time                              |
| **`checkpoint_timeout`**           | Max time between checkpoints (default 5 min)                                               |
| **`max_wal_size`**                 | Soft limit on WAL between checkpoints; approaching it triggers one (default 1 GB)          |
| **`min_wal_size`**                 | WAL kept for reuse instead of being deleted (default 80 MB)                                |
| **`checkpoint_completion_target`** | Fraction of the interval over which to spread checkpoint writes (default 0.9)              |
| **timed / requested checkpoint**   | Triggered by the timer / by WAL volume (or manually)                                       |
| **full-page image (FPI)**          | Whole 8 KB page written to WAL on first change after a checkpoint                          |
| **torn page**                      | A page left half-written by a crash; FPIs protect against it                               |
| **sync phase**                     | Final fsync of data files at the end of a checkpoint                                       |
| **`log_checkpoints`**              | Setting that logs each checkpoint's details                                                |
| **write absorption**               | A page modified many times between checkpoints being written only once                     |

### Cheat sheet

```txt
checkpoint = flush all dirty pages to data files + write "redo point" marker
3 jobs     = bound recovery time | let old WAL be recycled | flush dirty pages
triggers   = checkpoint_timeout (5 min)  OR  WAL ~ max_wal_size/(2+0.9)  ("requested")
spreading  = completion_target 0.9: paced trickle, not a burst (still adds I/O)
after a checkpoint  -> full-page images -> WAL SAWTOOTH (worse with random keys + more indexes)
spikes     = checkpoint I/O vs WAL fsync (same disk in your compose!) + fsync phase + backend writes
many "requested" checkpoints = write rate outruns max_wal_size
frequent  : fast recovery,  more I/O, more WAL
infrequent: slow recovery,  less I/O, more WAL on disk, better write absorption
recovery time ~ WAL since last redo point / replay speed
test hygiene: run >= 3 checkpoint intervals OR CHECKPOINT; before each step, log the checkpoint lines
never "fix" spikes with fsync=off / full_page_writes=off (corruption risk)
```

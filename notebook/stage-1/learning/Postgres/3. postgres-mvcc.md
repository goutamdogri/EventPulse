## 1. TL;DR

- Postgres never edits a row in place. Every change creates a **new version** of the row. Old versions stay until nobody can see them anymore.
- Each version is stamped with **who created it (`xmin`)** and **who deleted it (`xmax`)**.
- Each transaction sees a **snapshot**, a consistent view of which versions count as "visible". This is why **readers don't block writers and writers don't block readers**.
- The price is **dead tuples**: old versions that pile up and must be cleaned by **VACUUM** (done automatically by autovacuum).
- **UPDATE = mark old version dead + insert new version.** DELETE = just mark dead. Neither frees space immediately.
- MVCC does **not** stop two writers from conflicting on the _same row_. That is still a **row lock**, and it is the reason a hot row serializes writers (B4).
- **Inserts are the cheap case** for MVCC. Updates and deletes are where the cost lives.

> **One-line version:** _Postgres keeps multiple versions of each row so reads and writes don't block each other, then cleans up the old versions later._

## 2. The mental model

Imagine a shared document with **revision history**, like Google Docs.

| Shared document                                                | Postgres                                                  |
| -------------------------------------------------------------- | --------------------------------------------------------- |
| Every edit creates a new revision; old revisions are kept      | Every UPDATE creates a new row version; old versions stay |
| You view the document **as of a moment in time**               | Your transaction reads a **snapshot**                     |
| Someone editing now doesn't change what you're looking at      | Writers don't change what an existing snapshot sees       |
| Periodically someone prunes revisions nobody needs             | **VACUUM** removes versions nobody can see                |
| Two people editing the _same sentence_ at once must take turns | Two writers on the _same row_ take turns (row lock)       |

The big win: **a long report query can read a consistent view of the table while thousands of inserts and updates happen**, with no locks between them.

## 3. What a row version looks like

Every row version (called a **tuple**) in a table page carries a small hidden header. The important fields:

| Field      | Meaning                                                                                                    |
| ---------- | ---------------------------------------------------------------------------------------------------------- |
| **`xmin`** | Transaction ID that **created** this version                                                               |
| **`xmax`** | Transaction ID that **deleted or replaced** this version (0 if none)                                       |
| **`ctid`** | Physical location: `(page number, slot number)`. Points to itself, or to the newer version after an update |

You can see them by selecting the hidden columns:

```sql
SELECT xmin, xmax, ctid, event_id, type FROM events LIMIT 3;
```

```txt
 xmin | xmax | ctid  | event_id | type
------+------+-------+----------+---------------
  741 |    0 | (0,1) | 6f1c...  | order.created
  741 |    0 | (0,2) | 9a20...  | order.created
  742 |    0 | (0,3) | c3b8...  | payment.failed
```

Reading that: version created by transaction 741, not deleted (`xmax = 0`), located on page 0, slot 1.

### Transaction IDs (XIDs)

- Every transaction that **writes** gets a **transaction ID**, a number that increases over time.
- Read-only transactions don't consume one.
- Whether a transaction **committed or aborted** is recorded separately (in the commit log, `pg_xact`). Tuples don't store "committed" themselves; Postgres looks it up (and caches the answer in **hint bits** on the tuple, see section 12).

## 4. Snapshots and the visibility rule

A **snapshot** answers: _"Which transactions' changes count as committed from my point of view?"_

Conceptually a snapshot records:

| Part       | Meaning                                                                                         |
| ---------- | ----------------------------------------------------------------------------------------------- |
| `xmin`     | Oldest transaction still in progress when the snapshot was taken (everything older is finished) |
| `xmax`     | Next XID to be assigned (everything at or after this didn't exist yet)                          |
| `xip` list | Transactions that were **in progress** at that moment                                           |

### The visibility rule (simplified)

A row version is **visible** to a snapshot if both are true:

1. **It was created by a transaction that counts as committed** for this snapshot (`xmin` committed and not "in the future" or in-progress).
2. **It has not been deleted by a transaction that counts as committed** (`xmax` is 0, or its transaction is aborted/in-progress/in the future for this snapshot).

### Worked example

```txt
 time ->
 Tx 100: BEGIN ... INSERT row A ........ COMMIT
 Tx 101:              BEGIN, SELECT ....... (snapshot taken here)
 Tx 102:                       BEGIN ... UPDATE A -> A' ... COMMIT
 Tx 101:                                   SELECT again
```

- Tx 101's snapshot was taken after Tx 100 committed, so it sees row **A**.
- Tx 102 updates A: the old version A gets `xmax = 102`, and a new version A' is created with `xmin = 102`.
- If Tx 101 is in **REPEATABLE READ**, its snapshot is fixed, so it **still sees A** (not A').
- If Tx 101 is in **READ COMMITTED** (the default), its _next statement_ takes a new snapshot, so it sees **A'**.

Nobody blocked anybody. That is MVCC.

## 5. INSERT, UPDATE, DELETE under MVCC

| Operation  | What actually happens                                                                | Old version          |
| ---------- | ------------------------------------------------------------------------------------ | -------------------- |
| **INSERT** | A new tuple is written with `xmin = my txid`, `xmax = 0`                             | n/a                  |
| **DELETE** | The existing tuple's `xmax` is set to my txid. **Nothing is removed**                | Stays until vacuumed |
| **UPDATE** | **DELETE the old version + INSERT a new version** (old `xmax` = me; new `xmin` = me) | Stays until vacuumed |

### Picture of an UPDATE

```txt
 Before:   page 0:  [ slot 1: xmin=741 xmax=0   "balance=100" ]

 UPDATE balance = 150   (transaction 800)

 After:    page 0:  [ slot 1: xmin=741 xmax=800 "balance=100" ]   <- old version, now dead after 800 commits
                    [ slot 2: xmin=800 xmax=0   "balance=150" ]   <- new version
                       (slot 1's ctid now points to slot 2)
```

### What this means

- **An UPDATE costs like an INSERT plus a bit more:** a new tuple, **new index entries** (unless the HOT optimization applies, see section 7), and WAL for all of it.
- **A DELETE does not shrink the table.** Space is reclaimed later.
- **A rolled-back transaction leaves dead tuples too.** Its inserted versions have an `xmin` that aborted, so nobody can ever see them, but they still occupy space until vacuumed.
- **Rows are not updated "in place"**, so a frequently updated row creates a long chain of versions.

## 6. Dead tuples, bloat, and VACUUM

A **dead tuple** is a row version that **no current or future snapshot can see**. It's garbage, but it's still sitting in the table and its indexes.

### Why that's a problem: bloat

- Dead tuples take space, so tables and indexes **grow larger than the live data**.
- Bigger tables mean more pages to scan, a lower cache hit ratio, and more I/O.
- That slowdown is called **bloat**.

### What VACUUM does

| Step                           | Effect                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| Finds dead tuples              | Versions invisible to every running snapshot                                                     |
| Removes their index entries    | So indexes stop pointing at garbage                                                              |
| Marks the space **reusable**   | Future inserts/updates can reuse it                                                              |
| Updates the **visibility map** | Records which pages are "all visible" (helps index-only scans, and lets vacuum skip those pages) |
| Updates the **free space map** | Tells inserts where there's room                                                                 |
| **Freezes** old tuples         | Protects against transaction ID wraparound (section 11)                                          |

### Important: plain VACUUM does not shrink the file

Plain VACUUM makes space **reusable**; it does not give it back to the operating system (except sometimes trimming empty pages at the very end of the file). `VACUUM FULL` rewrites the table to compact it, but it takes a heavy lock and blocks access, so it's a last resort.

### Autovacuum

You don't run VACUUM by hand. A background **autovacuum** launcher starts workers automatically per table when enough has changed. Rough default trigger for dead tuples:

```txt
vacuum when dead tuples > autovacuum_vacuum_threshold (50)
                         + autovacuum_vacuum_scale_factor (0.2) x table rows
```

So for a table with 1,000,000 rows, vacuum starts after about **200,000 dead tuples**. For huge tables that's a lot, so busy big tables are often tuned with a lower scale factor. Newer versions also trigger vacuum on **insert-only** tables (so they still get frozen and their visibility map updated).

> **Stage 1 rule:** record the **untuned baseline**. Observe autovacuum, don't tune it yet.

### The cost of vacuum

VACUUM uses CPU and I/O (it competes with your workload). It's throttled by cost-based delays by default. A table that needs vacuum constantly but isn't getting it fast enough is a classic cause of slow degradation over time (B11).

## 7. HOT updates

Every UPDATE normally creates a new tuple **and a new entry in every index**, even if the indexed columns didn't change. That's expensive. **HOT (Heap-Only Tuple)** is the optimization that avoids it.

A HOT update happens when **both**:

1. **No indexed column** was changed by the update.
2. The new version fits **on the same page** as the old one.

Then Postgres creates the new version on the same page and chains it from the old one, **without touching any index**. Old index entries still reach the right row by following the chain. Dead chain members can even be cleaned up quickly **without a full vacuum** (page pruning).

Why you care:

- Updating a column that **is in an index** (or a table with no room left on the page) loses the HOT benefit, which means more index writes and more bloat.
- This is one reason hot-row counter updates (B4) are doubly bad: lock contention **plus** a constant stream of dead tuples.
- It is also a reason not to index columns you update often unless needed.

## 8. Isolation levels

An **isolation level** controls **when a transaction takes its snapshot** and which anomalies are possible.

| Level                        | Snapshot taken                                         | Notes                                                                                                                                           |
| ---------------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **READ COMMITTED** (default) | At the start of **each statement**                     | Each statement sees everything committed before it began. Two identical SELECTs in one transaction can return different results                 |
| **REPEATABLE READ**          | Once, at the **first statement** of the transaction    | A stable view for the whole transaction. A concurrent update to a row you try to change causes a **serialization failure** error you must retry |
| **SERIALIZABLE**             | Same as repeatable read, plus conflict detection (SSI) | Behaves as if transactions ran one at a time. May abort transactions that you must retry                                                        |

(Postgres has no true "read uncommitted": asking for it gives you read committed.)

### Anomalies in plain words

| Anomaly             | Meaning                                                                                | Read Committed | Repeatable Read       | Serializable |
| ------------------- | -------------------------------------------------------------------------------------- | -------------- | --------------------- | ------------ |
| Dirty read          | See another transaction's **uncommitted** data                                         | Prevented      | Prevented             | Prevented    |
| Non-repeatable read | Same row read twice, different values                                                  | **Possible**   | Prevented             | Prevented    |
| Phantom read        | Same query run twice, different set of rows                                            | **Possible**   | Prevented in Postgres | Prevented    |
| Write skew          | Two transactions each read overlapping data, then write disjoint rows, breaking a rule | Possible       | **Possible**          | Prevented    |

### What this means for EventPulse

- Stage 1 uses **autocommit single-row inserts** at the default **READ COMMITTED**. That's fine: each insert is its own tiny transaction and there are no multi-statement invariants.
- Isolation level starts to matter when you do **read-then-write logic** (check then insert, counters, outbox relay in Stage 3). Know which level you rely on and what retries it needs.

## 9. Locks: where MVCC does NOT save you

MVCC solves **read vs write** conflicts. It does **not** solve **write vs write** on the **same row**.

```txt
 Tx A: UPDATE tenant_counters SET n = n + 1 WHERE tenant_id = 't1';   -- takes the row lock
 Tx B: UPDATE tenant_counters SET n = n + 1 WHERE tenant_id = 't1';   -- WAITS for A to commit/abort
 Tx C: ...same row...                                                -- WAITS too
```

- The first writer holds a **row lock** (recorded via `xmax` on the tuple).
- Other writers on that row **queue behind it**, even though CPU and disk are idle.
- **Readers are not affected**: a plain `SELECT` still sees the old version.

This is exactly **B4 (hot row contention)**: all writers for one tenant serialize on a single row, so throughput collapses with **low CPU and high latency**. More hardware doesn't fix it. A design change does (the later answer is aggregating downstream, not synchronous counters).

### What happens when the waiter finally proceeds

- **READ COMMITTED:** after the first transaction commits, the waiting UPDATE **re-checks the row's new latest version** and applies to it (so `n = n + 1` correctly becomes n+2 overall, no lost update).
- **REPEATABLE READ:** the waiter gets a **serialization failure** and must retry the transaction.

### Inserts and unique keys

When two transactions try to insert the **same unique key** at once, the second one **waits** until the first commits or aborts, because only then is it known whether the key truly exists:

- First commits: the second hits the conflict (an error, or silently skipped with `ON CONFLICT DO NOTHING`).
- First aborts: the second succeeds.

That's how your `ON CONFLICT (event_id) DO NOTHING` stays correct under concurrent duplicates. It's also a place where duplicate-heavy workloads can show waiting, because the conflict check isn't free.

## 10. Long transactions

This is the most important operational consequence of MVCC.

**VACUUM can only remove a dead tuple if no running snapshot could still need it.** The oldest running transaction's snapshot sets a **horizon**: nothing newer than that can be cleaned.

```txt
 Long-running (or "idle in transaction") session holds an old snapshot
        |
        v
 vacuum cannot remove ANY tuple that became dead after that snapshot
        |
        v
 dead tuples accumulate  ->  bloat  ->  slower queries, bigger indexes
```

### The usual culprits

| Culprit                                                                        | Why it's bad                                                                                                |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| A transaction left open (`BEGIN` with no `COMMIT`)                             | Holds its snapshot (and its locks) forever                                                                  |
| **`idle in transaction`** connections                                          | A client started a transaction then went quiet, often due to an application bug or a leaked pool connection |
| A very long report/analytics query on the primary                              | Holds back vacuum for its whole duration                                                                    |
| Replication (Stage 6): long queries on a replica or a lagging replication slot | Can hold back cleanup on the primary                                                                        |

### Link to the connection notes

A pool connection stuck `idle in transaction` is doubly bad: it **occupies one of your scarce connections** _and_ **blocks vacuum**. In Stage 1 this ties to **B10 (missing timeouts)** and **B8**. Defenses:

- `idle_in_transaction_session_timeout`: kills sessions idle inside a transaction too long.
- `statement_timeout`: stops runaway queries.
- Keep transactions **short**. Don't hold one open across a network call.

## 11. Transaction IDs and freezing

XIDs are **32-bit numbers**, so there are only about **4 billion** of them, and comparisons treat the space as a circle where roughly **2 billion** are "in the past" and 2 billion "in the future". If old tuples were never marked, after about 2 billion transactions an old row's `xmin` would suddenly look like it was in the **future**, and the row would vanish. This is **transaction ID wraparound**.

### The fix: freezing

VACUUM **freezes** old tuples, marking them as "visible to everyone, forever", so their `xmin` no longer matters. Autovacuum does this automatically, forced once a table's oldest unfrozen XID reaches `autovacuum_freeze_max_age` (default **200 million**). If it falls dangerously behind, Postgres eventually **refuses writes** to protect data. This is a rare but severe outage, and it's usually caused by vacuum being blocked (long transactions again) or too slow.

### Why you should care at EventPulse volumes

Every **writing transaction consumes an XID**. If each event is its own transaction:

```txt
5,000 events/sec  ->  5,000 XIDs/sec
200,000,000 XIDs (default freeze trigger)  /  5,000 per sec  =  40,000 sec  =  about 11 hours
```

So at that rate autovacuum must freeze the table roughly **every 11 hours or so**, which is heavy I/O on a growing table. This is something **B11 (soak)** can show you.

**Batching helps again:** a 1,000-row batch in one transaction uses **one** XID instead of 1,000. That's another quiet reason Stage 2's batched consumer is much healthier for Postgres.

## 12. MVCC in an insert-heavy system

EventPulse's `events` table is almost **insert-only**. That's the friendliest MVCC workload, but not a free one.

| Aspect              | Insert-only behaviour                                                                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Dead tuples         | Very few. Only from rolled-back transactions and (rarely) conflict races. Little bloat                                                                                         |
| Updates / deletes   | None, so no HOT concerns, and no hot rows (unless you add the B4 counter)                                                                                                      |
| Readers vs writers  | No blocking. Your analytical `SELECT`s don't slow inserts through locks                                                                                                        |
| **XID consumption** | **One per transaction.** High at one-row-per-commit (section 11)                                                                                                               |
| **Freezing**        | Still required. Large insert-only tables need periodic freeze vacuums                                                                                                          |
| **Hint bits**       | The first reader to touch a freshly committed tuple may **set hint bits on the page** (a write caused by a read), so reading a big new table can generate unexpected write I/O |
| **Visibility map**  | Needs vacuum to be set. Without it, index-only scans fall back to visiting the table                                                                                           |
| **Retention**       | Deleting old events via `DELETE` creates dead tuples en masse. **Dropping old partitions** avoids this entirely (Stage 6)                                                      |

### Where MVCC bites later in the project

| Place                                     | MVCC consequence                                                                                                                                                                |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Stage 1, B4:** per-tenant counter row   | Hot row lock **and** a dead tuple per update                                                                                                                                    |
| **Stage 3: outbox**                       | `UPDATE outbox SET published_at = ...` makes dead tuples constantly; a partial index on unpublished rows plus good vacuum settings (or delete/partition published rows) matters |
| **Stage 4: processor checkpoint tables**  | Frequent overwrites of the same row = update churn, bloat, vacuum pressure                                                                                                      |
| **Stage 5: rule/alert state in Postgres** | Same: high-churn rows need attention                                                                                                                                            |
| **Stage 6: partitioning**                 | `DROP PARTITION` sidesteps dead tuples and vacuum for retention                                                                                                                 |

## 13. Prove it yourself

### See `xmin`, `xmax`, `ctid` change (two terminals)

Create a scratch table:

```sql
CREATE TABLE mvcc_demo (id int PRIMARY KEY, val text);
INSERT INTO mvcc_demo VALUES (1, 'a');
SELECT xmin, xmax, ctid, * FROM mvcc_demo;
```

Now update and look again:

```sql
UPDATE mvcc_demo SET val = 'b' WHERE id = 1;
SELECT xmin, xmax, ctid, * FROM mvcc_demo;
```

Notice: the `ctid` **changed** (a new physical version was created) and `xmin` is now the updating transaction. Do it a few more times and watch `ctid` move.

### Readers don't block writers (and the isolation levels)

Terminal 1:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT val FROM mvcc_demo WHERE id = 1;     -- sees 'b'
```

Terminal 2:

```sql
UPDATE mvcc_demo SET val = 'c' WHERE id = 1;   -- returns immediately, not blocked
```

Terminal 1:

```sql
SELECT val FROM mvcc_demo WHERE id = 1;     -- STILL 'b' (stable snapshot)
COMMIT;
SELECT val FROM mvcc_demo WHERE id = 1;     -- now 'c'
```

Repeat with `BEGIN;` (read committed) and notice the second SELECT shows `'c'` right away.

### Watch writers block each other (a mini B4)

Terminal 1:

```sql
BEGIN;
UPDATE mvcc_demo SET val = 'x' WHERE id = 1;   -- holds the row lock, do NOT commit yet
```

Terminal 2:

```sql
UPDATE mvcc_demo SET val = 'y' WHERE id = 1;   -- hangs, waiting
```

Terminal 3, see who is blocked:

```sql
SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, wait_event, left(query, 50) AS query
FROM pg_stat_activity
WHERE cardinality(pg_blocking_pids(pid)) > 0;
```

Then `COMMIT;` in Terminal 1 and watch Terminal 2 finish. You'll see `wait_event_type = Lock`. This is the signature of contention: **idle CPU, stuck requests**.

### Dead tuples and vacuum

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_vacuum
FROM pg_stat_user_tables
WHERE relname IN ('events', 'mvcc_demo');
```

Run many updates against `mvcc_demo`, then check `n_dead_tup`. Run `VACUUM mvcc_demo;` and check again.

### Table and index size (bloat check)

```sql
SELECT pg_size_pretty(pg_table_size('events'))   AS table,
       pg_size_pretty(pg_indexes_size('events')) AS indexes;
```

For a more precise view, the `pgstattuple` extension reports dead tuple percentage and free space. Install it with `CREATE EXTENSION pgstattuple;` and run `SELECT * FROM pgstattuple('mvcc_demo');`.

### Look at the raw tuples (advanced)

```sql
CREATE EXTENSION pageinspect;
SELECT lp, t_xmin, t_xmax, t_ctid
FROM heap_page_items(get_raw_page('mvcc_demo', 0));
```

You'll see every version on the page, including dead ones that SELECT no longer shows.

### Find sessions that block vacuum

```sql
SELECT pid, state, xact_start, now() - xact_start AS xact_age, backend_xmin, left(query, 50) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

Anything with a big `xact_age` or `state = 'idle in transaction'` is a vacuum-blocker.

### How close is XID wraparound?

```sql
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database;
```

Compare against `autovacuum_freeze_max_age` (`SHOW autovacuum_freeze_max_age;`).

### Vacuum progress

```sql
SELECT * FROM pg_stat_progress_vacuum;
```

| Experiment                            | MVCC connection                                                                                        |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| **B4 Lock contention with a hot row** | Write-write conflicts on one row are row locks. MVCC doesn't help. Every update also adds a dead tuple |

## 15. Common confusions

**"DELETE frees disk space."**
No. It marks the version dead. Space becomes reusable only after VACUUM, and the file usually doesn't shrink.

**"UPDATE changes the row in place."**
No. It creates a new version and leaves the old one. That's why update-heavy tables bloat.

**"MVCC means no locking at all."**
It removes read/write blocking. Writers on the _same row_ still queue on row locks, and DDL takes its own locks.

**"Readers never affect writers."**
Mostly true for locks. But a long-running reader's snapshot **blocks vacuum**, which indirectly hurts everyone via bloat.

**"A rolled-back transaction leaves no trace."**
Its versions remain as dead tuples until vacuumed.

**"VACUUM and VACUUM FULL are the same."**
Plain VACUUM runs alongside normal traffic and makes space reusable. VACUUM FULL rewrites the table under a heavy lock. Different tools.

**"Autovacuum is a nuisance; I'll switch it off."**
Never. Without it you get bloat and eventually wraparound trouble. Tune it, don't disable it.

**"`SELECT count(*)` is instant."**
Not in Postgres. Visibility is per-version, so counting requires checking visibility across many rows. Use estimates (`n_live_tup`, `reltuples`) where exactness isn't needed.

**"Higher isolation is always better."**
It costs retries and potential aborts. Use the lowest level that keeps your invariants true.

**"Our `events` table is insert-only so MVCC doesn't matter."**
It matters less, but XID consumption, freezing, hint bits, and aborted-insert garbage still exist, and any update (a counter, an outbox flag) changes the picture.

## 16. Self-test questions

Answer aloud first. Answers are below.

1. What does MVCC let Postgres do that a simple locking system can't?
2. What are `xmin` and `xmax`?
3. What actually happens inside the table when you `UPDATE` a row?
4. Why does a `DELETE` not shrink the table?
5. What does VACUUM do, and what can stop it from doing its job?
6. A transaction has been `idle in transaction` for 3 hours. What damage can it do?
7. Why do two writers on the same row still block each other under MVCC?
8. In READ COMMITTED vs REPEATABLE READ, what's the difference in when the snapshot is taken?
9. Your events table is insert-only. What MVCC-related costs remain?
10. Why does batching 1,000 inserts per transaction help with XIDs?

<details>
<summary>Answers</summary>

1. Let readers and writers proceed **without blocking each other**, by giving each transaction a consistent snapshot over multiple row versions.
2. `xmin` is the ID of the transaction that created that row version; `xmax` is the ID of the transaction that deleted or replaced it (0 if none).
3. The old version gets `xmax` set to the updater's ID and a **new version** is written (usually with new index entries unless it qualifies for a HOT update). The old version stays until vacuumed.
4. DELETE only sets `xmax`. The tuple physically remains until VACUUM marks its space reusable, and even then the file normally doesn't shrink.
5. It removes dead tuples' index entries, marks space reusable, updates the visibility and free space maps, and freezes old tuples. **Long-running or idle-in-transaction sessions** (old snapshots), or being too slow to keep up, stop it from cleaning.
6. It holds an old snapshot so vacuum can't remove tuples that died since, causing bloat. It may hold locks, and it occupies a scarce connection. It can also delay freezing, risking wraparound trouble in extreme cases.
7. MVCC only separates reads from writes. Two writers modifying the same row must be serialized to avoid lost updates, so the second waits for the first's **row lock**.
8. READ COMMITTED takes a new snapshot at the start of **each statement**. REPEATABLE READ takes **one snapshot** for the whole transaction.
9. One XID per transaction (consumption and freezing), hint-bit writes on first read, visibility map maintenance, garbage from aborted transactions, and no cheap bulk delete (use partition drops).
10. A transaction uses one XID no matter how many rows it writes, so batching uses 1/1,000th as many XIDs, reducing freeze pressure.

</details>

## 17. Glossary and cheat sheet

| Term                    | Meaning                                                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| **MVCC**                | Multi-Version Concurrency Control: keep multiple row versions so reads/writes don't block |
| **tuple**               | One physical version of a row                                                             |
| **xmin / xmax**         | Transaction that created / deleted-or-replaced a tuple                                    |
| **ctid**                | Physical location (page, slot) of a tuple                                                 |
| **XID**                 | Transaction ID (32-bit counter)                                                           |
| **snapshot**            | A transaction's view of which transactions count as committed                             |
| **dead tuple**          | A version nobody can see anymore, awaiting cleanup                                        |
| **bloat**               | Wasted space from dead tuples and empty gaps                                              |
| **VACUUM / autovacuum** | Cleanup of dead tuples; automatic background worker                                       |
| **HOT update**          | Update that avoids touching indexes (no indexed column changed, fits on same page)        |
| **freezing**            | Marking old tuples visible-to-all so XID wraparound can't hide them                       |
| **hint bits**           | Cached commit/abort info on a tuple, set by the first reader                              |
| **visibility map**      | Per-page flag: all tuples visible to everyone                                             |
| **isolation level**     | When a transaction takes its snapshot and which anomalies are allowed                     |
| **row lock**            | What serializes two writers on the same row                                               |
| **idle in transaction** | Session that began a transaction and went quiet (dangerous)                               |

### Cheat sheet

```txt
INSERT  = new tuple (xmin = me)
DELETE  = set xmax on old tuple (nothing removed)
UPDATE  = DELETE old + INSERT new      (HOT if no indexed col changed + fits on page)
snapshot decides visibility            -> readers never block writers
same-row writers still queue           -> row lock (hot row = serialized writers, B4)
dead tuples pile up                    -> VACUUM cleans, plain VACUUM does not shrink file
old snapshot (long / idle-in-tx)       -> blocks vacuum -> bloat
1 XID per writing transaction          -> batching saves XIDs; freezing prevents wraparound
READ COMMITTED  = snapshot per statement
REPEATABLE READ = snapshot per transaction (may need retry)
insert-only table = friendliest case, but XIDs, freezing, hint bits still exist
```

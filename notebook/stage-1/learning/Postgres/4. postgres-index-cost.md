## 1. TL;DR

- An index is a **separate, sorted data structure** that lets Postgres find rows fast without scanning the whole table.
- It is **not free**. Every index must be **updated on every INSERT** (and on most UPDATEs and DELETEs).
- Each index adds, per row inserted: **extra CPU, extra page changes, extra WAL, and extra disk space**.
- So **insert throughput falls as you add indexes**. This is called **write amplification**.
- **Where** a new key lands in the index matters hugely. **Sequential keys** hit one hot page. **Random keys (like UUIDv4)** hit random pages, which means more cache misses, more page splits, and more WAL.
- The right amount of indexing for a write-heavy ingest table is **as few as your queries allow**. This is part of why ClickHouse arrives in Stage 4.

> **One-line version:** _Every index is a second copy of part of your data that must be kept sorted on every write, so each one makes inserts slower._

## 2. The mental model

Think of a library with a **main shelf** (the table) and several **card catalogs** (the indexes): one sorted by title, one by author, one by date.

| Library                                                                  | Postgres                                                        |
| ------------------------------------------------------------------------ | --------------------------------------------------------------- |
| Books on the main shelf, in the order they arrived                       | **Heap** (table rows, unsorted)                                 |
| A card catalog sorted by title                                           | An **index** on one column (a B-tree)                           |
| Finding a book by title: look in the catalog, jump straight to the shelf | **Index scan**: fast lookup                                     |
| Finding a book with **no catalog**: walk every shelf                     | **Sequential scan**: slow on large tables                       |
| A new book arrives: shelve it **and** file a card in **every** catalog   | INSERT: write the heap row **and** one entry in **every** index |
| 5 catalogs means 5 cards to file per book                                | 5 indexes means 5 index insertions per row                      |

Reading gets faster with every catalog. **Receiving books gets slower with every catalog.** An index is a deliberate trade of write speed (and space) for read speed.

## 3. What an index actually is

The default index type in Postgres is a **B-tree**. It's a tree of **8 KB pages**, sorted by key.

```txt
                        [ root page ]
                     keys: 'm'            (points to child pages)
                    /               \
         [ internal page ]       [ internal page ]
          keys: 'd', 'h'          keys: 'q', 'u'
         /     |      \          /     |      \
     [leaf]  [leaf]  [leaf]   [leaf]  [leaf]  [leaf]   <- sorted entries
      |  |    |  |            ...
      v  v    v  v
   each entry = (key value, ctid -> where the row lives in the heap)
```

Key facts:

- **Leaf pages** hold the actual entries: a key value plus a **ctid** (the row's physical location: page and slot).
- **Internal pages** just guide the search toward the right leaf.
- The tree is **shallow**. Each page holds a few hundred entries, so even **hundreds of millions of rows** need only about **3-4 levels**. A lookup touches about that many pages.
- The leaf pages are linked, so **range scans** (`WHERE occurred_at BETWEEN ...`) walk along the leaves in order.
- The index stores **its own copy** of the indexed column values, so it takes real disk space and buffer cache.

### A lookup, step by step

```txt
 WHERE event_id = 'abc...'
   1. read root page                -> choose child
   2. read internal page            -> choose child
   3. read leaf page                -> find entry, get ctid
   4. read the heap page at ctid    -> fetch the row
```

Usually the top levels are always cached, so the real cost is the leaf and heap pages.

## 4. The trade

|                                | Without the index                                  | With the index                                                           |
| ------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------------ |
| **Read** by the indexed column | Scan the whole table (slow, grows with table size) | A handful of page reads (fast, nearly constant)                          |
| **Insert**                     | Write the heap row only                            | Heap row **+** index entry **+** their WAL                               |
| **Disk space**                 | Table only                                         | Table **+** index (sometimes the index is a large fraction of the table) |
| **Memory**                     | Table pages cached                                 | Table **and** index pages compete for `shared_buffers` and OS cache      |
| **Update / delete**            | Cheap                                              | Index entries must be maintained (see section 11)                        |

### The decision question

> **"Does a real query need this index enough to justify taxing every write?"**

For a **read-heavy** system, add indexes freely. For a **write-heavy ingest** system like EventPulse's Stage 1 `events` table, each index is a direct cost on your most important path.

## 5. What one INSERT does to each index

Recall the write path notes: an INSERT writes the heap row, then **one entry into every index**, then writes WAL for all of it, then commits.

Per index, the backend must:

1. **Descend the tree** from root to the correct leaf page (3-4 page lookups, usually cached).
2. **Find the right position** in that leaf (binary search among its entries).
3. **Insert the entry**, shifting others within the page.
4. **Mark the leaf page dirty** (it will be written later by bgwriter/checkpointer).
5. **If the leaf is full: split it** (section 6), which is considerably more work.
6. **Write a WAL record** for the change (and possibly a **full-page image** the first time that page is touched after a checkpoint).

```txt
 one INSERT with 3 indexes:

   heap page      : 1 tuple added          + 1 WAL record
   index #1 (PK)  : 1 entry added          + 1 WAL record (+ maybe split)
   index #2       : 1 entry added          + 1 WAL record (+ maybe split)
   index #3       : 1 entry added          + 1 WAL record (+ maybe split)
   commit         : 1 commit record + fsync
```

So the work per row grows roughly **linearly with the number of indexes**, and the **number of distinct dirty pages** (and so checkpoint I/O and full-page WAL) grows with it too.

### Illustrative effect (NOT measured numbers)

This is the shape B5 should show. Your actual numbers will differ.

| Secondary indexes            | Relative insert throughput | WAL bytes per event | Index size vs table               |
| ---------------------------- | -------------------------- | ------------------- | --------------------------------- |
| 0                            | highest                    | lowest              | PK only                           |
| 1                            | lower                      | higher              | grows                             |
| 3                            | lower still                | higher still        | can approach or exceed table size |
| 5 (incl. a GIN on `payload`) | lowest                     | highest             | often larger than the table       |

Your job in B5 is to **replace this guess with a real table**.

## 6. Page splits and fillfactor

A leaf page holds a limited number of entries. When a new entry has to go into a **full** page, Postgres **splits** it:

```txt
 before:  [ a b c d e f g h ]  <- full, new key 'e2' arrives

 after:   [ a b c d e ]   [ e2 f g h ]   <- two pages, new link added to the parent
```

A split is expensive:

- Allocate a **new page**.
- **Move half the entries** over.
- **Update the parent** (which can itself split, rarely cascading upward).
- **Write more WAL**, including full-page images.
- Leave both pages **partially empty**, so the index is bigger than the data strictly needs.

### Where do splits happen?

| Insert pattern                                  | What happens                                                                                                                                                           |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Sequential keys** (always the largest so far) | Always the **rightmost leaf**. When it fills, a new page is added at the right edge. Pages end up nearly **full**. Few wasteful splits                                 |
| **Random keys**                                 | Land on **any leaf**. Full pages split in the middle (about 50/50). Pages end up **only partly full** on average, so the index is **larger and splits keep happening** |

### Fillfactor

`fillfactor` is how full Postgres packs a page at build time (the B-tree default is **90%**). The remaining space gives room to absorb inserts without an immediate split. Don't tune it in Stage 1; just know it exists.

## 7. Random UUID vs ordered keys

This is the one design choice in your Stage 1 schema that the doc calls out deliberately:

```sql
event_id uuid PRIMARY KEY      -- random UUID (UUIDv4)
```

The primary key is backed by a **unique B-tree index**. With a **random** UUID, every new key lands in a **random place** in that index.

```txt
 ordered key (time-ordered ID):            random key (UUIDv4):

 inserts all go to the right edge          inserts scatter across the whole tree
 [.....][.....][.....][ NEW ] <-- hot      [ NEW ][.....][ NEW ][.....][ NEW ]
 same few pages stay in memory             touches many different pages
```

### Consequences of random keys

| Effect                                   | Why                                                                                                                                         |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Poor cache locality**                  | The "working set" is the **entire index**, not just the right edge. Once the index exceeds memory, inserts need **disk reads** (section 12) |
| **More dirty pages**                     | Many different leaf pages change, so more to write at each checkpoint                                                                       |
| **More full-page writes in WAL**         | Each page touched for the first time after a checkpoint logs a full 8 KB image. Random keys touch many more pages, so far more WAL          |
| **More page splits and a bloated index** | Splits in the middle of full pages, with pages ~50-70% full                                                                                 |
| **Slower inserts as the table grows**    | All of the above worsen as the index gets bigger                                                                                            |

### The alternatives you will compare in B5

| Key type                       | Order                    | Notes                                                                                                                                                         |
| ------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| UUIDv4 (random)                | None                     | Your baseline. Easy, globally unique, client-generated                                                                                                        |
| **Time-ordered UUID (UUIDv7)** | Roughly by creation time | Keeps UUID benefits with much better locality. Newer Postgres versions can generate it natively; otherwise generate it in the application or via an extension |
| `bigserial` / identity         | Strictly sequential      | Best insert locality, but needs the database to assign it, and it isn't client-supplied like `event_id`                                                       |

> **Why it matters beyond Stage 1:** EventPulse's `event_id` is supplied by the producer for idempotency, so you can't just switch to a database sequence. A time-ordered ID from the client is the realistic fix, and it's a good B5 finding to write up. Also note that ClickHouse (Stage 4) avoids this whole problem: it uses a sparse index over sorted data parts rather than a per-row tree.

## 8. Unique indexes and `ON CONFLICT`

A **unique** index (your primary key) does extra work compared to a plain one:

- On every insert it must **check whether the key already exists**, which means searching the leaf for a matching entry, not just finding the position.
- If another **in-progress** transaction has inserted the same key, the new insert **waits** for that transaction to commit or abort (see the MVCC notes).

### What `ON CONFLICT (event_id) DO NOTHING` costs

```txt
 INSERT ... ON CONFLICT (event_id) DO NOTHING
   1. probe the unique index for event_id
   2a. found (duplicate)   -> skip the insert  (you still paid for the probe)
   2b. not found           -> insert heap row + all index entries as normal
```

So:

- **Duplicates are cheap-ish but not free**: one index probe each.
- **Fresh keys** pay the normal full insert cost.
- With a **random UUID**, even the duplicate probe is a random access across the index, which is cheap when the index is cached and expensive when it isn't.

This is your naive Stage 1 dedup (S1-F4). In Stage 3 you'll compare it with Redis-based dedup, partly on cost grounds.

## 9. Index types

Postgres has several index types, each with different read and **write** costs.

| Type                 | Good for                                                                                     | Write cost       | Notes                                                                                 |
| -------------------- | -------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------- |
| **B-tree** (default) | Equality, ranges, sorting (`=`, `<`, `>`, `BETWEEN`, `ORDER BY`)                             | Moderate         | What you use for the PK and `(tenant_id, occurred_at)`                                |
| **GIN**              | Containment/search inside composite values: `jsonb`, arrays, full text                       | **High**         | See below                                                                             |
| **BRIN**             | Huge tables where the column correlates with physical order (timestamps in append-only data) | **Very low**     | Tiny index that stores min/max per block range. Imprecise but nearly free to maintain |
| **Hash**             | Equality only                                                                                | Moderate         | Rarely better than B-tree                                                             |
| **GiST / SP-GiST**   | Geometric, range, nearest-neighbor                                                           | Moderate to high | Specialized                                                                           |

### GIN on `payload` (B5 includes this)

A GIN index on a `jsonb` column creates **many index entries per row**, roughly one per key/value inside the JSON. That makes inserts **much more expensive** than a B-tree on a single column.

- GIN often uses a **pending list** (fast update buffer) to batch the work, which keeps individual inserts fast, but then **flushes it in bursts**, causing **latency spikes** when it fills or vacuum runs.
- For a write-heavy table, a GIN on a large payload is usually one of the most expensive indexes you can add.

### BRIN: the underrated option for append-only time data

If rows are inserted in roughly time order, a **BRIN index on `occurred_at`** (or `received_at`) is **tiny** and costs almost nothing per insert. It narrows scans to the right block ranges instead of pinpointing rows. That is attractive for an append-heavy table queried by time range. Worth trying as an extra B5 variant. It works best on `received_at`, since `occurred_at` can be out of order for late events (Stage 3/4).

## 10. Multi-column and partial indexes

### Multi-column (composite) indexes

```sql
CREATE INDEX events_tenant_time_idx ON events (tenant_id, occurred_at);
```

- Entries are sorted by `tenant_id` **first**, then by `occurred_at` within each tenant.
- **Column order matters.** This index serves:
  - `WHERE tenant_id = 't1'`
  - `WHERE tenant_id = 't1' AND occurred_at > ...` (the ideal case)
  - It does **not** efficiently serve `WHERE occurred_at > ...` alone (no leading `tenant_id`). This is the "leftmost prefix" rule.
- **Write locality:** because entries sort by tenant then time, inserts for a given tenant at "now" land near the end of that tenant's range, which gives **better locality than a random key**, but inserts from many tenants spread across many places.

### Partial indexes

```sql
CREATE INDEX outbox_unpublished_idx ON outbox (id) WHERE published_at IS NULL;
```

- Only rows matching the `WHERE` are in the index.
- The index stays **small**, and rows that **don't match don't pay** the index-insert cost.
- Ideal for "queue-like" tables where you only care about unprocessed rows. This is exactly your Stage 3 outbox design.

### Covering indexes (`INCLUDE`)

Adding `INCLUDE (col)` stores extra column values in the leaf so some queries can be answered **from the index alone** (index-only scan). The price is a bigger index and more write cost. It also depends on the **visibility map** being up to date (see MVCC notes).

## 11. Indexes and MVCC

Recall from the MVCC notes: an UPDATE creates a **new row version**. That interacts with indexes:

| Situation                                                            | Index consequence                                                                          |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| **INSERT**                                                           | One new entry in every index                                                               |
| **UPDATE that changes an indexed column**                            | New entries in the affected indexes (and, for non-HOT updates, in **all** indexes)         |
| **UPDATE with no indexed column changed and room on the page (HOT)** | **No index writes at all**                                                                 |
| **UPDATE without HOT**                                               | A **new entry in every index**, even for indexes whose column didn't change                |
| **DELETE / dead tuples**                                             | Index entries remain until **VACUUM** removes them. Dead index entries are **index bloat** |

Takeaways:

- **More indexes means fewer updates qualify for HOT** if you index frequently updated columns. Don't index columns you update often unless a query truly needs it.
- **Index bloat** is separate from table bloat and can be worse. Heavily churned indexes (random keys, lots of deletes) can end up much larger than their live data.
- For **insert-only** tables the MVCC interaction is small, and the index cost is dominated by the insert path (sections 5-7).

## 12. When the index outgrows memory

This is the **hidden cost that appears only in long runs**, and why B11 (the soak test) matters.

```txt
 Index fits in memory (shared_buffers + OS cache):
   insert -> leaf page already cached -> fast (CPU only)

 Index is bigger than memory, keys are RANDOM:
   insert -> leaf page is probably NOT cached -> DISK READ -> then modify -> slow
```

So a **random-key insert can need a disk read**, a read on the write path. Early in a test the index is small and everything is cached, so throughput looks great. As the table grows, throughput **decays** and p99 climbs.

| Key pattern               | Memory needed for steady inserts                                  |
| ------------------------- | ----------------------------------------------------------------- |
| Sequential / time-ordered | Only the **recent right edge** of the index (tiny and always hot) |
| Random                    | The **whole index**                                               |

Watch for this in your soak data:

- `cache hit ratio` falling over time,
- disk read IOPS rising during an insert-only workload,
- throughput slowly declining while CPU stays low.

> **This is a core Stage 1 lesson:** a benchmark that fits in memory proves little. The honest measure is steady-state behavior after the indexes have outgrown the cache. (In your compose file Postgres has 2 GB RAM and default `shared_buffers`, so this point arrives sooner than on a production box.)

## 13. Prove it yourself

### Index and table sizes

```sql
SELECT pg_size_pretty(pg_table_size('events'))   AS table,
       pg_size_pretty(pg_indexes_size('events')) AS indexes;

-- per index
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan
FROM pg_stat_user_indexes
WHERE relname = 'events'
ORDER BY pg_relation_size(indexrelid) DESC;
```

`idx_scan` is how many times the index has been used. An index with **zero scans** is a pure write tax. That's a good "unused index" check.

### Measure WAL per event (the cleanest B5 number)

```sql
SELECT pg_current_wal_lsn() AS start_lsn \gset
-- run N inserts
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'start_lsn')) AS wal_generated;
-- divide by N for WAL bytes per event
```

Repeat for 0, 1, 3, 5 indexes and for each key type.

### Full-page images (the random-key effect)

```sql
SELECT wal_records, wal_fpi, wal_bytes FROM pg_stat_wal;   -- Postgres 14+
```

Compare `wal_fpi` per event between random UUIDs and ordered keys. Random keys should produce visibly more.

### Index health: density and fragmentation

```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT * FROM pgstatindex('events_pkey');
```

Look at `avg_leaf_density` (how full leaf pages are) and `leaf_fragmentation`. A random-key index typically shows **lower density** than a sequential one (the section 6 effect).

### Watch the cache hit ratio

```sql
SELECT relname,
       heap_blks_read, heap_blks_hit,
       idx_blks_read,  idx_blks_hit
FROM pg_statio_user_tables
WHERE relname = 'events';
```

`idx_blks_read` rising over a long insert run means index pages are being fetched from disk (section 12).

### See whether a query uses the index

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE tenant_id = 't1' AND occurred_at > now() - interval '1 hour';
```

Look for `Index Scan` or `Bitmap Index Scan` vs `Seq Scan`, and the `Buffers:` line (pages hit vs read).

### Statement-level view

```sql
SELECT calls, mean_exec_time, total_exec_time, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 5;
```

Your INSERT's `mean_exec_time` should rise as you add indexes.

### The B5 recipe in short

1. `TRUNCATE events; SELECT pg_stat_statements_reset();`
2. Configure the variant (indexes present, key type).
3. Run the same load at the same rate or find the knee.
4. Record: max rps, p99, WAL bytes per event, `wal_fpi`, index sizes, CPU, `pgstatindex` density, checkpoint counts.
5. Repeat for each variant. **Change one variable at a time.**

Note: the primary key is itself an index. "0 secondary indexes" still pays for the PK. To see the cost of the PK, compare against a table variant with no PK (for the experiment only).

## 15. Practical rules of thumb

1. **Index for the queries you actually run**, not "just in case". Each index is a permanent tax on writes.
2. **Drop unused indexes.** Check `idx_scan = 0` over a meaningful period.
3. **On hot ingest tables, keep indexes few and narrow.** One or two is typical.
4. **Prefer ordered keys** for write-heavy tables where possible (time-ordered IDs).
5. **Use partial indexes** for queue-like tables where only some rows matter.
6. **Consider BRIN** for append-only, time-correlated columns.
7. **Be very wary of GIN** on write-heavy `jsonb`.
8. **For bulk loads, create indexes after loading.** Building an index once over existing data is far cheaper than maintaining it row by row.
9. **Test at steady state**, with data larger than memory. Short tests flatter random-key designs.
10. **Don't tune before the baseline.** Stage 1 records the untuned, honestly-indexed design as the "before".

### Why this points to Stage 4

A row store with per-row indexes is built for point lookups and transactional updates. For analytics over hundreds of millions of rows, EventPulse moves to **ClickHouse**, which stores data sorted in immutable parts with a **sparse index** (one entry per ~8,192 rows) instead of a tree entry per row. The write cost per row drops dramatically. That architectural difference is the real answer to "why not just add indexes to Postgres".

## 16. Common confusions

**"More indexes make everything faster."**
Only reads that use them. Every write pays for every index.

**"An index is free once it's built."**
It costs on every insert, update (where applicable), and delete, plus disk space and cache.

**"The primary key doesn't count as an index."**
It does. A primary key is a unique B-tree index, with a uniqueness check on each insert.

**"UUIDs and sequential IDs perform the same."**
Not for inserts. Random UUIDs scatter writes across the index, hurting cache locality, WAL volume, and index size. Time-ordered IDs avoid most of that.

**"A short benchmark showing high insert rates proves the design."**
Not if the index still fits in memory. Performance can decay badly once it doesn't.

**"Duplicates are free with `ON CONFLICT DO NOTHING`."**
Each one still costs a unique-index probe.

**"Indexing every column I might filter on is safe."**
It multiplies write cost and can prevent HOT updates. Choose deliberately.

**"Column order in a composite index doesn't matter."**
It matters a lot. `(tenant_id, occurred_at)` serves tenant-first queries and not time-only queries.

**"The index size is small compared with the table."**
Often not. With several indexes (especially GIN) the indexes can exceed the table's size. Always check `pg_indexes_size`.

**"If I add an index, queries will use it."**
Only if the planner thinks it's cheaper than the alternatives. Check with `EXPLAIN`.

## 17. Self-test questions

Answer aloud first. Answers are below.

1. Why does every index slow inserts?
2. What does one insert do to an index, step by step?
3. What is a page split and why is it expensive?
4. Why is a random UUID primary key worse for inserts than a sequential key?
5. Why can an insert-only workload start fast and then slow down over time?
6. What does a GIN index on a `jsonb` column cost on writes?
7. What does `ON CONFLICT DO NOTHING` cost when the row is a duplicate?
8. When would a partial index or a BRIN index be a good choice?
9. Why should you check `idx_scan` and `pg_indexes_size`?
10. Why does Stage 4 move analytics out of Postgres instead of adding more indexes?

<details>
<summary>Answers</summary>

1. Each index is a separate sorted structure that must receive an entry for every new row. That adds tree traversal, a page modification, and WAL per index per row, so cost grows with the number of indexes.
2. Descend from root to the correct leaf page, find the position, insert the entry, mark the page dirty, split the page if it's full, and write a WAL record (possibly with a full-page image).
3. When a leaf is full, Postgres allocates a new page, moves about half the entries, updates the parent, and writes extra WAL. It's expensive because of the extra I/O and WAL, and it leaves pages partly empty, bloating the index.
4. Random keys land on random leaf pages: poor cache locality, many more dirty pages, more full-page WAL images, more mid-tree splits, and a bigger, less dense index. Sequential keys all hit the same hot right-edge page.
5. At first the index fits in memory, so inserts are CPU-only. As it outgrows memory, random-key inserts need disk reads for non-cached leaf pages, and checkpoints write more, so throughput decays and p99 rises.
6. Many entries per row (about one per key/value inside the JSON), plus pending-list flushes that cause latency spikes. It's one of the most expensive index types for writes.
7. One probe of the unique index to find the existing key, then the insert is skipped. Cheap if the index pages are cached, expensive if not, and it isn't free.
8. A partial index suits queue-like tables where only a subset of rows matters (e.g. unpublished outbox rows), keeping the index small and non-matching rows free of index cost. BRIN suits huge append-only tables where a column (like a timestamp) correlates with physical order: tiny and almost free to maintain.
9. `idx_scan = 0` reveals unused indexes that are pure write tax; `pg_indexes_size` reveals when indexes rival or exceed the table, which has memory and WAL consequences.
10. Per-row tree indexes are costly to maintain and are a poor fit for scanning and aggregating huge volumes. ClickHouse uses sorted immutable parts with a sparse index and columnar storage, so writes are cheap and aggregates scan only needed columns.

</details>

## 18. Glossary and cheat sheet

| Term                      | Meaning                                                                     |
| ------------------------- | --------------------------------------------------------------------------- |
| **index**                 | A separate data structure that speeds up lookups on some columns            |
| **B-tree**                | Default sorted, balanced tree index                                         |
| **heap**                  | The table's own row storage                                                 |
| **leaf page**             | Index page holding actual entries (key + ctid)                              |
| **page split**            | Dividing a full index page into two to fit a new entry                      |
| **fillfactor**            | How full pages are packed when built (B-tree default 90%)                   |
| **write amplification**   | Physical bytes written divided by useful bytes (indexes multiply it)        |
| **full-page image (FPI)** | Whole 8 KB page written to WAL on first change after a checkpoint           |
| **unique index**          | Index that enforces no duplicate keys (and checks on every insert)          |
| **GIN**                   | Index for values containing many items (jsonb, arrays, text); costly writes |
| **BRIN**                  | Tiny block-range index for naturally ordered data; very cheap writes        |
| **partial index**         | Index covering only rows that match a condition                             |
| **composite index**       | Index on several columns; order matters (leftmost prefix)                   |
| **HOT update**            | Update that needs no index changes                                          |
| **index bloat**           | Wasted index space from dead entries and half-empty pages                   |
| **seq scan / index scan** | Reading the whole table vs using an index                                   |

### Cheat sheet

```txt
every index  = +1 entry per INSERT + extra WAL + extra dirty page + extra disk/cache
cost grows   ~ linearly with number of indexes (PK counts!)
random key   = scattered pages, more splits, more FPIs, whole index must be cached
ordered key  = hot right edge only: cheap and cache-friendly
index > RAM + random keys = inserts need disk READS -> throughput decays over time
GIN on jsonb = many entries per row + pending-list flush spikes (expensive)
BRIN         = tiny + nearly free writes (append-only, time-correlated data)
partial idx  = only matching rows pay (great for queue/outbox tables)
ON CONFLICT  = still probes the unique index
index more   -> fewer HOT updates, more index bloat
fix at scale = columnar store w/ sparse index (ClickHouse, Stage 4)
```

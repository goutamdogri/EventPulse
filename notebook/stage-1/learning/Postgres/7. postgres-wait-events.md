## 1. TL;DR

- A **wait event** is Postgres telling you **what a backend process is waiting for right now**: disk, a lock, the client, another process, and so on.
- You read it from `pg_stat_activity`, in the columns **`wait_event_type`** and **`wait_event`**.
- **No wait event on an `active` backend means it is running on the CPU.** So every active backend is either **computing** or **waiting for something specific**.
- One snapshot tells you little. **Many snapshots over a test run** tell you **where time goes**, like a profiler for the database.
- The classic Stage 1 mapping:

| You see                    | It usually means                                            | Notes topic                   |
| -------------------------- | ----------------------------------------------------------- | ----------------------------- |
| `IO: WALSync` / `WALWrite` | Commits waiting for the WAL fsync                           | Write path                    |
| `IO: DataFileRead`         | Cache misses; pages read from disk                          | Index cost                    |
| `Lock: transactionid`      | Waiting on another transaction's row lock                   | Locks                         |
| `LWLock: ...`              | Internal contention at high concurrency                     | Process-per-connection, Locks |
| `Client: ClientRead`       | Postgres is **waiting for your app** to send the next thing | Pool and app                  |
| _(none, state `active`)_   | Running on CPU                                              | Index cost, CPU               |

> **One-line version:** _Wait events turn "the database is slow" into "the database is slow because it is waiting for X", and X tells you which experiment and which fix._

## 2. The mental model

Imagine an **emergency room triage board** showing every patient (every backend process) and what is happening to them **at this instant**.

| Triage board                                               | Postgres                                         |
| ---------------------------------------------------------- | ------------------------------------------------ |
| "Being treated by a doctor right now"                      | **Active, no wait event**: running on CPU        |
| "Waiting for the X-ray machine"                            | **IO** wait (disk)                               |
| "Waiting for the specialist who is with another patient"   | **Lock** wait (another transaction holds a lock) |
| "Waiting for the corridor to clear"                        | **LWLock** wait (internal shared structure busy) |
| "Sitting in a bed, waiting for the family to bring a form" | **Client** wait (waiting on your app)            |
| "Waiting for a call back from another department"          | **IPC** wait (another process)                   |
| "Asleep in the waiting room"                               | **Idle** (nothing to do)                         |
| Taking **a photo of the board every second** and counting  | **Sampling** (section 7)                         |

The board does not say how long anyone has waited in total. It only says what they are doing now. But if you photograph it a thousand times and half the photos show "waiting for the X-ray machine", you have found your bottleneck.

## 3. What a wait event is

Every backend process, when it can't make progress, **records what it is about to wait for** in shared memory, then waits. That record is exposed through `pg_stat_activity`:

| Column                | Meaning                                                                         |
| --------------------- | ------------------------------------------------------------------------------- |
| **`state`**           | What the backend is doing overall: `active`, `idle`, `idle in transaction`, ... |
| **`wait_event_type`** | The **category** of wait (`IO`, `Lock`, `LWLock`, `Client`, ...)                |
| **`wait_event`**      | The **specific** wait (`WALSync`, `transactionid`, `ClientRead`, ...)           |

```sql
SELECT pid, state, wait_event_type, wait_event, left(query, 50) AS query
FROM pg_stat_activity
WHERE datname = 'eventpulse';
```

```txt
  pid  |        state        | wait_event_type |  wait_event   |          query
-------+---------------------+-----------------+---------------+------------------------
  4821 | active              | IO              | WALSync       | INSERT INTO events ...
  4822 | active              | Lock            | transactionid | UPDATE tenant_counters ...
  4823 | active              |                 |               | INSERT INTO events ...     <- on CPU
  4824 | idle                | Client          | ClientRead    | COMMIT
```

### Key properties

- It's an **instantaneous snapshot**, not a history. A backend can wait for 10 microseconds and you'll likely miss it.
- A **NULL** wait event on an active backend means **it's on the CPU** (or in code not instrumented with a wait event).
- It's **free to read** (a view over shared memory), so you can poll it every second even during a benchmark.

## 4. Reading `pg_stat_activity` correctly

### The `state` column matters as much as the wait event

| `state`                         | Meaning                                                   | How to read the wait event                                                               |
| ------------------------------- | --------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **`active`**                    | Running a query                                           | The wait event is the **interesting** one: NULL = CPU, otherwise the reason it's stalled |
| **`idle`**                      | Connected, no transaction, waiting for the client         | Wait event is `Client: ClientRead`. **Normal, ignore it**                                |
| **`idle in transaction`**       | In a transaction, waiting for the client's next statement | Also `ClientRead`. **Dangerous** if long (holds locks and blocks vacuum)                 |
| `idle in transaction (aborted)` | Transaction hit an error, client hasn't rolled back       | Same concern                                                                             |

### Always filter

```sql
-- only real client sessions, not background workers, not yourself
WHERE backend_type = 'client backend'
  AND pid <> pg_backend_pid()
  AND datname = 'eventpulse'
```

Without `backend_type = 'client backend'` you'll also see background processes (checkpointer, WAL writer, autovacuum, etc.). They show up with `Activity` waits (they're idle waiting for work) and will clutter your picture.

### The two most useful queries

```sql
-- What are the active backends waiting for, right now?
SELECT coalesce(wait_event_type, 'CPU') AS wait_type,
       coalesce(wait_event, '-')        AS wait_event,
       count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND state = 'active'
  AND pid <> pg_backend_pid()
GROUP BY 1, 2
ORDER BY 3 DESC;

-- Same, but also show sessions stuck idle in a transaction
SELECT state, coalesce(wait_event_type,'-') AS wt, coalesce(wait_event,'-') AS we, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND pid <> pg_backend_pid()
GROUP BY 1, 2, 3
ORDER BY 4 DESC;
```

(`coalesce(..., 'CPU')` is a helpful trick: it labels the "no wait event" case as CPU.)

## 5. The wait event types

Postgres groups waits into **types**. Knowing the type narrows the cause immediately.

| `wait_event_type` | What it means                                              | Typical cause                                          |
| ----------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| **`CPU`** (NULL)  | Not waiting; running                                       | Query work, parsing, index maintenance                 |
| **`IO`**          | Waiting for a disk operation                               | Reading pages, writing/fsyncing WAL, checkpoint writes |
| **`Lock`**        | Waiting for a **heavyweight lock** (the user-visible kind) | Row locks, table locks, advisory locks                 |
| **`LWLock`**      | Waiting for an **internal lightweight lock**               | Contention on shared structures at high concurrency    |
| **`Client`**      | Waiting for the **client** to send or receive data         | App is slow, idle sessions, network                    |
| **`IPC`**         | Waiting for **another process**                            | Replication acknowledgments, parallel workers          |
| **`Timeout`**     | Waiting for a timer                                        | `pg_sleep`, vacuum cost delay                          |
| **`BufferPin`**   | Waiting for exclusive access to a buffer                   | Usually vacuum or heavy page contention                |
| **`Activity`**    | A **background** process idle, waiting for work            | Normal. Ignore                                         |
| `Extension`       | Waiting inside an extension                                | Rare                                                   |

A rough mental grouping:

```txt
 CPU        -> I'm working
 IO         -> the DISK is the limit
 Lock       -> OTHER TRANSACTIONS are the limit (design / contention)
 LWLock     -> too much CONCURRENCY on internal structures
 Client     -> the APPLICATION / network is the limit
 IPC        -> another process (replica, worker) is the limit
```

## 6. The wait events you will actually meet

You don't need the whole catalogue. These are the ones relevant to EventPulse Stage 1, grouped by type. _(Exact names vary somewhat between Postgres versions, so check yours with `SELECT _ FROM pg_wait_events;` on Postgres 17+, or the docs table "Wait Events" for your version.)\*

### `IO` waits

| Wait event                           | What is happening                               | Connects to                                             |
| ------------------------------------ | ----------------------------------------------- | ------------------------------------------------------- |
| **`WALSync`**                        | Fsyncing the WAL: **the commit wait**           | Write path (commit latency is mostly fsync). B1, B3, B6 |
| **`WALWrite`**                       | Writing WAL to the OS                           | Write path                                              |
| **`DataFileRead`**                   | Reading a table/index page that wasn't in cache | Index cost section 12 (index outgrew memory). B11       |
| **`DataFileWrite`**                  | A backend writing a dirty page itself           | Checkpoints section 10 (workers not keeping up)         |
| **`DataFileExtend`**                 | Growing a data file (adding pages)              | Insert-heavy tables growing                             |
| **`DataFileSync` / `DataFileFlush`** | fsync/flush of data files                       | Mostly the checkpointer; sync phase of checkpoints      |
| `WALInitWrite` / `WALInitSync`       | Creating a new WAL segment                      | Brief stalls when new WAL files are needed              |

### `Lock` waits

| Wait event          | What is happening                                                                                        | Connects to                                               |
| ------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **`transactionid`** | Waiting for **another transaction to finish**: a row lock held by it, or a conflicting unique key insert | Locks (B4 hot row, duplicate keys)                        |
| **`tuple`**         | Queued for the lock on a specific row when **several** waiters want it                                   | Locks (B4, deeper queue)                                  |
| **`relation`**      | Waiting for a **table-level** lock                                                                       | Locks (DDL, migrations)                                   |
| **`extend`**        | Waiting for the lock to **extend a relation** (add a page)                                               | Many concurrent inserters growing the same table or index |
| `advisory`          | Waiting for an application-defined lock                                                                  | Locks                                                     |
| `virtualxid`        | Waiting for a transaction to end (e.g. concurrent index build)                                           | DDL                                                       |

### `LWLock` waits (internal)

| Wait event (examples)                 | What it protects                         | Connects to                                       |
| ------------------------------------- | ---------------------------------------- | ------------------------------------------------- |
| **`WALWrite`** (LWLock)               | The right to flush WAL                   | High concurrency commits                          |
| **`WALInsert`**                       | Appending records into WAL buffers       | Heavy parallel inserts into a single WAL          |
| **`BufferContent` / `BufferMapping`** | A page in the buffer cache               | Hot pages (right-edge index leaf, hot row's page) |
| **`LockManager`**                     | Table of heavyweight locks               | Many backends locking at once                     |
| **`ProcArray`**                       | List of running transactions (snapshots) | Very many connections                             |

> Don't confuse **`IO: WALWrite`** (the actual write call) with **`LWLock: WALWrite`** (waiting for permission to do the write). The _type_ tells you which.

### `Client` waits

| Wait event       | What is happening                                             | Reading it                                                                                                                  |
| ---------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **`ClientRead`** | Backend waiting for the client to send the next query or data | On `idle` sessions: normal. On `idle in transaction`: your **app** is holding a transaction open while doing something else |
| `ClientWrite`    | Backend waiting for the client to receive results             | Slow client or network                                                                                                      |

### `IPC`, `Timeout`, `Activity`

| Wait event                        | Meaning                                                                  |
| --------------------------------- | ------------------------------------------------------------------------ |
| `IPC: SyncRep`                    | Waiting for a synchronous replica (relevant from Stage 6)                |
| `IPC: ParallelFinish` and similar | Waiting for parallel workers                                             |
| `Timeout: PgSleep`                | `pg_sleep()`. Your **B3** experiment's artificial delay shows up as this |
| `Timeout: VacuumDelay`            | Vacuum throttling itself                                                 |
| `Activity: ...`                   | Background processes idle. Ignore                                        |

## 7. Sampling

A single look at `pg_stat_activity` is a **coin flip**. To get a real answer, **sample repeatedly** and count. This is exactly how a CPU profiler works: take many snapshots of "what is it doing", and the proportions approximate where the time goes.

```txt
 sample 1: 12 active ->  7 WALSync, 3 CPU, 2 transactionid
 sample 2: 14 active ->  9 WALSync, 3 CPU, 2 transactionid
 sample 3: 10 active ->  6 WALSync, 3 CPU, 1 DataFileRead
 ...
 After 60 samples: ~60% of active time was WALSync  =>  commit fsync is the bottleneck
```

### A simple sampler in plain SQL

Create a table to collect samples:

```sql
CREATE TABLE IF NOT EXISTS wait_samples (
  ts              timestamptz DEFAULT now(),
  state           text,
  wait_event_type text,
  wait_event      text,
  n               int
);
```

Then, in a **psql** session, record one sample per second (leave it running during the load test):

```sql
INSERT INTO wait_samples (state, wait_event_type, wait_event, n)
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE backend_type = 'client backend'
  AND datname = 'eventpulse'
  AND pid <> pg_backend_pid()
  AND state <> 'idle'
GROUP BY 1, 2, 3;
\watch 1
```

After the run, summarize **where active time went**:

```sql
SELECT coalesce(wait_event_type, 'CPU') AS wait_type,
       coalesce(wait_event, '-')        AS wait_event,
       sum(n)                           AS samples,
       round(100.0 * sum(n) / sum(sum(n)) OVER (), 1) AS pct
FROM wait_samples
GROUP BY 1, 2
ORDER BY samples DESC;
```

Truncate the table between runs (`TRUNCATE wait_samples;`), just as you reset `pg_stat_statements`.

> **Tip:** the sampler itself is cheap at 1 sample per second, so it won't disturb your benchmark. If you want finer resolution, sample 5-10 times per second, but the query is still lightweight.

### Why sampling is trustworthy

Long waits show up in many consecutive samples, so they dominate the counts. Rare tiny waits show up in few samples, which is exactly right: they don't matter. The method is **statistical**, so use enough samples (hundreds) before drawing conclusions.

## 8. Average active sessions

**Average Active Sessions (AAS)** is the single most useful number from wait event sampling:

```txt
AAS  =  total samples of active backends  /  number of sampling intervals
      =  average number of backends doing something at the same time
```

It is **Little's Law again** (concurrency = rate x time in system), applied to the database:

```txt
AAS  =  queries per second  x  average active time per query
```

### How to use it

Compare AAS with the **number of CPU cores** available to Postgres (your container has `cpus: 2`):

| Picture                               | Meaning                                                                                    |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| AAS well **below** cores, mostly CPU  | Plenty of headroom; not saturated                                                          |
| AAS **above** cores, mostly **CPU**   | CPU is saturated: queries are queueing for the processor                                   |
| AAS **above** cores, mostly **waits** | The database is **waiting**, not working: look at **which wait dominates** (IO, Lock, ...) |
| AAS roughly **equals your pool size** | Every pool connection is busy: the **pool** may be the limit                               |

### Splitting AAS by wait type is the "where does time go" chart

```txt
 AAS
  ^
 12|        ██████████████
   |        ██▓▓▓▓▓▓▓▓▓▓▓▓      █ = IO:WALSync
  8|        ██▓▓▓▓▓▓▓▓▓▓▓▓      ▓ = Lock:transactionid
   |   ░░░░ ██▓▓▓▓▓▓▓▓▓▓▓▓      ░ = CPU
  4|   ░░░░ ██▓▓▓▓▓▓▓▓▓▓▓▓
   |   ░░░░ ░░░░░░░░░░░░░░
  0+---------------------------> time (load rises)
```

If you graph this over a load test, you can watch **which wait appears as you approach the knee**. That is the explanation for the knee, in one picture.

## 9. What wait events cannot see

Wait events describe **backends inside Postgres**. Several important delays happen **outside** it and never appear here.

| Delay                                  | Where it lives                                 | How to see it instead                                 |
| -------------------------------------- | ---------------------------------------------- | ----------------------------------------------------- |
| **Waiting for a free pool connection** | Inside your **Node process** (`pg.Pool` queue) | `pool.waitingCount`, pool wait time in `/debug/stats` |
| Node CPU, event loop lag               | Node                                           | Event loop delay, flame graph                         |
| Network latency to Postgres            | Network                                        | `ClientRead/Write` hints; ping, traces                |
| Time in the OS accept queue / TCP      | Kernel                                         | `ss -ltn`, listen overflow counters (Stage 0)         |

### The most important consequence

```txt
 pool.waitingCount is HIGH  but  pg_stat_activity shows FEW active backends, mostly CPU/idle
        => Postgres is NOT the bottleneck. The pool or the app is.
        => A bigger pool or faster app code may help.

 pool.waitingCount is HIGH  and  pg_stat_activity shows MANY active backends, mostly waiting
        => Postgres IS the bottleneck, and the wait event tells you which resource.
        => A bigger pool will not help; it may make it worse.
```

### The `ClientRead` insight (Postgres waiting for you)

If many sessions are **`idle in transaction` with `ClientRead`**, Postgres is not slow: it's **waiting on your Node code** between statements (for example, while your service does other work inside a transaction). That's an app-side design problem (hold transactions open only as long as needed, section 7 of the Locks notes).

This distinction (pool wait vs database wait) is the "pool wait time vs query time" pitfall from the Stage 1 doc, now with a precise tool.

## 10. Diagnosis playbook

Start from the **symptom**, check the **wait**, find the **cause**.

| Symptom                                          | Dominant wait                                       | Likely cause                                      | Notes / next step                                                               |
| ------------------------------------------------ | --------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Latency high, **CPU low**, writes slow           | `IO: WALSync` / `WALWrite`                          | Slow commit fsync; disk busy (maybe a checkpoint) | `pg_test_fsync`, `iostat -x`, check checkpoint timing; batching later (Stage 2) |
| Latency spikes **on a rhythm**                   | `IO: WALSync`, `DataFileWrite`, `DataFileSync`      | Checkpoints competing for the disk                | Checkpoint log lines vs spike times                                             |
| Throughput **decays over a long run**, CPU low   | `IO: DataFileRead`                                  | Index/table no longer fits in cache (random keys) | Cache hit ratio, index sizes (B11, B5)                                          |
| Latency high, **CPU low**, one tenant hot        | `Lock: transactionid` (+ `tuple`)                   | Hot row serialization                             | `pg_blocking_pids`, locks notes (B4)                                            |
| Everything freezes after a migration             | `Lock: relation`                                    | `ALTER`/`TRUNCATE` queue convoy                   | `lock_timeout`, find the long query (Locks section 9)                           |
| Many inserters, rising latency, high concurrency | `Lock: extend`, `LWLock: WALInsert`/`BufferContent` | Contention on growing one relation or hot pages   | Fewer connections; ordered keys; batching                                       |
| Many connections, **throughput falling**         | `LWLock: *`, high CPU context switches              | Too many active backends                          | Reduce pool size (B2)                                                           |
| High latency, CPU low, **no Postgres waits**     | mostly `Client: ClientRead` / idle                  | The **app or pool** is the bottleneck             | Check pool counters, Node CPU/event loop                                        |
| High latency, **CPU high**                       | _(none, i.e. CPU)_                                  | Genuine CPU work: parsing, indexes, JSON          | `pg_stat_statements`, flame graph, B5                                           |
| Sessions piling up `idle in transaction`         | `Client: ClientRead`                                | App leaks or holds transactions                   | Fix app; set `idle_in_transaction_session_timeout`                              |
| B3: artificial delay                             | `Timeout: PgSleep`                                  | Your injected latency                             | Confirms the experiment works                                                   |

### A fast mental flow

```txt
 Is the query "active"?
   no  -> idle / idle in transaction: look at the APP (pool, transactions held open)
   yes -> wait_event IS NULL?
            yes -> CPU-bound:  pg_stat_statements, flame graph
            no  -> what is the TYPE?
                    IO      -> disk: WALSync (commit), DataFileRead (cache), DataFileWrite/Sync (checkpoint)
                    Lock    -> design: who is blocking? (pg_blocking_pids)
                    LWLock  -> too much concurrency or a hot page: cut connections / fix key order
                    Client  -> app/network is slow
                    IPC     -> replica / workers
```

## 11. Prove it yourself

Reproduce each wait so you recognize it in the wild. Use a scratch table for the lock demos.

### See a `Timeout: PgSleep` (this is your B3 delay)

Terminal 1:

```sql
SELECT pg_sleep(30);
```

Terminal 2:

```sql
SELECT pid, state, wait_event_type, wait_event, left(query, 40) AS query
FROM pg_stat_activity WHERE query LIKE 'SELECT pg_sleep%' AND pid <> pg_backend_pid();
```

### See `Lock: transactionid` (a row lock wait)

```sql
CREATE TABLE IF NOT EXISTS lock_demo (id int PRIMARY KEY, n int);
INSERT INTO lock_demo VALUES (1, 0) ON CONFLICT DO NOTHING;
```

Terminal 1: `BEGIN; UPDATE lock_demo SET n = n + 1 WHERE id = 1;` (don't commit)
Terminal 2: `UPDATE lock_demo SET n = n + 1 WHERE id = 1;` (hangs)
Terminal 3: run the "what are active backends waiting for" query from section 4. Terminal 2 shows `Lock / transactionid`. Then `COMMIT;` in Terminal 1.

### See `Lock: relation` (a table lock wait)

Terminal 1: `BEGIN; LOCK TABLE lock_demo IN ACCESS EXCLUSIVE MODE;`
Terminal 2: `SELECT * FROM lock_demo;` (hangs, shows `Lock / relation`)
`ROLLBACK;` in Terminal 1.

### See `Client: ClientRead` on an idle-in-transaction session

Terminal 1: `BEGIN; SELECT 1;` (leave it)
Terminal 3: `SELECT pid, state, wait_event_type, wait_event FROM pg_stat_activity WHERE state = 'idle in transaction';`
You'll see `Client / ClientRead`. This is Postgres waiting for **you**.

### See `IO: WALSync` and friends under write load

`pgbench` ships with Postgres and is handy for generating concurrent writes quickly:

```bash
pgbench -i -s 10 eventpulse_scratch          # initialize a scratch database (not your real one)
pgbench -c 16 -j 4 -T 60 -N eventpulse_scratch
```

While it runs, in another terminal run the "what are active backends waiting for" query repeatedly (or the sampler from section 7). Expect to see `IO: WALSync` (commits waiting for fsync), some `LWLock` entries, and CPU. Try again with `-c 2` and with `-c 64` and compare the mix: more connections usually adds `LWLock` and more waiting without more throughput.

### See `IO: DataFileRead` (cache misses)

Build a table larger than `shared_buffers` and scan it after the cache is cold:

```sql
CREATE TABLE big AS SELECT g AS id, md5(g::text) AS pad FROM generate_series(1, 5000000) g;
-- restart Postgres (or evict cache) so it's cold, then:
SELECT count(*) FROM big;
```

Sample during the scan: you should see `IO: DataFileRead`.

### Watch the sampler produce a profile

1. Start the sampler (section 7) in a `psql` terminal.
2. Run a k6 test against your service (or the `pgbench` run above).
3. Stop the sampler (`Ctrl-C`), run the summary query, and write the top 3 waits and their percentages in your notebook.

### Measure I/O time precisely (optional)

```sql
ALTER SYSTEM SET track_io_timing = on;
SELECT pg_reload_conf();
```

With this on, `EXPLAIN (ANALYZE, BUFFERS)` reports **I/O timings**, and I/O statistics views report time spent reading and writing. (It adds a small timing overhead, so record it as a setting you changed.)

### List what the wait events mean (Postgres 17+)

```sql
SELECT type, name, description FROM pg_wait_events ORDER BY type, name;
```

On older versions, use the "Wait Events" table in the documentation for your version.

## 12. Getting wait events into Grafana

You already run Prometheus and Grafana, so you can make the "AAS by wait type" chart a live panel. This is **optional** for Stage 1 (the SQL sampler is enough) but valuable from Stage 2 onward.

The idea:

1. Run a **Postgres exporter** (such as `postgres_exporter`) alongside Postgres in compose.
2. Add a **custom query** that returns the grouped counts from `pg_stat_activity` (the section 4 query) as a gauge labeled by `wait_event_type` and `wait_event`.
3. Prometheus scrapes it. Grafana plots it as a **stacked time series**.

```txt
 postgres_exporter  --(custom query: count by wait_event_type, wait_event)-->  Prometheus  -->  Grafana
```

Practical notes:

- Each scrape is **one snapshot**, so with a 1-5 s scrape interval you get a coarse but useful profile over time.
- Keep **label cardinality low**: group by type and event only. Don't add query text or pid as labels (a lesson from the Stage 7 observability notes).
- Plot **alongside** the other Stage 1 signals: pool counters, p99, Postgres CPU, and checkpoint events, so you can read them together.

(Verify the exact exporter configuration syntax against its documentation for the version you install.)

## 13. Stage 1 experiments

For each experiment, **sample wait events** and record the top waits next to your usual metrics. This is what turns "the knee was at X" into "the knee was at X **because** of Y".

| Experiment                       | Expected dominant waits                                                                                                            | What it confirms                                         |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **B1 Ramp to collapse**          | At the knee: `IO: WALSync` (commit), or CPU, or pool-limited with few DB waits                                                     | Which resource sets the knee                             |
| **B2 Pool exhaustion**           | Small pool: few active backends, DB mostly idle/CPU, pool queue grows. Large pool: more `LWLock`, more waiting, falling throughput | Pool limit vs database limit; the sweet spot             |
| **B3 Slow database propagates**  | `Timeout: PgSleep` (if you inject with `pg_sleep`) filling all active backends                                                     | Latency propagates one-for-one; max rps = pool / latency |
| **B4 Hot row**                   | `Lock: transactionid` and `Lock: tuple`, low CPU                                                                                   | One-row serialization                                    |
| **B5 Index write amplification** | More CPU and more `IO: DataFileRead/Write`, more `WALSync` with more indexes                                                       | Cost of indexes; random-key cache misses                 |
| **B6 Durability knob**           | With `synchronous_commit=on`: heavy `WALSync`. With `off`: `WALSync` largely **disappears** from client backends                   | Commit fsync is what you traded away                     |
| **B7 Payload size**              | More `IO` (WAL/data writes), more CPU                                                                                              | Bytes per event drive cost                               |
| **B8 DB restart**                | Connection errors and `Client`/idle shifts; recovery                                                                               | Failure behavior                                         |
| **B10 Missing timeouts**         | Backends stuck in `Lock` or `Timeout` with no limit                                                                                | Why every call needs a deadline                          |
| **B11 Soak**                     | Gradual rise of `IO: DataFileRead`; rhythmic `WALSync`/`DataFileWrite` bumps at checkpoints                                        | Cache decay and checkpoint spikes                        |

> Add one line to every notebook entry: **"Top 3 wait events and their percentage of active samples."** After a few experiments you'll see patterns that make diagnosis fast.

## 14. Caveats and limits

| Caveat                                 | What to remember                                                                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Snapshot, not duration**             | A single read shows only "now". Use sampling for proportions                                                                         |
| **Short waits are missed**             | Waits of microseconds rarely appear. That's fine: they rarely matter                                                                 |
| **NULL isn't always "CPU"**            | It means "no wait event reported". Usually CPU, but some code paths aren't instrumented                                              |
| **Names change between versions**      | New releases add, rename, and reorganize wait events. Don't hard-code assumptions; check your version's list                         |
| **Per-session, not per-query history** | `pg_stat_activity` has no waiting history. Per-query wait profiles need an extension such as `pg_wait_sampling`, or your own sampler |
| **Background processes appear too**    | Filter on `backend_type = 'client backend'`                                                                                          |
| **Sampling needs enough samples**      | Tens of samples can mislead. Aim for hundreds over a steady-state run                                                                |
| **It can't see outside Postgres**      | Pool waits and app CPU are invisible here (section 9)                                                                                |
| **Correlation, not proof**             | A dominant wait points at a bottleneck. Confirm with another signal (`iostat`, locks, flame graph) before declaring victory          |

## 15. Common confusions

**"No wait event means nothing is wrong."**
On an `active` backend it means it's **running on CPU**. If CPU is saturated, that's your bottleneck.

**"`ClientRead` means a slow client, so a problem."**
On an `idle` session it's normal. It's only a signal when it's on `idle in transaction` (your app is holding a transaction open) or when many _active-looking_ workloads are really waiting on the app.

**"Pool wait appears as a wait event."**
No. The pool queue lives in Node. Postgres never sees those requests until they get a connection.

**"One query of `pg_stat_activity` is enough."**
It's one frame of a movie. Sample repeatedly.

**"`WALWrite` is always the lock."**
There are two: `IO: WALWrite` (the write call itself) and `LWLock: WALWrite` (waiting for the right to write). Check the type.

**"High `Lock` waits mean add more hardware."**
Lock waits mean other transactions are the limit. Fix the design (shorter transactions, no hot rows).

**"High `IO` waits mean buy faster disks."**
Maybe, but first check which IO wait: `WALSync` (commit fsync: batch, or cheaper commits), `DataFileRead` (cache/memory or key order), or checkpoint-related writes (settings and WAL volume).

**"More connections will drain the waits."**
More active backends usually adds `LWLock` waits and more contention. Waiting in a **small pool** is cheaper than waiting inside Postgres.

**"If waits are low, the system is fast."**
Not necessarily. If AAS is low but requests are slow, the delay is **outside** Postgres (pool, app, network).

## 16. Self-test questions

Answer aloud first. Answers are below.

1. What does it mean when an `active` backend has no wait event?
2. What is the difference between `Lock` and `LWLock` waits?
3. You see `IO: WALSync` dominating. What does that tell you, and what experiment (B-number) is related?
4. Why is a single `pg_stat_activity` query insufficient, and what do you do instead?
5. What is Average Active Sessions and how do you use it with your CPU count?
6. Many sessions show `idle in transaction` with `ClientRead`. Who is the bottleneck?
7. `pool.waitingCount` is high but Postgres shows few active backends. Where is the bottleneck?
8. Throughput decays over a 1-hour soak with low CPU, and `DataFileRead` rises. What's likely happening?
9. Name two wait events that would show up in B4 (hot row contention).
10. Why can't wait events show you the `pg.Pool` queue?

<details>
<summary>Answers</summary>

1. It is running on the CPU (or in code with no instrumented wait). It isn't waiting for any resource, so CPU is the thing to check.
2. `Lock` is a heavyweight, user-visible lock (rows, tables, advisory) held by transactions, which you design around. `LWLock` is an internal lightweight lock on shared memory structures, indicating contention among many backends at high concurrency; you mostly reduce it by reducing concurrency, batching, and avoiding hot pages.
3. Backends are waiting for the WAL to be fsynced at commit, so commit/fsync latency is the bottleneck. Related to the write path notes and B6 (and B1/B3 for how it shapes capacity). Remedies: batching (Stage 2), faster storage, understanding checkpoint competition.
4. It's an instantaneous snapshot, so you'd miss most waits and get a misleading picture. Sample repeatedly (e.g. once per second, hundreds of samples) and aggregate counts by wait type and event.
5. AAS is the average number of active backends over time (equal to queries per second x average active time). Compare it with CPU cores: above cores and mostly CPU means CPU saturation; above cores and mostly waits means the waits (IO, Lock, etc.) are the bottleneck.
6. The application. Postgres is waiting for your Node code to send the next statement or commit while a transaction is open.
7. In the pool or the app (Node), not in Postgres. Postgres isn't saturated; requests are queued in the client-side pool.
8. The index/table is outgrowing memory (especially with random keys), so inserts and reads increasingly need disk reads. Cache hit ratio falls and `DataFileRead` rises, while CPU stays low. Related to index cost section 12 and B11.
9. `Lock: transactionid` and `Lock: tuple` (the queue behind the hot row's lock).
10. The pool queue lives inside your Node process, before any connection to Postgres is used. Postgres only sees backends that already have a connection, so you need the pool's own counters (`waitingCount`).

## 17. Glossary and cheat sheet

| Term                    | Meaning                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------- |
| **wait event**          | What a backend is currently waiting for, reported in `pg_stat_activity`               |
| **`wait_event_type`**   | Category: `IO`, `Lock`, `LWLock`, `Client`, `IPC`, `Timeout`, `BufferPin`, `Activity` |
| **`wait_event`**        | The specific reason within the type (e.g. `WALSync`)                                  |
| **active**              | Backend currently executing a query                                                   |
| **idle in transaction** | In a transaction but waiting for the client's next statement                          |
| **sampling**            | Reading `pg_stat_activity` repeatedly and counting to estimate where time goes        |
| **AAS**                 | Average Active Sessions: average number of backends active at once                    |
| **`WALSync`**           | Waiting for WAL fsync (the commit wait)                                               |
| **`DataFileRead`**      | Reading a data page not found in cache                                                |
| **`transactionid`**     | Waiting for another transaction to finish (row lock or unique-key conflict)           |
| **`ClientRead`**        | Waiting for the client to send something                                              |
| **LWLock**              | Lightweight internal lock on shared structures                                        |
| **`pg_wait_events`**    | View (Postgres 17+) describing every wait event                                       |
| **`pg_wait_sampling`**  | Extension that records wait samples over time                                         |

### Cheat sheet

```txt
state='active' + wait_event NULL     = on CPU
IO:WALSync / WALWrite                = commit waiting for WAL fsync          (write path, B6)
IO:DataFileRead                      = cache miss, page read from disk       (index cost, B11)
IO:DataFileWrite/Sync                = checkpoint / backend page writes      (checkpoints)
Lock:transactionid / tuple           = waiting on another txn's row lock     (locks, B4)
Lock:relation                        = table lock (DDL queue convoy)         (locks)
Lock:extend                          = many inserters extending one relation
LWLock:*                             = internal contention, too much concurrency
Client:ClientRead on idle in tx      = Postgres waiting for YOUR APP
Timeout:PgSleep                      = your artificial delay (B3)

one snapshot = a coin flip -> SAMPLE every second, hundreds of times, aggregate
AAS = avg active backends = QPS x active time ; compare with CPU cores
pool wait is INVISIBLE here: check pool.waitingCount (Node side)
  high pool wait + few DB waits  -> bottleneck is pool/app
  high pool wait + many DB waits -> bottleneck is Postgres (look at the wait type)
record in every notebook entry: top 3 waits + % of active samples
```

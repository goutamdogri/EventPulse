## 1. TL;DR

- Postgres gives **every client connection its own operating-system process** (called a _backend_).
- A connection is therefore **heavy**: it has real memory, real scheduling cost, and takes real time to set up.
- `max_connections` (default **100**) is a hard ceiling. Hit it and new clients are refused.
- More connections does **not** mean more throughput. Past a small number, more connections make Postgres **slower**, because the CPU spends time switching between processes and they fight over shared structures.
- The right design is **few, busy, reused connections** (a pool), not **many, idle, short-lived ones**.

> **One-line version:** _In Postgres, a connection is a process, so treat connections as a scarce resource._

## 2. The mental model

Imagine a restaurant.

| Restaurant                                               | Postgres                                                    |
| -------------------------------------------------------- | ----------------------------------------------------------- |
| The building and kitchen (shared by everyone)            | Shared memory: `shared_buffers`, WAL buffers, lock tables   |
| The host at the door                                     | The **postmaster**, the main Postgres process               |
| A **dedicated waiter** hired for each guest who walks in | A **backend process** forked for each client connection     |
| The waiter's own notepad                                 | The backend's **private memory** (caches, `work_mem`, etc.) |
| Number of tables / chefs                                 | CPU cores and disk bandwidth                                |

Now imagine 1000 guests arrive and the restaurant hires 1000 waiters, but there are only 4 chefs. Most waiters stand around, they crowd the kitchen, and the manager spends the day just arranging who gets to move. Service gets **slower**, not faster.

That is exactly what happens with too many Postgres connections.

## 3. What happens on connect

```txt
  Client (your Node app)
        |
        | 1. TCP connect to port 5432
        v
  +-------------------+
  |    postmaster     |   the "listener" process, always running
  +-------------------+
        |
        | 2. authenticate (password / SCRAM / TLS if enabled)
        | 3. fork()  -> creates a NEW OS process
        v
  +-------------------+
  |  backend process  |   dedicated to THIS client only
  |  (pid 4821)       |
  +-------------------+
        |
        | 4. initialize: load catalog caches, set up session state
        | 5. ready -> client sends SQL, backend runs it and replies
        v
   ...runs queries for as long as the client stays connected...
        |
        | 6. client disconnects -> the backend process exits
        v
   (process gone, memory returned to the OS)
```

Key facts:

- **One client = one backend = one OS process** for the whole lifetime of the connection.
- That backend handles **one query at a time** for its client. A connection is not multiplexed.
- The postmaster never runs your queries. It only accepts connections and supervises.
- When the client disconnects, the process exits. A new connection means a **new fork and a new set-up** every time (this is why reconnecting per request is so expensive).

### Other processes you will also see

Besides client backends, Postgres runs a handful of **fixed helper processes**. They exist regardless of how many clients connect:

| Process                       | Job                                                                                    |
| ----------------------------- | -------------------------------------------------------------------------------------- |
| checkpointer                  | Periodically flushes dirty pages to disk (source of latency spikes under heavy writes) |
| background writer             | Gently writes dirty pages ahead of time                                                |
| WAL writer                    | Flushes the write-ahead log                                                            |
| autovacuum launcher / workers | Cleans up dead row versions                                                            |

You can tell them apart in `pg_stat_activity.backend_type`: client connections show up as `client backend`.

## 4. Shared vs private memory

This is the key to understanding both _why_ connections cost memory and _why_ they interfere with each other.

```txt
 +------------------------------------------------------------+
 |                    SHARED MEMORY (one copy)                |
 |   shared_buffers (page cache) | WAL buffers | lock tables  |
 |   process list (ProcArray)    | other shared structures    |
 +------------------------------------------------------------+
      ^            ^            ^            ^
      |            |            |            |
 +---------+  +---------+  +---------+  +---------+
 | backend |  | backend |  | backend |  | backend |   ...
 |  #1     |  |  #2     |  |  #3     |  |  #4     |
 | private |  | private |  | private |  | private |
 | memory  |  | memory  |  | memory  |  | memory  |
 +---------+  +---------+  +---------+  +---------+
```

| Kind                                   | Examples                                                                                    | Scales with connections?                                           |
| -------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **Shared** (one copy for everyone)     | `shared_buffers`, WAL buffers, lock manager, the table of running processes                 | No for size, but **contention goes up** as more processes touch it |
| **Private** (each backend has its own) | Catalog/relation caches, per-session state, `work_mem` for sorts and hashes, `temp_buffers` | **Yes**, multiplied by connection count                            |

Two things to remember:

1. **Each backend has some baseline private memory** even when idle. It is typically a few megabytes, and it grows as the session runs more varied queries (it caches table and index metadata it has touched).
2. **`work_mem` is per operation, not per connection.** One complex query can use several chunks of `work_mem` at once (one per sort or hash step). Then multiply by the number of simultaneously active connections. This is how a "small" setting can still cause out-of-memory under load.

## 5. What a connection costs

| Cost                                    | What it means                                                  | Rough scale                                                                |
| --------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Setup time**                          | TCP handshake + authentication + fork + backend initialization | Milliseconds to tens of milliseconds. Often far more than the query itself |
| **Memory**                              | Private memory per backend, as above                           | A few MB idle, more when active                                            |
| **Scheduler cost**                      | The OS must switch between processes on each CPU core          | Grows with the number of _runnable_ processes                              |
| **Contention**                          | Processes compete for locks on shared structures               | Grows with the number of _active_ processes                                |
| **File descriptors / kernel resources** | Each process holds sockets and files                           | Small each, adds up                                                        |

> **Idle connections are cheaper than active ones, but not free.** Recent Postgres versions are better at handling many idle connections than older ones, but each still holds memory and a process slot, and counts toward `max_connections`. Do not rely on this as a design.

### The setup cost is why "connect per request" is a disaster

If every HTTP request opened a new connection, your 2 ms insert would be preceded by a 10-30 ms connection set-up, and the server would fork and destroy a process for every single request. That is why you **reuse** connections (a pool). Compare with Stage 0, experiment E0.6 (keep-alive vs a new connection per request): same idea, same lesson, one layer deeper.

## 6. `max_connections`

- Default is **100**. In your compose file it is set explicitly: `-c max_connections=100`.
- A few slots (default 3, `superuser_reserved_connections`) are reserved so an admin can still log in when the server is "full".
- When the limit is reached, new connection attempts fail immediately with:

```txt
FATAL: sorry, too many clients already
```

- This is **not a performance setting you tune upward to go faster.** It is a safety limit. Raising it mostly lets you overload the machine more.

### Who is using the connections? Add them up

Connections from your whole system share the same budget:

```txt
total connections  =  (API nodes x pool size)
                    + (consumer services x their pool size)
                    + admin / migration / monitoring tools
```

Example: 3 API nodes with `pool.max = 10` each = **30** connections, before anything else connects. With 12 API nodes you would already be at 120 and would exceed the default 100. **Scaling out your stateless API silently scales up your connection count.** This is a classic production surprise, and a core reason PgBouncer exists.

## 7. Why more connections hurt

It feels like more connections should mean more parallel work. Here is why that stops being true quickly.

Your database host has a fixed number of CPU cores (in your compose file, `cpus: 2`). Only that many processes can _actually run_ at any instant. Everything else is waiting for a turn.

### Effect 1: Context switching

With far more runnable processes than cores, the OS keeps pausing one process and starting another. Each switch costs time and **throws away the CPU's warm caches**. The more processes, the more of the CPU's time goes into switching instead of working.

### Effect 2: Contention on shared structures

Backends coordinate through shared memory (lock tables, the process list, buffer mapping). More active processes means more waiting on those internal locks. This is _contention_, and it is a cost that rises as concurrency rises.

### Effect 3: Memory pressure

More backends means more private memory. If the total exceeds RAM, you get swapping or the OOM killer, which is far worse than slow.

### Effect 4: It hides the real queue, and makes it worse

When Postgres is the bottleneck, requests have to queue _somewhere_. You have two choices:

| Where requests wait                                                            | Result                                                                          |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| **In your app's pool** (a few connections, others wait in a client-side queue) | Postgres stays healthy and efficient. Waiting is cheap (just a promise in Node) |
| **Inside Postgres** (hundreds of active connections)                           | Postgres thrashes. Waiting is expensive, and everyone gets slower               |

### The shape of the curve

```txt
 throughput
    ^
    |            ___________
    |         .-'           '-.
    |       .'                 '-._
    |     .'                       '-._      <- adding more connections
    |   .'                             '-.._    makes throughput DROP
    |  /
    | /
    +--------------------------------------------> number of active connections
       few        sweet spot            too many
```

The sweet spot is **small**, usually in the range of low tens for a modest machine, not hundreds. You will find yours by experiment B2 (pool exhaustion).

## 8. How many connections do you need?

Use **Little's Law** (from Stage 0):

```txt
concurrency = arrival rate x time in system
```

Applied to the database:

```txt
busy connections needed  =  queries per second  x  seconds per query
```

### Worked example

| Queries/sec | Time per query | Busy connections needed                                        |
| ----------- | -------------- | -------------------------------------------------------------- |
| 5,000       | 2 ms (0.002 s) | 5000 x 0.002 = **10**                                          |
| 5,000       | 20 ms          | 5000 x 0.02 = **100**                                          |
| 5,000       | 100 ms         | 5000 x 0.1 = **500** (impossible: more than `max_connections`) |

So **a slow query needs far more connections for the same throughput**, and that is what makes slow databases so dangerous.

### The same law, reversed: the throughput ceiling of a pool

```txt
max throughput  =  pool size  /  seconds per query
```

| Pool size | Query time | Maximum throughput         |
| --------- | ---------- | -------------------------- |
| 10        | 2 ms       | 10 / 0.002 = 5,000 per sec |
| 10        | 50 ms      | 10 / 0.05 = 200 per sec    |
| 10        | 100 ms     | 10 / 0.1 = **100 per sec** |

> This is the answer to **Stage 1 self-test question 1**: _Postgres adds 100 ms to every query and the pool has 10 connections: max throughput is about 100 requests per second._ No amount of API CPU changes that. It is a hard ceiling set by `pool size / latency`.

### A starting heuristic for pool size

A widely quoted starting point (from the Postgres community and connection-pool authors) is:

```txt
pool size  ~=  (CPU cores x 2) + number of disks
```

For your 2-CPU Postgres container that suggests something like **4-10**, which lines up with `pg.Pool`'s default of `max = 10`. Treat this as a **hypothesis to test**, not a rule. Your B2 experiment (pool 5, 10, 25, 50, 90, above 100) is what actually finds the right number for your setup.

## 9. Connecting this to Node: `pg.Pool`

Your NestJS service uses `pg.Pool`. Here is how the two sides map to each other.

```txt
  Node process (NestJS)                          Postgres
 +--------------------------+                  +------------------+
 |  HTTP request handlers   |                  |   postmaster     |
 |   (many at once)         |                  +------------------+
 |        |                 |
 |        v                 |
 |  pg.Pool  (max = 10)     |    10 sockets    +------------------+
 |   [conn1] ---------------+----------------> | backend process 1|
 |   [conn2] ---------------+----------------> | backend process 2|
 |   ...                    |                  |   ...            |
 |   [conn10] --------------+----------------> | backend process10|
 |        ^                 |                  +------------------+
 |  waiting queue           |
 |  (requests beyond 10)    |
 +--------------------------+
```

**One pool connection = one Postgres backend process.** That is the whole link.

### What `pg.Pool` does for you

- Keeps up to `max` connections open and **reuses** them (no connect-per-request cost).
- When all are busy, extra `pool.query()` calls **wait in a client-side queue** inside your Node process.
- If a request waits longer than `connectionTimeoutMillis`, it fails. This is where your **503** comes from in Stage 1.

### Counters to watch (from your `/debug/stats`)

| Counter             | Meaning                                             |
| ------------------- | --------------------------------------------------- |
| `pool.totalCount`   | Connections currently open (up to `max`)            |
| `pool.idleCount`    | Open but not currently running a query              |
| `pool.waitingCount` | Requests waiting in the queue for a free connection |

**Reading them:**

- `waitingCount` is **0** and `idleCount` is high: the pool is bigger than you need.
- `waitingCount` is **growing**: demand exceeds the pool. Either queries are slow or pool is too small.
- `waitingCount` is growing **and** Postgres CPU is low: the pool is the limit.
- `waitingCount` is growing **and** Postgres CPU is pegged: the _database_ is the limit, and a bigger pool will not help (it will make it worse).

### Two different "waits" people confuse

| Wait               | Where                | Meaning                                  |
| ------------------ | -------------------- | ---------------------------------------- |
| **Pool wait time** | Client side, in Node | Time spent waiting for a free connection |
| **Query time**     | Inside Postgres      | Time the query actually took to run      |

Request latency = pool wait + query time + overhead. If you see high latency, **compare these two** before blaming the database. (This is listed as a pitfall in the Stage 1 doc.)

## 10. Why processes, not threads?

You may wonder why Postgres is designed this way instead of using threads like many modern servers.

**Historical and practical reasons:**

- **Isolation and safety.** If one backend crashes or hits a bug, only that process dies. (Postgres does restart all backends after a crash to protect shared memory, but the isolation is still a robustness benefit.)
- **Portability.** Postgres was designed when portable, consistent thread support across operating systems was not reliable. Processes plus shared memory worked everywhere.
- **Simplicity.** Process isolation made the code easier to reason about, because only explicitly shared memory is shared.
- **Mature and stable.** The model is deeply embedded in the codebase.

**The trade-off:** processes cost more memory and set-up time than threads, and cross-process coordination is more expensive. So Postgres is great at serving a _moderate number of busy connections_, but poor at serving a _huge number of mostly-idle ones_. That gap is why **connection poolers** exist.

> Interesting contrast: MySQL uses a thread-per-connection model by default. Threads are lighter than processes, but the same principle (too many active connections hurts) still applies to both.

## 11. The fix pattern: pooling

Because of everything above, production Postgres deployments use **connection pooling** at one or two levels.

```txt
   Level 1: pool inside each app (pg.Pool)
   Level 2: external pooler in front of Postgres (PgBouncer)

  API node A  (pool 10) --\
  API node B  (pool 10) ---+--> PgBouncer --> Postgres
  API node C  (pool 10) --/    (many client      (only ~20 real
  Consumers   (pool 5)  -/      connections)       backends)
```

**PgBouncer** accepts hundreds or thousands of client connections but maps them onto a **small number of real Postgres backends**. That keeps Postgres in its efficient range while your app scales out freely.

PgBouncer modes (more detail in Stage 6):

| Mode            | A server connection is held for | Note                                                                                                         |
| --------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Session         | The whole client session        | Safest, least sharing                                                                                        |
| **Transaction** | One transaction                 | Best reuse. Breaks session-level features (e.g. session variables, advisory locks, some prepared statements) |
| Statement       | One statement                   | Most restrictive                                                                                             |

**For Stage 1 you do not use PgBouncer.** You only need to _feel_ the problem it solves. You will add it in Stage 6.

## 12. Prove it yourself

Reading is not enough. Run these and write down what you see in your notebook.

### See the processes

Run inside the Postgres container (or on the host if Postgres runs there):

```bash
# list Postgres processes
docker exec -it <postgres-container> ps aux | grep postgres
```

You will see one main process, helper processes, and one `postgres: eventpulse eventpulse <client> ...` line **per connection**. The process title also shows state such as `idle`, `idle in transaction`, or `INSERT`.

### Count connections from inside Postgres

```sql
-- how many backends, and what are they doing?
SELECT backend_type, state, count(*)
FROM pg_stat_activity
GROUP BY 1, 2
ORDER BY 3 DESC;

-- only your app's database
SELECT state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity
WHERE datname = 'eventpulse'
GROUP BY 1, 2, 3
ORDER BY 4 DESC;

-- the ceiling
SHOW max_connections;
SELECT count(*) AS in_use FROM pg_stat_activity;
```

### Link a process to a connection

```sql
SELECT pid, state, query_start, left(query, 60) AS query
FROM pg_stat_activity
WHERE datname = 'eventpulse';
```

Each `pid` is a real OS process ID. You can find the same number in `ps` output. That is the model, made visible.

### Watch the system under load

While k6 runs:

```bash
vmstat 1          # watch 'r' (runnable processes) and 'cs' (context switches per second)
pidstat -w 1      # context switches per process
```

### The experiment that makes it click

1. Run a fixed load with `pool.max = 5`, then 10, 25, 50, 90.
2. At each size, record: throughput, p99, `pool.waitingCount`, Postgres CPU, and `cs` from `vmstat`.
3. Expect: throughput rises, flattens, then falls; context switches keep rising. That is the model, proven with your own numbers.

## 14. Common confusions

**"A connection is just a socket."**
No. In Postgres it is a socket **plus a dedicated OS process** on the server. That is the whole reason it is expensive.

**"If requests are slow, I should raise the pool size / `max_connections`."**
Only if Postgres CPU is idle _and_ requests are waiting on the pool. If Postgres is already busy, a bigger pool adds contention and makes it worse. Check the database first.

**"Idle connections are free."**
They are cheaper than active ones but still use memory, hold a process, and count against `max_connections`.

**"More API nodes means more capacity."**
Only until the shared database connection budget or database capacity is hit. Every node adds `pool.max` connections.

**"`work_mem` is per connection."**
It is per sort/hash operation, and one query can have several. Total memory use = `work_mem` x operations x active connections.

**"The postmaster runs my queries."**
No. It only listens and forks. The backend runs your queries.

**"One connection can run many queries at once."**
No. One backend runs **one query at a time**. Parallelism comes from having more connections (or from Postgres's own parallel query workers, which are extra processes).

**"Pool wait and database slowness are the same thing."**
No. Pool wait is queueing in your Node process; query time is work inside Postgres. Measure both.

## 15. Self-test questions

Try to answer aloud without looking. Answers are below.

1. What does Postgres create when a client connects?
2. Why can adding more connections make Postgres slower?
3. Your pool has 10 connections and each query takes 100 ms. What is the maximum throughput?
4. You scale from 3 to 15 API nodes, each with `pool.max = 10`, against `max_connections = 100`. What happens?
5. `pool.waitingCount` is high and Postgres CPU is 10%. What is the bottleneck? What if Postgres CPU is 100%?
6. Why is opening a new connection per HTTP request so costly in Postgres specifically?
7. What does PgBouncer change, in one sentence?

<details>
<summary>Answers</summary>

1. A new dedicated backend OS process, forked by the postmaster, living for the whole connection.
2. More runnable processes than CPU cores causes context switching, cache thrashing, and contention on shared structures. More memory is used too.
3. About 10 / 0.1 = **100 queries per second**.
4. 15 x 10 = 150 connections, which exceeds 100. New connections are refused with `too many clients already`.
5. At 10% CPU the **pool is the limit** (queries are waiting for a connection, not for CPU), so a modest pool increase may help. At 100% CPU the **database is the limit**, and a bigger pool will not help and may hurt.
6. Each new connection costs a TCP handshake, authentication, a process fork, and backend initialization, then a process teardown on close. This costs more than a typical fast query.
7. It lets many client connections share a small number of real Postgres backends, keeping Postgres in its efficient range.

</details>

## 16. Glossary and cheat sheet

| Term                   | Meaning                                                                         |
| ---------------------- | ------------------------------------------------------------------------------- |
| **postmaster**         | The main Postgres process: listens for connections and forks backends           |
| **backend**            | The OS process dedicated to one client connection                               |
| **fork()**             | The OS call that creates a new process                                          |
| **shared memory**      | Memory visible to all Postgres processes (`shared_buffers`, WAL buffers, locks) |
| **private memory**     | Memory owned by a single backend (caches, `work_mem`)                           |
| **`max_connections`**  | Hard limit on simultaneous client connections (default 100)                     |
| **context switch**     | The CPU stopping one process and starting another                               |
| **contention**         | Processes waiting on each other for a shared resource                           |
| **connection pool**    | A set of reusable open connections (`pg.Pool`)                                  |
| **PgBouncer**          | An external pooler that multiplexes many clients onto few backends              |
| **`pg_stat_activity`** | System view with one row per backend: state, query, waits                       |

### Cheat sheet

```txt
connection  = process                  -> heavy, scarce
setup       = TCP + auth + fork + init -> reuse, never connect per request
throughput  <= pool size / query time  -> slow DB = low ceiling
connections needed = QPS x query time  -> Little's Law
more connections != more speed         -> past the sweet spot it hurts
total conns = nodes x pool.max + extras -> scaling out multiplies connections
fix at scale = PgBouncer (Stage 6)
```

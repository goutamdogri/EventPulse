## 1. TL;DR

- A status code is a **promise and an instruction** to the client: _what happened_ and _what you should do next_.
- **4xx = "your request is the problem, don't repeat it unchanged."** **5xx = "my problem, trying again later may work."** Choosing the wrong class makes clients do the **wrong thing at scale**.
- **`201 Created`** = the thing was created, **done, now**. **`202 Accepted`** = I took responsibility for processing it, **not necessarily finished**. Pick by **what you promise**, not by how you implemented it.
- **`400`** = the request is malformed or fails schema validation. **`422`** = well-formed and valid on its own, but **cannot be processed** (a semantic or state problem, like reusing an idempotency key with a different body).
- **`429`** = **policy**: _this tenant_ is sending too much. **`503`** = **protection**: _the system_ is overloaded or a dependency is down. Both should say when to retry.
- **`Retry-After`** tells the client **how many seconds to wait** (or a date). Without it, clients guess, usually **too fast**, and cause a **retry storm** (B9).
- Overload must produce **fast, honest 503s**, never **hanging requests** (B10) and never **4xx** (clients won't retry a 4xx).

> **One-line version:** _The status code decides whether the client fixes the request, waits and retries, or gives up, so it has to match what really happened and what you want the client to do._

## 2. The mental model

Think of the **front desk of an office** receiving forms.

| Front desk                                                            | HTTP                                           |
| --------------------------------------------------------------------- | ---------------------------------------------- |
| "Got it, it's filed in the system." (done, visible)                   | **201 Created** (or 200)                       |
| "Got it, we'll process it. Can't say when, or if it'll be approved."  | **202 Accepted**                               |
| "This form is unreadable / missing the required boxes."               | **400 Bad Request**                            |
| "The form is neatly filled in, but what it asks is impossible."       | **422 Unprocessable Content**                  |
| "Show me your ID first."                                              | **401 Unauthorized** (means _unauthenticated_) |
| "You're not allowed to file this."                                    | **403 Forbidden**                              |
| "This package is too big for the window."                             | **413 Content Too Large**                      |
| "You've filed too many forms today. Come back at 3 pm."               | **429 Too Many Requests** + `Retry-After`      |
| "We're swamped / the filing system is down. Try again in 30 seconds." | **503 Service Unavailable** + `Retry-After`    |
| "Something broke and I don't know what."                              | **500 Internal Server Error**                  |

The clerk's answer tells the person **whether to rewrite the form (4xx), wait and come back (429/503), or relax (2xx)**.

## 3. Status code classes

| Class   | Meaning                                            | Who is "at fault" | Client should...                                       |
| ------- | -------------------------------------------------- | ----------------- | ------------------------------------------------------ |
| **1xx** | Informational (rarely seen by apps)                | n/a               | Usually ignore                                         |
| **2xx** | Success                                            | n/a               | Proceed                                                |
| **3xx** | Redirection                                        | n/a               | Follow `Location`                                      |
| **4xx** | **Client error**: the request, as sent, won't work | The **client**    | **Not retry unchanged**; fix it (exceptions: 408, 429) |
| **5xx** | **Server error**: the server failed or can't serve | The **server**    | **Possibly retry** later, with backoff                 |

### Why the class matters operationally

- **Clients, SDKs, proxies, and monitoring** use the class to decide behavior and to compute error rates.
- **Your SLO** ("availability = successful 202s / valid requests", Stage 7) counts **5xx as your failures** but **4xx as the caller's**. If you return 400 for something that was really your overload, you have **hidden an outage from your own metrics** and told clients not to retry.
- A load balancer or client library may **auto-retry 502/503/504** but will **never** auto-retry a 400.

> **Rule:** _when in doubt about who is at fault, ask "would the same request succeed later without any change?"_ If yes, it's a 5xx/429. If no, it's a 4xx.

## 4. 2xx success codes

| Code    | Name       | Meaning                                                                                                  | Typical use                                                                                              |
| ------- | ---------- | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| **200** | OK         | Succeeded; the response body contains the result                                                         | `GET`, or an action returning data                                                                       |
| **201** | Created    | A **new resource was created** (and exists now)                                                          | `POST` that creates something you can fetch immediately; includes a **`Location`** header pointing at it |
| **202** | Accepted   | The request was **accepted for processing, which is not complete**. It may or may not eventually succeed | Asynchronous work                                                                                        |
| **204** | No Content | Succeeded, no body                                                                                       | `DELETE`, updates with nothing to return                                                                 |

### 201 vs 202: the real difference

```txt
 201 Created   : "It's done. The resource exists. Here is where to find it."
 202 Accepted  : "I've taken responsibility for it. It is not necessarily done,
                  and I'm not promising it will succeed."
```

| Question                                        | 201                         | 202                                                                                                                    |
| ----------------------------------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| Is the work finished?                           | **Yes**                     | **Not necessarily**                                                                                                    |
| Can the client fetch the resource now?          | **Yes** (`Location` header) | **Maybe not yet**                                                                                                      |
| Does HTTP tell the client the eventual outcome? | n/a                         | **No.** There is no mechanism to send a later status; you provide a status resource or webhook if the client needs one |
| Typical architecture                            | Synchronous write           | Queue, background job, async pipeline                                                                                  |

### What does EventPulse do, and why is it interesting?

Your Stage 1 doc returns **202** even though the row is **committed in Postgres** before the response. Strictly, **201 would also be defensible in Stage 1**, since the event genuinely exists. The project picks 202 deliberately, for two reasons worth understanding:

1. **Forward compatibility.** In **Stage 2** the handler only appends to Kafka and returns before the event reaches Postgres. If Stage 1 returned 201 and Stage 2 changed it to 202, **you'd change the API contract for every client**. Choosing 202 from the start means **the status code never changes, only the documented guarantee behind it**.
2. **Semantic honesty at scale.** An ingestion API says "I **accepted your event for processing**", not "I created a resource you will `GET` by id". There is no `GET /v1/events/{id}` promise in the platform's core path.

| Stage       | What `202` means for EventPulse                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------ |
| **Stage 1** | The event is **committed to Postgres**                                                                             |
| **Stage 2** | The event is **durably appended to the replicated log** under the configured acks; it may **not be queryable yet** |

> **The lesson:** _choose the status code for the promise you want to keep forever, then document what the promise currently is._ The Stage 1 doc explicitly asks you to **write down** how the meaning of 202 changes in Stage 2.

### Related decisions you'll face

| Situation                                    | Options                                                             | Notes                                                                                                                                                                               |
| -------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Duplicate `event_id`** (S1-F4)             | Return **202 again** (idempotent: same result as the first time)    | Not 409. Retried requests should look like successes. Stage 3 refines this (409 for in-flight, 422 for key reuse with a different body)                                             |
| **Batch endpoint** (`POST /v1/events:batch`) | All-or-nothing (one status for the batch), or **per-event results** | A **202 with a per-item result list** is common; **207 Multi-Status** exists (it comes from WebDAV). Decide and document, since partial failure semantics matter when clients retry |
| **Response body for 202**                    | Return `{ "event_id": "..." }`                                      | Lets the client correlate. Your Stage 1 contract does exactly this                                                                                                                  |
| **Status endpoint**                          | Optional `Location` of a status resource                            | Not needed for fire-and-forget ingestion                                                                                                                                            |

## 5. 4xx client errors

### 400 vs 422

| Code    | Name                  | Use when                                                                                                                                                                |
| ------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **400** | Bad Request           | The request is **malformed or can't be parsed/validated against the contract**: invalid JSON, missing required field, wrong type, bad UUID, bad timestamp               |
| **422** | Unprocessable Content | The request is **syntactically valid and the content type is understood**, but the server **can't process the instructions** because of a **semantic or state problem** |

A useful way to think about it:

```txt
 400 :  "I couldn't even understand this as a valid request."
        {"event_id": "not-a-uuid"}            <- fails schema validation
        {"event_id": ...                      <- broken JSON

 422 :  "I understood it perfectly, and it's valid on its own,
         but I can't do what it asks."
        Idempotency-Key reused with a DIFFERENT body   <- (Stage 3)
```

### The honest truth about 400 vs 422 in practice

Teams genuinely disagree. Two common conventions:

| Convention                                                  | Used by                                      | Notes                        |
| ----------------------------------------------------------- | -------------------------------------------- | ---------------------------- |
| **400 for all validation failures**                         | NestJS's `ValidationPipe` default, many APIs | Simple and widely understood |
| **400 for malformed, 422 for semantic validation failures** | Rails-style APIs, others                     | More granular                |

**What matters is picking one rule, documenting it, and applying it consistently.** EventPulse's contract:

| Condition                                                        | Status  | Reasoning                                                                                                                                      |
| ---------------------------------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Schema or field invalid (bad UUID, missing field, bad timestamp) | **400** | The event, as sent, **is not a valid event** (Stage 1 error contract; this is also NestJS's default)                                           |
| Idempotency key reused with a **different payload** (Stage 3)    | **422** | The request is a **valid event**, but the **key/payload combination** can't be processed. The IETF idempotency-key draft uses the same mapping |

### The rest of the client-error family you'll meet

| Code    | Name                   | Meaning in EventPulse                                                                                                                                  |
| ------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **401** | Unauthorized           | **Missing or invalid credentials** (despite the name, it means _unauthenticated_). Must include a **`WWW-Authenticate`** header (for example `Bearer`) |
| **403** | Forbidden              | **Authenticated but not allowed** (for example key valid but suspended)                                                                                |
| **404** | Not Found              | Resource or route doesn't exist. Often also used to **hide existence** across tenants in later query APIs                                              |
| **405** | Method Not Allowed     | Wrong HTTP verb; must include an **`Allow`** header                                                                                                    |
| **408** | Request Timeout        | The server gave up waiting for the client to finish sending the request                                                                                |
| **409** | Conflict               | The request conflicts with **current state** (Stage 3: same idempotency key still in progress)                                                         |
| **413** | Content Too Large      | Body over the size limit (older name: _Payload Too Large_)                                                                                             |
| **415** | Unsupported Media Type | Wrong `Content-Type` (not JSON)                                                                                                                        |
| **422** | Unprocessable Content  | See above                                                                                                                                              |
| **429** | Too Many Requests      | Rate limited (section 6)                                                                                                                               |

### Order of checks matters (cheap and early first)

The blueprint's lifecycle is **authenticate, rate limit, validate**. The principle: reject as **cheaply** and **early** as possible, and don't spend validation CPU on callers who are unauthenticated or over their limit.

```txt
 1. Size / syntax of body       -> 413 / 400   (done by the HTTP/body parser before your code)
 2. Authenticate                -> 401
 3. Authorize                   -> 403
 4. Rate limit                  -> 429         (Stage 5)
 5. Validate fields             -> 400 / 422
 6. Business logic / DB         -> 202 or 503
```

**NestJS detail:** the JSON body is parsed in **middleware**, which runs **before guards**. So an **unauthenticated** caller sending a broken or oversized body can get **400/413 before ever reaching the 401 guard**. That costs you parsing work for unauthenticated traffic. It's a known trade-off; if it matters, limit body size at the proxy/edge (Stage 7) as well.

## 6. 429 rate limited

**`429 Too Many Requests`** means **this caller has sent too many requests in a given time**. It's about **policy toward one tenant**, not about the health of your system.

|                          | **429**                                      | **503**                                           |
| ------------------------ | -------------------------------------------- | ------------------------------------------------- |
| What it says             | "**You** are over **your** limit"            | "**The service** can't handle requests right now" |
| Whose fault              | The tenant's traffic                         | Capacity / dependency failure                     |
| Triggered by             | Per-tenant limiter (Stage 5)                 | Pool exhaustion, DB down, load shedding           |
| Affects                  | Only the offending tenant                    | **Everyone**                                      |
| Client should            | Slow down; honor `Retry-After`               | Back off; honor `Retry-After`                     |
| Counts against your SLO? | Usually **not** (policy working as designed) | **Yes**                                           |

### Headers

- **`Retry-After`**: how long to wait (section 8).
- Rate-limit information headers are common (`RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`, and older `X-RateLimit-*` variants). The standardized form is still an **IETF draft**, so treat names as conventions and document yours.

### Stage 1 status

Stage 1 has **no rate limiter** (that's Stage 5, a Redis token bucket). Learn 429 now because **B9 (retry storm)** and the error contract set up the client-behavior lessons: clients that **ignore** `Retry-After` and retry immediately make overload worse, while clients that honor it with jitter let the system recover.

> **Don't mix them up:** returning 429 for a **system-wide** overload tells a well-behaved client "you're misbehaving", blames the wrong party, and hides a capacity problem from your dashboards. System overload is **503**.

## 7. 5xx and 503

| Code    | Name                  | Meaning                                                                               | Who usually generates it                        |
| ------- | --------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **500** | Internal Server Error | **Unexpected** failure, a bug or unhandled condition                                  | Your app                                        |
| **502** | Bad Gateway           | A proxy/gateway got an **invalid response** from the upstream                         | **Nginx / Envoy / load balancer**               |
| **503** | Service Unavailable   | **Temporarily unable to handle the request** (overload, maintenance, dependency down) | Your app **or** the proxy (no healthy upstream) |
| **504** | Gateway Timeout       | A proxy **timed out waiting** for the upstream                                        | **Nginx / Envoy / load balancer**               |

### 503 is the "honest overload" code

**`503 Service Unavailable`** says: _"I'm alive, but I can't serve this right now. It's temporary. Try again later."_ In Stage 1 you return it for:

| Cause                                                   | Where it originates         |
| ------------------------------------------------------- | --------------------------- |
| **Pool wait timeout** (`connectionTimeoutMillis` fired) | `node-pg-pool.md` section 8 |
| **Database unreachable / restarting**                   | B8                          |
| **Statement timeout**                                   | Postgres `57014`            |
| Too many Postgres connections                           | `53300`                     |
| (Later) Kafka unavailable, bounded queue full           | Stage 2                     |
| (Later) deliberate load shedding                        | Stage 2+                    |

### 500 vs 503: which one?

| Situation                                                                     | Use                     |
| ----------------------------------------------------------------------------- | ----------------------- |
| A **bug**: null pointer, unhandled exception, code path you didn't anticipate | **500**                 |
| A **known transient dependency/capacity problem** (pool timeout, DB down)     | **503** + `Retry-After` |

The difference matters because **clients treat them differently** and because **503 is a signal for retry and autoscaling**, while 500 is a signal for "page a developer".

### Once Nginx/Envoy is in front (Stage 7)

You will see **502/503/504 produced by the proxy**, not by your code, for example when a pod is restarting or an upstream is slow. Clients must treat **502, 503, and 504 all as retryable**, and your **dashboards should break errors down by who generated them** (proxy vs app).

### Why fast 503 beats a hung request

```txt
 BAD  : no timeouts -> request waits in the pool queue forever -> client times out (status 0 in k6)
        you see NO error, just rising latency and memory (B10)
 GOOD : bounded wait -> after 2 s the app answers 503 + Retry-After
        client knows to back off; your metrics show the error rate
```

A **fast, explicit 503** is a feature. A silent hang is a bug.

## 8. Retry-After

**`Retry-After`** tells the client **how long to wait before retrying**. It may accompany **429**, **503**, and certain 3xx responses.

### Two formats

| Format                             | Example                                      | Meaning                      |
| ---------------------------------- | -------------------------------------------- | ---------------------------- |
| **Delay in seconds** (most common) | `Retry-After: 5`                             | Wait at least 5 seconds      |
| **HTTP date**                      | `Retry-After: Wed, 21 Oct 2026 07:28:00 GMT` | Don't retry before this time |

### Choosing the value

| Approach                                  | Notes                                                                                                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fixed small value** (for example 1-5 s) | Simplest; fine for the Stage 1 baseline                                                                                                                                   |
| **Estimated from queue/load**             | Better: longer when the pool queue is longer                                                                                                                              |
| **Add jitter on the server side**         | If **every** client gets `Retry-After: 1`, they all come back at the **same moment** and cause a **thundering herd**. Send slightly randomized values (for example 1-3 s) |

```ts
// pseudo: randomized Retry-After in seconds
const retryAfter = 1 + Math.floor(Math.random() * 3); // 1..3
res.set("Retry-After", String(retryAfter));
```

### What the client should do

```txt
 on 429 / 503:
   wait = Retry-After header value (if present)
          else exponential backoff:  base * 2^attempt
   add random jitter                 (so clients don't synchronize)
   cap the attempts and the total time (a retry BUDGET)
   then give up and surface the error
```

This is the standard guidance from the AWS Builders' Library on **timeouts, retries, and backoff with jitter**, and it's exactly what **B9** demonstrates: **retries without backoff turn overload into a self-sustaining collapse (a metastable failure)**.

### What `Retry-After` does NOT do

- It's **advice**, not enforcement. Misbehaving clients ignore it. That's why the server also needs **rate limiting (Stage 5)** and **load shedding**.
- It **does not** make a non-idempotent retry safe. That's the next section.

## 9. Retry semantics

Whether a client should retry depends on **the status** and on **whether the operation is safe to repeat**.

| Status                                             | Retry?                         | Notes                                                                       |
| -------------------------------------------------- | ------------------------------ | --------------------------------------------------------------------------- |
| **2xx**                                            | No                             | Done                                                                        |
| **400, 401, 403, 404, 413, 415, 422**              | **No, not unchanged**          | Fix the request or credentials. Retrying only wastes capacity               |
| **408**                                            | Yes                            | The server gave up waiting for the request                                  |
| **409**                                            | Depends                        | Re-read state first (Stage 3: in-flight idempotency conflict, wait briefly) |
| **429**                                            | **Yes, after `Retry-After`**   | Slow down                                                                   |
| **500**                                            | Cautiously                     | Might be a bug that will repeat; cap attempts                               |
| **502, 503, 504**                                  | **Yes, with backoff + jitter** | Transient                                                                   |
| **No response at all** (timeout, connection reset) | **Unknown outcome**            | See below                                                                   |

### The hard case: "no response"

If the client times out, it **cannot know** whether the server processed the request or not. The write may have **succeeded** but the response was lost.

```txt
 client ---POST event--->  server  (commits to DB)  ---202--X (lost / client already gave up)
 client: "did it work?"  unknown.
   - don't retry  -> risk LOSS
   - retry        -> risk DUPLICATE
```

This is the **two generals problem** from the Stage 3 notes. The way out is **idempotency**: make repeating the request **safe**.

| Mechanism                                                                                              | Stage                         |
| ------------------------------------------------------------------------------------------------------ | ----------------------------- |
| **`POST` is not idempotent by definition** in HTTP (unlike `PUT`/`DELETE`/`GET`)                       | Concept                       |
| `event_id` + `ON CONFLICT DO NOTHING` makes a repeat harmless **at storage**                           | **Stage 1** (naive, DB-level) |
| `Idempotency-Key` header + dedup layer with defined conflict codes (409 in-flight, 422 different body) | **Stage 3**                   |

So in EventPulse, **retrying a `POST /v1/events` after a 503 or timeout is safe because every event carries a unique `event_id`**. That property is what allows you to tell clients "retry on 5xx and 429".

> Stage 1 has **no server-side retries** (requirement: failures surface honestly). Client-side retries appear only in **B9**.

## 10. The EventPulse Stage 1 error contract

From the Stage 1 doc, annotated with intent and the retry guidance for clients:

| Condition                           | Status  | Body                              | Headers                    | Client action                    |
| ----------------------------------- | ------- | --------------------------------- | -------------------------- | -------------------------------- |
| Success (**committed** to Postgres) | **202** | `{ "event_id": "..." }`           |                            | Done                             |
| Duplicate `event_id`                | **202** | `{ "event_id": "..." }`           |                            | Done (idempotent)                |
| Missing or bad API key              | **401** | error body                        | `WWW-Authenticate: Bearer` | Fix credentials, don't retry     |
| Schema or field invalid             | **400** | error body with field details     |                            | Fix the event, don't retry       |
| Body over limit                     | **413** | error body                        |                            | Shrink or split, don't retry     |
| Pool wait timeout or DB error       | **503** | error body                        | **`Retry-After`**          | Retry with backoff + jitter      |
| Unexpected bug                      | **500** | generic error body (no internals) |                            | Cautious retry; report           |
| `GET /healthz` ok                   | 200     |                                   |                            |                                  |
| `GET /readyz` DB unreachable        | 503     |                                   |                            | Orchestrator treats as not ready |

### Document what 202 means (Stage 1 deliverable)

Put wording like this in your API notes, and **update it in Stage 2**:

```txt
202 Accepted (Stage 1):  The event passed validation and was COMMITTED to Postgres.
                         Safe to treat as stored. Retrying with the same event_id is harmless.
202 Accepted (Stage 2):  The event was DURABLY APPENDED to the replicated log under the
                         configured acks policy. It may not be queryable yet.
```

Also keep the **error body shape** the same across all error responses (section 12).

## 11. Where each status comes from

Each status is **produced by a different layer** of your NestJS (Express) stack. Knowing the layer tells you where to look when a status looks wrong.

```txt
 HTTP request
   |
   |-- Node HTTP server / body parser (MIDDLEWARE) ---- 400 invalid JSON, 413 body too large
   |
   |-- Guard (ApiKeyGuard) ---------------------------- 401 / 403
   |
   |-- Interceptors  (later: rate limit) -------------- 429 (Stage 5)
   |
   |-- Pipe (ValidationPipe, DTO rules) --------------- 400 (or 422 if configured)
   |
   |-- Controller -> Service -> pg.Pool -> Postgres --- success 202, or an exception
   |
   |-- Exception filter ------------------------------- turns pool/DB errors into 503 + Retry-After,
                                                        unknown errors into 500
```

### Controller: returning 202

```ts
@Post()
@HttpCode(202)                       // Nest defaults POST to 201; override it explicitly
async ingest(@Body() dto: CreateEventDto, @Req() req: any) {
  await this.svc.insert(req.tenantId, dto);
  return { event_id: dto.event_id };
}
```

> **Nest default:** `POST` handlers return **201** unless you set `@HttpCode(...)`. Forgetting this is a classic accidental contract change.

### Validation pipe: 400 (or 422)

```ts
app.useGlobalPipes(
  new ValidationPipe({
    whitelist: true, // strip unknown fields
    forbidNonWhitelisted: false, // decide: reject or ignore unknown fields (document it)
    transform: false, // keep the raw shape for the DB path
    // errorHttpStatusCode: 422,     // only if you decide validation failures are 422
  }),
);
```

Default failure status is **400**, matching the Stage 1 contract.

### Body limit: 413

The body size limit comes from the body parser (Express's JSON parser defaults to about **100 KB**). Your Stage 1 requirement says the **payload limit is configurable by env var**, so set it explicitly (for example via the Nest/Express body-parser configuration for your version).

> **B7 trap:** your payload-size experiment includes **100 KB** bodies. With the default ~100 KB limit and JSON overhead, those requests may be rejected with **413** instead of measured. Set the limit above your largest test size, and record it.

### Exception filter: 503 with `Retry-After`

```ts
@Catch()
export class DbErrorFilter implements ExceptionFilter {
  catch(err: any, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();

    // keep Nest's own HttpExceptions (400, 401, 413 ...) as they are
    if (err instanceof HttpException) {
      return res.status(err.getStatus()).json(err.getResponse());
    }

    const transient =
      /timeout exceeded when trying to connect/i.test(err?.message ?? "") ||
      ["ECONNREFUSED", "ETIMEDOUT"].includes(err?.code) ||
      ["57014", "53300", "57P01"].includes(err?.code) ||
      String(err?.code ?? "").startsWith("08");

    if (transient) {
      res.set("Retry-After", String(1 + Math.floor(Math.random() * 3)));
      return res
        .status(503)
        .json({
          error: {
            code: "service_unavailable",
            message: "Temporarily unavailable",
          },
        });
    }
    // unknown: log full details server-side, return NOTHING internal to the client
    return res
      .status(500)
      .json({ error: { code: "internal_error", message: "Unexpected error" } });
  }
}
```

(More on mapping Postgres/pool error codes is in `node-pg-pool.md`, section 12.)

## 12. Error response bodies and headers

### A consistent error body

Clients can only handle errors well if **every error looks the same**. A simple shape:

```json
{
  "error": {
    "code": "invalid_event",
    "message": "Request body failed validation",
    "details": [
      { "field": "event_id", "problem": "must be a UUID" },
      { "field": "occurred_at", "problem": "must be an ISO 8601 timestamp" }
    ],
    "request_id": "req_8f2c..."
  }
}
```

| Part                                 | Why                                                         |
| ------------------------------------ | ----------------------------------------------------------- |
| **`code`** (machine-readable string) | Clients branch on it, not on message text                   |
| **`message`** (human-readable)       | For logs and developers                                     |
| **`details`**                        | Which fields failed (for 400/422)                           |
| **`request_id`**                     | Lets a customer quote it so you can find the trace/log line |

There's also a published standard for this idea, **RFC 9457 "Problem Details for HTTP APIs"** (`application/problem+json`). You may adopt it or use your own consistent shape.

### Security rule

**Never put stack traces, SQL, hostnames, or internal error text into responses.** Log the detail server-side with the `request_id`; return a generic message.

### Headers that go with specific statuses

| Status       | Header                               | Notes                                    |
| ------------ | ------------------------------------ | ---------------------------------------- |
| **201**      | `Location`                           | URL of the created resource              |
| **401**      | `WWW-Authenticate`                   | Required by the spec, e.g. `Bearer`      |
| **405**      | `Allow`                              | Lists permitted methods                  |
| **429, 503** | **`Retry-After`**                    | Seconds (or a date)                      |
| All          | `Content-Type: application/json`     | Make errors JSON too                     |
| All          | `X-Request-Id` (your choice of name) | Correlation across logs/traces (Stage 7) |

## 13. Status codes and load testing

Status codes are **data** in your experiments. k6 and your audit depend on handling them correctly.

### How k6 treats statuses

- By default, k6 counts a response as **failed** (`http_req_failed`) unless the status is **200-399**. Your **202** counts as success.
- **A 503 or 429 counts as "failed"**, which is correct for overload experiments but misleading if those responses are **expected** in a given test.
- If the request gets **no HTTP response** at all (timeout, connection error), k6 records **status `0`**. That's your signal for **hung or dropped requests**, versus a clean 503.

```js
import http from "k6/http";
import { check } from "k6";

// treat 202 AND 503 as "expected" in an overload experiment (so http_req_failed measures only surprises)
http.setResponseCallback(http.expectedStatuses(202, 503));

export default function () {
  const res = http.post(url, body, { headers });
  check(res, { accepted: (r) => r.status === 202 });
}
```

### Count statuses separately

In every Stage 1 run record the **status distribution**: how many 202, 400, 401, 413, 503, 500, and **status 0**. The shape of that distribution as load rises **tells the collapse story**:

| As load increases...                                                        | Interpretation                                               |
| --------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Almost all **202**, p99 flat                                                | Healthy                                                      |
| **202** then **503s appear**, latency capped near `connectionTimeoutMillis` | Pool saturated, **fast failure** working                     |
| **202** then **status 0 / client timeouts**, latency unbounded              | **No timeouts configured**: hangs (B10)                      |
| **500s**                                                                    | Unhandled errors, a bug rather than overload                 |
| **400s** appear unexpectedly                                                | Your load generator is sending bad events (check the script) |

### The row-count audit and statuses

The Stage 1 audit compares **requests sent**, **202s received**, and **rows in the table**. Only **202** means "stored". Everything else (503, status 0, 4xx) must **not** produce a row, and every 202 must. Note that **status 0** is the ambiguous case: **the row may exist even though the client saw no response** (the lost-response problem from section 9). Such rows explain a small "rows > 202s" gap and are a finding, not noise.

## 14. Prove it yourself

Replace host, port, and key as needed. Use `-i` to see headers, and `-s -o /dev/null -w "%{http_code}\n"` to print only the status.

### Happy path: 202

```bash
curl -i -X POST http://localhost:3000/v1/events \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"event_id":"6f1c2d3e-0000-4000-8000-000000000001","type":"order.created",
       "occurred_at":"2026-11-09T10:00:00Z","schema_version":1,"payload":{"user":"u1"}}'
```

Expect `202` and `{"event_id":"..."}`. **Send the exact same request again:** expect **202 again** (idempotent duplicate), and exactly one row in Postgres.

### 401: missing or wrong key

```bash
curl -i -X POST http://localhost:3000/v1/events -H "Content-Type: application/json" -d '{}'
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer wrong" \
     -H "Content-Type: application/json" -d '{}'
```

Check for a `WWW-Authenticate` header, and **zero rows** written.

### 400: invalid event (two kinds)

```bash
# schema invalid: bad UUID
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"event_id":"nope","type":"x","occurred_at":"2026-11-09T10:00:00Z","schema_version":1,"payload":{}}'

# malformed JSON
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" -d '{"event_id":'
```

Both should be **400** with a consistent error body, and **zero rows** written (S1-F2). Notice **which layer** produced each (the malformed JSON comes from the body parser; the bad UUID from the validation pipe).

### 413: oversized body

```bash
head -c 300000 /dev/zero | tr '\0' 'x' > /tmp/big.txt
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d "{\"event_id\":\"6f1c2d3e-0000-4000-8000-000000000002\",\"type\":\"x\",\"occurred_at\":\"2026-11-09T10:00:00Z\",\"schema_version\":1,\"payload\":{\"d\":\"$(cat /tmp/big.txt)\"}}"
```

Expect **413**. Then raise the limit by env and see it become 202.

### Content-Type surprises (decide your behavior)

```bash
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer $KEY" \
  -H "Content-Type: text/plain" -d 'hello'
```

By default this often ends up as a **400** from validation (empty body) rather than a **415**. Decide whether you want an explicit 415, and write the decision down.

### 503 with Retry-After: stop the database

```bash
docker stop <postgres-container>
curl -i -X POST http://localhost:3000/v1/events -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"event_id":"6f1c2d3e-0000-4000-8000-000000000003","type":"x","occurred_at":"2026-11-09T10:00:00Z","schema_version":1,"payload":{}}'
docker start <postgres-container>
```

Expect **503** and a **`Retry-After`** header, **no process crash**, and recovery after restart (from the Stage 1 integration test table). Also check what `/readyz` returns while the DB is down.

### See the status distribution of a burst

```bash
for i in $(seq 1 200); do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:3000/v1/events \
    -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
    -d "{\"event_id\":\"$(uuidgen)\",\"type\":\"x\",\"occurred_at\":\"2026-11-09T10:00:00Z\",\"schema_version\":1,\"payload\":{}}" &
done | sort | uniq -c
wait
```

Run it with a **tiny pool** (`PG_POOL_MAX=1`, short `PG_POOL_CONNECT_TIMEOUT_MS`) and watch **503s** appear in the count.

Test **every row of the error table** with supertest (or equivalent), asserting **status, headers, and body shape**, plus the **row count**:

## 16. Pitfalls checklist

- [ ] **`200` for everything with the error in the body**: breaks clients, monitoring, and retries.
- [ ] **4xx for overload** (400, 429, or 404 for "busy"): clients won't retry, your SLO hides the outage.
- [ ] **`429` for system-wide overload**: blames the tenant for your capacity problem.
- [ ] **`500` for known transient conditions**: should be 503 with `Retry-After`.
- [ ] **`503` without `Retry-After`**: clients guess and retry too fast (retry storm).
- [ ] **Identical `Retry-After` for every client**: synchronized retries (thundering herd). Add jitter.
- [ ] **Hanging requests instead of fast failure**: no pool/statement timeouts (B10).
- [ ] **Forgetting `@HttpCode(202)`**: Nest returns 201 for POST by default.
- [ ] **Treating `202` as "queryable"**: it's a promise of acceptance, not visibility. Document it.
- [ ] **Inconsistent error body shapes**: clients can't parse errors reliably.
- [ ] **Leaking stack traces, SQL, or hostnames** in error responses.
- [ ] **Retrying 4xx** (other than 408/429): wastes capacity and can't succeed.
- [ ] **Retrying non-idempotent operations blindly**: duplicates. Rely on `event_id` / idempotency keys.
- [ ] **Default body limit surprises (413)** when testing larger payloads.
- [ ] **Not recording the status distribution** during load tests.
- [ ] **Different layers generating similar codes** (app vs proxy) with no way to tell them apart.

## 17. Common confusions

**"202 means it failed or is uncertain."**
No. It means the request was **accepted for processing**. How certain it is depends on what you define it to promise (Stage 1: committed; Stage 2: durably in the log).

**"201 and 202 are interchangeable."**
They make different promises: 201 = created and available now; 202 = accepted, processing may not be complete.

**"401 means the user isn't allowed."**
It means **unauthenticated** (no or bad credentials). **403** is authenticated-but-not-allowed.

**"400 and 422 are the same."**
Both are client errors. 400 is for requests that are malformed or fail contract validation; 422 for valid-looking requests that can't be processed for semantic or state reasons. What matters is a **consistent, documented rule**.

**"429 and 503 both mean slow down, so it doesn't matter which."**
429 targets **one caller's** behavior (policy); 503 reflects **system** capacity. They differ in blame, metrics, and what you do about them.

**"`Retry-After` forces the client to wait."**
It's advice. Well-behaved clients follow it; others don't. The server needs its own protection.

**"A timeout means the request failed."**
It means the **outcome is unknown**. The write may have succeeded. That's why idempotency exists.

**"500s are fine during overload."**
Overload should surface as **503**. A 500 means "unexpected bug" and triggers the wrong response from both clients and humans.

**"If I return 503 the error rate looks bad."**
It should. A fast, honest 503 is far better than a hidden hang, and your SLO is supposed to see it.

**"The proxy and the app return the same 503."**
Once Nginx/Envoy is in front, many 502/503/504 are generated by the **proxy**. Break error rates down by source.

## 18. Self-test questions

Answer aloud first. Answers are below.

1. What's the practical difference between `201 Created` and `202 Accepted`?
2. Why does EventPulse return `202` in Stage 1 even though the row is already committed?
3. When would you return `400`, and when `422`?
4. What's the difference between `429` and `503`? Give a scenario for each.
5. What does `Retry-After` do, and why should its value have jitter?
6. A client times out waiting for a response to `POST /v1/events`. What does it know, and how does EventPulse make a retry safe?
7. Why should overload return `503` rather than `400` or `429`?
8. A request with a 10 MB body and no `Authorization` header reaches your NestJS app. Which status might you get, and which layer produces it?
9. Which statuses should clients retry, and which should they never retry unchanged?
10. During B10 you see k6 reporting `status 0` instead of 503. What does it mean?

<details>
<summary>Answers</summary>

1. 201 = the resource was created and exists now (usually with a `Location` header). 202 = the request was accepted for processing, which may not be complete, and HTTP gives no way to report the eventual result.
2. To keep the contract stable: in Stage 2 the handler returns after appending to Kafka (before the row exists), so 202 is the honest long-term code. Only the documented guarantee behind 202 changes between stages, not the status clients see.
3. 400 when the request is malformed or fails schema/field validation (bad JSON, bad UUID, missing field). 422 when the request is valid on its own but can't be processed for a semantic or state reason, such as an idempotency key reused with a different payload (Stage 3). Either way, apply one documented rule consistently.
4. 429 is policy toward one caller: a tenant exceeding its rate limit (Stage 5). 503 is system-wide: the DB is down or the pool is saturated and timing out. 429 affects only the offender; 503 affects everyone and counts against your SLO.
5. It tells the client how many seconds to wait (or a date) before retrying, so retries are paced instead of immediate. Without jitter all clients retry at the same instant, causing a thundering herd and re-overloading the server.
6. It knows nothing: the write might have committed with the response lost. Retrying is safe because each event has a unique `event_id` (Stage 1: `ON CONFLICT DO NOTHING`; Stage 3: idempotency keys and dedup), so a duplicate is harmless.
7. 4xx tells clients their request is wrong and not to retry, so overload would never drain and your 5xx-based SLO would hide the outage. 429 would blame an innocent tenant. 503 + `Retry-After` correctly says "temporary, my side, come back later".
8. Probably a 413 (or 400 if the body is malformed), produced by the body-parser middleware, which runs before guards, so it can answer before the 401 guard ever runs. This is why edge-level size limits (proxy) are worth adding.
9. Retry (with backoff and jitter): 408, 429 (after `Retry-After`), 502, 503, 504, and cautiously 500. Never retry unchanged: 400, 401, 403, 404, 413, 415, 422. Conflicts (409) depend on re-reading state.
10. The client got no HTTP response at all (timeout or connection error). It indicates hung or dropped requests, typically because no timeouts are set so requests wait indefinitely instead of failing fast with 503.

</details>

## 19. Glossary and cheat sheet

| Term                                 | Meaning                                                      |
| ------------------------------------ | ------------------------------------------------------------ |
| **status code**                      | Three-digit result code in the HTTP response                 |
| **2xx / 4xx / 5xx**                  | Success / client error / server error classes                |
| **202 Accepted**                     | Accepted for processing; not necessarily complete            |
| **201 Created**                      | New resource created and available; usually with `Location`  |
| **400 Bad Request**                  | Malformed or contract-invalid request                        |
| **422 Unprocessable Content**        | Well-formed but cannot be processed (semantic/state problem) |
| **401 / 403**                        | Unauthenticated / authenticated but not permitted            |
| **413 Content Too Large**            | Body exceeds the size limit                                  |
| **429 Too Many Requests**            | Caller exceeded its rate limit (policy)                      |
| **503 Service Unavailable**          | Server temporarily can't serve (capacity/dependency)         |
| **502 / 504**                        | Proxy got a bad response / timed out waiting on upstream     |
| **`Retry-After`**                    | Header: seconds (or date) to wait before retrying            |
| **idempotent**                       | Repeating the request has the same effect as doing it once   |
| **backoff + jitter**                 | Increasing, randomized delays between retries                |
| **retry storm / metastable failure** | Retries sustaining an overload after its trigger is gone     |
| **load shedding**                    | Rejecting work early to protect the system                   |
| **status 0 (k6)**                    | No HTTP response received (timeout or connection error)      |

### Cheat sheet

```txt
2xx  : 200 result | 201 created+Location (done now) | 202 accepted (processing, maybe not done) | 204 no body
EventPulse: success = 202 (stage 1: committed in Postgres; stage 2: durably in the log)
            duplicate event_id = 202 again (idempotent)

4xx  : your request is the problem -> DON'T retry unchanged
  400 malformed / schema-invalid      422 valid-looking but unprocessable (e.g. key reuse, Stage 3)
  401 no/bad credentials (+WWW-Authenticate)   403 not allowed
  413 body too large                  415 wrong media type     409 conflict with state
  429 YOU are over YOUR limit (policy)   -> Retry-After

5xx  : my problem -> retry with backoff + jitter
  500 unexpected bug     503 temporarily unavailable (+Retry-After)   502/504 from the proxy

pool timeout / DB down / statement timeout / too many conns  -> 503 + Retry-After (NOT 500, NOT 4xx)
overload must be a FAST 503, never a hang (status 0 in k6 = no response = missing timeouts)
Retry-After: seconds or date; add server-side jitter; clients: honor it + backoff + cap attempts
timeout with no response = OUTCOME UNKNOWN -> retry only because event_id makes it idempotent
check order: size/parse -> auth(401) -> authz(403) -> rate limit(429) -> validate(400/422) -> DB(202/503)
Nest: @HttpCode(202) (default POST=201); body parser (400/413) runs BEFORE guards (401)
record the STATUS DISTRIBUTION in every load test
```

## 1. TL;DR

- Every HTTP request in NestJS passes through a **fixed pipeline of layers**, in a **fixed order**:

```txt
 Middleware -> Guards -> Interceptors (before) -> Pipes -> Controller (-> Service)
            -> Interceptors (after) -> Exception filters (only if something threw) -> Response
```

- Each layer has **one job**: middleware (raw HTTP plumbing), guards (**may this proceed?**), interceptors (**wrap** the handler), pipes (**validate / transform input**), controller (**map HTTP to your logic**), filters (**turn errors into responses**).
- Order matters for **behavior** (auth runs before validation) **and for status codes** (a guard failure is 401/403, a pipe failure is 400).
- **Every layer costs CPU on every request.** Each one is small, but **they add up**, and **Node runs all of them on one thread**, so per-request CPU directly caps **requests per second per core**.
- The biggest single cost in a typical Nest ingest path is usually **decorator-based validation** (`class-validator` + `class-transformer`), because it **creates objects, reads metadata, and runs a validator per field per request**.
- **Measure, don't guess** (Stage 0 rule): flame graphs, CPU-microseconds-per-request, and a microbenchmark of the pipe tell you the real share.

> **One-line version:** _NestJS is a conveyor belt of layers with a defined order; it gives structure, and charges a small CPU toll at every station on every request._

## 2. The mental model

Think of an **airport**, from the curb to the plane.

| Airport                                                                                 | NestJS layer                                          |
| --------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| The road, the terminal doors, the baggage belt (everyone passes through, no matter who) | **Middleware**: body parsing, CORS, request id        |
| **Security check:** "Do you have a valid ticket? May you go through?"                   | **Guard**: authentication and authorization           |
| A **concierge who walks with you** and notes your time at the start and end             | **Interceptor**: timing, logging, wrapping the result |
| **Bag scanner** that rejects prohibited items or repacks your luggage                   | **Pipe**: validates and transforms input              |
| **Boarding the plane**: the actual purpose of the trip                                  | **Controller** (and the service behind it)            |
| **Airline desk** that handles anything that went wrong and tells you what to do         | **Exception filter**                                  |

Two airport truths map exactly:

1. **Everyone passes every station**, so a slow station slows the whole terminal (per-request cost).
2. **The order is fixed.** You can't be scanned for bags before you've shown a ticket (auth before validation), and a problem at any station sends you to the airline desk (filters).

## 3. The full order of execution

Official lifecycle order for a request (when all of these are present):

```txt
 1.  Incoming request
 2.  Middleware (global first, then module-bound)
 3.  Guards (global, then controller, then route)
 4.  Interceptors: BEFORE the handler (global, controller, route)
 5.  Pipes (global, controller, route, then route-parameter pipes)
 6.  Controller method (handler)
 7.  Service (called by the handler)
 8.  Interceptors: AFTER the handler (route, controller, global: REVERSE order)
 9.  Exception filters (route, controller, global), only if an exception was thrown
 10. Response sent to the client
```

### A picture with the "after" leg

```txt
 request ->  [Middleware] -> [Guard] -> [Interceptor pre] -> [Pipe] -> [Controller -> Service]
                                              |                                  |
 response <- [Interceptor post] <------------ +----------------------------------+

 any throw anywhere from Guard onward ----> [Exception filter] ----> error response
```

### Rules to remember

| Rule                                              | Detail                                                                                                                                                                                             |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Scope order is outside-in on the way in**       | Global, then controller, then route                                                                                                                                                                |
| **Interceptors "post" run in reverse**            | Because they wrap the handler like layers of an onion (they're built on RxJS observables)                                                                                                          |
| **Pipes run inside the handler call**             | Pipes execute as part of invoking the handler, _after_ interceptors' "before" code. So an interceptor's timing includes **pipe + controller + service** time, but **not** middleware or guard time |
| **Filters only run on exceptions**                | They don't run on the success path. They catch what's thrown from guards onward                                                                                                                    |
| **Middleware is outside Nest's handler pipeline** | It runs first and has no idea which handler will run                                                                                                                                               |

## 4. Each layer

### 4.1 Middleware

- A function (or class) with `(req, res, next)`: **the same as Express middleware**.
- Runs **before everything else** in the Nest pipeline.
- Has **no access to the execution context** (it doesn't know which controller or method will handle the request).
- Good for **raw HTTP concerns**: request ids, CORS, security headers, body-size limits, compression.
- **Body parsing is middleware.** Nest registers the JSON and URL-encoded body parsers for you (unless you disable them). This is the layer that produces **400 for invalid JSON** and **413 for oversized bodies**, **before any guard runs** (see `http-status-semantics.md`).

```ts
@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
  use(req: any, res: any, next: () => void) {
    req.id = req.headers["x-request-id"] ?? randomUUID();
    res.setHeader("x-request-id", req.id);
    next();
  }
}
```

### 4.2 Guards

- A class with `canActivate(context): boolean | Promise<boolean> | Observable<boolean>`.
- Answers **one question: may this request proceed to the handler?**
- Runs **after middleware**, **before interceptors and pipes**.
- Has access to the **execution context**, so it knows **which handler** is about to run and can read **metadata** (for example "this route is public").
- **Returning `false` produces a 403 Forbidden by default.** For a **401**, you must **throw `UnauthorizedException`**. (This is a classic mistake: a guard that returns `false` for a missing API key gives 403, but your Stage 1 contract says **401**.)

```ts
@Injectable()
export class ApiKeyGuard implements CanActivate {
  private readonly keys = parseKeyMap(process.env.API_KEYS); // Map<apiKey, tenantId>, built once

  canActivate(ctx: ExecutionContext): boolean {
    const req = ctx.switchToHttp().getRequest();
    const header = req.headers["authorization"];
    const key =
      typeof header === "string" && header.startsWith("Bearer ")
        ? header.slice(7)
        : undefined;
    const tenantId = key ? this.keys.get(key) : undefined;
    if (!tenantId) throw new UnauthorizedException(); // 401, not `return false` (403)
    req.tenantId = tenantId; // hand the tenant to later layers
    return true;
  }
}
```

### 4.3 Interceptors

- A class with `intercept(context, next)` that returns an **RxJS Observable**.
- Code **before** `next.handle()` runs **before the handler**; operators on the returned observable (`tap`, `map`, `timeout`) run **after** it.
- Good for: **timing/metrics**, **logging**, **response mapping** (wrapping results in an envelope), **timeouts**, **caching**.
- They **wrap** the handler, so they can see both input and output.

```ts
@Injectable()
export class TimingInterceptor implements NestInterceptor {
  intercept(_ctx: ExecutionContext, next: CallHandler): Observable<any> {
    const t0 = process.hrtime.bigint();
    return next
      .handle()
      .pipe(
        finalize(() =>
          handlerSeconds.observe(Number(process.hrtime.bigint() - t0) / 1e9),
        ),
      );
  }
}
```

### 4.4 Pipes

- A class with `transform(value, metadata)`.
- Two jobs: **validate** (throw if bad) and **transform** (convert input, for example string to number).
- Run on each **handler parameter**: `@Body()`, `@Query()`, `@Param()`.
- The built-in **`ValidationPipe`** uses **`class-validator`** (rules from decorators on a DTO class) and **`class-transformer`** (turns plain JSON into a class instance). On failure it throws **400** by default.
- **Applied only when the parameter has a class type** (see the metadata caveat in section 9).

### 4.5 Controller (and service)

- The controller maps **HTTP to your logic**: reads params, calls the service, returns a value (Nest serializes it as the response).
- Keep it **thin**: no business logic, no SQL. The **service** calls `pg.Pool`.
- Status code comes from the decorator (`@HttpCode(202)`). **POST defaults to 201** unless overridden.

### 4.6 Exception filters

- A class with `catch(exception, host)` marked `@Catch(...)`.
- Runs **only when something throws** (from guards onward).
- Turns an exception into an HTTP response: status, body, headers.
- Nest has a **built-in global filter**: `HttpException`s become their status and body; **anything else becomes a generic 500**.
- You add your own to produce the **consistent error body** and the **503 + Retry-After** mapping (see `http-status-semantics.md`).

### Binding scopes (where you attach each)

| Layer       | Global                                      | Controller              | Route                    |
| ----------- | ------------------------------------------- | ----------------------- | ------------------------ |
| Middleware  | `app.use()` or module `configure()`         | n/a (route patterns)    | route patterns           |
| Guard       | `app.useGlobalGuards()` or `APP_GUARD`      | `@UseGuards()` on class | `@UseGuards()` on method |
| Interceptor | `APP_INTERCEPTOR` / `useGlobalInterceptors` | `@UseInterceptors()`    | method                   |
| Pipe        | `APP_PIPE` / `useGlobalPipes`               | `@UsePipes()`           | method / parameter       |
| Filter      | `APP_FILTER` / `useGlobalFilters`           | `@UseFilters()`         | method                   |

> **DI tip:** registering globals with `app.useGlobal...()` happens **outside** the dependency-injection container, so those instances **can't inject services**. Use the **`APP_GUARD` / `APP_PIPE` / `APP_INTERCEPTOR` / `APP_FILTER`** provider tokens when a global layer needs injected dependencies.

### Skipping a guard for some routes (health checks)

```ts
export const Public = () => SetMetadata("isPublic", true);

// inside the guard:
const isPublic = this.reflector.getAllAndOverride<boolean>("isPublic", [
  ctx.getHandler(),
  ctx.getClass(),
]);
if (isPublic) return true;
```

Mark `/healthz` and `/readyz` with `@Public()` so a global API-key guard doesn't block the orchestrator.

## 5. What belongs where

| Concern                                               | Put it in                                      | Why                                        |
| ----------------------------------------------------- | ---------------------------------------------- | ------------------------------------------ |
| Body size limit, JSON parsing, CORS, security headers | **Middleware** (or the proxy)                  | Raw HTTP, independent of handlers          |
| Request id / correlation id                           | **Middleware**                                 | Needed by everything after it              |
| **Authentication** (who are you?)                     | **Guard**                                      | "May this proceed?" runs before validation |
| **Authorization** (are you allowed?)                  | **Guard**                                      | Same                                       |
| **Rate limiting** (Stage 5)                           | **Guard** (or middleware at the edge)          | A yes/no decision made early and cheaply   |
| Request timing, metrics                               | **Interceptor**                                | Wraps the handler; sees before and after   |
| Per-request logging                                   | **Interceptor** (but **off** during load runs) | Logging volume distorts results            |
| **Validation of input**                               | **Pipe**                                       | Input checking and conversion              |
| **Transform input** (types, defaults)                 | **Pipe**                                       | Same                                       |
| Response envelope / mapping                           | **Interceptor**                                | Sees the handler's result                  |
| Mapping errors to HTTP responses                      | **Exception filter**                           | Single place for the error contract        |
| HTTP details (status code, params)                    | **Controller**                                 | Thin adapter                               |
| Business logic, DB access                             | **Service**                                    | Testable, reusable                         |

### The deciding questions

```txt
 "May this request proceed at all?"                 -> Guard
 "Is this data well-formed / convert it?"           -> Pipe
 "I want to do something before AND after it runs"  -> Interceptor
 "This is raw HTTP plumbing"                        -> Middleware
 "Something threw: what should the client see?"     -> Filter
```

### Why order matters for EventPulse

```txt
 bad key + bad body   ->  401 (guard) not 400 (pipe)        auth before validation
 good key + bad body  ->  400 (pipe), zero DB writes        S1-F2: invalid events never touch the DB
 good key + good body ->  controller -> service -> pg.Pool -> 202
 DB down              ->  service throws -> filter -> 503 + Retry-After
```

## 6. Exceptions and filters

Anything thrown from a **guard, interceptor, pipe, controller, or service** travels to the **exception filters**. The first matching filter handles it (route-level, then controller-level, then global).

```txt
 guard throws UnauthorizedException   --\
 pipe throws BadRequestException       --+--> exception filter --> HTTP response
 service throws (pool timeout, etc.)  --/
```

### Where errors come from, and who answers

| Source                                                | Typical exception                                          | Result                                                                                       |
| ----------------------------------------------------- | ---------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Guard rejects                                         | `UnauthorizedException` (401) / `ForbiddenException` (403) | Built-in filter or yours                                                                     |
| ValidationPipe fails                                  | `BadRequestException` (400) with a list of messages        | Built-in filter or yours                                                                     |
| Controller/service throws `HttpException`             | its own status                                             | Same                                                                                         |
| Service throws a **non-HTTP error** (pg timeout, bug) | plain `Error`                                              | Built-in filter: **500**; **your filter** should map known transient ones to **503**         |
| Body parser (invalid JSON, too large)                 | error produced in middleware                               | Becomes 400/413, but **its response body may not match your custom error shape** (see below) |

> **Check this in your tests:** errors raised by the **body parser middleware** may be answered by the framework's default error handling rather than your custom filter, so their JSON body shape may differ from your standard error body. Add a contract test that sends invalid JSON and an oversized body and **inspects the response body**. If the shape differs, decide how to normalize it.

### Exception handling is also a performance topic

Throwing exceptions is **much more expensive than returning** (stack trace capture). Under a flood of invalid requests (a 400 storm), **creating exception objects** is part of your CPU cost. Another reason to reject bad traffic **early and cheaply** (and to rate limit in Stage 5).

## 7. The EventPulse ingest request

Your Stage 1 service mapped onto the lifecycle:

```txt
 POST /v1/events   (k6)
   |
   | [Middleware]  body-parser: read bytes, JSON.parse         -> 400 invalid JSON / 413 too large
   |
   | [Guard]       ApiKeyGuard: Authorization header -> tenant  -> 401
   |               (static Map from env, no DB call)
   |
   | [Interceptor] (optional) timing/metrics
   |
   | [Pipe]        ValidationPipe on CreateEventDto
   |               plainToInstance + class-validator rules       -> 400, zero DB writes
   |
   | [Controller]  EventsController.ingest()  @HttpCode(202)
   |
   | [Service]     EventsService.insert()  -> pg.Pool.query(INSERT ... ON CONFLICT DO NOTHING)
   |
   | [Interceptor] (post) record duration
   |
   v
 202 { "event_id": "..." }

 on any throw:  [Filter] DbErrorFilter -> 503 + Retry-After (pool timeout, DB down) | 500 | HttpException as-is
```

### Cost map of this path (what's _CPU_ and what's _waiting_)

| Layer                                     | Mostly...                                                                                                  |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Body parser (`JSON.parse`)                | **CPU** (scales with payload size)                                                                         |
| ApiKeyGuard                               | tiny **CPU** (header parse + Map lookup)                                                                   |
| ValidationPipe                            | **CPU** (object creation + per-field checks)                                                               |
| Controller/service glue                   | tiny **CPU**                                                                                               |
| `pg.Pool.query`                           | **mostly waiting** (pool queue, network, DB), plus driver CPU to serialize parameters and parse the result |
| Response serialization (`JSON.stringify`) | small **CPU**                                                                                              |

In **Stage 1** the **database and the pool dominate** latency (commit fsync, pool wait), so Node CPU is usually **not** the first bottleneck. But you must still capture the CPU breakdown now, because **in Stage 2 the DB leaves the request path** and then **this framework CPU becomes the new limit** (your Stage 2 K1 hypothesis).

## 8. CPU cost per layer

### Why it matters: one thread

All the layers above run **on the single JavaScript thread** (Stage 0 lesson). So:

```txt
 max requests per second per core  ~=  1 / (JS CPU time per request)
```

### Illustrative arithmetic (NOT measured; replace with your numbers)

| JS CPU per request | Ceiling per core |
| ------------------ | ---------------- |
| 50 µs              | 20,000 / s       |
| 100 µs             | 10,000 / s       |
| 200 µs             | 5,000 / s        |
| 400 µs             | 2,500 / s        |

Halving the CPU per request **doubles** the ceiling. This is why Stage 8 builds an **"overhead ladder"**: raw HTTP, then JSON parse, then validation, then auth, then the DB call, then the full Nest stack, measuring the CPU added by each rung.

### Where the per-layer cost comes from

| Layer                     | What it does per request                                    | Cost drivers                                                   |
| ------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------- |
| **Body parser**           | Reads bytes, `JSON.parse`                                   | **Payload size** (roughly linear)                              |
| **Middleware chain**      | Calls each function in turn                                 | Number of middleware; any work they do                         |
| **Guard**                 | Builds an execution context, runs your code, may `await`    | Your code; each `await` adds scheduling work                   |
| **Interceptor**           | Creates an RxJS observable pipeline around the handler      | RxJS overhead; closures and allocations                        |
| **Pipe (ValidationPipe)** | Class instantiation + metadata reads + per-field validators | **Payload shape, number of fields/decorators** (see section 9) |
| **Controller/service**    | Calls your methods                                          | Your code                                                      |
| **Response**              | Serialize with `JSON.stringify`, write headers              | Response size                                                  |
| **Filter**                | Only on errors: exception creation, formatting              | Error rate                                                     |

### The framework tax in one sentence

Nest's structure means **each request builds contexts, composes the layers (some async), and allocates short-lived objects**. Individually tiny, but **at thousands of requests per second the allocations also drive garbage collection** (the tail-latency effect from Stage 0 E0.10).

### Keep it in proportion

- Don't remove layers out of fear. They give you **structure, testability, and consistent behavior**.
- **Measure first.** Often 2-3 layers account for most of the framework cost (typically parsing and validation).
- The honest question is: _how much CPU does each layer cost, and is that a meaningful part of the per-request total?_ The optional experiment **B12** and Stage 8 answer it with data.

## 9. class-validator is not free

`ValidationPipe` is convenient, and it's usually **the largest single piece of framework CPU** on an ingest path. Here is why.

### What happens for each request

```txt
 1. Pipe gets the parsed JSON object (already parsed by body-parser)
 2. class-transformer: plainToInstance(CreateEventDto, value)
        -> creates a NEW class instance, copies properties, reads type metadata
 3. class-validator: validate(instance)
        -> looks up the DTO's stored validation metadata
        -> for EACH property, runs EACH decorator's validator function
        -> collects ValidationError objects (allocations) if any fail
 4. If errors: build a message array, throw BadRequestException (stack trace)
 5. Else: return the instance (or the original, depending on `transform`)
```

### Cost drivers

| Driver                               | Why                                                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`plainToInstance`**                | Extra object creation and property copying per request. It's **extra** work on top of the `JSON.parse` that already created the object                                                |
| **Per-decorator function calls**     | `@IsUUID()`, `@IsISO8601()` run **regex** checks; `@Length`, `@IsInt`, `@Min` each run a function. Five fields with several decorators means a dozen-plus validator calls per request |
| **Metadata lookups**                 | Reads validation metadata stored via `reflect-metadata`                                                                                                                               |
| **Whitelisting** (`whitelist: true`) | Extra pass to strip unknown properties                                                                                                                                                |
| **Nested objects / arrays**          | Each nested element is validated recursively: cost grows with payload shape                                                                                                           |
| **Failed validation**                | Building errors and throwing an exception costs **far more** than the success path                                                                                                    |
| **Large payloads**                   | More to copy and walk (but `@IsObject()` on a free-form `payload` is cheap, because it doesn't descend into it unless you add nested rules)                                           |

### Honest comparison (don't take numbers on faith)

- **Decorator-based validation** (class-validator) is built for **developer convenience**. It interprets rules **at runtime**, per call.
- **Compiled-schema validators** (for example Ajv-style libraries that **generate** a specialized validation function once at startup) are typically **faster per request**, often by a good margin. The size of the gap depends on your schema and library, so **measure on your DTO** (you'll do this in Stage 8, experiment **P3**).
- The trade-off: decorators are more ergonomic with Nest; compiled schemas need more wiring (a custom pipe) but cost less CPU.

### Things that reduce the cost _without_ changing libraries

| Lever                                                                        | Effect                                                                                                                              |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **`transform: false`** (if you don't need class instances or type coercion)  | Skips part of the transformation work (but validation still needs an instance internally in many setups; measure the actual effect) |
| **Validate the envelope strictly, leave the payload free-form**              | Cheap `@IsObject()` instead of deep nested rules                                                                                    |
| **Avoid regex-heavy decorators on hot fields when a cheaper check suffices** | Fewer expensive validators                                                                                                          |
| **Don't validate twice** (pipe _and_ service)                                | Duplicate work                                                                                                                      |
| **Keep the happy path allocation-light**                                     | Less GC                                                                                                                             |
| **Reject early** (size limit at the proxy)                                   | Cheaper failures                                                                                                                    |

(In Stage 1 you **don't tune** before recording the baseline. The point now is to **know that validation is a measurable cost center and to measure it.**)

### The silent failure: validation that never runs

`ValidationPipe` finds the DTO class through **TypeScript's emitted type metadata**. It only works if:

| Requirement                                                                | If violated                                                                             |
| -------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `emitDecoratorMetadata` and `experimentalDecorators` enabled in `tsconfig` | Metadata missing, **validation silently skipped**                                       |
| The DTO is a **class** (not an interface or type alias)                    | No runtime type to validate against                                                     |
| The DTO is **imported as a value**, not with `import type`                 | The import is erased; the parameter type becomes `Object`, so **no validation happens** |
| The parameter is typed with the DTO (`@Body() dto: CreateEventDto`)        | With `any`/`Object`, the pipe has nothing to validate                                   |

> **Always have a test** that sends an invalid body and asserts **400**. If validation silently doesn't run, bad events reach Postgres, and the `ON CONFLICT` and constraint errors become your "validation" (with 500s).

### Extra decorators that matter

- **`whitelist: true`** strips properties without a decorator; **`forbidNonWhitelisted: true`** rejects them with 400. Pick a policy and document it (unknown-fields behavior is part of your API contract).
- A DTO field with **no decorator** is unvalidated (and removed if whitelisting is on).

## 10. Other hidden costs

### Request-scoped providers (a big one)

Nest providers are **singletons by default**: one instance, created at startup. If you mark a provider **request-scoped** (a new instance per request), **every class that depends on it also becomes request-scoped**, all the way up the chain, including controllers.

| Scope                   | Instances             | Cost                                                                                            |
| ----------------------- | --------------------- | ----------------------------------------------------------------------------------------------- |
| **DEFAULT** (singleton) | One for the whole app | Near zero per request                                                                           |
| **REQUEST**             | One **per request**   | Allocation and DI resolution on every request. Nest's own docs warn it **degrades performance** |
| TRANSIENT               | One per consumer      | Some overhead                                                                                   |

**Rule of thumb for EventPulse:** keep everything **singleton**. Carry per-request data (like `tenantId`) on the **request object** (as the guard above does) or via `AsyncLocalStorage`, **not** by injecting a request-scoped provider.

### Logging

- Per-request logging (**especially `console.log` or a verbose logger**) is a **major** hidden cost and distorts benchmarks. Your Stage 1 requirement: **logging off by default during load runs**.
- Nest's built-in logger prints startup information; reduce it for runs: `NestFactory.create(AppModule, { logger: ['error', 'warn'] })`.

### Double JSON work

A request's body typically gets processed several times:

```txt
 bytes -> JSON.parse (body-parser) -> plainToInstance (copy) -> validate
       -> pg driver serializes params (payload object -> JSON string for jsonb)
       -> response JSON.stringify
```

That is **parse once, copy once, stringify at least once more**. It's a classic Stage 8 optimization target ("parse once, reuse"), and why **payload size** (B7) strongly affects CPU.

### Async hops

Every `await` or observable stage yields to the event loop and schedules continuations. A deep chain of async guards/interceptors adds **scheduling overhead** and slightly **raises latency under load**. Keep guards **synchronous when possible** (the sample guard above is), and don't put a **database call in a guard** (Stage 5 introduces a cache for exactly this reason).

### Reflection and DI at startup (not per request)

Nest does a lot of reflection and wiring **at bootstrap**. That cost is paid once. Per-request costs are mostly **context creation, async composition, and the work your layers do**.

## 11. Measuring the cost

Three complementary methods, all consistent with your Stage 0 methodology.

### Method 1: CPU microseconds per request (from metrics you already have)

Your Prometheus setup already exposes `process_cpu_seconds_total` and `http_requests_total`. Divide:

```txt
 CPU time per request (µs) = rate(process_cpu_seconds_total[1m]) / rate(http_requests_total[1m]) * 1e6
```

Compare across variants at the **same request rate**: raw Fastify `/health` from Stage 0, a minimal Nest route, Nest with the guard, Nest with the pipe, and the full ingest route (with the DB call stubbed out to isolate framework CPU). The **difference between variants** is each layer's cost.

> **Tip:** add an env flag such as `DB_MODE=stub` so the insert returns immediately. Then you can measure framework CPU without the database's waiting time. Record it as a diagnostic build, not the baseline.

### Method 2: Flame graphs (Stage 1 requires them)

Capture one at **~70% of the knee** and one **at saturation** (`0x` or `clinic flame`). Compare where CPU time goes: **framework, validation, JSON, the `pg` driver, GC**. In the flame graph, look for frames from:

| Frames you'll see                                                                                 | Layer                 |
| ------------------------------------------------------------------------------------------------- | --------------------- |
| `JSON.parse`, `body-parser`, `raw-body`                                                           | Body parsing          |
| `ValidationPipe.transform`, `ValidationExecutor`, `plainToInstance`, `TransformOperationExecutor` | **Validation**        |
| `RouterExecutionContext`, `GuardsConsumer`, `InterceptorsConsumer`, `rxjs`                        | Nest plumbing         |
| `Client.query`, `Pool`, `pg` internals, `Connection`                                              | pg driver             |
| `JSON.stringify`, `Buffer`, `write`                                                               | Serialization and I/O |
| `(garbage collector)`                                                                             | GC                    |

Wide frames are where CPU goes (Stage 0: width is time share).

### Method 3: A microbenchmark of the validation alone

Isolates `plainToInstance` + `validate` from everything else (script in section 13). It gives **µs per call**, which you can convert to a share of your per-request CPU.

### Interceptor timing caveat

A timing interceptor measures **pipes + controller + service + DB**, **not** middleware or guards (section 3). If you want total time, start a timer in **middleware** and read it in a response `finish` hook.

## 12. Express vs Fastify

NestJS runs on an **HTTP adapter**. The **default is Express**; **Fastify** is the alternative.

| Aspect                             | Express adapter             | Fastify adapter                                             |
| ---------------------------------- | --------------------------- | ----------------------------------------------------------- |
| **The Nest lifecycle (this note)** | Same layers, same order     | Same layers, same order                                     |
| Underlying HTTP handling           | Express middleware stack    | Fastify's request lifecycle and hooks                       |
| Raw speed                          | Slower in public benchmarks | Faster in public benchmarks                                 |
| Middleware ecosystem               | Huge (Express-style)        | Fastify plugins (some Express middleware needs equivalents) |

Key points:

- **Your code in guards, pipes, interceptors, and filters looks the same**, but anything touching raw `req`/`res` (like setting headers) uses **adapter-specific** objects, so code that assumes Express's `res.set()` needs adjusting on Fastify.
- Your **Stage 0 server was raw Fastify**, so **comparing Stage 0 `/health` with a Nest-on-Express `/healthz`** gives your first estimate of **framework + adapter overhead**.
- Switching to Fastify is the optional **B12** experiment (and a Stage 8 P2 experiment). **Don't assume** the gain: **measure** it.

### Probe 3: microbenchmark `class-validator`

```ts
// bench-validation.ts   (needs experimentalDecorators + emitDecoratorMetadata in tsconfig)
import "reflect-metadata";
import { plainToInstance } from "class-transformer";
import {
  validateSync,
  IsUUID,
  IsString,
  Length,
  IsISO8601,
  IsInt,
  Min,
  IsObject,
} from "class-validator";
import { randomUUID } from "node:crypto";

class CreateEventDto {
  @IsUUID() event_id!: string;
  @IsString() @Length(1, 100) type!: string;
  @IsISO8601() occurred_at!: string;
  @IsInt() @Min(1) schema_version!: number;
  @IsObject() payload!: Record<string, unknown>;
}

const input = {
  event_id: randomUUID(),
  type: "order.created",
  occurred_at: new Date().toISOString(),
  schema_version: 1,
  payload: { user: "u1", data: "x".repeat(300) },
};

const UUID_RE =
  /^[0-9a-f]{8}-[0-9a-f]{4}-[1-8][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/i;
const handWritten = (o: any) =>
  UUID_RE.test(o.event_id) &&
  typeof o.type === "string" &&
  o.type.length >= 1 &&
  o.type.length <= 100 &&
  !Number.isNaN(Date.parse(o.occurred_at)) &&
  Number.isInteger(o.schema_version) &&
  o.schema_version >= 1 &&
  typeof o.payload === "object" &&
  o.payload !== null;

function bench(name: string, fn: () => unknown, n = 200_000) {
  for (let i = 0; i < 20_000; i++) fn(); // warm-up (JIT)
  const t0 = process.hrtime.bigint();
  for (let i = 0; i < n; i++) fn();
  const nsPerOp = Number(process.hrtime.bigint() - t0) / n;
  console.log(
    `${name.padEnd(34)} ${(nsPerOp / 1000).toFixed(2)} µs/op   ~${Math.round(1e9 / nsPerOp).toLocaleString()} ops/s per core`,
  );
}

const body = JSON.stringify(input);
bench("JSON.parse (the body parser)", () => JSON.parse(body));
bench("plainToInstance only", () => plainToInstance(CreateEventDto, input));
bench("plainToInstance + validateSync", () =>
  validateSync(plainToInstance(CreateEventDto, input)),
);
bench("hand-written checks", () => handWritten(input));
```

Run it **pinned to one CPU** (`taskset -c 2 npx tsx bench-validation.ts`), several times, and note the spread (Stage 0 methodology). Interpret: add the validation µs/op to your estimate of total per-request CPU and see **what share** it is. Then try a **bad** input (for example an invalid UUID) and watch the **failure path** cost jump (errors are allocated).

> This is a **microbenchmark**: it shows relative magnitude, not your service's true cost. The flame graph at the knee is the real evidence.

## 15. Pitfalls checklist

- [ ] **Guard returns `false`** expecting 401 (it gives **403**). Throw `UnauthorizedException`.
- [ ] **POST returns 201** because `@HttpCode(202)` was forgotten.
- [ ] **Validation silently not running** (`import type`, missing `emitDecoratorMetadata`, `any` param type).
- [ ] **No test that sends an invalid body and expects 400.**
- [ ] **Assuming guards run before the body is parsed** (body parsing is middleware and runs **first**).
- [ ] **Global layers created with `useGlobal*()` that need injected services** (use `APP_*` tokens).
- [ ] **A DB call inside a guard** (puts the database back in front of every request, even rejected ones).
- [ ] **Request-scoped providers** spreading up the dependency chain.
- [ ] **Per-request logging on during load tests.**
- [ ] **Validating twice** (pipe and service) or **parsing the body twice**.
- [ ] **Putting business logic in controllers or guards.**
- [ ] **Forgetting health routes need `@Public()`** with a global guard.
- [ ] **Assuming an interceptor timer includes guard and middleware time.**
- [ ] **Not normalizing the error shape** from body-parser errors vs your filter's.
- [ ] **Measuring one build and calling the framework "slow" or "fast" without a flame graph.**
- [ ] **Optimizing the framework before recording the baseline** (Stage 1 rule: untuned baseline first).

## 16. Common confusions

**"Guards run before the body is parsed."**
No. Body parsing is **middleware**, which runs first. A broken or oversized body can fail **before** the guard.

**"Pipes run before interceptors."**
The interceptor's **before** code runs first, then the pipes (as part of invoking the handler), then the controller, then the interceptor's **after** code.

**"Filters run on every request."**
Only when an exception is thrown.

**"A guard returning `false` gives 401."**
It gives **403** by default. Throw `UnauthorizedException` for 401.

**"Interceptors and middleware are the same."**
Middleware is raw Express-style plumbing with no handler knowledge. Interceptors know the handler, wrap it, and see before **and** after.

**"`ValidationPipe` is just a quick check."**
It creates a class instance and walks metadata and decorators per field, so it's **real per-request CPU**.

**"Decorators have no runtime cost."**
The decorators register metadata at startup, but **using** them (validation, DI resolution, guards) happens **per request**.

**"NestJS is slow, so I should drop it."**
The framework tax is real but usually **smaller than the DB or I/O** in Stage 1. **Measure the share** before deciding. The Stage 8 comparison exists precisely to answer this.

**"Singleton providers are shared state problems."**
Singletons are fine if they're **stateless** (the pool, the key map). Don't store per-request data in them.

**"Adding another interceptor is free."**
Each adds closures, RxJS operators, and allocations. Cheap one at a time, not free at 10,000 requests per second.

## 17. Self-test questions

Answer aloud first. Answers are below.

1. List the order of execution of the NestJS layers for a successful request.
2. A request arrives with an invalid JSON body and no API key. What status do you get, and which layer produced it?
3. How do you make a guard return **401** instead of 403?
4. Where should input validation live, and why must it run after authentication?
5. Why do interceptors' "after" phase run in reverse order?
6. What does a timing interceptor measure and what does it miss?
7. Name three reasons `class-validator` costs CPU on every request.
8. Your invalid events are reaching Postgres and causing 500s. Name two likely causes in the Nest setup.
9. Why does per-request CPU time matter so much in a Node service?
10. Why is a database call inside a guard a bad idea?

<details>
<summary>Answers</summary>

1. Middleware, guards, interceptors (before), pipes, controller (and service), interceptors (after, reverse order). Exception filters run only if something throws.
2. Likely **400** (or 413 if oversized), produced by the **body-parser middleware**, which runs **before** guards, so the missing key never gets a chance to cause 401. (Check the response body shape: it may not match your custom error format.)
3. Throw `UnauthorizedException` inside `canActivate`. Returning `false` yields 403.
4. In a **pipe** (`ValidationPipe` with a DTO). Guards run before pipes, and you want to reject unauthenticated callers cheaply **without** spending validation CPU on them, and not leak validation details to them.
5. Interceptors wrap the handler like layers of an onion (built on RxJS), so the outermost interceptor's "after" code runs last, in reverse of the "before" order.
6. It measures the time from its "before" code through the handler's completion: pipes + controller + service + DB. It **misses middleware (including body parsing) and guard time**.
7. Any three of: `plainToInstance` creates a new object (extra copy); each field runs one or more validator functions (including regexes for UUID/ISO date); metadata lookups via reflection; whitelisting passes; recursive nested validation; building and throwing errors on failure.
8. Validation not actually running: `import type` erasing the DTO, `emitDecoratorMetadata`/`experimentalDecorators` off, the parameter typed as `any`/`Object`, or the ValidationPipe not registered globally or on that route.
9. All layers run on the single JS thread, so the ceiling per process is about 1 / (CPU time per request). Reducing per-request CPU raises throughput proportionally and reduces GC pressure and tail latency.
10. It puts the database back in the path of **every** request, including those that will be rejected, so a slow DB slows even unauthenticated traffic and holds pool connections. Use a static map (Stage 1) or a cache (Stage 5) instead.

</details>

## 18. Glossary and cheat sheet

| Term                        | Meaning                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------ |
| **middleware**              | Express-style `(req, res, next)` function that runs first, with no handler knowledge |
| **guard**                   | Decides whether a request may proceed (`canActivate`)                                |
| **interceptor**             | Wraps the handler (RxJS) to run logic before and after it                            |
| **pipe**                    | Validates and/or transforms handler input                                            |
| **filter**                  | Converts thrown exceptions into HTTP responses                                       |
| **controller**              | Maps HTTP routes to your logic                                                       |
| **provider / service**      | Injectable class holding logic or resources (singleton by default)                   |
| **DTO**                     | Data Transfer Object: a class describing and validating input                        |
| **ExecutionContext**        | Object giving a guard/interceptor access to request, handler, and class              |
| **`APP_GUARD` etc.**        | Tokens to register global layers with DI support                                     |
| **request-scoped provider** | Provider created per request; slower, spreads up dependencies                        |
| **`class-validator`**       | Library validating DTOs using decorators                                             |
| **`class-transformer`**     | Library converting plain objects into class instances                                |
| **HTTP adapter**            | Underlying server integration (Express or Fastify)                                   |
| **framework tax**           | CPU overhead per request from Nest's layers                                          |
| **overhead ladder**         | Measuring the cost added at each rung (Stage 8)                                      |

### Cheat sheet

```txt
ORDER:  Middleware -> Guard -> Interceptor(before) -> Pipe -> Controller/Service
        -> Interceptor(after, reverse) ;  Filter only on exceptions

middleware  = raw HTTP (body parse: 400 bad JSON / 413 too big, BEFORE guards)
guard       = "may proceed?"  throw UnauthorizedException (401); return false = 403
interceptor = wrap handler (timing, logging, mapping); timer misses middleware + guard time
pipe        = validate/transform input (ValidationPipe -> 400)
controller  = thin; @HttpCode(202) (POST defaults to 201)
filter      = errors -> responses (503 + Retry-After for pool/DB; consistent body)

auth BEFORE validation: bad key + bad body = 401, not 400
invalid event => 400 from the pipe, zero DB writes (S1-F2)

COST: all layers run on ONE thread  ->  max rps/core ~ 1 / (CPU per request)
biggest framework cost usually: JSON parse + class-transformer + class-validator
validation silently skipped if: import type / no emitDecoratorMetadata / param typed any
keep providers SINGLETON; no request-scoped; no DB call in guard; logging OFF in load runs
measure: CPU µs/request = rate(process_cpu_seconds_total)/rate(http_requests_total)
        + flame graph at 70% knee and at saturation + microbench of the pipe
Stage 1 = DB-bound (framework not first limit) ; Stage 2 = framework CPU becomes the ceiling
```

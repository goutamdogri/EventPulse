## 1. TL;DR

- `pg.Pool` keeps a **small, fixed-size set of open Postgres connections** and **lends** them to your code. Each connection is a real Postgres backend **process** (see the process-per-connection notes).
- When all connections are busy, new requests **wait in a queue inside your Node process**. That queue is cheap for Node but it is **where latency hides**.
- Defaults are **dangerous for a service**: **`max = 10`**, and **`connectionTimeoutMillis = 0`, which means "wait forever"**. There is also **no limit on how long the waiting queue can grow**.
- **Request latency = pool wait + query time + overhead.** Always measure the two parts separately.
- **Throughput ceiling = pool size / query time.** A slow database lowers it one-for-one.
- Always **release** a client you checked out (use `try/finally`), always handle the pool's **`'error'` event**, and **never run a transaction through `pool.query`**.
- **Total connections = (number of Node processes) x (pool `max`)**, plus everything else that connects.

> **One-line version:** _`pg.Pool` is a bounded set of expensive Postgres connections plus an unbounded waiting line, so you must put timeouts and limits on the line yourself._

## 2. The mental model

Think of a **taxi rank** with a fixed number of taxis.

| Taxi rank                                                                                  | `pg.Pool` / Postgres                              |
| ------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| A fixed fleet of taxis (say 10)                                                            | `max` connections                                 |
| Each taxi is expensive to buy and run                                                      | Each connection is a Postgres **backend process** |
| A passenger takes a taxi, rides, and the taxi returns to the rank                          | `pool.connect()` ... `client.release()`           |
| If no taxi is free, passengers **queue at the rank**                                       | Requests wait in the pool's **pending queue**     |
| The rank has **no limit** on queue length by default, and passengers will wait **forever** | `connectionTimeoutMillis = 0` and no queue cap    |
| A long ride (slow query) keeps a taxi away for longer, so the line grows                   | Slow queries shrink the throughput ceiling        |
| A passenger who **forgets to return the taxi** removes it from the fleet permanently       | **Client leak** (forgetting `release()`)          |
| Taxis idle for too long are sent home                                                      | `idleTimeoutMillis` closes idle connections       |

The point of the rank: **a few busy taxis serve many passengers well, while hundreds of taxis jam the road** (the same lesson as "more connections hurt" from the Postgres notes).

## 3. Client vs Pool vs PoolClient

Three objects, easy to mix up:

| Object           | What it is                                                          | Typical use                                         |
| ---------------- | ------------------------------------------------------------------- | --------------------------------------------------- |
| **`Client`**     | **One** connection to Postgres                                      | Rarely used directly in a service                   |
| **`Pool`**       | A **manager** of many `Client`s: creates, lends, recycles them      | **One shared instance** per Node process            |
| **`PoolClient`** | A `Client` **checked out** from the pool, with a `release()` method | Returned by `pool.connect()`; used for transactions |

Important properties of a single `Client`:

- It runs **one query at a time**. If you call `client.query()` several times concurrently on the same client, the calls are **queued inside the client** and run **one after another**. That is not parallelism.
- **Parallel queries need multiple clients**, which is exactly what the pool provides.
- Session state (`SET ...`, an open transaction, named prepared statements) belongs to **that one connection**.

```txt
 your code  --pool.query()-->  [ Pool ]  --picks a free Client-->  Postgres backend process
                                  |
                                  +-- no free Client? -> wait in pending queue
```

## 4. The lifecycle of a checkout

What happens when your code runs `pool.query(...)` or `pool.connect()`:

```txt
 request wants a connection
        |
        v
 +---------------------------+   yes   +--------------------------------+
 | Is an IDLE client free?   |-------->| hand it over immediately       |
 +---------------------------+         +--------------------------------+
        | no
        v
 +---------------------------+   yes   +--------------------------------+
 | totalCount < max ?        |-------->| open a NEW connection          |
 +---------------------------+         | (TCP + auth + Postgres FORK)   |
        | no                           | then hand it over              |
        v                              +--------------------------------+
 +---------------------------+
 | Join the PENDING QUEUE    |  <- waiting here counts toward waitingCount
 | (FIFO)                    |     and toward connectionTimeoutMillis
 +---------------------------+
        |
        |  a client is released (or a slot frees up)
        v
 hand the client to the oldest waiter
```

And on the way back:

```txt
 client.release()   ->  back to idle list  (or handed straight to the next waiter)
                        after idleTimeoutMillis of sitting idle -> closed (if above min, when supported)
 client.release(err) -> if err is truthy, the client is DESTROYED instead of reused
```

Key facts:

- Connections are created **lazily**, on demand, up to `max`. A fresh pool has **zero** connections.
- Creating a new connection is **slow** (milliseconds to tens of ms), so the first requests after startup or after an idle period are slower. This is the "cold pool" effect that shows up in your warm-up period.
- When a client is released and someone is waiting, the pool **hands it straight to the next waiter** without it ever becoming idle.
- Idle clients are closed after **`idleTimeoutMillis`**, which means connection counts can **drop and rebuild** across quiet periods (and can cause a latency bump when load returns).

## 5. Configuration options

Options you pass to `new Pool({...})`. Pool-specific options plus **client options passed through** to every connection.

### Pool options

| Option                                | Default              | What it does                                                           | Stage 1 advice                                     |
| ------------------------------------- | -------------------- | ---------------------------------------------------------------------- | -------------------------------------------------- |
| **`max`**                             | **10**               | Max connections in the pool                                            | Set from env. B2 sweeps it                         |
| `min` (newer versions)                | 0                    | Connections to keep open even when idle                                | Check your installed version supports it; optional |
| **`connectionTimeoutMillis`**         | **0 (wait forever)** | Max time to wait for a free connection **including** opening a new one | **Set it** (for example 1-5 s). B10 shows why      |
| **`idleTimeoutMillis`**               | 10000 (10 s)         | Close a client idle this long                                          | Know it exists; affects cold-start effects         |
| `maxUses`                             | unlimited            | Close a client after N checkouts                                       | Rarely needed                                      |
| `maxLifetimeSeconds` (newer versions) | disabled             | Recycle connections after an age                                       | Optional                                           |
| `allowExitOnIdle`                     | false                | Let the Node process exit when all clients idle                        | Mostly for scripts                                 |

### Client options passed through (very important)

| Option                                                | Default        | What it does                                                                            |
| ----------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------- |
| **`statement_timeout`**                               | none           | **Server-side**: Postgres cancels any statement running longer than this (milliseconds) |
| `query_timeout`                                       | none           | **Client-side** timer in Node for a query (the server may still be working)             |
| **`idle_in_transaction_session_timeout`**             | none           | Postgres kills a session idle inside a transaction too long                             |
| `lock_timeout`                                        | none           | Postgres gives up waiting for a lock after this long                                    |
| `application_name`                                    | none           | Label shown in `pg_stat_activity`: **set it** so you can recognize your connections     |
| `keepAlive`                                           | off            | TCP keepalive: helps detect dead connections                                            |
| `host`, `port`, `user`, `password`, `database`, `ssl` | env / defaults | Normal connection settings                                                              |

### The two dangerous defaults

```txt
 connectionTimeoutMillis = 0    -> a request can wait in the queue FOREVER
 statement_timeout       = none -> a slow query can hold a connection FOREVER
```

Together they turn **one slow dependency into hung requests, growing memory, and no error at all** (this is **B10, missing timeouts**). Your Stage 1 requirement says all limits must be configurable by environment variable. Make these explicit:

```ts
const pool = new Pool({
  host: process.env.PGHOST,
  port: Number(process.env.PGPORT ?? 5432),
  user: process.env.PGUSER,
  password: process.env.PGPASSWORD,
  database: process.env.PGDATABASE,

  max: Number(process.env.PG_POOL_MAX ?? 10),
  connectionTimeoutMillis: Number(
    process.env.PG_POOL_CONNECT_TIMEOUT_MS ?? 2000,
  ),
  idleTimeoutMillis: Number(process.env.PG_POOL_IDLE_TIMEOUT_MS ?? 10000),

  statement_timeout: Number(process.env.PG_STATEMENT_TIMEOUT_MS ?? 5000),
  idle_in_transaction_session_timeout: Number(
    process.env.PG_IDLE_TX_TIMEOUT_MS ?? 10000,
  ),
  application_name: "eventpulse-ingest",
});
```

> For B10, you will deliberately run **with timeouts unset** (default behavior), then **set sensible values** and repeat B3. Record both.

## 6. The three counters

The pool exposes three live numbers (in your `/debug/stats`):

| Property                | Meaning                                                 |
| ----------------------- | ------------------------------------------------------- |
| **`pool.totalCount`**   | Connections currently open (idle + in use), up to `max` |
| **`pool.idleCount`**    | Open but **not** currently lent out                     |
| **`pool.waitingCount`** | Requests **waiting in the queue** for a connection      |

Derived: **in use = totalCount - idleCount**.

### How to read them

| Picture                                                               | Meaning                                                               |
| --------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `waitingCount = 0`, `idleCount` high                                  | Pool bigger than needed                                               |
| `totalCount = max`, `idleCount = 0`, `waitingCount > 0`               | **Saturated**: demand exceeds the pool                                |
| `waitingCount` **growing steadily**                                   | Offered load is above capacity; the queue grows until timeouts cap it |
| `totalCount` < `max` and `waitingCount` > 0 briefly                   | New connections being opened (cold start)                             |
| `totalCount` stuck at `max` with `idleCount = 0` even at **low load** | **Client leak**: connections checked out and never released           |

### Pair the counters with Postgres (this is the key diagnosis)

| Pool says                            | Postgres says (`pg_stat_activity`)                  | Bottleneck                                                            |
| ------------------------------------ | --------------------------------------------------- | --------------------------------------------------------------------- |
| `waitingCount` high                  | **Few** active backends, mostly idle/CPU            | **Pool or app** (pool too small, or leak, or app holding connections) |
| `waitingCount` high                  | **Many** active backends, mostly waiting (IO, Lock) | **Postgres** (look at the wait event; a bigger pool won't help)       |
| `waitingCount` 0                     | Many active backends                                | Postgres busy, but the pool isn't limiting                            |
| `waitingCount` 0, latency still high | Few active                                          | Delay is elsewhere (Node CPU, network)                                |

## 7. Using the pool correctly

There are two ways to use a pool. Pick by whether you need **one connection across several statements**.

### Pattern A: `pool.query()` (single statement)

```ts
const res = await pool.query(
  'INSERT INTO events (event_id, tenant_id, ...) VALUES ($1, $2, ...) ON CONFLICT (event_id) DO NOTHING',
  [id, tenantId, ...],
);
```

- The pool **checks out a client, runs the query, and releases it automatically**, even on error.
- **Safe by construction**: no leak possible.
- Use for **every single-statement operation**, which includes your Stage 1 insert (autocommit).

### Pattern B: `pool.connect()` (several statements on one connection)

```ts
const client = await pool.connect();
try {
  await client.query("...");
  await client.query("...");
} finally {
  client.release(); // ALWAYS, in finally
}
```

- You get a **dedicated connection** until you release it.
- **You** are responsible for releasing it. Forgetting is a **leak**.

### Transactions: always Pattern B

`BEGIN`, your statements, and `COMMIT` **must all run on the same connection**. If you issued them with `pool.query`, each could go to a **different** connection and the transaction would not work.

```ts
async function withTx<T>(
  pool: Pool,
  fn: (c: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();
  let broken = false;
  try {
    await client.query("BEGIN");
    const result = await fn(client);
    await client.query("COMMIT");
    return result;
  } catch (err) {
    try {
      await client.query("ROLLBACK");
    } catch {
      broken = true;
    } // rollback failed -> connection is suspect
    throw err;
  } finally {
    client.release(broken); // truthy argument destroys the client instead of reusing it
  }
}
```

(Your Stage 1 baseline may not need transactions except in **B4**, where the insert and the counter update run in one transaction. Use this helper there.)

### Rules that prevent most pool bugs

| Rule                                                         | Why                                                                    |
| ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| **`release()` in `finally`, always**                         | Otherwise an exception leaks the connection                            |
| **Never `await` slow non-DB work while holding a client**    | Holds a scarce connection (and locks) idle; `idle in transaction` risk |
| **Transactions via `connect()`, never `pool.query`**         | Same-connection requirement                                            |
| **Keep checkout-to-release time short**                      | Holding time is the pool's "service time" in Little's Law              |
| **One shared pool per process**                              | Never create a pool per request                                        |
| `release(true)` / `release(err)` when a client may be broken | Destroys it so a bad connection isn't reused                           |

### Minor gotchas of the driver

- `pg` sends JavaScript **objects as JSON** (stringified), which suits a `jsonb` column.
- A JavaScript **array** is converted to a **Postgres array**, so for a **single `jsonb` column** pass `JSON.stringify(array)` yourself if you mean one JSON array value.
- `bigint` columns come back as **strings** by default (JS numbers can't hold them safely); `timestamptz` comes back as a `Date`.
- Parameters (`$1`, `$2`) are sent separately from the SQL text: safe against SQL injection and eligible for plan reuse.

## 8. Timeouts

There are **three different timeouts** at three different places. They protect against **different** problems, and you need all of them.

```txt
 request ---> [ POOL QUEUE ] ---> [ connection ] ---> [ statement running ] ---> [ lock waits inside it ]
               ^                                       ^                          ^
   connectionTimeoutMillis                       statement_timeout            lock_timeout
   (client-side, Node)                           (server-side, Postgres)      (server-side)
```

| Timeout                               | Where it acts    | Protects against                                 | If missing                                                                                                        |
| ------------------------------------- | ---------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| **`connectionTimeoutMillis`**         | Node pool queue  | Waiting forever for a free connection            | Requests hang; queue and memory grow without bound; clients time out first, but the server still holds their work |
| **`statement_timeout`**               | Postgres         | A slow query occupying a connection indefinitely | One slow statement can pin a pool slot; with a stuck lock, all slots                                              |
| `lock_timeout`                        | Postgres         | Waiting forever for a lock                       | Hot-row or DDL stalls turn into hangs                                                                             |
| `idle_in_transaction_session_timeout` | Postgres         | Abandoned open transactions                      | Locks held and vacuum blocked forever                                                                             |
| `query_timeout`                       | Node (per query) | A query that never returns                       | Mostly redundant with `statement_timeout`; the server may keep working after Node gives up                        |
| **HTTP server / client timeouts**     | Edge             | The caller waiting forever                       | Load generator and users hang                                                                                     |

**Prefer the server-side `statement_timeout`**: it actually **cancels** the query in Postgres and frees the backend. A Node-side timer only stops _waiting_.

### How the timeouts must nest

```txt
 client (k6) timeout   >   request budget   >   connectionTimeoutMillis + statement_timeout
```

If the pool timeout is longer than the caller's timeout, the caller gives up first while your server keeps queuing and doing work for a request nobody is waiting for. That is **wasted work during overload**, and it feeds retry storms (B9).

## 9. Capacity math

The pool is a **queue with `max` servers**. The Postgres notes derived the rule; here it is on the Node side.

```txt
 max throughput  =  pool max  /  seconds per query (checkout to release)
 busy connections needed  =  queries per second  x  seconds per query     (Little's Law)
```

| `max` | Time holding a connection | Throughput ceiling |
| ----- | ------------------------- | ------------------ |
| 10    | 2 ms                      | 5,000 / s          |
| 10    | 5 ms                      | 2,000 / s          |
| 10    | 50 ms                     | 200 / s            |
| 10    | 100 ms                    | **100 / s**        |
| 25    | 100 ms                    | 250 / s            |

**Holding time is the whole checkout, not just query execution**: it includes the **commit's WAL fsync**, any lock waits, and any other work you do while holding the client.

### What happens above the ceiling

Say the ceiling is 2,000 req/s and clients offer 3,000 req/s:

```txt
 excess  = 3,000 - 2,000 = 1,000 requests per second added to the queue
 queue (waitingCount) grows ~1,000 per second
 wait time grows ~ the same per second ... until connectionTimeoutMillis fires
 with a 2 s timeout: waiting ~ up to 2 s x arrival, then errors (503) start flowing
 the queue then plateaus; the system is "stable" but failing a third of the traffic
```

- With **no timeout** (`0`), the queue and latency grow **without bound** until memory or clients' own timeouts give out.
- This is also why **the knee is sharp**: as offered load approaches the ceiling, queueing delay explodes (Stage 0 "the knee").

### The in-flight requests link

HTTP in-flight requests = arrival rate x total latency (Stage 0 Little's Law). When the pool saturates, latency rises, so **in-flight requests pile up in Node memory**, each holding a request, a body, and a promise.

## 10. Choosing the pool size

| Direction     | What goes wrong                                                                                                |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| **Too small** | Pool saturates early; requests queue even though Postgres is idle                                              |
| **Too large** | Postgres thrashes (context switching, contention, memory); you may exceed `max_connections` when you scale out |

### Guidance

- Start at the default **10**, then **measure** (B2: 5, 10, 25, 50, 90, then above Postgres's limit).
- A common heuristic for the **database host**: about **(cores x 2) + disks**. Your Postgres container has 2 CPUs, so the useful active-connection count is **small**.
- Remember the **global budget**:

```txt
 total connections = (Node processes) x max  +  other services  +  admin tools   <  max_connections (100)
```

- Node being single-threaded does **not** mean you need a big pool. Node handles thousands of waiting requests cheaply; **a small pool plus a queue is the efficient design**. Waiting in the pool is far cheaper than waiting inside Postgres.
- When you scale out (Stage 2+ and Stage 7 with many API pods), shrink the per-process `max` or add **PgBouncer** (Stage 6).

### A sizing procedure

1. Hold Postgres CPU, disk, and workload constant.
2. Sweep `max`. For each value record: throughput, p99, `waitingCount`, Postgres CPU, active backends, context switches (`vmstat`), and top wait events.
3. Pick the **smallest** `max` at or near the best throughput. A flat top plateau means the extra connections are pure cost.

## 11. Failure behavior

Know what the pool does when the database misbehaves. This is **B8 (database restart under load)**.

### Common error messages

| Error (roughly)                                                          | Meaning                                                                     |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| `timeout exceeded when trying to connect`                                | `connectionTimeoutMillis` expired while waiting for or opening a connection |
| `Connection terminated unexpectedly`                                     | A connection died while in use (DB restart, crash, kill)                    |
| `connect ECONNREFUSED`                                                   | Nothing listening (DB down, restarting)                                     |
| Postgres `53300` / `sorry, too many clients already`                     | `max_connections` reached                                                   |
| Postgres `57014` / `canceling statement due to statement timeout`        | Your `statement_timeout` fired                                              |
| Postgres `57P01` / `terminating connection due to administrator command` | Server is shutting down or the backend was terminated                       |
| Postgres `40P01`, `40001`                                                | Deadlock / serialization failure (**retry**)                                |

(Match on **error codes** (`err.code`) where possible; matching message text is fragile.)

### Dead idle connections

```txt
 DB restarts  ->  all idle pooled connections are now dead sockets
              ->  the pool notices the socket error on an idle client,
                  emits 'error', and REMOVES that client
              ->  the next checkout opens a fresh connection
```

- **In-flight queries** on a dying connection reject with `Connection terminated unexpectedly`.
- If the network is **paused** (packets dropped, not refused), connects and queries can **hang** until a timeout fires. With `connectionTimeoutMillis = 0` they hang **forever**. This is why the Stage 1 plan includes a "network pause" variant of B8.
- `keepAlive: true` helps the OS notice dead peers sooner on idle connections.

### The pool `'error'` event: **must handle**

```ts
pool.on("error", (err) => {
  // An IDLE client emitted an error (e.g. server restarted).
  // If nobody listens to this event, Node treats it as unhandled and CRASHES the process.
  logger.error({ err }, "idle pg client error");
});
```

Without this handler, a database restart can take your **API process down**, which is a much worse failure than a few 503s.

### Recovery expectations (what to measure in B8)

| Measure              | Question                                                                               |
| -------------------- | -------------------------------------------------------------------------------------- |
| Error rate over time | How long are you failing after the DB comes back?                                      |
| Pool reconnect       | Does the pool recover on its own, or do dead clients linger?                           |
| Time to full success | Gap between "DB available" and "API success rate normal"                               |
| Row-count audit      | How many acknowledged vs stored (recall: no retries inside the server in the baseline) |

## 12. Mapping errors to HTTP

Your Stage 1 error contract says: **pool wait timeout or DB error returns 503 with `Retry-After`**. Implement it in an **exception filter**, classifying by cause.

| Cause                            | Detect by                                                                                           | HTTP                                            | Notes                                           |
| -------------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------- | ----------------------------------------------- |
| Pool wait timeout                | Error message `timeout exceeded when trying to connect` (or wrap `connect` in your own typed error) | **503** + `Retry-After`                         | Overload: tell the client to back off           |
| DB unreachable / connection lost | `ECONNREFUSED`, `Connection terminated unexpectedly`, class `08` / `57P01` codes                    | **503** + `Retry-After`                         | Transient                                       |
| `statement_timeout`              | code `57014`                                                                                        | **503** + `Retry-After`                         | The DB was too slow                             |
| Too many connections             | code `53300`                                                                                        | **503** + `Retry-After`                         | Capacity                                        |
| Deadlock / serialization         | codes `40P01` / `40001`                                                                             | 503 (or retry server-side later in the project) | Transient                                       |
| Invalid data reaching the DB     | class `22` codes (e.g. bad format)                                                                  | 400                                             | Should be caught by validation first            |
| Anything else                    | unknown                                                                                             | 500                                             | Log details, never leak internals to the client |

```ts
@Catch()
export class DbErrorFilter implements ExceptionFilter {
  catch(err: any, host: ArgumentsHost) {
    const res = host.switchToHttp().getResponse();
    const transient =
      /timeout exceeded when trying to connect/i.test(err?.message ?? "") ||
      ["ECONNREFUSED", "ETIMEDOUT"].includes(err?.code) ||
      ["57014", "53300", "57P01", "40P01", "40001"].includes(err?.code) ||
      String(err?.code ?? "").startsWith("08");
    if (transient) {
      res
        .status(503)
        .set("Retry-After", "1")
        .json({ error: "service_unavailable" });
    } else {
      res.status(500).json({ error: "internal_error" });
    }
  }
}
```

> **Retry-After** matters for **B9 (retry storm)**: clients that honor it with jitter drain the overload; clients that retry immediately sustain it.

## 13. Load shedding

The pool's queue is **unbounded**. `connectionTimeoutMillis` bounds how **long** someone waits, but not how **many** pile up. Under heavy overload that means a lot of memory and a lot of useless waiting.

A simple, powerful improvement is **admission control**: refuse new work **immediately** when the queue is already too long.

```ts
const MAX_WAITING = Number(process.env.PG_POOL_MAX_WAITING ?? 100);

async function query(text: string, params: any[]) {
  if (pool.waitingCount >= MAX_WAITING) {
    throw new OverloadedError(); // -> 503 + Retry-After, instantly, no DB work
  }
  return pool.query(text, params);
}
```

Why it helps (Little's Law again): bounding the queue **bounds the worst-case wait** to roughly `MAX_WAITING x service time / max`, instead of letting it grow until the timeout. Fast failure is cheap; slow failure ties up memory, sockets, and the client's patience. You will formalize the same idea as **load shedding and backpressure** in Stage 2 (the bounded micro-batcher) and as **rate limiting** in Stage 5.

(Stage 1 is the **naive baseline**: implement what the stage requires and **record how it collapses**. Treat shedding as a fix to test **after** the baseline, clearly labeled.)

## 14. Observability

You must be able to **separate pool wait from query time**. Wrap the pool:

```ts
async function timedQuery(text: string, params: any[]) {
  const t0 = process.hrtime.bigint();
  const client = await pool.connect(); // pool wait happens here
  const t1 = process.hrtime.bigint();
  try {
    return await client.query(text, params); // query time happens here
  } finally {
    client.release();
    const t2 = process.hrtime.bigint();
    poolWaitSeconds.observe(Number(t1 - t0) / 1e9);
    querySeconds.observe(Number(t2 - t1) / 1e9);
  }
}
```

(This costs a little extra versus bare `pool.query`, so measure its overhead once and record it. Note that it holds the client until after the metrics lines run; keep the work after `release()` trivial.)

### Metrics to export (Prometheus style)

| Metric                             | Type      | Meaning                                                           |
| ---------------------------------- | --------- | ----------------------------------------------------------------- |
| `eventpulse_pg_pool_total`         | gauge     | `pool.totalCount`                                                 |
| `eventpulse_pg_pool_idle`          | gauge     | `pool.idleCount`                                                  |
| `eventpulse_pg_pool_waiting`       | gauge     | `pool.waitingCount`                                               |
| `eventpulse_pg_pool_wait_seconds`  | histogram | Time to obtain a connection                                       |
| `eventpulse_pg_query_seconds`      | histogram | Time holding a connection (query + commit)                        |
| `eventpulse_pg_errors_total{kind}` | counter   | By class: pool timeout, connection lost, statement timeout, other |

  /* a client was checked out */

  /* a client was returned */

## 15. Wiring it into NestJS

Your Stage 1 plan has a "pool provider" and a service that injects it.

```ts
// db/pg-pool.provider.ts
import { Pool } from "pg";
import {
  Provider,
  OnApplicationShutdown,
  Injectable,
  Inject,
} from "@nestjs/common";

export const PG_POOL = Symbol("PG_POOL");

export const pgPoolProvider: Provider = {
  provide: PG_POOL,
  useFactory: () => {
    const pool = new Pool({
      /* options from env, section 5 */
    });
    pool.on("error", (err) => console.error("idle pg client error", err));
    return pool;
  },
};

@Injectable()
export class PgPoolShutdown implements OnApplicationShutdown {
  constructor(@Inject(PG_POOL) private readonly pool: Pool) {}
  async onApplicationShutdown() {
    await this.pool.end(); // waits for checked-out clients to be released, then closes all
  }
}
```

Points:

- **One provider = one pool = one instance** shared by all services in the process (Nest providers are singletons by default).
- Call `app.enableShutdownHooks()` in `main.ts` so `onApplicationShutdown` runs on SIGTERM (needed again in Stage 7 for graceful shutdown).
- **`pool.end()` waits for in-use clients**: if you leaked one, shutdown hangs. A good test of leak-freedom.
- **`/readyz` design:** the Stage 1 readiness check does a DB query. If it uses the **same pool** and the pool is saturated, readiness itself queues, times out, and (from Stage 7 on) Kubernetes marks the pod not ready, which is a self-inflicted outage during overload. Consider a **separate tiny pool** (`max: 1-2`) or a short timeout for health checks. Note this as a design question to record, and test it under B2.
- **`/healthz` (liveness)** should **not** touch the DB at all (Stage 7 rule).

## 16. Prove it yourself

Create a scratch folder with `pg` installed. Each script is small and teaches one behavior. (Use ESM: `"type": "module"` in `package.json`.)

### Script 1: watch the queue form (waves of completions)

```js
// pool-wave.mjs
import pg from "pg";
const pool = new pg.Pool({ max: 2, application_name: "pool-demo" });

const t0 = Date.now();
const jobs = Array.from({ length: 6 }, (_, i) =>
  pool
    .query("SELECT pg_sleep(1)")
    .then(() =>
      console.log(
        `query ${i} finished at ${((Date.now() - t0) / 1000).toFixed(1)}s | total=${pool.totalCount} idle=${pool.idleCount} waiting=${pool.waitingCount}`,
      ),
    ),
);
console.log(
  `right after submit: total=${pool.totalCount} idle=${pool.idleCount} waiting=${pool.waitingCount}`,
);
await Promise.all(jobs);
await pool.end();
```

**Expect:** with `max: 2` and 6 one-second queries, they finish in **waves**: two at ~1 s, two at ~2 s, two at ~3 s. `waiting` starts at **4**. That is the pool as a queue, made visible. Change `max` to 3 or 6 and watch the waves change.

### Script 2: `connectionTimeoutMillis` in action

```js
// pool-timeout.mjs
import pg from "pg";
const pool = new pg.Pool({ max: 1, connectionTimeoutMillis: 500 });

const hog = await pool.connect(); // take the only connection and sit on it
try {
  await pool.query("SELECT 1"); // no free connection: waits, then fails
} catch (e) {
  console.log("error after ~500ms:", e.message); // timeout exceeded when trying to connect
}
hog.release();
await pool.end();
```

Then set `connectionTimeoutMillis: 0` and run again: it **hangs forever**. That is the default behavior and the heart of B10.

### Script 3: leak a client

```js
// pool-leak.mjs
import pg from "pg";
const pool = new pg.Pool({ max: 3, connectionTimeoutMillis: 1000 });

for (let i = 0; i < 4; i++) {
  try {
    const client = await pool.connect(); // never released!
    await client.query("SELECT 1");
    console.log(
      `checked out ${i + 1}: total=${pool.totalCount} idle=${pool.idleCount} waiting=${pool.waitingCount}`,
    );
  } catch (e) {
    console.log(`checkout ${i + 1} failed:`, e.message);
  }
}
process.exit(0);
```

**Expect:** three succeed, the **fourth times out** even though you are doing no work: the signature of a leak (`idle = 0` at low load).

## 18. Pitfalls checklist

- [ ] **Unreleased clients** (no `finally`): pool silently shrinks to zero.
- [ ] **Transactions through `pool.query`**: statements land on different connections.
- [ ] **No `pool.on('error')` handler**: a DB restart can crash the process.
- [ ] **`connectionTimeoutMillis` left at 0**: requests hang forever.
- [ ] **No `statement_timeout`**: one slow query pins a connection.
- [ ] **Pool created per request** (or per module instance): connection explosion.
- [ ] **Raising `max` to "fix" latency** without checking Postgres CPU and wait events.
- [ ] **Forgetting the multiplier**: nodes x `max` can exceed `max_connections`.
- [ ] **Holding a client across `await` of non-DB work**: wasted connection time.
- [ ] **Timeouts not nested** (pool timeout longer than the caller's): wasted work during overload.
- [ ] **Blaming Postgres for pool queueing**: compare pool wait with query time.
- [ ] **Health checks on the same saturated pool**: readiness fails exactly when it matters.
- [ ] **Measuring a cold pool**: first requests open connections; exclude warm-up.
- [ ] **Logging per request during load runs**: distorts results.

## 19. Common confusions

**"`pool.query()` and `client.query()` are the same."**
`pool.query` borrows any free client for one statement and returns it. `client.query` runs on the specific connection you hold.

**"If I `await` several `client.query()` calls in parallel they run in parallel."**
No. One client runs one query at a time; the rest queue inside the client. Parallelism needs multiple clients.

**"The pool limits how many requests my server accepts."**
No. Node accepts all the HTTP requests; the pool only limits **simultaneous DB work**. The rest wait (in memory) in the pool queue.

**"A larger pool means more throughput."**
Only until Postgres saturates; beyond that it adds contention. The ceiling is also `pool / hold time`, so shortening hold time is often better than growing the pool.

**"`connectionTimeoutMillis` is how long a query may run."**
No. It's how long to wait **to get a connection**. Query duration is `statement_timeout`.

**"Pool wait time is database slowness."**
It's queueing in Node. Postgres may be idle at that moment.

**"A pooled connection is shared by many requests at once."**
It's lent to **one** user at a time, then returned.

**"`pool.end()` closes everything immediately."**
It waits for checked-out clients to be released. A leaked client makes shutdown hang.

**"The pool reconnects instantly and invisibly."**
Dead idle clients are removed when noticed and replaced on demand; in-flight queries on a dying connection still **fail** and need handling.

**"`release()` closes the connection."**
It **returns** it to the pool. `release(true)` (or with an error) is what destroys it.

## 20. Self-test questions

Answer aloud first. Answers are below.

1. What are the two dangerous `pg.Pool` defaults for a service?
2. What exactly does `pool.waitingCount` count, and where does that queue live?
3. Pool `max = 10`, each request holds a connection for 50 ms. What is the throughput ceiling?
4. Why can't you run `BEGIN ... COMMIT` using `pool.query`?
5. Why is the `'error'` event handler on the pool mandatory?
6. `waitingCount` is high, but Postgres shows few active backends. What's the bottleneck? What if Postgres shows many backends waiting on `Lock`?
7. What's the difference between `connectionTimeoutMillis` and `statement_timeout`?
8. You scale from 4 to 20 API pods with `max = 10`. What can go wrong?
9. After a DB restart under load, what happens to the pool's idle and in-flight connections?
10. Why might `/readyz` that queries the DB through the main pool be dangerous?

<details>
<summary>Answers</summary>

1. `connectionTimeoutMillis = 0` (wait forever for a connection, with no queue limit) and no statement timeout (a slow query can hold a connection forever). Also the default `max = 10` may not suit your database.
2. Requests waiting for a free connection. The queue lives **inside your Node process**, not in Postgres.
3. 10 / 0.05 = **200 requests per second** (the ceiling is pool size / holding time).
4. Each `pool.query` may use a different connection, so `BEGIN`, the statements, and `COMMIT` wouldn't share one session. Use `pool.connect()` and run them all on the same client, with `release()` in `finally`.
5. Idle clients can emit errors (for example when the server restarts). An `'error'` event with no listener is an unhandled event in Node and **crashes the process**.
6. Few active backends: the **pool or app** is the bottleneck, so Postgres is idle while requests queue. Many backends waiting on `Lock`: **Postgres contention** (such as a hot row); a bigger pool won't help and may hurt.
7. `connectionTimeoutMillis` is client-side and bounds the wait **to obtain** a connection from the pool. `statement_timeout` is server-side and cancels a **running** statement that takes too long.
8. Connections multiply: 20 x 10 = 200, exceeding `max_connections` (100), causing `too many clients already` errors. Reduce per-process `max`, or add PgBouncer.
9. Idle clients hold dead sockets; the pool gets an error, emits `'error'`, and removes them; new checkouts open fresh connections. In-flight queries fail with `Connection terminated unexpectedly`. With dropped packets and no timeout, connects and queries can hang.
10. Under overload the pool is saturated, so the readiness query queues behind other work and times out. Orchestration may then mark the pod not ready, turning overload into an outage. Use a separate tiny pool or a short timeout, and keep liveness DB-free.

</details>

## 21. Glossary and cheat sheet

| Term                                            | Meaning                                                       |
| ----------------------------------------------- | ------------------------------------------------------------- |
| **`Pool`**                                      | node-postgres manager of reusable connections                 |
| **`Client`**                                    | One connection to Postgres                                    |
| **`PoolClient`**                                | A client checked out from a pool; call `release()` when done  |
| **checkout**                                    | Borrowing a client from the pool                              |
| **pending queue**                               | FIFO line of requests waiting for a free client (inside Node) |
| **`max`**                                       | Maximum connections the pool will open                        |
| **`connectionTimeoutMillis`**                   | Max wait to obtain a connection (0 = forever)                 |
| **`idleTimeoutMillis`**                         | Time an idle client lives before being closed                 |
| **`statement_timeout`**                         | Server-side limit on a running statement                      |
| **client leak**                                 | Checked-out client never released                             |
| **holding time**                                | Checkout-to-release duration (the pool's service time)        |
| **admission control / load shedding**           | Rejecting work early when the queue is too long               |
| **`totalCount` / `idleCount` / `waitingCount`** | Open / idle / queued, the three live counters                 |

### Cheat sheet

```txt
pool        = bounded set of EXPENSIVE connections + UNBOUNDED waiting line (in Node)
1 pool connection = 1 Postgres backend process
defaults    : max=10, connectionTimeoutMillis=0 (FOREVER), no statement_timeout   <- set them!
latency     = pool wait + query time + overhead     -> measure both
ceiling     = max / holding time      (holding time includes commit fsync + lock waits)
total conns = Node processes x max + others   <  Postgres max_connections
pool.query()  = single statement, auto-release        | pool.connect() = multi-statement
transactions  = connect() + same client + release() in finally (release(true) if broken)
ALWAYS: pool.on('error', ...)   (else a DB restart can crash Node)
waitingCount high + few DB active   -> pool/app is the limit
waitingCount high + many DB waits   -> Postgres is the limit (bigger pool = worse)
totalCount==max, idle==0 at low load -> client LEAK
timeouts nest: client timeout > request budget > pool timeout + statement_timeout
overload fix: bound the queue (admission control) + 503 + Retry-After (+ jittered client backoff)
readiness: don't share the saturated pool; liveness: never touch the DB
```
